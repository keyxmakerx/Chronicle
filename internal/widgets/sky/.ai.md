# Sky Pane Widget

## Purpose

Renders the current world moment's sky for a campaign: sun position, moons
(phase, position, procedural surface), weather-driven look (clouds, fog,
rain/snow, storm darkening), stars, a decorative land silhouette, and small
visual overlays for the day's "moon-night" events (blood moon, magic surge,
conjunction, eclipse, harvest moon). It is the ambient, no-controls half of
Calendar V5's worldstate display — no hourglass, no per-entity binding, always
the campaign's default calendar (issue #763, part of Calendar V5 #741).

## Tier

**Widget** — reusable UI block with a thin Templ mount point and a client-side
JS module. Auto-mounted by `boot.js` on elements with
`data-widget="sky-pane"`.

## Dependencies

- **Uses:** `calendar` plugin — `CalendarService.GetDefaultCalendarForViewer`
  (server-side, resolves which calendar to mount) and the calendar's own JSON
  API (`GET /campaigns/:id/calendars/:calid`, `GET
  .../calendars/:calid/events`) client-side.
- **Uses:** `entities` plugin's `BlockRegistry` (`"skybox"` block type,
  `Addon: "calendar"`, `Contexts: ["template", "dashboard"]`, `Singleton:
  true`).
- **Used by:** the campaign dashboard and entity-page template layouts, via
  the `"skybox"` block; and the calendar (its own page and the Calendars
  page's unfolded preview), which docks the sky over its month through
  `SkyPane.Dock` — see "Docked in the calendar" below.

## Mount Syntax

```go
// Live pane — calendarID is the campaign's DEFAULT calendar, resolved
// server-side (never fetched client-side first):
@templates.Mount(campaignID, cal.ID)

// No default calendar yet, or the viewer may not see it — a quiet
// placeholder instead (do not call Mount with an empty calendarID):
@templates.Empty(campaignID)
```

Renders:

```html
<div data-widget="sky-pane" data-campaign-id="{cid}" data-calendar-id="{calid}" class="skypane">
  <div class="skypane-bar">
    <span class="skypane-title">Sky</span>
    <button type="button" class="skychip" aria-expanded="false" aria-controls="sky-pane-{calid}">
      <span class="sw" aria-hidden="true"></span>
      <span class="skychip-text">Today's sky</span>
    </button>
  </div>
  <div class="skywrap">
    <div class="sky" id="sky-pane-{calid}">
      <canvas></canvas>
      <p class="skycap" aria-live="polite">Loading the sky…</p>
    </div>
  </div>
</div>
```

`templates.MountID(calendarID)` returns `"sky-pane-" + calendarID` for a
caller that needs to point its own `aria-controls` at an existing mount
without re-deriving the format by hand.

## Configuration

| Attribute | Required | Description |
|-----------|----------|-------------|
| `data-campaign-id` | Yes | Campaign id — used to build the client's API fetch URLs. |
| `data-calendar-id` | Yes | The calendar to fetch and render (already resolved server-side; the widget never lists calendars to find it). |

No CSRF token: the widget only ever reads (`GET`), never writes.

## How It Works

### Frontend Behavior

1. **Mount**: `boot.js` calls `Chronicle.register('sky-pane', ...).init(el)`,
   which injects the pane's scoped `<style>` once (`sky-pane-styles`) and
   fetches `GET /campaigns/{cid}/calendars/{calid}` then `GET
   .../events?year=&month=` for the calendar's current month, filtered
   client-side to the events landing on the current day.
2. **Closed state**: `refreshPalette()` runs immediately (no canvas paint) —
   computes the chip's two-colour swatch and caption text ("weather · brightest
   moon & phase · time") so the collapsed chip still reflects "the sky now". A
   60s interval keeps this fresh even while the pane stays closed and open on
   a long-lived page.
2. **Open** (click the chip, or Enter/Space on it — a real `<button>`): the
   wrapper's height changes to `var(--skyH)` immediately (no transitioned
   layout property, ever — see Motion below), then a `requestAnimationFrame`
   adds `.sky-reveal`, which animates only `clip-path` from fully clipped to
   fully visible — a shade rolling down over the already-full-size canvas.
   `renderNow()` resizes the canvas to its CSS box (capped devicePixelRatio
   1–2) and draws the first frame.
3. **Render loop**: one shared `requestAnimationFrame` loop serves every
   open, on-screen (`IntersectionObserver`) sky-pane instance on the page — N
   panes cost one rAF tick, not N. An instance only re-renders every frame
   when its current state needs motion (`paceOf`: at least one moon is
   currently a blood moon tonight); otherwise it stays a still frame after
   `renderNow()`, since nothing else in the state changes fast enough to be
   worth a 60fps repaint.
4. **Close** (click again, or Escape): removes `.sky-reveal` (clip-path
   animates shut) and, after that transition's own duration (or
   instantly under reduced motion), removes `.sky-open` so the box collapses.
   Escape returns focus to the chip if focus was inside the pane.
5. **Resize**: debounced (`100ms`) canvas re-size while open; the closed pane
   does no canvas work at all.

### Rendering pipeline (per frame)

`sky_pane.js`'s `buildState(model, tSeconds)` is the one place the modules
above are composed:

1. `SkyWorld.hour24` + `SkyWorld.absoluteDay` place "now" on the calendar's
   own day/hour geometry.
2. `SkyWorld.makeSkym(cal).sun(...)` and `.moon(...)` compute the sun's and
   each visible moon's altitude/azimuth for that moment (`SkyWorld.PROJ`
   projects them onto a 270°-panorama).
3. `SkyEvents.parseDayEvents` + `.camFor` + `.overlaysFor` turn today's
   `MoonNightPayload` events into a camera-facing azimuth and a small set of
   overlay flags (blood/eclipse/harvest per moon id, conjunction groups, a
   magic tint).
4. `SkyLooks.spec/resolve` turns the calendar's `Weather` row into a look
   recipe; `SkyWorld.paletteFor` bakes the sun's altitude, that look, and the
   day/night split into the OKLab sky palette for this frame (optionally
   tinted for a "magic" event).
5. `SkyFX.sceneLight` and `SkyEvents.apply` add what moves: meteors,
   aurora, the bleeding blood moon, the world's shadow on an eclipsed moon,
   the harvest moon's warmth, the thread between conjunct moons.
6. `SkyGL.paint` paints it with the shared WebGL2 painter and copies the
   picture into the pane's canvas. When it returns false, `Sky2D.draw`
   paints the basic sky instead. Both use `MOONR.sprite` (via
   `SkyMoon.specFor`) for each moon's disc.

### Painted sky and the basic fallback

The basic sky draws whenever the painted one can't: no WebGL2, a browser
that would paint in software (`failIfMajorPerformanceCaveat`), a lost
context, a failed compile, and the first frames while the program compiles.
It also takes over for the rest of the session
(`sessionStorage["chronicle.sky.basic"]`) when a device paints slowly: two
frames in a row over 120ms, or a 45-frame average over 28ms while the sky
moves. Only the GPU pass and its copy are timed.

Pace: the painted sky repaints every frame while something visibly moves
(particles, rain or snow, meteors, a storm, aurora, a bleeding moon), 12
times a second while only clouds drift and stars twinkle, and never under
reduced motion. The basic sky moves only for a blood moon. Folded, off
screen or in a hidden tab, nothing is drawn.

### Scoped Styles

Injected once as `<style id="sky-pane-styles">`, mapped onto Chronicle's own
design tokens (`--color-*`, `--ease-*`, `--dur-*` from `static/css/input.css`)
rather than the design mockup's own palette names, so the pane matches the
rest of the app in both themes. `--skyH` (the open pane's height) is a
`clamp()` driven by a CSS container query (`container-type: inline-size` named
`cal`) so the pane sizes itself to the dashboard/entity block it sits in. The
`.dcard`/`.dsky`/`.dscrub`/`.dwx` rules (a day-card + weather band) are
ported here too, at the CSS layer only, ready for the day card's own sky
(TODO(#833)).

### Motion (issue #760)

The disclosure's box-model height change is instant, never transitioned —
only `clip-path` on the already-full-size `.sky` element animates, like a
shade rolling down. `prefers-reduced-motion: reduce` — and Chronicle's own
site-wide guard (`static/css/input.css`, a blanket `transition-duration:
0.01ms !important` under that same media query) — collapse the reveal to a
single instant frame and skip the continuous render loop entirely for a
reduced-motion viewer, rather than adding a redundant per-widget crossfade on
top of a guard that would clamp it to near-zero anyway.

## Data Flow

1. Widget mounts -> `GET /campaigns/:id/calendars/:calid` (the calendar, its
   months/weekdays/moons/weather — already viewer-gated server-side) ->
   `GET /campaigns/:id/calendars/:calid/events?year=&month=` (that month's
   events, already viewer-filtered server-side) -> client-side filter to
   today's events.
2. Every visible frame recomputes astronomy/palette/overlays from that same
   fetched snapshot plus the current wall-clock instant (no per-frame
   network call, no polling beyond the 60s closed-chip refresh).
3. No writes: the pane is read-only. World-state advancement (time, weather)
   happens elsewhere (the calendar plugin's own worldstate controls) and this
   widget simply reflects whatever the calendar's current date/weather says
   on its next fetch (page load / re-mount).

## Server-side seam: `renderSkyboxBlock` (`internal/app/routes.go`)

The `"skybox"` block resolves the campaign's default calendar server-side —
the widget itself never lists calendars — via
`CalendarService.GetDefaultCalendarForViewer`, gated exactly like every other
calendar read (ADR-049): a viewer built from the block's own
`CampaignContext`/`UserID` the same way `calendar.viewerFrom` builds one from
a request. Three outcomes:

| `GetDefaultCalendarForViewer` result | Rendered |
|---|---|
| A calendar (visible to this viewer) | `sky.Mount(campaignID, cal.ID)` |
| `apperror.NotFound` (no default calendar yet, OR one this viewer may not see — the two collapse identically) | `sky.Empty(campaignID)` |
| Any other error | logged (`slog.Error`) and `templ.NopComponent` — an ambient decoration block never turns a real infra error into a 500 |

## Docked in the calendar

The calendar (`static/js/widgets/calendar_view.js`) docks the sky flush at
the top of its card, over the month, as signed in the "Sky Pane" mockup
(#830). It builds its own markup (`#cal5-skywrap` before the header, the
**Sky** chip `#cal5-skybtn` leading the header's actions, styles in
`static/css/calendar-view.css`) and hands it to `new SkyPane.Dock({...})`,
which draws the sky and folds it. It never uses `Mount`, so it needs no
fetch of its own: `setDay(cal, events)` takes the calendar and today's
events the page already holds, both already filtered for this viewer
server-side (hidden moons, `dm_only` events). A player therefore sees
today as it is and nothing hidden.

- **The fold:** the chip folds the sky away like a window shade and opens
  it again. The pane's room changes at once; the card rides a transform so
  its top edge stays put while a clip hides what isn't there yet, and the
  sky is drawn whole into the strip that shows (`Sky2D.draw`'s `oy`), never
  cropped. Opening springs with a little give; closing is critically damped.
  Reduced motion only fades the sky in. While a phone's bulk bar, drawer or
  toast (`position:fixed` inside the card) shows, it folds without
  travelling, since a transform would carry them along.
- **Remembered per viewer:** `localStorage["chronicle.calendar.sky"] =
  "folded"`; open is the default. A private window just doesn't remember.
- **Size:** 14% of the card's width, from 100px (a phone's compact strip) to
  166px, set from script as `--skyH` because the card can't be a size
  container (its phone sheets are `position:fixed`).
- **Idle:** frames run only while the sky folds, fades, or animates a blood
  moon while showing. Folded, off screen or in a hidden tab, nothing is
  drawn and no animation frame is requested.
- **Tests:** `test/js/sky_dock.test.mjs`.

## Security

- **Read-only, viewer-gated at the source**: the widget issues plain `GET`s
  against the calendar plugin's own viewer-gated endpoints; it applies no
  visibility logic of its own and holds no elevated credentials. A hidden
  moon, a `dm_only` event, or a blanked linked-entity name is already filtered
  out before the JSON reaches the browser (see `calendar/service.go`'s
  `filterMoonsForViewer` / `eventVisibleToViewer` / `redactHiddenEntityLinks`).
- **`renderSkyboxBlock` fails closed on ambiguity**: NotFound (no calendar, OR
  a calendar this viewer may not see) always renders the same quiet
  placeholder — never distinguishes the two, so a block state can't be used to
  probe whether a hidden default calendar exists.
- **No CSRF surface**: no state-changing request originates from this widget.

## Disclosed deviations from the signed design contract

Ported from the sky-pane design mockup (artifact `TMkNkuGBUULZZxB6LyBfgd`) onto
Chronicle's real calendar/event data rather than the mockup's own Harptos
sample + generator engine:

- **Sky events need data the server doesn't send.** `MoonNightPayload` is
  `{type, moons:[ids]}` with five types (blood, magic, conjunction, eclipse,
  harvest), and no timing, so each holds at its peak while its moon is up.
  The mockup's comet, meteor-shower, aurora, solar-eclipse and custom-shape
  events need new payload types first (TODO(#870)). Weathers that carry
  aurora or fireballs (Luminous Sky, Meteor Shower) still show them, and a
  clear night still gets the odd shooting star.
- **Every "eclipse" is a lunar eclipse** of the named moons: the payload
  doesn't say solar or lunar.
- **Magic** tints the sky violet; the mockup has no matching event.
- **Land** is the mockup's own ridges in the painted sky; the basic sky
  keeps a per-calendar seeded ridge.
- **A moon's inclination** has no `calendar_moons` field, so it's derived
  from a hash of the moon's id/name. **Viewing latitude** is a fixed
  magnitude, sign-flipped by `Calendar.Hemisphere`.
- **Four moons are painted by the shader;** a fifth and later are drawn as
  sprites in the drawn layer, just in front of the painted moons.
