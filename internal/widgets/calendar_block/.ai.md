**Wave:** calendar-v4 wave 1, phase A (W-A) · dispatch `C-CALV4-BLOCK-P1`

## What this is

One plugin-agnostic widget package that renders a whole calendar as **four
zones**: A Nameplate · B Instrument · C docked Ledger · D Shelf. It imports
nothing from `internal/plugins/**` and never will — exactly the shape
`internal/widgets/calendar_v2` proves. Nothing here can collide with the
calendar plugin because it does not know the calendar plugin exists.

**There is no drawer.** The Ledger IS the drawer, permanently docked. Clicking a
day repaints a panel that is already on screen. Canon D9's 480px slide-in drawer
clause was STRUCK for this reason (canon amendment A3); it is why the Block &
Bench direction won its judging round.

## The three load-bearing decisions

### 1. Sizing is CSS, and it has to be

`boot.js:163` sets `htmx.config.allowScriptTags = false`, so a `<script>` inside
an HTMX-swapped fragment **never executes**. A JS-sized Block silently renders at
the wrong density after any swap. That is not a preference — a JS implementation
is broken by construction on this platform.

So: **size class is a container query on the host wrapper; density is a container
query on each cell.** There is zero JavaScript in this package.

| Thing | Where | Rule |
|---|---|---|
| size class | `.cal-block-host` (`container-name: cal-block`) | full ≥900 · std ≥300 · mini ≥240 · else sub-mini |
| density | each `.cell` (`container-name: cal-cell`) | measured column ≥84px → named chips, else underline |

`std` is the **unqueried baseline**, so a Block laid out before its container is
measured degrades to the middle class rather than to the widest.

`sizing.go` is the same arithmetic in Go. **Nothing in the render path calls it**
— it exists so `sizing_test.go` can pin the contract's model (the divergence
pair: Harptos 10 columns at host 1040 → 68.2px → underline; Gregorian 7 columns
at the same host → 97.4px → named).

### 2. Ten-day weeks are native

`--week-len` drives every column count and is written per month. There is no
literal 7 in the grid CSS and `TestCSS_NoLiteralWeekLength` keeps it that way
(every `repeat()` must take `var(--week-len)`; every `grid-template-columns` must
be a subgrid, a `--week-len` repeat, or the full-tier body split).

The **five-column rule** — the strong ramp step after column 5 — is read from the
producer's `Weekday.Half` / `DayCell.Half` flags, never re-derived from a week
length. It has **exactly two owners**, `.cell.half` and `.hd b.half`, pinned by
`TestCSS_TheFiveColumnRuleHasExactlyTwoOwners`. The `.halfrule` ruler that used
to be a third is gone with the band row it lived in (see "The tile" below).

**Era bands were PER WEEK ROW and the ROW IS DELETED** (C-CALV4-TILES §3,
2026-08-15). `EraBand` the struct and `Rows[].Bands` the data are untouched and
still load-bearing — `cellStyle` reads them to stamp `--erahue` on each day an
era covers, and deleting the data deletes the colour. Only the rendered caption
row went. The per-row cut still matters for that lookup: an era spanning days
1–17 is still described as one band per row it touches, because `cellEraToken`
matches `DayCell.Col` against a band's `StartCol`/`Span` **within its own row**.

### 3. Motion is a BUDGET, and it is exactly four items (W-B, 2026-07-28)

Wave 1 forbade motion outright and named W-B as the slice that re-opens the
question. It did, and what it opened is a budget rather than a permission.
`TestCSS_NoMotionAtAll` is now an **allowlist** — it was rewritten, not deleted,
and it still fails on everything outside the budget:

1. `background-color` and `color`, on the surfaces that ANSWER each other.
   Canon A5: ANSWERED "changes background-colour and ink hue ONLY. It never
   gains or loses shadow, never changes border thickness, never moves."
2. `transform: scaleX(var(--m-swell))` on a Ledger row's `.rail` — and **never
   on `.gr`**, the gold GM rail (cv4:435). A permission marker that animates
   reads as a state change. It is a transform rather than a width because
   `width:4px` on a flex item is a LAYOUT property (design notes §10 defect 3).
3. `m-latch` on the selected cell's ring: centre → corners, nothing slides.
4. **M5 non-target silence**, as a selector rather than a JS budget: rail and
   row transitions are killed unless the Block is `:hover` / `:focus-within` /
   `[data-swapping]`. **Adding Blocks must add RESTING cost only.**

All of it inside `@media (prefers-reduced-motion: no-preference)`. Under reduced
motion the colour change is instantaneous and every law still holds — which is
the proof that ANSWERED is a colour STATE and not an animation.

REFUSED, not omitted: `will-change` · `@starting-style` · `view-transition` ·
animating `box-shadow` apart from its ring (canon D3) · the `drawOnce()`
`--m-step` settle ladder, which is a JS post-repaint pass and there is no JS
here. **The month grid never moves** (2026-07-27 motion policy): the Ledger's
row filter is the ONE sanctioned content change and it is bounded to `.lrows`.

Two rules survived W-B and must survive everything after it:

- **canon guard B1** — `--dash` / `--gap` are NEVER animated. Morphing a dash
  pattern destroys the greyscale identity channel the signed greyscale render
  promises, and it is the obvious "improvement" the next hand reaches for.
- **canon D3** — the hover ring is a 0.5px spread carried INSIDE `box-shadow`, so
  a shadow animating alone is structurally impossible.

## The day cell is a TILE, and the tile is a PSEUDO-ELEMENT (C-CALV4-TILES, 2026-08-15)

The ruled treatment — a shared 1px hairline on every cell's right and bottom
edge — is gone. What replaced it is the reference's construction, measured:
**three flat steps and a gap.** The grid is the ground, the tile is a fill one
step off it, the tile's 1px rule is one step off the fill, and 3px of ground
shows between two tiles.

### Why the tile is `::before` and not the grid item — the container-query trap

`.cell` is simultaneously the grid item, the `container-type: inline-size`
subject, and the positioning context for six absolutely-positioned children.
**Anything that takes width off `.cell`'s content box moves every density
threshold**, and the obvious constructions all do:

| construction | subject at a 366px host, ten-day week |
|---|---|
| the old shared 1px right rule | 33.0px |
| `gap: 3px` on `.grid` + a 1px all-round border on `.cell` | **29.0px** |
| the tile on `.cell::before` | **34.0px** (measured, Chromium 141) |

`MoonSilhouetteColWidthMin` is **30px** — the std tier's column floor, and the
width the always-visible primary silhouette needs. The obvious construction
lands at 29 and **turns the moon back off on the operator's own phone**, which
is the exact defect this whole arc was opened to fix. It would ship green: the
probes that can see it are skipped under `-short`, which is what `make verify`
and `ci.yml` run.

Drawn inside the cell the tile costs the track nothing, and the subject actually
**gains** a pixel because the shared hairline goes away. The four container-query
thresholds (30 / 35 / 75 / 84) do not move.

```
.cell            { isolation: isolate; padding: 0; container-type: inline-size;
                   --tile-rule: oklch(from var(--cellbase) calc(l - 0.075) c h) }
.dark .cell      { --tile-rule: oklch(from var(--cellbase) calc(l + 0.058) c h) }
.cell::before    { content:''; position:absolute; inset:1.5px; z-index:-1;
                   border-radius:var(--r-ctl); border:1px solid var(--tile-rule) }
```

Three things about that are load-bearing and each is pinned:

- **`isolation: isolate`.** Without a stacking context on `.cell` the tile's
  `z-index: -1` escapes to the nearest ancestor context and paints *behind*
  `.grid`'s ground — i.e. nowhere. Nothing inside a cell needs to escape it
  (every z-index there is 0/1/2 and all of them are relative to each other), so
  the containment costs nothing.
- **`.cell` PAINTS NOTHING ITSELF.** Its box IS the grid track, so any fill on
  the element covers the 1.5px the tile insets and the gutter disappears. The
  whole fill chain therefore moved onto `::before`: the `--cellbase`/`--answer`
  expression (§ANSWERED), the hover wash, `.cell.fog`, and selection. `.interc`
  lost its long-dead `background: var(--surface-inset)` for the same reason —
  it had been losing to the answer wash's later `background-color` and would
  have started *winning* again the moment that rule moved.
- **The five-column rule survives as the ONE remaining border on `.cell`.**
  `.cell.half` keeps its `border-right`, drawn in the gutter between two tiles.
  That costs column 5 — and only column 5 — one pixel of subject: 33.0px against
  its neighbours' 34.0px, which is exactly what every column paid before.

Radius is `--r-ctl` (6px, the existing canon token; the reference measures ~6px).
No new scale value, and `TestCell_PopsAgainstItsOwnGround` verifies the token
still resolves to 6px rather than assuming it.

### The tile's RULE is derived, not borrowed — and the missing band was the defect

**The edge shipped at `--rule-structural` and that made it the loudest step in
the grid.** Measured in Chromium: **36.1 from the ground on light** (a 50/255
fill→rule step) and **39.7 on dark** — 3.6× and 2.3× the reference's +14, and
roughly **three times the era separation the same tile is framing** — on the one
surface the operator asked to make soft. `--rule-structural` is a general
STRUCTURAL rule token; a tile edge is not a structural rule and must not borrow
one.

**THE LAW, and it is one law for both themes: the tile rule sits ONE POP STEP ON
THE FAR SIDE OF THE GROUND FROM THE FILL.** The reference's number cannot simply
be copied, because the two themes have different room to move:

| | fill vs ground | where the rule goes | measured (untinted) |
|---|---|---|---|
| dark | 25.0 → 34.8, headroom left | further ABOVE the fill — a lit edge | `rgb(46,49,56)`, fill +14, ground **+23.9** |
| light | 242.9 → 255.0, CLAMPED AT WHITE | crosses the ground and sits BELOW it | `rgb(230,230,230)`, fill −25, ground **−12.9** |

Copying dark's +14 onto light lands the border on 241 — which *is* the ground
(242.9) — and the edge vanishes. That is why the law is written against the
GROUND and not against the fill.

**It is derived from `--cellbase`, not from the ground token, and that is the
point.** `--cellbase` already carries the era's hue, so a tinted tile gets a
tinted EDGE for free (`rgb(220,229,229)` / `rgb(231,226,220)` light,
`rgb(46,55,55)` / `rgb(57,52,46)` dark) and reads as **one soft object** rather
than a coloured field in a grey box. Relative colour syntax, never `color-mix` —
same reason as the fill: an oklch mix interpolates the hue ANGLE.

**No new palette entry, and the `--rule-*` ramp is untouched**, because other
surfaces in the sheet read it. The two rules that are *supposed* to be loud were
left alone and are now asserted to stay loud: the **five-column rule** keeps
`--rule-structural-strong` (61.2 light / 66.7 dark from the ground, a +44.9 /
+38.6 gap over the loudest tile edge) and the **selected tile's edge** keeps
`--accent` at full strength (132.4 / 132.6, +116.1 / +104.5) — selection is
identity and is allowed to be the loudest thing in the grid.

**`TestCellProbe_TheTileRuleIsTheQuietestRuleInTheGrid` is the guard, and its
absence was the actual defect.** The band is 8–32 from the ground in luminance,
one band covering both themes; measured 12.9–16.3 light and 23.9–28.1 dark, and
both shipped values (36.1 / 39.7) are outside it. It also asserts the loudness
ORDER of the grid's three rules and that a tinted tile's edge carries the era's
hue. **A step with a floor and no ceiling is how the last two loud things
shipped** — the era tint's 19/255 and 29/255 went past a bare floor, and this
edge went past no bound at all inside the very change that fixed that one.

### The ground must SHOW, and that is a measurement

The tile construction only produces the "popped out" look if the 3px it opens
shows something different from what the tile is filled with. The tokens already
differ in both themes and they **swap**: light ground `--surface-inset` / fill
`--surface-card`, dark ground `--surface-card` / fill `--surface-inset`. Nothing
asserted it, so `TestCellProbe_TheEraTintCarriesTheEraAndKeepsThePop` now reads
both back out of the layout in both themes. Measured, Chromium 141:

| | ground | untinted tile | ground↔fill, worst channel |
|---|---|---|---|
| light | lum 242.9 | lum 255.0 | 13/255 |
| dark | lum 25.0 | lum 34.8 | 10/255 |

### The era is a tint and NOTHING else, and softness has a CEILING

The era's caption row is deleted (`bandRow`, `.bl`, `.sfx`, `.halfrule`, every
`.band*` rule, `bandStyle`/`bandClass`/`halfRuleStyle`).

**"NOTHING WAS LOST — ONLY REPEATED" IS WHAT THIS PARAGRAPH USED TO SAY, AND IT
WAS WRONG ON BOTH HALVES.** Corrected 2026-08-15 against the package's own
fixtures rather than against the dispatch's prose:

- the Nameplate's era badge reads **`BlockData.EraLabel`, a DIFFERENT FIELD**
  from the `EraBand.Label` the deleted row printed, and the two are not kept in
  step — `"RoW"` on the badge against `"Reckoning of Wards"` /
  `"Age of the Emberfall"` in the band data. Rendered, `EraLabel` reaches the
  body and `EraBand.Label` does not appear at all. The badge also names ONE
  era, the calendar's current one, where the row named the era of each week.
- the season renders in **one** place by default, not two. `.sub season` on the
  Nameplate is unconditional; `.skseason` lives inside `skyHeader`, which is
  gated on `skySeated(d)` (a non-empty `SkyGradient`) and therefore renders in
  **0** of this package's three fixtures. It is real only where a host seats a
  sky, which today is the Bench's PRIMARY Block alone.

So `EraBand.Label` and `EraBand.Suffix` now have **zero readers in this widget**.
The fields stay — the producer pin asserts them and a legend will want them —
and `data.go` says so at the declaration. **The era colour has no legend naming
the era**, and that is booked as a real unbuilt gap in C-CALV4-TILES §7 rather
than dressed up as a surface that already exists.

That makes the tint the **only** thing inside the month that says "era", which
is why its strength stopped being a taste. `--eratint`'s chroma dropped from
0.022 → **0.010** on light and 0.030 → **0.012** on dark.

**`eraSeparation = 8.0` was a FLOOR WITH NO UPPER BOUND, and that is how a
19/255 (light) and 29/255 (dark) tint shipped** past a fully green suite — 1.5×
and 2.2× the reference's *entire* page-to-cell pop step of 13/255. Every number
above the floor passed, including every number that was too loud. It is now a
**band: floor 4, ceiling 12**, asserted in both themes in a real engine.
Measured after the change: **11.0/255 light, 10.0/255 dark**, with each tinted
cell still on the raised side of its own ground (+8.9/+8.5 light, +13.4 dark).

### Selection stops eating the tint

`.cell.sel` / `:has(> .daypick:checked)` used the `background:` **shorthand**
against `--surface-card`, at higher specificity than the fill chain. A selected
day therefore dropped its era hue entirely — and the day that left its era was
the one the reader had just pointed at. Untested, invisible in the markup.

Selection now paints the tile, is lifted **from `--cellbase`**, and uses relative
colour syntax (`oklch(from var(--cellbase) calc(l ± …) c h)`) rather than a mix:
`color-mix` in oklch interpolates the hue ANGLE, which is the same trap that made
a teal era render pink. `calc(l ± …)` keeps `c` and `h` untouched by
construction, so "a selected day keeps its era hue" is a property of the
expression and not of the numbers in it. The direction inverts with the theme
(light darkens by 0.015, dark lifts by 0.03).

**The probe measures TWO selected eras, not one, and that is load-bearing.** A
selected cell compared only with its own resting state passes on dark: the
shorthand mixed `--surface-card` with the blue accent, which carries the same
R−B sign as the fixture's teal era, so the same-cell arm reds on light
(−10.0 → +4.0) and stays green on dark (−9.0 → −13.0) while the defect is live
on both. Two selected eras cannot agree by accident — under the shorthand
neither reads `--cellbase`, so both paint the same pixel and their separation is
**0.0/255**. Verified red on all four hosts by restoring the declaration; green
at 12.0 (light) and 11.0 (dark) against resting 11.0 / 10.0.

The edge is `--accent`, **not `--gold`**, and that is a deliberate deviation from
the recipe's wording: the reference's selected border is gold because gold IS
that product's accent, whereas canon A7 makes `--accent` mean SELECTED here. A
second selection colour would put the meaning in two places.

## The cell's corners swapped, and the event marks became RUNES (C-CALV4-TILES §9.1/§9.2/§9.3, 2026-08-15)

### The two top corners swapped, and the reason is MOTION

The moon cluster is a flex row that grows from one disc to three plus a `+` on
hover or focus. Anchored **right** it grew **leftward**, so the primary
silhouette — the disc the pointer is already on — was displaced **35.05px** at
the moment of arrival. Nothing in this sheet may move, and `TestCSS_NoMotionAtAll`
cannot see this: it greps the sheet for `transition` / `animation`, and this is
displacement with neither.

`.phrow` is now `top: 4px; left: 4px; right: auto` and the date takes the
top-right corner (`.dn { text-align: right }`, `.dnw { justify-content:
flex-end }`, and the named cell's `> .cnamed > .dn` too). Re-measured in
Chromium 141 by `TestRuneProbe_TheExpansionGrowsRightward`, at a 105.4px column
in both themes:

| anchor | primary-disc displacement on expansion |
|---|---|
| `left: 4px` (ships) | **0.00px** |
| `right: 4px` (the same cluster, re-anchored in the same pass) | **35.05px** |

The control arm is not decoration. Measuring the new anchor alone reports
0.00px on a build where the expansion stopped working at all, which is the shape
of tautology this package's probes exist to refuse.

`right: auto` is written out rather than left to the initial value, because
`right: 4px` is what the rule said one change ago and an absolutely positioned
box with both offsets set is STRETCHED, not anchored.

### Today is INK, and three sizing rules went with the disc

The filled stamp read as a redaction over the numeral (*"a weird blacked out
date"*). `.cell .today` is now `display: inline; background: transparent;
box-shadow: none; color: var(--today-ink); font-weight: 750` — no width, no
height, no font-size, and none may come back: any of them re-creates a box
around the date.

The arithmetic that rule used to carry is gone with it. The stamp was **the
widest thing a date can be** (18.0px against two digits' ~13px), so it, not the
digits, set the corner architecture's inline budget and had to step with the
column. A numeral inked differently is the same width as the same numeral in
body ink. **Four** sizing declarations were deleted, not the three §9.1 counts:
the baseline 13px, the 35px rung's 14px, the mini tier's 13px, and the named
cell's 22px — the last is the one a rewrite most easily leaves behind, because
it only renders at a width no phone produces. `sizing.go`'s note about the 18px
stamp is history and is marked as such there.

### The runes, and where they are emitted

`.ul` / `.ulseg` keep their markup, their classes and their element. What
changes is the box and the paint: a centred block of masked **runes** in the
cell's empty middle instead of a bar in the bottom-left corner.

- **MASKS, NOT BACKGROUND-IMAGES.** A data-URI SVG used as `background-image` is
  an independent document and cannot see the host's `color`, so `currentColor`
  inside one is always black. The SVG supplies the SHAPE via `mask-image` and
  `background-color` supplies the paint. Both `-webkit-mask-*` and the
  unprefixed properties, on every rule.
- **32 GLYPHS POOLED** from four alphabets, selected by `:nth-child()` × the
  `p1..p8` class. `underlineCap` is **3**, so `:nth-child(4)` — the angular
  family, eight of the 32 — cannot match today. They ship anyway, for the reason
  p7/p8 are defined with no axis assigned: the first fourth segment ever emitted
  must find a glyph, not a slab. `TestCSS_ThePooledAlphabet` pins the 4×8 grid
  and fails if the cap ever outgrows the pool.
- **THE INK IS NOT THE RAW PALETTE.** `oklch(from var(--axis) 0.36 calc(c * 0.62) h)`
  on light, `0.72 calc(c * 0.8)` on dark. Measured distance from the raw token,
  worst channel in 0–255: **85–138 on light, 33–38 on dark**. (The design's
  earlier dark value of `0.80 0.075` came out chalky pastel and is not what
  ships.)
- **CHROMA IS SCALED, NOT REPLACED — a defect fix, not a style.** The first
  build wrote a constant `c` (`0.36 0.10` / `0.72 0.13`), so HUE was the only
  surviving channel. `--axis` is **not** one of six curated tokens: it is
  `EventCategories[].Color` verbatim out of `block_projection.go`, edited by a
  bare `<input type="color">`, so it is any sRGB value an operator picks. Three
  measured losses, each of them a distinction the operator's own data carried:
  - two types separated by **saturation** collapsed. This sheet's own palette
    did it — `--ev-social` (c 0.17) and `--ev-session` (c 0.04) share hue
    255–258 and were told apart by chroma alone; they inked **6/255** apart in
    both themes, one colour at 9×12px.
  - an **achromatic** category acquired a hue. OKLCH's `h` is powerless for
    grey, so `#888888` inked `rgb(235,130,125)` on dark — a grey category
    painting a red rune, **3/255** from a vivid red one.
  - the six shipped `DefaultEventCategories` lost most of their separation:
    min pairwise **80/255 raw → 32/255 light, 48/255 dark**.

  After the fix, decoded pixels: social/session **6 → 41** (light) and **6 → 64**
  (dark); grey vs vivid red **2 → 53** and **3 → 87**; `#888888` inks
  `rgb(61,61,61)` / `rgb(164,164,164)`. Guarded by
  `TestRuneInkChannels_ChromaSurvivesTheDeepening`, proven red against the
  constant-chroma recipe on all four arms.
- **TWO THINGS THE SCALING DOES NOT FIX**, recorded so they are not
  re-discovered as bugs:
  - **lightness is still normalised**, and that is what makes a rune an ink —
    so two types differing mainly in *lightness* still converge. The shipped
    defaults' closest pair (Holiday `#f59e0b` / Battle `#ef4444`) goes 80/255
    raw → **29/255** as ink, essentially untouched by the fix. Two achromatic
    picks ink identically, 0/255, for the same reason.
  - **the GM strike and a gold category still collide.** Permission ink is
    `oklch(from var(--gold) 0.44 0.11 h)` = `rgb(110,76,0)` on light; the
    shipped "Holiday" default inks **28/255** from it. Both are gold *by hue*,
    so no chroma treatment separates them: a GM-only day and a Holiday wear the
    same colour below 84px. Fixing it means moving the permission channel off
    gold or the shipped default off amber — a decision about what the product
    means, **booked for the operator, not guessed here**.
- **`--runeink` IS DECLARED ON THE GLYPH, NEVER ON AN ANCESTOR.** A custom
  property inherits its COMPUTED value, so an expression referencing `--axis`
  declared where `--axis` does not exist computes to the guaranteed-invalid
  value and every child inherits *that*. It cost a render during design.
- **GM-ONLY DAYS INK IN GOLD** via `.cell:has(> .dogear)`. The fold and the
  audience diamond therefore **stop painting below 84px** but STAY IN THE
  MARKUP — the fold is the datum the `:has()` reads, and deleting it from
  `gmMarks` would delete the gold silently, because a cell with no fold simply
  inks its runes in the type colour and still looks like a working build.
- **THE OVERFLOW MARK IS NOT A RUNE.** `.ulseg.rest` carries no pattern class,
  matches none of the 32, and unstyled would paint a solid 9×12 slab among
  letterforms. It gets a vertical three-dot tally in `--own-none`. It needed a
  `.dark` arm as well: `.dark …:has(> .dogear) .ulseg` carries one class more,
  so on dark the tally inked GOLD while on light it inked neutral — one mark,
  two meanings, split by theme. Found by measurement, not by reading.

### §9.3 — the density ruling, and why nothing moved in the markup

**Runes are the NARROW form. A name beats a rune wherever there is room for
one.** At ≥84px of column the cell keeps its event-NAME chips and draws **no**
runes; below that the runes replace the underline bars. (Every desktop render
shown during design had the chips stripped by the harness — those approved
pictures are real pixels of a state the product does not produce.)

`.ul` already lives inside `.cunder`, which **is** the narrow subtree —
`display: block` below 84px, `display: none` at or above it. So the ruling is
enforced by the subtree the element was already in, and no markup moved. That is
stronger than "not painting": `display: none` removes the element outright, so
there is no rect, no layout and nothing one cascade change from visible. `.ul` is
positioned against `.cell`, not `.cunder`, and `.cunder`'s `overflow: hidden`
does not clip it — the clip applies to descendants whose containing block is
inside the overflow box.

Measured by `TestRuneProbe_TheDensityRuling`, Chromium 141:

| host | column | chips | rune boxes | rune size | rune × numeral | spill |
|---|---|---|---|---|---|---|
| 1400px, named | 105.4px | 8 cells | **0** | — | — | — |
| 1150px, narrow | 80.4px | — | 11 (11 masked, 11 inked) | 13×17px | 0.00px² | 0.00px |
| 366px, narrow | 34.0px | — | 11 (11 masked, 11 inked) | 9×12px | 0.00px² | 0.00px |
| 280px, mini | 26.2px | — | 11 (11 masked, 11 inked) | 6×9px | 0.00px² | 0.00px |

The 1150px row is the one the two obvious hosts miss. Between the 75px expansion
rung and the 84px named flip the cell still draws runes and draws them at the
DESKTOP 13×17, one row, no wrap — a nine-pixel band of column width (1100px host
→ 75.4px, 1200px → 85.4px and flips to chips) and the only place the

### The chip tint was painting the wrong hue, and it predates all of this

`.chip` filled with `color-mix(in oklch, var(--surface-card) 90%, var(--axis))`.
**`color-mix(in oklch, …)` interpolates the HUE ANGLE**, and the light theme's
`--surface-card` is `oklch(1 0 0)` — white written with an *explicit* hue of
**zero**. So every chip was dragged 10% of the way from 0° toward its type's hue
and landed in the reds. Measured, decoded pixels, light theme:

| event axis | chip fill, OKLCH mix | chip fill, sRGB mix |
|---|---|---|
| blue `oklch(0.55 0.17 258)` | `rgb(250,236,242)` — pink | `rgb(233,241,251)` — pale blue |
| red `oklch(0.60 0.19 25)` | `rgb(254,237,241)` — pink | `rgb(251,236,236)` — pale red |
| green `oklch(0.65 0.13 145)` | `rgb(252,240,241)` — pink | `rgb(238,246,239)` — pale green |

Three different event types, **3–4/255 apart**: the largest colour surface a wide
cell has was showing the wrong hue *and* carrying no type separation at all. Dark
was the same failure mirrored through the card's own hue of 265 — a red event's
chip resolved to hue 241, still blue. Fixed by mixing **in sRGB**, which has no
hue channel to wrap: 12–18/255 apart, each in its own type's colour.

**It is at HEAD** and was invisible while the cell had a white ground; the gapped
tile and the era tint gave the chip a coloured surround and the pink stopped
hiding. It is fixed here rather than filed because §9.2's ruling — *"just have
the colors determine what kind of event"* — makes hue the type channel, and this
rule contradicted it on the density a desktop actually renders. `.surf.sel` had
the same trap against `--accent` and moved to sRGB too. The two
`--surface-card` × `--text-primary` mixes stayed in OKLCH deliberately: that
token is near-achromatic in both themes and the two spaces land 2/255 apart, so
changing a correct mix is churn. Mixes against `transparent` have no hue to drag.
Guarded by `TestRuneInkChannels_TheChipTintCarriesItsOwnHue`, proven red.

## The legend is a DISCLOSURE, and it is a COLOUR key (C-CALV4-TILES §9.4, 2026-08-15)

`legendZone` was not rebuilt. What changed is how it OPENS — a tab at rest,
resolving on hover, on keyboard focus and on a tap — and what its copy is allowed
to claim. The entries, the swatches, the counts and the single pass over
`Rows[].Cells[].Marks` that produces them are byte-identical, which is why the
producer-side count oracle (`block_count_oracle_test.go`, keyed on the literal
`<label> <span class="n">N</span>`) needed no edit.

**It is a COLOUR key and may never say a shape means anything.** §9.2 made the
rune decorative: the glyph is chosen by `:nth-child()`, i.e. by POSITION IN THE
DAY, so a four-event day draws four different runes and none of them carries a
type. `blockMarkFor`'s guarantee — *"a viewer who cannot separate the hues can
still separate the marks"* — is retired IN THE GRID, and the legend is the
surface most likely to go on promising it, because a legend is where a reader
goes to learn what a mark means. `legendTabLabel()` names the axis the swatch
actually carries and `TestLegend_TheTabIsAColourKeyAndClaimsNothingAboutShape`
fails on the vocabulary that would re-make the promise.

**`:focus-visible`, NOT `:focus-within`, and the dispatch names the latter.**
This is a deliberate deviation and the defect it avoids is specific: clicking a
`<label>` focuses its input, so under `:focus-within` a tap would check the box
(open) and the SECOND tap would un-check it while the box still held focus —
leaving the zone open. The tab would then be a control that visibly does nothing
on every press after the first, which is the failure
`TestCSS_TieToggleFlipsInkWithoutJS` exists to name. Measured, both pointer
types: under `:focus-within` the second tap left the body open on every host;
under `:focus-visible` it closes.

**Four openers, each answering a device the others do not**, and one of them is
gated:

| opener | device | note |
|---|---|---|
| `:hover` | a mouse | inside `@media (hover: hover)`. An ungated branch is the whole affordance on a desktop and NONE of it on a phone |
| `:has(> .legpin:focus-visible)` | the keyboard | the input is CLIPPED, not `display:none` — a display-none input is not focusable |
| `:has(> .legpin:checked)` | a thumb | and the pin that survives the pointer leaving |
| the switchboard's `legend` row `:hover` | the preview | pointing at a layer row lights the section it controls; a collapsed zone would light a 22px tab |

**Measured, Chromium (`legend_disclosure_probe_test.go`, 420px host):** tab
83.70 × 22.00px under a fine pointer and **91.70 × 44.00px under a genuinely
coarse one** (`--blink-settings=primaryPointerType=2,availablePointerTypes=2`);
`elementFromPoint` at its centre resolves to the label itself; rest closed,
keyboard open, one tap open, second tap closed, four entries disclosed. The 44px
floor is a REQUIREMENT here rather than a report — unlike the moon opener's,
which cannot meet it on a 52px cell — because the zone sits under the month with
block-axis room to spare, so no excuse is available and none is taken.

**The pass order in that probe is load-bearing** and it is the SECOND time this
package has paid for the same finding: Chromium's `:focus-visible` heuristic is
document-wide, so the first `click()` anywhere makes every later programmatic
`.focus()` stop matching it. Run as one pass per host the probe reported a
working keyboard for host 0 and a broken one for host 1 —
indistinguishable from the rule being missing. `moonReachOpenScript` records the
identical trap.

## The availability strip: BUILT, and DORMANT (C-CALV4-TILES §8.4/§8.9/§9.5)

The strip is a **TIME AXIS for the day, not a roster**: its width is the day, a
span's position says WHEN and its length says HOW LONG, one 3px lane per player

because "when can we all play" is the only question this surface exists to
answer. Lanes ABUT (the operator: *"no space between them because they are

removed. Below 75px of column the player lanes drop and the overlap alone
survives.

**IT PAINTS NOTHING, AND THAT IS MEASURED RATHER THAN ASSERTED.** `DayCell` has

fantasy-date blocker is unresolved. Three separate things hold the dormancy,
deliberately, because one would be an accident:

1. the geometry switch is on **`.cell.rsvp`**, a class no markup here emits, so

2. **`.lane` matches no element** — `availabilitySlot` emits no children, because

3. **`--m0`/`--m1` carry NO fallback**, a deliberate deviation from `/schedule`'s

   paint a FULL-DAY bar out of no data at all. Unset, the declaration is invalid
   at computed-value time, `left`/`right` fall back to `auto`, and the span has
   no width.

**Measured, Chromium (`availability_probe_test.go`):** at 366px light, 366px dark
and 1400px light, the Block as shipped against the Block with every availability

and **0 lanes**. The probe carries its own SENTINEL — the same host shot with the
strip's box deliberately filled, which differs by 4 068 px at the narrow hosts
and 16 852 px at the wide one — because a comparator that could never fail would
report perfect dormancy on a strip painting scarlet across every cell.

**The span primitive is `/schedule`'s, not a second one**
(`C-CALV4-DRAG-RESCHEDULE.md:172`), and `TestCSS_TheSpanPrimitiveIsSharedWithSchedule`

**`pointer-events: none` stays** (§8.7). A 3px lane is not a control and a 4px hit
area against a 44px floor is not one either; `/schedule` solved the identical
problem by making the CELL the target and the lozenge a MARK, the day cell is
already that target, and the detail lands in the Ledger. A third hit region in
one cell is what the two-target rule refuses.

**What the wiring dispatch still owes, named rather than discovered later:** a
filled strip is `4px + 3px × players` and grows UPWARD from the cell's inner
bottom edge, so between 75px and 84px of column it reaches the underline
cluster's 6px anchor. §9.2's rune block already answers that — a day with RSVPs
lifts by `calc(var(--avail-h) + 14px)`, measured off this strip's own token so
the two cannot drift — and that lift is the runes' rule, not this one. Nothing

`TestCSS_NoMotionAtAll`'s allowlist did not grow and needed no edit. A reader who

`calendar-block.css`, never against what renders.

## Channel discipline (canon A7)

## Deliberate divergences from the contract (all flagged in PR)

1. **The `isNamed()` row-height clause is RETIRED, not inherited.** The mockup's
   second clause (`instrument / rows >= 68`, with a hardcoded 470px at full tier
   against a measured 563px) is a known, booked, deliberately-unfixed defect
   (canon §D). The CSS implements the measured-column clause alone; vertical fit
   is settled by real layout. Correcting the constant to 563 was **refused** — it
   desynchronises every signed still. `TestIsNamed_RetiredRowHeightClause` pins
   the divergence so it can neither be reintroduced nor silently lost.
2. **RETIRED at C-CALV4-TILES §3.** This divergence read: "`.band.half` is
   applied, plus a `.halfrule` ruler" — the mockup declares `.band.half` and
   never applies it, so the ramp step stopped dead at the era band, and the
   class alone could not draw the rule where it belonged (a band is one grid
   item spanning many columns), so the band row carried a zero-width ruler item
   on the half column instead. **The band row is deleted**, so there is no
   spanning item, no seam and no ruler. It is recorded rather than removed
   because the reasoning is what a later hand needs if a spanning item ever
   returns to the grid.
3. **The week gutter's width is a container query, not an inline `--gut`.** The
   mockup drops the gutter below 481px of host — a host measurement the producer
   cannot make. The mockup additionally gates it on `week === 10`; wave 1 does
   not, because a literal week length in the renderer is what this brief exists
   to remove.
4. **Out-of-range cells render empty.** `DayCell.Day == 0` IS the out-of-range
   marker, so there is no field for the adjacent month's ordinal; the signed
   Gregorian still shows a greyed 28/29/30/1. A `LeadLabel string` on `DayCell`

## C-CALV4-HOST-P3 changes in this package (2026-07-28)

Phase B gave the Block its first production caller (the entity-page embed,
`internal/plugins/calendar/entity_calendar_block.go`). One thing changed HERE:
the tie toggle stopped being inert.

**The toggle is a hidden radio pair plus `:has()`, and that is the whole
mechanism.** `tieCounts` (`nameplate.templ`) now emits two `input[type=radio]`
carrying `data-tie-pick="tied|whole"`, each addressed by a `<label class=tiebtn>`
stating its count; `calendar-block.css` reads `:checked` off the Block with
`:has()` and changes the untied ink level. Everything about why:

- **It cannot be JavaScript.** `boot.js:163` sets
  `htmx.config.allowScriptTags = false`, so a `<script>` inside an
  HTMX-swapped fragment never executes — a JS toggle would die after any
  binding swap, silently, in production only.
- **It cannot be a route.** Wave 1 freezes `routes_snapshot.txt`, and it does
  not need one: pin r51 already puts EVERY viewer-visible mark and BOTH counts
  in the DOM in both modes, so the flip has nothing to fetch. That is also why
  the pair can never be differenced to infer a hidden event.
- **`data-tie-mode` stays on `.block`.** It is the server's initial answer AND
  the whole story on an engine without `:has()`. The `:has()` rules outrank it
  on specificity alone (the `:has()` argument contributes its own), so the
  viewer's choice wins without depending on source order.
- **TWO ink levels, not one.** The signed `setTie()`
  (`mockups/calendar-v4.html:2823-2824`) inks an untied mark at **0.28** in
  tied mode and at `--m-untied-ink` = **0.70** in whole mode. This sheet had
  only the tied branch, using the WHOLE value for it: tied mode under-dimmed
  and whole mode did not dim at all. Now `--tied-ink` / `--untied-ink`, with
  `TestCSS_TieToggleFlipsInkWithoutJS` pinning that a rule actually READS the
  radios (an unread pair is a control that visibly does nothing) and that tied
  dims harder than whole.
- **The radio group name is a pure function of `(CalendarSlug, HostEntity)`**
  (`tieGroupName` / `tieInputID`, `helpers.go`). Not a counter and not random:
  two Blocks on one page must not share one piece of state, and the SAME Block
  re-rendered by an HTMX binding swap must keep the mode the viewer just chose.
  A pure function satisfies both and is identical across servers.
- `boolAttr` went with `aria-pressed` — the `unused` lint has no `_test.go`
  exclusion, so a helper without a caller reds the build.

**Pin refreshed, intent unchanged:** `block_test.go`'s `stripMode` strips
` checked` where it used to strip `aria-pressed`. The property it protects is
the same one — flipping the mode may change the mode attribute and the selected
state, and NOTHING else about the DOM.

**Measured, and it retracts a plausible-sounding assumption:**
`container-type: inline-size` does NOT make an element a containing block for
`position: fixed`/`absolute` descendants; `contain: layout` does. Chromium 141,
three identical hosts: plain `(0,0)`, `container-type` `(0,0)`, `contain: layout`
`(82,450)`. This matters here because §"Sizing is CSS" makes every host of this
Block a container, and the obvious worry — that containing a host traps a
modal rendered inside it — is not what browsers do. Do not re-derive it from the
spec sentence, which reads the other way.

| | at rest | when its day is chosen | selected by |
|---|---|---|---|
| `.lhead .lctx`, `.lzero.lday` | `display:none` | revealed | the class `.lday` |
| `.lrow` | visible | filtered OUT | the attribute `[data-lday]` |

1. `ledgerRowClass` emits no `lday` (`helpers.go`), pinned by

2. the generated reveal rule NAMES its two surfaces —

3. `TestCSS_AnswerLadderChangesNothingButVisibility` checks the ladder's

only place the renderer learns which bodies the grid's ceiling excluded.

There is **no epithet** (`calendar.Moon` has no such column) and **no node-window
bracket** (`.abr` ships as vocabulary the way `.cell.fog` does, and
`AlmanacDay.Node` is false everywhere because no orbital-node data exists).

### The std tier, measured

The Shelf is `flex: 0 1 auto` at std and `flex: none` at full. Filled, the zone
wants 166px inside a 520px Block that also holds a month and a docked Ledger,
and with `flex: none` the LEDGER absorbed the whole deficit — crushed below its
own head and tab strip, it put 10.8px of rows on top of the Shelf at both
production host widths. The Shelf is the zone that can give (its body already
scrolls; the Ledger's furniture can only overflow), so it yields. The signed
132px ceiling is unchanged at both tiers: a smaller std ceiling was measured and
made the result WORSE, because the Shelf absorbs the whole deficit either way.

The strip is `overflow-x: auto`: six controls do not fit 358px of Bench host,
and clipping the last sub-tab would leave a control nobody can reach and nothing
saying it is there.
