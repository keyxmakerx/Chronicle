# Attributes Widget

## Purpose

Displays and edits entity custom fields defined by entity type templates, with
per-entity overrides (add fields, hide inherited ones, change definitions)
that leave the category template untouched.

## Tier

Widget, API-driven frontend.

## Files

| File | Role |
|------|------|
| `static/js/widgets/attributes.js` | Client-side widget implementation |

## Dependencies

- Uses the fields API (`GET/PUT /campaigns/:id/entities/:eid/fields`) and the overrides API (`PUT/DELETE .../field-overrides`).
- Used by the entity profile page.

## Frontend Widget

### Mount Syntax

```html
<div data-widget="attributes"
     data-endpoint="/campaigns/{cid}/entities/{eid}/fields"
     data-editable="true"
     data-csrf-token="{token}">
</div>
```

### Configuration

| Attribute | Required | Description |
|-----------|----------|-------------|
| `data-endpoint` | Yes | Fields API endpoint (GET/PUT) |
| `data-editable` | No | Enable editing (`true`/`false`) |
| `data-csrf-token` | No | CSRF token for mutations |

### Modes

1. **Read-only:** labels and formatted values (URLs as links, booleans as Yes/No).
2. **Edit form:** fields grouped by section with type-appropriate inputs (text, number, url, textarea, select, checkbox).
3. **Customize panel:** per-entity overrides (toggle visibility, add fields, reset to template).

### API Calls

- `GET {endpoint}` -- loads `{ fields, type_fields, fields_data, field_overrides }`
- `PUT {endpoint}` -- saves `{ fields_data: { key: value } }`, which replaces every field, so a value another editor wrote since loading must be taken in first: it listens for `chronicle:token-saved` and takes in the token field the token maker wrote
- `PUT {endpoint → /field-overrides}` -- saves per-entity overrides
- `DELETE {overrides-endpoint}` -- resets to category template
