# Notes Widget

Notes for everyone in a campaign, on two surfaces over one table: the full-page
**Journal** (`/campaigns/:id/journal`; notes with no page, in folders, linked
with `[[links]]`) and the floating **Jot notes** panel (notes on a page,
"jots"). Each note has an owner and one of four audiences.

## Architecture

- **Tier:** widget with a full backend (handler -> service -> repository ->
  MariaDB `notes`, `note_versions`, `note_attachments`, `note_pictures`).
- **Addon slug `notes`** gates the Jot notes panel (off by default); the Journal
  route is open to every member.
- **Sync API:** CRUD at `/api/v1/campaigns/:id/notes`
  (`internal/plugins/syncapi/note_api_handler.go`).
- **Frontend:** `static/js/widgets/journal.js` (Journal), `journal_list.js`
  (pure list rules), `editor_notelink.js` (`[[links]]`), `jot_place.js` (jot
  sheet placement), `notes.js` (Jot notes panel).

## Data model

- `notes`: per user and campaign. `entity_id` NULL is a Journal note (or
  folder); set is that page's jot. Pinned notes sort first, then `updated_at`
  DESC.
  - Content: legacy block JSON `[{type:"text",value},{type:"checklist",items}]`
    plus `entry` (ProseMirror JSON) and `entry_html` (sanitized, pre-rendered).
  - Sharing: `is_shared` (party), `shared_with` (JSON user ids),
    `shared_with_gm`.
  - `archived_at` (NULL = active), `linked_note_id` (a jot sent to the Journal),
    `last_edited_by`, `locked_by`, `locked_at`, `color` (left edge of a jot card).
- `note_versions`: snapshot (title, content, entry, entry_html); FK cascade;
  at most `MaxVersionsPerNote` (50), oldest pruned. Added only for title or body
  edits, not for pin, share, file or archive.
- `note_attachments` (migrations 5, 32): audio per note (`file_path`,
  `original_name`, `mime_type`, `file_size`, `duration_secs`, `transcript`).
- `note_pictures` (migration 44): which notes bind which picture (see "Pictures").

## Visibility

Four audiences derived from three columns (`Note.derive`), so rows written
before the GM audience keep theirs:

| Visibility | Columns | Who besides the owner reads it |
|---|---|---|
| `private` | none set | nobody, the GM included |
| `gm` | `shared_with_gm` | the campaign Owner and members with DM access (`VisibilityRole` >= Owner) |
| `party` | `is_shared` | every member |
| `custom` | `shared_with` | the named people |

- New notes are private. `UpdateNoteRequest.visibility` sets all three columns
  together (`applyVisibility`); `isShared`/`sharedWith` still work
  (`applyLegacySharing`) for the Foundry module.
- Anyone who can view a note may edit its title and body. Only the owner may
  change visibility, pin, archive, file into a folder or delete
  (`UpdateNoteRequest.StripOwnerOnly`, applied by both route sets).
- Archiving unpins; `archived` derives from `archived_at`.

## Behaviors

- **Edit lock:** editing a shared note POSTs `/lock` first; another holder
  denies edit. Heartbeat every 2 minutes; the lock expires after
  `LockTimeout` (5 min) and a stale lock is reclaimed by the query. Released on
  Done or panel close. Owners may `/force-unlock`. A note locked by another
  shows a lock icon and no edit button.
- **Versions:** every `Update` and `RestoreVersion` snapshots the current state
  first; restore applies the old content after a pre-restore snapshot.
- **Rich text:** both surfaces edit in TipTap. Checklists are task lists
  (`ul[data-type=taskList]`; the sanitizer keeps `data-type`/`data-checked` on
  `ul`/`li`, not the checkbox). Legacy checklist blocks show under the body and
  stay tickable through `/toggle`. View mode renders `entryHtml` when present,
  else legacy blocks.
- **Game-night entries:** with the sessions plugin wired (`SetNightEntries`),
  `JournalIndex` first asks for the viewer's due entries to be made, then tags
  each entry row with `night` (its game night, and whether it has started). The
  editor shows "Read after the night", "Read · N names found" or "Not read",
  with a hover card (`Chronicle.hovercard`). Entries are ordinary notes; see the
  sessions `.ai.md`.

## Routes

The Journal page is `/campaigns/:id/journal`; `/campaigns/:id/journal/:noteId`
opens one note (the href of every `[[note]]` link). Everything else is under
`/campaigns/:id/notes`:

| Method | Path | Handler | Description |
|--------|------|---------|-------------|
| GET | `/` | List | List notes (scope=all\|campaign\|entity\|jots) |
| GET | `/members` | MembersAPI | Campaign members for the share-with-players picker (see Access control) |
| GET | `/index` | Index | The Journal list: visible Journal notes and folders with snippet, links out, links in, has-audio |
| GET | `/search?q=[&jots=1]` | Search | Title or text match with the matching line (≥2 characters) |
| GET | `/labels?ids=a,b` | Labels | `[[note]]` link labels; a note the viewer can't see is absent, like a missing one |
| GET | `/page-refs?entity_id=` | PageRefs | Visible Journal notes that link to a page |
| GET | `/page-names?ids=a,b` | PageNames | Names of the pages the viewer may see (for All my jots); up to 200 ids, others absent |
| POST | `/bulk` | Bulk | Archive, unarchive, move, visibility or delete many; only the caller's own notes change |
| GET | `/:noteId` | Get | One note |
| GET | `/:noteId/backlinks` | Backlinks | What links to it: `{notes, pages}`, each only as far as the viewer may see |
| POST | `/` | Create | Create note |
| PUT | `/:noteId` | Update | Update note (creates version snapshot) |
| DELETE | `/:noteId` | Delete | Delete note (owner only) |
| POST | `/:noteId/toggle` | ToggleCheck | Toggle checklist item |
| POST | `/:noteId/send-to-journal` | SendToJournal | The caller's own jot becomes a private Journal note (201), or returns the one it became (200) |
| POST | `/:noteId/lock` | Lock | Acquire edit lock |
| POST | `/:noteId/unlock` | Unlock | Release edit lock |
| POST | `/:noteId/heartbeat` | Heartbeat | Keep lock alive |
| POST | `/:noteId/force-unlock` | ForceUnlock | Force release (owner only) |
| GET | `/:noteId/versions` | ListVersions | Version history |
| GET | `/:noteId/versions/:vid` | GetVersion | Get specific version |
| POST | `/:noteId/versions/:vid/restore` | RestoreVersion | Restore to version |
| POST | `/pictures` | UploadPicture | Picture for a note's text (multipart `file`; any member; 5 MB; PNG/JPEG/GIF/WebP sniffed from bytes). Returns `{id, url: "/media/<id>"}` |
| GET | `/:nid/attachments` | ListAttachments | List audio attachments for note |
| POST | `/:nid/attachments` | UploadAttachment | Upload audio file (multipart) |
| DELETE | `/:nid/attachments/:aid` | DeleteAttachment | Remove attachment |
| PUT | `/:nid/attachments/:aid/transcript` | UpdateTranscript | Save transcript text |
| GET, POST | `/allow-app` | ShowAllow, Allow | Foundry grant window (see "Notes in Foundry") |
| GET | `/app-grants` | List | The player's Foundry connections |
| DELETE | `/app-grants/:gid` | Revoke | Disconnect one |

## Jot notes (`notes.js`)

Registered as `Chronicle.register('notes', ...)` and mounted by `NotesWidget()`
in the app layout on every campaign page (addon on, signed in):
`<div data-widget="notes" data-campaign-id data-entity-id data-user-id>`.
`data-entity-id` comes from the request path (`layouts.GetRequestPath`), not the
active path, since a page's handler may point the active path at its category;
`TestNotesWidget_EntityIDFromTheRequestPath` pins it. The widget re-mounts when a
boosted navigation changes the page.

- **Entry point:** a "Jot notes" tab bottom-right with this page's count (no
  topbar button; `TestTopbarHasNoNotesButton`). The tab hides while the panel is
  open; Escape closes the panel (an open popover first) and returns focus to the
  tab. On the Journal it sits higher, clear of the editor footer.
- **Panel:** This page / All my jots (All only off a page); "N Journal notes
  reference this page" (`/page-refs`, 12 listed, then a link to the Journal
  filtered by `?links=<page id>`); a filter field; flat cards (pinned first, then
  recent; on All each names its page via `/page-names`); "New jot on this page".
  Settings hold S/M/L text and "Keep open on every page" (`localStorage`
  `chronicle_jots_pinned`). On a phone it is a bottom sheet from 18% down.
- **Placement (desktop):** a floating sheet; drag the title bar (or arrow keys
  when focused) to move, drag or arrow-key the bottom-right corner to resize.
  The two pin buttons dock it full height left or right (`jot-dock-l`/`-r` on
  `<html>`, `--jot-dock-w`), narrowing the page; dragging the title bar undocks.
  Fold shrinks it to the title bar. The place `{x, y, w, h, dock, folded}` is in
  `localStorage` `chronicle_jots_place` (`chronicle_notes_size` still supplies a
  size). The rules (defaults, on-screen clamping, pinned width, aside corner) are
  pure, in `jot_place.js` (`test/js/jot_place.test.mjs`).
- **Stepping aside:** a floating sheet never covers what needs the room. When
  focus enters an overlapped open `<dialog>` or `aria-modal` element it slides off
  its nearest edge and returns when no modal is open; when focus enters an
  overlapped editable in `#main-content` it folds and glides to the opposite
  bottom corner, returning when focus moves on. Neither is saved as the place; a
  pinned sheet stays put.
- **Cards:** tools (share, history, edit, delete) show on hover or focus, always
  on touch. The owner sees Pin/Unpin and Send to Journal / Open in Journal.
  Sharing uses the same four audiences. Editing uses the Journal's editor and
  autosave and takes the edit lock on a jot others can see.
- **Send to Journal** (`SendToJournal`, `jots.go`): jot owner only, jots only.
  It makes a new private Journal note titled like the jot: a first line linking
  the jot's page (named as the sender sees it, through `PageNamer`), then the
  jot's text, checklist blocks as a task list. The jot records it in
  `linked_note_id` and its card becomes Open in Journal. Sending again returns
  that note while it exists and the caller can see it; otherwise a new one is
  made.
- **Page names:** `PageNamer` is `notesPagesAdapter` in `app/routes.go` over the
  entities service; a page of another campaign or one the viewer may not see
  (`CheckEntityAccess`) is left out, so the panel says "on a page" rather than
  leak a name.
- **Journal hand-off:** `/journal?links=<page id>` opens the Journal with a
  `links:` token for that page, then drops the query from the address.
- **Tabs always answer:** clicking the open tab reloads it, showing the loading
  line first. A failed load says "Couldn't load your jots" with Try again, not
  "No jots yet".
- **Live updates:** only while the panel is open, a `/ws` socket (the cookie on
  the site, the notes grant in a frame) turns this campaign's `note.*` events
  into a quiet list reload. A reload waits while a jot is being edited, its
  history is open or focus is in the list (which also absorbs the echo of our own
  saves), keeps the list on failure, and is dropped if editing started meanwhile.
  `test/js/notes_live.test.mjs`.

## Notes in Foundry (app grants)

A player lets the Foundry notebook and calendar window use their notes and
the campaign calendar with one Allow click. The grant reaches the notes JSON
routes, the page search, and the calendar page's routes
(`calendar.RegisterAppRoutes`, each at its site gate), always as that player
at their live campaign role.

- **Allow window** (`allow_app.templ`, `app_grants_handler.go`):
  `GET /campaigns/:id/notes/allow-app?origin=` is opened by Foundry as a
  popup. Allow is offered only when `origin` is exactly the site address or
  an admin-allowed CORS origin (`OriginAllower`, wired in `app/routes.go` to
  the same list the CORS middleware reads). `POST` makes the grant and
  returns the token once; the page hands it to `window.opener` with
  `postMessage(…, origin)`, so a window at any other address gets nothing,
  and no grant is made without an opener. The page sets
  `Cross-Origin-Opener-Policy: unsafe-none` (the site default `same-origin`
  would cut the opener); framing stays forbidden. It also lists the player's
  connections with Disconnect (`GET /notes/app-grants`, `DELETE /notes/app-grants/:gid`).
- **Grants** (`app_grants.go`, table `notes_app_grants`): `cnt_` + 256 random
  bits; only the SHA-256 is stored. One campaign each. Ten live per player
  per campaign (the oldest past that are revoked); unused for 90 days ends
  one; `last_used_at` is written at most every 5 minutes. Rows that can't
  authenticate again (revoked, or idle past 90 days) are deleted at boot and
  daily (`StartAppGrantPruner`).
- **App routes**: `/api/notes-app/campaigns/:id/notes/*`, the same handlers
  as the site through `registerNoteJSONRoutes`. `RequireAppGrant` reads
  `Authorization: Bearer`, refuses a grant for another campaign, and sets a
  session carrying only the user id (never site admin); then
  `RequireCampaignAccess` checks live membership: while the player is out of
  the campaign the grant is refused, and removing a player revokes their
  grants there, so a re-invite starts with none. The campaign's Sync API switch gates the group (`AppGate`,
  wired in `app/routes.go`), and a disabled account's grants stop at once
  (the token look-up joins `users.is_disabled`). Every grant a player holds
  is revoked whenever all their sessions are destroyed (password reset or
  change, email change, admin force sign-out), through
  `auth.OnSessionsRevoked`. A per-IP limit runs before
  the look-up. Under `/api/` because there is no cookie to forge: the CSRF
  check skips `/api/`.
- **Allow window without an opener:** signing in on the way can cut the
  link to Foundry (the sign-in pages keep `same-origin` COOP), so the page
  checks `window.opener` on load and asks the player to click the notebook
  button again instead of offering Allow.

### The frames (`embed.templ`, `static/js/notes_embed.js`)

- `GET /embed/campaigns/:id/notes/{journal|jots|calendar}` is an empty shell with no
  sign-in and no campaign data. `ShowEmbed` swaps the site's
  `frame-ancestors 'none'` for `'self'` plus the allowed origins and drops
  `X-Frame-Options`; nothing else about the site's policy changes.
- `notes_embed.js` tells the parent it is ready, accepts the grant token
  only from `window.parent`, sets `Chronicle.embed`, then fetches
  `GET /api/notes-app/campaigns/:id/notes/embed?mode=` (`EmbedFragment`:
  `JournalFragment` or `JotsEmbedFragment`, the site's own templates) and
  mounts it. Jot notes follow their own "jot-notes" switch (`SetJotsGate`); the Journal follows "notes". The
  calendar mode fetches `GET /api/notes-app/campaigns/:id/calendars/embed`
  instead: the calendar plugin's default calendar for this member.
- `Chronicle.apiFetch` (boot.js) sends any `/campaigns/…` request to
  `/api/notes-app/campaigns/…` with the token while `Chronicle.embed` is
  set. `Chronicle.go` replaces direct navigation in the notes and editor
  code: in a frame a page opens on the site in a new tab and a Journal note
  opens in the Journal (or the parent is asked with
  `chronicle:open-note`). The Journal keeps the frame's address as is.
- The editor's @ picker reads `/api/notes-app/campaigns/:id/entities/search`
  and mention hovers read `…/entities/:eid/preview` (both added to the app
  group in `app/routes.go`, as the player sees pages).
- `notes_embed.js` is a page body script so it runs after boot.js. The
  parent may also send `chronicle:open-note` to the Journal frame.
- The jot panel's `data-embed="true"` fills the frame and has no tab, close,
  pin or resize.
- Pictures and voice memos: an `<img>`/`<audio>` in a frame can't send the
  grant, so `notes_embed.js` swaps each `/media/…` address for a link from
  `POST …/notes/media-links` (`AppGrantHandler.MediaLinks` →
  `media.Handler.SignedLinksForMember`). Only files the player may open on
  the site (the ADR-058 check, as a signed-in request) are signed, for the
  cookieless viewer like Foundry's own media links, for 15 minutes; audio
  not yet played is re-signed every 10.
- Live updates: the frame's Journal opens `/ws` with the grant offered as
  a subprotocol (`chronicle.notes` plus `chronicle.grant.<token>`), since a
  browser socket can't send a header and a token in the URL would reach
  access logs. The socket is the grant's player at their live role, gets
  `note.*` events only, and closes when that grant is revoked or Sync API
  is switched off (see the websocket `.ai.md`). The jot panel does the
  same while it is open (see Jot notes).

## Pictures in notes

The Journal (`journal.js`) and the jot panel (`notes.js`, also what the Foundry
notebook frames show) use `Chronicle.EditorImage`
(`static/js/widgets/editor_image.js`), the node pages use: `figure.ce-img` with
width/side classes, stored src always the plain `/media/<id>` (the frame swaps
in signed links on screen). `useNotePictures` points uploads at
`POST .../notes/pictures` and hides the "GM only" switch: a note has no GM-only
blocks, its audience is its share setting, and a picture follows it.

- **Who may open a picture:** the file is stored as `media.UsageNoteImage`, and
  `Handler.checkNoteImageAccess` (media) asks `NoteService.ViewerReadsMedia`
  (`NoteRepository.ViewerReadsMedia`, the SQL twin of `Note.CanView` over the
  notes in `note_pictures`). A row is written only when the uploader saves a
  note whose stored body did not already name the picture: `UpdateWithPictures`
  reads the stored body under a row lock in the update's transaction (edits),
  `SyncPictureBindings` does it for a new note (send-to-journal). A restore binds
  nothing, so a picture whose binding was dropped stays openable by its uploader
  alone until re-added. Any save drops rows whose picture is no longer in the
  text (the cap of 200 limits inserts only). So an id someone else pasted opens
  nothing, even after the uploader saves that note, and re-sharing a note that
  merely names a picture id opens nothing. Private from the GM too. Keep
  `TestDB_ViewerReadsMediaMatchesCanView` green when the visibility rule
  changes.
- **Upload limits:** the route (`registerNoteJSONRoutes`, so both site and
  `/api/notes-app`) is limited to 30 per minute per IP. Each member may hold at
  most 200 note pictures and the smaller of 100 MB and a quarter of the
  campaign's storage quota per campaign, counting every `note_image` row they
  uploaded there, bound or not (`mediaService.checkNotePictureCap`). Over it:
  "Remove some pictures from your notes to add more"; deleting a note (or
  removing the picture and letting the orphan sweep run) frees space. The owner
  cannot remove a member's note pictures, and removing the member does not delete
  them.
- **Wiring** (`app/routes.go`): `PictureUploader` is `mediaUploadAdapter`;
  `noteMediaAccessAdapter` feeds the media handler; pinned by
  `TestRoutes_WiresNotePictures`.
- Version history is not searched: a picture removed from a note's body is no
  longer openable by its other readers (the uploader keeps it), though an older
  version still names it.

## Audio attachments

Audio files on journal notes. The upload handler pipes the multipart file
through `MediaUploader` (an adapter over the media plugin's `UploadRaw`, wired
via `mediaUploadAdapter`), inheriting MIME validation, the magic-bytes check and
quota enforcement, then creates the `NoteAttachment`. Allowed types are the audio
entries of `AllowedMimeTypes` (`internal/plugins/media/model.go`).
`AttachmentRepository` and `AttachmentService` (`repository.go`, `service.go`)
cover create, list, get, delete and `UpdateTranscript`.

## The Journal (`journal.templ`, `journal.js`)

`journal.templ` holds the layout; `journal.js` fills it from the JSON routes and
never decides visibility. `ShowJournal` must render through `middleware.Render`
(the layout injector supplies the session for the chrome and `data-user-id`);
`TestShowJournal_RendersThroughTheLayoutInjector` pins it.

- **List pane:** `GET /index` once, then `journal_list.js` filters, groups and
  sorts in the browser (`test/js/journal_list.test.mjs`). Search takes free text
  plus tokens (`in:`, `by:`, `links:`, `is:`, `has:audio`, `before:`/`after:`);
  Titles/Contents switches to the server's `/search`. Tabs: All, saved views
  (per campaign, `localStorage`), Archive. The View fold sets group (folder,
  linked page, owner, month, visibility), sort, direction, density and
  show-archived. Pinned notes form their own first group. Empty folders show as
  headers until something narrows the list; a folder's owner gets a header menu
  (new note here, rename, who can see it, delete: contents move to the top level
  first).
- **Rows:** drawn in chunks of 60 on scroll. The hover peek shows after a 300 ms
  rest (at once on keyboard focus), never takes the pointer, and is off on touch.
- **Selection:** hover circle, Ctrl/Cmd-click, Shift-click range, or long press;
  the bulk pill archives, moves, sets visibility or deletes through
  `POST /bulk`. Delete is unconfirmed: rows leave at once and the request is held
  for the Undo toast's 6 s (sent at once, `keepalive`, if the page is left).
- **Resize:** four snap sizes (collapsed, compact, normal, wide) by dragging the
  edge, its button, or arrow keys; kept in `localStorage`
  (`chronicle.journal.listSize`). Width never animates. The grab zone sits on
  the editor's side so the list's scroll bar stays grabbable. Wide leaves the
  editor 260 px, less the docked drawer's 280 px.
- **Editor:** TipTap with `MentionLink` (`@` and page links),
  `Chronicle.NoteLink`, task lists and the `[[` picker (`WikiLinkExtension`:
  visible unarchived notes, then pages from entity search). Autosave after 1.5 s
  idle, on blur, on switching notes and on leaving. A note others can see takes
  the edit lock when editing starts; a note someone else holds opens read-only
  with an "Editing: ..." badge (the GM can unlock). One button names the
  audience and opens the sharing menu (`openVisMenu`); a move to the party asks

- **Drawer:** links out (note labels per viewer), backlinks (`/backlinks`: notes,

- **Look:** the `.jnl` tokens in `input.css` alias the theme's colour, elevation

## Links, backlinks and search

A body links out through anchors in `entry_html`: `a[data-note-id]` is a
`[[link]]` to a note, `a[data-mention-id]` a link to a page. A note link never
stores the target's title: its text is the fixed `NoteLinkText`, and every reader
labels it through their own visibility (`Labels`, the index, `PlainText`'s label
function), so no copy of the HTML (export, REST API, old version, page) can carry
a title its reader may not see. `links.go` parses anchors with `x/net/html`; the
sanitizer keeps `data-note-id` only when id-shaped.

Index, search, backlinks and page references all start from
`ListVisible`/`ListVisibleLinking`, so a snippet, title or count only comes from
a note the viewer can open.

Pages link to notes the same way: the page editor (`editor.js`, also posts and
character descriptions) has `Chronicle.NoteLink` and the `[[` picker (the
viewer's visible unarchived Journal notes from `/index`, then pages); reading,
a note link is labelled for the reader and opens the Journal, and a posts list
labels them with `hydrateNoteLinks`. Pages linking a note appear in its
backlinks through `PageLinker` (`page_links.go`, the same `notesPagesAdapter`):
pages the viewer may see, names only, and for a viewer who is not the owner or a
Co-DM no page whose only link sits inside an inline secret.

## Real-time sync

`NoteEventPublisher` receives a `NoteEvent` (ids and an `Audience`, never the
note) after every create, update (including toggles and restores) and delete.
`noteEventPublisherAdapter` in `app/routes.go` puts `{noteId, entityId}` on the
wire as `note.created`/`note.updated`/`note.deleted`, with no `id` key, narrowed
to the audience: no list for a party note; otherwise the named users, with
`StrictAudience` so the GM's socket is excluded unless the note is shared with
the GM. An update that changes the audience reaches the old and the new one, so a
viewer who lost access refetches and drops the note. Clients refetch over HTTP,
where `CanView` decides. Pinned by `internal/app/note_events_test.go` and
`TestEvents_CarryAudienceNotContent`.

## Access control

`Note.CanView`/`Note.IsOwnedBy` are the one read and ownership implementation;
do not re-derive. `CanView` takes a `permissions.Viewer` built from
`VisibilityRole` (DM access counts as GM) and never consults
`SkipsPerUserRules`: private is private from the GM too. Its SQL twin is
`visibleFilter`; `TestDB_ListVisibilityMatchesCanView` runs both over the same
rows.

The service and repository address a note by bare `WHERE id = ?`, so the handler
is the single-note gate: `viewableNote` loads and applies `CanView` (404, never
403, so a response does not confirm a hidden note) on every route including
versions (a version must belong to the note in the URL), attachments and
force-unlock. `syncapi/note_api_handler.go` applies the same predicate with the
API caller's live role (`SetCampaignService`). Pinned by `handler_access_test.go`
and `syncapi/note_ownership_test.go`.

**Folders.** A note may be filed only into a folder of the same campaign that its
owner can view, never into itself or its own subtree (`checkFolderTarget`).
Deleting a folder moves other people's notes in its subtree to the top level
first (`rescueForeignChildren`), so only the folder owner's notes are removed.

**`GET /campaigns/:id/notes/members`** returns `memberRef` =
`{user_id, username, role}`. The share picker (`notes.js`) must read those exact
keys: `members_api_shape_test.go` asserts a bare array with `user_id`/`username`/
`role` and neither `id` nor `name`, and `test/js/notes_share_picker.test.mjs`
parses the json tags off `type memberRef struct`. Renaming either side reddens
both.

**`ListSharedByCampaign` (repository + service) is the only list method with no
per-user filter**: the shared-note corpus is campaign data. Its single caller
(`noteExportAdapter`) is owner-gated and no HTTP route reaches it. Exposing it to
a handler re-opens a cross-user read.

## Export / import

Only `is_shared=TRUE` notes leave the instance; `shared_with` ids are dropped
(they name users absent from the destination) and personal notes never leave.
Checklist content lives only in the legacy `content` blocks, so `ExportNote`
carries it. Folder membership travels as a `parent_index` into the notes slice
(ids are not stable across instances); import runs two passes (create flat, then
re-parent) since a folder may follow its children. `entry`/`entry_html` are
applied through `Update` on import so imported HTML meets the sanitizer. Pinned
by `internal/app/export_notes_roundtrip_test.go` and
`internal/wire/export_adapter_wiring_test.go` (an AST pin requiring `routes.go`
to call every export/import setter).
