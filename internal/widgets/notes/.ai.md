# Notes Widget

## Purpose
Notes for everyone in a campaign, on two surfaces that read one table: the
full-page **Journal** (`/campaigns/:id/journal`, notes with no page, in
folders, linked with `[[links]]`) and the floating **Jot notes** panel (notes
on a page, "jots"). Each note has an owner and one of four audiences (see
Visibility).

## Architecture
- **Tier:** Widget (with full backend)
- **Addon slug:** `notes` gates the Jot notes panel (off by default); the
  Journal route is open to every member
- **Backend:** handler → service → repository → MariaDB `notes` + `note_versions` + `note_attachments`
- **Sync API:** Full CRUD at `/api/v1/campaigns/:id/notes` (via `internal/plugins/syncapi/note_api_handler.go`)
- **Frontend:** `static/js/widgets/journal.js` (the Journal), `journal_list.js`
  (its pure list rules), `editor_notelink.js` (`[[links]]`), `notes.js` (the
  Jot notes panel)

## Data Model

### notes table (baseline + migration 000031)
- Per-user, per-campaign. `entity_id` NULL = a Journal note (or folder);
  set = that page's jot. The two surfaces read the same table.
- Content is a JSON array of blocks: `[{type: "text", value: "..."}, {type: "checklist", items: [...]}]`
- Rich text: `entry` (ProseMirror JSON) + `entry_html` (pre-rendered HTML) dual storage
- Sharing: `is_shared` (party), `shared_with` (JSON user ids), `shared_with_gm`
- `archived_at` (NULL = active), `linked_note_id` (a jot sent to the Journal)
- Collaboration: `last_edited_by`, `locked_by`, `locked_at`
- Pinned notes sort first, then by `updated_at` DESC

### note_versions table (migration 000022)
- Snapshot of note content at a point in time (title, content, entry, entry_html)
- FK cascade delete from `notes.id`
- Max 50 versions per note (`MaxVersionsPerNote`), oldest auto-pruned

### note_attachments table (migrations 000005 + 000032)
- Per-note audio file attachments (voice memos, session recordings)
- `id`, `note_id` (FK CASCADE), `campaign_id`, all CHAR(36)
- `file_path`, `original_name`, `mime_type`, `file_size`
- `duration_secs` (INT nullable), `transcript` (LONGTEXT nullable — manual or AI-generated)
- `created_at`, `updated_at`

## Key Features

### Core
- **Two surfaces:** the Journal (below) for notes with no page, and the Jot
  notes panel for notes on a page (see "Jot notes")
- **Checklists:** task lists in the rich text; older notes' checklist blocks
  stay tickable through the toggle API
- **Color:** a note's `color` is the left edge of its jot card

### Visibility
Four audiences, derived from three columns (`Note.derive`), so every row
written before the GM audience existed keeps its audience:

| Visibility | Columns | Who besides the owner reads it |
|---|---|---|
| `private` | none set | nobody, the GM included |
| `gm` | `shared_with_gm` | the campaign Owner and co-DMs (`VisibilityRole` ≥ Owner) |
| `party` | `is_shared` | every member |
| `custom` | `shared_with` | the named people |

- New notes are private. `UpdateNoteRequest.visibility` sets all three
  columns together (`applyVisibility`); the older `isShared`/`sharedWith`
  fields still work (`applyLegacySharing`) for the Foundry module.
- Anyone who can view a note may edit its title and body. Only the owner may
  change its visibility, pin, archive it, file it into a folder or delete it
  (`UpdateNoteRequest.StripOwnerOnly`, applied by both route sets).
- Archiving unpins; `archived` is derived from `archived_at`.

### Pessimistic Edit Locking
- **Lock acquisition:** When editing a shared note, the widget POSTs to `/lock`
  before entering edit mode. If another user holds the lock, edit is denied.
- **Heartbeat:** 2-minute interval keeps the lock alive (server timeout is 5 min)
- **Lock release:** On "Done" click or panel close, the lock is released
- **Stale lock reclamation:** Locks older than 5 minutes are automatically
  reclaimed by the database query
- **Force unlock:** Campaign owners can force-unlock via `/force-unlock` endpoint
- **Lock indicator:** Locked-by-another notes show a lock icon, edit button hidden

### Version History
- **Snapshot-on-save:** Every `Update` and `RestoreVersion` saves the current
  state as a version before applying changes
- **Version list:** Sub-panel shows version history with title and timestamp
- **One-click restore:** Restoring a version creates a pre-restore snapshot,
  then applies the old version's content
- **Auto-pruning:** Oldest versions beyond `MaxVersionsPerNote` (50) are deleted

### Rich Text
- **Dual storage:** `entry` stores ProseMirror JSON, `entry_html` stores
  pre-rendered HTML (sanitized server-side)
- **Display:** When `entryHtml` is present on a note (view mode), it's rendered
  as HTML; legacy block content is used as fallback
- **Editing:** both surfaces edit text in TipTap. The Journal writes checklists
  into the rich text as task lists (`ul[data-type=taskList]`; the sanitizer
  keeps `data-type`/`data-checked` on `ul`/`li`, not the checkbox) and shows a
  note's legacy checklist blocks under the body, still tickable through
  `/toggle`. The Jot notes panel edits with the same editor, node types and
  pickers, and shows a jot's legacy checklist blocks the same way.

## Jot notes (`notes.js`)

Registered as `Chronicle.register('notes', ...)` and mounted by `NotesWidget()`
in the app layout on every campaign page (addon on, signed in):
`<div data-widget="notes" data-campaign-id data-entity-id data-user-id>`.
`data-entity-id` comes from the **request path** (`layouts.GetRequestPath`),
not the active path, because a page's handler may point the active path at
its category for the sidebar; `TestNotesWidget_EntityIDFromTheRequestPath`
pins it. The widget re-mounts when a boosted navigation changes the page.

- **One way in:** a small "Jot notes" tab bottom-right with this page's
  count (the topbar has no notes button; `TestTopbarHasNoNotesButton`). The
  tab hides while the panel is open; Escape closes the panel (an open popover
  first) and returns focus to the tab.
- **Panel:** This page / All my jots (All only, off a page), "N Journal notes
  reference this page" (`/page-refs`, 12 listed, then a link to the Journal
  filtered by `?links=<page id>`), a filter field, flat cards (pinned first,
  then most recent; each card on All names its page via `/page-names`), and
  "New jot on this page". Pin the panel to reopen it on every page
  (`localStorage` `chronicle_jots_pinned`); collapse to the header; resize by
  the top-left corner and S/M/L text on desktop (`localStorage`); on a phone
  it is a bottom sheet from 18% down.
- **Cards:** tools (share, history, edit, delete) show on hover or focus
  where the pointer hovers, always on touch. The owner sees Pin/Unpin and
  Send to Journal / Open in Journal. Sharing is the same four audiences as
  the Journal. Editing uses the Journal's editor and autosave, and takes the
  edit lock on a jot others can see.
- **Send to Journal** (`SendToJournal`, `jots.go`): the jot's owner only,
  and only a jot. It makes a new, **private** Journal note titled like the
  jot: a first line linking the jot's page (named as the sender sees it,
  through `PageNamer`), then the jot's text, its checklist blocks as a task
  list. The jot records it in `linked_note_id`, so the card turns into Open
  in Journal. Sending again returns that note while it exists and the caller
  can see it; otherwise a new one is made.
- **Page names:** `PageNamer` is implemented in `app/routes.go`
  (`notesPagesAdapter`) over the entities service: a page of another
  campaign or one the viewer may not see (`CheckEntityAccess`) is left out,
  so the panel says "on a page" instead of leaking a name.
- **Journal hand-off:** `/journal?links=<page id>` opens the Journal with a
  `links:` token for that page, then drops the query from the address.

## Notes in Foundry (app grants)

A player lets the Foundry notebook use their notes with one Allow click. The
grant reaches the notes JSON routes and nothing else, always as that player
at their live campaign role.

- **Allow window** (`allow_app.templ`, `app_grants_handler.go`):
  `GET /campaigns/:id/notes/allow-app?origin=` is opened by Foundry as a
  popup. Allow is offered only when `origin` is exactly the site address or
  an admin-allowed CORS origin (`OriginAllower`, wired in `app/routes.go` to
  the same list the CORS middleware reads). `POST` makes the grant and
  returns the token once; the page hands it to `window.opener` with
  `postMessage(…, origin)`, so a window at any other address gets nothing,
  and no grant is made without an opener. The page sets
  `Cross-Origin-Opener-Policy: unsafe-none` (the site default `same-origin`
  would cut the opener); framing stays forbidden. It also lists the player's
  connections with Disconnect (`GET`/`DELETE /notes/app-grants`).
- **Grants** (`app_grants.go`, table `notes_app_grants`): `cnt_` + 256 random
  bits; only the SHA-256 is stored. One campaign each. Ten live per player
  per campaign (the oldest past that are revoked); unused for 90 days ends
  one; `last_used_at` is written at most every 5 minutes.
- **App routes**: `/api/notes-app/campaigns/:id/notes/*`, the same handlers
  as the site through `registerNoteJSONRoutes`. `RequireAppGrant` reads
  `Authorization: Bearer`, refuses a grant for another campaign, and sets a
  session carrying only the user id (never site admin); then
  `RequireCampaignAccess` checks live membership: while the player is out of
  the campaign the grant is refused (it is not revoked, so it works again if
  they rejoin). The campaign's Sync API switch gates the group (`AppGate`,
  wired in `app/routes.go`), and a disabled account's grants stop at once
  (the token look-up joins `users.is_disabled`). Every grant a player holds
  is revoked whenever all their sessions are destroyed (password reset or
  change, email change, admin force sign-out), through
  `auth.OnSessionsRevoked`. A per-IP limit runs before
  the look-up. Under `/api/` because there is no cookie to forge: the CSRF
  check skips `/api/`.
- **Allow window without an opener:** signing in on the way can cut the
  link to Foundry (the sign-in pages keep `same-origin` COOP), so the page
  checks `window.opener` on load and asks the player to click the notebook
  button again instead of offering Allow.

## Audio Attachments

Audio file attachments for journal notes.

### Backend
- **`MediaUploader` interface** in `handler.go` — adapter wrapping the media plugin's `UploadRaw` method
  for multipart file uploads. Wired in `app/routes.go` via `mediaUploadAdapter`.
- **`AttachmentRepository`** interface in `repository.go` — CRUD for `note_attachments` table.
  Methods: `CreateAttachment`, `ListByNote`, `FindAttachmentByID`, `DeleteAttachment`, `UpdateTranscript`.
- **`AttachmentService`** interface in `service.go` — business logic layer.
  Methods: `ListAttachments`, `GetAttachment`, `CreateAttachment`, `DeleteAttachment`, `UpdateTranscript`.
- Upload handler reads multipart file, pipes through `MediaUploader` (inherits media plugin's
  MIME validation, magic bytes check, quota enforcement), then creates `NoteAttachment` record.
- Allowed audio MIME types: `audio/mpeg`, `audio/ogg`, `audio/wav`, `audio/webm`.

## The Journal (`journal.templ`, `journal.js`)

`journal.templ` holds the whole layout; `journal.js` fills it from the JSON
routes and never decides visibility itself. `ShowJournal` must render through
`middleware.Render` (the layout injector supplies the session for the chrome
and `data-user-id`); `TestShowJournal_RendersThroughTheLayoutInjector` pins it.

- **List pane:** `GET /index` once, then `journal_list.js` filters, groups and
  sorts in the browser (`test/js/journal_list.test.mjs`). The search field
  takes free text plus tokens (`in:`, `by:`, `links:`, `is:`, `has:audio`,
  `before:`/`after:`); Titles/Contents switches to the server's `/search`.
  Tabs: All, saved views (per campaign, in `localStorage`), Archive. The View
  fold sets group (folder, linked page, owner, month, visibility), sort,
  direction, density and show-archived. Pinned notes always form their own
  group first. Empty folders show as headers until something narrows the list;
  a folder's owner gets a menu on its header (new note here, rename, who can
  see it, delete: its contents move to the top level first).
- **Rows:** drawn in chunks of 60 as the list scrolls. The hover peek shows
  after a 300 ms rest (at once for keyboard focus), never takes the pointer,
  hides the moment the row is left, and is off on touch.
- **Selection:** hover circle, Ctrl/Cmd-click, Shift-click range, or a long
  press on touch; the bulk pill archives, moves, sets visibility or deletes
  through `POST /bulk`. Delete is not confirmed: the rows leave at once and
  the request is held back for the Undo toast's 6 s (sent at once, with
  `keepalive`, if the page is left).
- **Resize:** four snap sizes (collapsed, compact, normal, wide) by dragging
  the edge, the button on it, or arrow keys on it; remembered in
  `localStorage` (`chronicle.journal.listSize`). The width never animates.
- **Editor:** TipTap with `MentionLink` (`@` and page links), `Chronicle.NoteLink`,
  task lists and the `[[` picker (`WikiLinkExtension`: visible, unarchived
  notes, then pages from entity search). Autosave after 1.5 s idle, on blur,
  on switching notes and on leaving. A note others can see takes the edit
  lock when editing starts (heartbeat every 2 minutes); a note someone else
  holds opens read-only with an "Editing: …" badge (the GM can unlock).
  Sharing chips, pin and archive show only to the owner.
- **Drawer:** links out (from the editor; note labels per viewer), backlinks
  (`/backlinks`: notes, 25 shown, then a `links:` filter; then the pages
  that link the note), version history with
  restore, audio (upload from the toolbar, play, transcript, remove).
- **Phone:** Notes / Note / Links tabs, one pane at a time.
- **Players:** a "Playing …" card for a claimed character (`CharacterLister`,
  an adapter over the entities service in `app/routes.go`), with a
  "Foundry: soon" badge: mirroring is not built.
- **Live:** the campaign WebSocket's `note.*` events (ids only) refetch the
  list; the open note reloads only when someone else changed it and nothing
  is unsaved here.
- `/journal/:noteId` opens a note (the href of every note link); the page
  keeps the address in step with `history.replaceState`. While mounted,
  `Chronicle.openJournalNote(id)` lets the Ctrl/Cmd+K search open a note in
  place.

## Links, backlinks and search

A body links out through anchors in `entry_html`: `a[data-note-id]` is a
`[[link]]` to another note, `a[data-mention-id]` a link to a page. **A note
link never stores the target's title** — its text is the fixed word
`NoteLinkText` — and every reader labels it through their own visibility
(`Labels`, the index, `PlainText`'s label function). So no copy of the HTML
(export, REST API, an old version, a page) can carry a title its reader may
not see. `links.go` parses anchors with `x/net/html`; the sanitizer keeps
`data-note-id` only when id-shaped.

The index, search, backlinks and page references all start from
`ListVisible`/`ListVisibleLinking`, so a snippet, a title or a count can
only come from a note the viewer can open. Versions are added only for
content edits (title or body), not for pin, share, file or archive.

**Pages link to notes the same way.** The page editor (`editor.js`, also
used for posts and character descriptions) has `Chronicle.NoteLink` in its
schema and the `[[` picker (the editor's own visible, unarchived Journal
notes from `/index`, then pages); reading, a note link is labelled for the
reader and opens the Journal, and a posts list labels them with
`hydrateNoteLinks`. The pages that link a note come into its backlinks
through `PageLinker` (`page_links.go`), the same `notesPagesAdapter` over
the entities service: pages the viewer may see, names only, and for a
viewer below Scribe no page whose only link sits inside an inline secret.

## Real-Time Sync

`NoteEventPublisher` receives a `NoteEvent` — IDs and an `Audience`, never the
note — after every create, update (including checklist toggles and restores)
and delete. `noteEventPublisherAdapter` in `app/routes.go` puts
`{noteId, entityId}` on the wire as `note.created` / `note.updated` /
`note.deleted`, with no `id` key, and narrows delivery to the audience: no
list for a party note; otherwise the named users, with `StrictAudience` so the
GM's socket is excluded unless the note is shared with the GM. An update that
changes the audience reaches the old and the new one, so a viewer who lost
access refetches and drops the note. Clients refetch over HTTP, where
`CanView` decides. Pinned by `internal/app/note_events_test.go` and
`TestEvents_CarryAudienceNotContent`.

## Access control

**`Note.CanView`/`Note.IsOwnedBy` on the model are the one read and ownership
implementation — use them, do not re-derive.** `CanView` takes a
`permissions.Viewer` built from `VisibilityRole` (a co-DM counts as GM) and
never consults `SkipsPerUserRules`: private is private from the GM too. Its
SQL twin is `visibleFilter` in the repository; `TestDB_ListVisibilityMatchesCanView`
runs both over the same rows.

The service and repository address a note by bare `WHERE id = ?`, so the
handler is the single-note gate: `viewableNote` loads and applies `CanView`
(404, never 403, so a response does not confirm a hidden note exists), for
every route including versions (a version must also belong to the note in the
URL), attachments and force-unlock. `internal/plugins/syncapi/note_api_handler.go`
applies the same predicate, resolving the API caller's live role through
`SetCampaignService`. Pinned by `handler_access_test.go` and
`internal/plugins/syncapi/note_ownership_test.go`.

**Folders.** A note may be filed only into a folder of the same campaign that
its owner can view, never into itself or its own subtree
(`checkFolderTarget`). Deleting a folder moves other people's notes in its
subtree to the top level before the database cascade runs
(`rescueForeignChildren`), so a delete only removes the folder owner's notes.

**`GET /campaigns/:id/notes/members` returns `memberRef` =
`{user_id, username, role}`.** The share-with-players picker
(`notes.js`) must read those exact keys — `members_api_shape_test.go` asserts
the body is a bare array with rows carrying `user_id`/`username`/`role` and
neither `id` nor `name`, and `test/js/notes_share_picker.test.mjs` parses the
json tags off `type memberRef struct` rather than hardcoding them. Renaming
either side reddens both files.

**`ListSharedByCampaign` (repository + service) is the only list method in
this package with no per-user filter** — deliberate: the shared-note corpus
is campaign data rather than a person's. It is owner-gated by its single
caller (`noteExportAdapter`) and reachable from no HTTP route. Exposing it to
a handler re-opens a cross-user read.

## Export / import

What leaves the instance: `is_shared=TRUE` notes only. `shared_with` target
user ids are dropped (they name users who don't exist in the destination).
Personal notes never leave. `checklist` content lives only in the legacy
`content` block field, so `ExportNote` carries it even though `entry`/
`entry_html` are the primary storage. Folder membership travels as a
`parent_index` into the notes slice, because note ids are not stable across
instances; import runs two passes (create flat, then re-parent) since a
folder may appear after its children. `entry`/`entry_html` are applied
through `Update` on import so imported HTML meets the sanitizer.

Pins: `internal/app/export_notes_roundtrip_test.go` and
`internal/wire/export_adapter_wiring_test.go` (an AST pin requiring
`routes.go` to call all twenty export/import setters).
