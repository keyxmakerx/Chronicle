# Notes Widget

## Purpose
Floating personal note-taking panel (Google Keep-style) that appears in the
bottom-right corner of campaign pages. Each user has their own private notes
within a campaign, optionally scoped to specific entities (pages). Notes can
be shared with all campaign members via the `is_shared` flag.

## Architecture
- **Tier:** Widget (with full backend)
- **Addon slug:** `notes` (disabled by default, owner enables per-campaign)
- **Backend:** handler → service → repository → MariaDB `notes` + `note_versions` tables
- **Sync API:** Full CRUD at `/api/v1/campaigns/:id/notes` (via `syncapi/note_api_handler.go`)
- **Frontend:** `static/js/widgets/notes.js` — self-contained floating panel

## Data Model

### notes table (migration 000017 + 000022)
- Per-user, per-campaign, optional `entity_id` scoping
- Content is a JSON array of blocks: `[{type: "text", value: "..."}, {type: "checklist", items: [...]}]`
- Rich text: `entry` (ProseMirror JSON) + `entry_html` (pre-rendered HTML) dual storage
- Collaboration: `is_shared`, `last_edited_by`, `locked_by`, `locked_at`
- Pinned notes sort first, then by `updated_at` DESC

### note_versions table (migration 000022)
- Snapshot of note content at a point in time (title, content, entry, entry_html)
- FK cascade delete from `notes.id`
- Max 50 versions per note, oldest auto-pruned

### note_attachments table (migration 000005)
- Per-note audio file attachments (voice memos, session recordings)
- `id` (CHAR(26) ULID), `note_id` (FK CASCADE), `campaign_id`
- `file_path`, `original_name`, `mime_type`, `file_size`
- `duration_secs` (INT nullable — for future metadata extraction)
- `transcript` (LONGTEXT nullable — manual or AI-generated transcript text)
- `created_at`, `updated_at`

## Key Features

### Core
- **Page-specific notes:** When viewing an entity, shows notes for that page
- **Campaign-wide notes:** General notes not tied to any entity
- **Checklists:** Interactive checkboxes with toggle API
- **Collapsible panel:** Minimizes to a small FAB, expands on click
- **Color coding:** Notes can have a color accent
- **Text size:** S/M/L settings gear (localStorage persistence)
- **Resizable panel:** Drag top-left corner to resize (localStorage persistence)

### Shared Notes (Sprint 4)
- **Share toggle:** Owner can make a note visible to all campaign members
- **Shared badge:** Non-owners see a users icon on shared notes
- **Access control:** Owner can edit all fields; non-owners can edit content only
  (cannot change pinned/shared status)
- **Delete:** Only the note owner can delete

### Pessimistic Edit Locking (Sprint 4)
- **Lock acquisition:** When editing a shared note, the widget POSTs to `/lock`
  before entering edit mode. If another user holds the lock, edit is denied.
- **Heartbeat:** 2-minute interval keeps the lock alive (server timeout is 5 min)
- **Lock release:** On "Done" click or panel close, the lock is released
- **Stale lock reclamation:** Locks older than 5 minutes are automatically
  reclaimed by the database query
- **Force unlock:** Campaign owners can force-unlock via `/force-unlock` endpoint
- **Lock indicator:** Locked-by-another notes show a lock icon, edit button hidden

### Version History (Sprint 4)
- **Snapshot-on-save:** Every `Update` and `RestoreVersion` saves the current
  state as a version before applying changes
- **Version list:** Sub-panel shows version history with title and timestamp
- **One-click restore:** Restoring a version creates a pre-restore snapshot,
  then applies the old version's content
- **Auto-pruning:** Oldest versions beyond `MaxVersionsPerNote` (50) are deleted

### Rich Text (Sprint 4)
- **Dual storage:** `entry` stores ProseMirror JSON, `entry_html` stores
  pre-rendered HTML (sanitized server-side)
- **Display:** When `entryHtml` is present on a note (view mode), it's rendered
  as HTML; legacy block content is used as fallback
- **Editing:** Rich text editing uses legacy blocks for now; full TipTap
  integration in the notes panel is a future enhancement

| DELETE | `/:noteId` | Delete | Delete note (owner only) |

## Audio Attachments (Sprint V-5)

Audio file attachments for journal notes. Foundation for future AI transcription.

### Backend
- **`MediaUploader` interface** in `handler.go` — adapter wrapping media plugin's `UploadRaw` method
  for multipart file uploads. Wired in `app/routes.go` via `mediaUploadAdapter`.
- **`AttachmentRepository`** interface in `repository.go` — CRUD for `note_attachments` table.
  Methods: `CreateAttachment`, `ListByNote`, `FindAttachmentByID`, `DeleteAttachment`, `UpdateTranscript`.
- **`AttachmentService`** interface in `service.go` — business logic layer.
  Methods: `ListAttachments`, `GetAttachment`, `CreateAttachment`, `DeleteAttachment`, `UpdateTranscript`.
- Upload handler reads multipart file, pipes through `MediaUploader` (inherits media plugin's
  MIME validation, magic bytes check, quota enforcement), then creates `NoteAttachment` record.
- Allowed audio MIME types: `audio/mpeg`, `audio/ogg`, `audio/wav`, `audio/webm`.

### Journal UI (`journal.js`)
- **Upload button**: Microphone icon (`<label>` wrapping hidden file input) in note toolbar.
  Accepts audio MIME types only.
- **Attachments area**: `#journal-attachments` div between editor and status bar in `journal.templ`.
  Hidden when no attachments.
- **Audio player**: Inline `<audio>` element with native controls per attachment.
- **Transcript**: Collapsible section per attachment with editable textarea and "Save transcript" button.
  Submits via `PUT /:nid/attachments/:aid/transcript`.
- **Delete**: Trash icon per attachment with confirmation dialog.
- Attachments auto-load when a note is selected (`loadAttachments` in `selectNote`).

### Journal @Mentions
The journal's TipTap editor now includes `MentionLink` mark (preserves `data-mention-id`
and `data-entity-preview` attributes) and `MentionExtension` lifecycle hooks (onCreate,
onUpdate, onKeyDown, onDestroy). Users can type `@` to search entities and insert mention
links with tooltip cards, matching the main entity editor's behavior.

## Real-Time Sync

`NoteEventPublisher` interface emits domain events when notes change:
- `note.created` — after Create
- `note.updated` — after Update
- `note.deleted` — after Delete

Implemented by `noteEventPublisherAdapter` in `app/routes.go` which publishes
to the WebSocket EventBus. External clients (Foundry VTT) receive these events
on their WebSocket connection for real-time sync.

## C-SWEEP-R3 findings (2026-08-07)

**`Note.CanAccess` / `Note.IsOwnedBy` on the model are the ONE ownership
implementation — use them, do not re-derive.** The sync API's note routes
(`internal/plugins/syncapi/note_api_handler.go`) served the identical caller
population as these web routes and checked only that the note belonged to the
campaign in the URL. The service and repository address a note by bare
`WHERE id = ?` with **no user predicate at any layer**, so the handler was the only
possible gate — and it was missing: any campaign member read any other member's
private journal, any Scribe overwrote or deleted it. The web route's predicate is
now lifted onto the model (owner, campaign-wide share, or explicit per-user share —
ADR-013); `canAccessNote` in this widget's handler delegates to it, and the API
handler gates `GET`/`PUT` on `CanAccess` and `DELETE` on `IsOwnedBy` (reading a
shared note is not authority to destroy it). `UpdateNote` on the API side also
strips `is_shared`/`shared_with`/`pinned` from a non-owner's patch so a share
recipient cannot re-broadcast someone else's note. Pinned by
`syncapi/note_ownership_test.go`.

**`GET /campaigns/:id/notes/members` returns `memberRef` = `{user_id, username,
role}` — and always has.** The share-with-players picker in `notes.js` read `m.id`
and `m.name`, and three failures compounded in one silent render: `escapeHtml`
maps `undefined` to `''` so every label was just the separator, `escapeAttr(m.id)`
put `value=""` on every checkbox, and the `m.id !== currentUserId` self-filter
excluded nobody because `undefined` never equals a user id. Ticking a row PUT
`{isShared:false, sharedWith:[""]}` — **the note was persisted shared with no one**,
with no error anywhere. Both ends are now pinned so the contract cannot drift
silently again: `members_api_shape_test.go` asserts the body is a bare array whose
rows carry `user_id`/`username`/`role` and **neither `id` nor `name`**, and
`test/js/notes_share_picker.test.mjs` parses the json tags off `type memberRef
struct` rather than hardcoding them, failing on any `m.<field>` read the struct does
not ship. Renaming either side reddens both files.

**CLOSED (C-SWEEP-R4 stage 15): shared notes now export and import, and the egress
ruling is narrower than any option the booking listed.** `ListSharedByCampaign`
(repository + service + the `NoteService` interface) is **the only list method in
this package with no per-user filter** — that is deliberate and it is the one thing
to check before touching it: the shared-note corpus is campaign data rather than a
person's, it is owner-gated by its single caller (`noteExportAdapter`), and it is
reachable from **no HTTP route**. If you ever expose it to a handler you have
re-opened a cross-user read.

What leaves the instance: `is_shared=TRUE` notes only. `shared_with` target user ids
are **dropped**, because they name users who do not exist in the destination.
Personal notes never leave — they belong to a person, and an export is handed to
whoever imports it. `calendar/rsvp_egress_test.go` still walks `CampaignExport` as
its root and still passes: the root widened by a `notes` field the envelope had
declared since v1, not by a new class of person-owned data.

Three details worth keeping: `ExportNote` carries `content` because **checklists live
only in the legacy block content**, so shipping notes without it would still have lost
every checkbox in the campaign; folder membership travels as a `parent_index` into the
notes slice (the trick `ExportEventConnection` already uses) because note ids are not
stable across instances; and import runs **two passes** — create flat, then re-parent —
since a folder may appear after its children. `entry`/`entry_html` are applied through
`Update` so imported HTML meets the sanitizer: an imported export is untrusted input.

Pins: `internal/app/export_notes_roundtrip_test.go` and
`internal/wire/export_adapter_wiring_test.go` (an AST pin requiring `routes.go` to call
all twenty export/import setters — the test that would have caught the original hole,
which was two setters nobody ever called).

**The original booking, for the reasoning it records:** ~~campaign export/import
silently omits all shared notes~~ — the
exporter and importer are never wired. It is not a plumbing gap: closing it needs a
new cross-user listing capability on this widget (repository + service + the
`NoteService` interface) and forces an **egress policy** ruling — which notes leave
the instance (`is_shared=TRUE` only? also `shared_with` notes, whose target user ids
do not exist in the destination instance? never personal notes?) and who owns an
imported note. That is the class governed by `.ai/decisions.md:1997` and pinned
structurally by `calendar/rsvp_egress_test.go`, which walks
`campaigns.CampaignExport` as its root — so widening that root is a deliberate,
signed egress change. Getting it wrong turns a data-omission bug into a data-leak
bug. See `C-EXPORT-IMPORT-FIDELITY`.
