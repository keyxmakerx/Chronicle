## What it is

Three reusable templ components shared by the calendar plugin's V2 surface and
any downstream consumer (Chronicle-DnD-5.5e, Chronicle-Draw-Steel, AI Workspace
event imports):

| Export | File | What it renders |
|---|---|---|
| `EventCard(data EventCardData, density Density)` | `event_card.templ` | One event, at 3 densities (Compact / Standard / Detailed) × 3 tiers (Minor / Standard / Major) |
| `MultiDayRibbon(data MultiDayRibbonData)` | `multi_day_ribbon.templ` | A horizontal ribbon spanning grid columns — also the era-band and session-block primitive |
| `VisibilityEditor(data VisibilityEditorData)` | `visibility_editor.templ` | The Q-V2-7 chip-row audience builder |

Exported types: `Density`, `Tier`, `EventCardData`, `MultiDayRibbonData`,
`VisibilityRule`, `VisibilityEditorData`, `UserOption`, `RoleOption`.
Everything in `helpers.go` is deliberately unexported — consumers compose the
components, never the class-string helpers.

## Architecture

**templ + Go only. Zero JS, zero CSS in this directory.** That is a deliberate
property, not an accident of history, and it is what makes the package
plugin-agnostic: it imports nothing from `internal/plugins/**`, so a game-system
package can render an `EventCard` without pulling in the calendar plugin.

The two consequences a contributor trips over:

1. **The animation classes live somewhere else.** `.lift-hover`,
   `.drawer-slide-in` / `.drawer-slide-out`, `.ribbon-enter`, `.drag-ghost`,
   `.drop-receive-pulse`, `.today-pulse`, `.tier-transition`, `.chip-add` /
   `.chip-remove` are all defined in `static/css/input.css` under the
   "V2 widget animations" section (`input.css:2490-2610`), each with a
   `@media (prefers-reduced-motion: reduce)` override. Emitting a class name
   here that has no rule there produces silently dead markup — Go will not tell
   you. Those rules consume the `--motion-fast` / `--motion-standard` /
   `--motion-leisurely` durations, which C-CALV4-FOUNDATION-P0 finally *defined*
   in `input.css` (at exactly the values their `var(…, 150ms)`-style fallbacks
   were already producing; the library had run on fallbacks since it shipped).

2. **The behaviour lives somewhere else too** — see the next section.

## The `data-visibility-*` contract (the load-bearing bit)

`visibility_editor.templ` emits a DOM contract and implements none of it:

```
data-visibility-editor          data-visibility-mode (on each radio)
data-visibility-field-prefix    data-visibility-specific-panel
data-visibility-available-users data-visibility-chip-row
data-visibility-available-roles data-visibility-summary
data-visibility-add             data-visibility-rules-json  (the hidden round-trip input)
data-visibility-picker          data-visibility-picker-kind / -input / -confirm / -cancel
```

**TWO INDEPENDENT JS DRIVERS consume it, both in the calendar plugin:**

- `internal/plugins/calendar/static/js/event_grid.js:1249-1420` — the drawer
  instance.
- `internal/plugins/calendar/static/js/calendar_permissions.js:62-180` — the
  modal instance.

They are separate implementations of the same contract, not one shared module.
Renaming or dropping an attribute here therefore breaks *two* call sites, in a
*different* package, with **no compile error and no test failure** — the Go
tests in this directory assert helper output, not DOM wiring. That asymmetry is
the whole reason this package is frozen for the v4 wave.

If the contract ever genuinely must change: update both drivers in the same PR,
and say so explicitly in the PR body.

## Conventions

- Every value resolves from a token — zero hardcoded hex, zero raw shadow rules,
  zero `transition: all`. `leftBarColor()` falling back to a CSS variable rather
  than a literal is the pattern to copy.
- Tier is a *prominence* model; `TierLabel` / `TierColor` on `EventCardData` are
  the Wave-1.6 §D campaign-aware overlay. Empty → platform-default rendering.
  Never branch on campaign identity inside the widget.
- `rulesToJSON` / `usersToJSON` / `rolesToJSON` are the serialization boundary.
  The client is free to re-render from them; the **server stays the authority**
  on render-time access checks. The effective-audience summary computed here and
  in JS is advisory UI, never an authorization decision.

## Consumers

`internal/plugins/calendar/` imports it as `calwidget` from `calendar_v2.templ`,
`calendar_v2_helpers.go`, `calendar_v2_ledger.go`, `app_dashboard.templ`, plus
`calendar_v2_tier_test.go` and `calendar_v2_events_test.go`. Note that
`calendar_v2.templ` and `calendar_v2_helpers.go` are themselves frozen for the
v4 wave and are dense with source-text pins.

## Test coverage

`helpers_test.go` + `event_card_test.go` cover tier classes and badges, ribbon
grid-column/tint computation, chip classes and labels, the five
effective-audience scenarios, rule-JSON round-trip, specific-panel toggling,
left-bar colour fallback, and the timed/untimed rt-hint marker. DB-level and
drag-interaction coverage lives in the consuming plugin
(`calendar_v2_events_test.go`).

**Not covered anywhere:** that the emitted `data-visibility-*` attribute names
match what the two JS drivers query for. That gap is the risk this document
exists to name.
