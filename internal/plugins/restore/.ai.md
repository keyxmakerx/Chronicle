# Restore Plugin

Admin UI for restoring a backup; mirror of `backup/`. The mechanics live in
`scripts/restore.sh` (POSIX shell). This package decides when it may run,
closes the whole site while it does (`internal/maintenance`), runs the script
against its own process, and opens the site again afterwards. Restoring is
destructive (drops and re-applies DB state): the request needs a recent reauth
and the literal confirmation `RESTORE`, and the script verifies the manifest's
sha256 first. See ADR-073.

## How a restore runs
1. `POST /admin/restore/run` checks reauth, the `RESTORE` text and that the
   request has a session, then `Service.Start`. Start validates the manifest,
   calls `maintenance.State.Enter` (which writes the marker file and refuses if
   it cannot) and returns; the rest runs in a goroutine on a context the
   browser cannot cancel.
2. From `Enter` on, the global gate answers every request except health probes,
   static files and the owning admin's session with a 503 (`maintenance` package).
3. `execute` waits for requests in flight, disconnects websockets (`Hooks.Quiesce`),
   then runs `restore.sh --manifest … --yes --force --from-inside` with
   `CHRONICLE_RESTORE_TOKEN` and `CHRONICLE_MAINTENANCE_FILE` in its environment.
   The script reads its own progress lines (`step=…`, `safety_backup=…`) as they
   are printed and the page shows them in plain words.
4. The script saves the current database first as
   `chronicle_pre_restore_manifest_<TS>.txt`, a manifest of its own that the
   restore list shows as "Before a restore". If that save fails the restore stops
   before the database is touched.
5. Pooled DB connections are reset (a dropped database leaves them with no
   default schema). On script success: `Hooks.Migrate` (same schema steps as a
   normal boot, wired in `cmd/server/restore_schema.go`), then `Hooks.FlushCaches`
   (derived Redis caches deleted, every session forced to re-check its user), then
   `State.Succeed`, which removes the marker and opens the site.
6. On any failure: `State.Fail`. The site stays closed, the marker is rewritten
   as `failed`, and the owner's page shows what happened, whether the database
   had been touched, the safety copy's name, the exact by-hand command and a
   "Leave maintenance anyway" button.

## Who gets through while closed
Only the session that started the restore. The gate compares the SHA-256 of the
session cookie to the hash stored in the marker (constant time), and serves
only `GET /admin/restore`, `GET /admin/restore/status` and
`POST /admin/restore/leave` for it, through `Handler.OwnerView`, with no router,
auth middleware or database (the database is what is being replaced).
Leaving needs the per-restore `leave_token` that only the owner's page carries,
plus a same-origin check, because global CSRF runs after the gate. Leaving is
refused while the restore is still running.

## After a process restart
`maintenance.NewState` reads the marker: `running` comes back closed as
"interrupted", `failed` comes back closed as failed (with the saved output). The
owner and leave token survive, the script's run token does not. `cmd/server`
tolerates migration and health-check failures at boot while a marker exists, so
the admin sees the page instead of a crash loop. A restore finished by hand with
`restore.sh` (site stopped) clears the marker.

## Key files
- `service.go` — `Start`, `execute`, `Leave`, `RunRestore` (script with timeout, process group, single-flight), `Hooks` and `ActivityRecorder` interfaces
- `handler.go` — `Page`, `Run` (owns the `RESTORE` check), `Status`, and `OwnerView` for the closed site
- `progress.go` — turns the script's stdout lines into the page's step text
- `manifest.go` — reads the manifests the page lists: `chronicle_manifest_*` (`scripts/backup.sh`), `chronicle_pre_migrate_manifest_*` (flagged `PreUpdate`, "Before update") and `chronicle_pre_restore_manifest_*` (flagged `PreRestore`, "Before a restore"); the path check accepts only these three
- `capbuf.go` — write-capped buffer for the script's output
- `routes.go` — `RegisterRoutes(admin, h, reauth, state)` mounts everything under `/admin/restore` and installs `OwnerView` on the state
- `restore.templ` — the admin page and the standalone `MaintenancePage` (no layout)

## Routes
- `GET /admin/restore` — restore dashboard (while closed, the owner gets `MaintenancePage` from the gate instead)
- `GET /admin/restore/status` — JSON progress for the poll, site admin only
- `POST /admin/restore/run` — `reauth`, then `RateLimit(3, 1h)`, then the `confirm=RESTORE` check (a wrong value is a 400)
- `POST /admin/restore/leave` — only reachable through the gate by the owning session

## Audit
`restore.started`, `restore.run`, `restore.failed` and `restore.left_maintenance`
go to the admin change log (with the admin's id, through `ActivityRecorder`) and
to the server log as `restore audit`. The change log lives in the database being
replaced, so `restore.started` is lost on success; the server log keeps it.

## Wiring
Constructed inline in `internal/app/routes.go` with the shared `App.Maintenance`
state, `restoreHooks` (`internal/app/restore_hooks.go`) and the admin change-log
adapter; registered via `restore.RegisterRoutes(adminGroup, restoreHandler, reauth, a.Maintenance)`. Auth
comes from the parent admin group. `GET /healthz` answers `{"status":"maintenance"}`
while closed, which is also one of three things the script checks.

## Not paused
There is no central way to pause Chronicle's background jobs, so none are
paused. The gate stops everything that arrives over HTTP; the daily backup, the
trash purger and the other schedulers keep their own timers and tolerate a
missing database by logging. A shared pause for schedulers is a follow-up.

## Dependencies
- `apperror` — domain error types
- `internal/maintenance` — the shared state and gate
- `scripts/restore.sh` at runtime — see `docs/deployment.md` §9 for the script's contract
