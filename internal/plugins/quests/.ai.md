# Quests Plugin

## Purpose

Two page blocks. **Quest board**: a quest page's cork board (notice, map scrap,
reward tag) plus a DM-only ledger, stored as one JSON sheet per page.
**Notice boards**: place pages (taverns, temples) and category pages (an entity
type's dashboard, e.g. Quests) hold up to 12 boards each that players
cycle through, pinned with quest notices, notes, pages, maps and string. The
services return only what the viewer may see; the widgets (`quest_board.js`,
`notice_boards.js`) only draw it.

## Tables

`quests` (sheet per page, `version`), `quest_board_pages` (looks per place
page), `quest_board_type_looks` (looks per category), `quest_boards` (`who`
dm/scribe/all; `fill`, the statuses it fills itself with, comma separated,
empty for hand-pinned; exactly one of `entity_id` / `entity_type_id` is set,
the board's home), `quest_board_items` (`kind`, `by_dm`, `hidden`, `ref_id`
with no FK; `auto_ref` set on a notice the board placed itself, unique per
board). All FK to core `entities` / `entity_types` / `campaigns` with cascade,
so deleting a category removes its boards.

| Method | Path | Who |
|--------|------|-----|
| GET | `/campaigns/:id/quests/:eid` | page viewers incl. public guests; DM team gets the full sheet |
| PUT | `/campaigns/:id/quests/:eid` | DM (`CanControlWorldState`), partial, `version` required, 409 on mismatch |
| GET | `/campaigns/:id/quests/picker?kind=page\|quest\|map\|character&q=` | members (`character`: DM only, claimed characters with `player`, every character when none is claimed); bare array, max 25 for pages |
| GET | `/campaigns/:id/notice-boards/:eid` | page viewers incl. guests |
| GET | `/campaigns/:id/category-boards/:tid` | anyone with campaign view access (a category page has no visibility of its own); `:tid` must be a category of the campaign, else 404 |
| (all other methods) | `.../category-boards/:tid/...` | the same routes, handlers and gates as `notice-boards/:eid/...` below |
| POST/PATCH/DELETE | `.../notice-boards/:eid/boards[/:bid]` | DM |
| DELETE | `.../boards/:bid/player-items` | DM; removes `by_dm=0` items except notices |
| PUT | `.../notice-boards/:eid/order`, `/looks` | DM |
| POST | `.../boards/:bid/items` | `canChange(board)` |
| PATCH/DELETE | `.../boards/:bid/items/:iid` | owner (while `canChange`), or manager |

The Foundry module reads and runs quests through the sync API
(`/api/v1/campaigns/:id/quests/...`, `syncapi/quest_api_handler.go`), which
calls these same services: `BoardService.Homes` lists the places with boards,
and its players copy reads as `PlainPlayer()`. AI Import's `quest` and
`notice-board` kinds use the same services as the DM (`QuestService.List`
reads every saved sheet), through `internal/app/ai_quests_adapter.go`.

## Permission matrix

canChange: `who=all` any member; `scribe` scribe+ or DM; `dm` DM only. Manager:
DM, or scribe on a `scribe` board. A notice pin needs DM, or scribe on a
`scribe` board. `hidden` is DM-settable only. Guests never write.

## Homes

`Home{EntityID, TypeID}` names where boards live (`PageHome`, `TypeHome`); the
repository refuses a Home with neither or both set. A type home passes only
the "category belongs to this campaign" check (`TypeDirectory`); everything
else (who can change, DM-only, hidden items, concealed pages) is identical.
The category dashboard draws the block through `entities.RegisterCategoryBlock`
(`internal/app/routes.go`), because entities cannot import this plugin.

## Lookups and the maps addon

Pages and maps are named in one query per load: `Entities` reads through
`entities.PageCards`, and `Maps` reads the campaign's map list once. With the
maps addon off (`MapDirectory.Enabled`; no addon row counts as off, as for the
maps routes) the adapter finds no maps, so map pins drop from boards, map
links lose their name, new ones are refused, and `mapsOn: false` in the board
and DM quest answers hides the map choices.

## Boards that fill themselves

A board's `fill` (PATCH `{"fill": ["not_started","active"]}`; `[]` or `null`
stops) pins a notice for every quest page whose saved sheet has one of those
statuses, and takes down its own notices (with their strings) when the status
moves away. Setting the list refills that board from every sheet in the
campaign (`QuestRepository.ListAll`); after that, `WithBoardFill` wraps
`QuestService.Put` and calls `BoardService.FillQuest` for the saved quest,
announcing each home that changed. A failed fill is logged and never undoes
the save.

- Every matching quest is pinned whoever may see it; `buildViews` filters per
  viewer as for any notice, so hidden, DM-only and named-player quests reach
  only the DM.
- A quest the DM pinned by hand is never pinned twice, and hand-pinned items
  are never touched. Clearing `fill` takes down only the auto notices.
- An auto notice cannot be taken down while the board fills (it would return
  on the next save); the DM hides it instead.
- A page counts once its sheet has been saved; a quest page never opened in
  its ledger has no row yet.
- New notices go four to a row (`fillSpot`); the 60-item cap still applies, so
  a full board shows what fits.

## Live updates

`WithAnnouncer` (`live.go`) wraps both services so each successful change is
announced through `Announcer` (implemented in `internal/app` over the websocket
bus): `quest.updated` and `notice_boards.updated`, ids only. A page a plain
player may not open (hidden, DM-only, or shown to named players only) is
announced to DM-equivalent sockets alone, since even its id would tell a
player it exists (so is a category home a player may not know of, checked
through `TypeDirectory`); those named players see changes on their next load. The
widgets refetch through their own routes, so the services still decide what
anyone sees.

## Due dates

A sheet may carry `dueDate` `{year, month, day}` on the campaign's primary
calendar, plus `dueEventId`, the calendar event that mirrors it. `Notice.Due`
stays free text for campaigns without a calendar.

- `CalendarDirectory` (`directory.go`) is the only door to the calendar; the
  adapter in `internal/app/quests_adapters.go` owns the date maths by calling
  `calendar.Calendar`'s own methods. With the calendar addon off or no calendar
  it answers nil: the DM view's `dueCalendar` is `null` and setting a date is 422.
- DM view: `dueCalendar` (name, today, months with leap days, leap rule) and
  `due` (`label`, `daysLeft`, negative when late). Player view: `due` only,
  hidden with the notice piece. Board notice items carry `daysLeft`, omitted
  without a due date.
- PUT `dueDate`: absent preserves, `null` clears, a value sets. A value is
  checked against the calendar (`|year| <= 1,000,000`, a real month, a day that
  month has that year) before anything is written.
- The event is "Due: <notice title>", all day, linked to the quest page,
  announced ahead. It is `dm_only` unless a plain player may open the page and
  the notice is shown (a hidden notice hides its due date on the sheet, so the
  calendar hides it too); a rename or a notice hide/show rewrites it.
- Write order: the event is saved before the sheet, so a failing calendar
  refuses the save (5xx) and changes nothing; a lost version race removes an
  event the save created. A cleared date's event is deleted after the sheet
  save and a failure is only logged.
- `SyncDueEvent` / `RemoveDueEvent` keep the event right when the page's
  visibility changes or the page is deleted. `internal/app` fans the entities
  plugin's `updated` / `deleted` events out to them in the background; a page
  with no due date costs one sheet read. A hard-deleted page's sheet is already
  gone, so its event can no longer be found.

## Footguns

- Every `:bid` / `:iid` lookup is scoped by home and campaign; a foreign id is a
  404. Keep new repo methods scoped the same way.
- Player GET shapes are separate types (`PlayerQuestView`); never add a DM
  field to them. Hidden items, notices of unviewable quests and strings with an
  omitted end are dropped; unviewable pages stay as anonymous `concealed` pins.
- Sheet text is plain text; the widgets must render it with `textContent`.
- Quest PUT is partial (absent preserves, explicit `null` clears only `mapId` and `dueDate`);
  pinned by `quest_service_test.go`.
- Item cap (60) and board cap (12) are count-then-insert, abuse limits only.
