# Transformations Plugin

## Purpose

Layers on a hero: a vampire's bite, rising as a revenant, a curse, a
polymorph. A layer names the sheet fields it changes; the hero's own fields
(which mostly come from Foundry) are never written, so taking a layer off puts
the hero back exactly as they were. Built against the signed mockup
`transformations-preview-2025`, option A (a Changes drawer on the sheet),
for Chronicle#2025.

This plugin stores and serves layers and knows no game's rules. The game
system's sheet draws what a change means (a weakness, a trait) and its data
holds the ready-made presets; the Draw Steel package ships Vampire Scion and
Revenant.

## A layer

```json
{ "name": "Revenant", "source": "drawsteel:revenant", "note": "",
  "changes": [
    { "field": "ancestry", "op": "set", "value": "Revenant" },
    { "field": "recoveries_max", "op": "add", "value": -2 },
    { "field": "features_json", "op": "append", "value": { "name": "Tough But Withered" }, "label": "Tough But Withered" },
    { "field": "features_json", "op": "remove", "value": "Staying Power" } ] }
```

- `field` is the sheet field's key as the game system names it
  (`^[a-z][a-z0-9_]*$`, at most 64).
- `op`: `set` replaces the value (text, number or object), `add` adds a
  number, `append` adds an entry to a list field (text, number or object),
  `remove` hides the list entry with that name (text).
- Choices a preset asks for (how a revenant's ancestry points are spent) are
  settled in the browser before Push, so stored changes are final.
- Layers apply oldest first. At most 20 per page, 40 changes per layer,
  4 KB per value; values are re-encoded so only valid JSON is stored.

## Presets of the Director's own

A preset the Director saves from the sheet is a Homebrew Workshop recipe
with one `transformation` part whose data is the layer (`{name, source,
note, changes}`), checked by `CheckLayer`, the same check `Add` makes. The
part is registered from `internal/app/transformations_homebrew_adapters.go`
while this plugin is healthy, with the client-run action
`put-on-transformation`: a rule never puts a layer on by itself, it waits in
the Homebrew drawer, and running it hands the game system's sheet the
recipe and the page the rule was set off on, so the Director previews it and
presses Push there.

## Who may do what

| | See a page's layers | Put one on, take one off |
|---|---|---|
| Anyone who can see the page | yes | no |
| Director (owner or granted co-DM) | yes | yes, when the page's own edit rule also allows it |

A hidden or missing page, and a page in another campaign, read as not found.
There are no drafts on the server: the Director's preview happens in the
browser and nothing is stored until Push.

## Routes

All behind the `transformations` add-on (`RequireAddon`; off answers 404,
which the sheet reads as "no layers").

| Method | Path | Does |
|--------|------|------|
| GET | `/campaigns/:id/pages/:eid/layers` | `{layers, canEdit}` |
| POST | `/campaigns/:id/pages/:eid/layers` | Put a layer on (body as above) |
| DELETE | `/campaigns/:id/layers/:lid` | Take it off |

The Foundry module reads the same `{layers, canEdit}` on the Sync API at
`GET /api/v1/campaigns/:id/entities/:eid/layers` (behind the same add-on),
through `ListForPage`, and draws each layer as one Active Effect on the
hero's actor. After a layer is put on or taken off, the service tells its
`Notifier` (`WithNotifier`); the app's publisher sends the GM side a
`hero_layers.changed` WebSocket message naming the page only.

## The AI's part

`ai.go` is this plugin's AI part (ADR-071), registered in
`internal/app/ai_kinds.go`: the `layer` block (put a layer on, or take one
off with `action: delete`; a layer is never changed in place) and the
`layers` lookup, which is also the connected AI's `transformations` tool.
Both go through `Service`, so the rules above hold, and both refuse while
the add-on is off. `PageFinder` (a page by the name an AI wrote) is
implemented in `internal/app` over the entities service.
