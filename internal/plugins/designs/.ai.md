# Designs Plugin

## Purpose

One library per campaign for what an Owner designs from Chronicle's known
parts, and the ways to share it: a share code, a link, or named owners on this
instance. Shop counter room themes (`room-theme`) are the first kind; the
crafting designs follow. A design is data only: a list of choices from known
parts, never a picture or markup.

## Routes (all Owner-only; players never reach any)

`/campaigns/:id/designs` GET list (`?kind=`, also returns the campaign's `systemId`), POST save.
`/designs/:did` GET, PATCH (partial: `name`, `note`), DELETE.
`/designs/:did/share` GET state (`code`, `linkOn`, `linkUrl`, `owners`), DELETE stop sharing.
`/designs/:did/share/link` PUT `{"on":bool}`; `/share/owners` POST `{"userId"}`; `/share/owners/:uid` DELETE.
`/designs/owners?q=` search owners; `/designs/shared-with-me?kind=`.
`/designs/code/preview` and `/designs/code/take` POST `{"code"}`.
`/designs/shared/:did/preview` GET and `/take` POST (a design named to the caller).
`/designs/link/:token` GET and `/designs/link/:token/take` POST `{"campaignId"}`: outside any campaign, signed-in only (the service requires the reader to own a campaign).

## Server gallery

An Owner publishes a snapshot of a library design to this instance's gallery with a name (60), a note (140) and a shown-as name (display name by default). Any campaign Owner browses, copies and reports. Routes, all Owner-only, under `/campaigns/:id/designs`:
`GET /gallery?system=all&kind=rooms|crafting&q=&page=` browse (visible entries only, 12 a page, newest first; default is the campaign's game system), `GET /gallery/mine`, `POST /gallery/:gid/copy`, `POST /gallery/:gid/report` `{reason: adult|spam|other, note}`, `DELETE /gallery/:gid` unpublish, `POST` and `PUT /:did/gallery` publish and "Update in gallery" (partial: absent keeps, `null` note clears).
Admin (site admins only, on the `/admin` group): `GET /admin/design-gallery` page, `GET /admin/design-gallery/entries?status=pending|visible|rejected` (rejected lists refused and taken-down entries; approve works on any non-visible one), `POST /admin/design-gallery/:gid/approve|reject|remove`. Each decision is written to the admin change log (`ActivityRecorder`; the campaign audit log needs a campaign, a gallery decision has none).

Checks run on every publish and update, on the free text only (the data is already validated parts). Clean text is `visible` at once; anything flagged is `pending` with stored reason codes. The publisher reads the reasons in plain words, never the matched term.
- **Maturity** (`gallery_terms.txt`, edit freely): text is lowercased, accents stripped, leetspeak undone (0 1 3 4 5 7 @ $), runs of 3+ repeated letters collapsed to 2, and a squashed-to-one variant is tried for terms with no double letter. Terms match as whole words or phrases; runs of three or more single letters ("s e x") and punctuation-joined forms ("s.e.x") are also read. Terms are never matched inside a longer word or across two plain words, so "Essex" and "open island" pass; the `[allow]` list is a second guard.
- **Spam**: a URL or domain-like text, an email, an `@handle`, `discord.gg`; 8+ letters of which over 70% are capitals; a run of 6+ identical characters; the name 3+ times in the note; more than 5 publishes or updates by one user in 24 hours; the same data (hash of kind + canonical data) already published by the same user.
- Free text inside the design data (every string value, recursively; `#hex` colours skipped) gets the maturity rule only, never the spam rules.
- A report is once per Owner on a visible entry (never your own); the third distinct report sets the entry `pending` with reason `reported`. Approve clears the reports.
- An update of a `rejected` or `removed` entry goes to `pending` with reason `resubmitted`, and a `pending` entry keeps its `reported` or `resubmitted` reasons through every update until an admin approves it; a clean update of anything else is `visible`. Publishing again over a refused entry, or publishing data an admin already refused, is the same.
- Unpublish deletes a `visible` entry only; a waiting, refused or removed one is kept (409), so unpublish-then-publish cannot wipe a review.
- Only `visible` entries are shown to anyone but the publisher (`GET /gallery/mine`) and admins (the queue). Pending, rejected and removed entries are NotFound to everyone else, for copy and report too.
- A copy is its own library row (`origin` `gallery`, no link back). A different game system is allowed with a gentle note, as a code is; the kind re-validates and `Lacks` is shown on the card.
- Unpublish deletes the entry; copies stay. Entries are snapshots: editing or deleting the library design changes nothing until the publisher updates.

## Game system package designs

A manifest's `designs` list (format: `docs/build/game-system.md`, loader: `internal/systems/package_designs.go`) ships read-only designs. The loader checks each entry's labels and file path at manifest load (a bad entry is dropped into `DesignWarnings`), and reads and validates the file through this plugin's kind registry when asked (`systems.PackageDesignsFor`; skip reasons show on the system diagnostics page). The plugin reaches it only through `PackageSource`, adapted by `designsPackageSource` in `internal/app/designs_wiring.go`; `designKindChecker` lends the kinds back to the loader (`systems.SetDesignKinds`).
- `GET /campaigns/:id/designs/package?kind=` the "From <system>" group: only the campaign's own system (none for no system or a custom one). Ids are `pkg-` + a hash of kind and file, never a library id, so rename, delete, share and publish of one are 404.
- `POST /campaigns/:id/designs/package/:pid/copy` "Save as my design": an independent library row, origin `package`, re-validated by the kind.
- `POST /campaigns/:id/designs/:did/suggestion` `{note (<=240), credit}` answers `{filename, suggestion}`; the page downloads `suggestion` as JSON. It is `{format: chronicle-design-suggestion:v1, system, designs: [manifest entries], data: {file: data}, messageForMaintainer?}`; `maker` is the Owner's display name only when `credit` is true. Only a design the Owner made (origin `made`) on the campaign's own system can be suggested, so a copy is never credited to the exporter (400 otherwise). A custom or absent system has no maintainer (400); the data is re-validated.
- The AI reads the group in `what: designs` as a read-only section with no block; it cannot change a package.

## Rules the service keeps (each is tested)

- Every call needs the campaign's **Owner** (`campaigns.RoleOwner` through `CampaignDirectory.Member`): a co-DM, player or stranger is refused 403 even if the route gate were missing.
- A design in another campaign is **404**, the same as a missing one. A design that is not shared is never confirmed to exist.
- Reading a design from outside its campaign needs: link on and token matches, or the reader is a named owner; **and** the reader is Owner of the campaign they copy into; **and** that campaign's `SystemID` equals the design's `system_id`. A link reader who owns no campaign is refused before the token is looked at.
- Naming an owner who has no campaign on the design's game system is refused with a plain message. Search needs 2+ characters, returns display name, a user handle and the de-duplicated game systems they own a campaign on (never campaign names or ids), never the searcher, never a disabled account, never a player.
- A **share code** is `chronicle-design:v1:` + base64url(JSON `{kind, system_id, name, maker_name, data}`), at most 16 KB decoded, unsigned on purpose (it works across instances). Import always re-validates through the kind and runs `Lacks`; a code from another game system imports with a warning, never silently.
- Turning the link on mints a new 128-bit token; off clears it. Stop sharing turns the link off and removes every named owner. Copies already taken stay: a copy is its own `design_library` row, with `origin` `code` or `shared` as a label only and no link back.
- A design whose source campaign is in the Trash or archived (`CampaignDirectory.Live`) is **not found** by link, by name and in Shared with me, for preview, take and listing; it returns when the campaign is live again.
- `origin_ref` is the maker's display name for a shared copy and empty for a code; it never holds a campaign name.
- A saved design's `system_id` is copied from the campaign when saved or taken, so it keeps its meaning if the campaign later changes system.
- Names are at most 60 characters, notes 140, makers 100; control characters are dropped. 500 designs per campaign.

## Adding a kind

A feature registers its kind on the registry app wiring owns (`newDesignKinds` in `internal/app/designs_wiring.go`, the `designKinds` variable in `RegisterRoutes`): `designKinds.Register("crafting-circle", kind)` where `kind` implements `designs.Kind`:

- `Validate(raw)` returns the canonical JSON or an error naming the part it refuses. The owning feature is the authority; this plugin never reads `data`.
- `Lacks(ctx, campaignID, raw)` returns plain sentences on what the receiving campaign lacks (a material, a shape), or none.

The crafting kinds are `crafting-circle`, `crafting-item-look` and `crafting-bench`; the crafting thread registers them when its plugin is up, with a wrapper around its own validator, so no plugin imports another. An unregistered kind is refused (400) on save, preview and take. Give the kind a label in `KIND_LABEL` in `static/js/widgets/design_library.js`.

## AI

`records.DesignKind` (`design`) saves a design or renames one, through the owner review; `records.DesignsLookup` (`what: designs`) lists the library with each design as a block. `records.GalleryLookup` (`what: gallery`) browses visible gallery entries, read only, without their data. None of them shares, publishes, reports, moderates or deletes anything. Adapted in `internal/app/ai_designs_adapter.go`.
