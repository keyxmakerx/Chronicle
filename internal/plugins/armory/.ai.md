# Armory Plugin

## Purpose
Item gallery plus shop economy for a campaign. Items are entities whose entity
type has `preset_category = 'item'`; the plugin adds named item collections
("instances") and a transaction log for shop purchases and transfers.

## Tables (own, core migrations)
- `inventory_instances` — named collections per campaign.
- `inventory_items` — links an entity to an instance with a quantity.
- `shop_transactions` — purchase/sale/transfer/gift/restock records.
- `stashes`, `stash_viewers`, `stash_items` — named campaign stashes (items and a
  money number), and the characters allowed to see each. No viewers = GM only.
- `item_moves` — history of every move (applied, pending, declined, failed); a
  `pending` row is a request waiting for the GM.
- `campaign_downtime` — the per-campaign switch; a missing row means closed.
- `shop_rooms` — one saved room layout (normalized JSON) per shop entity, for the shop room widget.
Items themselves live in `entities` / `entity_types`.

## Tables (own, plugin migration `migrations/`)
- `armory_item_shares` — one row per holder character, hidden item and player
  it was shared with; `made_grant` marks the row whose share added that
  player's view grant. Read only while the plugin's migrations are healthy.

## Architecture
- Gallery: `ArmoryService` resolves item type IDs (`ItemTypeFinder`), the repo
  returns candidate IDs with no visibility predicate, and the service narrows
  them with the entities plugin's `FilterViewableEntityIDs`
  (`EntityVisibilityFilter`) before paginating. The `?type=` filter can only
  narrow the item types, never widen them.
- Instances: `InstanceService` counts a collection's items through the same
  visibility filter per viewer; `AddItem` verifies the entity belongs to the
  campaign (`EntityCampaignChecker`).
- Transactions: `TransactionService` owns purchase/stock/currency logic.
  `TransactionReader` is the list read path: it blanks names of entities the
  viewer cannot see and 404s a shop they cannot see.
- Tags on cards and the tag filter come from `TagLister`. GM-only tags only at
  Owner visibility (Owner or DM-granted DM access), like the tags widget; below
  that, a `?tag=` slug the viewer isn't offered returns the empty result.
- Stashes and moves: `StashService` (`stash_service.go`, `stash_moves.go`) owns
  the rules. A user sees a stash if Owner/Scribe or if they own (claim) one of
  its viewer characters; an unseen stash is a 404. Moves are item or money
  between characters and stashes. Owner/Scribe moves, and any move while
  downtime is open, apply at once; otherwise the move is a `pending` request
  that only Owner visibility (Owner or DM-granted DM access, never a Scribe) can
  approve or turn down. `run` is the one apply path (immediate, approval and the
  sweep when downtime opens): campaign lock, debit the source with a
  held-enough check, credit the destination, restore the source and mark the
  move `failed` if the credit fails. Opening downtime applies pending requests
  oldest first; one that can no longer be covered is marked `failed`.
- Money is the game system's own sheet field on the character: the first
  numeric field keyed `gp`, `coins`, `gold`, `money` or `wealth`. A character
  type without one refuses money moves. Amounts are carried as cents. Stash moves
  only ever touch that one field.
- Purse (D&D 5e): when a character type has numeric `gp`, `sp` and `cp` (`ep`
  and `pp` join when present), the directory fills `EntityRef.Purse` (coin → field
  key; `MoneyKey` stays `gp`). `purse.go` holds the pure arithmetic: rates in
  copper (cp 1, sp 10, ep 50, gp 100, pp 1000), `toCp` (rounds up, so a price is
  never a fraction of a copper), `payFromPurse` (spends cp, sp, ep, gp, pp in
  that order, taking only as many of each coin as needed; the overpayment comes
  back as change in gp, sp, cp, never ep or pp)
  and `formatPurse` ("9 gp 7 sp 3 cp"). A gold-only sheet has no purse and pays
  from `gp` alone; `gp` cents are copper, so the two agree.
- Wealth (Draw Steel): a `wealth` money field is a threshold, never spent. A
  hero can buy when Wealth is at least the dearest unit price in the basket
  (currency is ignored); nothing is written and nothing is rolled back.
- Money edits outside a move: `MoneyHistory` (`money_history.go`) is the
  entities plugin's field-change observer, wired in `internal/app`. When a
  character's money field changes by any door but a stash move, it writes an
  `applied` `money` row to `item_moves` from the character to itself (amount
  = new − old, signed; `requested_by` = the source's user). The reason is the
  sentence shown in history, e.g. `Wealth changed 2 → 3 · in Foundry`, built
  from the field label and the change source (`changesource`): the source's
  label if it has one (a shop's), else "in Foundry" / "on the sheet" / "by an
  extension". `MoveSummary` shows that reason as-is for a self-move money row.
  A purse sheet logs one line comparing the whole purse before and after
  (`Purse 12 gp 3 sp → 11 gp 8 sp 3 cp · at a shop`) with the amount as the
  copper value gained or lost; a change in only cp, sp, ep or pp is logged, and
  coins that trade evenly are not.
  Not logged: stash-source writes (moves log themselves), an unchanged amount,
  non-characters, types without a money key, or a write that set no source.
  Visibility follows character history (whoever can act as the character, plus
  Owner/Scribe). `ShopPurchaseSource(ctx, userID, label)` marks a shop's own
  sheet write so its line reads the shop's label.
- Sync API surface: `StashAPI` (`stash_api.go`) answers the Foundry module as a
  named member (`actingUserId`). `ActorFor` builds the `Actor` from THAT member's
  real campaign role and DM-access grant (never the key's Owner role unless the
  member is Owner or DM-granted), non-members are NotFound, absent means the key
  caller. Only an Owner, or a caller with DM access, may name someone else (else
  Forbidden), because browser sessions use the same routes; so naming a player
  is a narrowing, never a widening.
  Endpoints are in the syncapi `.ai.md`; `internal/app` adapts the facade to
  syncapi's `StashAPIService`.
- Giving: the Owner (Owner visibility, never a Scribe) hands a character an
  Armory item or a map from the character page's "+ Give an item" button or an
  item card's "Give to..." menu entry (`stash_give.go`, `give_box.templ`).
  `Give` runs under the campaign lock and credits the character's Has Item line
  with `adjustCarried(+qty, allowDM)`, exactly as a move crediting a character,
  so the existing relation events reach Foundry. It is recorded in `item_moves`
  as an applied item row whose from and to are the same character
  (`Move.IsGive`; no ENUM changed). Because it is already applied, `run` refuses
  to replay one, `Move` still refuses from == to for everyone, and history
  readers show it through `giveSummary` ("You gave Mira 2 × Potion" to a GM,
  "Your GM gave you 2 × Potion" to the player; the sync API carries the same
  sentence). It publishes `stash.moved` for the one character. A map is given as
  an item: `HandoutStore` (wired in `internal/app/armory_give_adapters.go` over
  the maps and entities services) finds or creates an item entity named
  "Map: <map name>" assigned to that map, whose entry links `/maps/:mid`. A
  handout carries a `fields_data` marker no entity type declares
  (`chronicle_map_handout` = the map id) and only a marked one is reused (the
  oldest), so an item someone typed with the same name is never taken over.
  Every give, item or map, adds the receiving character's claimed player to
  the item's allow list (`AllowViewers`: a public item is left alone, a private
  one becomes custom with Scribe-and-up edit plus the player, a custom one
  gains the player), so a private item still shows on the player's panel and
  history; a character with no player adds nobody. History reads "gave you"
  only for the character's claimed player; other non-GM viewers read
  "<GM> gave <Character> ...". The claimed player is notified (`item_given`,
  "Your GM gave you ...", detail "On <Character>") through `GiveNotifier`,
  over the sessions notification store.
- The Give box: on the character page "Give an item" opens it in place, in
  the panel's `.ag-fold` above the item list; on an Armory card the ...
  menu (`.ag-pop`: "Add to collection..." for Scribe and up, "Give to..." for
  Owner visibility) turns into it. `GET /armory/give?character=` renders
  `GiveBox` (Armory items, searched server-side with `list=items&q=`, at most
  50 shown with "Showing 50 of N"; a map tab tagging maps the character
  holds), `?item=` renders `GiveCardBox` (characters with their player's
  name). `static/js/widgets/give_box.js` (`Chronicle.GiveBox`, loaded by the
  base layout) folds it, guards an unsent pick (a click outside or Escape
  shakes it and shows the amber warn bar), posts with the CSRF header and
  reads `armory-given` from the answer for the toast and the line to flash.
  The `ag-*` styles are in `static/css/input.css`. `HX-Trigger` values are
  ASCII-escaped (`triggerJSON`) because browsers read header bytes as
  Latin-1.
- Sharing a hidden item: on a hidden (custom or private) item a character
  holds, the character's claimed player gets "Share..." on the panel row. It
  opens `ShareBox` (one checkbox per other player's character in the party,
  one per player) in the row's `.ag-fold`; Save posts the checked players and
  the service sets exactly those view grants, under the campaign lock. Only
  a grant sharing added is ever taken back: `AllowViewers` returns which
  players it newly added, and only those rows get `made_grant`. Unchecking a
  player removes the row; its grant goes (`RevokeViewers`, which removes view
  grants only) unless another holder's share of the item still covers that
  player (ownership moves to that row) or that player holds the item too. The
  holder's own grant, a give's grant and a hand-set grant are never removed.
  The holder's player or Owner visibility may share; anyone else gets 403, an
  item the character doesn't hold or the caller can't see 404, a public item
  400. A save that changes anything writes an `item.shared` audit entry
  (`ShareAuditor`). Without a healthy plugin migration `Shares` is nil and
  sharing answers 400 and the link is not shown. A share ends with the
  holding: armory moves release it as they go, and a "Has Item" line deleted,
  lowered or made GM-only elsewhere reaches `ReleaseLetGoShares` through the
  relation event adapter in `app/routes.go`.
- Live events: the stash service publishes `stash.moved`, `stash.requested`,
  `stash.settled` and `downtime.changed` through `StashEventPublisher` after the
  campaign lock is released; `MoneyHistory` publishes `stash.money_changed`.
  Payloads are ids and statuses only (`stash_events.go`). `internal/app` sends
  them to DM-equivalent sockets and the change feed records them.
- A character's items are its "Has Item" relations (quantity in the relation
  metadata, other keys preserved); `HasItemStore` wraps the relations service.
- "Acting as" a character is Owner/Scribe, the claimed owner, or entity edit
  access (`BuyerAccessChecker`, with a stash-specific adapter).
- The entities plugin lazy-loads the character "Items and money" panel through
  its generic page-panel hook (`entities.PagePanel`), wired in `internal/app`:
  the "Items & Money" layout block, shown on its own only on player-character
  pages that place neither it nor Inventory.
- Shop rooms: a page has a shop only where the owner placed the Shop block
  (`shop_inventory`) in its layout; nothing mounts it on its own. It starts
  closed as a shopfront with a drawn door. Pointing at the door draws it
  closer; pressing it swings it open, its dark doorway grows until the block
  is black, the room swaps in behind the dark and fades up. A press outside
  closes it unless the basket has items.
  With Shadows on Full the room is lit: light comes from what is in it (forge,
  lamp, window, wall candles), floor shadows fall away from the nearest forge
  or lamp (`ShopRoomLight.castOffset`), glows flicker, the forge has flames and
  embers, dust drifts in window light and the anvil throws sparks. Lights warm
  up after you walk in, the room tilts a little toward the mouse (not while
  arranging, not on touch), and every loop follows MotionRest.
  In Arrange the GM can drag any furniture kind or decoration from a list into
  the room, or onto the bin that appears while dragging to remove it. Added
  furniture counts as moved by hand; hand-placed decorations are saved as
  `decor` (piece id, spot index, icon), take their spot ahead of goods, and
  are dropped with their piece. Any decoration can be picked up: picking up
  one the generator placed first keeps all of them where they stand as
  hand-placed ones and sets Decorations to None (`ShopRoomDecor.freeze`).
  Goods are dealt to spots shuffled with the hand-placed decorations still in
  them, so moving a decoration never sends the goods to other shelves.
  Each shop picks its look in Arrange (`look`: `lit`, `paper`; empty reads as
  lit). Paper (`static/js/widgets/shop_room_paper.js`) stands the same room up
  as a pop-up book of cut card from the engine's `room` model, seen from the
  front: every card faces the viewer, only walls that face the viewer are
  drawn, and side-wall pieces stand as front-facing cut-outs. Furniture,
  goods, decorations, keeper and sign fold up as you walk in, cast shadows
  away from the forge and lamps, warm up near them, and the price tag over a
  good leans back to face the viewer. With Shadows on Full a faint haze,
  window light on the floor and dust in the warm light give it atmosphere;
  the dust is off whenever the owner's motion setting is Calm or Off. Arranging and dragging work the same in
  both looks; paper maps the pointer onto the floor from four corner markers
  (`floorAt`) and picks small cards by their box (`hit`), since browsers
  hit-test 3D cards unreliably. Nothing in the paper book uses
  mix-blend-mode, which would flatten it.
  `ShopRoomService` (`shop_room_service.go`) stores the layout the
  `shop_room` widget draws. `NormalizeShopRoomLayout` (`shop_room_validate.go`)
  decodes into a typed struct, validates every field and re-marshals; the
  client's body is never stored. The icon allowlist (`shop_room_icons.go`) must
  match `static/js/widgets/shop_room_icons.js`. The shop must be in the campaign
  and have entity type slug `shop` (`ShopEntityChecker`); a read of a shop the
  viewer cannot see is a 404 via `EntityVisibilityFilter`. The layout only
  references goods by relation id.
  The sync API reads the same service for the Foundry module
  (`GET /api/v1/campaigns/:id/armory/shops/:eid/room`, see syncapi's `.ai.md`).
  Foundry buys through the sync API too (`/buyers`, `/buy` under the same
  path), with `ShopBuyService` called as the member the call names.
- Shop buying: `ShopBuyService` (`shop_buy_service.go`) lets a player spend a
  character's coins on a shop's "sells" listings. It shares the stash service's
  campaign lock and its money and Has Item helpers, so a purchase and a stash move
  cannot spend the same coins. Prices and currency come only from the listing
  metadata (a listing with no positive price is refused, never free); all lines must
  share one currency. How the basket is paid depends on `buyKind`: `purse` (5e sheet
  with several coin fields, paid by `payFromPurse` and written with
  `adjustPurse`, one field update for every changed coin, refused if any coin would
  go negative), `wealth` (above) or `coins` (one number). On a `gp` sheet, a
  basket priced in cp/sp/ep/gp/pp (case-insensitive) is converted through
  `toCp` first, so 5 sp costs half a gold; any other currency, and any other
  money field (`gold`, `coins`, `money`), is charged at face value. Quotes and
  the "price went up" check stay in the listing currency. Order under the lock:
  price the whole basket and check coins (no writes), reserve stock per line (`reserveStock` with `requireSells`),
  take the coins, credit the items, then write one `purchase` row per line with
  `buyer_entity_id`. Any failure before the log undoes the earlier steps in reverse
  (stock released by compare-and-set; a purse gets the inverse coin changes). A log row that fails to write is logged
  loudly, not undone. The mutation phase runs on a context that survives client
  disconnect. Who may buy: the Owner (Owner visibility) for any character, anyone
  else only for a character they claimed and may act as (a Scribe's edit rights do not
  reach another player's coins). A player buys at once only while downtime is
  open; while it is closed the basket is stored as a purchase request instead
  (see below). A hidden shop, a relation of another shop or campaign, a
  non-"sells" relation, a DM-only listing (for non-GM) and a good the buyer cannot see are all a 404.
- Purchase requests (`shop_request_service.go`, table `shop_purchase_requests`,
  core migration 000042): while downtime is closed, `Buy` by a non-Owner prices the
  basket only to refuse one that could never be bought, then stores
  `{relationId, quantity}` lines under the campaign lock and answers
  `{"status":"requested"}`. No coins, stock or items move, and coins are not
  checked yet. At most 10 pending requests per player (plain 400). The Owner
  approves (`POST /armory/purchase-requests/:rid/approve`), declines (`.../decline`),
  or opens downtime (`SetDowntime` calls `sweepRequests` under its lock, after the
  move sweep). An approval runs `applyBasket`, the same path as a live buy, as the
  requester with player visibility (the approval lifts only the downtime gate): shop
  visibility, character claim, coin field, listings, prices, currency, stock and
  coins are all read again. The request also stores the server-computed basket total
  and currency from when it was asked (`quoted_total`, `quoted_currency`): at apply
  time a higher total or a different currency fails the request with "The price went
  up since you asked." and spends nothing, while an equal or lower price is charged
  at the current (lower) price. A refusal at apply time marks the request `failed` with the plain reason
  and spends nothing; an internal fault stores a generic reason. Ordering: the row
  is claimed `pending -> applied` before the basket runs and rewritten to `failed`
  if it cannot go through, so a crash can lose a purchase but never charge twice.
  `stashService.purchases` (set by `NewShopBuyService`) is how the downtime sweep,
  the stashes page ("Requests waiting on you", `purchase_request_row.templ`) and the
  character panel/history (requests appear as `MoveLine`s carrying a `Summary`) reach
  requests. No websocket event is published for requests yet.
- Cross-plugin access is only through interfaces wired in `internal/app/routes.go`.
- All routes are gated by the "armory" addon.

## Routes (`routes.go`)
Public-capable, Player+ view:
- `GET /campaigns/:id/armory` — gallery (filters: `q`, `sort`, `tag`, `type`, `instance`, `page`)
- `GET /campaigns/:id/armory/count` — visible item count for the sidebar badge
- `GET /campaigns/:id/armory/shops/:eid/room` — `{"layout": <object or null>}`; 404 for a shop that is missing, not a shop, or hidden from the viewer

Authenticated:
- `GET /armory/instances` (Player+) — instances with viewer-visible counts
- `GET /armory/instances/manage` (Scribe+) — management panel fragment
- `POST /armory/instances`, `PUT|DELETE /armory/instances/:iid` (Scribe+); PUT is a partial update (absent keeps, null clears the description, present replaces)
- `GET /armory/items/:eid/collections` (Scribe+) — which collections hold an item, for the card menu
- `POST /armory/instances/:iid/items`, `DELETE /armory/instances/:iid/items/:eid` (Scribe+)
- `GET /armory/shops/:eid/buyers` (Player+) — `{"downtimeOpen","canBuyNow","buyers":[{"id","name","moneyKey","money":number|null,"kind":"coins"|"purse"|"wealth","moneyCp":number,"purse":{coin:count}}]}` (`kind`/`moneyCp`/`purse` only when they apply; `money` is the gp equivalent for a purse, Wealth for a hero); the caller's claimed characters, every character for Owner visibility; 404 for a hidden shop
- `POST /armory/shops/:eid/buy` (Player+) — body `{"buyerEntityId","items":[{"relationId":number|"numeral","quantity":1..99}]}` (1..50 lines, no duplicates); answers `{"status":"bought","spent","currency","moneyLeft","purseLeft","change"}` (`purseLeft`/`change` for a purse; a Wealth buy has no `spent`/`currency`), or `{"status":"requested"}` (nothing spent) for a player while downtime is closed; 400 `Not enough coin` / `Needs Wealth N` / `Items are priced in different currencies` / `This sheet has no coin field` / `You have 10 purchase requests waiting for the GM already.`, 403 for another player's character, 404 for anything not buyable
- `POST /armory/purchase-requests/:rid/approve|decline` (Player+ at the route, Owner visibility in the service, else 403) — HTMX 204 with the `armory-moved` signal and a toast (error toast when an approved request fails), else a redirect to the stashes page; 409 once answered, 404 for an unknown id
- `POST /armory/transactions` (Scribe+) — manual gift/transfer/restock
- `GET /armory/transactions` (Player+) — filtered list, names redacted per viewer
- `GET /armory/shops/:eid/transactions` (Player+) — per-shop list
- `PUT /armory/shops/:eid/room` (Owner) — replaces the whole layout, body max 64 KiB, answers `{"layout": <normalized>}`; not a partial update

Stashes and moves (Player+ at the route; the service decides what each caller
may see or do):
- `GET /armory/stashes` — stashes page (visible stashes; requests panel at Owner visibility)
- `POST /armory/stashes`, `PUT|DELETE /armory/stashes/:sid`, `PUT /armory/stashes/:sid/viewers`,
  `POST /armory/stashes/:sid/items` — Owner/Scribe management; `PUT` is partial (absent keeps, null clears)
- `GET /armory/stashes/:sid/history` — history of a stash the caller can see
- `GET /armory/move` — move dialog fragment; `POST /armory/moves` — move or request
- `POST /armory/moves/:mid/approve|decline` — Owner visibility only
- `GET /armory/give?character=<eid>|item=<eid>[&q=][&list=items]` — "Give to" dialog fragment (`list=items` returns the item list alone) (Owner visibility, else 403);
  `POST /armory/give` — form `character_id`, `item_id` or `map_id`, `quantity` (blank = 1, max 1,000,000);
  HTMX 204 with `armory-moved` and a toast; 403 for anyone below Owner visibility, 404 for a non-item,
  non-character or foreign-campaign id
- `POST /armory/pay` — form `character_id`, `amount` (gold, two decimals, up to 1,000,000), `reason`
  (the money history phrase, 120 chars); adds coins to the sheet's money field, or splits them into
  gp/sp/cp on a coin purse, and tells the player. JSON `{characterName, paid}`. Owner visibility only;
  400 for a Wealth sheet (a level, not coins), a sheet with no money field, or a purse that cannot hold
  the amount; 404 as for a give. Used by the quest board's Hand out
- `POST /armory/downtime` — open or close downtime (Owner visibility); opening applies pending requests
- `GET /armory/characters/:eid/panel|history` — the "Items and money" panel and full history
- `GET /armory/characters/:eid/items/:iid/share` — the share box fragment;
  `POST` the same path — form `user` (repeated; the players to share with, none = only the holder);
  HTMX 204 with `armory-moved` and `armory-shared` (`message`, `itemId`); 400 for a player outside the party

Sync API (key-authenticated, in the syncapi plugin): `GET /stashes/view|history|requests|downtime`,
`POST /stashes/moves`, `POST /stashes/requests/:moveId/approve|decline`, `PUT /stashes/downtime`.
