# Armory Plugin

## Purpose
Item gallery plus shop economy for a campaign. Items are entities whose entity
type has `preset_category = 'item'`; the plugin adds named item collections
("instances") and a transaction log for shop purchases and transfers.

## Tables (own, core migrations)
- `inventory_instances` — named collections per campaign.
- `inventory_items` — links an entity to an instance with a quantity.
- `shop_transactions` — purchase/sale/transfer/gift/restock records.
- `stashes`, `stash_viewers`, `stash_items` — named campaign stashes (items and a
  money number), and the characters allowed to see each. No viewers = GM only.
- `item_moves` — history of every move (applied, pending, declined, failed); a
  `pending` row is a request waiting for the GM.
- `campaign_downtime` — the per-campaign switch; a missing row means closed.
- `shop_rooms` — one saved room layout (normalized JSON) per shop entity, for the shop room widget.
Items themselves live in `entities` / `entity_types`.

## Tables (own, plugin migration `migrations/`)
- `armory_item_shares` — one row per holder character, hidden item and player
  it was shared with; `made_grant` marks the row whose share added that
  player's view grant. Read only while the plugin's migrations are healthy.
- `armory_item_looks` — one look per page, usually an item (`{"look","tint","sound","words","spots","madeFrom"}`,
  normalized by `NormalizeItemLook`; every value but the words is from a fixed
  list mirrored in `static/js/widgets/item_look_fx.js`). The AI connection reads
  and writes looks through the same service (`ListLooks`, `CheckLook`,
  `SaveLook`, via `aiItemLooksAdapter` in `internal/app`), so its checks are
  these ones.
- `armory_item_copies` — part of a holder's count of an item (`holder_kind`
  `character` or `stash`) that remembers something: `memory` is JSON
  (`{"marks","quality","quirk","how","by","on","offDay","offOn","becomes","becomesName","off"}`)
  cleaned by `Memory.Clean`. The rest of the count is plain. `fitCopies` keeps
  the oldest copies up to the holder's count, so a count lowered by hand
  hides the newest.
- `armory_move_picks` — the copy a waiting move request asked for, so it is
  still the one that goes when the Director approves.
- `armory_item_places` — which container a hero carries an item in (`hand`,
  `worn`, `belt`; no row means the backpack). It arranges the panel only:
  counts stay on the Has Item line and a move never reads it.

## Remembered copies
- Crafting gives them (`Give`/`GiveSpoil` with a memory) and spends them
  (`Spend` with picks), through `internal/app/crafting_adapters.go`.
- A move takes the picked copy first (form field `pick`, the copy id, from
  the Move box's "Which ones"), then plain ones, then the oldest remembered
  ones; the copies taken arrive at the other hero or stash unchanged.
  Selling to a shop or using an item up ends its copies.
- The hero sheet's Armory panel and the Stashes page list each holder's
  copies under the item (`heldCopies`): its tags (Fine, Poor, marks, Gone
  off) and its words (who made or harvested it, its quirk, when it goes off).
- `GoOff` runs at each respite the Director logs, given the calendar's day:
  a copy past its day becomes its `becomes` item at the same holder, or is
  marked `off` when it becomes nothing. Without a calendar nothing goes off.
- The stash API's items stay `{itemId, name, quantity}`; copies are not on it.

## Architecture
- Gallery: `ArmoryService` resolves item type IDs (`ItemTypeFinder`); the repo
  returns candidate IDs with no visibility predicate; the service narrows them
  with the entities plugin's `FilterViewableEntityIDs` (`EntityVisibilityFilter`)
  before paginating. `?type=` only narrows, never widens.
- Instances: `InstanceService` counts items through the same per-viewer filter;
  `AddItem` verifies the entity belongs to the campaign (`EntityCampaignChecker`).
- Transactions: `TransactionService` owns purchase/stock/currency logic.
  `TransactionReader` is the list read path: blanks names of entities the viewer
  cannot see, 404s a shop they cannot see.
- Tags on cards and the tag filter come from `TagLister`. GM-only tags only at
  Owner visibility (Owner or DM-granted DM access), like the tags widget; below
  that, a `?tag=` slug the viewer isn't offered returns the empty result.
- Stashes and moves: `StashService` (`stash_service.go`, `stash_moves.go`) owns
  the rules. A user sees a stash if Owner/Scribe or if they own (claim) one of
  its viewer characters; an unseen stash is a 404. Moves are item or money
  between characters and stashes. Owner/Scribe moves, and any move while
  downtime is open, apply at once; otherwise the move is a `pending` request
  that only Owner visibility (Owner or DM-granted DM access, never a Scribe) can
  approve or turn down. DM-only inventory lines follow the same Owner-visibility
  rule (`Actor.SeesDmOnly`): a Scribe neither sees nor moves them. `run` is the one apply path (immediate, approval and the
  sweep when downtime opens): campaign lock, debit the source with a
  held-enough check, credit the destination, restore the source and mark the
  move `failed` if the credit fails. Opening downtime applies pending requests
  oldest first; one that can no longer be covered is marked `failed`.
- Money is the game system's own sheet field on the character: the first
  numeric field keyed `gp`, `coins`, `gold`, `money` or `wealth`. A character
  type without one refuses money moves. Amounts are carried as cents. Stash moves
  only ever touch that one field.
- Purse (D&D 5e): when a character type has numeric `gp`, `sp` and `cp` (`ep`
  and `pp` join when present), the directory fills `EntityRef.Purse` (coin → field
  key; `MoneyKey` stays `gp`). `purse.go` holds the pure arithmetic: rates in
  copper (cp 1, sp 10, ep 50, gp 100, pp 1000), `toCp` (rounds up, so a price is
  never a fraction of a copper), `payFromPurse` (spends cp, sp, ep, gp, pp in
  that order, taking only as many of each coin as needed; the overpayment comes
  back as change in gp, sp, cp, never ep or pp)
  and `formatPurse` ("9 gp 7 sp 3 cp"). A gold-only sheet has no purse and pays
  from `gp` alone; `gp` cents are copper, so the two agree.
- Wealth (Draw Steel): a `wealth` money field is a threshold, never spent. A
  hero can buy when Wealth is at least the dearest unit price in the basket
  (currency is ignored); nothing is written and nothing is rolled back.
- Money edits outside a move: `MoneyHistory` (`money_history.go`) is the
  entities plugin's field-change observer, wired in `internal/app`. When a
  character's money field changes by any door but a stash move, it writes an
  `applied` `money` row to `item_moves` from the character to itself (amount
  = new − old, signed; `requested_by` = the source's user). The reason is the
  sentence shown in history, e.g. `Wealth changed 2 → 3 · in Foundry`, built
  from the field label and the change source (`changesource`): the source's
  label if it has one (a shop's), else "in Foundry" / "on the sheet" / "by an
  extension". `MoveSummary` shows that reason as-is for a self-move money row.
  A purse sheet logs one line comparing the whole purse before and after
  (`Purse 12 gp 3 sp → 11 gp 8 sp 3 cp · at a shop`) with the amount as the
  copper value gained or lost; a change in only cp, sp, ep or pp is logged, and
  coins that trade evenly are not.
  Not logged: stash-source writes (moves log themselves), an unchanged amount,
  non-characters, types without a money key, or a write that set no source.
  Visibility follows character history (whoever can act as the character, plus
  Owner/Scribe). `ShopPurchaseSource(ctx, userID, label)` marks a shop's own
  sheet write so its line reads the shop's label.
- Sync API surface: `StashAPI` (`stash_api.go`) answers the Foundry module as a
  named member (`actingUserId`). `ActorFor` builds the `Actor` from THAT member's
  real campaign role and DM-access grant (never the key's Owner role unless the
  member is Owner or DM-granted), non-members are NotFound, absent means the key
  caller. Only an Owner, or a caller with DM access, may name someone else (else
  Forbidden), because browser sessions use the same routes; so naming a player
  is a narrowing, never a widening.
  Endpoints are in the syncapi `.ai.md`; `internal/app` adapts the facade to
  syncapi's `StashAPIService`.
- Giving: the Owner (Owner visibility, never a Scribe) hands a character an
  Armory item or a map from the character page's "+ Give an item" button or an
  item card's "Give to..." menu entry (`stash_give.go`, `give_box.templ`).
  `Give` runs under the campaign lock and credits the character's Has Item line
  with `adjustCarried(+qty, allowDM)`, exactly as a move crediting a character,
  so the existing relation events reach Foundry. It is recorded in `item_moves`
  as an applied item row whose from and to are the same character
  (`Move.IsGive`; no ENUM changed). Because it is already applied, `run` refuses
  to replay one, `Move` still refuses from == to for everyone, and history
  readers show it through `giveSummary` ("You gave Mira 2 × Potion" to a GM,
  "Your GM gave you 2 × Potion" to the player; the sync API carries the same
  sentence). It publishes `stash.moved` for the one character. A map is given as
  an item: `HandoutStore` (wired in `internal/app/armory_give_adapters.go` over
  the maps and entities services) finds or creates an item entity named
  "Map: <map name>" assigned to that map, whose entry links `/maps/:mid`. A
  handout carries a `fields_data` marker no entity type declares
  (`chronicle_map_handout` = the map id) and only a marked one is reused (the
  oldest), so an item someone typed with the same name is never taken over.
- Crafting (`stash_craft.go`): the crafting plugin reaches the stash service
  through `internal/app/crafting_adapters.go`. `CraftPack` reads what a
  character carries and how they pay (`""`, wealth, purse or coins, as a shop
  reads it). `CraftSpend` takes a project's materials and cost all or
  nothing under the campaign lock; a Wealth sheet must reach the cost and
  spends nothing, and coins convert to the sheet's money field
  (`CraftCharge`); with a `Purpose` it takes items for something other than
  a project, and the history says what ("Used 2 × Bloodmoss in an
  experiment"). `CraftGive` puts the made item in the pack. `CraftGiveFor`
  puts an item in a character's pack on behalf of a hero the actor may act
  for, with the history line crafting gives: what a helper's roll finished
  reaches the project's owner, and what breaking an item down gives back
  reaches the hero who broke it. Adding to a pack takes nothing from anyone,
  so acting for the hero is the check; crafting has already checked the
  hero may help. And
  `SpoilGive` an item taken or harvested from the spoils tray (its history
  says "Took 2 × Troll tooth from the spoils" or "Harvested 2 × Troll hide",
  never where it dropped, which the player may not be allowed to see). Each checks
  the actor may act for the character (`canAct`), as every move does, writes
  history lines that say what was used or made, and labels the money
  history with what is being made (`changesource.KindCraft`).
  Every give, item or map, adds the receiving character's claimed player to
  the item's allow list (`AllowViewers`: a public item is left alone, a private
  one becomes custom with Scribe-and-up edit plus the player, a custom one
  gains the player), so a private item still shows on the player's panel and
  history; a character with no player adds nobody. History reads "gave you"
  only for the character's claimed player; other non-GM viewers read
  "<GM> gave <Character> ...". The claimed player is notified (`item_given`,
  "Your GM gave you ...", detail "On <Character>") through `GiveNotifier`,
  over the sessions notification store.
- The Give box: on the character page "Give an item" opens it in place, in
  the panel's `.ag-fold` above the item list; on an Armory card the ...
  menu (`.ag-pop`: "Add to collection..." for Scribe and up, "Give to..." for
  Owner visibility) turns into it. `GET /armory/give?character=` renders
  `GiveBox` (Armory items, searched server-side with `list=items&q=`, at most
  50 shown with "Showing 50 of N"; a map tab tagging maps the character
  holds), `?item=` renders `GiveCardBox` (characters with their player's
  name). `static/js/widgets/give_box.js` (`Chronicle.GiveBox`, loaded by the
  base layout) folds it, guards an unsent pick (Escape or the opening
  button asks first in the shared slip, `static/js/theme.js`; a click
  outside never closes a box), posts with the CSRF header and
  reads `armory-given` from the answer for the toast and the line to flash.
  The `ag-*` styles are in `static/css/input.css`. `HX-Trigger` values are
  ASCII-escaped (`triggerJSON`) because browsers read header bytes as
  Latin-1.
- Sharing a hidden item: on a hidden (custom or private) item a character
  holds, the character's claimed player gets "Share..." on the panel row. It
  opens `ShareBox` (one checkbox per other player's character in the party,
  one per player) in the row's `.ag-fold`; Save posts the checked players and
  the service sets exactly those view grants, under the campaign lock. Only
  a grant sharing added is ever taken back: `AllowViewers` returns which
  players it newly added, and only those rows get `made_grant`. Unchecking a
  player removes the row; its grant goes (`RevokeViewers`, which removes view
  grants only) unless another holder's share of the item still covers that
  player (ownership moves to that row) or that player holds the item too. The
  holder's own grant, a give's grant and a hand-set grant are never removed.
  The holder's player or Owner visibility may share; anyone else gets 403, an
  item the character doesn't hold or the caller can't see 404, a public item
  400. A save that changes anything writes an `item.shared` audit entry
  (`ShareAuditor`). Without a healthy plugin migration `Shares` is nil and
  sharing answers 400 and the link is not shown. A share ends with the
  holding: armory moves release it as they go, and a "Has Item" line deleted,
  lowered or made GM-only elsewhere reaches `ReleaseLetGoShares` through the
  relation event adapter in `app/routes.go`.
- Live events: the stash service publishes `stash.moved`, `stash.requested`,
  `stash.settled` and `downtime.changed` through `StashEventPublisher` after the
  campaign lock is released; `MoneyHistory` publishes `stash.money_changed`.
  Payloads are ids and statuses only (`stash_events.go`). `internal/app` sends
  them to DM-equivalent sockets and the change feed records them.
- A character's items are its "Has Item" relations (quantity in the relation
  metadata, other keys preserved); `HasItemStore` wraps the relations service.
- "Acting as" a character is Owner/Scribe, the claimed owner, or entity edit
  access (`BuyerAccessChecker`, with a stash-specific adapter).
- The entities plugin lazy-loads the character "Items and money" panel through
  `entities.PagePanel`, wired in `internal/app`: the "Items & Money" layout
  block, shown on its own only on player-character pages that place neither it
  nor Inventory.
- The panel draws each held item as a tile in its container (`places.go`,
  `character_panel.templ`): In hand, Worn, Belt pouch, Backpack. Pressing a
  tile opens its card under the boxes with the copies spread out one card
  each, Move, Share and "Carried". With a place store, the character's
  player or a GM drags tiles between boxes or uses "Carried"
  (`static/js/widgets/hero_pack.js`), which posts the place; a refusal puts
  the tile back.

### Shop buying
- `ShopBuyService` (`shop_buy_service.go`) lets a player spend a character's
  coins on a shop's "sells" listings. It shares the stash service's campaign
  lock and money/Has Item helpers, so a purchase and a stash move cannot spend
  the same coins. Prices and currency come only from listing metadata (no
  positive price is refused, never free); all lines share one currency.
- Payment depends on `buyKind`: `purse` (paid by `payFromPurse`, written with
  `adjustPurse` as one field update, refused if any coin would go negative),
  `wealth`, or `coins` (one number). On a `gp` sheet a basket priced in
  cp/sp/ep/gp/pp (case-insensitive) is converted through `toCp`; any other
  currency, and any other money field (`gold`, `coins`, `money`), is charged at
  face value. Quotes and the "price went up" check stay in the listing currency.
- Order under the lock: price the basket and check coins (no writes), reserve
  stock per line (`reserveStock` with `requireSells`), take the coins, credit
  the items, write one `purchase` row per line with `buyer_entity_id`. A failure
  before the log undoes earlier steps in reverse (stock released by
  compare-and-set; a purse gets the inverse coin changes). A log row that fails
  to write is logged loudly, not undone. The mutation phase runs on a context
  that survives client disconnect.
- Who may buy: the Owner (Owner visibility) for any character; anyone else only
  for a character they claimed and may act as (a Scribe's edit rights do not
  reach another player's coins). A player buys at once only while downtime is
  open; otherwise the basket is stored as a purchase request. A hidden shop, a
  relation of another shop or campaign, a non-"sells" relation, a DM-only
  listing (below Owner visibility, Scribe included) and a good the buyer cannot
  see are all 404.
- Purchase requests (`shop_request_service.go`, table `shop_purchase_requests`,
  core migration 000042): while downtime is closed, a non-Owner `Buy` prices the
  basket only to refuse one that could never be bought, stores
  `{relationId, quantity}` lines under the campaign lock and answers
  `{"status":"requested"}`. No coins, stock or items move and coins are not yet
  checked. At most 10 pending per player (plain 400). The Owner approves
  (`POST /armory/purchase-requests/:rid/approve`), declines (`.../decline`), or
  opens downtime (`SetDowntime` calls `sweepRequests` under its lock, after the
  move sweep).
- Approval runs `applyBasket`, the same path as a live buy, as the requester
  with player visibility (it lifts only the downtime gate): shop visibility,
  claim, coin field, listings, prices, currency, stock and coins are read again.
  The request stores the basket total and currency from when it was asked
  (`quoted_total`, `quoted_currency`): at apply time a higher total or different
  currency fails it with "The price went up since you asked." and spends
  nothing; an equal or lower price is charged at the current price. A refusal
  marks the request `failed` with the plain reason (an internal fault stores a
  generic one). The row is claimed `pending -> applied` before the basket runs
  and rewritten to `failed` if it cannot go through, so a crash can lose a
  purchase but never charge twice.
- `stashService.purchases` (set by `NewShopBuyService`) is how the downtime
  sweep, the stashes page ("Requests waiting on you", `purchase_request_row.templ`)
  and the character panel/history (requests appear as `MoveLine`s carrying a
  `Summary`) reach requests. No websocket event is published for requests.

### Shop rooms
- A page has a shop only where the owner placed the Shop block
  (`shop_inventory`) in its layout. The block shows a door; pressing it opens
  the room in a modal `<dialog>` (`shop_room.js`, plus `shop_room_paper.js` and
  `shop_room_counter.js`, loaded on sight: icons, paper, counter, then the
  widget, ADR-063). The room has a basket (who pays, Buy); Escape closes the
  basket first, then leaves. The GM arranges furniture and decorations by drag
  in Arrange.
- Saved layout fields (`shop_room_model.go`): `look` (`lit` isometric room,
  `paper` pop-up book, `counter` standing at the counter; empty reads as lit),
  `mood` (one of `MOOD_ORDER` in `shop_room.js`; empty is Cozy), `effects`
  (null means the mood's defaults, `moodEfx`), `decor` (hand-placed
  decorations: piece id, spot index, icon; they take their spot ahead of goods
  and are dropped with their piece), and pieces moved by hand. Picking a mood
  swaps the previous mood's furniture but keeps anything moved by hand
  (`applyMood`). Picking up a generator-placed decoration first freezes all of
  them as hand-placed and sets Decorations to None (`ShopRoomDecor.freeze`).
  Goods are dealt to spots shuffled with hand-placed decorations in place, so
  moving a decoration never moves goods to other shelves.
- Rendering rules: every loop follows the visitor's motion setting (Calm, Off or
  reduced motion stops loops and hides travelling details). The paper look maps
  the pointer to the floor from four corner markers (`floorAt`) and picks small
  cards by their box (`hit`) because browsers hit-test 3D cards unreliably; it
  uses no `mix-blend-mode`, which flattens it. The counter look's `layout`
  places every good once; pile, buying and parcel go through `shop_room.js`'s
  basket hooks, so the add rules are the same in every look. Counter lighting is
  a distant light only, never a blend or point light. The keeper token is a
  same-site or http(s) address only. Shadows on Full light the room from its
  forge/lamp sources (`ShopRoomLight.castOffset`).
- `ShopRoomService` (`shop_room_service.go`) stores the layout.
  `NormalizeShopRoomLayout` (`shop_room_validate.go`) decodes into a typed
  struct, validates every field and re-marshals; the client's body is never
  stored. The icon allowlist (`shop_room_icons.go`) must match
  `static/js/widgets/shop_room_icons.js`. The shop must be in the campaign with
  entity type slug `shop` (`ShopEntityChecker`); reading a shop the viewer
  cannot see is a 404 via `EntityVisibilityFilter`. The layout references goods
  by relation id only.
- The sync API reads the same service for the Foundry module
  (`GET /api/v1/campaigns/:id/armory/shops/:eid/room`) and buys through
  `/buyers` and `/buy` under that path, with `ShopBuyService` called as the
  member the call names (see syncapi's `.ai.md`).

## Routes (`routes.go`)
Public-capable, Player+ view:
- `GET /campaigns/:id/armory` — gallery (filters: `q`, `sort`, `tag`, `type`, `instance`, `page`)
- `GET /campaigns/:id/armory/count` — visible item count for the sidebar badge
- `GET /campaigns/:id/armory/shops/:eid/room` — `{"layout": <object or null>}`; 404 for a shop that is missing, not a shop, or hidden from the viewer
- `GET /campaigns/:id/armory/items/:eid/look` — `{"look": <object or null>, "source": {"id","name","url","look"} or null}` for any page in the campaign; 404 for a page that is missing or hidden from the viewer. `source` is the page named by `madeFrom` with its own look (one hop: its `madeFrom` is stripped); `id`, `name` and `url` are left out when the viewer cannot see that page

Authenticated:
- `GET /armory/instances` (Player+) — instances with viewer-visible counts
- `GET /armory/instances/manage` (Scribe+) — management panel fragment
- `POST /armory/instances`, `PUT|DELETE /armory/instances/:iid` (Scribe+); PUT is a partial update (absent keeps, null clears the description, present replaces)
- `GET /armory/items/:eid/collections` (Scribe+) — which collections hold an item, for the card menu
- `POST /armory/instances/:iid/items`, `DELETE /armory/instances/:iid/items/:eid` (Scribe+)
- `GET /armory/shops/:eid/buyers` (Player+) — `{"downtimeOpen","canBuyNow","buyers":[{"id","name","moneyKey","money":number|null,"kind":"coins"|"purse"|"wealth","moneyCp":number,"purse":{coin:count},"own":true}]}` (`kind`/`moneyCp`/`purse`/`own` only when they apply; `own` marks the caller's claimed characters and the Paying picker starts on the first one; `money` is the gp equivalent for a purse, Wealth for a hero); the caller's claimed characters, every character for Owner visibility; 404 for a hidden shop
- `POST /armory/shops/:eid/buy` (Player+) — body `{"buyerEntityId","items":[{"relationId":number|"numeral","quantity":1..99}]}` (1..50 lines, no duplicates); answers `{"status":"bought","spent","currency","moneyLeft","purseLeft","change"}` (`purseLeft`/`change` for a purse; a Wealth buy has no `spent`/`currency`), or `{"status":"requested"}` (nothing spent) for a player while downtime is closed; 400 `Not enough coin` / `Needs Wealth N` / `Items are priced in different currencies` / `This sheet has no coin field` / `You have 10 purchase requests waiting for the GM already.`, 403 for another player's character, 404 for anything not buyable
- `POST /armory/purchase-requests/:rid/approve|decline` (Player+ at the route, Owner visibility in the service, else 403) — HTMX 204 with the `armory-moved` signal and a toast (error toast when an approved request fails), else a redirect to the stashes page; 409 once answered, 404 for an unknown id
- `POST /armory/purchase-requests/:rid/withdraw` (Player+ at the route; the requester or Owner visibility in the service, else 403) — deletes the row only while it is still `pending` (`DELETE ... WHERE status='pending'`, rows affected checked, so it cannot race an approval or the downtime sweep); 409 once answered, 404 for an unknown or other-campaign id. HTMX 204 with the `armory-moved` signal. A waiting purchase line in the character history carries `Purchase`/`CanWithdraw` and shows a Withdraw link that opens an inline "Withdraw this request?" confirm (`withdrawControl`, `withdrawToggleOnClick`), standard `btn-danger`/`btn-secondary` buttons
- `POST /armory/transactions` (Scribe+) — manual gift/transfer/restock
- `GET /armory/transactions` (Player+) — filtered list, names redacted per viewer
- `GET /armory/shops/:eid/transactions` (Player+) — per-shop list
- `PUT /armory/shops/:eid/room` (Owner) — replaces the whole layout, body max 64 KiB, answers `{"layout": <normalized>}`; not a partial update
- `PUT /armory/items/:eid/look` (Owner) — body `{"look","tint","sound","words","spots","madeFrom"}` max 1 KiB, replaces the whole look; `look: ""` with no `madeFrom` removes it. Looks: ember, frost, storm, bloom, dawn, rot, venom, glass, quiet; `tint` is one of eight palette colours; `sound` one of nine sounds or `none`; `words` up to 24 characters of plain text; `spots` maps `item`, `trail`, `impact`, `body` or `ground` to `{"look","tint"}` from the same lists; `madeFrom` names another page in the campaign (never itself), and with it `look` may be `""` (no colour then). Answers the same shape as the GET (as the Owner sees it), 400 for anything off the lists or a `madeFrom` that is not another page in this campaign

Stashes and moves (Player+ at the route; the service decides what each caller
may see or do):
- `GET /armory/stashes` — stashes page (visible stashes; requests panel at Owner visibility)
- `POST /armory/stashes`, `PUT|DELETE /armory/stashes/:sid`, `PUT /armory/stashes/:sid/viewers`,
  `POST /armory/stashes/:sid/items` — Owner/Scribe management; `PUT` is partial (absent keeps, null clears)
- `GET /armory/stashes/:sid/history` — history of a stash the caller can see
- `GET /armory/move` — move dialog fragment; `POST /armory/moves` — move or request
- `POST /armory/moves/:mid/approve|decline` — Owner visibility only
- `GET /armory/give?character=<eid>|item=<eid>[&q=][&list=items]` — "Give to" dialog fragment (`list=items` returns the item list alone) (Owner visibility, else 403);
  `POST /armory/give` — form `character_id`, `item_id` or `map_id`, `quantity` (blank = 1, max 1,000,000);
  HTMX 204 with `armory-moved` and a toast; 403 for anyone below Owner visibility, 404 for a non-item,
  non-character or foreign-campaign id
- `POST /armory/pay` — form `character_id`, `amount` (gold, two decimals, up to 1,000,000), `reason`
  (the money history phrase, 120 chars); adds coins to the sheet's money field, or splits them into
  gp/sp/cp on a coin purse, and tells the player. JSON `{characterName, paid}`. Owner visibility only;
  400 for a Wealth sheet (a level, not coins), a sheet with no money field, or a purse that cannot hold

- `GET /armory/characters/:eid/panel|history` — the "Items and money" panel and full history
- `POST /armory/characters/:eid/items/:iid/place` — form `place` (`hand`, `worn`, `belt`, `pack`);
  204. The character's player or a GM, for an item the character holds (Director-only lines only for

- `GET /armory/characters/:eid/items/:iid/share` — the share box fragment;
  `POST` the same path — form `user` (repeated; the players to share with, none = only the holder);
  HTMX 204 with `armory-moved` and `armory-shared` (`message`, `itemId`); 400 for a player outside the party

Sync API (key-authenticated, in the syncapi plugin): `GET /stashes/view|history|requests|downtime`,

## Block
- `armory_preview`: compact item grid for entity page layouts.
- `item_look` ("Look", in the entities block registry, gated by the armory
  addon) mounts `static/js/widgets/item_look.js` over `item_look_fx.js`: the item
  on a small stage with On the card / When used / When made and a sound switch
  (off until the viewer turns it on). The Owner picks gallery looks (every
  change saves on its own) and can place them on five stage spots; the item and
  impact spots fall back to the item's own look until filled. "Made from" names
  the page the item was made from (a Remnant): with no look of its own the item
  takes that page's look, with one the source shows through
  (`ItemLookFX.carried`); the block on the Remnant's page sets the look its items
  carry. The block is hidden from players when the item has no look, and from
  everyone on a non-item page. Motion comes from the subtype or sheet `type`
  (blade, potion, ring, else its picture).
- `item_look_fx.js` is a shared engine the crafting bench loads on its own.
  `SPOTS` (item stage), `BENCH_SPOTS` (crafting stations), `MOMENT_SPOTS` and
  `MOTION_SPOTS` name the spots; `spotLayers` keeps only known spots and gallery
  looks, so saved placements can never name anything else.
