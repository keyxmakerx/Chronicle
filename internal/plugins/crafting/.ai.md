# Crafting Plugin

## Purpose

The **Crafting** app (`/campaigns/:id/crafting`, sidebar "Crafting", behind
the `crafting` addon and shown only while the Armory is on). A Director writes
recipes, tags Armory items as materials, sets up benches and picks the
campaign's crafting defaults; a player reads the recipe book of what their
characters know. A player starts a project from the **Crafting block** on
their character's page, paying the materials and cost at the start, and makes
one roll for every respite the Director logs, at the bench or as a plain
roll; the Director follows every project on the app's **Projects** tab.
What a fight or a search leaves waits in the party's **spoils tray**: players
take or harvest it from the block, and the Director hands it out, puts more
in and keeps every page's **drop list** on the **Spoils** tab. An AI reads
all of it and writes recipes, material kinds and drop lists through AI
Import; see "The AI connection".

The bench itself (`static/js/widgets/craft_bench.js` and its parts) and the
"When… then…" rules editor (`craft_rules.js` and its parts) are core widgets
with their own `.ai.md`; this plugin stores what they edit and mounts them
through their `el._craftApp` hook.

## Who may do what

| | Recipe book | Editors' data (recipes, catalog, benches) | Any change | Projects |
|---|---|---|---|---|
| Player | approved recipes everyone knows, plus those one of their characters learned | no (403) | no (403) | start, roll and cancel for a character they claimed; any other character is a 404 |
| Director (Owner or granted co-Director) | every approved recipe | yes | yes | all of that for any character, plus the Projects tab, respites, giving a roll and setting points |

Spoils follow the same split: a player takes or harvests a waiting line for
a character they claimed (any other character is a 404); the Spoils tab, drop
lists, putting spoils in, clearing them and giving to any hero are the
Director's.

Every route is open to any member (`RequireRole(RolePlayer)`); the service
decides with `Viewer.Director` (`CampaignContext.CanAuthorDmOnly()`), which a
role middleware cannot express. Each Director-only method starts with
`directorOnly(v)`, so a mis-wired route cannot widen access.
`TestEveryWriteIsDirectorsOnly` calls every write as a player and checks
nothing changed.

## What a player never receives

The book is built on the server (`Service.Book`, `book.go`); the browser only
draws it.

- Drafts are left out.
- A rule reaches the book only when it is written in the book
  (`players: "book"`); rules shown when they happen and secret rules never do.
- Item names come from the items the player may see (`Directory.ListItems`
  at their role). An item they cannot see reads "an item you haven’t seen".
- `knownBy` names only the player's own characters.
- A recipe on the Crafting block carries only the rules written in the book.
  When a rule holds a roll or changes one, a rule shown when it happens is
  named; a secret rule reads "A rule the Director keeps hidden", never its
  condition. What a project took and whether its item reached the pack are
  the Director's only.
- The block renders only for the Director and the player who claimed the
  character (`CanCraftFor`), so nobody else's page carries an empty block.
- A roll reads the calendar's today with the Director's sight, because the
  rules are the Director's (ADR-049's allowlist, `crafting_adapters.go`).
  The block shows today's date only to a viewer who can see the default
  calendar, and a respite's date is on the Director's tab only.
- A drop list never leaves the Director's routes. In the tray
  (`trayViews`), a spoil whose page the player can't see reads "Something
  the party found", with no copy count, no fight name and no "put in by
  hand"; an item they can't see reads "An item you haven’t seen" with no id
  or kinds, until a hero takes it and the Armory lets that hero's player see
  it. The tray names the page, never the name the Director typed on the
  fight's row, and the pack's history never names where a spoil came from.

## Data model

| Table | What |
|---|---|
| `crafting_settings` | one row per campaign: default look, difficulty, botched work gives a bane, players may skip steps |
| `crafting_recipes` | a recipe; materials, steps, rules, looks and extras are JSON cleaned on every write; name unique per campaign |
| `crafting_known` | who knows a "must be learned" recipe, one row per character |
| `crafting_material_tags` | a crafting tag on an Armory item |
| `crafting_kind_pictures` | a campaign's picture and tint for one kind, when it isn't the default |
| `crafting_material_pictures` | an item's own picture and tint, when it doesn't follow its kind |
| `crafting_benches` | a named bench of one kind, with each look's build-mode arrangement (`desk`, `journal`) and its upgrade ladders |
| `crafting_projects` | a hero's project: what the recipe said when it started (name, goal, characteristic, item), points, rolls ready, status, whether the item reached the pack, what it took, and its details (what the item came out as, the substitutes' standing costs) |
| `crafting_respites` | one row per respite logged, with the calendar's date then |
| `crafting_rolls` | every project roll: dice, each term, the total, points before and after, how the work went |
| `crafting_drops` | a page's drop list: its lines (JSON, cleaned on every write), the page it also drops from, a version |
| `crafting_spoils` | one thing that dropped: the page and its name then, which copy of how many, the fight's name ("" by hand) |
| `crafting_spoil_lines` | a spoil's line as the drop list read then: item, take or harvest, amounts; waiting, taken (by whom, for which hero, how many, what was rolled) or cleared |

- A material's item id is not a foreign key: a deleted item leaves the recipe
  saying "That item was deleted" rather than changing what it asks for. The
  result item is a foreign key that sets NULL; deleting a character removes
  it from `crafting_known`.
- A stored tag the library no longer has is dropped on read (`knownTags`), so
  it never hides the item's other tags.
- Pictures are named for what they show (`leaf`, `flask`, `ingot`), never for
  a material; the drawings are `static/js/widgets/craft_pictures.js` and
  `Pictures` in `library.go` lists the same keys in the same order
  (`TestPicturesMatchTheDrawings`). An item wears its own picture, else its
  first kind's as the campaign set it, else that kind's default. A stored
  picture the library no longer has falls back the same way.
- An item's first tag picks its picture and recipes store tag keys, so new
  kinds are appended to `Tags` and keys are never renamed
  (`TestKindOrderIsAppendOnly`).
- Armory items are entity types with `preset_category = 'item'`, the
  Armory's own rule. A campaign without a game system that adds item types
  has no items to tag.
- A project copies the recipe's name, goal, characteristic and item when it
  starts, so editing or deleting the recipe never moves the goal under a
  player; the recipe's rules still apply while it exists.

- Deleting a page deletes its drop list; a list that also dropped from it
  stops doing so, and a spoil from it keeps the page's name. A spoil line's
  item cascades: an item deleted from the Armory leaves the tray.

## Spoils and harvesting

- **What drops.** Ending a fight on the DM Screen's Fight tab tells
  `FightEnded` which creature rows were down: every copy at 0 hit points or
  less drops its own share of its page's drop list, the page it also drops
  from first (one step only). A row with no page, a page with no drop list,
  or a creature not down leaves nothing, and the report says which. The
  encounters plugin ends the fight once (`EndRun` reads and deletes in one
  transaction), so two presses can't drop twice. **Put spoils in the tray**
  drops a page's list by hand, up to 20 times, for a Foundry fight or a
  search.
- **Copied at drop time.** A spoil's lines are the drop list as it read
  then; editing the list later changes only what drops next. Spoils keep
  until taken or cleared.
- **Taking** claims the line with one conditional update (first come, first
  served), then the Armory puts it in the hero's pack (`GiveSpoil`). If the
  pack refuses, the line goes back to waiting.
- **Harvesting** is a test: the system's dice plus the characteristic the
  line names, read from the hero's sheet (+0 with a note when the sheet has
  no number for it). The system's tiers (Draw Steel: 11 or less, 12 to 16,
  17 or more) each pay what the line says, and the lowest pays at least 1.
- **The tray is capped** at 500 waiting lines; a fight that would overflow
  it drops nothing more and says so.
- **The Fight tab** asks `DropNotes` for a chip beside each creature ("Has a
  drop list", "No drop list") and shows none when no page in the fight has
  one. With crafting off, or a listener that fails, the fight still ends.

## The AI connection

AI Import (and the connector's `crafting` tool) reads crafting through the
`crafting` lookup and writes it with three blocks, all in
`internal/plugins/ai_workspace/records` (`crafting.go`, `crafting_kinds.go`,
`lookup_crafting.go`) over `aiCraftingAdapter`, so every write goes through
this service's own checks:

- **How the parts tie together.** A material is an Armory item with one or
  more kinds (`kind: material`, which calls `SetTags`). A recipe asks for it
  by the item's name or for any item of a kind (`kind: recipe`). A creature,
  Remnant, place or magic source gives it through its drop list
  (`kind: drops`), and a fight's end drops that list into the tray. The
  lookup prints each material with the pages that drop it and the recipes
  that use it.
- **A recipe from an AI arrives as a draft** (`SaveAIRecipe`), so players
  see nothing until a Director approves it in the editor. Changing a recipe
  keeps it approved or not, keeps its rules, looks, colours and bench, and
  keeps each step on the same material (`KeepStepMaterials`) unless the AI
  sends `method`, which lays the steps again with `LayTemplate`, exactly as
  the editor's `applyTemplate` does.
- **The review runs the save's checks without saving** (`check`), the name
  included, so the review and the commit refuse the same things. An item
  the same paste makes is checked once its page exists.
- **Directors only** for every block and every part of the lookup but the
  recipe book; a lookup in the Safe privacy mode reads as a player and gets
  only the book. While the add-on is off, AI Import refuses the three blocks
  (`aiFeatureGate`) and the lookup says crafting is off.
- The tray, projects, benches and the "When… then…" rules are changed only
  in the app.

## Projects

- **Starting.** The hero must know the recipe (approved; known to everyone
  or learned). The service checks the materials and the cost against the
  hero's pack, then the Armory takes them all or nothing (`Armory.Spend`). A
  Draw Steel hero's Wealth must reach the cost and is never spent; coins are
  converted to the sheet's money field. Each "any herb" line is filled with
  the item the player picked.
- **Rolls.** Each respite adds one roll to every project in progress; unused
  rolls stack. A roll is made on the server: the system's dice, the
  characteristic from the sheet, an edge for clean work and a bane for
  botched work (when the campaign gives banes), then the recipe's rules on
  the day. The browser only reports how the steps went (`clean`, `botched`,
  `steady`, `skipped`), so the most it can claim is an edge. Skipping is
  refused when the campaign asks for the steps and the recipe has some,
  unless a Director rolls.
- **The day's rules.** `verdict.go` reads the rules the way the rules editor
  previews them: a certain "can't be made" or "only then" with none on holds
  the roll (409, the roll stays ready); a chance of "can't be made" is rolled
  and spoils that roll; points, an edge or bane, a say line and extra items
  are added. The roll knows the bench, the time of day by the calendar's
  clock and the maker's skills from the sheet. Ingredient marks are still
  unknown, so a rule needing one never holds or changes it.
- **What befalls the work.** A fired rule can make the item fine, mark it,
  give it a quirk rolled on one of the campaign's Rolling Tables, or make it
  as another Armory item; these are kept on the project and shown when it is
  made. "Discovers…" teaches the maker that recipe. The recipe's "If it goes
  wrong" settings add a mishap rolled on a table, at its chance, and what
  botched work costs (a bane, a quirk, or the work's points). Its extras add
  a breakthrough on a natural high roll, mastery (an edge once the hero has
  made it cleanly often enough) and substitutes the hero picks when
  starting, each with its standing cost. A table or item the campaign
  doesn't have is told to the Director only.
- **Bench upgrades.** Each piece of a bench climbs a ladder of up to five
  levels; a level is words for the table or a rule in a recipe's words. The
  rules of every level the party has reached join the recipe's at every roll
  made at that bench.
- **Finishing.** Reaching the goal makes the item (points over the goal are
  dropped) and the Armory puts it in the pack. If that fails the project
  still finishes, marked undelivered, and the Projects tab tells the Director
  to give it by hand.
- **Cancelling** keeps what the project took; the Director gives things back
  by hand.
- **Respites** come from the Projects tab (which then runs the Homebrew
  rules a respite sets off) or the Homebrew drawer's "Log a respite" button
  (whose `Pressed` hook logs it here first). Either way one press is one
  respite.
- **Versions.** A roll, the Director setting points and cancelling carry the
  project's version; a stale one is a 409 and the browser reloads.

## The system's crafting rules

A game system package may declare a read-only `crafting` block in its manifest
(`internal/systems/crafting.go`): the dice, the characteristics a recipe may
add, what an edge and a bane are worth, the harvesting tiers, and the words
for the goal, prerequisite and source. A campaign with no block, or no system,
gets `DefaultCraftingRules`. `Library` sends the rules filled in, so the
editor never checks for gaps. A recipe's `stat` is a characteristic key from
the block, or free words when the block names none.

## Saving in the browser

Everything saves as the Director works; there is no Save button.

- **Recipes**: one queue per recipe. The form and the rules save on their own
  routes, so the recipe form and the rules editor never overwrite each other;
  each save waits for the one before it and carries the version it returned.
- **Benches**: one queue per bench. A rename goes first, then the upgrade
  ladders, then each look's arrangement; `then(fn)` waits for the queue before the bench remounts.
- **Material tags** save per row on each click and roll back on failure.
- **Drop lists** save a moment after the last change, one save at a time per
  page, each with the version the last one returned.
- **Pictures** save on each pick; a swap on the picture board is one save.
- Whatever is still queued is sent with `keepalive` when the page closes.
