# Timeline Plugin

## Purpose

Visual timelines for campaigns. The timeline page draws the River, one draggable,
zoomable line through history (`timeline-river`); the entity-page block keeps the
D3.js chart (`timeline-viz`). A timeline optionally references a calendar (for
**linked** calendar events, many-to-many) or is calendar-free and holds only
**standalone** events (owned by the timeline). Entity groups organize events into
swim-lanes.

**Tier:** Plugin.

## Domain Concepts

- **Timeline:** named, per campaign; optional calendar link, color, icon,
  visibility, zoom config.
- **Event link:** M:N join between timelines and calendar events with per-link
  overrides for label, color, visibility. `Source="calendar"`.
- **Standalone event:** owned by one timeline; multi-day, times, recurrence.
  `Source="standalone"`.
- **Entity group:** named group of entities; events linked to a group's entities
  appear in that lane.
- **Visibility rules:** JSON per-user overrides (`allowed_users`, `denied_users`)
  on top of everyone/dm_only.
- **Zoom levels:** era, century, decade, year, month, day.

## Dependencies

- **Uses:** campaigns (CampaignContext, RequireRole), auth (RequireAuth, GetUserID),
  middleware (Render, GetCSRFToken), apperror
- **Cross-plugin:** three adapters in `app/routes.go` read through the
  calendar plugin, all campaign-scoped (a calendar id from another campaign
  answers empty, never an error): `CalendarLister` for the create-form's
  calendar selector, `CalendarEventLister` for the event picker, and
  `CalendarEraLister` for the D3 visualization's era background bands. Eras
  are calendar structure, so `CalendarEraLister` additionally gates on
  role — Owner or DM access only, regardless of the bound calendar's own
  visibility. `CalendarScope` (adapter wraps the calendar's campaign-scoped
  read) must confirm a calendar is in the timeline's own campaign before
  `CreateTimeline` stores it; unwired, any calendar is refused.
- **Internal:** sanitize (HTML sanitization for standalone event descriptions)
- **Connections are filtered per viewer:** `VisibleConnections` keeps only
  connections whose two ends are both in the viewer's already-filtered event
  list, so a connection never names an event the viewer can't see. The show
  page, `/data` and the connections API all apply it.
- **Used by:** Sidebar navigation (app.templ), addon system (installedAddons)

## Database

Tables come from `migrations/001_timeline_tables`; `002` clears the plugin's links to calendar rows.

### timelines

`id` VARCHAR(36) PK · `campaign_id` FK->campaigns(id) CASCADE · `calendar_id`
FK->calendars(id) SET NULL, nullable · `name` VARCHAR(255)
required · `description`/`description_html` TEXT · `color` VARCHAR(7) default
#6366f1 · `icon` VARCHAR(100) FontAwesome class, default fa-timeline ·
`visibility` VARCHAR(20) everyone/dm_only · `visibility_rules` JSON per-user
overrides · `sort_order` INT · `zoom_default` VARCHAR(20) · `created_by`
FK->users(id)

### timeline_event_links

`id` INT AUTO PK · `timeline_id` FK->timelines(id) CASCADE · `event_id`
FK->calendar_events(id) CASCADE · `display_order` INT · `visibility_override`
VARCHAR(20) · `visibility_rules` JSON per-user overrides · `label`
VARCHAR(255) event-name override · `color_override` VARCHAR(7). Unique:
(timeline_id, event_id).

### timeline_entity_groups

`id` INT AUTO PK · `timeline_id` FK->timelines(id) CASCADE · `name`
VARCHAR(200) · `color` VARCHAR(7) swim-lane color · `sort_order` INT.

### timeline_entity_group_members

`id` INT AUTO PK · `group_id` FK->timeline_entity_groups(id) CASCADE ·
`entity_id` FK->entities(id) CASCADE. Unique: (group_id, entity_id).

### timeline_events

`id` VARCHAR(36) PK · `timeline_id` FK->timelines(id) CASCADE · `entity_id`
FK->entities(id) SET NULL · `name` VARCHAR(255) required ·
`description`/`description_html` TEXT · `year` INT required · `month`/`day`
INT default 1 · `start_hour`/`start_minute` INT optional ·
`end_year`/`end_month`/`end_day`/`end_hour`/`end_minute` INT optional
(multi-day) · `is_recurring` TINYINT(1) default 0 · `recurrence_type`
VARCHAR(20) yearly/monthly/weekly/daily · `category` VARCHAR(100) ·
`visibility` VARCHAR(20) everyone/dm_only · `visibility_rules` JSON per-user
overrides · `display_order` INT · `label` VARCHAR(255)
display override · `color` VARCHAR(7) override · `created_by` FK->users(id).
Index: (timeline_id, year, month, day).

### timeline_event_connections

`id` INT AUTO PK · `timeline_id` FK->timelines(id) CASCADE · `source_id`/`target_id`
VARCHAR(36) event ids · `source_type`/`target_type` VARCHAR(20) default
`standalone` · `label` VARCHAR(200) · `color` VARCHAR(7) · `style` VARCHAR(20)
default `arrow`. Unique: (timeline_id, source_id, target_id).

## Design Decisions

- **ADR-018:** D3.js over Leaflet.js (Leaflet is geographic-only).
- **Lens over calendar events:** links, not copies, so the calendar stays the
  single source of truth.
- **Unified event view:** the service merges linked calendar events and
  standalone events into one `[]EventLink` (via `ToEventLink`), sorted by
  date; `Source` ("calendar"/"standalone") lets the frontend dispatch to the
  right endpoints.
- Visibility rules extend everyone/dm_only with per-user allowed/denied
  lists, applied to timelines, event links, standalone events, and calendar
  events alike.

## Audit Log Taxonomy

Timeline mutations emit audit events in the handlers via `Handler.logTimelineAudit`
(wired by `timelineHandler.SetAuditService` in `internal/app/routes.go`). Event names (constants
in `internal/plugins/audit/model.go`): `timeline.created/updated/deleted/
visibility_changed`, `timeline.event_linked/event_unlinked/
event_link_visibility_changed`, `timeline.standalone_event_created/updated/
deleted`, `timeline.entity_group_created/updated/deleted`,
`timeline.entity_group_member_added/removed`,
`timeline.event_connection_created/deleted`.

`LinkAllEvents` (bulk) emits no per-link audits; operators see the aggregate via
the timeline's event-count delta.

## Security & Validation

- **IDOR protection**: `requireTimelineInCampaign()` verifies the timeline
  belongs to the campaign; standalone event handlers verify the event's
  `timeline_id` matches; entity group operations are scoped to `timeline_id`
  in SQL.
- **HTML sanitization**: standalone event `description_html` runs through
  `sanitize.HTML()` on Create and Update (same pattern as calendar events).
- **Input validation**: timeline names (max 255), group names (max 200),
  event names (max 255), icon pattern (`^fa-[a-z0-9-]+$`), hex color
  pattern, visibility enum (everyone/dm_only), `visibility_rules` JSON --
  validated on all write paths.
- **Visibility filtering**: `canUserView()` applies role-based + per-user
  JSON rules; malformed JSON fails open with `slog.Warn` (validated on
  write); owners always see everything; view-as-player via `effectiveRole()`.
- **Viewer, not `(role, userID)` (ADR-049):** `ListTimelines`,
  `ListTimelinesForCalendar` and `ListTimelineEvents` take a `permissions.Viewer`,
  so a logged-out visitor to a public campaign cannot skip the per-user
  visibility layer: `filterTimelinesByUser` bypasses only on
  `SkipsPerUserRules()`. `timeline_widget_type.go`'s `ListInstances` (Scribe-gated
  at the route) is the one trusted caller and says so with
  `permissions.SystemViewer(role)`. Pinned by `anonymous_visibility_test.go`.
- **Role enforcement:** route middleware, plus CSRF tokens on state-changing endpoints.
- **`EventCount` and `visibility_rules`:** the `EventCount` subqueries in
  `List`/`ListByCalendar` apply the base `visibility` predicate but cannot see
  `visibility_rules`, which resolve in Go (`canUserView`). `ListTimelines` and
  `ListTimelinesForCalendar` therefore recount each timeline through
  `recountEventsForViewer`, using the same `filterEventLinksByUser` as
  `ListTimelineEvents`, for any viewer that doesn't skip the per-user layer.
  Owners, DM-access members and system callers keep the SQL count.

## Known Limitations

- **No time or end-date in the unified view:** `ToEventLink()` maps name, date,
  category, visibility and entity fields, not `start_hour`, `end_year` etc., so
  the D3 viz and event list show no time info.
- **Recurring events:** fields stored, no server-side expansion.
- **No event duplication.**
- **`LinkAllEvents` race:** two simultaneous bulk-links can hit duplicate-key
  errors and link partially.

## Widget-binding

- `timeline_widget_type.go` registers `"timeline"` with the widget-binding
  framework (`internal/plugins/widgetbindings/.ai.md`); instance = a timeline
  record. No single `DefaultInstance` (the entity block is a campaign preview
  list), so an unbound `BlockTimeline(cc, "")` keeps that list; a bound host
  renders the one timeline.
- `DeleteTimeline` calls the injected `BindingCleaner.OnInstanceDeleted` to
  sweep the timeline's bindings (`SetBindingCleaner`, wired in `app/routes.go`).
- `ListInstances` (-> `ListTimelines`) + `CreateInstance` (-> `CreateTimeline`,
  name only, defaults applied) power the create-or-pick picker. `RenderBlock`
  wraps `BlockTimeline` in `widgetbindings.BlockHost` for in-place swaps;
  `BlockTimeline(cc, timelineID, entityID, source, isScribe)` carries the
  shared Scribe+ `BindingAffordance` (pick a specific timeline / revert to
  the preview list). `timeline-viz` is a `data-widget`, so swaps re-mount cleanly.
