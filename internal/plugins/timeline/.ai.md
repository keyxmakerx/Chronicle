# Timeline Plugin

## Purpose

Interactive visual timelines for campaigns. Each campaign can have multiple
timelines that display events in a zoomable, draggable D3.js visualization.
Timelines support two types of events:
- **Linked calendar events:** Many-to-many links to calendar events (original design).
- **Standalone events:** Events created directly on the timeline, no calendar required.
Timelines can optionally reference a calendar (for linking), or be calendar-free
(standalone events only). Entity groups organize events into swim-lanes.

## Tier

Plugin (Feature app with handler/service/repo/templates)

## Domain Concepts

- **Timeline:** A named visual timeline within a campaign. Optionally references
  a calendar for linking calendar events. Has its own color, icon, visibility, zoom config.
- **Event Link:** A many-to-many join between timelines and calendar events. Supports
  per-link overrides for label, color, and visibility. Source="calendar".
- **Standalone Event:** An event owned directly by a timeline (1:N). Has full parity
  with calendar events (multi-day, times, recurrence). Source="standalone".
- **Entity Group:** A named group of entities used for swim-lane organization. Events
  linked to entities in a group appear in that group's lane.
- **Visibility Rules:** JSON-based per-user visibility overrides (allowed_users,
  denied_users) for fine-grained access control beyond everyone/dm_only.
- **Zoom Levels:** era, century, decade, year, month, day — each with distinct
  visual styles in the D3.js visualization (Sprint 3+).

## Design Decisions

- **ADR-018:** D3.js chosen over Leaflet.js for timeline visualization (Leaflet is
  geographic-only; D3 provides time scales, SVG rendering, zoom/pan, tree layouts)
- **Lens over calendar events:** Timeline events are links (not copies) to calendar
  events, preserving calendar as single source of truth
- **Optional calendar:** Each timeline has a nullable calendar_id FK. When set,
  users can link calendar events. When null, only standalone events are available.
- **Standalone events are 1:N:** Standalone events belong to exactly one timeline
  (not shareable across timelines). Calendar event linking remains M:N.
- **Unified event view:** Service merges linked calendar events and standalone events
  into a single []EventLink slice (via ToEventLink), sorted by date. The Source field
  ("calendar" or "standalone") lets the frontend dispatch actions to correct endpoints.
- **Visibility rules as JSON:** Extends existing everyone/dm_only system with
  per-user allowed/denied lists. Applied to timelines, event links, and standalone
  events. Calendar events also gained per-user rules (migration 000037).

## Audit Log Taxonomy

Timeline mutations emit audit events at the HTTP handler layer via `Handler.logTimelineAudit`, wired by `app/routes.go::timelineHandler.SetAuditService(...)`. Same fire-and-forget contract as the calendar plugin.

Event names (constants in `internal/plugins/audit/model.go`):

- `timeline.created`, `timeline.updated`, `timeline.deleted`, `timeline.visibility_changed`
- `timeline.event_linked`, `timeline.event_unlinked`, `timeline.event_link_visibility_changed`
- `timeline.standalone_event_created`, `timeline.standalone_event_updated`, `timeline.standalone_event_deleted`
- `timeline.entity_group_created`, `timeline.entity_group_updated`, `timeline.entity_group_deleted`
- `timeline.entity_group_member_added`, `timeline.entity_group_member_removed`
- `timeline.event_connection_created`, `timeline.event_connection_deleted`

`UpdateEventConnection` is service-level only — no current HTTP handler entry; `timeline.event_connection_updated` is reserved for when an editor surface lands. `LinkAllEvents` (bulk) doesn't emit per-link audits; operators see the aggregate via the timeline's event-count delta.

## Security & Validation

- **IDOR protection**: `requireTimelineInCampaign()` verifies timeline belongs to
  campaign. Standalone event handlers verify event's `timeline_id` matches. Entity
  group operations are scoped to `timeline_id` in SQL queries to prevent cross-timeline
  manipulation.
- **HTML sanitization**: Standalone event `description_html` is sanitized via
  `sanitize.HTML()` on both Create and Update paths (same pattern as calendar events).
- **Input validation**: Timeline names (max 255), group names (max 200), event names
  (max 255), icon pattern (`^fa-[a-z0-9-]+$`), hex color pattern, visibility enum
  (everyone/dm_only), visibility_rules JSON validated on all write paths.
- **Visibility filtering**: `canUserView()` applies role-based + per-user JSON rules.
  Malformed JSON fails open with `slog.Warn` (validated on write path). Owners always
  see everything. View-as-player mode supported via `effectiveRole()`.
- **Role enforcement**: Route middleware + CSRF tokens on all state-changing endpoints.

## Known Limitations

- **Time/end-date fields not in unified view:** `ToEventLink()` maps name, date, category,
  visibility, and entity fields but does not map time/duration or end date fields
  (start_hour, end_year, etc.) since `EventLink` was designed for calendar event
  links which lack these. Phase 2A will add end date mapping for range bar rendering.
  The D3 viz and event list don't display time info for any events.
- **Recurring events**: Fields stored but no server-side expansion logic.
- **No event duplication**: Events must be manually recreated.
- **LinkAllEvents race condition**: If two users bulk-link simultaneously, duplicate
  key errors may cause partial linking. Acceptable for the current usage pattern.
- **EventCount and `visibility_rules` (C-CALV4-TIEFIX-PB, partial fix, 2026-07-26)**:
  `List`/`ListByCalendar`'s `EventCount` now folds in the same base `visibility`
  (`everyone`/`dm_only`) predicate `ListEventLinks`/`ListStandaloneEvents` already
  apply, so the dm_only delta is closed. A residual gap remains for events carrying
  `visibility_rules` (`{allowed_users, denied_users}`): those are resolved in Go by
  `canUserView` (`ListTimelineEvents`), which the SQL `COUNT(*)` cannot see, so a
  viewer excluded only by `visibility_rules` still inflates the count by one. See
  `## EventCount visibility fix` below.

## EventCount visibility fix (C-CALV4-TIEFIX-PB Bug 2, 2026-07-26)

`List` and `ListByCalendar` computed `EventCount` with two unconditional
`COUNT(*)` subqueries (over `timeline_event_links` and `timeline_events`) while
the row-returning siblings `ListEventLinks`/`ListStandaloneEvents` already
filtered by base visibility. A player would see e.g. "12 events" from the list
while the actual rows they could open numbered 9 — the difference being the
count of hidden events, a value that differences into knowledge the player
shouldn't have (the same class of leak as the entity-tie visibility gap this
same dispatch closed in the calendar plugin).

**Fix:** both subqueries now carry the identical conditional predicate their
row-returning siblings use — `linkedEventVisFilter` (`AND ce.visibility =
'everyone'`, applied via a new `JOIN calendar_events ce` the linked-event
subquery didn't have before) mirrors `ListEventLinks`; `standaloneVisFilter`
(`AND te.visibility = 'everyone'`) mirrors `ListStandaloneEvents`. Both clear
under `permissions.CanSeeDmOnly(role)`, same as every other `visFilter` in this
file.

**This is a PARTIAL fix, not a closed oracle.** `visibility_rules`
(`{allowed_users, denied_users}`) is resolved in Go by `canUserView`
(`ListTimelineEvents` in service.go) — SQL has no visibility into that JSON, so
a viewer excluded from a specific event only via `visibility_rules` still
inflates `EventCount` by one relative to what they can actually open. Booked
for the coordinator; see also `## Known Limitations` above.

**Tests** (`repository_test.go`, new file):
`TestEventCountVisibility_MatchesListFilters` is a DB-less structural guard —
parses `repository.go` via `go/parser`, extracts `List`/`ListByCalendar`'s
source, and asserts (whitespace-flattened, per COMMON §3's safe pin pattern)
that both carry the same visibility fragment their row-returning siblings use.
Proven to fail against the pre-fix code (`git stash` the fix, re-run) with the
exact "subquery missing ..." message, then pass after. `TestTimelineEventCount_
Integration` is a real-MariaDB behavioral proof (one timeline, a public linked
event, a dm_only linked event, a dm_only standalone event) asserting
`EventCount` agrees with `len(ListEventLinks)+len(ListStandaloneEvents)` for
both a player and an owner viewer — mirrors the two pre-existing integration
tests in `internal/plugins/entities` (same DSN/skip helpers, copied verbatim);
like those two, it is skipped under `-short` and was NOT executed in this
sandbox (no docker/MariaDB available here). Run via `make docker-up && make
migrate-up && make test-int`.

## C-SWEEP-R3 bookings (2026-08-07)

- **CLOSED in sweep R4 (2026-08-07): the standalone-event edit modal cleared
  eight fields on a rename.** `UpdateStandaloneEvent` assigned all twenty-one
  fields unguarded and the modal sends five keys, so the entity link, the
  rich-text `description_html`, start/end times, recurrence and per-player
  `visibility_rules` all went when an author only renamed.

  Fixed as the coordinator ruled: **server-side presence-merge**.
  `UpdateTimelineEventInput` is `patch.Field` field for field — an ABSENT key
  preserves, an EXPLICIT null clears, a present value replaces — and the
  service load-merge-writes. The predicted client widening never happened:
  `openEdit` still dispatches its ten keys and the modal still sends its five,
  so raw TipTap `description_html` never goes near `fmt.Sprintf %q` in an HTML
  attribute. `standalone_event_partial_update_test.go` reddens if it ever does.
  The sibling bug is fixed too — the modal now sends an explicit `null` for a
  field the operator emptied, so a description can finally be cleared.

  `visibility_rules` is deliberately still absent from the edit request struct:
  `PUT .../visibility` owns it, and the edit endpoint's job was to stop
  DESTROYING it, not to gain the right to write it. That endpoint in turn
  stopped re-echoing all twenty fields off the loaded row (the pattern the
  ruling replaced) and now sends only the two it owns.
- **`timeline_widget_type.go:81` is the real dependent of the empty-userID sentinel.**
  `ListTimelines(ctx, campaignID, role, "")` passes a genuine NON-owner role with an
  empty user id **on purpose** (its comment: the picker is Scribe-gated at the route).
  That is why the calendar/timeline `userID == ""` bypass cannot simply be failed
  closed — doing so silently drops allow-list-restricted timelines from the widget
  create-or-pick UI. Booked as `C-AUTHZ-EMPTY-USERID`; do not "fix" the sentinel from
  one side.
