# Timeline Plugin

## Purpose

Interactive visual timelines for campaigns: events in a zoomable, draggable
D3.js visualization. A timeline optionally references a calendar (for
**linked** calendar events, many-to-many) or is calendar-free and holds only
**standalone** events (1:N, owned by the timeline). Entity groups organize
events into swim-lanes.

## Tier

Plugin (Feature app with handler/service/repo/templates)

## Domain Concepts

- **Timeline:** named, per-campaign, optional calendar link, own color, icon,
  visibility, zoom config.
- **Event Link:** M:N join between timelines and calendar events; per-link
  overrides for label, color, visibility. `Source="calendar"`.
- **Standalone Event:** owned by exactly one timeline; full parity with
  calendar events (multi-day, times, recurrence). `Source="standalone"`.
- **Entity Group:** named group of entities for swim-lane organization;
  events linked to a group's entities appear in that lane.
- **Visibility Rules:** JSON per-user overrides (`allowed_users`,
  `denied_users`) on top of everyone/dm_only.
- **Zoom Levels:** era, century, decade, year, month, day — distinct visual
  styles in the D3.js visualization.

## Dependencies

- **Uses:** campaigns (CampaignContext, RequireRole), auth (RequireAuth, GetUserID),
  middleware (Render, GetCSRFToken), apperror
- **Cross-plugin:** three adapters in `app/routes.go` read through the
  calendar plugin, all campaign-scoped (a calendar id from another campaign
  answers empty, never an error): `CalendarLister` for the create-form's
  calendar selector, `CalendarEventLister` for the event picker, and
  `CalendarEraLister` for the D3 visualization's era background bands. Eras
  are calendar structure, so `CalendarEraLister` additionally gates on
  role — Owner/co-DM only, regardless of the bound calendar's own
  visibility. `CalendarScope` (adapter wraps the calendar's campaign-scoped
  read) must confirm a calendar is in the timeline's own campaign before
  `CreateTimeline` stores it; unwired, any calendar is refused.
- **Internal:** sanitize (HTML sanitization for standalone event descriptions)
- **Used by:** Sidebar navigation (app.templ), addon system (installedAddons)

## Design Decisions

- **ADR-018:** D3.js over Leaflet.js (Leaflet is geographic-only; D3 gives
  time scales, SVG rendering, zoom/pan, tree layouts).
- **Lens over calendar events:** links, not copies, so calendar stays the
  single source of truth.
- **Unified event view:** the service merges linked calendar events and
  standalone events into one `[]EventLink` (via `ToEventLink`), sorted by
  date; `Source` ("calendar"/"standalone") lets the frontend dispatch to the
  right endpoints.
- Visibility rules extend everyone/dm_only with per-user allowed/denied
  lists, applied to timelines, event links, standalone events, and calendar
  events alike.

## Audit Log Taxonomy

Timeline mutations emit audit events at the HTTP handler layer via
`Handler.logTimelineAudit`, wired by
`app/routes.go::timelineHandler.SetAuditService(...)`. Event names (constants
in `internal/plugins/audit/model.go`): `timeline.created/updated/deleted/
visibility_changed`, `timeline.event_linked/event_unlinked/
event_link_visibility_changed`, `timeline.standalone_event_created/updated/
deleted`, `timeline.entity_group_created/updated/deleted`,
`timeline.entity_group_member_added/removed`,
`timeline.event_connection_created/deleted`.

`UpdateEventConnection` is service-level only — no HTTP handler entry yet;
`timeline.event_connection_updated` is reserved for when an editor surface
lands. `LinkAllEvents` (bulk) emits no per-link audits; operators see the
aggregate via the timeline's event-count delta.

## Security & Validation

- **IDOR protection**: `requireTimelineInCampaign()` verifies the timeline
  belongs to the campaign; standalone event handlers verify the event's
  `timeline_id` matches; entity group operations are scoped to `timeline_id`
  in SQL.
- **HTML sanitization**: standalone event `description_html` runs through
  `sanitize.HTML()` on Create and Update (same pattern as calendar events).
- **Input validation**: timeline names (max 255), group names (max 200),
  event names (max 255), icon pattern (`^fa-[a-z0-9-]+$`), hex color
  pattern, visibility enum (everyone/dm_only), `visibility_rules` JSON --
  validated on all write paths.
- **Visibility filtering**: `canUserView()` applies role-based + per-user
  JSON rules; malformed JSON fails open with `slog.Warn` (validated on
  write); owners always see everything; view-as-player via `effectiveRole()`.
- **`ListTimelines` / `ListTimelinesForCalendar` / `ListTimelineEvents` take a
  `permissions.Viewer`, not `(role, userID)` (ADR-049),** so a logged-out
  visitor to a public campaign cannot silently skip the per-user visibility
  layer: the shared `filterTimelinesByUser` bypasses only on
  `SkipsPerUserRules()`. `timeline_widget_type.go`'s create-or-pick
  `ListInstances` is the one genuine trusted caller and states so with
  `permissions.SystemViewer(role)` (Scribe-gated at the route) — trust
  merely stated, not new behavior. Pinned by `anonymous_visibility_test.go`.
- **Role enforcement**: route middleware + CSRF tokens on all state-changing endpoints.
- **`EventCount` and per-user `visibility_rules`:** `List`/`ListByCalendar`'s
  `EventCount` subqueries carry the same base `visibility` predicate the
  row-returning siblings use, but can't see `visibility_rules`
  (`{allowed_users, denied_users}`), which resolve in Go (`canUserView`). The
  service layer closes that gap: `ListTimelines`/`ListTimelinesForCalendar`
  recount each timeline via `recountEventsForViewer`, reusing the same
  per-event filter (`filterEventLinksByUser`) `ListTimelineEvents` applies to
  its rows, for any viewer that doesn't skip the per-user layer. Owners/co-DMs
  and system callers keep the cheap SQL count.

## Known Limitations

- **Time/end-date fields absent from the unified view:** `ToEventLink()` maps
  name, date, category, visibility and entity fields but not time/duration or
  end-date fields (`start_hour`, `end_year`, etc.) — `EventLink` was designed
  for calendar links, which lack these. The D3 viz and event list show no
  time info for any event.
- **Recurring events**: fields stored, no server-side expansion logic.
- **No event duplication**: events must be manually recreated.
- **`LinkAllEvents` race**: two users bulk-linking simultaneously can hit
  duplicate-key errors and partial linking; acceptable for current usage.

## Widget-binding

- `timeline_widget_type.go` registers `"timeline"` with the widget-binding
  framework (`internal/plugins/widgetbindings/.ai.md`); instance = a timeline
  record. No single `DefaultInstance` (the entity block is a campaign preview
  list), so an unbound `BlockTimeline(cc, "")` keeps that list; a bound host
  renders the one timeline.
- `DeleteTimeline` calls the injected `BindingCleaner.OnInstanceDeleted` to
  sweep the timeline's bindings (`SetBindingCleaner`, wired in `app/routes.go`).
- `ListInstances` (-> `ListTimelines`) + `CreateInstance` (-> `CreateTimeline`,
  name only, defaults applied) power the create-or-pick picker. `RenderBlock`
  wraps `BlockTimeline` in `widgetbindings.BlockHost` for in-place swaps;
  `BlockTimeline(cc, timelineID, entityID, source, isScribe)` carries the
  shared Scribe+ `BindingAffordance` (pick a specific timeline / revert to
  the preview list). `timeline-viz` is a `data-widget`, so swaps re-mount cleanly.
