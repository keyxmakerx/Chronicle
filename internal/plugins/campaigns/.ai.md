# Campaigns Plugin

<!-- Core plugin -- always enabled, cannot be disabled. -->

## Purpose

Core plugin, always enabled. Manages campaigns (worldbuilding containers): the
top-level organizational unit that holds all entities, maps, timelines, etc.
Provides the campaign public page, owner dashboard, settings, member
management, ownership transfer, and the customization hub.

## Tier

Plugin (Core — always enabled)

## Domain Concepts

- **Campaign:** A named worldbuilding project. Contains entities, has settings
  for which modules/plugins are enabled, and owns entity type configurations.
- **Campaign Member:** A user who has access to a campaign with a specific role.
- **Campaign Role:** Owner (3), Scribe (2), Player (1). Numeric levels for >= comparisons.
- **Ownership Transfer:** Token-based transfer flow. 72h expiry, optional email.
- **Dual Permission Model:** MemberRole for content visibility, IsSiteAdmin for admin actions.

## Business Rules

- Campaign names must be non-empty (max 200 chars)
- Slug auto-generated from name, deduplicated with -2/-3 suffix
- Owner cannot remove self or change own role (must transfer first)
- Ownership transfer: DB transaction swaps roles atomically
- Old owner becomes Scribe after transfer
- Admin force-transfer: admin joining as Owner demotes current owner to Scribe
- Regular member addition cannot assign Owner role (use transfer instead)
- Deleting a campaign cascades to all members, transfers, etc. (FK CASCADE)
- Campaign settings JSON stores which modules/plugins are enabled
- Default visibility for new content is `everyone` or `dm_only` (`is_private`
  bool). There is no creator-only "Private" tier — that option was removed
  per ADR-056; a campaign that still has `default_visibility:"private"`
  stored just collapses to `is_private=true` (DM Only) on read.

## Sidebar navigation

`nav.go` owns what a campaign sidebar holds. `sidebar_config.items` is the one
items model: apps (`type:"app"`, older `"addon"`), categories, the owner's
sections (`type:"section"`) and links, each with `section` naming where it
sits (`pinned`, `apps`, `categories` or a section id).

- `NormalizeNav` reads the stored items into sections. Items saved before
  sections existed carry no `section`: an app or link under a section heading
  stays in it, any other app or link lands in Pinned, a category in
  Categories. Enabled apps and categories that are missing are added (a
  never-arranged campaign starts with Journal and Calendar pinned).
- `ViewNav` cuts that down for one viewer. `visible:false` means **hidden
  from players**: the owner still sees the row, marked; nobody else gets it,
  including an owner viewing as a player. Apps also need their addon on and
  the viewer's access (`NavAccess` mirrors each app route's gate).
- A section heading with `visible:false` (only the old editor wrote one) is
  no section for anyone, the owner included: `NormalizeNav` leaves it out,
  the rows after it stay under the visible heading before it, and
  `validateSidebarItems` drops it on the next save. Its label can never
  reach a player.
- Everything a viewer's sidebar shows (the HTML and the command palette's
  "Go to" list) comes from `ViewNav`, so a hidden row cannot reach a player
  through either. Hiding a row does not make its pages private; page
  visibility is separate.
- `validateSidebarItems` guards `PUT /sidebar-config`: known types, ids,
  existing sections, label length, safe link URLs, Font Awesome link icons.
- The app catalog (which addon turns each app on, its page and access) lives
  in `internal/app/routes.go` (`navAppCatalog`), since it names other plugins.
- Drawing is the layout's: `internal/templates/layouts/nav.templ` draws the
  rows it is given and `nav_state.go` works out where the viewer is. The
  current row is the one an entity page names through `layouts.WithNavHint`
  (its category), else the longest row URL the path starts with; it carries
  the living ring and the open page's name. Folds are remembered per viewer
  in the `chronicle_nav_folds` cookie, scoped to the campaign's path, so the
  server paints them. `static/js/sidebar_nav.js` runs folding, moves the ring
  on boosted navigation (it reads the `[data-nav-current]` marker in
  `#main-content`) and keeps the phone drawer's focus.
- A category row opens the category's page. The sidebar has no page tree;
  nothing in it opens the category slide-over (`GET /sidebar/drill/:slug`).
- Manage (Members, Customize, Extensions, Settings) is the owner's alone.
- **Editing** is the owner's pencil (`static/js/sidebar_editor.js`). It works
  on one staged draft of the whole arrangement, which only the owner's page
  carries (`#sidebar-nav[data-nav-edit]`, built by `buildNavEdit` in
  `internal/app/nav_layout.go`; hidden rows and turned-off apps included).
  Save writes it with one `PUT /sidebar-config` (each owner section ahead of
  its rows, every row naming its section, turned-off apps kept in place),
  then swaps in the sidebar the server draws. Nothing is stored before Save;
  Cancel drops the draft. `nav_editor_test.go` and
  `test/js/sidebar_editor.test.mjs` pin that contract.
- **A member's own pins**: players and scribes pin rows for themselves with
  the pin on each row; ViewNav moves those rows into Pinned, after the
  campaign's, marked as theirs. They live in `campaign_members.nav_pins`
  (read for the viewer only, in the LayoutInjector). `PUT /nav-pins` refuses
  the owner, who pins for everyone, and checks every key against the
  caller's own sidebar (`NavSectionsSource`, drawn by `internal/app`;
  `PinnableNavKeys`, `CleanNavPins`), so a pin can never name a row hidden
  from players or an app they cannot open.

## Campaign Customization

- **Backdrop image**: `backdrop_path` column — campaign hero image uploaded via settings page
- **Accent color**: four semantic slots (below), all stored in the
  `campaigns.settings` JSON column — no migration per slot added
- Campaign settings page has image upload and color picker sections

### Accent slots

| Slot | Name | Covers | `CampaignSettings` field | Empty falls back to |
|---|---|---|---|---|
| 1 | **Site accent** | Overall feel — nav/chrome, links, selection, today ring | `AccentColor` (`accent_color`) | hardcoded default (`#6366f1`) |
| 2 | **Action highlight** | Primary buttons, hover/press states, FABs | `AccentAction` (`accent_action`) | Site accent |
| 3 | **App accent** | Per-app identity — character pages, calendar app | `AccentApp` (`accent_app`) | legacy Surface-1, then Site accent |
| 4 *(optional)* | *(unnamed — legacy surface pair)* | Not surfaced as its own picker; defaults to slot 3 when unused | `AccentSurface2` (`accent_surface_2`) | Site accent |

`AccentSurface1`/`AccentSurface2` (`accent_surface_1`/`accent_surface_2`) are
the pre-slots "surface pair" fields, kept for back-compat (mapped, not
deleted); `AccentApp` takes precedence over `AccentSurface1` wherever both are
consumed (`model.go:539-543`).

All five fields live in `CampaignSettings` (`model.go:536-549`), JSON inside
the existing `campaigns.settings` column — adding a slot is additive, never a
migration. `internal/templates/layouts/data.go`'s `AccentColorCSS` emits each
set slot as a `--color-accent{,-action,-app,-surface-1,-surface-2}` CSS
custom property block; unset slots emit nothing. Consumers resolve the
fallback chain client-side via `var(--color-accent-app,
var(--color-accent-surface-1, var(--color-accent, #6366f1)))`-shaped chains,
not server-side branching. Save path: `PUT /campaigns/:id/accent-color` with
an optional `slot` form value (`action`/`app` string keys for the two new
slots, `1`/`2` numeric for the legacy surface pair, omitted for Site) — no
new route. Hub UI: three labeled pickers in the Appearance tab ("Site accent",
"Action highlight", "App accent"), `branding.templ` + `appearance_editor.js`'s
staged draft/save flow.

## Two-Dashboard Architecture

Campaigns have two independently customizable dashboards:

- **Campaign Page** (`GET /campaigns/:id`) — visible to all members and public visitors. The "front page" of the campaign. Layout stored in `dashboard_layout` column.
- **Owner Dashboard** (`GET /campaigns/:id/dashboard`) — visible only to campaign owner. Management-focused dashboard with quick links (Settings, Customize, Members, Plugins), category grid, and recent entities. Layout stored in `owner_dashboard_layout` column (migration 000006).

Both dashboards use the same `DashboardBlockSwitch` dispatcher and are editable via the Customization Hub (Dashboard tab shows both editors side-by-side). The dashboard editor widget mounts with different `data-endpoint` values pointing to the respective layout APIs.

## Dashboard Block Types

The campaigns plugin defines the central `DashboardBlockSwitch` dispatcher. Supported block types:
- `entity_count`, `recent_entities`, `calendar_preview`, `timeline_preview`, `map_preview`,
  `relations_graph`, `quick_links`, `media_gallery`
- `calendar_full`, `timeline_full`, `relations_graph_full`, `map_full` (full-page embeds)
- `session_tracker`, `activity_feed`, `sync_status` (utility blocks)
- All embed blocks use HTMX lazy-loading via `/embed` endpoints on their respective plugins

## Export / import fidelity

Read this before touching `export_service.go`, `internal/app/export_adapters.go`,
`import_report.go` or `import.templ`.

- **Import is best-effort by design, and now says so.** One unparseable row
  must not abandon a half-built campaign, but a partial import must not claim
  full success either. `campaigns.ImportReport` is threaded through the
  importer adapters the same way `*IDMap` is, and is a **return value, not a
  side channel** — `Import` returns `(*Campaign, *ImportReport, error)`. A
  lossy import renders `ImportResultPanel` ("Imported with losses", the
  tally, the per-object list) instead of the plain success redirect.
  - Record degraded-but-created rows too (object exists but something on it
    was still lost), not just hard failures.
  - Detail is capped at 200 records but the count stays exact past the cap.
  - `FailN` records a homogeneous batch as one row with a real count.
  - Section/kind labels route through constants in `import_report.go`, not
    inline literals (plugin-slug strings outside the owning plugin directory
    fail `tools/check-plugin-isolation.sh`).
- **Shared notes travel; egress is narrow.** `SetNoteExporter`/`SetNoteImporter`
  wire `internal/widgets/notes`' `ListSharedByCampaign` into export/import.
  Only `is_shared=TRUE` notes leave; `shared_with` targets are dropped;
  personal notes never leave. See `internal/widgets/notes/.ai.md`. Structural
  pin: `internal/wire/export_adapter_wiring_test.go` (an AST pin requiring
  `routes.go` to call all twenty export/import setters).
- **Media is archived, not re-attached.** `?include_media=1` produces a
  correct archive (`campaign.json` plus `media/<uuid>.<ext>` with real
  bytes); import currently discards every media entry, with an honest
  unrestored-file count in `ImportResultPanel` and copy on both the settings
  and import pages saying so. `ExportMediaFile` carries no `Filename`, so a
  manifest row cannot be joined to a `media/` zip entry yet either. Open
  work (restoring the references, not just the files): #612.
- **Import ordering is unchanged.** The Player Character addon gate can still
  fire because addons import after entities; reordering is deferred to the
  same media-restore work (#612), which needs media to move ahead of
  entities anyway.
- Every campaign export inherits the entities repository's paginated
  readers; see `entities/.ai.md` for the total-order fix those readers
  needed to stop dropping/duplicating rows.
