# Campaigns Plugin

Core plugin, always enabled. A campaign is the top-level container for entities,
maps, timelines and the rest. This plugin owns the campaign pages and dashboards,
settings, members and roles, ownership transfer, the sidebar, the Customize
hub and campaign export/import.

## Domain Concepts

- **Roles:** Owner (3), Scribe (2), Player (1), None (0, a site admin who has not
  joined). Compare numerically (`>=`). Co-DM is the Scribe role plus a DM grant.
- **Dual permission model:** `MemberRole` for content visibility, `IsSiteAdmin`
  for admin actions.
- **Ownership transfer:** token flow, 72h expiry, optional email.
- **Hand-over when the owner is away:** the owner picks Never (default), 3, 6 or
  12 months (`handover_after_months`, owner-only `PUT /campaigns/:id/handover-setting`).
  Once `last_seen_at` is that far back, a site admin may give the campaign to an
  existing non-guest member (`AdminHandOver`, `handover.go`). Every rule is
  re-checked there, a pending transfer is cancelled, the old owner becomes Co-DM
  and is emailed.

## Foundry

- **Connect line.** The Foundry row on `/campaigns/:id/extensions` shows a status
  dot, module version and a paste box. It reads through `FoundryConnector`
  (`SetFoundryConnector`, wired in `internal/app/routes.go` by
  `foundryConnectorAdapter` over the sync key service, the websocket hub and
  `BaseURL`); a nil connector leaves the plain "Set up" link. Status is the hub's
  live socket, else the newer of the hub's last contact and the newest
  `last_used_at` of the campaign's active keys: under 24 hours green, longer
  amber, nothing grey. The paste box shows only the newest active key's stored
  prefix. "Make a new connect line" mints an additional key (read, write, sync)
  and shows the full line once (`Cache-Control: no-store`); older keys are not
  revoked. Format: `chronicle://host[:port]/path/c/<campaignID>?key=...` for an
  https base URL, `chronicle+http://` for http, built only by
  `BuildFoundryConnectLine`.
- **Presence.** `GET /campaigns/:id/foundry-presence` lives in the `foundry_vtt`
  plugin. Campaigns still owns the version-pin settings (`FoundryModulePin`,
  `FoundryModulePinMode` in `model.go`; `SetFoundryModulePin` /
  `GetFoundryModulePin` / `SetFoundryModulePinMode` / `GetFoundryModulePinMode`
  on `CampaignService`), which `foundry_vtt` reads through
  `foundryCampaignSettingsAdapter`. Extracting this coupling is #719.

## Business Rules

- Deleting a campaign (owner or site admin) moves it to the site Trash (`deleted_at`, `trash_repository.go`); it never hard-deletes. Every repository read filters on `deleted_at IS NULL`, and `FindMember` and `ListMembers` join the campaign (so the sessions token routes stop too), invite and transfer acceptance refuse it, and the Foundry auto-pin lists skip it, so campaign routes, the sync API, sockets and media all see "not found". Only the admin Trash page (admin plugin) can Undo (`RestoreFromTrash`) or purge (`PurgeTrashed`, which claims with `purge_started_at`, then runs the old delete flow: media files, hook, row). Owners have no Trash page.

- Guest codes let someone with no account join one campaign as a player
  with only a name. Auth owns the guest account and the join page; this
  plugin owns the codes and the membership. A guest is shown as "Guest" with
  no email. Removing a guest, or purging their campaign from the Trash, ends their
  account (`OnMemberRemoved`, `OnCampaignDeleted`). Merging a guest into an account
  moves their membership (`MoveMembership`: an existing member keeps their
  role and gains the guest's character only if they had none).

- A new campaign starts with the site look: when an admin has chosen one
  (Admin > Site look), `Create` seeds the whole Appearance from that look
  (`look_presets.go`, read through the `SiteLookSource` interface), so the
  campaign renders as the look straight away. `lookPresets` mirrors the LOOKS
  table in `static/js/widgets/customize_look.js`; `test/js/fixtures/look_pins.json`
  pins both. Seeding runs the same validation as a Customize save. Classic is
  the default and stores nothing; a failed read never blocks creating a campaign.
- Campaign names must be non-empty (max 200 chars)
- Slug auto-generated from name, deduplicated with -2/-3 suffix
- Owner cannot remove self or change own role (must transfer first)
- Ownership transfer: DB transaction swaps roles atomically
- Old owner becomes Scribe after transfer
- Admin force-transfer: admin joining as Owner demotes current owner to Scribe
- Regular member addition cannot assign Owner role (use transfer instead)
- Deleting a campaign cascades to all members, transfers, etc. (FK CASCADE)
- Campaign settings JSON stores which modules/plugins are enabled
- Settings writers save through `saveSettingsChanges`, which writes only the top-level keys they changed (`UpdateSettingsKeys`, one JSON_SET/JSON_REMOVE statement), so writers holding an older copy of the campaign can't undo each other (`settings_keys_integration_test.go`). `Update` (name, description, public) never writes settings.
- Default visibility for new content is `everyone` or `dm_only` (`is_private`
  bool). There is no creator-only "Private" tier — that option was removed
  per ADR-056; a campaign that still has `default_visibility:"private"`
  stored just collapses to `is_private=true` (DM Only) on read. A new
  campaign starts on `dm_only` (`newCampaignSettings`); existing campaigns
  keep what they have.

## Sidebar navigation

`nav.go` owns what a sidebar holds. `sidebar_config.items` is the one items
model: apps (`type:"app"`; `"addon"` is the older spelling, still read), categories,
the owner's sections (`type:"section"`) and links, each with `section` naming
where it sits (`pinned`, `apps`, `categories` or a section id).

- `NormalizeNav` reads stored items into sections. Items without a `section`:
  an app or link under a section heading stays in it, any other app or link goes
  to Pinned, a category to Categories. Missing enabled apps and categories are
  added (a never-arranged campaign starts with Journal and Calendar pinned).
- `ViewNav` cuts that down for one viewer. `visible:false` means **hidden from
  players**: the owner still sees the row, marked; nobody else does, including an
  owner viewing as a player. Apps also need their addon on and the viewer's
  access (`NavAccess` mirrors each app route's gate). An app marked `Empty` (set
  by the composition root for Calendar when the viewer can see no calendar)
  reaches only the owner.
- A section heading with `visible:false` is no section for anyone:
  `NormalizeNav` omits it, its rows stay under the visible heading before it, and
  `validateSidebarItems` drops it on the next save. Its label can never reach a
  player.
- The sidebar HTML and the command palette's "Go to" list both come from
  `ViewNav`, so a hidden row cannot reach a player through either. Hiding a row
  does not make its pages private.
- `validateSidebarItems` guards `PUT /sidebar-config`: known types, ids, existing
  sections, label length, safe link URLs, Font Awesome link icons.
- `OrderNavCategories` is how AI Import's `menu-order` change reorders
  categories: the listed ones swap places among themselves within each section,
  so none changes section and other rows stay put. A category with no row gets
  one where the sidebar already draws it; a never-arranged sidebar first gets its
  default-pinned apps written, because any stored row makes the layout count as
  arranged.
- The app catalog (which addon turns each app on, its page and access) is
  `navAppCatalog` in `internal/app/routes.go`, since it names other plugins.
- Drawing is the layout's: `internal/templates/layouts/nav.templ` draws given
  rows; `nav_state.go` works out where the viewer is. The current row is the one
  an entity page names via `layouts.WithNavHint` (its category), else the longest
  row URL the path starts with. The highlight is the look's nav style
  (`Appearance.EffectiveNavStyle`); a blank style means Classic's still rail on
  Classic and the living ring on other looks, so a style is stored only when it
  differs. Folds are remembered per viewer in the `chronicle_nav_folds` cookie
  (scoped to the campaign path) so the server paints them. `static/js/sidebar_nav.js`
  runs folding, moves the ring on boosted navigation (reads `[data-nav-current]`
  in `#main-content`) and keeps the phone drawer's focus.
- Hiding the sidebar slides it left; while hidden, resting the pointer on the
  window's left edge peeks it 70 px out (`static/js/sidebar_peek.js`; hover-capable
  screens 768 px and up). Empty space in the peek opens it fully.
- A category row is a button that slides the category drill panel over the
  sidebar (`GET /sidebar/drill/:slug`, `static/js/sidebar_drill.js`): entity
  tree, folders, favorites, recently viewed, tag filters. The category's own page
  stays reachable from the panel header. The sidebar itself has no page tree.
- Manage (Overview, People, Media, Customize, Game & features, Foundry while
  sync-api is on, Settings) is the owner's alone. The sidebar is the only Manage
  menu; each page opens with `layouts.ManageHeader` (a title, no tab strip).
- **Editing** is the owner's pencil (`static/js/sidebar_editor.js`) on one staged
  draft of the whole arrangement, carried only on the owner's page
  (`#sidebar-nav[data-nav-edit]`, `buildNavEdit` in `internal/app/nav_layout.go`;
  hidden rows and turned-off apps included). Save writes one `PUT /sidebar-config`
  (each owner section ahead of its rows, every row naming its section, turned-off
  apps kept in place), then swaps in the server's sidebar. Nothing is stored
  before Save; Cancel drops the draft. Pinned by `nav_editor_test.go` and
  `test/js/sidebar_editor.test.mjs`.
- **Member pins.** Players and scribes pin rows for themselves; `ViewNav` moves
  them into Pinned after the campaign's, marked as theirs. Stored in
  `campaign_members.nav_pins`, read for the viewer only (LayoutInjector).
  `PUT /nav-pins` refuses the owner (who pins for everyone) and checks every key
  against the caller's own sidebar (`NavSectionsSource`, `PinnableNavKeys`,
  `CleanNavPins`), so a pin cannot name a row hidden from players or an app they
  cannot open.
- **Row menu** (`static/js/sidebar_row_menu.js`; right-click, long press, dots
  button, Shift+F10 / Menu key). Owner: pin for everyone, hide from players,
  move up/down in the section, Edit sidebar; each saves at once through the
  editor's `quickChange` (same `PUT /sidebar-config`). Player/scribe: own pin.
  Link rows also offer a new tab. Shut while the owner edits.
  `test/js/sidebar_row_menu.test.mjs`.
- **Category panel rows** use the same menu: open, new tab, copy link for anyone;
  scribe or owner also new page inside, new folder beside, rename
  (`PUT …/metadata`), Move to folder (`PUT …/reorder`); folders offer new folder
  inside, rename, move, and owner delete after a second step. The tree's
  `data-can-edit` and `data-can-delete-folders` (`sidebar_list.templ`) say which
  to offer; routes check again. `test/js/sidebar_tree_menu_browser.test.mjs`.

## Customize

One frame (`customize_shell.templ`, `static/js/widgets/customize_shell.js`,
`static/css/customize_shell.css`) around areas that each have their own address:
a rail, a trail, Find ("/", over areas, categories and look sections) and one
save bar. Every area writes into the owner's one draft (ADR-066) via
`Chronicle.customizeSet(section, value)`; the shell stores it on the server as
the owner edits, so it survives a reload or another device. The save bar lists
changes from each section's `_changes`, undoes, redoes, discards (with an Undo
toast) and saves (Ctrl+S too). A Save that leaves a section unapplied keeps it in
the draft and says which. The shell tells areas about undo, redo, discard,
restore and save with a `chronicle:customize-draft` event, never about their own
edits.

- **Categories** (`static/js/widgets/customize_categories.js`, section
  `categories`): a grid, a New category dialog (blank or copying another's layout
  and fields), and per category the tabs Page layout, Category home, Fields,
  Starting text, Settings. Settings (names, icon, colours, claiming, players'
  menu, parent, kinds, delete) go through the draft. Page layout is the
  Customizer's layout tool (`static/js/widgets/customize_page_editor.js`,
  entities plugin), which writes the category layout into the same section via
  `Chronicle.customizeCategoryWrite`, so the save bar still lists its changes.
  Widgets draw from one of the category's pages; a widget that page leaves
  empty, or every widget when the category has no page, shows fixed example
  content marked "Example". The other tabs are the existing editors, loaded from
  `/entity-types/:etid/customize-tab/:tab`, and save with their own buttons, as
  do Home pages and plugin areas; each says so.
- **Look** is the look editor inside the frame (`customize_look.templ`,
  `static/js/widgets/customize_look.js`, `static/css/customize.css`); its draft
  is the `look` section and its own save bar is hidden. The owner starts from
  one of eight looks, then works in four rooms (`ROOMS` in the widget): Site
  frame, Colours and type, Pages and sheets, People. Each room shows a live
  example site; clicking a part opens that section's panel (`FZ` maps sections to
  parts; `#section` / `#room` addresses, `hashTarget`). One Save sends the whole
  draft to `PUT /campaigns/:id/appearance`, the only route that writes a look
  (no single-setting routes). The example sheet is a sample on a
  `data-sheet data-sheet-preview` root, so `sheet_styles.css` draws it in the
  draft's sheet style; `sheet_motion.js` lets a preview root keep its own style.
- **Hover cards and sheets:** `hover_card` (paper, plain, night, compact) becomes
  `data-cz-hover`; `sheet_style` becomes `data-cz-sheet`, omitted for `modern`
  (`layouts/appearance.go`). A rulebook has no setting: it wears its game
  system's look.
- **DM Screen look:** `Appearance.DmScreenKit` (`page.dmKit` in the draft; `same`
  clears it, `material` is kept as a real choice). Empty wears the pages' kit;
  set, it becomes `data-dms-kit` for the DM team, and a co-DM's own `dmscreen`
  pick still wins for them. Players never see the screen.
- **Who can change.** For the sheet style (`sheet`), pages' style kit (`page`),
  hover card look (`hover`) and DM Screen kit (`dmscreen`), the owner picks who
  may choose their own: `owner`, `codm` or `everyone`. Stored as
  `Appearance.AccessSheet` / `AccessPage` / `AccessHover` / `AccessDmScreen`
  (empty defaults: sheet `everyone`, page and hover `owner`, DM Screen `codm`),
  the `access` object of the draft and `AppearanceInput`; an input without
  `access` keeps what is stored, so a preset cannot reset it. The DM Screen never
  allows `everyone`: save refuses it and `LookPart.Access` reads a hand-edited one
  as the default. "Co-DM" = scribes, the owner and any member given DM access.
  A pick is per campaign and person in `campaign_member_look_picks` (core
  migration 000057, keyed by part, so new parts need no migration); the owner has
  none (their pick is the campaign's look). The LayoutInjector lays the viewer's
  picks over a copy of the appearance for that request only (`MemberLookPicks`
  re-checks access every time, so a narrowed setting hides a pick without
  deleting it): sheet pick to `data-cz-sheet`; page pick to `StyleKit`
  (`data-cz-kit`, only under the Material page look); hover pick to `HoverCard`;
  DM Screen pick to `AppearanceData.DmScreenKit` (`data-dms-kit`, scoping the
  kit's tokens to `.dms-overlay`, so the page keeps the campaign's kit).
- **Timeline popups:** `timeline_popup` (`classic` | `corner`, draft
  `hover.timelinePopup`) becomes `data-cz-tlpop`, omitted for classic. New
  campaigns start on `corner`; older ones keep classic; a save that omits it
  keeps the stored value (`timelinePopupChoice`).
- **Page look:** `page_look` (`standard` | `annals`, draft `page.look`) becomes
  `data-cz-page`, omitted for standard; `.ai/ui-standard.md` ("Customize goes
  further") says what Annals draws.
- **Style kit:** `style_kit` (material, sharp, ornate, flowing, lumen,
  sketchbook; draft `page.kit`) becomes `data-cz-kit` only under Annals, omitted
  for material; a save without a kit keeps the stored one (`styleKitChoice`).
  `layouts/style_kits.go` loads the kit's faces where the owner picked none and
  reads the campaign colour against the kit's page; `static/css/style_kits.css`
  draws them (`.ai/ui-standard.md`, "Style kits").
- **Starting draft:** `customize_state.go` fills every unset choice from the
  Classic look and carries older slots over (`accent_app` becomes Surface A,
  `font_family` the nearest text face).
- **Save:** `applyAppearance` validates the whole draft and writes one settings
  update (the backdrop has its own column and goes first). Choices live in
  `CampaignSettings.Appearance`; defaults are stored empty, so a campaign that
  never saves renders as shipped. Colours pass through `internal/colour.Tame`
  (the page picker's rule), so no request can store a neon colour.
- **Pictures:** uploaded on choice to `/appearance/picture` (logo 1 MB, backdrop
  4 MB, header 1.5 MB, menu banner 1.5 MB), used only once a saved draft holds
  them. Save accepts a picture only if it is already stored for this campaign or
  this campaign uploaded it (`MediaUploader.OwnsFile`). The page deletes pictures
  it uploaded and no longer needs through `DELETE /appearance/picture`; the
  handler refuses malformed names and does nothing when the saved settings or
  backdrop column still name the picture (`appearancePictureSaved`);
  `MediaUploader.DeletePicture` (`internal/app/routes.go`) deletes only a file of
  this campaign stored with the backdrop usage type, which only the picture
  upload sets.
- **Showing it:** `layouts.AppearanceAttrs` and `layouts.AppearanceCSS` put the
  look on every page. After a Save the editor re-renders in the background and
  swaps the style blocks, `data-cz-*` attributes, header and menu logo/name; no
  reload.
- **Sidebar:** always dark. Colour: Charcoal (default), Ink, Tinted (dark shade
  of the chrome accent) or the owner's own; Tinted and own pass through
  `colour.MenuDark`, which darkens until white menu words keep 7:1 (and
  `customize_look.js` applies the same rule). Top-left corner: plain, a subtitle
  (40 chars) or a banner picture; the peeking menu shows only the logo. Peek glow
  follows the accent or has its own colour (`--peek-glow-rgb`, `sidebar_peek.js`).
  A look may set the menu colour (`colours.sidebar`). A companion value (own
  colour, banner, subtitle, glow colour) is stored only while the choice using it
  is selected.
- **Header:** Slim (default) or Tall (6rem), `data-cz-hdr` on `<html>`.
  Backgrounds: solid, gradient, moving (a transform-only strip slid by
  `static/js/widgets/header_motion.js` on the shared `MotionRest` clock in
  `static/js/motion_rest.js`; it rests when the tab hides, the window blurs, the
  pointer leaves or 8 s pass without input, and stays still under
  `prefers-reduced-motion` or the campaign's reduce switch), a picture, or the sky.
  Sky stores only its mode; the page draws the campaign's own sky from its
  default calendar as the viewer may see it (`static/js/widgets/header_sky.js`;
  calendar id from `headerSkyCalendarID` in `internal/app/header_widgets.go`),
  over still night colours when there is no calendar or it cannot be read.
  Widgets are an ordered list of at most four: `links`, `text`, `note` (opens
  quick capture), `search` (opens topbar search). Below md the bar shows the
  first widget and a "+N" tray button (Alpine). `TopbarContent.Mode` still names
  the first widget for older readers, or `widgets`.
- **Live header widgets:** `date`, `weather`, `moon`, `era` and `session` (next
  game night) are read-only chips for today's world, never days ahead. Settings
  store only the kind names; `internal/app/header_widgets.go` (called from the
  layout injector in `routes.go`) resolves data from the calendar service
  (default calendar's date, today's weather, each visible moon's phase, current
  era) and the sessions service (`NextGameNight`, members only) into
  `layouts.TopbarLiveData`. A widget with no data, or a failed read, draws nothing
  and does not count toward "+N". The calendar-backed ones also need the calendar
  addon on and healthy.
- **Not built:** the Sky background (#959); the editor lists it as under
  construction.

## Dashboards

- **Campaign page** (`GET /campaigns/:id`): all members and public visitors;
  layout in the `dashboard_layout` column.
- **Owner dashboard** (`GET /campaigns/:id/dashboard`): owner only; "Needs you"
  card, quick links, category grid, recent entities; layout in
  `owner_dashboard_layout` (migration 000006).

Both use `DashboardBlockSwitch` (`dashboard_blocks.templ`; an unknown type
renders nothing) and the dashboard editor widget with different `data-endpoint`
values.

**Tile sections.** A `DashboardRow` with `kind: "tiles"` holds `tiles` (shared
`tilegrid.Tile`) instead of columns (ADR-065); `dashTileSection`
(`dash_tiles.templ`) draws it. `validateDashboardLayout` checks the shape and,
through the `TileSizeResolver` the composition root wires (`SetTileSizeResolver`,
the entities block registry), each tile's type and size. A size falls back to its
type's first allowed size; a type with none shows a notice. A `dm_only` tile is
left out for viewers who cannot read DM-only content. `ComingUpRepeats` keys tile
positions as `{row, -1, tile}`.

**Block types.**
- Native: `welcome_banner`, `quick_actions`, `category_grid`, `recent_pages`,
  `entity_list`, `text_block`
- Embeds of other plugins: `pinned_pages` (lazy-loads
  `GET /campaigns/:id/pinned-pages` from the entities plugin: the Director's
  pins, then the viewer's starred pages), `calendar_preview`, `timeline_preview`,
  `relations_graph`, and the full-size `calendar_full`, `timeline_full`,
  `relations_graph_full`, `map_full`
- Utility: `activity_feed`, `sync_status` (lazy-loaded from foundry_vtt's
  dashboard sync block).
- `coming_up`: placeholder that lazy-loads `GET /campaigns/:id/coming-up`, served
  from `internal/app/coming_up.go` because it joins the calendar and game nights.
  Not in `DefaultDashboardLayout`; the owner places it. An empty response (both
  addons off) removes the placeholder. Retired `session_tracker` draws the same
  card where a saved layout holds one (`BlockMeta.Retired`; the editor no longer
  offers it); `DashboardLayout.ComingUpRepeats` keeps a layout holding both to one
  card. The same "waiting on you" rows feed the Game nights calendar's button via
  `GET /campaigns/:id/coming-up/waiting`.
- `map_preview` is retired; saved layouts holding it drop the block at render.

**Homes.** Each viewer gets one saved home (`CampaignContext.HomeAudience`):
the owner and every co-DM the Director's, a viewer with no membership the guest
one, members their role's. Director's, players' and Scribes' fall back to
Default, then the built-in home; the guest home falls back to
`DefaultGuestDashboardLayout` (built-in home without quick actions), never to
Default, so a members' home never reaches a visitor. `Campaign.HomeLayout` is the
one place these fallbacks live, used by the page and the Customizer. A new
campaign is created with the Director's home saved (`starterDirectorHome`,
`first_run_home.go`): the built-in home plus an ordinary Text Block of setup
steps under the welcome banner; nothing re-adds it. The Customizer names that tab
"<GM term> team" and the owner dashboard tab "Overview".

**Visibility.** A block shows only when its viewer can see something in it; the
owner sees every block. `activity_feed` and `sync_status` read owner-only routes,
so only the owner gets them. `category_grid` omits categories with no page the
viewer can open (`dashVisibleCategories`). Calendar cards show "isn't enabled"
to the owner alone, link into the members-only calendar only for members, and
mark their lazy slot `data-drop-if-empty`, which `boot.js` answers by removing the
block when the fragment comes back empty.

Blocks carry the shared parts (`cb-title`, `cb-head`, `cb-link`, `cb-card`, plus
`cb-hero`, `cb-epi`, `cb-quiet`, `cb-shortcut`, `cb-row`), so the Annals page look
turns the home into a front page (`page_look_annals.css`, "The campaign home").

## Export / import fidelity

Read before touching `export_service.go`, `internal/app/export_adapters.go`,
`import_report.go` or `import.templ`.

- **Import is best-effort and reports losses.** One unparseable row must not
  abandon a half-built campaign, and a partial import must not claim full
  success. `ImportReport` is threaded through the importer adapters like `*IDMap`
  and is a **return value, not a side channel**: `Import` returns
  `(*Campaign, *ImportReport, error)`. A lossy import renders `ImportResultPanel`
  ("Imported with losses", tally, per-object list) instead of the success
  redirect.
  - Record degraded-but-created rows too, not just hard failures.
  - Detail is capped at 200 records (`maxRecordedImportFailures`); the count stays
    exact past the cap. `FailN` records a homogeneous batch as one row with a
    real count.
  - Section/kind labels come from constants in `import_report.go`, not inline
    literals (plugin-slug strings outside the owning plugin directory fail
    `tools/check-plugin-isolation.sh`).
- **Shared notes travel; egress is narrow.** `SetNoteExporter` / `SetNoteImporter`
  wire `internal/widgets/notes`' `ListSharedByCampaign`. Only `is_shared=TRUE`
  notes leave; `shared_with` targets are dropped; personal notes never leave (see
  `internal/widgets/notes/.ai.md`). `internal/wire/export_adapter_wiring_test.go`
  is an AST pin requiring `routes.go` to call all twenty-one export/import setters.
- **ZIP import restores pictures.** `?include_media=1` writes `campaign.json` plus
  `media/<basename>` (stored names carry date folders; the entry is the
  `<uuid>.<ext>` basename, named by `ExportMediaFile.Filename`). On import, media
  is restored first through `MediaService.Upload` (same type, size and quota
  checks as any upload); `remapMediaReferences` then replaces each restored
  file's old id with its new one across the envelope (portraits, covers, map
  backgrounds, tokens, `/media/<id>` in any text). An id with no restored file
  is left alone. A manifest without `Filename` is paired by id. A JSON upload
  carries no bytes; the report counts missing files and pages whose picture did
  not come back.
- **Add-ons import first; the file's categories replace the defaults.** An add-on
  gates what may be created (the Player Character category is refused while its
  addon is off), so `Import` restores add-ons before entity types. A file that
  carries categories creates the campaign with `SkipEntityTypeSeed`, so defaults
  do not arrive twice. A category an add-on already made (premade Player
  Character type, a game system's presets) is reused, matched by the PC rule or
  slug. Types export `preset_category`, `parent_type_slug` and `claimable`, which
  keeps a PC category claimable and nested on restore.
- **Page ids are remapped wherever the campaign names them.** `sidebar_config` and
  each category's description and `pinned_entity_ids` are written after every
  page exists: `remapSidebarIDs` (`import_sidebar.go`) and the importer adapter
  map category and page ids to new ones and drop any whose original did not come
  back (the report lists it). Timeline events export from the full event, so
  description, times of day and repeat travel. A calendar's `tracks_real_time` and
  `real_time_zone` travel; import enables real time only for a zone this server
  can load and reports any other.
- Exports use the entities repository's paginated readers (see `entities/.ai.md`
  for the total ordering they need).
