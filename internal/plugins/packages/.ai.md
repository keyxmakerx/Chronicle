# Packages Plugin

The packages plugin manages external package repositories for Chronicle. It pulls
content packages (game systems and other extensions) from GitHub repos, providing
version management, auto-updates, and an admin UI.

This plugin is **fully type-agnostic**: it knows nothing about
the specifics of any particular package type. The `PackageType` enum (currently
`system` and `foundry-module`) is just a label admins attach to a package;
type-specific behavior is owned by sub-plugins that register via the
`PostInstallHook` extension point. The first such sub-plugin is `foundry_vtt`,
which owns every Foundry-specific behavior (manifest rewriting, per-campaign
signed URLs, descriptor reading). Future TTRPG VTT integrations (Roll20,
Owlbear) follow the same pattern.

## Architectural decision log

| Decision | Why |
|---|---|
| No Foundry-specific coupling in this plugin | Foundry-specific behavior lives entirely in the `foundry_vtt` sub-plugin; this plugin is generic and serves any package type via `PostInstallHook`. Keeps "Foundry stuff baked into Chronicle natively" out of the generic package manager. |
| `PackageType` enum kept as a plain label | Admins need to declare what kind of package they're adding (system vs. foundry-module) so the right sub-plugin's hook fires. Having sub-plugins inspect the zip's contents to self-identify would be more brittle. |
| `PostInstallHook` extension point | Cross-plugin extension primitive: sub-plugins attach type-specific install-time behavior without packages having to know about them. Hooks fail loudly on errors (operator-actionable failures vs. silent stale state). |
| Multi-version preservation by default | `InstallVersion` writes to a per-version directory and never deletes old ones, so `foundry_vtt` can serve campaigns pinned to historical versions after a newer one is installed. `PruneStaleVersions` (`service.go` + `prune.go` + `handler.go`, with a dry-run/execute wizard) lets operators reclaim old on-disk version dirs, keeping the N newest. |

## Key Concepts

- **PackageType**: `system` (game content packs) or `foundry-module` (Foundry VTT sync module)
- **UpdatePolicy**: `off`, `nightly`, `weekly`, `on_release` — controls auto-update frequency
- **Version pinning**: Locks a package to a specific version, preventing auto-updates
- **GitHub integration**: Uses GitHub Releases API; supports GITHUB_TOKEN for higher rate limits

## Old-version clean-up

Default is manual: nothing is removed unless an admin clicks Clean up. The
site rule (`packages.retention_mode`, `packages.retention_keep_newest`,
`packages.retention_unused_days` in site settings) can be "keep the newest N"
(default 2) or "remove versions unused for N days" (default 30); N is 1..1000.
A package's own `retention_keep_newest` column overrides it. The auto-update
worker calls `RunRetention` after each update pass. Manual and automatic runs
share `prune`, which never removes the installed version, a pinned version, a
dir the systems loader is serving, or any foundry-module folder. Campaigns
store no system version (`campaign_addons` holds only the enabled system), so
"the version a campaign is on" is the installed one. "Unused" is measured from
the folder's modified time: install time, refreshed when the version stops
being the installed one.

## Database Tables

- `packages` — registered package repositories with installed state
- `package_versions` — discovered versions from GitHub releases

## Admin page

`/admin/packages` is one page with four tabs (`?tab=installed|updates|review|settings`,
unknown falls back to installed). The Installed tab is a filterable list
(`?f=`, `?q=`) with a side panel for the open package (`?pkg=`, `?ptab=`); all of
it is plain links, so it works without JavaScript. Writes keep their HTMX
endpoints and redirect back to the page the admin was on (`HX-Current-URL`,
whitelisted). `/admin/packages/pending` and `/admin/packages/settings` redirect
browser visits to the Review and Settings tabs; their HTMX responses are unchanged.

The auto-pin banner finds the Foundry module's Versions list through the hidden
`data-fvtt-versions-trigger` button in `packages.templ`; the per-version
campaign hooks live in `VersionList`. `TestVersionListKeepsForeignHooks` pins them.

## Admin Routes

All under `/admin/packages`, requiring site admin authentication:
- `GET /admin/packages` — package management page
- `POST /admin/packages` — add new package repo
- `DELETE /admin/packages/:id` — remove package
- `GET /admin/packages/:id/versions` — list versions (HTMX fragment)
- `PUT /admin/packages/:id/version` — install version
- `PUT /admin/packages/:id/pin` — pin version
- `DELETE /admin/packages/:id/pin` — unpin
- `PUT /admin/packages/:id/auto-update` — change policy
- `PUT /admin/packages/:id/retention` — set (`mode=own`, `keep_newest=N`) or clear (`mode=site`) the package's own old-version rule
- `POST /admin/packages/:id/check` — manual update check
- `GET /admin/packages/:id/usage` — campaign usage (HTMX fragment)

## Extension points

### `PostInstallHook`

Sub-plugins attach type-specific behavior to the install pipeline via
`packages.PostInstallHook`:

```go
type PostInstallHook interface {
    PackageType() PackageType
    AfterInstall(ctx context.Context, pkg *Package, version, destDir string) error
}
```

Registered at boot via `packages.RegisterPostInstallHook(svc, hook)`.
Hooks fire after the zip is extracted, validated, and the DB row
updated. The packages plugin dispatches by `PackageType` — a hook
registered for `PackageTypeFoundryModule` only fires for foundry-module
installs.

Errors fail the install loudly + cleanup `destDir` so a retry installs
cleanly. No silent warn-and-continue.

First consumer: `foundry_vtt` registers a hook that reads
`chronicle-package.json` and rewrites `module.json` version — the
mechanism behind Foundry showing the correct version immediately after
an install rather than the previous one.

### `InstallDirForVersion`

`PackageService.InstallDirForVersion(pkgType, slug, version) string`
returns the on-disk path for a specific historical version of a
package, regardless of which version is marked "installed" in the
DB. Used by sub-plugins to serve a campaign-pinned version that may
not be the package's currently-active install.

Path is computed deterministically; no filesystem check is
performed. Callers stat the returned path to confirm the version
is actually installed on disk.
