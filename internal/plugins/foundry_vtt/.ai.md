# foundry_vtt Sub-Plugin

The `foundry_vtt` plugin is the Foundry-VTT-specific extension to the generic
`packages` plugin: per-campaign signed manifest URLs, per-campaign pinning,
the `chronicle-package.json` descriptor reader, and the post-install
`module.json` version rewrite that keeps Foundry's reported version in sync
with what was actually installed. `packages` stays generic — zero
Foundry-specific code there; this plugin is the only place strings like
`"manifest"`, `"download"`, `"module.json"`, and `"chronicle-package.json"`
appear in the Chronicle backend. This sub-plugin owns ALL Foundry-specific
behavior so `packages` doesn't become a redundant mess for every future VTT
integration; the boundary is the `packages.PostInstallHook` extension point,
and future VTT extensions (Roll20, Owlbear) follow the same sibling-plugin
pattern.

## Modularity contract

**This plugin is INERT when no foundry-module typed package is registered in
the `packages` catalog.** Routes mount unconditionally at boot, but the owner
tab fragment renders an empty state, the public manifest endpoint returns a
categorized 503 (`code=no_package_registered`), and the `PostInstallHook` is
registered but never fires. Removing the Chronicle-Foundry-Module package
from `/admin/packages` turns this plugin off; nothing else to configure.

## Architectural decisions

### Descriptor-driven, not hardcoded

The post-install hook reads `chronicle-package.json` from the extracted
install dir — it declares the manifest path, which fields to rewrite, and the
endpoint URL templates — rather than hardcoding Foundry assumptions in
Chronicle. `defaultDescriptor()` applies when no descriptor is present, so a
module zip without one still works. A present-but-invalid descriptor fails
the install loudly rather than silently falling back, so upstream packaging
bugs surface immediately.

**loadDescriptor canonical-vs-fallback pin**: `defaultDescriptor()`
MUST match what the canonical
`chronicle-package.json` ships from `chronicle-foundry-module`, or an install
WITH a descriptor would behave differently from one WITHOUT, defeating the
descriptor's purpose. `descriptor_fallback_test.go` +
`testdata/chronicle-package.json` pin this as a committed snapshot
(per-field; `package.id` excluded since it's descriptor-required and
intentionally empty in defaults). Not a live fetch — regenerate by hand when
`chronicle-foundry-module`'s canonical descriptor changes;
`tools/check-package-descriptor.mjs` reminds maintainers there.

### Tokens live in their own table, not CampaignSettings JSON

`foundry_vtt_campaign_tokens` is a dedicated table with `(campaign_id,
token_version, rotated_at)`, separate from `CampaignSettings.FoundryModulePin`
(owned by the campaigns plugin). Token rotation is a `foundry_vtt`-owned
operation; a separate table avoids needing a campaigns-plugin write path.

### HTMX-swap-safe pattern requirements (standing rules)

Every interactive element in an HTMX-swappable fragment in this plugin
(`admin.templ`, `owner_tab.templ`, `autopin_banner.templ`) follows:

1. **Inline `onclick="(function(){...})()"` IIFEs**, built in Go as a string
   in `onclick_handlers.go`, wrapped in a `templ.ComponentScript` with an
   empty `Function` (no `<script>` tag) and the body in `Call` (templ writes
   `Call` directly into the `onclick="..."` attribute). Single-quoted JS
   strings throughout (double quotes would close the outer `onclick="..."`,
   since templ doesn't HTML-escape `Call`); interpolated values are
   JS-escaped via `text/template.JSEscapeString` so apostrophes/backslashes
   can't break out. **Never use templ `script` helpers or
   `document.addEventListener`/delegated listeners** in an HTMX-loaded
   fragment: a templ `script` helper emits
   `<script>function __templ_X(){...}</script>` alongside a button whose
   onclick references it by name, and browsers do not reliably execute an
   innerHTML-swapped `<script>` tag synchronously with the surrounding HTML —
   the button can be clicked before the function is defined
   (`Uncaught ReferenceError: __templ_X is not defined`). Pinned by
   `onclick_handlers_test.go`: every handler starts with `(function(`,
   contains no literal `"`, contains no `__templ_` substring.
2. **Inline literal Alpine `x-data="{ open: false }"`** — never
   `x-data="someExternalFunction()"`, which can be undefined when Alpine
   processes the directive right after an HTMX swap.
3. **`<details>` + `<summary>`** for collapsible sections when JS isn't
   needed — browser-native, zero race window. Combine with
   `hx-trigger="toggle once from:closest details"` for lazy-load on expand.
4. **Defense-in-depth `style="display:none"`** alongside `x-show=open` for
   modal-like reveals, to prevent a flash if `x-cloak` evaluation runs late.

### Contract tests

Failure classes pinned by tests:

- **A URL served without the on-disk artifact carrying it:** Foundry reads the
  extracted `module.json`, not just the manifest endpoint, so
  `zip_rewrite_test.go` checks the rewritten file.
- **A click handler in an HTMX-loaded fragment that is not an inline IIFE:**
  `onclick_handlers_test.go`.

### Per-campaign zip rewriting at download time

The download endpoint streams a zip with the embedded `module.json`
REWRITTEN to carry per-campaign Chronicle URLs, on every request — no
caching, since per-campaign URLs need per-campaign zips, and Foundry treats
the on-disk `module.json` (not the manifest endpoint) as its update-check
source of truth after extraction. Re-zipping per request is cheap: modules
are small (<5 MB) and installs are infrequent. The manifest and download
endpoints share `resolveCampaignManifest` as their single source of truth
for descriptor loading + URL rewriting, so both produce identical rewritten
bytes for the same `(campaign_id, token_version)` pair.

### Auto-pin-on-install (vs. silent forward-bump)

After every foundry-module install, every campaign with an empty pin
(auto-tracking) gets explicit-pinned to the PREVIOUS version instead of
silently following the newly-installed one. The admin sees the version
spread via the "Campaigns Using vX.Y.Z" UI and decides per-campaign whether
to bump; "Force-update All Older" mass-moves every older-pinned campaign to
the latest in one click.

### Update modes

The packages plugin's per-campaign update modes map onto the existing pin and
`foundry_module_pin_mode` (`UpdateModeFromLegacy`, `campaign_binding.go`): a pin
or stored `preserve` is `pinned`; empty or `promote` is `automatic`; the new
stored value `approve_first` ("Ask me first") keeps the pin and has a newly
installed version held until approved. Serving still reads only the pin. The
update-mode hook is registered after `AutoPinHook`, which still freezes
`preserve` campaigns.

The Foundry module asks by default (`AsksByDefault`): new installs never move
a campaign. Automatic campaigns become `approve_first` frozen at their current
version; pinned ones stay pinned but still see the waiting version. The owner
acts through `owner_updates.go` (`OwnerUpdates`): Update, Later, and "Use
another version". The old owner pin selector and `PUT /foundry-vtt/pin` are
gone, so an admin hold cannot be bypassed.

A one-time bootstrap migration pins every pre-existing auto-tracking campaign
to the currently-installed version at first boot after this shipped.
Idempotency: the pinned-to version is stored under
`foundry_vtt.autopin_migration_completed_for_version` in `site_settings`;
later boots read that key and skip (clearing it re-triggers the migration).
No-op, and doesn't set the flag, when no foundry-module package is
registered yet or it has no installed version.

## Database tables

### `foundry_vtt_campaign_tokens`

```
campaign_id   CHAR(36)  NOT NULL  PRIMARY KEY
token_version INT       NOT NULL  DEFAULT 1
rotated_at    TIMESTAMP NOT NULL  DEFAULT CURRENT_TIMESTAMP
FOREIGN KEY (campaign_id) REFERENCES campaigns(id) ON DELETE CASCADE
```

`token_version` is the rotation counter. Sign payload =
`HMAC(secret, "foundry-vtt:{campaign_id}:{token_version}")`. Rotate =
increment counter; every previously-signed URL becomes invalid on the next
manifest request.

Renamed from `foundry_module_campaign_tokens` by migration 001, which also
drops the orphaned `foundry_module_versions` table. See "Fresh-database
bootstrap" below for why migration 001 alone can't bring up a fresh database,
and what migration 002 + the reconciler do about it.

## Extension point: PostInstallHook

`foundry_vtt.NewPostInstallHook()` returns a struct satisfying
`packages.PostInstallHook`, registered at boot via
`packages.RegisterPostInstallHook(pkgService, hook)`. Fires after every
`PackageTypeFoundryModule` install:

1. Loads `chronicle-package.json` from the install dir (or applies defaults).
2. Reads `module.json` at the descriptor-declared `moduleJsonPath`.
3. Overwrites the `version` field with the installed version string.
4. Writes the file back.

Errors fail the install loudly. `packages`' `InstallVersion` cleans up
`destDir` on hook failure, so a retry installs from scratch.

## Extension point: chronicle-package.json descriptor

The schema is owned on the Foundry side
(the Chronicle-Foundry-Module repo); this section describes Chronicle's
adoption of it.

### Schema v1 (canonical)

```jsonc
{
  "schemaVersion": 1,
  "package": {
    "id": "chronicle-sync",
    "kind": "foundry-module",
    "moduleJsonPath": "module.json"
  },
  "serving": {
    "rewriteFields": ["manifest", "download"],
    "manifestEndpoint": "/api/v1/campaigns/{campaign_id}/foundry-vtt/module.json?token={token}",
    "downloadEndpoint": "/api/v1/campaigns/{campaign_id}/foundry-vtt/module.zip?token={token}",
    "perCampaignSignedToken": true,
    "zipContentRoot": ""
  }
}
```

### Fallback semantics

When no `chronicle-package.json` exists in the install dir,
`defaultDescriptor()` applies. Its defaults match the canonical schema
above, so a module zip without a descriptor still works (fallback), while a
zip that ships one drives behavior from it.

### Schema versioning

`schemaVersion` is the load-bearing field. The hook recognizes only
`currentSchemaVersion` (1 today); unknown major versions fail the install
loudly. Future v2+ requires coordinated Foundry + Chronicle releases. Within
v1, missing optional fields fall back to defaults via `applyDefaults()` — a
module can ship just `schemaVersion` + `package.id` and inherit the rest.

## Error handling contract

Every public-facing error follows this format:

```
<what failed>: <technical detail>. <likely cause>. <actionable next step>.
```

See `errors.go` for all pre-defined constructors. Examples:

<!-- foundry-vtt-error-catalog-start -->
| Constructor | Category | HTTP Status | Format-compliant Message |
|---|---|---|---|
| `ErrInvalidToken` | auth | 403 | Wrong HMAC or rotated → operator rotates URL via campaign settings. |
| `ErrNoPackageRegistered` | config | 503 | No foundry-module package → admin adds it via `/admin/packages`. |
| `ErrPinnedVersionNotInstalled` | config | 503 | Pin to missing version → admin installs OR owner changes pin. |
| `ErrNoVersionAvailable` | config | 503 | Package exists, no version installed → admin clicks Install. |
| `ErrTokenNotInitialized` | config | 503 | First-time campaign hit before owner visited settings → owner opens VTT Setup Guides. |
| `ErrDescriptorInvalid` | validation | 422 | Bad descriptor in zip → fix upstream OR remove descriptor for defaults. |
| `ErrModuleJSONMissing` | internal | 500 | Zip malformed → admin retries OR upstream fix. |
| `ErrCampaignNotFound` | not_found | 404 | URL refers to deleted/wrong-instance campaign → owner mints a fresh URL. |
| `ErrInternal` | internal | 500 | Server-side fault; code is dynamic. Wildcard constructor; logged with the wrapped cause. |
<!-- foundry-vtt-error-catalog-end -->

JSON shape returned to public endpoints (Foundry's `update-info.mjs` consumes
this):

```json
{
  "error": "<code>",
  "message": "<format-compliant message>",
  "category": "<config|auth|not_found|validation|internal>"
}
```

### Adding a new error code

Three sources are checked against each other by `errors_test.go` and must
stay in sync — `errors.go` (typed constructors, source of truth for Code +
Category), this `.ai.md` catalog table, and `error-catalog.json`
(machine-readable, consumed by Foundry-side docs; the shared parser is
`errors_catalog.go`, used by both `errors_test.go` and
`cmd/foundry-error-catalog/main.go`). The canonical catalog also publishes at
`/internal/plugins/foundry_vtt/error-catalog.json`; Foundry's repo
references it in its own `.ai.md` and `API-CONTRACT.md`.

1. Add the constructor to `errors.go` in the four-clause Message format
   (`Category`, `Code` snake_case, `Message` = what/detail/cause/action).
2. Add a row to the catalog table above, inside the
   `<!-- foundry-vtt-error-catalog-start/end -->` markers (HTTP status is
   derived from category; the test enforces the mapping).
3. Run `make foundry-error-catalog` and commit the regenerated
   `error-catalog.json`.
4. Run `go test ./internal/plugins/foundry_vtt/...` — `TestErrorCatalog_*`
   passes when all three files agree, and fails with a precise diff until
   then.

Foundry's `update-info.mjs` reads `category` and `message` from Chronicle's
response directly, so adding new codes needs zero Foundry deploy. `TestErrorCatalog_*` guards against
the wrong-contract and silent-regression class of bug.

## Fresh-database bootstrap — read before touching migrations

**This plugin's migration `001` cannot run on a fresh database and never
will.** It's a consolidation migration (`RENAME TABLE
foundry_module_campaign_tokens TO foundry_vtt_campaign_tokens`) whose source
table is created by a plugin that no longer exists. On a genuinely fresh
install there is no source table to rename, so `001` fails — and the plugin
migration runner returns on the first failed migration, so every migration
after `001` (including any future one) would be unreachable too.

The repair has two halves, and **neither edits `001`** (migrations are
append-only, `tools/check-migration-immutability.sh`):

- **`reconcile_consolidation.go` → `ReconcileConsolidationState`** records
  `001` as applied on any database where its RENAME has **no source table**.
  It runs next to `PreMigrationCheck` in `cmd/server/main.go`, before the
  plugin schema pass.
- **Migration `002_ensure_campaign_tokens`** states the post-consolidation
  shape in idempotent DDL (`CREATE TABLE IF NOT EXISTS` /
  `ADD COLUMN IF NOT EXISTS`).

**A database that still HAS `foundry_module_campaign_tokens` is untouched** —
the reconciler doesn't fire, `001` runs for real, and its live token rows
carry across. Fresh install, completed upgrade, and an upgrade that died
between `001`'s two statements all converge on the same schema.

`make test-freshdb` / `cmd/server/freshdb_migration_test.go` replay the real
bootstrap against genuinely empty MariaDB schemas — one from zero, one from
the pre-consolidation shape — in CI, and fail if either test merely skips
rather than running (a silent skip is how this defect went unnoticed for a
long time). Pin: `reconcile_consolidation_test.go`.

The general rule this established — an immutable plugin migration is
repaired by a reconciler plus an append-only idempotent successor, never by
an edit — is **ADR-050**. The runner-side half (pre-flight applicability +
partial-progress resume) is in `internal/database/plugin_migration_safety.go`;
see `internal/database/.ai.md`.
