# foundry_vtt Sub-Plugin

The Foundry-specific extension to the generic `packages` plugin: per-campaign
signed manifest URLs, per-campaign pinning, the `chronicle-package.json`
descriptor reader, and the post-install `module.json` version rewrite. `packages`
has zero Foundry-specific code; this plugin is the only place strings like
`"manifest"`, `"download"`, `"module.json"` and `"chronicle-package.json"` appear
in the backend. The boundary is the `packages.PostInstallHook` extension point;
future VTT integrations follow the same sibling-plugin pattern.

**Inert without a foundry-module package.** Routes mount at boot, but with no
foundry-module typed package in the `packages` catalog the owner tab renders an
empty state, the public manifest endpoint returns a 503
(`code=no_package_registered`) and the hook never fires. Removing the package
from `/admin/packages` turns the plugin off.

## Design rules

### Descriptor-driven
The post-install hook reads `chronicle-package.json` from the extracted install
dir (manifest path, fields to rewrite, endpoint URL templates) instead of
hardcoding Foundry assumptions. `defaultDescriptor()` applies when none is
present. A present-but-invalid descriptor fails the install loudly.
`defaultDescriptor()` must match what `chronicle-foundry-module` ships, or an
install with a descriptor would behave differently from one without.
`descriptor_fallback_test.go` pins it field-by-field (`package.id` excluded)
against the committed `testdata/chronicle-package.json`; regenerate that
snapshot by hand when the canonical descriptor changes.

### Tokens
`foundry_vtt_campaign_tokens` (`campaign_id` PK, `token_version`, `rotated_at`;
FK to `campaigns` with cascade) is separate from
`CampaignSettings.FoundryModulePin` (campaigns plugin), so rotation needs no
campaigns write path. Sign payload =
`HMAC(secret, "foundry-vtt:{campaign_id}:{token_version}")`; rotating bumps the
counter and invalidates every previously signed URL on the next manifest
request. The domain prefix isolates this signer from `media.URLSigner`, which
shares the secret.

### HTMX-swap-safe fragments
Every interactive element in a swappable fragment (`admin.templ`,
`owner_tab.templ`, `autopin_banner.templ`, update dialogs):

1. Uses an inline `onclick="(function(){...})()"` IIFE built in Go
   (`onclick_handlers.go`, `update_onclick.go`) as a `templ.ComponentScript`
   with an empty `Function` and the body in `Call`. Single-quoted JS only
   (templ does not HTML-escape `Call`); interpolated values go through
   `text/template.JSEscapeString`. Never use templ `script` helpers or
   delegated listeners: an innerHTML-swapped `<script>` may run after the
   button is clickable (`__templ_X is not defined`).
   `onclick_handlers_test.go` pins: starts with `(function(`, no literal `"`, no
   `__templ_`.
2. Uses a literal `x-data="{ open: false }"`, never `x-data="someFn()"` (can be
   undefined right after a swap).
3. Prefers `<details>`/`<summary>` for collapsibles; lazy-load with
   `hx-trigger="toggle once from:closest details"`.
4. Adds `style="display:none"` beside `x-show=open` on modal-like reveals.

`zip_rewrite_test.go` pins that the rewritten `module.json` on disk carries the
per-campaign URLs (Foundry reads it, not the manifest endpoint).
`cfmc9_test.go` pins typed-error wrapping in `ForcePinCampaign`, the
`showAffectedCampaignsOnClick` DOM id, and that `sanitizeVersionForDOMID` stays
in step with `packages.sanitizeForID`.

### Per-campaign zip rewriting
The download endpoint streams a zip with the embedded `module.json` rewritten to
per-campaign Chronicle URLs on every request, uncached. The manifest and
download endpoints share `resolveCampaignManifest`, so the same
`(campaign_id, token_version)` yields identical rewritten bytes.

### Update modes and auto-pin
- Every foundry-module install runs two hooks: the version rewrite, then
  `AutoPinHook`, which pins every campaign with an empty pin (auto-tracking) to
  the previous version rather than silently moving it. Admins see the spread in
  "Campaigns Using vX.Y.Z" and "Force-update All Older" mass-moves older pins to
  the latest.
- The packages plugin's per-campaign update modes map onto the pin and
  `foundry_module_pin_mode` (`UpdateModeFromLegacy`, `campaign_binding.go`): a
  pin or stored `preserve` is `pinned`; empty or `promote` is `automatic`; stored
  `approve_first` ("Ask me first") keeps the pin and holds a newly installed
  version until approved; stored `automatic` ("Update automatically") is set by
  the owner or an admin. Only `approve_first` and `automatic` are explicit
  choices. Serving reads only the pin. The update-mode hook is registered after
  `AutoPinHook`, which still freezes `preserve` campaigns.
- The module asks by default (`AsksByDefault`): installs never move a campaign.
  Automatic campaigns with no stored choice (empty or `promote`) become
  `approve_first` frozen at their current version, at install and every boot; a
  stored `automatic` is left alone; pinned campaigns stay pinned but see the
  waiting version. The owner acts through `OwnerUpdates` (`owner_updates.go`):
  Update, Later, "Use another version". The owner pin selector and
  `PUT /foundry-vtt/pin` do not exist, so an admin hold cannot be bypassed.
- `AutoPinMigrate` runs once at boot: it pins every auto-tracking campaign to
  the installed version and records it under
  `foundry_vtt.autopin_migration_completed_for_version` in `site_settings`
  (clear the key to re-run). It is a no-op, and does not set the key, when no
  foundry-module package is registered or none is installed.

## PostInstallHook

`foundry_vtt.NewPostInstallHook()` satisfies `packages.PostInstallHook`,
registered at boot with `packages.RegisterPostInstallHook(pkgService, hook)`. After
every `PackageTypeFoundryModule` install it loads the descriptor (or defaults),
reads `module.json` at the declared `moduleJsonPath`, overwrites `version` with
the installed version and writes it back. Errors fail the install; `packages`'
`InstallVersion` cleans up `destDir`, so a retry starts from scratch.

## chronicle-package.json descriptor

Schema owned by the Chronicle-Foundry-Module repo; Chronicle adopts it:

```jsonc
{
  "schemaVersion": 1,
  "package": { "id": "chronicle-sync", "kind": "foundry-module", "moduleJsonPath": "module.json" },
  "serving": {
    "rewriteFields": ["manifest", "download"],
    "manifestEndpoint": "/api/v1/campaigns/{campaign_id}/foundry-vtt/module.json?token={token}",
    "downloadEndpoint": "/api/v1/campaigns/{campaign_id}/foundry-vtt/module.zip?token={token}",
    "perCampaignSignedToken": true,
    "zipContentRoot": ""
  }
}
```

`schemaVersion` is the load-bearing field: only `currentSchemaVersion` (1) is
recognized and an unknown major version fails the install; v2+ needs
coordinated Foundry and Chronicle releases. Within v1 missing optional fields
come from `applyDefaults()`, so a module may ship just `schemaVersion` +
`package.id`.

## Errors

Every public-facing error reads
`<what failed>: <technical detail>. <likely cause>. <actionable next step>.`
(constructors in `errors.go`). HTTP status derives from category.

<!-- foundry-vtt-error-catalog-start -->
| Constructor | Category | HTTP Status | Format-compliant Message |
|---|---|---|---|
| `ErrInvalidToken` | auth | 403 | Wrong HMAC or rotated → operator rotates URL via campaign settings. |
| `ErrNoPackageRegistered` | config | 503 | No foundry-module package → admin adds it via `/admin/packages`. |
| `ErrPinnedVersionNotInstalled` | config | 503 | Pin to missing version → admin installs OR owner changes pin. |
| `ErrNoVersionAvailable` | config | 503 | Package exists, no version installed → admin clicks Install. |
| `ErrTokenNotInitialized` | config | 503 | First-time campaign hit before owner visited settings → owner opens VTT Setup Guides. |
| `ErrDescriptorInvalid` | validation | 422 | Bad descriptor in zip → fix upstream OR remove descriptor for defaults. |
| `ErrModuleJSONMissing` | internal | 500 | Zip malformed → admin retries OR upstream fix. |
| `ErrCampaignNotFound` | not_found | 404 | URL refers to deleted/wrong-instance campaign → owner mints a fresh URL. |
| `ErrInternal` | internal | 500 | Server-side fault; code is dynamic. Wildcard constructor; logged with the wrapped cause. |
<!-- foundry-vtt-error-catalog-end -->

Public endpoints return `{"error": "<code>", "message": "...", "category": "<config|auth|not_found|validation|internal>"}`;
Foundry's `update-info.mjs` reads `category` and `message` directly, so a new
code needs no Foundry deploy.

### Adding an error code
`errors.go` (source of truth for Code + Category), the catalog table above and
`error-catalog.json` must agree (`TestErrorCatalog_*` in `errors_test.go`; the
parser is `errors_catalog.go`, shared with `cmd/foundry-error-catalog`). The
catalog also ships at `internal/plugins/foundry_vtt/error-catalog.json`, which
the Foundry repo references.

1. Add the constructor to `errors.go` (`Category`, snake_case `Code`, four-clause `Message`).
2. Add a row inside the `foundry-vtt-error-catalog` markers.
3. Run `make foundry-error-catalog` and commit the regenerated JSON.
4. Run `go test ./internal/plugins/foundry_vtt/...`.

## Fresh-database bootstrap (read before touching migrations)

Migration `001` (`RENAME TABLE foundry_module_campaign_tokens TO
foundry_vtt_campaign_tokens`, drops the orphaned `foundry_module_versions`)
cannot run on a fresh database: the source table came from a plugin that no
longer exists. The runner stops at the first failed migration, so everything
after `001` would be unreachable. Neither half of the repair edits `001`
(`tools/check-migration-immutability.sh`):

- `ReconcileConsolidationState` (`reconcile_consolidation.go`) records `001` as
  applied wherever its RENAME has no source table. It runs next to
  `PreMigrationCheck` in `cmd/server/main.go`, before the plugin schema pass.
  `PreMigrationCheck` refuses to start if `foundry_module_versions` has rows
  (`001` would destroy them).
- Migration `002_ensure_campaign_tokens` states the post-consolidation shape in
  idempotent DDL.

A database that still has `foundry_module_campaign_tokens` is untouched: `001`
runs for real and keeps its token rows. Fresh install, completed upgrade and an
upgrade that died between `001`'s two statements converge on one schema.
`make test-freshdb` / `cmd/server/freshdb_migration_test.go` replay the bootstrap
on empty MariaDB schemas and fail rather than skip; pin:
`reconcile_consolidation_test.go`. The general rule (an immutable plugin
migration is repaired by a reconciler plus an append-only idempotent successor)
is ADR-050; the runner side is in `internal/database/plugin_migration_safety.go`
(see `internal/database/.ai.md`).
