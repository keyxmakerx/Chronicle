# Sessions Plugin

Game session scheduling and RSVP tracking for campaigns: real-world play
sessions (game nights) with attendee management, entity linking, soft
delete/restore, and a personal calendar feed. The plugin also owns the
availability scheduler (a recurring weekly grid + heatmap for finding a
slot) and DM slot proposals with per-option RSVP.

## Architecture

- **model.go**: Session, Attendee, SessionEntity structs + DTOs. Status:
  `planned`/`completed`/`cancelled`. Recurrence: `weekly`/`biweekly`/
  `monthly`/`custom` (every N weeks via `recurrence_interval`). `Notes`
  (ProseMirror JSON) is GM-only; `Recap` (post-session write-up, also
  ProseMirror JSON) is visible to every member.
- **repository.go**: SQL CRUD for sessions + attendees + entity linking;
  `ListByCampaign` sorts planned first, then by `scheduled_date`. Every
  read filters `deleted_at IS NULL` except `FindByIDIncludingDeleted` (the
  restore flow's own read).
- **service.go**: validation, CRUD orchestration, `InviteAll` for batch
  invites, RSVP updates, entity linking with role validation.
- **game_night_service.go, game_night_repository.go**: soft delete/restore,
  per-occurrence RSVPs, the tally-exclusion switch, "suggest another time",
  and the private calendar feed (see Game Nights below).
- **handler.go**: HTTP handlers for list/detail/CRUD/recap/RSVP/entity
  link-unlink; HTMX-aware responses.
- **routes.go**: route registration with role middleware.
- **nights.go, nights_handler.go**: game nights for the calendar's day card
  (see Game Nights below). `NextGameNight` returns the soonest planned night
  that has not started, with no roster, for the header's countdown widget; a
  night with no time lasts until the end of its day, in its own zone.
- **sessions.templ**: list (grouped by status), detail (attendees + RSVP),
  create modal, edit modal (`editSessionModal` — PARTIAL PUT to
  `UpdateSessionAPI`; status `<select>` uses `data-initial` + JS since
  templ has no `selected?=`).
- **availability_model.go, availability_repository.go,
  availability_service.go, availability_overlay.go, availability_handler.go,
  availability.templ, static/js/availability.js**: the scheduler (below).
- **proposals_model.go, proposals_repository.go, proposals_service.go,
  proposals_handler.go, proposals.templ**: slot proposals (below).
- **notifications_repository.go, notifications_service.go,
  notifications_handler.go, static/js/widgets/notification_bell.js**: the
  in-app notification store and topbar bell.
- **callout.go, callout_handler.go, static/js/widgets/callout.js**: the
  call-to-action banner (below).

## Data Model

- `sessions` — id, campaign_id, name, summary, notes, notes_html, recap,
  recap_html, scheduled_date (DATE, zone-less), scheduled_time (VARCHAR(5)
  `HH:MM`, nullable, null = no time; set by a confirmed proposal or the
  create/edit modal), scheduled_tz (the organizer's IANA zone
  `scheduled_time` was set in; nullable — only `ConfirmProposalWinner` ever
  sets it, so a manually created or edited session has none), calendar_year/
  month/day plus `calendar_id` (the calendar those positions belong to; the
  service stamps the campaign's default calendar whenever a complete date is
  saved and clears it with the date; `ReconcileWorldDateCalendars` backfills
  older rows at boot; `ListPlannedSessionsInWorldDateRange` filters on it),
  status, sort_order, deleted_at (soft delete; every read filters
  it except the restore flow), created_by, created_at, updated_at
- `session_attendees` — id, session_id, user_id, status (invited/accepted/
  declined/tentative/carried_yes — see Slot Proposals for carried_yes),
  responded_at, note (a short player-set note on their own RSVP; nullable,
  an explicit empty string also clears it), excluded_from_count (a
  Director's own "leave myself out of the N/M tally" switch, settable only
  on their own row), needs_recheck (set when the session moved or was
  cancelled after this member had already answered — the answer itself is
  never cleared, only flagged "look again")
- `session_entities` — id, session_id, entity_id, role (mentioned/
  encountered/key)
- `session_rsvp_tokens` — id, token, session_id, user_id, action
  (`accepted`/`declined`/`suggest`), used_at, expires_at, created_at.
  Single-use, 7-day-expiring email RSVP tokens; `action = 'suggest'` is the
  "suggest another time" link (see Game Nights).
- `member_availability` — id, campaign_id, user_id, day_of_week (0=Sun..6=Sat),
  start_minute, end_minute, state (available/preferred), tz (IANA),
  week_parity, updated_at. Recurring, ZONE-LOCAL never UTC; absent row =
  unavailable. `week_parity`: 0 = every week (default, so pre-cadence rows
  keep their meaning), 1/2 = the two alternating tracks; it's in the
  unique key, so alternating-week availability never collides.
- `member_availability_status` — campaign_id, user_id, answered_at, tz. PK
  (campaign, user). Records that a member ANSWERED, not what — undecidable
  from the block tables alone (absent blocks mean "unavailable" either
  way; an EMPTY saved grid still writes a row here). Stamped atomically
  with the block replace; exposed as `OverlayMember`/
  `RosterEntry.HasAnswered`, party-visible though the lanes aren't.
- `availability_exceptions` — id, campaign_id, user_id, on_date, start_minute,
  end_minute, state, tz, updated_at. Per-date override, replacing that
  date's whole recurring pattern.
- `slot_proposals` — id, campaign_id, created_by, title, note, status
  (open/closed), created_at, updated_at (see Slot Proposals below).
- `slot_proposal_options` — id, proposal_id, starts_at_utc, ends_at_utc (UTC
  instants, unlike the wall-clock recurring table above), ordinal (1..5,
  display order), is_winner.
- `slot_proposal_responses` — id, option_id, user_id, response
  (yes/no/maybe), updated_at. Own table, never `session_attendees`; one row
  per (option, user), re-responding upserts.
- `slot_proposal_tokens` — mirrors `session_rsvp_tokens`: token, option_id,
  user_id, response, used_at, expires_at.
- `notifications` — id, user_id, campaign_id (nullable), type, payload
  (JSON), link, read_at (null = unread), created_at. Generic and
  campaign-optional; every writer (proposals, calendar-RSVP invites,
  availability nudge, game-night lifecycle events) is inside this plugin.
- `session_occurrence_rsvps` — id, session_id, user_id, occurrence_date,
  status, note, excluded_from_count, needs_recheck, responded_at. UNIQUE
  (session_id, user_id, occurrence_date). A RECURRING session's answers
  live here, one row per specific night, instead of one shared row in
  `session_attendees`; `UpdateRSVPDetailed` decides per call which table an
  answer belongs in. A non-recurring session is unaffected.
- `session_reschedule_suggestions` — id, session_id, user_id, occurrence_date
  (nullable — set only against one night of a series), suggested_date,
  suggested_time, note, created_at. The record behind the emailed "suggest
  another time" link (`ValidateAndRecordSuggestion`); the token that
  authorizes writing one is a `session_rsvp_tokens` row with
  `action = 'suggest'`.
- `session_calendar_feed_tokens` — id, campaign_id, user_id, token,
  created_at. UNIQUE (token) and UNIQUE (campaign_id, user_id): one
  private, replaceable feed credential per member. Replacing a token
  deletes-and-recreates it, so a leaked link stops resolving at once.
- `session_calendar_feed_settings` — campaign_id (PK), enabled. Absence of a
  row means enabled, the same "absence is a first-class state" convention
  `member_availability_status` uses — the feed is on by default for every
  campaign, and a row only exists once an owner has explicitly turned it
  off.

Availability, proposal-response and notification data live in their own
tables, never `session_attendees`, so they stay out of campaign/AI export
egress by construction (`availability_egress_test.go`). Migration
`006_calv5_clear_availability` truncated `member_availability`,
`member_availability_status` and `availability_exceptions` once for the
calendar V5 clean slate (rationale in the file); sessions itself was
untouched, and the tables refill as members repaint availability.

## Cross-Plugin Dependencies

- **campaigns**: `MemberLister.ListMembers()` auto-invites all campaign

### `PUT /campaigns/:id/sessions/:sid` (and `/recap`) are PARTIAL updates

| body | stored value |
|---|---|
| key **absent** | preserved |
| key present, **value** | replaced |
| key present, **explicit `null`** | cleared (nullable columns only) |

Every field of `updateSessionRequest`/`UpdateSessionInput` is a
`patch.Field[T]` (`internal/patch`), recording presence in
`UnmarshalJSON` (a plain pointer can't tell "absent" from "null"); the
service does `load-merge-write` in `UpdateSession` (comment has the "Mark
Complete" rationale). `internal/patch/partial_update_contract_test.go`
tracks every presence-aware input repo-wide. Non-nullable columns (`name`,
`status`, `is_recurring`, `recurrence_interval`) have no "cleared" state —
an explicit `null` preserves rather than zeroing (`patch.Field.Val`);
`name` is required only when sent. Pinned by `partial_update_test.go`.

## RSVP Flow

Session creation auto-invites every campaign member (status `invited`);
players answer with on-page RSVP buttons (HTMX POST, refreshed attendee
fragment) or a one-click emailed link (`/rsvp/:token`). Detail page shows a
count summary (e.g. "3/5 going"). The invite email goes to every member
with an email address when a session is created (including one confirmed
from a slot proposal, and a repeating night's next one, made when the last
is marked complete), but only when the mail server is saved and turned on
in Admin > Email (`/admin/smtp`); otherwise no mail is sent and members
answer in Chronicle.

- A member with no attendee row shows "you have not answered" — never
  "invited" — and still gets RSVP controls; `rsvpControls` renders for
  every member, not just those with a row.
- `UpdateAttendeeStatus` is its own upsert (separate `INSERT ... ON
  DUPLICATE KEY UPDATE` from `AddAttendee`'s): re-submitting is never "not
  found", and a member who joins after the session still gets a
  first-class row. Callers must check membership first.
- RSVPing also accepts an optional note and, for a repeating session, an
  occurrence date (`RSVPSession`/`UpdateRSVPDetailed`) — see Game Nights
  below for per-occurrence RSVPs, the tally-exclusion switch, and "suggest
  another time". A bare `{status}` POST behaves exactly as above.

## Key Design Decisions

- **Separate from calendar events**: sessions track real-world scheduling;
  calendar events stay in-world.
- **IDOR protection**: `requireSessionInCampaign()` verifies the session
  belongs to the URL's campaign before any operation. `RestoreSessionAPI`
  re-implements the same check by hand instead, since the soft-deleted
  session it targets would always 404 through the normal deleted_at-filtered
  read.
- **Upsert on invite**: `AddAttendee` (auto-invite on create) has its own
  `ON DUPLICATE KEY UPDATE`, so re-inviting is idempotent — independent of
  `UpdateAttendeeStatus`'s upsert above.
- **One notification fan-in**: `NotifyUsers` (`notifications_service.go`)
  is the generic way to notify members — a new feature adds its own type
  constant (e.g. `NotifAvailabilityNudge`, `NotifSessionRestored`) rather
  than a bespoke `NotifyX` method. `NotifyUsersWithDetail` adds an optional
  second line (payload `detail`, list JSON `detail`) that the bell shows
  before the time, e.g. the armory's `item_given` "On Bren"; the bell gives
  `item_given` a gift icon.
- **Co-Directors run game nights**: a co-Director (the `IsDmGranted`
  capability, not necessarily Scribe role) gets the same move/cancel/
  restore/propose/confirm controls as the Owner — see Routes above. It is a
  capability laid over a role, never a promotion to the Owner's own
  account/campaign settings.

## Availability Scheduler

Members paint a recurring weekly grid; the DM sees it stacked as a
translucent heatmap, composed with per-user IANA timezones and
alternating-week (fortnightly) patterns.

- **Encoding**: heatmap density, count gutter, full-house star, per-member
  lanes (DM only), WCAG-AA — see the widget's header comment (signed
  mockup).
- **Alternating weeks**: `week_parity` on `member_availability` (0 = every
  week, 1/2 = the two tracks), computed by `availability_cadence.go` from a
  fixed global epoch (1970-01-04) so members can't disagree which track a
  week is (edge cases in that file). `cadenceApplies` treats
  0/unrecognised as every week: fails toward over-showing, never silently
  hiding availability. The paint grid submits all three layers every save
  — a replace-all that omitted one would delete it.
- **Has-not-answered is a first-class state**, distinct from "answered:
  never free" (see `member_availability_status` in Data Model above).
- **Nudge** (`POST /availability/nudge`, Owner or DM access only): messages every
  member who hasn't answered, returning names not just a count. No
  scheduled-job runner; it fires only on an explicit click.
- **Security**: member-only (authed, never public); detail gated by role
  not route (Role and Zone Display Rules); own tables keep it out of
  export egress (Data Model above).

### Footguns

- **Never compute "end of the local day" as `time.Date(y,m,d,0,0,0,0,loc).AddDate(0,0,1)`.**
  A DST jump landing on local midnight (e.g. America/Havana) can make that
  boundary non-increasing and hang a day-splitting loop; use
  `timeutil.StartOfCivilDay` instead (mechanism in its doc comment).
  `splitToViewerDays` also carries a hard segment cap and a did-not-advance
  break as backstop, since a non-terminating loop can OOM the instance.
  Guards: `internal/timeutil/start_of_civil_day_test.go`,
  `availability_overlay_dst_test.go`.
- **A member's zone lives in two places**: `member_availability.tz`
  (`PUT /availability/mine`) and `users.timezone`
  (`PUT /account/timezone`). `memberZone`/`resolveViewerTZ` prefer the
  availability-page zone (`CampaignMemberZones`, read for the whole
  roster), so reading `users.timezone` alone under-reports players who
  only set it there (empty-zone display: see Role and Zone Display Rules).
- **Compose, don't overwrite, when writing availability for a day.**
  `AddMyAvailableWindows` and `AddMyException`/`ReplaceMyDayExceptions`
  build on the day's EXISTING rows (`composeDayWithState`): an exceptions
  row replaces the WHOLE recurring pattern for its date, so a blind
  insert would erase the rest of the day. Composed in the source rows'
  own zone, not the caller's, so a block is never silently relabeled
  hours off from what was painted.

## Slot Proposals

A DM proposes up to 5 candidate slots; members respond yes/no/maybe per
option, by page or by a one-click emailed token (mirrors the session RSVP
token). An option is a concrete UTC instant, rendered to each viewer's zone
at read time — unlike the wall-clock recurring availability table.
Confirming (`ConfirmProposalAPI`, Scribe+ or co-Director) picks the winner,
closes the proposal and creates a planned session from that slot; the only
DDL confirm touches is `sessions`.

The confirmer is set `accepted` immediately; anyone else who voted `yes` on
the WINNING option is carried in as `carried_yes` rather than plain
`invited` — a yes vote on a proposed time is not itself a Going, so they
still owe an explicit confirm through the normal RSVP flow, which simply
overwrites the carried status. Both are set by the HANDLER, after
`InviteAll`: `ConfirmProposalWinner` itself only reports who voted yes on
the winning option, since writing statuses inside it would just be
overwritten by the handler's own subsequent `InviteAll` call.

## Game Nights

Real-world scheduling layered onto the RSVP flow above.

- **In the calendar**: `ListGameNights` turns planned sessions into one
  `GameNight` per night inside a date window (a series is stepped with
  `computeNextOccurrence` up to its end date) and gives each a roster of
  every current campaign member, so silence shows as "no answer yet". A
  departed member's row is dropped. Answers map accepted/tentative/declined
  to yes/maybe/no; `invited` and `carried_yes` read as no answer. The
  endpoint is members-only because the roster carries notes. A calendar
  with real dates renders it in the day's card (calendar plugin `.ai.md`).
- **Links into the calendar**: the sidebar's "Game nights" app (slug still
  `sessions`) and the dashboard's game-nights block point at `/game-nights`, which
  redirects a member to the campaign's real-world calendar (the default one
  first, found through `RealWorldCalendarFinder`, wired in `internal/app`)
  on that session's next night, or on the next night of all. A public
  viewer, or a campaign with no real-world calendar, lands on the Sessions
  page or the session's own page instead.
- **Planned from the calendar**: the calendar's "Plan it" opens the Sessions
  page with `?plan_date=&plan_time=&plan_tz=` (Scribe+ only), which opens
  the New Session form filled in (`SessionPlan`); the zone rides along as
  `scheduled_tz`, so the night keeps the zone it was planned in.

- **Per-occurrence RSVPs**: a repeating session's answers are keyed per
  night, not shared across the whole series (`session_occurrence_rsvps` in
  Data Model above); `UpdateRSVPDetailed` decides per call which table an
  answer belongs in.
- **Tally exclusion**: `excluded_from_count` lets a session's organizer (or
  the campaign Owner) leave themselves out of the "N/M going" count on
  their own row only, while their individual answer stays visible to them
  and to the Director.
- **"Suggest another time"**: invite emails mint and link a third one-click
  token alongside accept/decline (`session_rsvp_tokens.action = 'suggest'`,
  minted by `CreateRSVPTokens` and linked by `sendRSVPEmails`), opening a
  small date/time/note form at `/rsvp/:token/suggest`. The submission is
  validated BEFORE the token is consumed (`ValidateAndRecordSuggestion`),
  so a rejected submission never burns the single-use link. It writes a
  `session_reschedule_suggestions` row and notifies the session's
  organizer; it never changes the suggester's own RSVP status.
- **Soft delete, restore, and move all notify whoever had already RSVPed.**
  `DeleteSession` sets `sessions.deleted_at` instead of a hard
  `DELETE ... CASCADE`, so a co-Director/Owner can restore a cancelled game
  night (`RestoreSessionAPI`) without losing its attendee history. Every
  answer is KEPT, never cleared — only flagged `needs_recheck` — and
  `DeleteSession`/`RestoreSession`/`MoveSession` return the affected user
  ids so the HANDLER sends `NotifSessionCancelled`/`NotifSessionRestored`/
  `NotifSessionMoved`, the same service-reports/handler-notifies split
  `ConfirmProposalWinner` uses above.
- **Personal calendar feed**: a private, per-member ICS feed
  (`session_calendar_feed_tokens`) at `GET /sessions/feed/:token`
  (`GameNightFeedICS`/`BuildFeedICS`), on by default per campaign
  (`session_calendar_feed_settings` — absence of a row means enabled) and
  toggleable by the Owner. Replacing a token deletes-and-recreates it, so a
  leaked link stops resolving at once. No Google/Apple/Outlook quick-add
  links or copy-link UI yet — just the feed endpoint and the token/settings
  API a future page wires up.
- **Timezone display**: `Session.ScheduledTZ` is the zone a game night's
  time was set in: the confirmer's zone for a night won from a slot
  proposal, or the `scheduled_tz` the create form sends (the calendar's
  in-card plan form sends the calendar's own zone), stored only if it is a
  real IANA zone. A viewer with no saved zone of their own falls back to
  it, never UTC. The real-world calendar shows times in its own zone,
  labelled, with "Show in my time" to switch. The invite email
  (`FormatScheduledWhen`) labels the time with the zone's abbreviation
  (e.g. `7:00 PM CDT`, or a numeric offset like `+0545` for a zone with no
  name) and never converts it, since it can't know the reader's zone.
- **A new real-world calendar starts with the four seasons of its zone's
  half of the world** — the calendar plugin's own `defaultRealLifeSeasons`.

## Role and Zone Display Rules

Applies to the availability overlay roster and any consumer of
`CampaignRoster`/`CampaignWeekOverlay` (below).

- **Role comes from `campaigns.Role.DisplayName()`**, not derived locally.
  `IsCoDM` (the DM grant) is a separate boolean, not a fourth role — a
  consumer badging a member with DM access checks it directly rather than inferring from
  the role name.
- **RSVP answers, roles, zones and per-member local clocks are
  party-visible; per-member availability LANES are owner or DM access only.**
  Detail is gated by role in the handler, never by route: a player's
  payload never contains another member's lane data; the aggregate
  (everyone's) is post-filtered server-side, never recomputed client-side.
  The count lane's denominator is every member including the Director,
  never "of N players".
- **Zone abbreviations are shown directly** (e.g. `EDT`, via the stdlib's
  DST-correct `Format("MST")`), not the last IANA path segment — degrading
  to a numeric offset (`+0545`) with none; full IANA identifier is in the
  `title` attribute.
- **A member's zone is set or explicitly not set — never guessed.**
  `users.timezone` is nullable; every resolver falls back to "UTC" for the
  GRID, but a per-member CLOCK never does — unset renders a "zone not set"
  badge, an "Ask →" action, and an empty time field, never `--:--` or a
  UTC guess.

`CampaignRoster`/`CampaignWeekOverlay` (`availability_handler.go`) are
exported `Handler` methods meant for a calendar-plugin consumer through a
narrow interface (`internal/wire/plugin_import_guard_test.go` bars a direct
import either way): roster = name/role/DM-access grant/zone, no availability;
overlay = the same projection `GetOverlayAPI` calls for
`GET /availability/overlay`, `includeDetail` decided from role in a
handler. Its consumer, the v4 Bench, was deleted with calendar's UI for V5;
the bridge (`calendarBenchScheduleAdapter`) is on `routes.go`'s
CALV5-PLACEHOLDER list to rebuild. The roster's stable sort (owners, name,
user id) is what a consumer would key a member's hue and pattern to — an
RSVP must never reorder it.

## Notifications and the call-to-action banner

`GET /notifications/call-to-action` returns the one thing the calling
player should act on, or an empty body; the app shell polls it alongside
the notification badge, swapping it into a `.cta-host` that collapses when
empty. It is state, not a fire-once event, and an unanswered RSVP always
outranks a missing-timezone prompt — `callout.go`'s package comment and
`BuildCallout` have the full rationale.

- Only proposal-created notifications raise the
  banner (`calloutNotifTypes`); proposal-confirmed/response, the
  availability nudge, and every game-night lifecycle notification stay in
  the bell only.
- Every error path returns empty HTML with a 200, so an outage can't become
  a page-wide error toast once a minute.
- The mount sits outside `#main-content` (the HTMX-boosted swap target), so
  it isn't discarded and re-fetched on every sidebar navigation.
- The browser reports its own IANA zone
  (`Intl.DateTimeFormat().resolvedOptions().timeZone`); the accept button
  stays hidden until JS fills it in, degrading to the `/account` settings
  link if the browser won't report one. Dismissal is per-kind, tab-session
  only — no persistent per-user preferences table.
