# Sessions Plugin

Game session scheduling and RSVP tracking for campaigns. Sessions represent
real-world play sessions (game nights) with attendee management and entity
linking. The plugin also owns the availability scheduler (a recurring
weekly grid + heatmap for finding a slot) and DM slot proposals with
per-option RSVP.

## Architecture

- **model.go**: Session, Attendee, SessionEntity structs + DTOs.
  Status constants: `planned`, `completed`, `cancelled`. Recurrence
  constants: `weekly`, `biweekly`, `monthly`, `custom` (every N weeks, via
  `recurrence_interval`). RSVP constants: `invited`, `accepted`, `declined`,
  `tentative`. Entity role constants: `mentioned`, `encountered`, `key`.
  `Notes` (ProseMirror JSON) is GM-only; `Recap` (also ProseMirror JSON,
  post-session write-up) is visible to every member.
- **repository.go**: SQL CRUD for sessions + attendees + entity linking.
  ListByCampaign sorts planned first, then by scheduled_date. AddAttendee
  uses ON DUPLICATE KEY UPDATE for upsert.
- **service.go**: Validation, CRUD orchestration, InviteAll for batch invites,
  RSVP status updates, entity linking with role validation.
- **handler.go**: HTTP handlers for list, detail, create, update, delete,
  recap, RSVP, entity link/unlink. MemberLister interface for cross-plugin
  dependency (auto-invite campaign members). HTMX-aware responses.
- **routes.go**: Route registration with role middleware.
- **sessions.templ**: List page with status grouping (Upcoming/Completed/Cancelled),
  detail page with attendee list and RSVP buttons, create modal, edit modal
  (`editSessionModal` — pre-populated fields, JSON PUT to `UpdateSessionAPI`).
- **availability_model.go / availability_repository.go / availability_service.go
  / availability_overlay.go / availability_handler.go / availability.templ /
  static/js/availability.js**: the availability scheduler (below).
- **proposals_model.go / proposals_repository.go / proposals_service.go /
  proposals_handler.go / proposals.templ**: DM slot proposals (below).
- **game_night_service.go / game_night_repository.go**: game-night RSVP
  additions — soft delete/restore with needs-recheck flagging, per-occurrence
  RSVPs on a repeating session, the Director's tally-exclusion switch, the
  "suggest another time" token flow, and the private calendar feed (below).
- **notifications_repository.go / notifications_service.go /
  notifications_handler.go / static/js/widgets/notification_bell.js**: the
  generic in-app notification store and topbar bell.
- **callout.go / callout_handler.go / static/js/widgets/callout.js**: the
  page-wide "you have something to act on" banner (below).

## Data Model

- `sessions` — id, campaign_id, name, summary, notes, notes_html, recap,
  recap_html, scheduled_date (DATE, zone-less), scheduled_time (VARCHAR(5)
  `HH:MM`, nullable — set by a confirmed proposal or the create/edit modal;
  null means no time), calendar_year/month/day, status, sort_order,
  created_by, created_at, updated_at
- `session_attendees` — id, session_id, user_id, status (invited/accepted/
  declined/tentative), responded_at
- `session_entities` — id, session_id, entity_id, role (mentioned/
  encountered/key)
- `session_rsvp_tokens` — id, token, session_id, user_id, action, used_at,
  expires_at, created_at. Single-use, 7-day-expiring email RSVP tokens.
- `member_availability` — id, campaign_id, user_id, day_of_week (0=Sun..6=Sat),
  start_minute, end_minute, state (available/preferred), tz (IANA),
  week_parity, updated_at. RECURRING weekly pattern stored as ZONE-LOCAL
  wall-clock, never UTC. Absence of a row = unavailable. `week_parity` is the
  CADENCE: 0 means every week (the default, so a pre-cadence row keeps its
  meaning), 1 and 2 are the two alternating tracks; the unique key includes
  it, so "free Monday evening on week A, busy on week B" is two rows, not a
  collision.
- `member_availability_status` — campaign_id, user_id, answered_at, tz. PK
  (campaign, user). Records that a member ANSWERED, not what they answered.
  It cannot be derived from the block tables: absence of blocks means
  "unavailable", so a member who never opened the page and one who is
  genuinely never free would otherwise be the same row count (zero). Saving
  an EMPTY grid is a real answer and writes a row here.
- `availability_exceptions` — id, campaign_id, user_id, on_date, start_minute,
  end_minute, state, tz, updated_at. Per-date override; any row for a date
  fully replaces the recurring pattern for that date.
- `slot_proposals` — id, campaign_id, created_by, title, note, status
  (open/closed), created_at, updated_at. A DM's scheduling proposal: a
  title/note plus candidate slots.
- `slot_proposal_options` — id, proposal_id, starts_at_utc, ends_at_utc (UTC
  instants, unlike the wall-clock recurring table above), ordinal (1..5,
  display order), is_winner.
- `slot_proposal_responses` — id, option_id, user_id, response
  (yes/no/maybe), updated_at. Its own table, never `session_attendees`. One
  row per (option, user); re-responding upserts.
- `slot_proposal_tokens` — one-click email response tokens, mirroring
  `session_rsvp_tokens`'s shape: token, option_id, user_id, response,
  used_at, expires_at.
- `notifications` — id, user_id, campaign_id (nullable), type, payload
  (JSON), link, read_at (null = unread), created_at. Generic and
  campaign-optional by design; the scheduler is currently the only writer.
- `sessions.scheduled_tz` — the organizer's IANA zone `scheduled_time` was set
  in. Nullable (every pre-existing row, and a manual session whose creator's
  zone was never captured, have none); a viewer with no saved zone of their
  own falls back to THIS zone for display, never UTC — a session is not
  necessarily tied to one calendar row, so there is no calendar zone to fall
  back to instead.
- `sessions.deleted_at` — soft delete. A cancelled/removed game night is
  restorable (a co-Director/Owner control) rather than gone; every read in
  `repository.go` filters `deleted_at IS NULL` except the restore path itself.
- `session_attendees.note` / `.excluded_from_count` / `.needs_recheck` — a
  short player-set note on their own RSVP (nullable, an explicit empty string
  also clears it); the Director's own "leave myself out of the N/M tally"
  switch, settable only on the caller's own row by the session's organizer or
  the campaign owner; and a flag set when the session moved or was cancelled
  AFTER this member had already answered — the answer itself is never
  cleared, only flagged "look again".
- `session_occurrence_rsvps` — id, session_id, user_id, occurrence_date,
  status, note, excluded_from_count, needs_recheck, responded_at. UNIQUE
  (session_id, user_id, occurrence_date). A RECURRING session's answers live
  here, one row per specific night, instead of one shared row in
  `session_attendees` — "an answer keyed to the night (series plus date), not
  once for the whole series". A non-recurring session keeps using
  `session_attendees` unchanged; `UpdateRSVPDetailed` is the one place that
  decides which table a given session's answer belongs in.
- `session_reschedule_suggestions` — id, session_id, user_id, occurrence_date
  (nullable — set only against one night of a series), suggested_date,
  suggested_time, note, created_at. The record behind the emailed "suggest
  another time" link (see `ValidateAndRecordSuggestion`); the token that
  authorizes writing one lives in the existing `session_rsvp_tokens` table,
  with `action = 'suggest'`.
- `session_calendar_feed_tokens` — id, campaign_id, user_id, token,
  created_at. UNIQUE (token) and UNIQUE (campaign_id, user_id) — one private,
  replaceable feed credential per member. Replacing deletes-then-recreates,
  so a leaked link stops resolving at once.
- `session_calendar_feed_settings` — campaign_id (PK), enabled. ABSENCE OF A
  ROW MEANS ENABLED, the same "absence is a first-class state" convention
  `member_availability_status` uses — the feed is on for every campaign by
  default (operator answer #1), and a row only ever exists once an owner has
  explicitly turned it off.

Availability, proposal-response and notification data live in their OWN
tables — deliberately NOT `session_attendees` — so they stay out of
campaign/AI export egress by construction (pinned by
`availability_egress_test.go`).

The calendar V5 clean-slate migration (`006_calv5_clear_availability`)
truncated `member_availability`, `member_availability_status` and
`availability_exceptions` as a one-time data wipe; the sessions plugin
itself was untouched and the tables refill as members repaint their
availability.

All availability, proposal and RSVP-token routes ride the AUTHED member-only
group (never `AllowPublicCampaignAccess`), except the two public one-click
token routes, whose credential is the token itself. Both public token routes
split GET (confirm interstitial) from POST (apply) so mail scanners and link
prefetchers cannot auto-RSVP via a background GET. Per-member overlay detail
is gated to the owner / DM-granted member inside the handler by role, not by
a separate route.

### `PUT /campaigns/:id/sessions/:sid` (and `/recap`) are PARTIAL updates

| what the body does | what happens to the stored value |
|---|---|
| key **absent** | preserved |
| key present with a **value** | replaced |
| key present and **explicitly `null`** | cleared (nullable columns only) |

Every field of `updateSessionRequest` / `UpdateSessionInput` is a
`patch.Field[T]` (`internal/patch`), which records presence in
`UnmarshalJSON` — a plain pointer collapses "absent" and "null" into the
same `nil`. The service does `load-merge-write` in `UpdateSession`.

This matters because the "Mark Complete" button sends `{status}` only and
the Edit modal never sends `calendar_year/month/day` or
`recurrence_day_of_week` (it has no inputs for them): an unguarded field
assignment would erase the schedule, summary, in-world date and recurrence
config on every such save, silently stopping the next-occurrence generator.
Pinned by `partial_update_test.go` in all three directions, plus source-level
pins on what the templ clients actually send.

Non-nullable columns (`name`, `status`, `is_recurring`, `recurrence_interval`)
have no "cleared" state, so an explicit `null` on one of those preserves
rather than writing the zero value (`patch.Field.Val`). `name` is still
required when it is SENT; absent means "not editing it".

## RSVP Flow

1. Session created → all campaign members auto-invited (status: `invited`)
2. Players see session with RSVP buttons (Going / Maybe / Can't Make It), or
   answer via a one-click emailed link (`/rsvp/:token`, single-use, 7-day
   expiry)
3. RSVP updates via HTMX POST, returns refreshed attendee list fragment
4. Session detail shows attendee count summary (e.g., "3/5 going")
5. A member with no attendee row shows as "you have not answered" — never
   "invited" — and still gets RSVP controls; `rsvpControls` renders for
   every member rather than only those with an existing row.
6. `UpdateAttendeeStatus` is an upsert: re-submitting the same status is
   never reported as "not found", and a member who joins the campaign after
   a session was created still gets a first-class attendee row. Callers are
   responsible for checking membership before calling it.
7. Both token routes re-check that the token's user still belongs to the
   campaign, and consume the token (mark it used) BEFORE applying it, so the
   loser of a concurrent double-submit is refused rather than double-applied.

See "Game Nights" below for the Part C additions this flow got: an optional
note, per-occurrence keying for a repeating session, the organizer's own
tally-exclusion switch, and the "suggest another time" email link — all
additive; a bare `{status}` POST to `/sessions/:sid/rsvp` behaves exactly as
described above, unchanged.

## Session Edit UI

- **Edit button**: Pencil icon in session detail header, visible to Scribe+ users.
  Opens `#edit-session-modal` dialog.
- **Edit modal** (`editSessionModal` templ component): Pre-populated with current
  session values (name, scheduled_date, summary, status, recurrence settings).
  Uses `<dialog>` element matching `createSessionModal` pattern.
- **Status select**: Dropdown with planned/completed/cancelled. Uses `data-initial`
  attribute + JS initialization (templ doesn't support `selected?=` syntax).
- **Submit**: JS serializes form to JSON, sends `PUT` to existing `UpdateSessionAPI`
  endpoint via `Chronicle.apiFetch()`, reloads page on success.
- **Recurrence**: AlpineJS `x-data` toggle for recurring settings (same as create modal).

## Key Design Decisions

- **Separate from calendar events**: Sessions are their own entity, not calendar
  events. This keeps the calendar clean for in-world events while sessions
  track real-world scheduling.
- **Auto-invite on create**: All campaign members are automatically invited when
  a session is created, reducing manual setup.
- **IDOR protection**: `requireSessionInCampaign()` verifies session belongs to
  the campaign in the URL path before any operation.
- **Upsert attendees**: AddAttendee uses ON DUPLICATE KEY UPDATE so re-inviting
  or changing RSVP is idempotent.
- **One notification fan-in**: `NotifyUsers` (`notifications_service.go`) is the
  generic way to notify campaign members. A new feature adds its own type
  constant (like `NotifAvailabilityNudge`) and calls `NotifyUsers`, rather than
  adding a bespoke `NotifyX` method.
- **Co-Directors run game nights**: a co-Director (the `IsDmGranted`
  capability) gets the same move/cancel/restore/propose/confirm controls as
  the Owner on a session — see the Routes section's note on
  `CanAuthorDmOnly`. The Owner's own account/campaign settings are never
  among them; this is a capability laid over a role, not a promotion to it.

## Availability Scheduler

Members paint a recurring weekly availability grid; the DM sees everyone
stacked as a translucent heatmap to find the best slot. Composes with
per-user IANA timezones and with alternating-week (fortnightly) patterns.

- **Encoding** (`static/js/availability.js`): density underlay = the heatmap
  (steep green ramp, deeper = more free), count gutter, a star marks full
  house AND all prefer, slim opaque per-member lanes so identity never
  blends into the wash, an explicit DM-zone label, WCAG-AA contrast.
- **Alternating weeks**: `week_parity` on `member_availability` (0 = every
  week, 1/2 = the two tracks). `availability_cadence.go` maps a real date
  onto a track from a fixed global epoch (1970-01-04, a Sunday) — global
  rather than per-campaign or per-member, so two members can never disagree
  about which track a given week is. `cadenceApplies` treats 0 and anything
  unrecognised as every week: over-applying is visible and correctable on
  the member's own grid, under-applying makes availability silently vanish
  from the heatmap. The picker offers "Every week" / "Week of `<date>`" /
  "Week of `<date>`" — labels the server derives — never "odd"/"even". The
  paint grid holds all three layers and submits all three on every save (a
  replace-all that omitted an off-screen layer would delete it).
- **Has-not-answered is a first-class state**, separate from "answered:
  never free". `member_availability_status` is stamped inside the same
  transaction as the block replace. `OverlayMember.HasAnswered` and
  `RosterEntry.HasAnswered` are party-visible (knowing somebody hasn't
  answered is not knowing when they're free, which is what the lanes gate
  protects). The member's own grid shows a banner until they save once; the
  roster shows a "not answered" badge.
- **Nudge** (`POST /availability/nudge`, Owner/co-DM only): messages every
  member who has not answered and returns their names — not just a count,
  because the Director needs to know who to follow up with. Members who
  already answered are counted but not messaged. There is no scheduled-job
  runner in this product and none is added for this: the nudge button only
  appears, and only fires, on an explicit click.
- **Security**: member-only (authed group, never public); per-member detail
  gated to owner / DM-granted; own tables keep availability out of export
  egress (`availability_egress_test.go`).

### Footguns

- **Never compute "end of the local day" as `time.Date(y,m,d,0,0,0,0,loc).AddDate(0,0,1)`.**
  In a zone whose DST jump lands on midnight (e.g. America/Havana,
  America/Santiago, Atlantic/Azores), local 00:00 does not exist and Go
  normalizes it backwards, which can turn a day-splitting loop into one that
  never advances. Use `timeutil.StartOfCivilDay`, which returns the first
  real instant of a civil date. `splitToViewerDays` also carries a hard
  segment cap and a did-not-advance break as a backstop, because a
  projection loop that cannot terminate can OOM the whole self-hosted
  instance. Guards: `internal/timeutil/start_of_civil_day_test.go`,
  `availability_overlay_dst_test.go` (both run under a deadline, since a
  hang would otherwise just hang the test binary).
- **A member's zone lives in two places**: `member_availability.tz` (written
  only by the availability page's "Your timezone" control, via
  `PUT /availability/mine`) and `users.timezone` (the account setting,
  written only by `PUT /account/timezone`). `sessionService.CampaignMemberZones`
  reads the availability-page zone for the whole roster in one query, and
  `Handler.memberZone` / `resolveViewerTZ` prefer it over the account zone.
  Reading `users.timezone` alone under-reports players who set a zone only
  on the availability page. Empty stays a first-class state — see the
  role/zone rules below — never a silent UTC guess for a per-member clock.
- **Compose, don't overwrite, when writing availability for a day.**
  `AddMyAvailableWindows` (the RSVP-driven offer path) and
  `AddMyException` / `ReplaceMyDayExceptions` (the exceptions API) both
  build on the day's EXISTING rows (`composeDayWithState`) rather than
  replacing the day outright — an exceptions row replaces the whole
  recurring pattern for its date, so inserting a single blind row would
  turn "I'm also free at 7am" into "I'm only free at 7am". The day is
  composed and written in the zone its source rows were authored in; an
  offered window is converted into that zone rather than stamped with the
  caller's own zone, so a block is never silently relabeled as hours later
  or earlier than the member actually painted.

## Slot Proposals

A DM proposes up to 5 candidate slots; members respond yes/no/maybe per
option, by page or by a one-click emailed token (mirrors the session RSVP
token). A proposal option is a concrete UTC instant (unlike the wall-clock
recurring availability table), rendered to each viewer's zone at read time.
Confirming a proposal (`ConfirmProposalAPI`, Scribe+ or co-Director) picks the
winning option, closes the proposal and creates a planned session from that
slot — the only DDL confirm touches is `sessions`. The confirmer is set
`accepted` immediately; a member who voted `yes` on the WINNING option is
carried in as `carried_yes` instead of plain `invited` — a yes vote on a
proposed time is not automatically a Going, so they still owe an explicit
confirm through the normal RSVP flow (which simply overwrites the status).
Both are set by the HANDLER after the blanket `InviteAll`, never inside
`ConfirmProposalWinner` itself — that service method only reports who voted
yes; setting statuses there would have them immediately overwritten back to
`invited` by the handler's own subsequent `InviteAll` call.

## Game Nights (real-world calendars + RSVP, issue #741 Part C)

The operator's four signed answers, and where each lands:

1. **"Members get a private link that puts game nights in their own calendar
   app. It is on for every campaign, and the owner can switch it off."** — a
   per-member, replaceable ICS feed token (`session_calendar_feed_tokens`),
   served at `GET /sessions/feed/:token` (`GameNightFeedICS` /
   `BuildFeedICS`), gated by a campaign-wide switch that defaults to on
   (`session_calendar_feed_settings` — absence of a row means enabled).
   Replacing a token deletes-and-recreates it, so a leaked link stops
   resolving at once. **Gap**: no Google/Apple/Outlook quick-add links or a
   copy-link UI — just the feed endpoint and the token/settings API a future
   page wires up.
2. **"A new real-world calendar starts with the four seasons of its zone's
   half of the world."** — calendar plugin, see its `defaultRealLifeSeasons`.
3. **"The Director counts in a game night's answers like any member, with a
   switch to leave themselves out."** — `excluded_from_count` on the
   organizer's own attendee/occurrence row, settable only by the session's
   `created_by` or the campaign Owner, on their own row only
   (`SetExcludedFromCount`, `PUT .../rsvp-exclude`).
4. **"Someone who has not saved a time zone sees the calendar's own zone,
   labelled (for example CDT), with their browser's zone offered in one
   press."** — `Session.ScheduledTZ` is the organizer's zone a game night's
   time was set in, persisted from `ConfirmProposalWinner`'s confirmer zone;
   a viewer with no saved zone of their own falls back to it, never UTC.
   `internal/timeutil.ZoneAbbrev` is the `Format("MST")` abbreviation helper
   (degrades to a numeric offset for a zone with no name, e.g. `+0545`), unit
   tested but with no production caller yet. **Gaps, honestly**: a MANUALLY
   created session never captures its creator's zone at all —
   `CreateSessionInput`/`updateSessionRequest` have no zone field, so
   `ScheduledTZ` stays nil for every session except one confirmed from a slot
   proposal; and the actual calendar day-card/session-page rendering of "your
   time" vs. "CDT" is a future UI's job (Part A owns the calendar page) — this
   build ships the stored zone and the abbreviation helper, not a finished
   widget or call site.

Other server changes from the same build (not directly one of the four
answers, but named in the operator's "what the mockup changes on the server"
comment on #741):

- **Per-occurrence RSVPs**: see the Data Model section's
  `session_occurrence_rsvps` entry and `UpdateRSVPDetailed`.
- **RSVP notes**: a short (140-char) note on a player's own answer, settable
  and clearable (an explicit empty string clears it) alongside their status.
- **Moving, cancelling or restoring a session that has RSVPs notifies whoever
  had already answered.** Their answer is KEPT, never cleared — only flagged
  `needs_recheck` — and `game_night_service.go`'s `MoveSession` /
  `DeleteSession` / `RestoreSession` return the affected user ids so the
  HANDLER sends the notification (`NotifSessionMoved` /
  `NotifSessionCancelled` / `NotifSessionRestored`), matching this file's
  existing service-reports/handler-notifies division of labor.
- **Soft delete**: `DeleteSession` now sets `sessions.deleted_at` instead of
  a hard `DELETE ... CASCADE`, so a co-Director/Owner can restore a cancelled
  game night (`RestoreSessionAPI`) rather than losing its attendee history.
- **"Suggest another time"**: the third RSVP email-link fix from issue #741
  — the emailed link's token (`session_rsvp_tokens.action = 'suggest'`) is
  consumed ONLY AFTER the submitted date/time validates
  (`ValidateAndRecordSuggestion`), never before, so a bad first submission
  never burns the single-use link. The other two email-link fixes named in
  #741 (a same-status resubmit never 404s; a removed member's link fails
  closed) were already fixed and are pinned by `rsvp_token_guard_test.go`;
  this build only had to avoid regressing them.

## Role and Zone Display Rules

Applies to the availability overlay roster and the calendar Bench (a
cross-plugin consumer — see `CampaignRoster` / `CampaignWeekOverlay` below).

- **Role is read from `campaigns.Role.DisplayName()`** (Owner / Scribe /
  Player), not derived locally. `IsCoDM` (the DM grant) rides as a separate
  boolean rather than being folded into the role string, because a co-DM is
  a capability laid over a role, not a fourth role. A consumer that needs to
  badge a co-DM checks `IsCoDM` directly rather than trying to infer it from
  the role name.
- **RSVP answers, roles, zones and per-member local clocks are
  party-visible. Per-member availability LANES are owner/co-DM only.** The
  aggregate density row is everyone's. Detail is gated in the handler by
  role, never by route, so a player's payload never contains another
  member's lane data at all; the aggregate is post-filtered server-side from
  the set the viewer is entitled to, never recomputed from the viewer's own
  DOM; the count lane's denominator is every member including the Director,
  never "of N players".
- **Zone abbreviations are shown directly** (e.g. `EDT`), via the stdlib's
  per-instant, DST-correct `Format("MST")` — not the last IANA path
  segment. It degrades to a numeric offset (`+0545`) for zones with no
  alphabetic abbreviation. The full IANA identifier is always available in
  the element's `title` attribute.
- **A member's zone is either set or explicitly not set — never guessed.**
  `users.timezone` is nullable and every viewer-zone resolver falls back to
  "UTC" for drawing the GRID (it has to be drawn in some zone), but a
  per-member CLOCK never does: an unset zone renders a "zone not set" badge
  plus an "Ask →" action and a literally empty time field — never `--:--`,
  never a dash, never a UTC guess presented as a fact.

Two exported entry points serve the calendar plugin's Bench widget, through
a narrow interface declared in the calendar plugin and injected from
`internal/app/routes.go` (neither plugin imports the other directly —
`internal/wire/plugin_import_guard_test.go` enforces it):
`CampaignRoster` returns the party-visible roster (name, role, co-DM grant,
zone) with no availability attached; `CampaignWeekOverlay` returns the same
projection `GET /availability/overlay` serves, so the Bench and the
scheduler page cannot disagree about who is free or who may see it —
`includeDetail` is always the caller's decision, made from role in a
handler, never by a route. The roster's stable sort order (owners, then
name, then user id) also drives the hue and pattern a consumer draws a
member with, so answering an RSVP must never reorder it.

## Notifications and the call-to-action banner

`GET /notifications/call-to-action` returns the one thing the calling
player is expected to act on, or an empty body; the app shell polls it on
the same cadence as the notification badge and swaps it into a `.cta-host`
that collapses when empty.

- **It is state, not an event.** A player is rarely looking at the page the
  moment an RSVP opens, so a fire-once toast would often be missed. The
  banner instead reports "there is an unanswered request", survives a
  reload, and disappears once they answer.
- **Precedence**: an unanswered RSVP outranks a missing-timezone prompt,
  because the RSVP is time-limited (the session gets scheduled with or
  without that player) while a missing zone is wrong every day and keeps
  until tomorrow. Only one banner is ever shown at a time.
- **News is not a request.** Only proposal-created and calendar-event-RSVP
  notifications raise the banner; proposal-confirmed/response notifications
  and the availability nudge are informational and stay in the bell only.
- **It never fails the poll**: every error path returns empty HTML with a
  200, so a banner outage cannot become a page-wide error toast once a
  minute.
- **The mount sits outside `#main-content`** (the HTMX-boosted swap
  target), so it is not discarded and re-fetched on every sidebar
  navigation.
- The browser reports its own IANA zone
  (`Intl.DateTimeFormat().resolvedOptions().timeZone`); the accept button is
  hidden until JS fills it in, so a browser that won't report one degrades
  to the `/account` settings link rather than submitting and clearing the
  zone. Dismissal is per-kind and lasts the tab session; there is no
  persistent per-user notification-preferences table.
