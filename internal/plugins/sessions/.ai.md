# Sessions Plugin

Game sessions (real-world game nights): scheduling, RSVPs, attendees, entity
links, soft delete/restore, per-night sightings, Journal entries and bells, a
private calendar feed, the availability scheduler, slot proposals and the
notification bell. Sessions are real-world scheduling; calendar events stay
in-world.

## Files

- **model.go**: Session, Attendee, SessionEntity structs + DTOs. Status:
  `planned`/`completed`/`cancelled`. Recurrence: `weekly`/`biweekly`/
  `monthly`/`custom` (every N weeks via `recurrence_interval`). `Notes`
  (ProseMirror JSON) is GM-only; `Recap` (post-session write-up) is shown
  to members only, never to a public visitor. It is the page editor's
  ProseMirror JSON when written on the night's page, or the typed text when
  written in the calendar's plain box (`isEditorDoc` tells them apart, and
  the calendar never opens editor JSON in its textarea). The recap opens on
  the night's own date with no Mark Complete needed (`recapOpen`), and
  GM-only content is stripped on save because every member reads it.
- **repository.go**: SQL CRUD for sessions + attendees + entity linking;
  `ListByCampaign` sorts planned first, then by `scheduled_date`. Every
  read filters `deleted_at IS NULL` except `FindByIDIncludingDeleted` (the
  restore flow's own read).
- **service.go**: validation, CRUD orchestration, `InviteAll` for batch
  invites, RSVP updates, entity linking with role validation.
- **game_night_service.go, game_night_repository.go**: soft delete/restore,
  per-occurrence RSVPs, the tally-exclusion switch, "suggest another time",
  and the private calendar feed (see Game Nights below).
- **handler.go**: HTTP handlers for list/detail/CRUD/recap/RSVP/entity
  link-unlink; HTMX-aware responses.
- **routes.go**: route registration with role middleware.
- **nights.go, nights_handler.go**: game nights for the calendar's day card
  (see Game Nights below). `NextGameNight` returns the soonest planned night
  that has not started, with no roster, for the header's countdown widget; a
  night with no time lasts until the end of its day, in its own zone.
- **sessions.templ**: list (Upcoming, Played: planned one-offs dated before the viewer's today, Completed, Cancelled; `groupSessions`), detail (attendees + RSVP),
  create modal, edit modal (`editSessionModal` — PARTIAL PUT to
  `UpdateSessionAPI`; status `<select>` uses `data-initial` + JS since
  templ has no `selected?=`).
- **availability_model.go, availability_repository.go,
  availability_service.go, availability_overlay.go, availability_handler.go,
  availability.templ, static/js/availability.js**: the scheduler (below).
- **proposals_model.go, proposals_repository.go, proposals_service.go,
  proposals_handler.go, proposals_calendar.go, proposals.templ**: slot
  proposals (below).
- **notifications_repository.go, notifications_service.go,
  notifications_handler.go, static/js/widgets/notification_bell.js**: the
  in-app notification store and topbar bell. Every bell write and every
  game-night email first drops people who switched that kind off
  (`RecipientFilter`, wired to the auth service in `internal/app/routes.go`);
  those emails end with a link to the person's Notifications settings.
- **callout.go, callout_handler.go, static/js/widgets/callout.js**: the
  call-to-action banner (below).
- **sightings.go, sightings_nights.go, sightings_handler.go,
  sightings_repository.go**: per-night sightings (see Data Model). `NightsFor`
  lists the campaign's played nights (a repeating series expanded, cancelled and
  undated sessions left out, newest first, bounded) for the Last seen block's
  strip, "Every night" and night pickers; it carries names and dates only, so
  any member may read it.
- **static/js/session_edit.js**: Save in the session page's Edit Session
  dialog, mounted by `data-widget="session-edit"` and loaded on sight, so it
  works after a boosted swap too.
- **last_seen.go, last_seen_block.templ, static/js/last_seen.js,
  ../../../static/css/last_seen.css**: the entity page's "Last seen" block (type
  `last_seen`, addon `sessions`, one per page, tile sizes 4x1 and 2x1,
  registered by `registerLastSeenBlock` in `internal/app/routes.go`). The
  server renders one line from `SightingsFor` for the viewer ("Last seen: name
  · 5 weeks ago · N nights"); a player whose page was never seen gets no block,
  the Director gets "Not seen yet". A click grows a sheet out of the line (visible
  Close, Escape, a click outside does not close; Calm fades, Off shows the end
  state) and the script fetches `GET /sessions/sightings` and
  `/sessions/sightings/nights` for the rows. The Director's controls
  (suggestions with Add / Not seen / Add all, "Add a sighting", Remove) are
  rendered only when the viewer sees DM-only content, and every write is a
  `PUT`/`DELETE /sessions/:sid/sightings` followed by a re-read, so the sheet
  shows what the server holds. Remove on a link-derived or undated row changes
  nothing: the link lives on the game night, so it says so and links to the
  night. `AgoText` (Go) and `agoText` (JS) are the same rule and pinned by the
  same cases in `last_seen_test.go` and `test/js/last_seen.test.mjs`. Loads on
  sight through the `last-seen` widget; handlers are inline IIFEs.

## Data model

- `sessions`: id, campaign_id, name, summary, notes, notes_html, recap,
  recap_html, scheduled_date (DATE, zone-less), scheduled_time (`HH:MM`,
  nullable, null = no time), scheduled_tz (the organizer's IANA zone
  `scheduled_time` was set in; nullable; set by `ConfirmProposalWinner` and the
  create/edit `scheduled_tz`), calendar_year/month/day plus
  `calendar_id`, status, sort_order, deleted_at, created_by, timestamps.
  The service stamps the campaign's default calendar on `calendar_id`
  whenever a complete date is saved and clears it with the date;
  `ReconcileWorldDateCalendars` backfills at boot;
  `ListPlannedSessionsInWorldDateRange` filters on it; the calendar calls
  `RemapMonthPositions` (through an adapter) after a structure edit reorders
  months. Status: `planned`/`completed`/`cancelled`. Recurrence: `weekly`/
  `biweekly`/`monthly`/`custom` (every N weeks, `recurrence_interval`).
- `session_attendees`: session_id, user_id, status (invited/accepted/
  declined/tentative/carried_yes), responded_at, note (nullable; empty string
  clears), excluded_from_count (a Director's own "leave me out of the N/M
  tally", own row only), needs_recheck (the session moved or was cancelled
  after the member answered; the answer is kept and flagged, never cleared).
- `session_entities`: session_id, entity_id, role (mentioned/encountered/key).
- `session_occurrence_rsvps`: session_id, user_id, occurrence_date, status,
  note, excluded_from_count, needs_recheck, responded_at; UNIQUE (session_id,
  user_id, occurrence_date). A recurring session's answers live here, one row
  per night; `UpdateRSVPDetailed` decides per call which table an answer
  belongs in. A non-recurring session is unaffected.
- `session_reschedule_suggestions`: session_id, user_id, occurrence_date
  (nullable, one night of a series), suggested_date/time, note. Written by
  `ValidateAndRecordSuggestion`.
- `session_rsvp_tokens`: token, session_id, user_id, action (`accepted`/
  `declined`/`suggest`), used_at, expires_at. Single-use, 7 days.
- `session_calendar_feed_tokens`: campaign_id, user_id, token; UNIQUE token
  and (campaign_id, user_id): one private, replaceable credential per member.
  Replacing deletes and recreates it, so a leaked link stops resolving.
- `session_calendar_feed_settings`: campaign_id (PK), enabled. No row means
  enabled; a row exists only once an owner turned the feed off.
- `session_night_sightings`: session_id, occurrence_date, entity_id, state
  (`seen`/`not_seen`), source (`checkin`/`manual`), added_by; UNIQUE
  (session_id, occurrence_date, entity_id). Who the party saw on one night
  (a one-off uses its scheduled date). `not_seen` keeps a dismissed
  suggestion dismissed.
- `session_night_entries`: PK (session_id, occurrence_date, user_id), UNIQUE
  note_id: which Journal note is whose entry for which night. `note_id` has no
  foreign key, so a deleted entry keeps its row and is not made again.
- `session_night_bells`: PK (session_id, occurrence_date, user_id, kind
  `before`/`checkin`/`share`/`unanswered`), sent_at. An item is claimed here before it is
  written, so a restart or second server never sends one twice.
- `member_availability`: campaign_id, user_id, day_of_week (0=Sun..6=Sat),
  start_minute, end_minute, state (available/preferred), tz (IANA),
  week_parity. Recurring and zone-local, never UTC; an absent row means
  unavailable. `week_parity`: 0 every week (default), 1/2 the two alternating
  tracks; part of the unique key.
- `member_availability_status`: PK (campaign, user), answered_at, tz. Records
  that a member answered, not what: an empty saved grid still writes a row.
  Stamped atomically with the block replace; surfaces as `OverlayMember`/
  `RosterEntry.HasAnswered`, party-visible though the lanes are not.
- `availability_exceptions`: campaign_id, user_id, on_date, start_minute,
  end_minute, state (available/preferred/unavailable), tz. A per-date
  override that replaces that date's whole recurring pattern.
- `slot_proposals`: campaign_id, created_by, title, note, status (open/closed).
- `slot_proposal_options`: proposal_id, starts_at_utc, ends_at_utc (UTC
  instants, unlike the wall-clock recurring table), ordinal (1..5), is_winner.
- `slot_proposal_responses`: option_id, user_id, response (yes/no/maybe); one
  row per (option, user), re-responding upserts. Never `session_attendees`.
- `slot_proposal_tokens`: mirrors `session_rsvp_tokens` (option_id, response).
- `notifications`: user_id, campaign_id (nullable), type, payload (JSON), link,
  read_at, created_at. Every writer is inside this plugin.

Availability, proposal-response and notification data stay out of
`session_attendees`, so they stay out of campaign/AI export egress by
construction (`availability_egress_test.go`). Migration
`006_calv5_clear_availability` truncated the three availability tables once;
they refill as members repaint.

### `PUT /sessions/:sid` and `/recap` are partial updates

| body | stored value |
|---|---|
| key absent | preserved |
| key present, value | replaced |
| key present, explicit `null` | cleared (nullable columns only) |

Every field of `updateSessionRequest`/`UpdateSessionInput` is a
`patch.Field[T]` (`internal/patch`), which records presence in `UnmarshalJSON`
(a plain pointer cannot tell absent from null); `UpdateSession` does
load-merge-write. `internal/patch/partial_update_contract_test.go` tracks every
presence-aware input. Non-nullable columns (`name`, `status`, `is_recurring`,
`recurrence_interval`) have no cleared state: an explicit `null` preserves
(`patch.Field.Val`); `name` is required only when sent. Pinned by
`partial_update_test.go`.

## Notes and recap

`Notes` (ProseMirror JSON) is GM-only. `Recap` is shown to members only, never
a public visitor. It is the page editor's ProseMirror JSON when written on the
night's page, or typed text when written in the calendar's plain box
(`isEditorDoc` tells them apart; the calendar never opens editor JSON in its
textarea). The recap opens on the night's date with no Mark Complete needed
(`recapOpen`). GM-only content is stripped on save because every member reads
it.

## RSVP flow

Creating a session auto-invites every campaign member (`invited`). Players
answer with on-page buttons (HTMX POST, refreshed attendee fragment) or a
one-click emailed link (`/rsvp/:token`). The detail page shows a count ("3/5
going"). The invite email goes to every member with an address on create
(including a session confirmed from a proposal and a repeating night's next
one, made when the last is marked complete), only when the mail server is saved
and on in Admin > Email (`/admin/smtp`).

- A member with no attendee row shows "you have not answered", never
  "invited", and still gets RSVP controls (`rsvpControls`).
- `UpdateAttendeeStatus` is its own upsert (`INSERT ... ON DUPLICATE KEY
  UPDATE`), separate from `AddAttendee`'s idempotent one: re-submitting is never
  "not found" and a late joiner gets a normal row. Callers check membership
  first.
- RSVP also takes an optional note and, for a repeating session, an occurrence
  date (`RSVPSession`/`UpdateRSVPDetailed`). A bare `{status}` POST behaves as
  above.

## Design rules

- **IDOR:** `requireSessionInCampaign()` verifies the session belongs to the
  URL's campaign before any operation. `RestoreSessionAPI` repeats the check by
  hand because a soft-deleted session would 404 through the normal read.
- **One notification fan-in:** `NotifyUsers` is the way to notify members; a
  feature adds a type constant (e.g. `NotifAvailabilityNudge`,
  `NotifSessionRestored`), not a bespoke `NotifyX`. `NotifyUsersWithDetail`
  adds an optional second line (payload `detail`) that the bell shows before
  the time, e.g. the armory's `item_given` "On Bren" (gift icon).
- **Co-Directors run game nights:** the `IsDmGranted` capability gives the same
  move/cancel/restore/propose/confirm controls as the Owner. It is a capability
  over a role, never a promotion to the Owner's account or campaign settings.
- **Service reports, handler notifies:** `DeleteSession`/`RestoreSession`/
  `MoveSession` and `ConfirmProposalWinner` return the affected user ids and
  the handler sends the notification.

## Availability scheduler

Members paint a recurring weekly grid; the DM sees it stacked as a translucent
heatmap, composed with per-user IANA zones and alternating-week patterns.
Encoding (density, count gutter, full-house star, per-member lanes for DMs
only, WCAG-AA) is in the widget's header comment.

- **Alternating weeks:** `week_parity` is computed by `availability_cadence.go`
  from a fixed global epoch (1970-01-04) so members cannot disagree which
  track a week is. `cadenceApplies` treats 0 or unrecognised as every week:
  fail toward over-showing, never hiding availability. The paint grid submits
  all three layers on every save, since a replace-all that omitted one would
  delete it.
- **Has-not-answered is its own state**, distinct from "answered: never free"
  (`member_availability_status`).
- **Nudge** (`POST /availability/nudge`, Owner or DM access) messages every
  member who has not answered and returns names, not a count. It fires only on
  an explicit click; there is no scheduled job.
- **Security:** authed members only, never public; detail gated by role, not
  route (see "Role and zone display").

### Footguns

- Never compute "end of the local day" as
  `time.Date(y,m,d,0,0,0,0,loc).AddDate(0,0,1)`. A DST jump landing on local
  midnight (e.g. America/Havana) can make the boundary non-increasing and hang a
  day-splitting loop. Use `timeutil.StartOfCivilDay`. `splitToViewerDays` also
  has a segment cap and a did-not-advance break, since a non-terminating loop
  can OOM the instance. Guards: `internal/timeutil/start_of_civil_day_test.go`,
  `availability_overlay_dst_test.go`.
- A member's zone lives in two places: `member_availability.tz`
  (`PUT /availability/mine`) and `users.timezone` (`PUT /account/timezone`).
  `memberZone`/`resolveViewerTZ` prefer the availability zone
  (`CampaignMemberZones`, read for the whole roster); reading `users.timezone`
  alone under-reports players who only set it there.
- Compose, don't overwrite, when writing availability for a day.
  `AddMyAvailableWindows` and `AddMyException`/`ReplaceMyDayExceptions` build on
  the day's existing rows (`composeDayWithState`): an exceptions row replaces
  the whole recurring pattern for its date, so a blind insert erases the rest
  of the day. Compose in the source rows' own zone, not the caller's, so a
  block is never relabeled hours off.

## Slot proposals

A DM proposes up to 5 slots (`maxProposalOptions`); members answer yes/no/maybe
per option, on the page or by one-click emailed token. An option is a concrete
UTC instant, rendered to each viewer's zone at read time. Confirming
(`ConfirmProposalAPI`, Scribe or co-Director) picks the winner, closes the
proposal and creates a planned session; the only DDL confirm touches is
`sessions`.

The confirmer is set `accepted`. Anyone else who voted `yes` on the winning
option becomes `carried_yes`, not `invited`: a yes on a proposed time is not a
Going, so they still confirm through the normal RSVP flow, which overwrites the
status. The handler sets both after `InviteAll`; `ConfirmProposalWinner` only
reports who voted yes, since statuses written inside it would be overwritten by
the handler's `InviteAll`.

Members answer date polls on the Game nights calendar. `OpenPollsAPI` gives the
calendar every open poll with its dates in the calendar's zone; each date shows
on its day, where members answer and whoever may confirm picks the date. Every
link to a poll (bell, emails, Coming up, the Availability page's send) names
`/proposals/:pid`, which redirects to the calendar on the poll's picked or next
date (`pollTarget`, `pollLandingDate`). The list and detail pages render only
for a campaign with no real-world calendar.

## Game nights

- **In the calendar:** `ListGameNights` turns planned sessions into one
  `GameNight` per night in a date window (a series stepped by
  `computeNextOccurrence` up to its end date), each with a roster of every
  current campaign member, so silence shows as "no answer yet"; a departed
  member's row is dropped. accepted/tentative/declined map to yes/maybe/no;
  `invited` and `carried_yes` read as no answer. Members only, because the
  roster carries notes. A calendar with real dates renders it in the day card
  (calendar plugin `.ai.md`).
- **Links into the calendar:** the sidebar's "Game nights" app (slug
  `sessions`) and the dashboard block point at `/game-nights`, which redirects
  a member to the real-world calendar (default first, via
  `RealWorldCalendarFinder`, wired in `internal/app`) on that session's night,
  or, with no session, on this month with no day open. A public viewer, or a
  campaign with no real-world calendar, lands on the Sessions page or the
  session's page.
- **Planned from the calendar:** "Plan it" opens the Sessions page with
  `?plan_date=&plan_time=&plan_tz=` (Scribe+), which opens the New Session form
  filled in (`SessionPlan`); `plan_tz` is stored as `scheduled_tz`.
- **Tally exclusion:** `excluded_from_count` lets a session's organizer (or the
  Owner) leave themselves out of the "N/M going" count, own row only; their
  answer stays visible to them and the Director.
- **"Suggest another time":** invite emails link a third one-click token
  (`session_rsvp_tokens.action = 'suggest'`, minted by `CreateRSVPTokens`,
  linked by `sendRSVPEmails`) to a date/time/note form at `/rsvp/:token/suggest`.
  The submission is validated before the token is consumed
  (`ValidateAndRecordSuggestion`), so a rejected one never burns the link. It
  writes a `session_reschedule_suggestions` row and notifies the organizer; it
  never changes the suggester's own RSVP.
- **Soft delete, restore and move notify everyone who had RSVPed.**
  `DeleteSession` sets `deleted_at` instead of a cascading hard delete, so a
  cancelled night can be restored (`RestoreSessionAPI`) with its attendee
  history. Answers are kept and flagged `needs_recheck`, never cleared; the
  handler sends `NotifSessionCancelled`/`NotifSessionRestored`/
  `NotifSessionMoved`.
- **Personal calendar feed:** a private per-member ICS feed at
  `GET /sessions/feed/:token` (`GameNightFeedICS`/`BuildFeedICS`), on by default
  per campaign and toggleable by the Owner. The calendar's feed panel
  (`static/js/game_nights.js`) gets and replaces the token.
- **Timezone display:** `Session.ScheduledTZ` is the zone the time was set in
  (the confirmer's for a proposal winner, or the create form's `scheduled_tz`),
  stored only if a real IANA zone. A viewer with no saved zone falls back to it,
  never UTC. The real-world calendar shows times in its own zone, labelled,
  with "Show in my time". The Sessions list, a night's page and the dashboard
  embed (`FormatScheduledFor`) convert to the viewer's account zone and label
  it; without one they show the organizer's clock with its zone label, never a
  bare time. The invite email (`FormatScheduledWhen`) labels the time with the
  zone abbreviation (`7:00 PM CDT`, or an offset like `+0545` for an unnamed
  zone) and never converts it, since it cannot know the reader's zone.

### Sightings and the Last seen block

`SightingService` (`sightings.go`) is the only reader and writer of
`session_night_sightings`. `SightingsFor` merges those rows with the page's
`encountered`/`key` links, newest first. A link on a repeating series has no
single night, so it comes back undated and is dropped once any night of that
series is marked seen; a stored answer for a night outranks its link. Only a
viewer with DM visibility also gets unanswered `mentioned` nights as
suggestions and the `not_seen` answers. A viewer who cannot see the page gets
nothing. Recording and clearing are DM only, and the date must be one of the
session's nights. `NightsFor` lists the campaign's played nights (a series
expanded, cancelled and undated sessions left out, newest first, bounded) for
the strip, "Every night" and night pickers; names and dates only, so any member
may read it.

The "Last seen" block (type `last_seen`, addon `sessions`, one per page, sizes
4x1 and 2x1, registered by `registerLastSeenBlock` in `internal/app/routes.go`)
renders one line from `SightingsFor` for the viewer ("Last seen: name · 5 weeks
ago · N nights"); a player whose page was never seen gets no block, the
Director gets "Not seen yet". A click opens a sheet (Close and Escape close it,
a click outside does not; Calm fades, Off shows the end state) and the script
fetches `GET /sessions/sightings` and `/sessions/sightings/nights`. The
Director's controls (suggestions with Add / Not seen / Add all, "Add a
sighting", Remove) render only when the viewer sees DM-only content; every write
is a `PUT`/`DELETE /sessions/:sid/sightings` followed by a re-read. Remove on a
link-derived or undated row changes nothing, since the link lives on the game
night; it says so and links there. `AgoText` (Go) and `agoText` (JS) are one
rule, pinned by `last_seen_test.go` and `test/js/last_seen.test.mjs`. The block
loads through the `last-seen` widget; handlers are inline IIFEs.

### Journal entries per night

Every member gets a private Journal note per game night, titled like "Game
night 14, Sat 10 Oct", in their own "Game nights" folder, made through
`NightJournal` (an adapter over the notes widget in `internal/app/routes.go`).
Entries are made lazily for the viewer (`EnsureEntries`, via the notes widget's
`NightEntries` hook with Game nights on, or when a night's page opens): a
one-off night's as soon as it is planned (up to 60 days ahead), each night of a
series the day before, and nights up to a week past. Note and folder ids are
fixed per night and member, so two concurrent loads make one note; a deleted
entry is not remade because its `session_night_entries` row stays. `Tags` tells
the Journal which notes are entries and whether their night has started.

`ForNight` lists the entries the viewer can read (the notes' own visibility:
the DM never reads a player's private entry) and, for a viewer with DM
visibility once the night has started, builds the check-in: every page named in
those entries or linked as `mentioned`, plus any page already answered, with its
answer. `encountered`/`key` links are already in Last seen and not asked about;
a page the viewer cannot see is left out (`NightPageNamer`). Answers go through
`RecordSighting` with source `checkin`.

### Bells

`StartNightBells` runs `SendBells` every 10 minutes for nights from three days
back to two ahead, in campaigns with Game nights on (`NightBellCampaigns`, an
adapter in `routes.go` that raises a co-DM's role to Owner). From 9:00 the day
before a planned night, in the night's zone, each member gets
`game_night_entry_ready` ("... is tomorrow at 7:00 PM. Your Journal has an entry
ready for it."), their entry made first and opened by the bell (a deleted
entry's bell opens the night). At the same time, everyone on the night's list
who hasn't answered or left themselves out of the count, other than the
organizer, gets `game_night_reminder` ("... is tomorrow at 7:00 PM. Can you make
it?", opening the night), read through `NightBellRoster` (`ListGameNights`). A
night is over 4 hours after its start, or when
its day ends if it has no time. For 36 hours after that, each DM gets
`game_night_checkin` (amber edge) once the check-in has someone unanswered, and
each player whose entry no DM can read is told once, at the first look after the
night, with `game_night_share_entry`. Reads use each member's own role and id.
Those three fall under the "Game nights" notification setting
`gameNightEntries`; the unanswered nudge falls under game night invites.
`RemindNightAPI` (`game_night_reminder`) is the organizer's version, at any
time: a bell plus an email; a one-off night's email carries one-click Going / Can't links, a
repeating night's links to the calendar because those tokens cannot name one
night.

## Role and zone display

Applies to the availability overlay roster and any consumer of
`CampaignRoster`/`CampaignWeekOverlay`.

- Role comes from `campaigns.Role.DisplayName()`. `IsCoDM` (the DM grant) is a
  separate boolean, not a fourth role; check it directly.
- RSVP answers, roles, zones and local clocks are party-visible; per-member
  availability lanes are owner or DM access only. Detail is gated by role in the
  handler, never by route: a player's payload never contains another member's
  lanes, and the aggregate is post-filtered server-side, never recomputed
  client-side. The count lane's denominator is every member including the
  Director.
- Zone abbreviations are shown directly (`EDT`, from the stdlib's DST-correct
  `Format("MST")`), not the last IANA path segment; with none, a numeric offset
  (`+0545`). The full IANA id is in the `title` attribute.
- A member's zone is set or not set, never guessed. `users.timezone` is
  nullable; resolvers fall back to "UTC" for the grid, but a per-member clock
  never does: unset shows a "zone not set" badge, an "Ask" action and an empty
  time field, never `--:--` or a UTC guess.

`CampaignRoster`/`CampaignWeekOverlay` (`availability_handler.go`) are exported
`Handler` methods for a calendar-plugin consumer through a narrow interface
(`internal/wire/plugin_import_guard_test.go` bars a direct import either way).
Roster = name/role/DM-access grant/zone, no availability; overlay = the
projection `GetOverlayAPI` uses, `includeDetail` decided from role in a handler.
The bridge to the calendar (`calendarBenchScheduleAdapter`) is on the
CALV5-PLACEHOLDER list in `internal/app/routes.go` to rebuild. The roster's stable sort (owners, name, user
id) is what a consumer keys a member's hue and pattern to; an RSVP must never
reorder it.

## Notifications and the call-to-action banner

`GET /notifications/call-to-action` returns the one thing the caller should act
on, or an empty body; the app shell polls it with the badge and swaps it into a
`.cta-host` that collapses when empty. It is state, not a fire-once event, and
an unanswered RSVP outranks a missing-timezone prompt (`BuildCallout` and
`callout.go`'s package comment have the rationale).

- Only proposal-created notifications raise the banner (`calloutNotifTypes`);
  everything else stays in the bell.
- Every error path returns empty HTML with a 200, so an outage never becomes a
  page-wide toast.
- The mount sits outside `#main-content` (the boosted swap target), so sidebar
  navigation does not discard it.
- The browser reports its IANA zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`);
  the accept button stays hidden until JS fills it, degrading to the `/account`
  link. Dismissal is per kind, tab-session only.
