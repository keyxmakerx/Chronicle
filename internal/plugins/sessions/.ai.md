# Sessions Plugin

Game session scheduling and RSVP tracking for campaigns. Sessions represent
real-world play sessions (game nights) with attendee management and entity linking.

## Architecture

- **model.go**: Session, Attendee, SessionEntity structs + DTOs.
  Status constants: `planned`, `completed`, `cancelled`.
  RSVP constants: `invited`, `accepted`, `declined`, `tentative`.
  Entity role constants: `mentioned`, `encountered`, `key`.
- **repository.go**: SQL CRUD for sessions + attendees + entity linking.
  ListByCampaign sorts planned first, then by scheduled_date. AddAttendee
  uses ON DUPLICATE KEY UPDATE for upsert.
- **service.go**: Validation, CRUD orchestration, InviteAll for batch invites,
  RSVP status updates, entity linking with role validation.
- **handler.go**: HTTP handlers for list, detail, create, update, delete,
  RSVP, entity link/unlink. MemberLister interface for cross-plugin
  dependency (auto-invite campaign members). HTMX-aware responses.
- **routes.go**: Route registration with role middleware.
- **sessions.templ**: List page with status grouping (Upcoming/Completed/Cancelled),
  detail page with attendee list and RSVP buttons, create modal, edit modal
  (`editSessionModal` — pre-populated fields, JSON PUT to `UpdateSessionAPI`).

## Data Model

- `sessions` — id, campaign_id, name, summary, notes, notes_html,
  scheduled_date, calendar_year/month/day, status, sort_order,
  created_by, created_at, updated_at
- `session_attendees` — id, session_id, user_id, status (invited/accepted/
  declined/tentative), responded_at
- `session_entities` — id, session_id, entity_id, role (mentioned/
  encountered/key)
- `member_availability` (migration 002, C-SCHED-P1; `week_parity` added by
  migration 005, C-RSVP-P9) — id, campaign_id, user_id,
  day_of_week (0=Sun..6=Sat), start_minute, end_minute, state
  (available/preferred), tz (IANA), week_parity, updated_at. RECURRING weekly
  pattern stored as ZONE-LOCAL wall-clock, never UTC (RC-12.5). Absence of a
  row = unavailable. `week_parity` is the CADENCE: 0 every week (the DEFAULT, so
  every pre-005 row keeps its meaning), 1 and 2 the two alternating tracks. The
  unique key was re-cut to include it — without that, "free Monday evening on
  week A, busy on week B" collides into one row.
- `member_availability_status` (migration 005, C-RSVP-P9) — campaign_id,
  user_id, answered_at, tz. PK (campaign, user). Records that a member ANSWERED,
  not what they answered. It cannot be derived from the block tables: absence of
  blocks means "unavailable", so a member who never opened the page and one who
  is genuinely never free are the same row-count (zero), and saving an EMPTY
  grid — a real answer — writes nothing but this.
- `availability_exceptions` (migration 002) — id, campaign_id, user_id, on_date,
  start_minute, end_minute, state, tz, updated_at. Per-date override; any row for
  a date fully replaces the recurring pattern for that date.

Availability lives in its OWN tables — deliberately NOT `session_attendees` —
so it stays out of campaign/AI export egress by construction (design §5;
pinned by `availability_egress_test.go`).

## Cross-Plugin Dependencies

- **campaigns**: MemberLister interface provides ListMembers() for auto-inviting
  all campaign members when a session is created.
- **addons**: Registered as addon slug "sessions" — must be enabled per campaign.

### `PUT /campaigns/:id/sessions/:sid` is a PARTIAL update

Contract, ruled 2026-08-07 (sweep R4, extending `C-SIDEBAR-REORDER-RESCUE`
PR1 step 1 and `C-CAL-NULL-PRESERVE` to the whole partial-write class):

| what the body does | what happens to the stored value |
|---|---|
| key **absent** | preserved |
| key present with a **value** | replaced |
| key present and **explicitly `null`** | cleared (nullable columns only) |

The distinction is real, not incidental: every field of
`updateSessionRequest` / `UpdateSessionInput` is a `patch.Field[T]`
(`internal/patch`), which records presence in `UnmarshalJSON` — a plain
pointer collapses "absent" and "null" into the same `nil`. The service does
`load-merge-write` in `UpdateSession`.

Before this, every field was assigned unguarded, so the "Mark Complete"
button (which sends `{status}` only) erased the schedule, the summary, the
in-world date and the entire recurrence config — and with `is_recurring`
gone the **next-occurrence generator silently stopped firing**. The Edit
modal lost `calendar_year/month/day` and `recurrence_day_of_week` the same
way, because it has no inputs for them and therefore never sends them.
Pinned by `partial_update_test.go` in all three directions, plus two
source-level pins on what the templ clients actually send.

Non-nullable columns (`name`, `status`, `is_recurring`,
`recurrence_interval`) have no "cleared" state, so an explicit `null` on one
of those preserves rather than writing the zero value — `patch.Field.Val`.
`name` is still required when it is SENT; absent means "not editing it".

All availability routes ride the AUTHED member-only group (never
`AllowPublicCampaignAccess`). Per-member overlay detail is gated to the owner /
DM-granted inside the handler by role (design §5), not by a separate route.

## RSVP Flow

1. Session created → all campaign members auto-invited (status: `invited`)
2. Players see session with RSVP buttons (Going / Maybe / Can't Make It)
3. RSVP updates via HTMX POST, returns refreshed attendee list fragment
4. Session detail shows attendee count summary (e.g., "3/5 going")

## Session Edit UI

- **Edit button**: Pencil icon in session detail header, visible to Scribe+ users.
  Opens `#edit-session-modal` dialog.
- **Edit modal** (`editSessionModal` templ component): Pre-populated with current
  session values (name, scheduled_date, summary, status, recurrence settings).
  Uses `<dialog>` element matching `createSessionModal` pattern.
- **Status select**: Dropdown with planned/completed/cancelled. Uses `data-initial`
  attribute + JS initialization (templ doesn't support `selected?=` syntax).
- **Submit**: JS serializes form to JSON, sends `PUT` to existing `UpdateSessionAPI`
  endpoint via `Chronicle.apiFetch()`, reloads page on success.
- **Recurrence**: AlpineJS `x-data` toggle for recurring settings (same as create modal).

## Key Design Decisions

- **Separate from calendar events**: Sessions are their own entity, not calendar
  events. This keeps the calendar clean for in-world events while sessions
  track real-world scheduling.
- **Auto-invite on create**: All campaign members are automatically invited when
  a session is created, reducing manual setup.
- **IDOR protection**: `requireSessionInCampaign()` verifies session belongs to
  the campaign in the URL path before any operation.
- **Upsert attendees**: AddAttendee uses ON DUPLICATE KEY UPDATE so re-inviting
  or changing RSVP is idempotent.

## Availability Scheduler (C-SCHED-P1, Slice 1)

Real-world session scheduling: members paint a recurring weekly availability
grid; the DM sees everyone stacked as a translucent heatmap to find the best
slots. Composes with per-user IANA timezones. Proposals/notifications are P2/P3.

- **Files**: `availability_model.go` (types, DTOs, palette), `availability_repository.go`
  (CRUD on `member_availability` + `availability_exceptions`, methods on the
  existing `sessionRepository`), `availability_service.go` (validation + overlay
  orchestration), `availability_overlay.go` (the PURE DST-correct projection),
  `availability_handler.go` (HTTP + role gating), `availability.templ` (page
  shell), `static/js/availability.js` (paint grid + heatmap rendering).
- **DST correctness** is the crux and lives in `internal/timeutil` (stdlib-only,
  no plugin imports — shared with the real-calendar lane): a recurring block is a
  zone-local wall-clock resolved to an absolute instant only against a concrete
  week's real dates (`time.Date(y,m,d,0,min,0,0,loc)`), then converted to the
  viewer's zone. `buildWeekOverlay` projects each member's pattern onto the
  target week in the DM's zone. Tested with cross-zone + spring-forward cases —
  including, since C-RSVP-ROBUST, the **midnight-jump** zones (see below), which
  this line previously claimed coverage of and did not have.
- **Signed encoding** (`mockups/availability-calendar-concept.html`): density
  underlay = the heatmap (steep green ramp, deeper = more free), count gutter,
  ★ = full house AND all prefer, slim OPAQUE per-member lanes so identity never
  blends into the wash, explicit DM-zone label, WCAG-AA.
- **Security**: member-only (authed group, never public); per-member detail
  gated to owner / DM-granted; own-tables keep availability out of export egress
  (`availability_egress_test.go`).
- **Deferred to later slices**: slot proposals, per-option RSVP, notifications,
  the month view, and a richer per-date exception editor UI.

## C-CALV4-RSVP-P8 (2026-07-28) — the overlay's role column told the truth for the first time

- **`roleLabel(isOwner)` is DELETED.** It mapped a member to `"DM"` | `"player"`
  from `Role >= RoleOwner` alone and **ignored `IsDmGranted`** — so a co-DM
  rendered as a plain player while the same request handed them full owner-tier
  detail, on the surface whose entire subject is who-may-see-what. It was also a
  SECOND role vocabulary competing with `campaigns.Role.DisplayName()`. Deleted
  rather than deprecated: leaving it compiling is how a second vocabulary comes
  back. `static/js/availability.js` was its only other consumer and moved with it.
- **`OverlayMember` gained `TZ` and `IsCoDM`.** `TZ` is the member's stored IANA
  zone and **empty means NOT SET** — a first-class state, not a default.
  `resolveViewerTZ` still falls back to UTC (the grid must be drawn in some zone
  and it labels which); the new `storedTZ` deliberately does not, because a
  per-member CLOCK rendered from a UTC guess is a guess presented as a fact.
  Consumers print a `zone not set` repair and NO clock — never `--:--`, never a
  dash. Both egress pins grew in the same commit (a `timezone` token on the
  scheduler guard, a separate whereabouts walk on the calendar's RSVP guard),
  plus an assertion that the field still EXISTS so the guard cannot be satisfied
  by deleting what it guards.
- **`CampaignReader` is a one-read seam, not an N+1.** `campaigns`'
  `IsUserDmGranted` re-reads the campaign row per call, so the grant SET is read
  once per overlay via `GetByID` + `ParseSettings()` and every member labelled
  from it. Nil-safe: a missing reader under-marks (a co-DM loses their badge)
  rather than over-marking.
- **Two exported entry points now serve the calendar's Bench**, wired through a
  narrow interface declared in the calendar plugin and injected from
  `internal/app/routes.go` — neither plugin imports the other, which
  `internal/wire/plugin_import_guard_test.go` forbids outright:
  - `CampaignRoster` → `[]RosterEntry`, the PARTY-VISIBLE half (name, role,
    co-DM grant, zone) with no availability attached. It exists because
    `WeekOverlay.Members` fuses identity and lanes and is therefore populated
    only under `includeDetail`, so a player-facing surface that needs the names
    cannot use it.
  - `CampaignWeekOverlay` → the same projection `GET /availability/overlay`
    serves, so the Bench and the scheduler page cannot disagree about who is
    free or who may see it. `includeDetail` remains the CALLER'S decision, made
    from role in a handler, never by a route.
- **The order is the identity key.** `overlayMembers`' stable sort (owners, then
  name, then user id) now also drives the hue and pattern the Bench draws a
  member with — so a member answering an RSVP must not move a single element.
  Never sort that roster by availability, tally or answer.

## C-SWEEP-R3 bookings (2026-08-07) — both need a signature

- **"Mark Complete" wipes the session.** The button sends `{name, status}` only and
  `UpdateSession` assigns every field unguarded, so the schedule, summary, in-world
  date and recurrence are erased and **the next-occurrence generator silently stops
  firing**. It is not one client: the Edit modal wipes `calendar_year` and
  `recurrence_day_of_week` too, so patching only the button leaves the endpoint loaded
  and the loss live on the other surface. The honest fix changes the shared PUT's
  semantics (presence-aware `UpdateSessionInput` + load-merge in the service, both
  templ clients normalized to send only what they mean), which forces the user-visible
  answer to *"how does a client now explicitly CLEAR `summary` / `scheduled_date`?"* —
  the presence-flag design `C-SIDEBAR-REORDER-RESCUE` PR1 step 1 already reserves. It
  is also a campaign-scoped JSON API with potential external consumers. Booked as part
  of `C-PARTIAL-PUT-CONTRACT`; two ready-made red probes exist.
- **The "Sessions" feature toggle gates nothing that matters** — Sessions routes are
  actually gated on the **Calendar** addon, so enabling Sessions alone silently
  redirects to the dashboard. Severity corrected DOWN from high: the toggle DOES gate
  the dashboard block and the sidebar item, and routes stay protected by auth +
  campaign access + role, so this is a feature-hub consistency / dead-link gap, not an
  authz hole. Both remedies amend ADR-023 and have opposite blast radii — gating routes
  on `"sessions"` silently removes the whole plugin from every campaign whose row is
  off, while dropping the addon needs an idempotent reconciler plus a re-point of the
  `session_tracker` block meta. Booked as `C-ADDON-TOGGLE-TRUTH`.

## C-RSVP-ROBUST (2026-08-16) — the RSVP and availability systems, made runnable

Seven defects, each with a guard that was proved red before it was proved green.

### 1. The overlay could not RETURN, and the process died with it

`splitToViewerDays` computed the end of the viewer's local day as
`time.Date(y,mo,d,0,0,0,0,loc).AddDate(0,0,1)`. In a zone whose DST jump lands
**on midnight** — America/Havana (2026-03-08), America/Santiago (2026-09-06),
Atlantic/Azores (2026-03-28) — local 00:00 does not exist, Go normalises it
BACKWARDS to 23:00 the previous day, and `AddDate` landed on 23:00 of the SAME
day. The loop's only advance was `cur = segEnd`, which assigned `cur` the value
it already held, while APPENDING a `LaneSegment` every iteration. Not a spin: an
allocation storm, measured live at 41 MB → 2.6 GB RSS in ten seconds, still
climbing after the client disconnected, with no ctx check anywhere in the loop.

Reachable two ways. **Deliberately:** `GET /availability/overlay` takes an
arbitrary `?tz=` and `?week=` from any Player. **By accident:** the Bench and
`/schedule` project in the viewer's own stored profile zone, so a Cuban, Chilean
or Azorean table loses the instance twice a year.

- Every "end of the local day" now goes through **`timeutil.StartOfCivilDay`**,
  which returns the first REAL instant of a civil date (the transition instant
  where midnight does not exist). Never re-inline the naive expression.
- `splitToViewerDays` also carries a hard `maxViewerSegs` fuse and a
  did-not-advance break. They are not optimisations: a projection loop that
  cannot terminate is an OOM of the whole self-hosted instance, so the blast
  radius of a future arithmetic mistake is a short segment list, not the process.
- Guards: `internal/timeutil/start_of_civil_day_test.go`,
  `availability_overlay_dst_test.go`. **Every overlay call there runs under a
  deadline** — a plain call would hang the test binary instead of failing it,
  and a suite that hangs gets its timeout raised, not its bug fixed.

### 2. A member's zone lives in TWO columns and the product read one

The availability page's control is labelled "Your timezone" and saving writes
`member_availability.tz` and **nothing else** (`static/js/availability.js` PUTs
`{tz, blocks}` to `/availability/mine`; the only writer of `users.timezone` is
`PUT /account/timezone`, which that page never calls). Every surface that
reported a member's zone read `users.timezone` only.

`sessionService.CampaignMemberZones` (ONE read per roster, not per member) is
now the availability-page half, and `Handler.memberZone` prefers it over the
account zone. Consequences fixed: the Bench stopped printing "zone not set" and
a repair chip beside players who HAD set their zone; `resolveViewerTZ` stopped
rendering their own heatmap in UTC; and the calendar's RSVP flows (below) got a
real zone to work with. **Empty is still a first-class state** — no UTC guess.

### 3. `AddMyAvailableWindows` relabelled the member's existing hours

The composed day was written back with the CALLER'S zone stamped on every row,
while the minutes on the canvas had been authored in the member's own. One click
apart, so a New York player with no account zone had their whole stated evening
moved four hours earlier in real time, with no edit by them and no signal.

The day is now composed and written in the zone its SOURCE ROWS were authored in,
and the OFFER is converted (`resolveOfferedDays`, a bounded fixed point because
the target zone depends on the date and the date depends on the zone). Stored
minutes are never renumbered and never relabelled.

### 4. `POST /availability/exceptions` deleted the rest of the member's day

Exception rows REPLACE the recurring pattern for their date, so the single row
this endpoint inserted became the member's ENTIRE day: "I'm ALSO free 07:00–08:00"
left them free for one hour at 7am and busy every evening, with their own grid
still showing 09:00–23:00. The compose-the-day rule existed and had been applied
to the RSVP-offer path and the client-side editor, never to this documented
Player+ route. `AddMyException` now composes (`composeDayWithState`, shared with
the offer path; `keepPreferred=false` here because this is the member SAYING what
a window is) and writes atomically through `ReplaceMyDayExceptions`.

### 5. `/rsvp/:token` — three fixes

- **Membership is re-checked on BOTH halves** (`tokenUserStillBelongs`), as
  `/proposals/respond/:token` and `/calendar-rsvp/:token` already did. A removed
  player's emailed "Going" link used to keep working for the token's full 7-day
  life. Fail-closed on a missing session, a lookup error, or a nil lister.
- **The token is single-use for real.** `MarkRSVPTokenUsed` gained
  `AND used_at IS NULL` + a RowsAffected check (`ErrRSVPTokenSpent`), and
  `ApplyRSVPToken` now **consumes BEFORE it applies** so the loser of a race is
  refused before it can write. The order is the guarantee, not the predicate
  alone.
- **`UpdateAttendeeStatus` is an UPSERT.** It was a bare UPDATE whose
  `RowsAffected==0` was reported as "attendee not found" — but MariaDB counts
  CHANGED rows, so re-submitting the same status inside one second 404'd on a row
  that was sitting right there ("the RSVP thing is flaky"). The upsert also makes
  a member who joined the campaign AFTER a session was created a first-class
  attendee. **Membership is the caller's to enforce** and both callers do.

### 6. A late joiner had no RSVP control at all

`AttendeeList` rendered the buttons inside `for a := range attendees { if
a.UserID == currentUserID }`, inside the `len(attendees) != 0` branch. The
controls are now a separate `rsvpControls` component rendered for every member,
with `myRSVPStatus` returning `""` — "you have not answered", never "invited" —
for a member with no row.

### Where the guards are

`availability_overlay_dst_test.go`, `availability_offer_zone_test.go`,
`availability_exception_compose_test.go`, `rsvp_token_guard_test.go`,
`attendee_controls_test.go`, `member_zone_test.go`, and the shared real-MariaDB
harness `dbtest_support_test.go` (own scratch schema per test — the repo's other
integration helpers take `CHRONICLE_TEST_DB_DSN` verbatim and die on
"No database selected" under `make test-int-local`).

## C-RSVP-P9 (2026-08-16) — silence stopped counting as a "no", and weeks can alternate

Two gaps the operator found by asking whether the RSVP work had been *expanded*
rather than merely hardened. It had not been; this is the expansion.

### 1. "Has not answered" is now a state

The defect was structural, not cosmetic. Absence of `member_availability` rows
has always meant *unavailable*, so **a member who never opened the availability
page was indistinguishable from a member who is genuinely never free**. The
Director could not tell "nobody is free Tuesday" from "nobody has answered", and
planned around a fact nobody had stated.

- `member_availability_status` (migration 005) records that a member ANSWERED.
  It is stamped **inside the same transaction** as the block replace, because
  "these are their blocks" and "they have answered" are one fact written twice.
- It **cannot be derived** from row counts, which is why it is a table and not a
  `COUNT(*)`: saving an EMPTY grid is a real answer ("none of these times"), and
  a derived flag would report that member as silent forever. Pinned by
  `TestDB_EmptySaveStillRecordsTheAnswer`.
- `OverlayMember.HasAnswered` and `RosterEntry.HasAnswered` carry it. Both are
  **party-visible**: knowing somebody has not answered is not knowing when they
  are free, which is the fact the lanes gate protects.
- The member's own grid shows a banner until they save once; the Director's
  roster chip shows a gold "not answered" badge.

### 2. Alternating weeks

`week_parity` on `member_availability` (0 every week / 1 and 2 the two tracks).
`availability_cadence.go` maps a real date onto a track from a **fixed global
epoch** (1970-01-04, a Sunday). The epoch is global on purpose: if each campaign
or member counted from its own start, two members could disagree about which
track a given week is and the overlay would silently combine incompatible
answers.

- `cadenceApplies` treats 0 **and anything unrecognised** as every week. That
  direction is deliberate: applying too often is visible and correctable on the
  member's own grid, while applying never makes availability vanish from the
  heatmap with nothing on screen to explain it.
- The unique key was re-cut to include the cadence. Without that, "free Monday
  evening on week A, busy on week B" collides into one row
  (`TestDB_SameSlotOnBothTracksIsStorable`).
- The save's dedupe key gained the cadence for the same reason.
- **The UI never says "odd" or "even".** The picker offers *Every week*,
  *Week of 16 Aug*, *Week of 23 Aug* — labels the server derives, so the client
  cannot disagree with the projection. The paint grid holds three layers and
  emits all three on save (a replace-all that omitted an off-screen layer would
  delete it).

### 3. The nudge

`POST /availability/nudge` bells every member who has not answered, and reports
their NAMES back — the Director is about to be asked "did you ping me?" and a
bare count cannot answer that. Members who already answered are counted, not
messaged; nudging everyone trains a table to ignore the bell.

**NO TIMER, ON PURPOSE.** There is no scheduled-job runner in this product
(`notifications_service.go` says so), and inventing one to power a reminder
would be infrastructure justified by a nicety — and would mean people being
