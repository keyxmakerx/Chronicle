# Entities Plugin

Core plugin, always enabled: pages ("entities") with configurable types,
dynamic fields, full-text search, nesting and the profile page.

## Footguns

- **`entity_types` SELECTs** MUST route through `entityTypeColumns` +
  `scanEntityType(rowScanner)` in `repository.go`. The scan binds by position,
  so a mismatch panics at runtime, not build. Guard:
  `TestEntityTypeRepository_Integration`.
- **Paginated reads** MUST end their `ORDER BY` in `e.id`: no other sort column
  is unique (except `uq_entities_campaign_slug`), so a walk to exhaustion can
  skip or repeat rows. Callers: list page, syncapi `ListEntities` + pull loop,
  both campaign-export walks. `pagination_total_order_test.go` requires a
  tiebreaker on every `LIMIT ? OFFSET ?` query in `repository.go`.
- **Public-capable routes authorize the `:eid`, not just the campaign.**
  `AllowPublicCampaignAccess` + `RequireViewAccess` check the campaign only. A
  new route under them needs the campaign-match 404 + `CheckEntityAccess`, as
  `Show`, `GetEntry`, `GetFieldsAPI`, `PreviewAPI`, `GetAliasesAPI` and
  `.../:eid/backlinks` have. `FindBacklinks` pins `e.campaign_id = ?` first
  through `backlinksWhere`, mirroring `visibilityFilter`.
- **Entity reads use `visibilityFilter` or `CheckEntityAccess`; category-level
  reads use `TypesForViewer`** (Adventures, below).

## Domain concepts

- **Entity**: a page: name, type, entry, fields.
- **Entity type**: per-campaign template of an entity's fields; 7 defaults
  (Character, Location, Organization, Item, Note, Event, Shop) plus Adventures,
  all GM-customizable. Seeded on campaign creation via `EntityTypeSeeder`.
- **Fields definition**: JSON array on `entity_types` (key, label, type,
  options, section). `link` and `rule` types read more than their stored value
  (`field_kinds.go`; "Link and worked-out fields").
- **Fields data**: JSON object of an entity's values.
- **Entry**: rich text body (TipTap/ProseMirror JSON).
- **Player notes**: `player_notes` JSON + `player_notes_html`, separate from the
  DM entry; maps to a second Foundry journal page.
- **Privacy**: `is_private` shows an entity only to the owner and Co-DMs;
  others get 404. The slide-in permissions card (`static/js/widgets/permissions.js`,
  `PUT /entities/:eid/permissions`, DM team; member emails go to the owner only)
  is the only writer; the edit form carries no `is_private` input.
  `UpdateEntityInput.IsPrivate` is `*bool` (nil preserves); syncapi uses
  `patch.Field[bool]`, as does its batch twin `syncChange`. A bare bool would
  bind `false` on a name-only rename and publish a hidden page to players.
- **Optimistic concurrency**: `expected_updated_at` on update gives 409 if the
  entity changed since.

### `Update` is a partial update

| caller sends | stored value |
|---|---|
| field absent (`patch.Field` zero / `IsPrivate == nil`) | preserved |
| value | replaced |
| explicit `null` (or `""` on `type_label`/`parent_id`) | cleared |

`UpdateEntityInput`'s doc comment (`model.go`) has the full contract.
`Name`/`TypeLabel`/`ParentID`/`Entry` are `patch.Field[string]`.
`ParentID` needs an explicit `parent_id` member in syncapi's update body and in
every AI-workspace commit-update (`""` cannot say "absent"), or the page is
silently detached. `Entry` keeps a legacy `""` = preserve reading; explicit null
clears. Pictures are not on this input: `UpdateImage`/`UpdateCoverImage` are
their only writers and check the file belongs to the page's campaign. Pinned by
`entity_partial_update_test.go` and `syncapi/entity_partial_update_test.go`.

### Field-level visibility

Mechanism in `gm_fields.go`'s package comment. Two tiers, orthogonal to
whole-entity privacy and to each other:

- `FieldDefinition.GMOnly` hides the value from every Player-tier viewer,
  including the claimed owner.
- `FieldDefinition.OwnerOnly` hides it from everyone but GM-tier roles and the
  claimed owner (`Entity.IsOwnedBy`).

Both come from a system manifest's `gm_only`/`owner_only`, converged onto
existing types by `SyncFieldGMFlags`/`SyncFieldOwnerOnlyFlags`
(`internal/app/preset_applier.go`, at boot and on install/update).
`FilterRestrictedFields` is the one call every `fields_data` egress uses. The
server is the authority; a widget hiding its own box (`data-is-gm`/`data-is-owner`
in `show_renderer_registry.go`) is never the fix.

## Link and worked-out fields

`GET .../fields` (and the era version's) carries `shown`: how a field reads to
this viewer when that differs from the stored value. `attributes.js` draws it.

- **link**: `text` is the page's name and `href` its page, only if the page is in
  this campaign, in the field's `link_to` category, and the viewer may open it;
  otherwise `text` is empty (the id is never shown). A changed link value is
  checked on every write (`checkLinkValues` in `Create`, `Update`,
  `UpdateFields`): same campaign, not the page itself, right category. An
  unchanged one is not, so a removed page never blocks saving the sheet.
- **rule**: `text` is the rule's result for the page's values; a typed value wins
  and sets `byHand`, with `ruleGives` when the rule differs.
- **calendar_date** (`field_dates.go`): value `year-month-day` (month by number),
  optionally `|` plus the length each countdown uses (`1043-3-22|1`). `text` is
  the date on the campaign's calendar; `date` carries `ago` (when `date_ago`
  asks) and `countdowns` (`before`, `running`, `last`, `ended` as of today). A
  countdown's own `gm_only` hides it from players. `checkLinkValues` checks a
  changed value: a day the calendar has, a length the countdown has. The calendar
  comes through `FieldCalendar` (`internal/app/field_dates_adapter.go`); unwired
  or with no calendar, dates show as numbers and no countdown runs. `GET
  .../fields` adds `dateBook` (months, today) for the picker.
- **local words**: a text, select or rule value with a local name for the page's
  place or the current era shows it, with `usual` the replaced word. Numbers,
  ticks, URLs and prose are never renamed. `GET
  /campaigns/:id/entities/:eid/local-words` serves widgets outside the fields box
  (shop room and list coins) via `Chronicle.localWords`/`localName` in `boot.js`.
  Rules and words come through `FieldWords`
  (`internal/app/fieldrules_adapters.go`); unwired, rule fields show only typed
  values and nothing is renamed.
- A field the viewer may not see (`GMOnly`, `OwnerOnly`) is skipped first
  (`restrictedKeys`); a rule field stores nothing to strip, so it would otherwise
  be worked out and shown.
- `UpdateEntityType` checks a category's link fields name a category of the
  campaign, rule fields a rule it has, and date-field countdowns
  (`checkFieldKinds`, `CheckDateSettings`).

## Undo: history, Trash, save clashes

- **Trash (ADR-060):** `Delete` marks the page and its live sub-pages
  (`deleted_at`, one `trash_root_id`) once `SetPageSafety` is wired; without it
  (unit tests) delete is permanent. Every read excludes trashed rows:
  `visibilityFilter` starts with `liveOnly` for every role, and reads that skip it
  add `liveOnly` themselves. Owners see the Trash at `/campaigns/:id/trash`.
  Restore puts a page whose parent is still trashed at the top level.
  `StartPurger` purges after `settings.TrashRetentionDays`. Player Notes
  (`entity_notes`, FK cascade) stay with the trashed page and go at purge.
  `NoteCounter` (`SetNoteCounter`, nil = silent) gives counts only:
  `TrashItem.NoteCount` and the `&notes=N` redirect after `Delete`; a count
  failure never blocks a delete. A page kind with pages in the Trash cannot be
  deleted.
- **History:** `entity_versions` keeps title and text, not field values (sync
  clients change those constantly). Kinds: `created`; `edit` (joined into the
  author's last row within `versionCoalesceWindow`); `baseline` (first save of a
  page older than history, recording what it replaced); `restore`.
  `MaxVersionsPerPage` = 100. Owners and scribes only.
- **Save clashes:** `entities.entry_rev` counts text changes. `GET .../entry`
  returns `rev` to editors, who send it back as `base_rev`; `SaveEntry` writes
  only if it still matches, else 409 `edit_conflict` with the stored text and
  author. The editor then offers: see their changes, keep both (mine on top), use
  mine. No `base_rev` means no check.
- **Who saved:** `withActorMiddleware` puts the user on the context (`WithActor`);
  syncapi uses `WithSyncActor`. Sync, import and actor-less saves list as "Sync or
  import".
- **Access:** History, restore and the entry PUT run `CheckEntityAccess`, so a
  scribe never reads or restores a page hidden from them (a clash answer carries
  the stored text).

## Extra places in the page tree

A page can be listed under more than one parent. `entities.parent_id` stays its
only real home: breadcrumb, Sub-pages, sync API and Foundry journals never see a
listing. Table `entity_places` (migration 49); `PlaceRepository`
(`place_repository.go`), rules in `PlaceService` (`place_service.go`).

- **Refused:** a page under itself, under its own real parent, under any
  page below it (the walk follows real parents AND listings, so a loop
  through either is seen; trashed pages are walked too), and across
  campaigns. A trashed page or parent is "not found". 25 per page. Adding
  one that exists is a no-op.
- **Real moves keep up:** `ReorderEntity` and `Update` (via `PlaceGuard`,
  `place_guard.go`) refuse a real move that would loop through a listing and
  drop a listing next to the page's new real parent.
- **Visibility is the page's:** a read keeps a listing only when the viewer
  can see both the page and the parent (`FilterViewableEntityIDs`, the one
  predicate). The Trash hides a listing through the joins; Restore brings it
  back; a purge cascades.
- **Who:** add and remove need a Scribe route AND `CanEdit` on the page; the
  parent must be visible to the viewer.
- **Where it draws:** `entityPlacesLine` under both page titles
  (`place_line.templ`, `static/js/widgets/page_places.js`); the sidebar tree
  (`SidebarEntityList` rows with `data-place-key`, no `data-entity-id`,
  never moved on their own, `static/js/sidebar_tree.js`); the category
  page's tree view
  (`buildEntityTreeWithPlaces`). Searches and plain lists never join the
  table, so a page is never listed twice there.
- **Routes:** `POST /campaigns/:id/entities/:eid/places` `{parent_id}` and
  `DELETE .../places/:pid`, both answering with the refreshed line.
- **Export/import:** `ExportEntity.also_listed_under` (parent slugs); import adds
  them after every parent link so the cycle rule sees the finished tree.

## Standing block

`standing` is a page block (one per page; `standing_block.templ`,
`static/js/standing.js`, `static/css/standing.css`): how a page, usually a guild
or person, feels about the party or one character. The Director sets the word
(Hostile, Wary, Neutral, Warm, Trusted) and gives reasons. Tables
`entity_standings`, `entity_standing_reasons`, `entity_standing_settings` (see
`.ai/data-model.md`; migration slug `entity_standing`, so a failed migration
leaves out only this block).

- **`StandingService` alone decides who sees what.** A player gets the word and
  non-DM-only reasons, only for subjects that have a word and whose character page
  they can open, and no block when the page's switch is off. The repository never
  selects a DM-only reason for a player, and the service filters again. The
  Director also gets unset characters, the switch and each reason's `dmOnly`.
  Never add a second decider.
- **Routes:** `GET .../entities/:eid/standing/:subject` (Player+, narrowed by the
  service), `POST .../standing/:subject/reasons`, `DELETE .../reasons/:rid`,
  `PUT .../entities/:eid/standing-settings` (Director or co-Director). `:subject`
  is `party` or a character page id.
- **Limits:** `StandingReasonMax` 90 chars, `StandingWhenMax` 30,
  `MaxStandingReasons` 300 per standing; a read sends the newest
  `standingReasonsShown` (200) per subject with the true total.
- Foundry sync and export do not read standings.

## Pinned pages

The campaign home's Pinned Pages widget (`page_pins.go`,
`page_pins_service.go`, `page_pins_handler.go`, `page_pins.templ`). The
campaigns plugin's `pinned_pages` home block only loads
`GET /campaigns/:id/pinned-pages` into place, so it never reads pages itself.
The widget shows the pages the Director pinned for everyone (`page_pins`;
migration slug `page_pins`, package `pinschema`) as cards, then the viewer's
own pins as rows. A member's own pins are the pages they starred: the star
beside a page's name, the same `entity_favorites` rows the sidebar's
Favorites shows, so there is one way to keep a page, not two.

- **Who sees what is `PagePinService.ForViewer`'s decision.** Every page goes
  through `FilterViewableEntityIDs` for the viewer, so a page they can't open
  is left out without a trace; a page pinned for everyone isn't listed again
  under their own; at most 12 of their own are drawn and the rest counted.
  A Director looking as a player gets what a player gets and no Director
  controls. An empty widget tells the Director how to fill it and draws
  nothing for anyone else.
- **Pinning for everyone** is the Director's (owner or granted co-Director):
  the quiet pin icon beside a page's name (`pagePinMount`, loaded on sight
  for the Director's team only) and the × on a card. At most `MaxSharedPins`
  (12). The × on a member's own row takes their star off.
- **Degraded:** without the `page_pins` table the pin icon is not offered and
  the widget shows each member's own pins only.
- **Routes:** `GET /campaigns/:id/pinned-pages` (public-capable, narrowed per
  viewer), `GET`/`POST /campaigns/:id/entities/:eid/pin` and
  `DELETE /campaigns/:id/pinned-pages/everyone/:eid` (Director),
  `DELETE /campaigns/:id/pinned-pages/mine/:eid` (Player+).

## Named page layouts

A category keeps its main layout (`entity_types.layout_json`) plus up to
`MaxPageLayouts` (8) named layouts; each page wears one (`page_layouts.go`,
`page_layouts_repository.go`, `page_layouts_service.go`,
`page_layouts_handler.go`). Tables `entity_type_page_layouts`,
`entity_page_layouts` (see `.ai/data-model.md`; migration slug `page_layouts`,
package `layoutschema`; while degraded every category has only its main layout).

- **Worn layout** is `PageLayouts.WornKey`: the Director's pick for the page,
  else (player character, claimed or playable) the layout the category starts
  claimed pages on, else the main one. A pick since removed falls back.
- **Drawing:** `prepareShowFor` calls `wornLayout`, which hands the page a copy of
  its category carrying the named layout's blocks and records the choice in the
  context. A page on a named layout is drawn from it even where a game system would
  draw the whole page (`NamedLayout`, `wearsNamedLayout`); the system's sheet is
  then the `game_system_sheet` block.
- **Picking:** the chip beside the name (`page_layout_chip.templ`,
  `static/js/page_layout_chip.js`), Director team only and never while viewing as a
  player, sends `PUT .../entities/:eid/layout`. A category's layouts are arranged
  in Customize > Page layout (`customize_page_editor.js`), saved by the draft's
  `categories` item `page_layouts`, whose blocks are checked like the main layout's.
- **Elsewhere:** the AI outline groups a category's pages by layout and `read_page`
  names it (Director only); the prompt lists each category's layouts and import
  takes `layout:`; campaign export carries both tables.

## Family tree block

`family_tree` is a page block (one per page, tile sizes 4x1 and 2x1;
`family_tree_block.templ`, `static/js/family_tree.js`,
`static/css/family_tree.css`): a page's parents, children and partners from its
entity relations. At rest one line of circles; a click opens the tree over the
page; Close or Escape folds it. Nothing is stored: the tree is read per page draw
and the block has no route or migration of its own.

- **Relations that count** (`familyRelations`, `family_tree.go`; trimmed,
  lower-cased type from the reading page's side): `parent of`/`child of`,
  `adoptive parent of`/`adopted child of`, `guardian of`/`ward of`, `married to`/
  `spouse of`/`partner of`. Only the first pair is in the Relations block's
  suggestion list. Siblings are pages sharing a parent. No gender is held, so the
  words are Parent, Child, Sibling, Partner.
- **`FamilyTreeService` alone decides who sees what.** A relative the viewer cannot
  open (`FilterViewableEntityIDs`) is not read past, named or counted, and a
  `dm_only` relation is not followed, so a player's JSON holds no trace of either.
  The Director gets them marked `DMOnly` (amber edge, DM tag). "View as player"
  hides the same in script (`html[data-view-as-player]`). Never add a second
  decider.
- **Bounds:** `MaxFamilyGenerations` 4 each way (read one further to know whether
  the family goes on), `MaxFamilyPeople` 60 (nearest first), `maxFamilyReads` 120.
  `CutGenerations`/`CutPeople` say which bound cut someone, and the block says so.
  A relative the walk did not read (`Read` false) gets "Open page" but no "Make
  centre".
- **Wiring:** relations via the `FamilyLinks` interface
  (`internal/app/family_tree_adapters.go`), pages via `PageCards`, visibility via
  the entity service; no other plugin's repository is read.
  `registerFamilyTreeBlock` is in `internal/app/routes.go`.
- **Edit tab** (`family_edit.go`, `family_edit_handler.go`): the Director (owner or
  granted co-Director, not a Scribe) adds and removes parents, children and
  partners and saves together. `FamilyEditService` checks `FamilyActor.IsDirector`
  on every call, and the routes (`GET .../entities/:eid/family/candidates`, `POST
  .../entities/:eid/family`, `RequireFamilyDirector`) check again. Writes go
  through `FamilyWriter` (`family_tree_adapters.go`, over the relations service, so
  both rows of a pair are written and removed as the Relations block does, and
  relation events and the Foundry change feed see them). A parent link is written
  from the child as `child of`/`parent of`, `adopted child of`/`adoptive parent of`
  or `ward of`/`guardian of`; a partner link as `partner of` both ways. New links
  are not DM-only.
- **A save is all or nothing.** Order: create pages (entity service create path,
  campaign default visibility, character category else first enabled), then
  removals, then additions. A failed write takes back what the save already wrote;
  the result says which edits did not save, whether the takeback worked, and flags
  any pair left half-written (`halfWritten`). A created page is never deleted (the
  retry reuses it). A page cannot become its own ancestor. Caps: `MaxFamilyEdits`,
  `MaxFamilyNewPages` per save.
- **Picker:** at most `FamilyPickerMax` pages the Director can open, narrowed by
  `?q=` through the sidebar's list and search. Not a partial-update endpoint
  (`internal/patch` does not apply): a save names the links to add and remove.
- `relations.CommonRelationTypes` is not extended with family types: it is served
  to the Foundry module (`GET /api/v1/campaigns/:id/relations/types`), so that
  would change the contract.

## Pages by era

The calendar plugin stores versions and picks the current era (`EraVersionService`,
`internal/plugins/calendar/.ai.md`); this plugin reaches it through `EraPages`
(`era_pages.go`, wired in `internal/app/era_pages_adapter.go`).

- **Readers** see the page as its version for the current era when it has one
  (`withEraVersion`: name, picture, text, changed fields over the usual ones);
  hover cards and peeks too (`currentEraEntity`). Players get no era controls; the
  era routes answer NotFound for any era but the current one unless the viewer is
  the Owner or a granted co-DM (`CanAuthorDmOnly`). Pages a game system draws keep
  their usual self.
- **Eras panel** (`era_panel.templ`, `static/js/widgets/era_pages.js`, loaded on
  sight): the Eras button by History opens a ribbon of the main calendar's eras
  ("now", a dot where the page has a version). `?era=<id>` or `?era=usual` swaps
  the page in place. Highlights (default) show marked words, "Added" paragraphs, a
  dashed note for removed paragraphs (`EraDiff`, `era_diff.go`), "Changed in this
  era" on the picture, and "Usually X" under changed fields. `hl=0` is editing: the
  editor, attributes and picture widgets save to the version's routes, and the
  panel adds the era name, "Use the usual picture" and Remove version. A non-DM
  Scribe sees that their edits change the current era's version, the only one they
  may write. The Edit name fold always renames the usual page.
- **Routes** (`era_handler.go`): `POST`/`PATCH`/`DELETE
  /campaigns/:id/entities/:eid/eras/:eraID` make, rename/re-picture and remove a
  version (make and remove are the GM's). `GET`/`PUT .../eras/:eraID/entry` and
  `.../fields` mirror the usual routes' shapes (secrets stripped for anyone but
  owner and Co-DMs, same clash answer; the fields read adds `era_changed` for the
  GM). `PUT .../eras/:eraID/image` takes the picture widget's body. A fields save
  keeps only values that differ from the usual page (`eraFieldChanges`).
- **Moon chip:** a moon's lore page shows the moon and tonight's phase under its
  name, linking to the calendar (`PageMoons`, `page_moons.go`).

## Page Files section

Every page ends with a "Files" section drawn by media (`media/page_files.templ`,
see its `.ai.md`). This plugin only mounts it: `pageFilesMount` in
`page_extras.templ` is an `hx-get` placeholder for
`/campaigns/:id/entities/:eid/files?first=1`, for campaign members, after the
layout and character-items panel. Visibility and edit rights follow the page:
media asks `FilterViewableEntityIDs` (which leaves out the Trash) and
`CheckEntityAccess` through an adapter in `internal/app/routes.go`. It is not a
layout block, so an owner cannot place or hide it.

## Field-change observer

`SetFieldChangeObserver` takes a `FieldChangeObserver`. After a successful custom
fields write, in `UpdateFields` (used by `MergeFields` and the attributes widget)
and in `Update` when `FieldsData` was part of the write, the service calls
`FieldsChanged(ctx, entity, oldFields, newFields)`. An observer error is logged,
never returned. Another plugin hooks in from `internal/app`; this plugin names
none. Web field writes mark the context `changesource.KindWeb`
(`webWriteContext`).

## Sidebar navigation

The sidebar drill panel: the slide-over category view with entity tree, folders,
favorites and search. A category row opens it (campaigns `.ai.md` > "Sidebar
navigation").

- **Dual-Parent Model:** two mutually exclusive parent refs — `parent_id`
  (CHAR(36) FK->entities) and `parent_node_id` (CHAR(36)
  FK->sidebar_nodes, a folder). One set means the other must be NULL,
  enforced in `ReorderEntity()`; `static/js/sidebar_tree.js`'s tree
  builder resolves both.
- **Sidebar Nodes (pure folders):** `sidebar_nodes` stores organizational
  folders with NO entity record (CRUD routes: see Routes above). The create,
  rename and delete handlers call `FolderService` (folder_service.go), which
  also checks the category and parent belong to the campaign. Deleting a
  folder moves its sub-folders up to its parent and its pages to the top
  level of the category; it deletes no page.
  **Footgun — keyed by the CATEGORY type, exact-match on reload:** a
  node's `entity_type_id` must be the drilled category's own type
  (`?type=`), since `SearchAPI` reloads via
  `ListByType(campaignID, typeID)` (exact match) while the drill listing
  rolls up sub-types (`expandTypeIDsForListing`), so
  `results[0].EntityTypeID` can be a **sub-type**. The row menu's "New
  folder" (`sidebar_row_menu.js`) scopes a new folder from the tree's
  `data-entity-type-id`, which MUST be the category type or the node
  orphans under a sub-type, never returning on refresh. `SidebarEntityList`
  resolves it via `sidebarTreeType()` (prefers `typeID`; row/node fallback
  only when `typeID<=0`). Pinned by `sidebar_list_test.go`.
- **Sidebar order:** each list in the tree (a category's top level, a
  folder, a page with pages under it) sorts A to Z, by hand or newest
  first; folders always lead. `sidebar_child_orders` holds the lists that
  are not A to Z (`ChildOrderRepository`, sidebar_order.go), read by
  `FolderService.ChildOrders` and drawn as `data-root-order` /
  `data-child-order`; rows carry `data-created`. By hand follows
  `sort_order`. A Scribe moves a row by dragging it, with its arrows,
  Alt+Up/Down or the row menu (dropping a row on a folder files it there); `PUT /sidebar-order/move` names the neighbour to pass, not an
  index, so siblings the mover cannot see keep their places, and the whole
  sibling set is renumbered (`placeNextTo`). A page of one sub-category
  cannot be placed among another's pages: each keeps its own numbering.
  Pinned by `folder_service_test.go`, `sidebar_list_test.go`,
  `sidebar_tree_sort.test.mjs` and `sidebar_tree_order_browser.test.mjs`.
- **Favorites:** `entity_favorites` stores per-user, per-campaign
  bookmarks (routes: see Routes above). They are also each member's own pins
  on the home's Pinned Pages widget (see "Pinned pages").
- **Tag Filtering:** the search API's `?tags=slug1,slug2`, AND-logic via a
  subquery with `HAVING COUNT(DISTINCT)`.
- **Lazy Loading:** 50 entities/page; a "Load more" sentinel renders when
  `total > len(results)`, and a JS IntersectionObserver auto-triggers
  next-page fetches.
- **DM-only marks:** for the DM team (`visibilityGlanceVisible`) a page set
  to DM-only gets a lock on its sidebar row (`sidebarDMOnly`; not on every
  row of a DM-only category) and a "{GM} team only" label beside its name
  (`dmOnlyTitleLabel`, both page headers). The label is always rendered for
  the DM team, hidden unless DM-only, so `permissions.js` can show or hide it
  when the corner control saves. Players get neither (ADR-055 rule 3).
- **Sidebar config model:** ONE stored model
  (`campaigns.SidebarConfig.Items`) with ONE editor
  (`static/js/sidebar_editor.js`, pencil-triggered inline edit).

## Business rules

- **Content templates.** A new page copies its Content Template's JSON. The four
  built-in templates (seeded per campaign by `SeedDefaults`) are headings plus
  empty prompt lines (see the editor's `templatePrompt`). `ReconcileTemplatePrompts`
  runs at boot and swaps any built-in template still exactly as first seeded
  (`template_prompts_legacy.go`) for the prompt version; edited ones are left.
- **Side columns follow the reader.** Layout rows/columns carry `data-page-row` /
  `data-page-col` inside `[data-page-frame]` (`show.templ`). `static/js/page_sides.js`
  keeps each column at least 120px shorter than the row's tallest one in view while
  scrolling (`position: sticky`, md and up); a column taller than the view sticks
  once its bottom shows. Pinned by `test/js/page_sides.test.mjs`.
- Names are non-empty, max 200 chars. Slug is generated from the name,
  deduplicated with -2/-3, unique per campaign. The entity type determines the
  profile/edit fields; dynamic fields parse from form params `field_<key>`.
- Private entities are filtered in SQL from lists; Show returns 404, not 403.
- FULLTEXT search on name (BOOLEAN MODE), LIKE fallback under 4 chars.
  Deleting cascades via FK.
- **A Scribe sees what players see** (ADR-070). Hidden pages, GM-only fields,
  secrets and Adventures belong to the owner and Co-DMs (`CanAuthorDmOnly`, or
  `VisibilityRole() >= RoleOwner` where a role is passed). A Scribe keeps write
  access limited to what they are served (`hidden_parts.go`):
  - Every Scribe write route on `/entities/:eid` runs `requirePageWrite` after
    `RequireRole(RoleScribe)`: a page they cannot see is 404; one they can see but
    not edit (custom permissions) is 403. The description and picture saves open
    to players, so they run `requireOwnPageOrPageWrite`: same check for Scribes,
    `authorizeOwnPageWrite` for players.
  - Text with secrets is read-only to them: entry and player-notes reads add
    `locked: true`, the editor shows a lock note, and saves (including the legacy
    form `PUT /entities/:eid`) refuse with 403 or keep the stored text.
  - A fields save keeps stored GM-only and owner-only values
    (`keepRestrictedFields`); a `fields_patch` drops those keys
    (`dropRestrictedFields`).
  - Their new pages are always open to players (`NewPagePrivacy`); they cannot
    create, change into or bulk-move into Adventures (`requireCreatableType`), and
    bulk hide/show is refused.
- **Adventures** (`preset_category = 'adventures'`; every seed list carries it) is
  invisible to anyone but owner and Co-DMs in every read: pages vanish from lists,
  search, counts, mentions, relations, backlinks and ancestors whatever their own
  visibility or grants; the category home and every page endpoint answer 404; the
  category is left out of category lists, the sidebar and its websocket events.
  It cannot have kinds, and `CreateEntityType` refuses the reserved marker. New
  campaigns are seeded with it, import restores it via `EnsureAdventures`, and no
  route adds it to an existing campaign.
- `GET .../entities/:eid/sheet` renders an Adventures page's body with no site
  chrome (`EntitySheet`, sharing `entityPageBody` with the full page, and
  `prepareShow` with `Show`) for the DM Screen overlay. 404 for anyone but owner
  and Co-DMs and for any page outside an Adventures category (`sheet_test.go`).
- The profile page composes widgets: title, editor (TipTap, `data-widget="editor"`,
  view/edit toggle), tags, attributes (`data-widget="attributes"`), relations.
- **Pages that link a note** (`PagesLinkingNote`, for the Journal's backlinks):
  `pagesLinkingNoteWhere` scopes by campaign and applies `visibilityFilter`; for a
  viewer who does not read inline secrets, a page whose only `[[link]]` sits inside
  one is left out. Only names leave through the notes adapter, never a body.

## Player Character Claiming

Links player-owned entities to campaign members. Gated by the
`player-character-claiming` addon; existing campaigns default off.

- **`entity_types.claimable BOOLEAN NULL`** (migration 000029): NULL falls back to
  a legacy heuristic (`preset_category == "character"` or slug `*-character`);
  TRUE/FALSE is the Owner's override (`isClaimableType`). A player-character
  sub-type (`PresetCategory`/slug `player_character`/`player-character`) requires
  the addon (`CreateEntityType` via `AddonChecker`) and defaults `claimable=true`.
  ADR-039: both the sub-type and the legacy heuristic stay supported.
- **UI** (needs `addon-enabled(player-character-claiming)` AND
  `isClaimableType(type)`, never on an NPC's page: `isNPCPage`, an unclaimed,
  unplayable page of a type on the NPC list; the owner's Playable mark moves it to
  the party): (1) `claim_banner.templ`: "Claim this character" (Player+) when
  unclaimed, else "Claimed by &lt;name&gt;" (via `memberLister`, fallback "a
  player"); (2) the Characters page's Players box; (3) a per-type "Players can claim
  entities of this type" checkbox in Customize's Add-Category form, default true
  when the addon is on.
- **Audit:** `entity.claimed`, `entity.owner_changed` (details: `new_owner_id`,
  `new_owner_name`, or `cleared: true`).
- **API:** `POST .../:eid/claim` (Player+): idempotent if already the caller's,
  409 if someone else's, 400 if the type isn't claimable or the page is an NPC's.
  `ClaimOwner` writes only if the page is still unowned or the caller's, so of two
  simultaneous claims one gets 409. `PUT .../:eid/owner` (Scribe+) body
  `{"owner_user_id": "user-uuid-or-null"}`: validates membership; 200 no-op if
  unchanged.

`GET /campaigns/:id/characters` (public-capable: signed-out visitors of a public
campaign see only what visibility allows; owner names and member-only links are
hidden from non-members) -> `Handler.Characters` -> `CharactersPage`/
`CharactersContent` (`characters.templ`), the campaign-wide "who's who". A "Yours"
band (the viewer's own characters, any type, `ListByOwner`) sits on top, then two
addon-gated bands; the page 404s when neither addon is on. `GET /me` redirects
here. The owner picks which page types each band shows (`character_lists.go`); the
owner's page has an Add button and a chip with an x per type, opening boxes in
place (`.ag-fold`, inline handlers from `cast_onclick.go`, no modal) and posting to
`POST /campaigns/:id/characters/lists` (owner only), answered with the refreshed
`#cast-content`. A band with no chosen type is hidden from everyone but the owner.

- **Players section** (`player-character-claiming`, `view.ShowPlayers`): every
  claimed character of a listed type: `service.ListClaimed` (`owner_user_id IS NOT
  NULL` + `visibilityFilter`) unioned with the viewer's unfiltered `ListByOwner` (a
  player sees their own PC even if private), de-duplicated and viewer-first by pure
  `assembleCastParty(...)`, narrowed by `filterCastByType`. The viewer's cards get
  a "You" ribbon and accent ring.
- **Players box** is `view.Roster` (Scribe+, addon on), opened by the Party head's
  "Players" button. Characters on it are listed-type ones that are `playable` OR
  owned (`service.ListRoster` -> `ListOnRoster`, name order, 500 cap), so same-type
  NPCs stay off. `entities.playable` (migration 000054) is the per-character mark;
  `UpdateOwner` with a non-nil owner sets it in the same statement (clearing an
  owner keeps it), so a claimed character joins by itself and an unclaimed one
  lands in **Free to pick**. The box (`players_box.templ`, `players_box.go`) has a
  row per Player-role member (plus any other member owning a roster character) with
  chips that unclaim, then Free to pick chips whose x takes a character off the
  list. One `.pw-find` finder moves under the Give or Add button that opened it
  (`castFinderJS`) and searches through htmx. `view.Pickable` is, for a member with
  no character, the playable unclaimed ones they can see; it draws "Pick your
  character" above the Party (`castPickBox`), whose Yes posts the ordinary claim
  with `from=characters` so the answer is the page body and a notice, not a
  redirect. Routes (all 404 with the addon off, all Scribe+): `POST
  /characters/owner` (entity_id, owner_user_id; "" unclaims; owner must be a
  member), `POST /characters/playable` (entity_id, playable 1/0; marking needs a
  claimable type, unmarking never does), `GET
  /characters/players/search?q=&for=<user id|free>` (HTML rows, max 8,
  `rosterFinderResults`; `SearchRoster` filters in SQL, free-to-pick first then
  name). Giving with nothing typed lists only free characters; adding with nothing
  typed lists none; a name searches every listed-type character the viewer can see,
  skipping what the player already plays (give) or anything playable or owned (add).
  The POSTs answer with `#cast-content` carrying `view.Notice`, box left open
  (`view.Open = "players"`). `ClaimEntity` itself is not limited to playable pages.
- **NPCs section** (`npcs` addon) comes from npcs, not this plugin: `entities`
  defines `NPCSectionProvider` (a `templ.Component` from `npcs.Handler.NPCSection`),
  injected via `SetNPCSectionProvider` so core never imports the addon. npcs renders
  a featured portrait row (tag `CastTagSlug` = `cast`) above the revealed list with
  a DM reveal/hide toggle. `GET /npcs` redirects to `GET /campaigns/:id/characters`.
- **Cards** are real links (work without JS); the corner "quick look" button is
  enhanced by `static/js/characters.js` into the dynamic-surface frame's mini->full
  launch. **It mounts from the plugin body-script registry, NOT `characters.templ`**:
  a boosted navigation strips `<script>` tags from the swapped `#main-content`
  (`allowScriptTags=false` in boot.js), so an embedded script would only wire on a
  direct load. Mechanism in `characters_boosted_nav_test.go`'s header; ratcheted by
  `tools/check-page-scripts.sh`.
- Nav: the `characters` entry of `navAppCatalog` (`internal/app/routes.go`), shown
  when either addon is on. No migration (reuses `owner_user_id` + tags).

## Hero creator

`GET /campaigns/:id/characters/new` (Player+): one paper page per step and, for the
entry being read, a pull-out leaf. `static/js/hero_creator.js` mounts on
`[data-hero-creator]` from the plugin body-script registry, fetches steps from
`GET .../characters/new/plan`, and posts the hero as `POST .../characters/new`
`{name, picks: {fieldKey: {name, options}}}`, answered `201 {id, url}`. The
Characters page shows "Create hero" when `CastView.CanCreateHero`.

- **Steps** come from `HeroPlanner`, filled by the composition root from the
  systems plugin (`internal/app/hero_planner_adapter.go`): each text field of the
  system's character preset that has entries (package or campaign-made), in preset
  order. This plugin never reads a package.
- **Who:** Scribe+ make heroes for the table. A Player may make their own (which
  they then own) when the owner enabled `player-character-claiming`, the hero's
  page type is claimable, and they own no character page yet: one at a time
  (`heroAccessFor`). The page type is the owner's listed character type the system
  marks as its character, else the player-character type, else the first listed
  (`pickHeroType`); a Player only gets a claimable one.
- **Saved:** each step's field holds the chosen entry's NAME (as the sheet and
  Foundry expect). For an entry with a buy list (`{name, cost}` items plus a
  positive `*_points` number, `heroBuyList`), purchases are a JSON array of names in
  `<field>_choices_json`. The server checks every pick against the plan: unknown
  steps, entries or options, duplicates and overspending are refused. Privacy
  follows the campaign's new-page default.
- The draft lives in `localStorage` (`chronicle:hero-draft:<campaign>`) until the
  hero is made. Narrow screens show the leaf over the page; Calm fades it.
- **Look:** follows the campaign's Customize card look (`html[data-cz-hover]`):
  Paper by default, Plain and Compact on site theme colours, Night in ink and gold.
  "Your own entries" is a tool and always takes Plain tokens (`.hc--tool`). Only
  paper tokens change, in `static/css/hero_creator.css`.

### Hero builder

On the Characters page, `heroBuilder` in `characters.templ` mounts
`data-widget="hero-builder"` (loaded on sight, ADR-063) when the viewer has heroes
of their own or may make one (`CastView.Builder`, `buildHeroBuilder`). Each hero
reads as a sentence ("Tess's ancestry is [..], class is [..]") with a blank per
plan step; a blank opens a panel listing every entry with roll range, facts and
text (under the hero on a phone).

- **Heroes** are the viewer's own pages of a listed character type
  (`builderHeroes`). For anyone but owner and Co-DMs, fields the type or page marks
  GM-only are left out of the sentence and the mount data.
- **Saving:** a pick on an existing hero is `PUT .../entities/:eid/fields`
  `{fields_patch: {key: name}}` through the builder-step door in `identity_edit.go`;
  a refused save restores the blank. Roll everything left sends one patch; Undo
  sends the earlier values (null clears). A new hero keeps picks in `localStorage`
  (`chronicle:hero-builder:<campaign>`) until Make this hero posts to the creator's
  `POST .../characters/new`.
- **A new hero's sentence** stays folded until the page's Create hero
  (`data-create-hero`) unfolds it; Not now refolds and keeps the draft; a draft
  reopens it next visit. With no heroes and nothing unfolded, the mount is hidden.
- **Rolling:** up to ten entries use a d10, longer lists percentile dice, each entry
  owning an even share of faces. Dice go through `Chronicle.dice.roll` when present;
  without it, or if it refuses, faces are drawn at once.
- **Plan** (`GET .../characters/new/plan`) is readable by a Player who may make a
  hero or owns a character-type page (`mayReadHeroPlan`).
- Bought options (`<field>_choices_json`) are chosen only in the creator.

### Your own entries

`GET /campaigns/:id/characters/entries`: a Director adds the campaign's own
entries to the creator's pick lists; a site-look page with a tab per step. A player
who may read the plan opens it too, limited to lists a Director let them write in
(`?field=` opens a tab; `?for=` names their hero, whose sheet takes the new entry's
name; `?back=new` links back to the creator). The Rules page's top bar links it for
Directors who may edit the book (`static/js/widgets/rulebook.js`).
`static/js/own_entries.js` mounts on `[data-own-entries]`, reads steps and the
system's entries from the creator plan (Directors may read it without being able to
make a hero), and reads/writes the campaign's entries through the systems plugin's
`/campaigns/:id/system-entries` API, which enforces the Director rule and validates
every list.

- **Editor** grows over the page from the clicked row: form left, the player's
  creator view right (points can be test-spent). Unsaved writing asks before
  being dropped.
- **Form shape** (`shapeOf`): fact lines for scalar properties at least half the
  system's own entries share; a list section for each list of named items at least
  half carry (items with a cost are bought from); and the `*_points` budget. Facts
  save under a snake_case key, numbers as numbers; lists save only named items.
  Problems the server would refuse block Save; an unspendable budget warns.
- **Text** is server-sanitized HTML; "Hide from players" wraps a passage in
  `<span data-secret>`, which players never receive.
- **Player-made entries:** under each list a Director lets a player write one entry
  with the points budget, renews a used permission or takes it back. A player's entry
  shows Draft or Waiting for you; opening a handed-in one offers Ask for changes
  (with a note) and Accept (with who sees it). The player's editor has no hidden
  passages, a locked budget, Save draft and Hand it in, and shows the Director's
  note. The creator and the sheet's pick list link here when the player may; the
  creator keeps a picked draft for the hero it makes.
- **Paste from an AI** reads the AI Import format (YAML front matter, then text)
  into the form for checking; nothing saves until Save. "Copy the guide" copies that
  format with the pick list's shape and one of the system's own entries as a model.

## `contents` block

A core layout block (`Type: "contents"`, `Contexts: ["template"]`, `Singleton`, no
tile sizes; `registerContentsBlock`). No route, table or setting: the server renders
an empty shell (`blockContents`), and `static/js/page_contents.js` (widget
`page-contents`, loaded on sight via the entities registration in
`internal/app/routes.go`) reads the `h1`-`h3` headings of the page's rich-text
editor from the viewer's own rendered page, so a viewer only gets headings their
page shows (an all-Director heading arrives empty for a player and is skipped; one
wholly in a `[data-secret]` mark carries the DM tag for the Director). Fewer than
four headings draws nothing.

- **Rail or button is decided by room beside the sidebar.** `placement()` takes the
  page area's rect (`#main-content`), the sidebar's rect and the window. The rail
  sits at the page area's left edge + 8px, never left of the sidebar's right edge
  (open 256px, folded 48px, hidden 0, and while sliding via a `ResizeObserver` on
  both). While a rail is wanted the script adds `ct-railed` to `#main-content`,
  reserving a 40px gutter. When the area cannot hold the gutter plus 520px of text,
  or the window is 767px or narrower, the block is a labelled Contents button
  instead. The panel is `position: fixed` from the area's left edge in both modes.
- `destroy` removes `ct-railed`, so a boosted navigation (which keeps
  `#main-content`) leaves no gutter.
- Every shell handler is an inline IIFE (`contentsCall`); a test pins that each
  named handler exists in the script. Tests: `test/js/page_contents.test.mjs`,
  `contents_block_test.go`.
- The editor's own "On this page" outline (`editor_outline.js`, with
  `data-outline`) is separate; a page with both shows both.

## `character_surface` block

A layout block (`Type: "character_surface"`, `Contexts: ["template"]`, `Singleton`,
`block_registry_core.go`) and the default layout for player-character types:
`CreateEntityType` gives `isPlayerCharacterType(...)` types `CharacterLayout()`
(`model.go`) instead of `DefaultLayout()`. Owners can customize it in the layout
editor.

- **Server** (`character_surface.go`, `character_surface_block.templ`):
  `blockCharacterSurface` emits `<div data-widget="dynamic-surface">` + an inline
  `<script type="application/json" data-surface-schema>` from
  `CharacterSurfaceSchemaJSON(entity, entityType, campaignID, csrf, canEdit,
  canSeeGM, isOwner, pictureEndpoint)`: data seeded (no extra fetch),
  `json.Marshal`-escaped. `canEdit` is `canWriteDescription`, so the claimed
  owner's description box opens editable. `pictureEndpoint`
  (`surfacePictureEndpoint`, empty unless `canChangeOwnPage`) makes the
  `char-header` portrait the `image-upload` widget's picker.
- **Client** (`static/js/widgets/character_surface.js`, after `dynamic_surface.js`):
  registers box renderers `char-header`, `char-attributes`, `char-entry`; a System
  can override by re-registering the names. The surface is usually built before
  these register, so the frame paints such boxes when their renderer arrives.
- **Security:** the description box mounts the standard `editor` widget rather than
  inlining `EntryHTML`, which would bypass role-aware secret stripping.
- **Auto-premake on addon enable** (`EnsurePlayerCharacterType`; doc comment has the
  three cases): idempotent, only nests/creates, never touches existing data. Wired
  from `addons.EnableForCampaign` -> `ApplyAddonEnableEffects`, replayed by the
  startup backfill (`internal/app/backfill.go`). Tests: `ensure_pc_type_test.go`.
- **Duplicate reconciliation** (`MergeDuplicatePlayerCharacterType`; doc comment has
  the mechanism): handles what migration `000030` (kept permanently: deleting an
  applied migration crash-loops boot, ADR-044) does not auto-merge, surfaced by the
  player-character SetupProvider (`addons/.ai.md` "Setup Provider framework"). Calls
  `MoveEntitiesAndDeleteType`, which reassigns `entity_type_id` before deleting
  (mandatory: ON DELETE CASCADE). Idempotent. Tests: `merge_duplicate_pc_test.go`,
  `pc_setup_snapshot_test.go`.
- **One home for characters** (`AdoptDefaultCharacterType`,
  `ReconcileCharacterPresetHome`, `MoveCharacterPresetHome`): a system's character
  preset lives on the seeded top-level Characters type, not a twin. New installs
  adopt Characters; the boot sweep moves the sheet off an empty twin; a twin that
  holds pages is the owner's call, offered as the "home" step on the
  player-character setup page, which moves its pages (Trash included) and disables
  it with `claimable` false, never deleting it. Tests:
  `character_preset_home_test.go`, `app/setup_pc_test.go`.
- **Field reconcile in place** (`ReconcileEntityTypeFields`): lets a system pack add
  fields to an existing type; `mergeNewFields` appends declared fields whose `Key`
  is absent (never overwrites a user edit), persisted via `UpdateEntityType`, driven
  by `ApplySystemPresets` on install/update. Type schema only. Tests:
  `reconcile_fields_test.go`.
- **Single-owner duplicate guard** (`CreateEntityType`): one type per
  preset-category; a manual PC-type request when one exists gets `Conflict`, on top
  of the addon gate.
