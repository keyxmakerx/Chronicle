# Entities Plugin

Core plugin, always enabled — the heart of Chronicle: universal entity
system with configurable types, dynamic fields, full-text search, nesting,
and a rich profile page.

## Critical footgun

All `entity_types` SELECT queries MUST route through `entityTypeColumns` +
`scanEntityType(rowScanner)` in `repository.go` — never a bespoke
SELECT/Scan per method. All six list/find methods route through it; the
scan binds *by position*, so a mismatch panics at runtime, not build.
`TestEntityTypeRepository_Integration` is the live-DB guard.

## Domain Concepts

- **Entity**: a worldbuilding object — name, type, entry, configurable
  fields; everything is an entity.
- **Entity Type**: a per-campaign template for an entity's fields.
  Defaults ship pre-configured and are GM-customizable (7 defaults, see
  Business Rules).
- **Fields Definition**: JSON array on `entity_types` — field key, label,
  type, options, display section.
- **Fields Data**: JSON object holding an entity's field values.
- **Entry**: the rich text body (TipTap/ProseMirror JSON).
- **Player Notes**: player-facing content (`player_notes` JSON +
  `player_notes_html`), distinct from the entry (DM content); maps to a
  second Foundry Journal page.
- **Privacy**: `is_private` makes an entity visible only to Scribes/Owners;
  Players see 404. Owned end-to-end by the slide-in permissions card
  (`static/js/widgets/permissions.js`, writes via
  `PUT /entities/:eid/permissions`) — the edit form and metadata panel
  carry no `is_private` input. `UpdateEntityInput.IsPrivate` is `*bool` so
  handlers can pass `nil` to preserve the value; syncapi's wire side is
  `patch.Field[bool]`, not value-typed (its batch twin `syncChange`
  matches) — a bare bool once let a name-only rename bind `false` and
  publish a hidden entity to every player.

### `Update` is a PARTIAL update

| caller sends | stored value |
|---|---|
| field **absent** (`patch.Field` zero / `IsPrivate == nil`) | preserved |
| field present, **value** | replaced |
| field present, **explicit `null`** (or `""` on `type_label`/`parent_id`) | cleared |

`UpdateEntityInput`'s doc comment (`model.go`) has the full contract:
`Name`/`TypeLabel`/`ParentID`/`Entry` are `patch.Field[string]`;
`IsPrivate` stays `*bool` on the same contract, the permissions widget its
sole writer. `ParentID` needs an explicit `parent_id` member in syncapi's
update body and every AI-workspace commit-update (`""` can't express
"absent"), or the entity is silently detached. `Entry` keeps a legacy
`""`-means-preserve reading; explicit null still clears it. Pictures are
not on this input: `UpdateImage`/`UpdateCoverImage` are their only
writers, and both check the file belongs to the page's campaign.
Pinned by `entity_partial_update_test.go` and
`syncapi/entity_partial_update_test.go`.

- **Field-level visibility** (`gm_fields.go`'s package comment has the
  mechanism): two tiers, orthogonal to whole-entity privacy and to each
  other. `FieldDefinition.GMOnly` hides a field's VALUE from every
  Player-tier viewer including the claimed owner — a true GM secret.
  `FieldDefinition.OwnerOnly` hides it from everyone except GM-tier roles
  AND the claimed owner (`Entity.IsOwnedBy`) — private to one player, not
  a GM secret. Both come from a system manifest's `gm_only`/`owner_only`
  annotation, converged onto existing types by
  `SyncFieldGMFlags`/`SyncFieldOwnerOnlyFlags` (`internal/app/preset_applier.go`,
  which calls the entities service methods, at boot and on install/update). `FilterRestrictedFields` is the one call
  every fields_data egress point uses — server is the authority; a widget
  hiding its own box client-side (`data-is-gm`/`data-is-owner` in
  `show_renderer_registry.go`) is never the fix.
- **Optimistic Concurrency:** `expected_updated_at` on update requests
  triggers 409 Conflict if the entity was modified since that timestamp.

## Undo: history, Trash, save clashes

- **Trash (ADR-060):** `Delete` marks the page and its live sub-pages
  (`deleted_at`, one `trash_root_id`) instead of removing them, once
  `SetPageSafety` is wired; without it (unit tests) delete is permanent.
  Every read excludes trashed rows: `visibilityFilter` starts with
  `liveOnly` for every role, owners too, and reads that skip it add
  `liveOnly` themselves. Owners see the Trash at `/campaigns/:id/trash`
  (Manage > Trash); restoring puts a page whose parent is still trashed at
  the top level. `StartPurger` removes pages after the site's retention
  (`settings.TrashRetentionDays`, Admin > Storage > Trash).
- **History:** `entity_versions` keeps a page's title and text (not field
  values: sync clients change those constantly). Create records
  `created`; text or title saves record `edit`, joined into the author's
  last row within `versionCoalesceWindow`; the first save of a page older
  than history records a `baseline` of what it replaced; a restore records
  `restore`. 100 per page. Owners and scribes open it from the page's
  History button; players never see it.
- **Save clashes:** `entities.entry_rev` counts text changes.
  `GET .../entry` returns `rev` to editors; the editor sends it back as
  `base_rev` and `SaveEntry` writes only if it still matches, else 409
  `edit_conflict` with the stored text and who saved it. The editor then
  holds the save and offers: see their changes, keep both (mine on top),
  use mine. A save without `base_rev` behaves as before.
- **Who saved:** `withActorMiddleware` puts the signed-in user on the
  request context (`WithActor`); syncapi uses `WithSyncActor`, so Foundry
  and import saves are `sync` versions listed as "Sync or import". Saves
  with no actor are listed the same way.
- **Access:** History, restore and the entry PUT check `CheckEntityAccess`
  like the page itself, so a scribe never reads or restores a page hidden
  from them (a clash answer carries the stored text).
- **Page kinds:** a page kind with pages in the Trash can't be deleted;
  the error says how many are waiting.

## Field-change observer

`SetFieldChangeObserver` takes a `FieldChangeObserver`. After a successful write
of custom fields, in `UpdateFields` (which `MergeFields` and the attributes widget
use) and in `Update` when `FieldsData` was part of the write, the service calls
`FieldsChanged(ctx, entity, oldFields, newFields)` with the fields as they were
before the write. An observer error is logged, never returned: the write already
happened. Another plugin hooks in from `internal/app`; this plugin names none.
Web field writes mark the context `changesource.KindWeb` (`webWriteContext`).

## Sidebar Navigation System

Manages the sidebar drill panel: the slide-over category view with its
entity tree, folder nodes, favorites, and search. A category row in the
campaign sidebar opens it (see the campaigns `.ai.md` → "Sidebar navigation").

- **Dual-Parent Model:** two mutually exclusive parent refs — `parent_id`
  (CHAR(36) FK->entities) and `parent_node_id` (CHAR(36)
  FK->sidebar_nodes, a folder). One set means the other must be NULL,
  enforced in `ReorderEntity()`; `static/js/sidebar_tree.js`'s tree
  builder resolves both.
- **Sidebar Nodes (pure folders):** `sidebar_nodes` stores organizational
  folders with NO entity record (CRUD routes: see Routes above).
  **Footgun — keyed by the CATEGORY type, exact-match on reload:** a
  node's `entity_type_id` must be the drilled category's own type
  (`?type=`), since `SearchAPI` reloads via
  `ListByType(campaignID, typeID)` (exact match) while the drill listing
  rolls up sub-types (`expandTypeIDsForListing`), so
  `results[0].EntityTypeID` can be a **sub-type**. `sidebar_tree.js
  createGroupFolder` scopes a new folder from the tree's
  `data-entity-type-id`, which MUST be the category type or the node
  orphans under a sub-type, never returning on refresh. `SidebarEntityList`
  resolves it via `sidebarTreeType()` (prefers `typeID`; row/node fallback
  only when `typeID<=0`). Pinned by `sidebar_list_test.go` +
  `sidebar_tree_reorder.test.mjs`.
- **Favorites:** `entity_favorites` stores per-user, per-campaign
  bookmarks (routes: see Routes above).
- **Tag Filtering:** the search API's `?tags=slug1,slug2`, AND-logic via a
  subquery with `HAVING COUNT(DISTINCT)`.
- **Lazy Loading:** 50 entities/page; a "Load more" sentinel renders when
  `total > len(results)`, and a JS IntersectionObserver auto-triggers
  next-page fetches.
- **Sidebar config model:** ONE stored model
  (`campaigns.SidebarConfig.Items`) with ONE editor
  (`static/js/sidebar_editor.js`, pencil-triggered inline edit).

## Business Rules

- Entity names must be non-empty (max 200 chars)
- Slug auto-generated from name, deduplicated with -2/-3 suffix, unique per campaign
- Entity type determines the profile/edit form fields
- Dynamic fields parsed from form params (`field_<key>`)
- Private entities (`is_private=true`) are filtered at SQL level from
  lists; Show returns 404 (not 403) to avoid revealing existence
- FULLTEXT search on name (BOOLEAN MODE), LIKE fallback under 4 chars
- Deleting cascades via FK
- 7 default types seeded on campaign creation (via `EntityTypeSeeder`, see
  Dependencies): Character, Location, Organization, Item, Note, Event, Shop

## Player Character Claiming

Links player-owned entities to campaign members, so GMs see who plays
which character. Gated behind the `player-character-claiming` addon;
existing campaigns default to off.

- **`entity_types.claimable BOOLEAN NULL`** (migration 000029): NULL falls
  back to a legacy heuristic (`preset_category == "character"` or slug
  `*-character`); TRUE/FALSE is the Owner's override (`isClaimableType`).
  A player-character sub-type
  (`PresetCategory`/`slug` == `player_character`/`player-character`)
  requires the addon (`CreateEntityType` via `AddonChecker`), defaulting
  `claimable=true`.
- **UI surfaces** (gated on `addon-enabled(player-character-claiming)` AND
  `isClaimableType(type)`): (1) `claim_banner.templ` on the show page —
  "Claim this character" (Player+) when unclaimed, or "Claimed by
  &lt;name&gt;" (resolved via `memberLister`, falling back to "a player");
  (2) `category_owner_roster.templ` — Scribe+ owner overview, capped at
  100/category, reassign/unclaim both hitting the owner API below;
  (3) a per-type "Players can
  claim entities of this type" checkbox in the Customize hub/Add-Category
  form, defaulted true when the addon is on.
- **Audit:** `entity.claimed`/`entity.owner_changed` actions, human-readable
  in the activity feed; `owner_changed` details carry `new_owner_id`,
  `new_owner_name`, or `cleared: true`.
- **API:** `POST .../:eid/claim` (Player+) — idempotent if already owned
  by the caller, 409 if by someone else, 400 if the type isn't claimable.
  `PUT .../:eid/owner` (Scribe+) — body
  `{"owner_user_id": "user-uuid-or-null"}`, validates membership, no-op
  (200) if unchanged.
- **Design rationale (ADR-039):** owner-toggleable addon, per-type
  claimability, and both the dedicated sub-type and legacy heuristic stay
  supported so existing campaigns keep claiming on their "Character" type.

## Characters ("Cast") Page

`GET /campaigns/:id/characters` (public-capable view route: signed-out visitors of a public campaign see only what visibility allows; owner names and member-only links are hidden from non-members) -> `Handler.Characters` -> `CharactersPage`/
`CharactersContent` (`characters.templ`), the campaign-wide "who's who".
A "Yours" band (the viewer's own characters, any type, via `ListByOwner`)
sits on top, then two addon-gated bands; the page 404s when neither addon
is on. There is no separate "My Characters" sidebar row (`GET /me` still
renders the old page for old links). Which page types each band shows is
the owner's choice (`character_lists.go`); the owner's page carries an Add
button and a chip with an x per chosen type, which open boxes in place
(`.ag-fold`, inline handlers from `cast_onclick.go`, no modal) and post to
`POST /campaigns/:id/characters/lists` (owner only), answered with the
refreshed `#cast-content`. A band with no chosen type is hidden from
everyone but the owner.

- **Players section** (`player-character-claiming` addon,
  `view.ShowPlayers`) = every claimed character of a listed type:
  `service.ListClaimed`
  (`owner_user_id IS NOT NULL` + `visibilityFilter`) unioned with the
  viewer's own unfiltered `ListByOwner` (so a player sees their own PC
  even if private), de-duplicated and viewer-first via the pure
  `assembleCastParty(...)` (unit-tested), then narrowed by
  `filterCastByType`; the viewer's own cards get a
  "You" ribbon + accent ring.
- **NPCs section** (`npcs` addon) is contributed by npcs, NOT
  built here: `entities` defines `NPCSectionProvider` (a `templ.Component`
  from `npcs.Handler.NPCSection`), injected via `SetNPCSectionProvider` so
  core never imports the addon; npcs renders a featured portrait row
  (tagged `CastTagSlug` = `cast`) above the full revealed list with a DM
  reveal/hide toggle. The standalone `GET /npcs` gallery redirects to
  `GET /campaigns/:id/characters`.
- **Cards** are real links to the entity page (work with no JS); the
  corner "quick look" button is progressively enhanced by
  `static/js/characters.js` into the dynamic-surface frame's mini->full
  launch. **It mounts from the plugin body-script registry, NOT from
  `characters.templ`**: a boosted sidebar navigation strips `<script>`
  tags from the swapped `#main-content` fragment
  (`allowScriptTags=false` in boot.js), so an embedded script would only
  wire on a direct URL load. `characters_boosted_nav_test.go`'s header
  comment has the mechanism; ratcheted by `tools/check-page-scripts.sh`.
- Nav: the `characters` entry of `navAppCatalog` (`internal/app/routes.go`),
  shown when either addon is on. No migration (reuses
  `owner_user_id` + tags).

## Hero creator

`GET /campaigns/:id/characters/new` (Player+) draws the creator: one paper
page per step and, for the entry being read, a leaf that slides out from
under the page (the signed "pull-out leaf"). `static/js/hero_creator.js`
mounts on `[data-hero-creator]` from the plugin body-script registry and
fetches its steps from `GET .../characters/new/plan`; the finished hero is
`POST .../characters/new` with `{name, picks: {fieldKey: {name, options}}}`,
answered `201 {id, url}`. The Characters page shows "Create hero" when the
viewer may use it (`CastView.CanCreateHero`).

- **Steps** come from `HeroPlanner`, which the composition root fills from
  the systems plugin (`internal/app/hero_planner_adapter.go`): each text
  field of the system's character preset that has entries, package or
  campaign-made, in preset order. This plugin never reads a package.
- **Who:** Scribe and above make heroes for the table. A Player may make
  their own, which they then own, when the owner switched on
  `player-character-claiming`, the hero's page type is claimable, and they
  own no character page yet: one hero at a time (`heroAccessFor`). The page type is the owner's listed character type the
  system marks as its character, else the player-character type, else the
  first listed (`pickHeroType`); a Player only gets a claimable one.
- **What is saved:** each step's field holds the chosen entry's NAME, as the
  sheet and Foundry expect. When an entry has a list to buy from (a list of
  `{name, cost}` items plus a positive number under a `*_points` key, see
  `heroBuyList`), what was bought is a JSON array of names in
  `<field>_choices_json`. The server checks every pick against the plan:
  unknown steps, entries or options, duplicates and overspending are
  refused. Privacy follows the campaign's new-page default.
- The draft lives in `localStorage` (`chronicle:hero-draft:<campaign>`) until
  the hero is made. Narrow screens get the leaf over the page instead of
  beside it; Calm fades it instead of sliding.

## `character_surface` block — the player-character "big widget"

A real layout block (`Type: "character_surface"`, `Contexts: ["template"]`,
`Singleton`, in `block_registry_core.go`) and the default page layout for
player-character types: `CreateEntityType` gives
`isPlayerCharacterType(...)` types `CharacterLayout()` instead of
`DefaultLayout()` (`service.go`, `model.go:CharacterLayout`). A normal
registered block, so owners can customize it in the layout editor.

- **Server** (`character_surface.go`, `character_surface_block.templ`):
  `blockCharacterSurface` emits `<div data-widget="dynamic-surface">` +
  inline `<script type="application/json" data-surface-schema>` from
  `CharacterSurfaceSchemaJSON(entity, entityType, campaignID, csrf,
  canEdit)`: data seeded (zero extra fetch), `json.Marshal`-escaped.
- **Client** (`static/js/widgets/character_surface.js`, after
  `dynamic_surface.js`): registers box renderers `char-header`,
  `char-attributes`, `char-entry`; a System can override by re-registering
  the same names.
- **Security:** the description box mounts the standard `editor` widget
  rather than inlining `EntryHTML` (would bypass role-aware secret
  stripping), so secrets and edit-gating match every other entry block.
- **Auto-premake on addon enable** (`EnsurePlayerCharacterType`, doc
  comment has the three cases): idempotent, nests/creates only, never
  touches existing data. Wired from `addons.EnableForCampaign` ->
  `ApplyAddonEnableEffects`, replayed by the startup backfill
  (`internal/app/backfill.go`). Tests: `ensure_pc_type_test.go`.
- **Owner-driven duplicate reconciliation** (`MergeDuplicatePlayerCharacterType`,
  doc comment has the mechanism): handles what migration `000030`
  (retained permanently — deleting an applied migration crash-loops boot,
  ADR-044) doesn't auto-merge — ambiguous/later duplicates — surfaced by
  the player-character SetupProvider (`addons/.ai.md` §"Setup Provider
  framework"). Calls `MoveEntitiesAndDeleteType`: reassigns
  `entity_type_id` before deleting, mandatory since it's ON DELETE
  CASCADE. Idempotent. Tests: `merge_duplicate_pc_test.go`,
  `pc_setup_snapshot_test.go`.
- **Field reconcile in place** (`ReconcileEntityTypeFields`): lets a system
  pack add fields after a campaign's type already exists; `mergeNewFields`
  appends any declared field whose `Key` is absent (never overwrites a
  user edit), persisted via `UpdateEntityType`, driven by
  `ApplySystemPresets` on install/update. Type schema only. Tests:
  `reconcile_fields_test.go`.
- **Single-owner duplicate guard** (`CreateEntityType`): one type per
  preset-category, so a manual PC-type request when one exists gets a
  `Conflict`, on top of the addon gate.

## Notes

- The entity profile page (a Templ template) composes widgets: title,
  editor, tags, attributes, relations. The editor (TipTap) mounts via
  `data-widget="editor"` with a view/edit toggle; attributes via
  `data-widget="attributes"` for inline field editing.
- **Footgun — every paginated read here MUST end its `ORDER BY` in `e.id`**
  (`pagination_total_order_test.go`'s header has the mechanism: no leading
  sort column is unique except `uq_entities_campaign_slug`, so a walk to
  exhaustion can silently skip or repeat rows). Callers: the list page,
  the sync API's `ListEntities` + pull loop, both campaign-export
  walk-to-exhaustion loops. The test walks every `LIMIT ? OFFSET ?` query
  in `repository.go` and requires a tiebreaker.
- **Footgun — a public-capable route must authorize the `:eid`, not just
  the campaign.** `GET .../:eid/backlinks` carries the same campaign-match
  404 + `CheckEntityAccess` as `Show`, `GetEntry`, `GetFieldsAPI`,
  `PreviewAPI`, `GetAliasesAPI`; `FindBacklinks` pins `e.campaign_id = ?`
  as its first predicate via the pure `backlinksWhere` builder, mirroring
  `visibilityFilter`. `AllowPublicCampaignAccess` + `RequireViewAccess`
  authorize the campaign only — any new route under them must authorize
  the entity id itself.
- **Pages that link a note** (`PagesLinkingNote`, for the Journal's
  backlinks): `pagesLinkingNoteWhere` scopes by campaign and applies
  `visibilityFilter`, and for a viewer who doesn't read inline secrets a
  page whose only `[[link]]` sits inside one is left out. Only names leave
  through the notes adapter, never a body.
