# Entities Plugin

Core plugin, always enabled: pages ("entities") with configurable types,
dynamic fields, full-text search, nesting and the profile page.

## Footguns

- **`entity_types` SELECTs** MUST route through `entityTypeColumns` +
  `scanEntityType(rowScanner)` in `repository.go`. The scan binds by position,
  so a mismatch panics at runtime, not build. Guard:
  `TestEntityTypeRepository_Integration`.
- **Paginated reads** MUST end their `ORDER BY` in `e.id`: no other sort column
  is unique (except `uq_entities_campaign_slug`), so a walk to exhaustion can
  skip or repeat rows. Callers: list page, syncapi `ListEntities` + pull loop,
  both campaign-export walks. `pagination_total_order_test.go` requires a
  tiebreaker on every `LIMIT ? OFFSET ?` query in `repository.go`.
- **Public-capable routes authorize the `:eid`, not just the campaign.**
  `AllowPublicCampaignAccess` + `RequireViewAccess` check the campaign only. A
  new route under them needs the campaign-match 404 + `CheckEntityAccess`, as
  `Show`, `GetEntry`, `GetFieldsAPI`, `PreviewAPI`, `GetAliasesAPI` and
  `.../:eid/backlinks` have. `FindBacklinks` pins `e.campaign_id = ?` first
  through `backlinksWhere`, mirroring `visibilityFilter`.
- **Entity reads use `visibilityFilter` or `CheckEntityAccess`; category-level
  reads use `TypesForViewer`** (Adventures, below).

## Domain concepts

- **Entity**: a page: name, type, entry, fields.
- **Entity type**: per-campaign template of an entity's fields; 7 defaults
  (Character, Location, Organization, Item, Note, Event, Shop) plus Adventures,
  all GM-customizable. Seeded on campaign creation via `EntityTypeSeeder`.
- **Fields definition**: JSON array on `entity_types` (key, label, type,
  options, section). `link` and `rule` types read more than their stored value
  (`field_kinds.go`; "Link and worked-out fields").
- **Fields data**: JSON object of an entity's values.
- **Entry**: rich text body (TipTap/ProseMirror JSON).
- **Player notes**: `player_notes` JSON + `player_notes_html`, separate from the
  DM entry; maps to a second Foundry journal page.
- **Live refresh**: an update also publishes a content-free `page.changed`
  (`entityEventPublisherAdapter`, `internal/app/routes.go`) to every member,
  only for a page that is not private, not custom-access and not in a DM-only
  category. the `page-live` widget (`static/js/widgets/page_live.js`) re-fetches the open page through the
  boosted swap, and waits while an editor is open, a form is dirty, a field has
  focus or a dialog is open; one that lands after the reader started such work
  is dropped and tried again later. When the page's arrangement (its frame, rows,
  columns and the blocks in them) came back the same, only the parts that
  changed are touched: a block whose markup differs is replaced, and a widget
  whose markup is the same is handed to its `update(el, fresh)` hook if it has
  one (`Chronicle.updateWidget` in `boot.js`; `page_tabs.js` keeps its tabs
  this way) or mounted afresh in place. Any change to the arrangement, or a
  page boot.js has no served copy of, takes the whole swap. While widgets on
  the fresh markup draw, it holds
  the old height with an empty block under the content and keeps the reader's
  scroll position, until they scroll or the page has grown back. A refresh is
  not an arrival: the `data-whole` frame is shown at once and the fade-in is
  off for that swap (`data-page-live-swap`, outranking Calm and Off), so only widgets that draw late
  fill in. A link to another page keeps the hold and fade. Pinned by
  `TestPageChangedNudge`, `test/js/page_live.test.mjs`,
  `test/js/page_live_browser.test.mjs` and
  `test/js/page_live_parts_browser.test.mjs`.
- **Privacy**: `is_private` shows an entity only to the owner and Co-DMs;
  others get 404. The slide-in permissions card (`static/js/widgets/permissions.js`,
  `PUT /entities/:eid/permissions`, DM team; member emails go to the owner only)
  is the only writer; the edit form carries no `is_private` input.
  `UpdateEntityInput.IsPrivate` is `*bool` (nil preserves); syncapi uses
  `patch.Field[bool]`, as does its batch twin `syncChange`. A bare bool would
  bind `false` on a name-only rename and publish a hidden page to players.
- **Optimistic concurrency**: `expected_updated_at` on update gives 409 if the
  entity changed since.

### `Update` is a partial update

| caller sends | stored value |
|---|---|
| field absent (`patch.Field` zero / `IsPrivate == nil`) | preserved |
| value | replaced |
| explicit `null` (or `""` on `type_label`/`parent_id`) | cleared |

`UpdateEntityInput`'s doc comment (`model.go`) has the full contract.
`Name`/`TypeLabel`/`ParentID`/`Entry` are `patch.Field[string]`.
`ParentID` needs an explicit `parent_id` member in syncapi's update body and in
every AI-workspace commit-update (`""` cannot say "absent"), or the page is
silently detached. `Entry` keeps a legacy `""` = preserve reading; explicit null
clears. Pictures are not on this input: `UpdateImage`/`UpdateCoverImage` are
their only writers and check the file belongs to the page's campaign. Pinned by
`entity_partial_update_test.go` and `syncapi/entity_partial_update_test.go`.

### Field-level visibility

Mechanism in `gm_fields.go`'s package comment. Two tiers, orthogonal to
whole-entity privacy and to each other:

- `FieldDefinition.GMOnly` hides the value from every Player-tier viewer,
  including the claimed owner.
- `FieldDefinition.OwnerOnly` hides it from everyone but GM-tier roles and the
  claimed owner (`Entity.IsOwnedBy`).

Both come from a system manifest's `gm_only`/`owner_only`, converged onto
existing types by `SyncFieldGMFlags`/`SyncFieldOwnerOnlyFlags`
(`internal/app/preset_applier.go`, at boot and on install/update).
`FilterRestrictedFields` is the one call every `fields_data` egress uses. The
server is the authority; a widget hiding its own box (`data-is-gm`/`data-is-owner`
in `show_renderer_registry.go`) is never the fix.

## Link and worked-out fields

`GET .../fields` (and the era version's) carries `shown`: how a field reads to
this viewer when that differs from the stored value. `attributes.js` draws it.

- **link**: `text` is the page's name and `href` its page, only if the page is in
  this campaign, in the field's `link_to` category, and the viewer may open it;
  otherwise `text` is empty (the id is never shown). A changed link value is
  checked on every write (`checkLinkValues` in `Create`, `Update`,
  `UpdateFields`): same campaign, not the page itself, right category. An
  unchanged one is not, so a removed page never blocks saving the sheet.
- **rule**: `text` is the rule's result for the page's values; a typed value wins
  and sets `byHand`, with `ruleGives` when the rule differs.
- **calendar_date** (`field_dates.go`): value `year-month-day` (month by number),
  optionally `|` plus the length each countdown uses (`1043-3-22|1`). `text` is
  the date on the campaign's calendar; `date` carries `ago` (when `date_ago`
  asks) and `countdowns` (`before`, `running`, `last`, `ended` as of today). A
  countdown's own `gm_only` hides it from players. `checkLinkValues` checks a
  changed value: a day the calendar has, a length the countdown has. The calendar
  comes through `FieldCalendar` (`internal/app/field_dates_adapter.go`); unwired
  or with no calendar, dates show as numbers and no countdown runs. `GET
  .../fields` adds `dateBook` (months, today) for the picker.
- **local words**: a text, select or rule value with a local name for the page's
  place or the current era shows it, with `usual` the replaced word. Numbers,
  ticks, URLs and prose are never renamed. `GET
  /campaigns/:id/entities/:eid/local-words` serves widgets outside the fields box
  (shop room and list coins) via `Chronicle.localWords`/`localName` in `boot.js`.
  Rules and words come through `FieldWords`
  (`internal/app/fieldrules_adapters.go`); unwired, rule fields show only typed
  values and nothing is renamed.
- A field the viewer may not see (`GMOnly`, `OwnerOnly`) is skipped first
  (`restrictedKeys`); a rule field stores nothing to strip, so it would otherwise
  be worked out and shown.
- `UpdateEntityType` checks a category's link fields name a category of the
  campaign, rule fields a rule it has, and date-field countdowns
  (`checkFieldKinds`, `CheckDateSettings`).

## Undo: history, Trash, save clashes

- **Trash (ADR-060):** `Delete` marks the page and its live sub-pages
  (`deleted_at`, one `trash_root_id`) once `SetPageSafety` is wired; without it
  (unit tests) delete is permanent. Every read excludes trashed rows:
  `visibilityFilter` starts with `liveOnly` for every role, and reads that skip it
  add `liveOnly` themselves. Owners see the Trash at `/campaigns/:id/trash`.
  Restore puts a page whose parent is still trashed at the top level.
  `StartPurger` purges after `settings.TrashRetentionDays`. Player Notes
  (`entity_notes`, FK cascade) stay with the trashed page and go at purge.
  `NoteCounter` (`SetNoteCounter`, nil = silent) gives counts only:
  `TrashItem.NoteCount` and the `&notes=N` redirect after `Delete`; a count
  failure never blocks a delete. A page kind with pages in the Trash cannot be
  deleted.
- **Other kinds in the Trash:** another plugin's things join the same Trash by
  registering a `TrashKind` (`AddTrashKind`, `trash_kinds.go`); the adapters
  live in `internal/app`, so entities never reads another plugin's tables. The
  Trash page merges them with pages, newest first; a kind that fails to list is
  left out with a log line. `POST /trash/:kind/:tid/restore` restores one and
  goes to the link the kind returns, or back to the Trash when that link leaves
  the campaign. The purger runs every kind with the pages' cutoff.
  `page_safety.js` shows the Undo toast for any kind from `?trashed=<id>&kind=<kind>`.
  Every restore, a page's or another kind's, writes `trash.restored` to the
  campaign activity log (`PageSafetyHandler.SetAuditService`; nil = unrecorded).
- **History:** `entity_versions` keeps title and text, not field values (sync
  clients change those constantly). Kinds: `created`; `edit` (joined into the
  author's last row within `versionCoalesceWindow`); `baseline` (first save of a
  page older than history, recording what it replaced); `restore`.
  `MaxVersionsPerPage` = 100. Owners and scribes only. `PageSafetyService.RestoreText`
  puts a title and text kept elsewhere back as a `restore` row (Undo on an applied AI
  request, `ai_workspace/request_undo.go`); it does no access check, so its caller scopes
  the page.
- **Save clashes:** `entities.entry_rev` counts text changes. `GET .../entry`
  returns `rev` to editors, who send it back as `base_rev`; `SaveEntry` writes
  only if it still matches, else 409 `edit_conflict` with the stored text and
  author. The editor then offers: see their changes, keep both (mine on top), use
  mine. No `base_rev` means no check.
- **Who saved:** `withActorMiddleware` puts the user on the context (`WithActor`);
  syncapi uses `WithSyncActor`. Sync, import and actor-less saves list as "Sync or
  import".
- **Access:** History, restore and the entry PUT run `CheckEntityAccess`, so a
  scribe never reads or restores a page hidden from them (a clash answer carries
  the stored text).

## Extra places in the page tree

A page can be listed under more than one parent. `entities.parent_id` stays its
only real home: breadcrumb, Sub-pages, sync API and Foundry journals never see a
listing. Table `entity_places` (migration 49); `PlaceRepository`
(`place_repository.go`), rules in `PlaceService` (`place_service.go`).

- **Refused:** a page under itself, under its own real parent, under any
  page below it (the walk follows real parents AND listings, so a loop
  through either is seen; trashed pages are walked too), and across
  campaigns. A trashed page or parent is "not found". 25 per page. Adding
  one that exists is a no-op.
- **Real moves keep up:** `ReorderEntity` and `Update` (via `PlaceGuard`,
  `place_guard.go`) refuse a real move that would loop through a listing and
  drop a listing next to the page's new real parent.
- **Visibility is the page's:** a read keeps a listing only when the viewer
  can see both the page and the parent (`FilterViewableEntityIDs`, the one
  predicate). The Trash hides a listing through the joins; Restore brings it
  back; a purge cascades.
- **Who:** add and remove need a Scribe route AND `CanEdit` on the page; the
  parent must be visible to the viewer.
- **Where it draws:** `entityPlacesLine` under both page titles
  (`place_line.templ`, `static/js/widgets/page_places.js`); the sidebar tree
  (`SidebarEntityList` rows with `data-place-key`, no `data-entity-id`,
  never moved on their own, `static/js/sidebar_tree.js`); the category
  page's tree view
  (`buildEntityTreeWithPlaces`). Searches and plain lists never join the
  table, so a page is never listed twice there.
- **Routes:** `POST /campaigns/:id/entities/:eid/places` `{parent_id}` and
  `DELETE .../places/:pid`, both answering with the refreshed line.
- **Export/import:** `ExportEntity.also_listed_under` (parent slugs); import adds
  them after every parent link so the cycle rule sees the finished tree.

## Standing block

`standing` is a page block (one per page; `standing_block.templ`,
`static/js/standing.js`, `static/css/standing.css`): how a page, usually a guild
or person, feels about the party or one character. The Director sets the word
(Hostile, Wary, Neutral, Warm, Trusted) and gives reasons. Tables
`entity_standings`, `entity_standing_reasons`, `entity_standing_settings` (see
`.ai/data-model.md`; migration slug `entity_standing`, so a failed migration
leaves out only this block).

- **`StandingService` alone decides who sees what.** A player gets the word and
  non-DM-only reasons, only for subjects that have a word and whose character page
  they can open, and no block when the page's switch is off. The repository never
  selects a DM-only reason for a player, and the service filters again. The
  Director also gets unset characters, the switch and each reason's `dmOnly`.
  Never add a second decider.
- **Routes:** `GET .../entities/:eid/standing/:subject` (Player+, narrowed by the
  service), `POST .../standing/:subject/reasons`, `DELETE .../reasons/:rid`,
  `PUT .../entities/:eid/standing-settings` (Director or co-Director). `:subject`
  is `party` or a character page id.
- **Limits:** `StandingReasonMax` 90 chars, `StandingWhenMax` 30,
  `MaxStandingReasons` 300 per standing; a read sends the newest
  `standingReasonsShown` (200) per subject with the true total.
- Foundry sync and export do not read standings.

## Pinned pages

The campaign home's Pinned Pages widget (`page_pins.go`,
`page_pins_service.go`, `page_pins_handler.go`, `page_pins.templ`). The
campaigns plugin's `pinned_pages` home block only loads
`GET /campaigns/:id/pinned-pages` into place, so it never reads pages itself.
The widget shows the pages the Director pinned for everyone (`page_pins`;
migration slug `page_pins`, package `pinschema`) as cards, then the viewer's
own pins as rows. A member's own pins are the pages they starred: the star
beside a page's name, the same `entity_favorites` rows the sidebar's
Favorites shows, so there is one way to keep a page, not two.

- **Who sees what is `PagePinService.ForViewer`'s decision.** Every page goes
  through `FilterViewableEntityIDs` for the viewer, so a page they can't open
  is left out without a trace; a page pinned for everyone isn't listed again
  under their own; at most 12 of their own are drawn and the rest counted.
  A Director looking as a player gets what a player gets and no Director
  controls. An empty widget tells the Director how to fill it and draws
  nothing for anyone else.
- **Pinning for everyone** is the Director's (owner or granted co-Director):
  the quiet pin icon beside a page's name (`pagePinMount`, loaded on sight
  for the Director's team only) and the × on a card. At most `MaxSharedPins`
  (12). The × on a member's own row takes their star off.
- **Degraded:** without the `page_pins` table the pin icon is not offered and
  the widget shows each member's own pins only.
- **Routes:** `GET /campaigns/:id/pinned-pages` (public-capable, narrowed per
  viewer), `GET`/`POST /campaigns/:id/entities/:eid/pin` and
  `DELETE /campaigns/:id/pinned-pages/everyone/:eid` (Director),
  `DELETE /campaigns/:id/pinned-pages/mine/:eid` (Player+).

## Entity List widget

The home's Entity List block lists one category's pages (`entity_list.templ`,
`entity_list_handler.go`). `dashEntityList` (campaigns) loads it with hx-get
like Pinned Pages. Route: `GET /campaigns/:id/entity-list?type=<id>&limit=<n>`
(public-capable). Pages come from `EntityService.List` with the viewer's role,
so hidden pages never appear; a Director previewing as a player reads as a
player. A category from another campaign counts as not chosen. With no
category, only the Director is told to pick one.

## New pages since (home block)

`PagesSinceReader.Since` (`pages_since.go`) feeds the home's "Since you were
last here" row, built in `internal/app/since_last_here.go`. It counts and names
the live, non-template pages of one campaign created after a time that the
viewer may open: the count and the names share one WHERE with
`visibilityFilter`, so a private page, an ungranted custom-permission page or an
Adventures page never adds to the number. It reads through
`idx_entities_campaign_created`. The block passes the owner viewing as a player
as a player.

## Shop goods

A good a shop sells must be a page (stock is a `sells` relation with a NOT
NULL target), so a good with no page of its own becomes a page with
`shop_good = 1`. `EnsureShopGood` reuses one by name across shops. Every list,
search, Auto-link, recent pages, pages-since, category count, page walk and
the Foundry sync leaves shop goods out unless the caller asks for them; they
publish no live event and no change-feed row. Lookups by id, the shop's own
stock, export and import still carry them. `ReconcileShopGoodVisibility` keeps
a shop good hidden unless a public listing sells it (the relations widget calls
it on every listing added or removed). `SetShopGood` promotes or demotes a page
(`POST /campaigns/:id/entities/:eid/full-page`, Director only) and tells the
sync the page appeared or went.

## Home blocks on ordinary pages

`when_we_could_play`, `next_game`, `today_in_world`, `open_quests`,
`world_clocks` and `since_last_here` are registered for the `dashboard` and
`template` contexts with a renderer (`placeable_blocks.go`), and for category
homes through `RegisterCategoryBlock`. The renderer draws
`campaigns.PageBlockFragment`, the same lazy placeholder the campaign home
uses, with `?on=<pageID>` on a page; this plugin reads nothing for them.

`BlockPlacementChecker.GuestMaySee` is the other half of the guest rule
(`campaigns.BlockVisibleTo`): true only when the page exists in the campaign,
`CheckEntityAccess` lets the viewer open it at their own role, and the layout
the page wears (the category's main layout, or the named layout
`PageLayoutService.Worn` picks, as `wornLayout` does) draws the block for a
viewer outside the Director team. `layoutDrawsBlockForGuests` counts only
column blocks and tiles; a block marked `dm_only` or inside a container does
not count, because the page does not draw it for a guest. Every error is false,
and a missing page, another campaign's page and a hidden page answer alike.

The older home blocks (`pageHomeBlockTypes` in `placeable_blocks.go`:
`welcome_banner`, `quick_actions`, `category_grid`, `recent_pages`,
`entity_list`, `pinned_pages`, `calendar_preview`, `timeline_preview`,
`calendar_full`, `timeline_full`, `relations_graph_full`, `map_full`,
`coming_up`, `start_here`, `brochure`, `at_a_glance`, `party`, `your_hero`,
`getting_started`, `when_we_play`, `where_we_play`, `house_rules`, `last_time`,
`table_agreement`, `making_a_hero`, `run_by`,
`activity_feed`, `sync_status`) are offered the same way, mechanically:
`BlockRegistry.offerOnPages` adds the `template` context and the renderer to the
block `RegisterCoreBlocks` already registered, so label, icon, addon gate,
settings and tile sizes stay as registered. The renderer (`homeBlockRenderer`,
`drawHomeBlock`) calls `campaigns.DashboardBlockSwitch` for that one block with
the page's `CampaignContext` and `TemplateBlock.Config`, so the block's own
visibility rules apply wherever it sits, and a block that shows the viewer
nothing leaves no frame. The frame (`pageBlockFrameClass`) keeps the home's
card grids to the column they sit in. `recent_pages` is the one block that needs
data the home handler preloads; it reads `ListRecentForDashboard` through
`SetRecentPagesLister` as the viewer (an owner looking as a player reads as a
player). Category homes get the same blocks through
`RegisterCategoryBlockWithConfig`, which hands the renderer the settings saved
on the block; `pinned_pages`, `recent_pages`, `calendar_preview` and
`timeline_preview` keep the category's own versions
(`CategoryBlockSwitch`). `text_block`, the retired `session_tracker` and the
unoffered `relations_graph` are not offered; a test fails when a home block is
neither offered nor named as left out.

## The party

The campaign home's `party` block (`party_block.go`, `party_block.templ`).
`GET /campaigns/:id/party` lists the claimed characters of the page types the
owner listed on the Characters page (the same `buildCastParty` and
`filterCastByType` it uses, judged as a player while the Director views as one),
with ancestry, class and level read by `partyFacts` from the first matching
key (`ancestry`/`race`/`species`/`heritage`, `class`/`calling`/`career`,
`level`). A field its type marks GM-only or owner-only is never read. Who plays
a hero shows for members only. Empty when the Player Character Claiming addon is
off or nobody is claimed.

The `your_hero` block (`your_hero_block.go`, `your_hero_block.templ`,
`GET /campaigns/:id/your-hero`) is the same list cut to the viewer's own hero
(`CastMember.IsViewer`), worded by `buildParty`, so it shows the same facts and
never a GM-only or owner-only field. With no hero it offers "Choose a hero" (the
Characters page). Empty for a non-member or when claiming is off.

## Start here

The campaign home's `start_here` block (`start_here.go`, `start_here.templ`).
The campaigns plugin's placeholder loads `GET /campaigns/:id/start-here?page=`
with the page the owner picked. The page goes through `CheckEntityAccess` for
the viewer (a player's role while the Director views as one); a page they
can't open is an empty answer, which removes the block. The first line is the
first non-heading paragraph of the served entry (`startHereFirstLine`), so
secrets and hidden page names are already gone; viewing as a player strips
secrets too. The DM team gets a dashed slot when nothing is picked or the page
was deleted, and an amber edge on a page players can't see.

## Brochure

The campaign home's `brochure` block (`brochure.go`, `brochure.templ`, with
`static/js/brochure.js` in this plugin and the `.cb-bro` rules in `input.css`): a small box
for one page the owner wrote as a new-player leaflet. Config `entity_id` (the
page) and `content` (optional words on the box; empty uses the page's first
line, as Start here does). Both blocks resolve the page through
`loadHomePage`, so access, era version and the empty answer for a viewer who
can't open it are the same. The brochure strips the owner's secrets for
everyone, because it is what a new player reads. The box is one button
(`GET /campaigns/:id/brochure?page=&text=`) with a closed native dialog beside
it holding the served, sanitized entry HTML. `Chronicle.brochure.open` (loaded
on sight through the `brochure` widget mount, called from an inline `onclick`) wraps that HTML into
panels once: the cover is everything before the first `h2` (a horizontal rule is
dropped), each `h2` starts a panel, a panel with a long or many-column table is
two folds wide, and `h3` parts of a wide panel sit side by side. Three panels
to a row, one column with "Panel N of M" on a phone, by the dialog's own width.
Page mentions keep `data-entity-preview`, so the document's hover card binding
previews them; `hovercard.js` seats its card inside an open dialog so it shows
above it. Checklist boxes are display-only (TODO(#2389)). Tests:
`brochure_test.go`, `test/js/brochure_browser.test.mjs`,
`test/live/brochure_home.spec.mjs`.

## Named page layouts

A category keeps its main layout (`entity_types.layout_json`) plus up to
`MaxPageLayouts` (8) named layouts; each page wears one (`page_layouts.go`,
`page_layouts_repository.go`, `page_layouts_service.go`,
`page_layouts_handler.go`). Tables `entity_type_page_layouts`,
`entity_page_layouts` (see `.ai/data-model.md`; migration slug `page_layouts`,
package `layoutschema`; while degraded every category has only its main layout).

- **Worn layout** is `PageLayouts.WornKey`: the Director's pick for the page,
  else (player character, claimed or playable) the layout the category starts
  claimed pages on, else the main one. A pick since removed falls back.
- **Drawing:** `prepareShowFor` calls `wornLayout`, which hands the page a copy of
  its category carrying the named layout's blocks and records the choice in the
  context. A page on a named layout is drawn from it even where a game system would
  draw the whole page (`NamedLayout`, `wearsNamedLayout`); the system's sheet is
  then the `game_system_sheet` block.
- **Picking:** the chip beside the name (`page_layout_chip.templ`,
  `static/js/page_layout_chip.js`), Director team only and never while viewing as a
  player, sends `PUT .../entities/:eid/layout`. A category's layouts are arranged
  in Customize > Page layout (`customize_page_editor.js`), saved by the draft's
  `categories` item `page_layouts`, whose blocks are checked like the main layout's.
- **Elsewhere:** the AI outline groups a category's pages by layout and `read_page`
  names it (Director only); the prompt lists each category's layouts and import
  takes `layout:`; campaign export carries both tables.

`BlockMeta.ShowsSheet` marks a block that draws a page's own sheet or its fields
(`attributes`, `character_surface`, the game system's panels and sheet); a layout with
none of them leaves its pages without a sheet. `BlockRegistry.ShowsSheet` answers it by
type (false for an unknown one), which AI Import's `layout` review uses to warn before
an update drops the last such block.

## Putting a block on a category's pages

The Game & features page's "Put on a page" (widget `put-on-page`) and the DM
Screen's Trackers section place a block without the Customizer. `layout_append.go`:
`BlockPlacementOptions` lists the campaign's top-level, enabled categories
(`GET .../entity-types/placement?block=`), the one the block is made for first
(`suggestedHomes`, by slug or preset: quests for the quest board, locations for
notice boards, Adventures for trackers and tests); `AppendBlockToCategoryLayout`
(`POST .../entity-types/:etid/layout/blocks`, `{type}`) adds the block in a
full-width section at the end of the main layout and of each named layout, through
the same `ValidateLayout` and `checkPageLayouts` as a Customizer Save, writing
nothing if either fails. A layout that already holds the block (searched inside
containers too) is left alone and the answer is `already_there`. Owner only.

## Family tree block

`family_tree` is a page block (one per page, tile sizes 4x1 and 2x1;
`family_tree_block.templ`, `static/js/family_tree.js`,
`static/css/family_tree.css`): a page's parents, children and partners from its
entity relations. At rest one line of circles; a click opens the tree over the
page; Close or Escape folds it. Nothing is stored: the tree is read per page draw
and the block has no route or migration of its own.

- **Relations that count** (`familyRelations`, `family_tree.go`; trimmed,
  lower-cased type from the reading page's side): `parent of`/`child of`,
  `adoptive parent of`/`adopted child of`, `guardian of`/`ward of`, `married to`/
  `spouse of`/`partner of`. Only the first pair is in the Relations block's
  suggestion list. Siblings are pages sharing a parent. No gender is held, so the
  words are Parent, Child, Sibling, Partner.
- **`FamilyTreeService` alone decides who sees what.** A relative the viewer cannot
  open (`FilterViewableEntityIDs`) is not read past, named or counted, and a
  `dm_only` relation is not followed, so a player's JSON holds no trace of either.
  The Director gets them marked `DMOnly` (amber edge, DM tag). "View as player"
  hides the same in script (`html[data-view-as-player]`). Never add a second
  decider.
- **Bounds:** `MaxFamilyGenerations` 4 each way (read one further to know whether
  the family goes on), `MaxFamilyPeople` 60 (nearest first), `maxFamilyReads` 120.
  `CutGenerations`/`CutPeople` say which bound cut someone, and the block says so.
  A relative the walk did not read (`Read` false) gets "Open page" but no "Make
  centre".
- **Wiring:** relations via the `FamilyLinks` interface
  (`internal/app/family_tree_adapters.go`), pages via `PageCards`, visibility via
  the entity service; no other plugin's repository is read.
  `registerFamilyTreeBlock` is in `internal/app/routes.go`.
- **Edit tab** (`family_edit.go`, `family_edit_handler.go`): the Director (owner or
  granted co-Director, not a Scribe) adds and removes parents, children and
  partners and saves together. `FamilyEditService` checks `FamilyActor.IsDirector`
  on every call, and the routes (`GET .../entities/:eid/family/candidates`, `POST
  .../entities/:eid/family`, `RequireFamilyDirector`) check again. Writes go
  through `FamilyWriter` (`family_tree_adapters.go`, over the relations service, so
  both rows of a pair are written and removed as the Relations block does, and
  relation events and the Foundry change feed see them). A parent link is written
  from the child as `child of`/`parent of`, `adopted child of`/`adoptive parent of`
  or `ward of`/`guardian of`; a partner link as `partner of` both ways. New links
  are not DM-only.
- **A save is all or nothing.** Order: create pages (entity service create path,
  campaign default visibility, character category else first enabled), then
  removals, then additions. A failed write takes back what the save already wrote;
  the result says which edits did not save, whether the takeback worked, and flags
  any pair left half-written (`halfWritten`). A created page is never deleted (the
  retry reuses it). A page cannot become its own ancestor. Caps: `MaxFamilyEdits`,
  `MaxFamilyNewPages` per save.
- **Picker:** at most `FamilyPickerMax` pages the Director can open, narrowed by
  `?q=` through the sidebar's list and search. Not a partial-update endpoint
  (`internal/patch` does not apply): a save names the links to add and remove.
- `relations.CommonRelationTypes` is not extended with family types: it is served
  to the Foundry module (`GET /api/v1/campaigns/:id/relations/types`), so that
  would change the contract.

## Pages by era

The calendar plugin stores versions and picks the current era (`EraVersionService`,
`internal/plugins/calendar/.ai.md`); this plugin reaches it through `EraPages`
(`era_pages.go`, wired in `internal/app/era_pages_adapter.go`).

- **Readers** see the page as its version for the current era when it has one
  (`withEraVersion`: name, picture, text, changed fields over the usual ones);
  hover cards and peeks too (`currentEraEntity`). Players get no era controls; the
  era routes answer NotFound for any era but the current one unless the viewer is
  the Owner or a granted co-DM (`CanAuthorDmOnly`). Pages a game system draws keep
  their usual self.
- **Eras panel** (`era_panel.templ`, `static/js/widgets/era_pages.js`, loaded on
  sight): the Eras button by History opens a ribbon of the main calendar's eras
  ("now", a dot where the page has a version). `?era=<id>` or `?era=usual` swaps
  the page in place. Highlights (default) show marked words, "Added" paragraphs, a
  dashed note for removed paragraphs (`EraDiff`, `era_diff.go`), "Changed in this
  era" on the picture, and "Usually X" under changed fields. `hl=0` is editing: the
  editor, attributes and picture widgets save to the version's routes, and the
  panel adds the era name, "Use the usual picture" and Remove version. A non-DM
  Scribe sees that their edits change the current era's version, the only one they
  may write. The Edit name fold always renames the usual page.
- **Routes** (`era_handler.go`): `POST`/`PATCH`/`DELETE
  /campaigns/:id/entities/:eid/eras/:eraID` make, rename/re-picture and remove a
  version (make and remove are the GM's). `GET`/`PUT .../eras/:eraID/entry` and
  `.../fields` mirror the usual routes' shapes (secrets stripped for anyone but
  owner and Co-DMs, same clash answer; the fields read adds `era_changed` for the
  GM). `PUT .../eras/:eraID/image` takes the picture widget's body. A fields save
  keeps only values that differ from the usual page (`eraFieldChanges`).
- **Moon chip:** a moon's lore page shows the moon and tonight's phase under its
  name, linking to the calendar (`PageMoons`, `page_moons.go`).

## Page Files section

Every page ends with a "Files" section drawn by media (`media/page_files.templ`,
see its `.ai.md`). This plugin only mounts it: `pageFilesMount` in
`page_extras.templ` is an `hx-get` placeholder for
`/campaigns/:id/entities/:eid/files?first=1`, for campaign members, after the
layout and character-items panel. Visibility and edit rights follow the page:
media asks `FilterViewableEntityIDs` (which leaves out the Trash) and
`CheckEntityAccess` through an adapter in `internal/app/routes.go`. It is not a
layout block, so an owner cannot place or hide it.

## Field-change observer

`SetFieldChangeObserver` takes a `FieldChangeObserver`. After a successful custom
fields write, in `UpdateFields` (used by `MergeFields` and the attributes widget)
and in `Update` when `FieldsData` was part of the write, the service calls
`FieldsChanged(ctx, entity, oldFields, newFields)`. An observer error is logged,
never returned. Another plugin hooks in from `internal/app`; this plugin names
none. Web field writes mark the context `changesource.KindWeb`
(`webWriteContext`).

An observer that also implements `PageChangeObserver` hears about title and
text saves (`TextChanged`, from `recordVersion` for edit and sync saves, with
the saving person from `WithActor`) and removals (`PageTrashed`, from `Delete`
once the page is in the Trash). Both need page safety wired. `internal/app`
fans one observer out to the Armory's money history and "What players
changed" (`fieldObservers`).

## Long-term trash

`PageSafetyService.SetLongTermTrash` wires a `LongTermTrash` keeper. The hourly
purge asks it for the Trash item roots to keep and leaves those pages whole,
links and pictures included; if it can't answer, no page is removed that hour.
A kept page past its Trash days is left out of the Trash list; the owner brings
it back from "What players changed" (playerchanges `.ai.md`). A page that comes back
out of the Trash by any route is reported to the keeper (`PageRestored`), which
stops keeping it, so deleting it again lets it expire normally. Without a keeper
the Trash behaves as before.

## A page arrives whole (first paint)

`Show` sends the first content of the page's four late-filling widgets with the
page (`first_paint.go`): the text (`entryPayload`), the attributes
(`fieldsPayload`), the tags and the connections (`PageParts`, implemented in
`internal/app/entity_page_parts_adapter.go` over the tags and relations widget
handlers, so their visibility rules stay in one place). Each endpoint and the
page build the same payload with the same function. A part is worked out only
when a block on the page asks for it, and a failed part sends nothing, so that
widget fetches as before. An era version sends nothing (its widgets read a
different address).

The payload sits in the widget's mount as `<template data-first-paint-data>`
(not a script: page scripts are stripped from a boosted swap), the mount carries
`data-first-paint`, and the page frame carries `data-whole`. The widget reads it
with `Chronicle.firstPaint(el)` and says `Chronicle.drawn(el)` after its first
render. CSS keeps a `[data-whole]` frame unseen until boot.js (`holdWhole`) sets
`data-whole-ready`: every filled mount drawn and every `hx-trigger="load"` block
in the frame answered, or 1.5 s, with a CSS release at 2 s if the script never
runs. The frame keeps its room meanwhile, so the reveal is a fade, not a move.
`test/live/one_speed.spec.mjs` measures the text's top edge every frame.

## Sidebar navigation

The sidebar drill panel: the slide-over category view with entity tree, folders,
favorites and search. A category row opens it (campaigns `.ai.md` > "Sidebar
navigation").

- **Dual-Parent Model:** two mutually exclusive parent refs — `parent_id`
  (CHAR(36) FK->entities) and `parent_node_id` (CHAR(36)
  FK->sidebar_nodes, a folder). One set means the other must be NULL,
  enforced in `ReorderEntity()`; `static/js/sidebar_tree.js`'s tree
  builder resolves both.
- **Sidebar Nodes (pure folders):** `sidebar_nodes` stores organizational
  folders with NO entity record (CRUD routes: see Routes above). The create,
  rename and delete handlers call `FolderService` (folder_service.go), which
  also checks the category and parent belong to the campaign. Deleting a
  folder moves its sub-folders up to its parent and its pages to the top
  level of the category; it deletes no page.
  **Footgun — keyed by the CATEGORY type, exact-match on reload:** a
  node's `entity_type_id` must be the drilled category's own type
  (`?type=`), since `SearchAPI` reloads via
  `ListByType(campaignID, typeID)` (exact match) while the drill listing
  rolls up sub-types (`expandTypeIDsForListing`), so
  `results[0].EntityTypeID` can be a **sub-type**. The row menu's "New
  folder" (`sidebar_row_menu.js`) scopes a new folder from the tree's
  `data-entity-type-id`, which MUST be the category type or the node
  orphans under a sub-type, never returning on refresh. `SidebarEntityList`
  resolves it via `sidebarTreeType()` (prefers `typeID`; row/node fallback
  only when `typeID<=0`). Pinned by `sidebar_list_test.go`.
- **Sidebar order:** each list in the tree (a category's top level, a
  folder, a page with pages under it) sorts A to Z, by hand or newest
  first; folders always lead. `sidebar_child_orders` holds the lists that
  are not A to Z (`ChildOrderRepository`, sidebar_order.go), read by
  `FolderService.ChildOrders` and drawn as `data-root-order` /
  `data-child-order`; rows carry `data-created`. By hand follows
  `sort_order`. A Scribe moves a row by dragging it, with its arrows,
  Alt+Up/Down or the row menu (dropping a row on a folder files it there); `PUT /sidebar-order/move` names the neighbour to pass, not an
  index, so siblings the mover cannot see keep their places, and the whole
  sibling set is renumbered (`placeNextTo`). A page of one sub-category
  cannot be placed among another's pages: each keeps its own numbering.
  Pinned by `folder_service_test.go`, `sidebar_list_test.go`,
  `sidebar_tree_sort.test.mjs` and `sidebar_tree_order_browser.test.mjs`.
- **Favorites:** `entity_favorites` stores per-user, per-campaign
  bookmarks (routes: see Routes above). They are also each member's own pins
  on the home's Pinned Pages widget (see "Pinned pages").
- **Tag Filtering:** the search API's `?tags=slug1,slug2`, AND-logic via a
  subquery with `HAVING COUNT(DISTINCT)`.
- **Lazy Loading:** 50 entities/page; a "Load more" sentinel renders when
  `total > len(results)`, and a JS IntersectionObserver auto-triggers
  next-page fetches.
- **DM-only marks:** for the DM team (`visibilityGlanceVisible`) a page set
  to DM-only gets a lock on its sidebar row (`sidebarDMOnly`; not on every
  row of a DM-only category) and a "{GM} team only" label beside its name
  (`dmOnlyTitleLabel`, both page headers). The label is always rendered for
  the DM team, hidden unless DM-only, so `permissions.js` can show or hide it
  when the corner control saves. Players get neither (ADR-055 rule 3).
- **Sidebar config model:** ONE stored model
  (`campaigns.SidebarConfig.Items`) with ONE editor
  (`static/js/sidebar_editor.js`, pencil-triggered inline edit).

## Business rules

- **Content templates.** A new page copies its Content Template's JSON. The four
  built-in templates (seeded per campaign by `SeedDefaults`) are headings plus
  empty prompt lines (see the editor's `templatePrompt`). `ReconcileTemplatePrompts`
  runs at boot and swaps any built-in template still exactly as first seeded
  (`template_prompts_legacy.go`) for the prompt version; edited ones are left.
- **Side columns follow the reader.** Layout rows/columns carry `data-page-row` /
  `data-page-col` inside `[data-page-frame]` (`show.templ`). `static/js/page_sides.js`
  keeps each column at least 120px shorter than the row's tallest one in view while
  scrolling (`position: sticky`, md and up); a column taller than the view sticks
  once its bottom shows. Pinned by `test/js/page_sides.test.mjs`.
- Names are non-empty, max 200 chars. Slug is generated from the name,
  deduplicated with -2/-3, unique per campaign. The entity type determines the
  profile/edit fields; dynamic fields parse from form params `field_<key>`.
- Private entities are filtered in SQL from lists; Show returns 404, not 403.
- FULLTEXT search on name (BOOLEAN MODE), LIKE fallback under 4 chars. The
  parser's operator characters (`+ - > < ( ) ~ * " @`) in a query become
  spaces first (`stripFTOperators`), so they are word breaks and never search
  syntax; a query with no word left also takes the LIKE path.
  Results come best match first (`searchRank`): the exact name, a name that
  starts with the query, a word in the name that does, any other name match,
  an alias, then pages that only mention it; name and id break ties, so paging
  stays a total order. Deleting cascades via FK.
- **The Search page** (`/campaigns/:id/search`, `search_page.templ`,
  `static/js/search_page.js`, `static/css/search_page.css`) asks `SearchAPI`
  twice with `scope=`: `named` (the words are in the name, an alias or the
  descriptor, plus maps, timelines, events, game nights and rules, which are
  found by name only and answered with page 1) and `mention` (only the page's
  text has them; each result carries `snippet`, an array of `{text, mark}` runs
  the page escapes and wraps, never HTML). A category or tag filter leaves the
  non-page hits out. Each group shows five rows until "Show all N", then pages
  in 20. Without `scope` the answer is the whole one quick search and the
  pickers use. A snippet is quoted from `search_text`, the one column search
  matches for every reader (secrets, owner-only fields and mention link text are
  already out of it, `buildSearchText`), by `SearchSnippets` in
  `search_snippet.go`, one query for the page's rows, filtered again with
  `visibilityFilter`. So a word that exists only inside a secret sentence finds
  no page for anyone, the owner included, and no snippet quotes a line the
  reader could not have matched. The mention scope writes the name side as
  separate AND terms (`NOT name`, `NOT LIKE` descriptor, `NOT IN` aliases) so the
  alias check is materialised, not run per row.
- **A Scribe sees what players see** (ADR-070). Hidden pages, GM-only fields,
  secrets and Adventures belong to the owner and Co-DMs (`CanAuthorDmOnly`, or
  `VisibilityRole() >= RoleOwner` where a role is passed). A Scribe keeps write
  access limited to what they are served (`hidden_parts.go`):
  - Every Scribe write route on `/entities/:eid` runs `requirePageWrite` after
    `RequireRole(RoleScribe)`: a page they cannot see is 404; one they can see but
    not edit (custom permissions) is 403. The description and picture saves open
    to players, so they run `requireOwnPageOrPageWrite`: same check for Scribes,
    `authorizeOwnPageWrite` for players.
  - Text with secrets is read-only to them: entry and player-notes reads add
    `locked: true`, the editor shows a lock note, and saves (including the legacy
    form `PUT /entities/:eid`) refuse with 403 or keep the stored text.
  - A fields save keeps stored GM-only and owner-only values
    (`keepRestrictedFields`); a `fields_patch` drops those keys
    (`dropRestrictedFields`).
  - Their new pages are always open to players (`NewPagePrivacy`); they cannot
    create, change into or bulk-move into Adventures (`requireCreatableType`), and
    bulk hide/show is refused.
- **Adventures** (`preset_category = 'adventures'`; every seed list carries it) is
  invisible to anyone but owner and Co-DMs in every read: pages vanish from lists,
  search, counts, mentions, relations, backlinks and ancestors whatever their own
  visibility or grants; the category home and every page endpoint answer 404; the
  category is left out of category lists, the sidebar and its websocket events.
  It cannot have kinds, and `CreateEntityType` refuses the reserved marker. New
  campaigns are seeded with it, import restores it via `EnsureAdventures`, and no
  route adds it to an existing campaign.
- `GET .../entities/:eid/sheet` renders an Adventures page's body with no site
  chrome (`EntitySheet`, sharing `entityPageBody` with the full page, and
  `prepareShow` with `Show`) for the DM Screen's page sheet. 404 for anyone but owner
  and Co-DMs and for any page outside an Adventures category (`sheet_test.go`).
- The profile page composes widgets: title, editor (TipTap, `data-widget="editor"`,
  view/edit toggle), tags, attributes (`data-widget="attributes"`), relations.
- **Pages that link a note** (`PagesLinkingNote`, for the Journal's backlinks):
  `pagesLinkingNoteWhere` scopes by campaign and applies `visibilityFilter`; for a
  viewer who does not read inline secrets, a page whose only `[[link]]` sits inside
  one is left out. Only names leave through the notes adapter, never a body.

## Player Character Claiming

Links player-owned entities to campaign members. Gated by the
`player-character-claiming` addon; existing campaigns default off.

- **`entity_types.claimable BOOLEAN NULL`** (migration 000029): NULL falls back to
  a legacy heuristic (`preset_category == "character"` or slug `*-character`);
  TRUE/FALSE is the Owner's override (`isClaimableType`). A player-character
  sub-type (`PresetCategory`/slug `player_character`/`player-character`) requires
  the addon (`CreateEntityType` via `AddonChecker`) and defaults `claimable=true`.
  ADR-039: both the sub-type and the legacy heuristic stay supported.
- **UI** (needs `addon-enabled(player-character-claiming)` AND
  `isClaimableType(type)`, never on an NPC's page: `isNPCPage`, an unclaimed,
  unplayable page of a type on the NPC list; the owner's Playable mark moves it to
  the party): (1) `claim_banner.templ`: "Claim this character" (Player+) when
  unclaimed, else "Claimed by &lt;name&gt;" (via `memberLister`, fallback "a
  player"); (2) the Characters page's Players box; (3) a per-type "Players can claim
  entities of this type" checkbox in Customize's Add-Category form, default true
  when the addon is on.
- **Audit:** `entity.claimed`, `entity.owner_changed` (details: `new_owner_id`,
  `new_owner_name`, or `cleared: true`).
- **API:** `POST .../:eid/claim` (Player+): idempotent if already the caller's,
  409 if someone else's, 400 if the type isn't claimable or the page is an NPC's.
  `ClaimOwner` writes only if the page is still unowned or the caller's, so of two
  simultaneous claims one gets 409. `PUT .../:eid/owner` (Scribe+) body
  `{"owner_user_id": "user-uuid-or-null"}`: validates membership; 200 no-op if
  unchanged.

## Characters ("Cast") page

`GET /campaigns/:id/characters` (public-capable: signed-out visitors of a public
campaign see only what visibility allows; owner names and member-only links are
hidden from non-members) -> `Handler.Characters` -> `CharactersPage`/
`CharactersContent` (`characters.templ`), the campaign-wide "who's who". A "Yours"
band (the viewer's own characters, any type, `ListByOwner`) sits on top, then two
addon-gated bands; the page 404s when neither addon is on. `GET /me` redirects
here. The owner picks which page types each band shows (`character_lists.go`); the
owner's page has an Add button and a chip with an x per type, opening boxes in
place (`.ag-fold`, inline handlers from `cast_onclick.go`, no modal) and posting to
`POST /campaigns/:id/characters/lists` (owner only), answered with the refreshed
`#cast-content`. A band with no chosen type is hidden from everyone but the owner.

- **Players section** (`player-character-claiming`, `view.ShowPlayers`): every
  claimed character of a listed type: `service.ListClaimed` (`owner_user_id IS NOT
  NULL` + `visibilityFilter`) unioned with the viewer's unfiltered `ListByOwner` (a
  player sees their own PC even if private), de-duplicated and viewer-first by pure
  `assembleCastParty(...)`, narrowed by `filterCastByType`. The viewer's cards get
  a "You" ribbon and accent ring.
- **Players box** is `view.Roster` (Scribe+, addon on), opened by the Party head's
  "Players" button. Characters on it are listed-type ones that are `playable` OR
  owned (`service.ListRoster` -> `ListOnRoster`, name order, 500 cap), so same-type
  NPCs stay off. `entities.playable` (migration 000054) is the per-character mark;
  `UpdateOwner` with a non-nil owner sets it in the same statement (clearing an
  owner keeps it), so a claimed character joins by itself and an unclaimed one
  lands in **Free to pick**. The box (`players_box.templ`, `players_box.go`) has a
  row per Player-role member (plus any other member owning a roster character) with
  chips that unclaim, then Free to pick chips whose x takes a character off the
  list. One `.pw-find` finder moves under the Give or Add button that opened it
  (`castFinderJS`) and searches through htmx. `view.Pickable` is, for a member with
  no character, the playable unclaimed ones they can see; it draws "Pick your
  character" above the Party (`castPickBox`), whose Yes posts the ordinary claim
  with `from=characters` so the answer is the page body and a notice, not a
  redirect. Routes (all 404 with the addon off, all Scribe+): `POST
  /characters/owner` (entity_id, owner_user_id; "" unclaims; owner must be a
  member), `POST /characters/playable` (entity_id, playable 1/0; marking needs a
  claimable type, unmarking never does), `GET
  /characters/players/search?q=&for=<user id|free>` (HTML rows, max 8,
  `rosterFinderResults`; `SearchRoster` filters in SQL, free-to-pick first then
  name). Giving with nothing typed lists only free characters; adding with nothing
  typed lists none; a name searches every listed-type character the viewer can see,
  skipping what the player already plays (give) or anything playable or owned (add).
  The POSTs answer with `#cast-content` carrying `view.Notice`, box left open
  (`view.Open = "players"`). `ClaimEntity` itself is not limited to playable pages.
- **NPCs section** (`npcs` addon) comes from npcs, not this plugin: `entities`
  defines `NPCSectionProvider` (a `templ.Component` from `npcs.Handler.NPCSection`),
  injected via `SetNPCSectionProvider` so core never imports the addon. npcs renders
  a featured portrait row (tag `CastTagSlug` = `cast`) above the revealed list with
  a DM reveal/hide toggle. `GET /npcs` redirects to `GET /campaigns/:id/characters`.
- **Cards** are real links (work without JS); the corner "quick look" button is
  enhanced by `static/js/characters.js` into the dynamic-surface frame's mini->full
  launch. **It mounts from the plugin body-script registry, NOT `characters.templ`**:
  a boosted navigation strips `<script>` tags from the swapped `#main-content`
  (`allowScriptTags=false` in boot.js), so an embedded script would only wire on a
  direct load. Mechanism in `characters_boosted_nav_test.go`'s header; ratcheted by
  `tools/check-page-scripts.sh`.
- Nav: the `characters` entry of `navAppCatalog` (`internal/app/routes.go`), shown
  when either addon is on. No migration (reuses `owner_user_id` + tags).

## Hero creator

`GET /campaigns/:id/characters/new` (Player+): one page of steps with cards inside: a step
header and a row of chips on a phone, three columns (step rail, cards, the open
entry) on a computer. `static/js/hero_creator.js` mounts on
`[data-hero-creator]` from the plugin body-script registry, fetches steps from
`GET .../characters/new/plan`, and posts the hero as `POST .../characters/new`
`{name, picks: {fieldKey: {name, options}}, about?: {fieldKey: text}}`, answered
`201 {id, url}`. The Characters page shows "Create hero" when `CastView.CanCreateHero`.

- **About your hero** (`hero_about.go`): an optional step between the picks and
  Name and review, for who the hero is in the player's words. The plan's `about`
  lists the boxes (`{key, label, long}`) the hero's page type has, of `pronouns`,
  `gender`, `appearance` and `backstory`, never a GM-only one; a type with none
  gets no step, and practice heroes and try-outs never show it. Every box may be
  left empty. `CreateHero` takes only offered keys (`heroAboutValues`: others are
  400, empty ones skipped, 200 characters for a line and 20000 for a paragraph) and
  writes them as fields. The draft keeps them. They are owner-editable afterwards
  through `identity_edit.go` (`pronouns`, `gender` short; `appearance`,
  `backstory` long); the backstory is what Foundry's Biography carries.

- **Steps** come from `HeroPlanner`, filled by the composition root from the
  systems plugin (`internal/app/hero_planner_adapter.go`): each text field of the
  system's character preset that has entries (package or campaign-made), in the
  order the system's `creator_order` names, then preset order. This plugin never
  reads a package. A step may carry the system's declarations: `Needed` (reads as
  not optional, never refused server-side), `Parent` (its entries live inside the
  entry picked at the parent step; each `HeroChoice.Parent` names that entry) and
  `CountFrom` (how many the picked entries allow; 0 means not asked). The creator,
  builder, practice and try-out plans all carry them.
  `resolveHeroPicks` (creator and practice alike) refuses a pick on a `Parent` step
  that is not under the parent pick, or with none, and a pick on a step the picked
  entries allow none of ("A Conduit doesn't use a kit"). A parent that lists nothing
  leaves the step unasked. The builder door (`checkParentFit` in `identity_edit.go`)
  refuses a dependent value that belongs to another parent entry than the hero's
  (or the same patch's), and leaves count-0 steps unrefused: the builder just does
  not offer them. In `hero_creator.js` `pool`, `stepState` (`open`, `wait`,
  `unused`), `allowance` and `scrub` apply this (a changed parent clears what no
  longer fits, said in the live region; a draft is scrubbed on restore);
  `hero_builder.js` does the same with per-hero step views and a `dependents` pass
  that adds the nulls to the one save.
- **Rules words and skin:** each builder mount (creator, practice, try-out) carries
  `data-skin` (`plain` | `paper` | `ornate`, from the campaign's Customize "Hero
  builder look" via `layouts.BuilderSkin`; Plain when unset or unknown) and, when
  the system's Rules book names a glossary, `data-terms-url`. The words come from
  `HeroTermsReader` (`hero_terms.go`, filled by `heroTermsAdapter` from the systems
  `RulesTerms`), served as `{"terms": {"<key>": {name, category, text}}}` with
  `Cache-Control: private, max-age=300`: `GET .../characters/new/terms` (same gate
  as the plan, `requireHeroPlanAccess`), `GET .../characters/practice/terms`
  (`practiceMaker`) and `GET .../characters/try/terms` (`tryoutReady`, read-only).
  The key is the markup's term trimmed, lowercased, whitespace runs to `-`
  (`systems.NormalizeTermKey`, also the slug). Text is plain (markup and HTML
  stripped, `systems.PlainTermText`); words in a Director-only category are never
  included. A system with no glossary answers 200 with empty `terms` and its mounts
  omit `data-terms-url`; a glossary that fails to read also leaves the URL off.
- **Who:** Scribe+ make heroes for the table. A Player may make their own (which
  they then own) when the owner enabled `player-character-claiming`, the hero's
  page type is claimable, and they own no character page yet: one at a time
  (`heroAccessFor`). The page type is the owner's listed character type the system
  marks as its character, else the player-character type, else the first listed
  (`pickHeroType`); a Player only gets a claimable one.
- **Saved:** each step's field holds the chosen entry's NAME (as the sheet and
  Foundry expect). For an entry with a buy list (`{name, cost}` items plus a
  positive `*_points` number, `heroBuyList`), purchases are a JSON array of names in
  `<field>_choices_json`. The server checks every pick against the plan: unknown
  steps, entries or options, duplicates and overspending are refused. Privacy
  follows the campaign's new-page default.
- **Hero-choice rules** (systems `.ai.md`, ADR-075) arrive in the plan: `choices[].state`
  (`ask_first`) and `steps[].rules`. `HeroPlan` for a Player is read with the rules
  on; a Scribe's is `WithUnlimitedPlan`; a Director's `?as=<userId>` previews one
  player's. A step with `rules.limited` is a pick from the list even where the
  system's text is free (H1); `rules.required` can't be emptied or skipped, and a
  `prefilled` step is filled in by the server (H2); `Held` (never served) lets a
  hero that holds an entry the rules took off keep editing what it bought (H5).
  `buildHeroFields` returns ask-first picks as asks; the handler records them
  through `HeroRules` after the hero exists (`201 {..., requests, requestFailed?}`),
  and `UpdateFieldsAPI` takes them out of a claimed owner's patch
  (`takeAskFirst`) and answers `{status, requests}`: the pick never reaches
  `fields_data`. A player's AI is refused an ask-first entry
  (`authorizeFieldsWriteAs(..., refuseAsk=true)`). The fields GET adds
  `choice_breaks` (rules the hero already breaks) for the hero's player and
  Directors, and `choice_waiting` (blanks waiting on a Director).
- The draft lives in `localStorage` (`chronicle:hero-draft:<campaign>`; practice and
  try-out have their own keys) until the hero is made.
- **Layout:** the creator measures its mount, not the window: 900px or wider gets
  the desk (rail, card grid, right pane that reads the focused entry and holds the
  Choose button); narrower gets the phone (step header opening a step list, chip row
  of picks, a hand of cards, a bottom sheet for the entry with scrim, drag, inert
  background, Tab trap and focus returned to the card). Choosing an entry fills its
  chip or rail row and moves to the next open step. Entries with a buy list show a
  points meter and buy cards inside the entry. The die deals one card at random
  (d10 up to ten entries, percentile above; Ask first and Not offered entries are not
  dealt). Create is never blocked on the client; the server refuses what the rules
  forbid.
- **Skins:** the mount's `data-skin` (`plain`, `paper`, `ornate`; plain when absent)
  picks a `--hc-*` token set in `static/css/hero_creator.css`. Plain is the site's
  own tokens; paper and ornate load their fonts only when named. Light or dark
  follows the site (`html.dark`), never the skin. The Customize card look no longer
  reaches the creator. "Own entries" is a tool with Plain tokens
  (`.hc--tool`) in `static/css/own_entries.css`.
- **Motion:** `html[data-motion]` `full` is Lively (flight, deal, sheet slides),
  `calm` is Gentle (fades, a slide one seventh the size, durations at most
  180ms), `off` or a device that prefers reduced motion is Still (instant, a
  colour cue). The level is mirrored on `.hc-app[data-mo]`; signed durations pass through
  `ms()` so the owner's Motion speed retimes them.
- **Rules words:** `data-terms-url` names a glossary
  `{"terms": {"<key>": {name, category, text}}}`, read once beside the plan. The key
  is the term as written in `{@category term|label}`, lowercased, trimmed, with
  whitespace runs turned into "-" (`termKey`). A known marker becomes a button that
  opens one hover card (hover, focus or tap; Escape closes); an unknown word, a
  failing request or no address leaves plain words. All text is escaped. The
  built-in marks (Ask first, Not offered here, locked, own, campaign) use the same
  card.
- **Stage look:** `GET .../characters/new?look=stage` (only that exact value;
  `heroLookFrom`) puts `data-look="stage"` on the mount and links
  `static/css/hero_stage.css`; without it the creator is the classic one, byte for
  byte in behaviour. `static/js/hero_stage.js`, listed ahead of `hero_creator.js` in
  the registry, defines `window.ChronicleHeroStage(Creator, kit)`, a subclass that
  `hero_creator.js` builds once and uses when the mount names the look; `kit` hands
  over the helpers it borrows. The base keeps small named seams the subclass
  overrides (`topHTML`/`barHTML`, `chipsBlockHTML`, `cardIx`, `railHead`,
  `aboutHeadHTML`, `room`, `flightTarget`/`prepFlight`/`landed`, `glowPick`) and
  `save()` records `kept`. It draws the hero (portrait, name, line, and Stamina,
  Speed, Size and Stability tiles only when some entry in the plan can give one) in a
  banner on a phone and at the head of the rail on a computer, in the campaign's
  accent held dark enough for white words; there is no chip row, and the chosen card
  flies to the hero's line. The creator fills the window above the docked Table bar
  and makes `#sidebar` and `#app-topbar` inert until `destroy()`. Its own bar says
  **Save and leave** (a link; **Leave** in a try-out or on a copy or change) and the
  draft's status. Looking at an entry shows what picking it would change, with the
  pick set, read and put back (nothing saved); on a phone the stage tucks when the
  body scrolls past 48px; a mouse drags and wheels the hand. The review card is the
  hero, and About your hero's head says it is optional. Test:
  `test/js/hero_stage_browser.test.mjs`; the page switch is
  `TestNewHero_StageLook`.
- Tests: `test/js/hero_creator_browser.test.mjs`, `_practice_`, `_tryout_` and
  `_terms_browser.test.mjs`.

### Hero builder

On the Characters page, `heroBuilder` in `characters.templ` mounts
`data-widget="hero-builder"` (loaded on sight, ADR-063) when the viewer has heroes
of their own (`CastView.Builder`, `buildHeroBuilder`). Each hero reads as a
sentence ("Tess's ancestry is [..], class is [..]") with a blank per plan step; a
blank opens a panel listing every entry with roll range, facts and text (under the
hero on a phone). A new hero is made in the hero creator: the page's Create hero
(`data-create-hero`) is a plain link to `/characters/new`, and the builder offers
no sentence for a hero that does not exist yet.

- **Heroes** are the viewer's own pages of a listed character type
  (`builderHeroes`). For anyone but owner and Co-DMs, fields the type or page marks
  GM-only are left out of the sentence and the mount data.
- **Saving:** a pick on an existing hero is `PUT .../entities/:eid/fields`
  `{fields_patch: {key: name}}` through the builder-step door in `identity_edit.go`;
  a refused save restores the blank. Roll everything left sends one patch; Undo
  sends the earlier values (null clears).
- **A sentence draft kept on a device** (`chronicle:hero-builder:<campaign>`, from
  the builder's old new-hero sentence) never reopens here. The creator takes it
  once as its starting picks when it has no draft of its own, then removes it.
- **Rolling:** up to ten entries use a d10, longer lists percentile dice, each entry
  owning an even share of faces. Dice go through `Chronicle.dice.roll` when present;
  without it, or if it refuses, faces are drawn at once.
- **Plan** (`GET .../characters/new/plan`) is readable by a Player who may make a
  hero, owns a character-type page, or was let write an entry of their own by a
  Director (their plan offers "make your own" or holds an entry they wrote;
  `mayReadHeroPlan`).
- Bought options (`<field>_choices_json`) are chosen only in the creator.
- **Hero-choice rules in the blanks:** the panel numbers dice over rollable entries
  only (Ask-first entries are listed with an "Ask first" mark and never rolled);
  entries marked Not here are absent and fold open from a "N not here" line with
  the Director's reasons. Picking an Ask-first entry on a saved hero sends the
  patch, reads `requests` from the answer, and the blank reads "<Entry>, waiting
  for your Director" beside any value the hero already holds (the waiting pick
  is never in the hero's fields). A step with `rules.prefilled` is filled in and
  locked; `rules.required` with several entries is a short list. `rules.suggested`
  shows the Director's note; `requestFailed` on a new hero shows a plain line.
  Rows match plan entries by name since the plan's `choices[].key` is not read here.

### Changing heroes

A Director chooses when a player may change their own hero's builder picks
(`hero_changes.go`, `hero_changes_handler.go`, `hero_changes.templ`). The rule is
`hero_changes` in the campaign settings (`campaigns.HeroChangeRule`, read and
saved through `HeroChangeRules`, wired in `internal/app/hero_changes_adapters.go`):
some days after the hero is made, some days after each new level from a level on
(level 2 at the earliest), or both. No rule is any time, which is every campaign
until a Director sets one.

- **The window** (`heroChangeWindow`) is open while any of these is: the days
  after the page's `created_at`; the days after `level_at` while the hero is still
  at the recorded level; a Director's `reopened_until`. A level is recorded by
  `HeroChangeService.FieldsChanged`, a field observer, when a claimed page's
  `level` field goes up to 2 or more (`hero_change_state`).
- **What locks:** only a change to a builder step or what its entry bought
  (`heroPickChanges`): a stored value that is not blank and differs. Filling a
  blank finishes a hero and is always allowed; an Ask-first pick waits for a
  Director anyway and is never locked. Staff are never locked.
- **Every door:** the fields route (`UpdateFieldsAPI`, 403 with the reason), a
  player's Foundry edit (`syncapi` `judgeActingPlayer`, held with the reason) and
  a player's AI (`aiPlayerSheets`, held or refused) all ask the same service.
- **The bell:** a change one of those doors stores rings the owner and every
  Co-DM (`hero_changed`, "Ana changed Tess", detail "Class: Fury → Tactician"),
  whatever the rule.
- **A level a player gave themselves:** when a player's Foundry write raises the
  level of a hero they claim, the same Directors get `hero_level_raised`, "Ana
  raised Tess to level 3", with no detail and nothing else from the page,
  whatever the rule. The level still counts and opens a level window. Staff,
  the plain sync (no `actingUserId`), and a level that stays or drops ring
  nothing. A Director who sets the level back also takes the window back, since
  a level window counts only while the hero is at the recorded level.
- **The builder** gets each hero's `lock` (`HeroLock`) in the mount data when the
  campaign has a rule: a line under the name says until when the picks are open,
  or that they are set and which level opens them; a chosen step offers no
  Choose or roll while shut. A 403 that says locked turns the line on.
- **Directors** see "Changing heroes" on the Characters page: the rule in a
  sentence, a fold to change it (`POST .../characters/hero-changes`), and, under
  a rule, each claimed hero with its state and "Open picks" for some days
  (`POST .../characters/hero-changes/:eid/reopen`). The routes admit Scribes
  and up; the handlers answer 404 to anyone but the Director team.
- While the `hero_changes` schema is unhealthy the service is not wired: every
  hero is open and nothing rings.

### Practice heroes

A player has one hero at a time; a practice hero lets them try other builds
without using that slot. It is **not an `entities` row**: it is a saved
hero-creator result (a name and the picks) in `practice_heroes` (migration
`001_practice_heroes` in `practiceschema/`, its own slug `entity_practice`, so a failed
practice migration leaves only practice heroes out and never the Standing block). Every "who is a hero" reader, visibility rule and the Foundry
sync works on entities, so a practice hero is invisible to the party, the DM
Screen, game nights, the AI's party and Foundry by construction. Nothing here
touches entity rows, visibility or syncapi.

- **Who:** making, changing, asking and the shelf are for `MemberRole ==
  RolePlayer` exactly (a Scribe or Director gets the 404 a stranger gets), with the
  `player-character-claiming` addon and a hero page type players may claim
  (`PracticeService.Target`, the same `pickHeroType(..., claimableOnly)` the
  creator uses); a player who already has a hero qualifies. Opening one: its
  maker, or a Director (`CanAuthorDmOnly`); everyone else, Scribes who are not
  Directors included, gets 404. Changing, asking and throwing away: the maker
  only (a Director gets 404). Answering an ask: Directors only.
- **Cap:** `MaxPracticeHeroes` (3) per player per campaign. `PracticeRepository.Insert`
  takes a named lock (`GET_LOCK`, hashed from campaign and maker, on one
  connection, released after the insert) around a conditional `INSERT ... SELECT`,
  so the count and the insert never interleave whatever the isolation level
  (the integration test runs the race at READ COMMITTED too). A deadlock between
  different makers' statements is retried.
- **Practice plan** (`GET .../characters/practice/plan`): the player's own
  limited plan (`HeroPlanner.HeroPlan`, never unlimited, never the Directors'
  view) with every `HeroStep.Held` entry put back as `state: "not_offered"`;
  ask-first entries keep `ask_first`; step rules are dropped so nothing is
  locked, forced or asked for; `HeroPlan.Practice` is true. `Held` comes from
  systems' `Excluded`, which `Limit` fills after the visibility overlay, so it is
  a subset of what that player may read, carried whole. Entries a required short
  list leaves out come back the same way. `practicePlan` builds it.
- **Saving:** `POST .../characters/practice` `{name, picks, copy?}` (201 `{id,
  url}`), `PUT .../characters/practice/:pid` (clears a waiting or declined ask).
  Picks are checked by `resolveHeroPicks`, shared with `buildHeroFields` (unknown
  step, entry not in the practice plan, option budget): ask-first and
  not-offered picks are stored as plain picks and no request is recorded. Only
  validated picks are stored, never derived fields; the body is read through a
  128 KB limit and the stored picks are bounded at 64 KB. `copy: true` makes the
  server read the player's own hero again (same GM-only field filtering as the
  builder, `practiceCopyFields`) for the "A copy of <hero>" line and the level,
  so a client cannot claim either.
- **Pages:** `GET .../characters/practice/new` is the creator in practice mode
  (`?from=hero` a copy, `?edit=<id>` a change); `GET .../practice/:pid` is the
  page. Each pick is a row; an entry the rules keep from the maker carries "Not
  offered at this table. Needs the Director's yes to play." (ask-first: "Ask first
  at this table."), worked out from the maker's plan when the page is drawn.
  `DELETE .../practice/:pid` deletes outright (not the Trash, not recorded as a
  hero change).
- **Ask and answer:** `POST .../practice/:pid/ask` (maker) sets `ask_status`
  `waiting`; `/decline` (Director, optional `note`) sets `declined`, which the
  maker reads as "The Director said not now." with the note; `/allow` (Director,
  with `seen`) promotes it. The Characters page lists every practice hero to
  Directors, waiting ones first, with "Say yes" and "Not now"; a yes for a player
  who has a hero asks first, in the row, saying "<Old hero> goes back to Free to
  pick." A waiting row also carries a muted "Holds picks you don't offer <Player>:
  <names>." when its picks include entries the maker's rules do not offer or hold
  for a word (`PracticeService.HeldPicks`, one maker plan per waiting maker, at
  most three names then "and N more"; the names come from the maker's own plan).
- **A Director's yes** (`PracticeService.Promote`, in `practice_promote.go`; the
  handler binds `seen`, calls it, writes the audit entry and draws the page):
  checks the stored picks against the maker's own plan with `WithUnlimitedPlan`
  (the yes covers held entries), then claims the row (`TakeWaiting`: one
  transaction that locks the waiting row, refuses with "This practice hero
  changed. Look again before saying yes." when its version (`updated_at`) is not
  the `seen` the Director's form carried, deletes it and returns it), and builds
  the hero from the claimed row, so two Directors cannot both promote it and a
  maker's change and re-ask after the Director looked is never approved unseen.
  The hero is made through `createHeroPage` (the function `CreateHero` also uses;
  owner = the maker, playable, the copied level when the page type has a `level`
  field) and is **not private**, which is what the maker's own creation yields:
  the creator passes `cc.NewPagePrivacy(...)`, the yes passes false because the
  maker must be a Player. The maker must still be a Player (409 otherwise). A
  failed build or create puts the row back as it was (same version). Then the
  maker's current hero is released through `HeroReleaser.ReleaseOne` (owner
  cleared, playable kept, as a leaver's hero is; no event is published, so Foundry
  is not told). The handler writes `entity.created` before anything about the old
  hero can fail; if the release fails the new hero stands and the Characters page
  comes back with a lasting alert naming both heroes ("<New> is now <Player>'s
  hero, but <Old> couldn't be freed. Open <Old> and free it.").
- **Leaving:** the member-removed hook (leave, removal, account deletion) deletes
  that person's practice heroes in the campaign; a guest merge moves them to the
  target and keeps the newest three; campaign delete is the FK cascade. A member
  whose role changes to anything but Player (`campaigns.OnMemberRoleChanged`, run
  by `UpdateMemberRole` and the admin role update) has their waiting asks put back
  to not asked; the heroes stay on their shelf. An ownership transfer does not run
  that hook. All are wired in `internal/app/routes.go`.
- **Creator JS** (`static/js/hero_creator.js`) goes into practice mode from
  `data-practice="true"` (`data-update-url`, `data-preload` for a copy or change):
  a band, "Not offered here" seals, ask-first picked as a plain pick, "Keep this
  practice hero" / "Save changes", the draft key `chronicle:hero-practice:<campaign>`
  (no draft for a preload). Saving goes through `persist()` alone.
- **Swap safety:** the shelf, the Directors' list and the page use inline IIFE
  handlers from `practice_onclick.go` and no script tags; proof in
  `practice_handler_test.go`.

- **The try-out (look-around visitors):** a signed-in non-member on a live
  look-around pass (`cc.VisitUntil` in the future, `!IsMember`) builds one
  practice hero that lives only in their browser. **A visitor writes nothing to
  the server**: its routes are GET only, on the public-capable group
  (`GET .../characters/try`, `.../try/plan`, `.../try/terms`), and no write route
  for a visitor exists or may be added. Each handler admits only that viewer
  (`tryoutReady`), with the claiming addon on, `SetVisitorPlanner` wired and a
  hero page type players may claim; everyone else gets 404 (anonymous, an
  ordinary signed-in reader, an expired pass), except a Player, whose page route
  redirects to the practice creator. Every other route, the stage-one practice
  routes and the creator's included, still refuses a visitor.
- **Visitor plan:** `VisitorPlanner.VisitorPlan` (adapter in
  `internal/app/hero_planner_adapter.go`) reads the creator plan under
  `systems.WithChoiceVisitor`, which rewrites the context so no wrapper can widen
  it (not a Director, no account, not unlimited), skips a Director-only data file
  (the test `SystemDataAPI` makes), skips registered extra sources, drops anything
  kept to a character, a draft or a player's own, and applies the rules as for a
  player with no account (rows for everyone narrow the list; rows naming a player
  never reach it). The campaign's own entries come through the same overlay a
  signed-out reader's catalog uses, so what is offered is what the public can
  already read. The adapter copies entries only; `tryoutPlan` then rebuilds the
  plan from an allow-list: no `Rules` (not-here names and reasons), no held list,
  no waiting or suggested asks, no make-your-own offer, ask-first entries as plain
  choices, steps with nothing to pick dropped; `practice` and `tryout` are true.
  Proof: `systems/choice_visitor_test.go`, `tryout_plan_test.go`.
- **Where it lives:** `localStorage` key `chronicle:hero-tryout:<campaign>:<user>`
  holding `{v:1, name, picks, summary, savedAt}`. The creator (`data-tryout="true"`,
  the band "Trying it out. Kept in this browser only.", "Keep it on this device")
  writes it and goes back to the Characters page; no request but the plan GET is
  made; a stored one opens the page filled in; a browser that will not store says
  "This browser won't keep things, so the try-out can't be saved here." One
  try-out per campaign per browser. The server never reads or learns it.
- **Characters page mounts** (`tryout_mount.templ`, `static/js/hero_tryout.js`,
  widget `hero-tryout`, loaded on sight): `visitor` is the visitor's Practice
  section ("kept on this device": the row with "Change it" and "Throw it away", or
  "Try the hero builder"), `offer` is a Player's "You built <name> while you were
  looking around." with "Make <name> my hero" and "Not now" (sessionStorage hides
  it for the session), `shelf` is the same try-out as the last row of the Practice
  shelf ("On this device"). The server draws shells only; the widget fills them
  with `textContent`, never markup, and every mount reads the same key. "Make my
  hero" is the one request: `POST .../characters/new` (the creator's own save,
  which checks every pick against the player's real plan) or, for a player who has
  a hero (`data-has-hero`), `POST .../characters/practice`. On success the try-out
  is removed; a refusal keeps it, writes the creator's draft key
  (`chronicle:hero-draft:<campaign>`, or `chronicle:hero-practice:<campaign>`) and a
  one-time sessionStorage notice (`chronicle:hero-handoff:<campaign>`, shown in the
  creator's band) and opens that creator.

### Own entries

`GET /campaigns/:id/characters/entries`, named "Own entries" for everyone. A Director
reaches it from the "Own entries" row under Game in Campaign settings (which counts
entries and handed-in drafts, and lists waiting drafts under Needs you) and from
"Before you play"; the bare address opens the page. Tabs and the settings row count accepted entries, with what waits on a Director beside them ("5 · 1 waiting": handed-in drafts plus Ask-first picks, the same on the tab, the row, Needs you and the sidebar badge); a Director's page opens on the first list with a waiting draft, else with entries, and lists every waiting draft at the top. A Director adds the campaign's own
entries to the creator's pick lists; a site-look page with a tab per step. A player
who may read the plan opens it too, limited to lists a Director let them write in
(`?field=` opens a tab; `?for=` names their hero, whose sheet takes the new entry's
name; `?back=new` links back to the creator). The Rules page's top bar links it for
Directors who may edit the book (`static/js/widgets/rulebook.js`).
`static/js/own_entries.js` mounts on `[data-own-entries]`, reads steps and the
system's entries from the creator plan (Directors may read it without being able to
make a hero), and reads/writes the campaign's entries through the systems plugin's
`/campaigns/:id/system-entries` API, which enforces the Director rule and validates
every list.

- **Editor** grows over the page from the clicked row: form left, the player's
  creator view right (points can be test-spent). Unsaved writing asks before
  being dropped.
- **Form shape** (`shapeOf`): fact lines for scalar properties at least half the
  system's own entries share; a list section for each list of named items at least
  half carry (items with a cost are bought from); and the `*_points` budget. Facts
  save under a snake_case key, numbers as numbers; lists save only named items.
  Problems the server would refuse block Save; an unspendable budget warns.
- **Text** is server-sanitized HTML; "Hide from players" wraps a passage in
  `<span data-secret>`, which players never receive.
- **Player-made entries:** under each list a Director lets a player write one entry
  with the points budget, renews a used permission or takes it back. A player's entry
  shows Draft or Waiting for you; opening a handed-in one offers Ask for changes
  (with a note) and Accept (with who sees it). The player's editor has no hidden
  passages, a locked budget, Save draft and Hand it in, and shows the Director's
  note. Players do not come here to write: the creator, the Characters-page hero
  builder and the sheet's pick list each offer "Make your own ..." in place (below).
- **One shared editor** (`static/js/own_entry_editor.js` + `css/own_entry_editor.css`,
  `window.ChronicleOwnEntry`): the pure form logic (`shapeOf`, `problems`, `tidy`, ...)
  and an `Editor` that mounts into a host-owned body and foot. `own_entries.js`
  aliases the pure helpers, so it needs the editor script listed first (registry in
  `internal/app/routes.go`, for the hero-creator, hero-builder and own-entries
  widgets). The editor loads its own stylesheet from its script's address and
  reads `/system-entries/grants` for the locked budget. It shows name, short
  description, fact lines, lists, a "How a hero buys it" try-spend preview that
  reuses the creator's meter wording ("Needs N points, M left"), Save draft, Hand it
  in, server errors inline and an unsaved-close confirm. Blocking problems show only
  after the first attempt.
- **In the creator:** while a step's `canMake` is true (the grant is unspent) the
  hand ends with a dashed "Make your own <step>" card, with a row in List and a card
  in the desk grid, marked "Your Director allows one". It opens the editor in the
  sheet (phone) or the right pane (computer). Own entries lead the hand marked
  Draft, Waiting for your Director or Changes asked, and are choosable; the detail
  shows the Director's note and an edit bar. Practice and try-out never show the
  card. The creator keeps a picked draft for the hero it makes.
- **In the hero builder:** a dashed make row in each blank's panel (also when the
  list is otherwise empty) opens the editor in the panel; a saved entry joins the
  list and is picked for the hero. The sheet pick list (`choice_picker.js`) does the
  same in its fold, loading the editor script on demand.
- **Tests:** `test/js/hero_creator_own_browser.test.mjs`,
  `hero_builder_own_browser.test.mjs`, `own_entries.test.mjs`,
  `own_entries_browser.test.mjs`.
- **Director's marks** (`own_entries.js`, ADR-075): each tab lists every entry of the
  step, built-in and the campaign's own, from `GET .../choice-rules/entries` (the
  page's `data-entries-url` base), each with a quiet mark (Ask first, Not here,
  Everyone takes it; Open shows nothing) and a three-dots menu: the four marks for
  everyone, "For one player..." (a second step picks the player, a third their
  mark, including Open as an exception), and a reason. The first row is the group
  "This campaign's own". "Showing" switches the list to `?as=<player>`. "Mark the
  rest..." marks every unmarked entry at once (saves are chunked at 200). A mark
  that could break heroes already made (Not here, Everyone takes it) is checked
  with `POST .../choice-rules/check` first and the strip names them; a quiet mark
  saves at once. Requests waiting on the Director show above the list with Allow
  and Suggest another. Deleting an entry says how many hero rules it is in
  (`.../choice-rules/count`). Name-clash warnings and orphaned rules show quietly
  under the list. Players never get this UI (`data-director`).
- **Paste from an AI** reads the AI Import format (YAML front matter, then text)
  into the form for checking; nothing saves until Save. "Copy the guide" copies that
  format with the pick list's shape and one of the system's own entries as a model.

## `contents` block

A core layout block (`Type: "contents"`, `Contexts: ["template"]`, `Singleton`, no
tile sizes; `registerContentsBlock`). No route, table or setting: the server renders
an empty shell (`blockContents`), and `static/js/page_contents.js` (widget
`page-contents`, loaded on sight via the entities registration in
`internal/app/routes.go`) reads the `h1`-`h3` headings of the page's rich-text
editor from the viewer's own rendered page, so a viewer only gets headings their
page shows (an all-Director heading arrives empty for a player and is skipped; one
wholly in a `[data-secret]` mark carries the DM tag for the Director). Fewer than
four headings draws nothing.

- **Rail or button is decided by room beside the sidebar.** `placement()` takes the
  page area's rect (`#main-content`), the sidebar's rect and the window. The rail
  sits at the page area's left edge + 8px, never left of the sidebar's right edge
  (open 256px, folded 48px, hidden 0, and while sliding via a `ResizeObserver` on
  both). While a rail is wanted the script adds `ct-railed` to `#main-content`,
  reserving a 40px gutter. When the area cannot hold the gutter plus 520px of text,
  or the window is 767px or narrower, the block is a labelled Contents button
  instead. The panel is `position: fixed` from the area's left edge in both modes.
- `destroy` removes `ct-railed`, so a boosted navigation (which keeps
  `#main-content`) leaves no gutter.
- Every shell handler is an inline IIFE (`contentsCall`); a test pins that each
  named handler exists in the script. Tests: `test/js/page_contents.test.mjs`,
  `contents_block_test.go`.
- The editor's own "On this page" outline (`editor_outline.js`, with
  `data-outline`) is separate; a page with both shows both.

## New categories and tags/relations

A category created now (`CreateEntityType`, a campaign's seeded categories,
the "Standard" layout preset) is stored with `NewCategoryLayout()`: the
default plus `tags` and `relations` under the title. `DefaultLayout()` itself is
unchanged, because it is what a type with no stored rows falls back to when a
block is placed into it, and existing categories' stored layouts are never
rewritten. In the Annals look, a page with no tags, no relations and no extra
places shows no add control at rest (`data-tp-empty`, `data-rel-empty`,
`data-places-empty`, hidden by `page_look_annals.css`); while Edit page is on
they show as quiet words ("Add a tag", "Add a relation", "Add a place"). Other
looks and pages without the page editor keep the controls visible, since they
have no Edit page to reveal them.

## `character_surface` block

A layout block (`Type: "character_surface"`, `Contexts: ["template"]`, `Singleton`,
`block_registry_core.go`) and the default layout for player-character types:
`CreateEntityType` gives `isPlayerCharacterType(...)` types `CharacterLayout()`
(`model.go`) instead of `DefaultLayout()`. Owners can customize it in the layout
editor.

- **Server** (`character_surface.go`, `character_surface_block.templ`):
  `blockCharacterSurface` emits `<div data-widget="dynamic-surface">` + an inline
  `<script type="application/json" data-surface-schema>` from
  `CharacterSurfaceSchemaJSON(entity, entityType, campaignID, csrf, canEdit,
  canSeeGM, isOwner, pictureEndpoint)`: data seeded (no extra fetch),
  `json.Marshal`-escaped. `canEdit` is `canWriteDescription`, so the claimed
  owner's description box opens editable. `pictureEndpoint`
  (`surfacePictureEndpoint`, empty unless `canChangeOwnPage`) makes the
  `char-header` portrait the `image-upload` widget's picker.
- **Client** (`static/js/widgets/character_surface.js`, after `dynamic_surface.js`):
  registers box renderers `char-header`, `char-attributes`, `char-entry`; a System
  can override by re-registering the names. The surface is usually built before
  these register, so the frame paints such boxes when their renderer arrives.
- **Security:** the description box mounts the standard `editor` widget rather than
  inlining `EntryHTML`, which would bypass role-aware secret stripping.
- **Auto-premake on addon enable** (`EnsurePlayerCharacterType`; doc comment has the
  three cases): idempotent, only nests/creates, never touches existing data. Wired
  from `addons.EnableForCampaign` -> `ApplyAddonEnableEffects`, replayed by the
  startup backfill (`internal/app/backfill.go`). Tests: `ensure_pc_type_test.go`.
- **Duplicate reconciliation** (`MergeDuplicatePlayerCharacterType`; doc comment has
  the mechanism): handles what migration `000030` (kept permanently: deleting an
  applied migration crash-loops boot, ADR-044) does not auto-merge, surfaced by the
  player-character SetupProvider (`addons/.ai.md` "Setup Provider framework"). Calls
  `MoveEntitiesAndDeleteType`, which reassigns `entity_type_id` before deleting
  (mandatory: ON DELETE CASCADE). Idempotent. Tests: `merge_duplicate_pc_test.go`,
  `pc_setup_snapshot_test.go`.
- **One home for characters** (`AdoptDefaultCharacterType`,
  `ReconcileCharacterPresetHome`, `MoveCharacterPresetHome`): a system's character
  preset lives on the seeded top-level Characters type, not a twin. New installs
  adopt Characters; the boot sweep moves the sheet off an empty twin; a twin that
  holds pages is the owner's call, offered as the "home" step on the
  player-character setup page, which moves its pages (Trash included) and disables
  it with `claimable` false, never deleting it. Tests:
  `character_preset_home_test.go`, `app/setup_pc_test.go`.
- **Field reconcile in place** (`ReconcileEntityTypeFields`): lets a system pack add
  fields to an existing type; `mergeNewFields` appends declared fields whose `Key`
  is absent (never overwrites a user edit), persisted via `UpdateEntityType`, driven
  by `ApplySystemPresets` on install/update. Type schema only. Tests:
  `reconcile_fields_test.go`.
- **Single-owner duplicate guard** (`CreateEntityType`): one type per
  preset-category; a manual PC-type request when one exists gets `Conflict`, on top
  of the addon gate.
