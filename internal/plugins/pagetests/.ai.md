# Page Tests Plugin

## Purpose

The Tests page block (`page_tests`, one per page): long efforts the party makes
on a quest or adventure page (a montage test, a chase) and the result each ended
in. A test is the DM's own setup, not a game rule: a name, a kind (free text),
up to eight DM-named results, and two optional totals, the successes that end it
(`needed`) and the failures that end it (`limit`). A result can be offered when
a total fills (`on: "successes"` or `"failures"`); the DM records it by pressing
it, stamped with the campaign calendar's current date when there is one.

A recorded result is what an encounter version's pick reads
(`internal/plugins/encounters`, `ResultDirectory`): "Restore the Lastwell:
partial success" can choose which version of a fight plays.

A game system may offer a new test's starting setup through `chronicle:test-results` on `document`,
`{campaignId, reply(setup)}`, with setup `{kind, needed, limit, results:
[{label, on}]}`; without a reply a test starts with Success, Partial success
and Failure and no totals.

## Who may do what

| | See | Set up, tally, record, delete |
|---|---|---|
| Player (or anyone below Owner visibility) | shown tests only: name, kind, recorded result and its date label | no |
| DM (owner or granted co-DM) | every test, with results, totals and tally | yes, when the page's own edit rule also allows it |

A test is hidden from players until the DM ticks "Players see its name and
result". The player view is built by `presentToPlayer`, which copies only
those fields, so results, totals and the tally never leave the server for a
player. `GET /campaigns/:id/tests` (every test on a page the DM may see, for
the encounter builder) is DM-only.

## The block

Drawn with the shared block parts (`cb-head`, `cb-count`, `cb-section`, `cb-dm`,
`data-dm-only`), so page looks and style kits apply; `static/css/page_tests.css`
sets layout only, from theme tokens. A hidden test and the tally line carry
`data-dm-only`. Each write is one request carrying the version, one at a time; a
409 reloads the list.

## Table

`page_tests (id PK, campaign_id, entity_id, name, shown, data LONGTEXT,
version, created_by, updated_by, created_at, updated_at)`; `data` is `{kind,
needed, limit, successes, failures, results, recorded}`. FKs to core
`entities` and `campaigns` cascade, so deleting a page removes its tests; a
trashed page's tests are left out of the campaign list.

## Routes (JSON)

| Method | Path | Notes |
|--------|------|-------|
| GET | `/campaigns/:id/pages/:eid/tests` | `{tests, canEdit}`, filtered per viewer |
| POST | `/campaigns/:id/pages/:eid/tests` | body `{name, kind, shown, needed, limit, results}`; 20 per page |
| GET | `/campaigns/:id/tests` | DM: `[{id, page, name, results}]` for version picks |
| PUT | `/campaigns/:id/tests/:tid` | setup plus `version`; the tally and record are kept |
| POST | `/campaigns/:id/tests/:tid/tally` | `{side, step, version}`: one success or failure up or down |
| POST | `/campaigns/:id/tests/:tid/record` | `{result, reset, version}`: record, clear (empty result), or start again (`reset`) |
| DELETE | `/campaigns/:id/tests/:tid` | 204 |

## Rules

- Every write needs `version`; a mismatch is 409.
- At most one result per total, and a result offered on a total needs that
  total to be set. Successes are checked before failures; nothing is offered
  once a result is recorded.
- The tally stays between 0 and the side's total (or 30 when there is none).
  Saving a new setup trims the tally to the new totals, keeps the record when
  its result still exists (relabelled) and clears it when it does not.
- A calendar that fails is logged and the result is recorded without a date.
- Limits: name 120 characters, kind 40, result label 60, 1 to 8 results,
  totals 0 to 30, 20 tests per page, 16 KB request body.
