# Calendar Plugin

Two-mode calendar system for campaigns. **Fantasy mode**: arbitrary months, weekdays,
moons (with phase calculations), seasons (with wrap-around date ranges), leap years,
configurable time systems, weather state, zodiac/elemental cycles, festivals.
**Real-life mode**: Gregorian calendar synced to wall clock, user timezone-aware.
Both modes support events (single-day, multi-day, recurring with interval/end date,
with optional start/end times, color, icon, all_day). One calendar per campaign.

## Architecture

- **model.go**: Calendar, Month, Weekday, Moon, Season, Event structs + DTOs.
  `ModeFantasy`/`ModeRealLife` constants. `IsRealLife()` mode check.
  `MoonPhase()` / `MoonPhaseName()` for lunar cycle math.
  `IsLeapYear()`, `YearLengthForYear()`, `MonthDays()` for date arithmetic.
  `ContainsDate()` on Season with wrap-around support.
  `FormatCurrentTime()` on Calendar for HH:MM display.
  `HasTime()`, `FormatTime()`, `FormatEndTime()`, `FormatTimeRange()` on Event.
  `HasRichText()`, `PlainDescription()` on Event for rich text support.
- **repository.go**: SQL CRUD for calendar + sub-resources. Set* methods replace
  all records (bulk update). Event listing with entity JOIN, visibility filtering,
  recurring event support. Events sort by date then time (COALESCE for null times).
- **service.go**: One-calendar-per-campaign enforcement, validation, date advancement
  with month/year rollover (leap-year-aware), time advancement with minute→hour→day
  rollover, CRUD orchestration. Per-user visibility filtering via `filterEventsByUser()`
  and `canUserView()`. Input validation for time system values (positive integers),
  event names (max 255), event dates (month/day >= 1), visibility rules JSON.
- **handler.go**: HTTP handlers for monthly grid, timeline, settings, events, setup,
  advance date/time, import/export. HTMX detection for fragment vs full page. Mode-aware
  CreateCalendar seeds Gregorian months/weekdays for real-life mode.
- **routes.go**: Route registration with role middleware.
- **export.go**: Chronicle native JSON export format (`chronicle-calendar-v1`).
  `ChronicleExport` envelope with calendar config + optional events. `BuildExport()`
  creates export from a fully-loaded Calendar + events.
- **import.go**: Auto-detection and parsing of 4 calendar JSON formats:
  Chronicle native, Simple Calendar (Foundry VTT v1+v2), Calendaria (Foundry VTT),
  and Fantasy-Calendar.com. `DetectAndParse()` inspects top-level JSON keys to
  identify format, then delegates to format-specific parsers. Handles 0-indexed vs
  1-indexed conversion, localization key stripping, day-of-year→month+day conversion,
  and {values: {...}} nesting patterns. Returns `ImportResult` with normalized months,
  weekdays, moons, seasons, eras, and settings.
- **calendar.templ**: Monthly grid, timeline view, event modal (create/edit with
  TipTap rich text editor + @mentions, optional time picker), upcoming events fragment,
  entity-events fragment, setup page with mode chooser (Real Life / Custom Fantasy /
  Import from File). Timeline renders rich HTML descriptions with `templ.Raw()`.
- **calendar_settings.templ**: settings page tabs (General, Months, Weekdays,
  Moons, Seasons, Eras, Categories) with Alpine.js list management. General tab
  includes time system configuration (hours/day, minutes/hour, seconds/minute) and
  current time. Seasons tab includes weather effect field per season. Eras tab
  manages named time periods with year ranges. Real-life mode hides Months /
  Weekdays / Eras / Weather / Cycles / Festivals tabs and date/time/leap-year fields.
  Export button in settings header.
- **calendar_settings_wcf.templ**: Weather / Cycles / Festivals tabs (added in
  C-CAL-WCF-UI, 2026-05-19). Wire missing GET-via-eager-load + PUT pairs onto
  the existing settings page. Weather tab edits the single calendar_weather row
  (PresetID + temperature + wind + precipitation + zone + description). Cycles
  tab manages named periodic cycles + their entries (Tyr's Endlean / Seofean
  shape). Festivals tab manages fixed calendar entries (month+day OR after_month
  intercalary). All three forms render the wire-contract `{error, message,
  category}` error shape inline via respondSettingsError (see settings_errors.go).

## Data Model

- `calendars` — id, campaign_id, mode, name, description, epoch_name,
  current_year/month/day, hours_per_day, minutes_per_hour, seconds_per_minute,
  current_hour, current_minute, leap_year_every, leap_year_offset
- `calendar_months` — id, calendar_id, name, days, sort_order, is_intercalary,
  leap_year_days
- `calendar_weekdays` — id, calendar_id, name, sort_order
- `calendar_moons` — id, calendar_id, name, cycle_days, phase_offset, color
- `calendar_seasons` — id, calendar_id, name, start_month/day, end_month/day,
  description, color, weather_effect
- `calendar_eras` — id, calendar_id, name, start_year, end_year (nullable=ongoing),
  description, color, sort_order
- `calendar_events` — id, calendar_id, entity_id (FK), name, description (ProseMirror
  JSON for rich text, plain text for legacy), description_html (pre-rendered sanitized
  HTML), year/month/day, start_hour, start_minute, end_year/end_month/end_day, end_hour,
  end_minute, is_recurring, recurrence_type, visibility, visibility_rules (JSON,
  per-user allowed/denied lists, migration 000037), category, created_by

## Time System

Calendars have a configurable time system with three parameters:
- **hours_per_day** (default 24) — How many hours in one day
- **minutes_per_hour** (default 60) — How many minutes in one hour
- **seconds_per_minute** (default 60) — How many seconds in one minute

Current time is tracked via `current_hour` and `current_minute`. The `AdvanceTime()`
service method handles rollover: minutes overflow into hours, hours overflow into
days (which then roll over months/years via the same logic as `AdvanceDate()`).

Events optionally have `start_hour/start_minute` and `end_hour/end_minute` (all
nullable). When set, times display on grid chips, timeline, and entity event lists.

## Calendar Modes

Two modes controlled by `calendars.mode`:

- **Fantasy** (`mode='fantasy'`, default): Full customization — arbitrary months,
  weekdays, time units, leap years. All settings tabs visible. Setup seeds generic
  12×30-day months and 7 weekdays.
- **Real-Life** (`mode='reallife'`): Gregorian calendar synced to wall clock.
  Setup seeds correct Gregorian months (Jan 31, Feb 28 +1 leap, etc.), weekdays
  (Sunday–Saturday), 24/60/60 time, leap year every 4. Settings page hides Months,
  Weekdays tabs and date/time/time-system/leap-year fields (Gregorian is fixed).
  Current date/time derived from `time.Now()` + user's IANA timezone.

User timezone stored in `users.timezone` (nullable, default UTC). Managed via
`GET /account` settings page.

## Rich Text Event Descriptions

Event descriptions use the same dual-storage pattern as entity entries:
- **`description`**: ProseMirror JSON (from TipTap `getJSON()`) — used for re-editing
- **`description_html`**: Pre-rendered sanitized HTML (from TipTap `getHTML()` + `sanitize.HTML()`) — used for display

The event create/edit modal embeds a compact TipTap editor instance (no headings,
just inline formatting + @mentions). The editor is initialized lazily on first modal
open. On form submit, both JSON and HTML are sent to the backend.

Legacy events with plain text descriptions (created before Sprint 10) are handled
gracefully: `HasRichText()` returns false, `PlainDescription()` returns the text as-is.
When editing a legacy event, the plain text is loaded into the TipTap editor as a paragraph.

Timeline view renders `description_html` via `templ.Raw()` for rich text events, or
falls back to plain text `<p>` for legacy events. Tooltips use `PlainDescription()`
which returns empty for rich text events (ProseMirror JSON is not user-readable).

## Key Design Decisions

- **One calendar per campaign** (unlike maps' many-per-campaign). Enforced in
  service CreateCalendar().
- **Bulk sub-resource updates**: SetMonths/SetWeekdays/SetMoons/SetSeasons/SetEras
  replace all records rather than individual CRUD — simpler client-side serialization.
- **Percentage-free date system**: Month days and leap year days are integers.
  Year length calculated by summing month days + per-month leap extras.
- **Moon phases**: Continuous 0.0–1.0 value from `cycle_days` and `phase_offset`.
  Mapped to 8 named phases (New, Waxing Crescent, etc.).
- **Season wrap-around**: `ContainsDate()` handles seasons crossing year boundary
  (e.g., Winter from month 11 to month 2).
- **Event categories**: holiday, battle, quest, birthday, festival, travel, custom.
  Each has an icon in the UI.
- **Dual views**: Monthly grid (default) and timeline (chronological, year-grouped).
- **Per-user visibility**: Events support `visibility_rules` JSON column (migration
  000037) with `allowed_users` (whitelist) and `denied_users` (blacklist). Owners
  always see all events. Service-layer `filterEventsByUser()` applies rules after
  role-based filtering. UI in event modal (Owner-only) with Alpine.js member checkboxes.

## Import/Export

Calendar supports import from 4 external formats and export in Chronicle's native format.

### Supported Import Formats

| Format | Detection | Key Mapping |
|--------|-----------|-------------|
| **Chronicle** | `"format": "chronicle-calendar-v1"` | Native round-trip |
| **Simple Calendar** (Foundry VTT) | `"calendar"` key (v1) or `"exportVersion"` + `"calendars"` (v2) | `numberOfDays`→Days, `hoursInDay`→HoursPerDay, 0→1 indexed |
| **Calendaria** (Foundry VTT) | `"days.hoursPerDay"` or months-as-object | `days`/`leapDays`, day-of-year seasons, localization key stripping |
| **Fantasy-Calendar.com** | `"static_data"` + `"dynamic_data"` | `timespans`→Months, `global_week`→Weekdays, `cycle`→CycleDays |

### Export

`GET /campaigns/:id/calendar/export?events=true` returns JSON in Chronicle's native
format with all sub-resources + optional events. Settings page has download button.

### Import Flows

1. **Setup import** (`POST /calendar/import-setup`): Upload file during calendar
   creation. Creates new calendar + applies import + auto-enables addon.
2. **Existing calendar import** (`POST /calendar/import`): Replaces all sub-resources
   on an existing calendar. Destructive operation (months, weekdays, moons, seasons,
   eras all replaced).
3. **Preview** (`POST /calendar/import/preview`): Returns parsed preview without applying.

### Sync API

Import/export also available via REST API:
- `GET /api/v1/campaigns/:id/calendar/export` (read permission)
- `POST /api/v1/campaigns/:id/calendar/import` (write permission)

## Audit Log Taxonomy

Calendar mutations emit audit events at the HTTP handler layer (entities-plugin pattern) via `Handler.logCalendarAudit`, wired by `app/routes.go::calendarHandler.SetAuditService(...)`. Emission is fire-and-forget — failures `slog.Warn` but never block the primary write.

Event names (constants in `internal/plugins/audit/model.go`):

- `calendar.created`, `calendar.updated`, `calendar.deleted`
- `calendar.months_set`, `calendar.weekdays_set`, `calendar.moons_set`, `calendar.seasons_set`, `calendar.eras_set`, `calendar.categories_set`
- `calendar.weather_set`, `calendar.cycles_set`, `calendar.festivals_set`
- `calendar.weather_zones_set` — catalog replace (PR #360)
- `calendar.weather_active_zone_changed` — reserved for `SetActiveWeatherZone` direct calls (no current HTTP entry point; service-method only)
- `calendar.event_created`, `calendar.event_updated`, `calendar.event_deleted`, `calendar.event_visibility_changed`
- `calendar.date_advanced`, `calendar.time_advanced`
- `calendar.imported` — full import (file upload or setup-time)

**Counts-only payload discipline:** bulk Set* events log `{count: N}` in `Details`, not the full array. This matches V1-E precedent + keeps audit_log row size bounded for high-cardinality settings (e.g. categories).

**Per-era CRUD + `SetActiveWeatherZone` + `SetEventTierDefinitions`:** these service-layer methods have no HTTP entry point in calendar plugin today (`SetEventTierDefinitions` is exposed by the campaigns plugin and emits `campaign.event_tier_definitions.updated` there). Wave 1 will surface per-era CRUD via the in-card editor; audit emission will follow at that handler.

**Foundry sync (per-campaign-token) writes are NOT audited today.** SyncAPI's `APIHandler` uses per-campaign tokens with no user session; emitting with empty `user_id` would fail the audit-log validator. Operator decision required on actor model (synthetic `foundry-sync` user vs separate sync-audit table vs skip). Tracked as a follow-up.

## Security & Validation

- **IDOR protection**: `requireEventInCampaign()` verifies event's calendar belongs
  to the campaign before allowing modifications.
- **HTML sanitization**: Rich text `description_html` is sanitized via `sanitize.HTML()`
  on both Create and Update paths.
- **Input validation**: Event names (max 255), month/day (>= 1), time system values
  (hours_per_day, minutes_per_hour, seconds_per_minute must be >= 1), visibility
  enum (everyone/dm_only only), visibility_rules JSON validated on all write paths.
- **Visibility filtering**: `canUserView()` applies role-based + per-user JSON rules.
  Malformed JSON fails open with `slog.Warn` (validated on write, so only affects
  manually corrupted data). Owners always see everything.
- **Who the filter is deciding for is a TYPE, not a string pair
  (C-AUTHZ-EMPTY-USERID / ADR-049).** `calendarVisibleTo`,
  `filterCalendarsByUser` and `filterEventsByUser` take a
  `permissions.Viewer` and bypass only on `SkipsPerUserRules()`
  (`system || CanSeeDmOnly(role)`). They used to bypass on
  `CanSeeDmOnly(role) || userID == ""`, calling the empty user id "the system
  context" — but that is exactly what an ANONYMOUS request carries, so on a
  PUBLIC campaign a logged-out visitor was served every `dm_only` calendar and
  every per-user-restricted event. A `Viewer` built from a request
  (`permissions.RequestViewer`) can never be a system one: the `system` bit is
  unexported and only `permissions.SystemViewer` sets it. **This plugin has no
  system callers at all** — every exported service method builds a
  `RequestViewer` at its boundary. Pinned by `anonymous_visibility_test.go`
  (anonymous vs Player vs Owner, all three) and by the INVERTED rows in
  `calendar_visibility_w5a_test.go` and `entity_ties_test.go`.
- **Role enforcement**: Route middleware + CSRF tokens on all state-changing endpoints.

## Known Limitations

- **Recurring events**: shipped (chronicle#461, 2026-06-11) — weekly/biweekly/monthly/
  custom/**yearly** share the sessions recurrence vocabulary via a single
  `Event.OccursOn` expansion predicate, leap-aware monthly (migration 011).
  `yearly` was added by C-CALV4-GAMEREADY §6 [GR-11]; a base day absent from a
  later year is **SKIPPED, never clamped**. An unsupported `recurrence_type` is
  now a **400** at both event handlers ([GR-12]) instead of a 201 followed by a
  single silent occurrence. Recurrence end-date UI controls remain future polish
  (`C-CALV4-RECUR-END`); still no "edit series" workflow. **Multi-day SPANS now
  mark every day of their window** in the Block and the day card
  (C-CALV4-GAMEREADY §3 [GR-5]); a span that is also RECURRING marks its whole
  window only at the base occurrence — measured, pinned and booked as
  `C-CALV4-SPAN-RECURRENCE`, not designed.
- **No event duplication**: Users must manually recreate similar events.
- **No bulk delete**: Events must be deleted individually.
- **ApplyImport IS transactional**: `repository.go`'s `ApplyImport` wraps the multi-step
  import (calendar + months + weekdays + moons + seasons + eras) in one
  `BeginTx`/`Commit`/deferred `Rollback`.

## The real Moon (moon_fallback.go, 2026-08-11)

**A real-life calendar with ZERO `calendar_moons` rows shows THE Moon.** Pipeline
A (`BuildWorldStateSeed` → `moonSeeds`) has done this since
C-CAL-SKY-COMPLETION A; the Block spine did not, and the Bench never calls
`BuildWorldStateSeed`, so the surface the nav points at showed nothing. That was
the whole of "I don't see the real moon on the real calendar".

`synthesizedRealMoon(cal)` closes it by reshaping — never re-deriving —
`gregorianMoonPhase`'s answer into the `(CycleDays, PhaseOffset)` pair
`Moon.MoonPhase` steps through. **There is still exactly one implementation of
this astronomy.** `applyRealMoonFallback` is called from
`BlockService.hydrate` (so every Block host gets it) and from `draftCalendar`
(so the wizard previews the same body).

**THE THREE FOOTGUNS, in the order you will hit them:**

1. **One authored row switches it OFF.** The condition is `len(cal.Moons) == 0`,
   matching Pipeline A. That is deliberate — an operator's declaration must win
   whole — but it means **any code that seeds a moon onto a real-life calendar
   silently downgrades an exact Moon to whatever it seeded**. That is why
   `seedDefaults` seeds none and why the builder wizard's "Luna" was removed
   rather than persisted: measured, Luna ran **0.85 days behind the real sky**.
2. **The anchor is the calendar's CURRENT date, so ordering matters.** Call it
   AFTER `ApplyRealTime`, or a real-time calendar's Moon is pegged to whatever
   day the row was last written — and the discs still draw, just wrong.
3. **The accuracy has a stated band.** `Calendar.AbsoluteDay` counts with the
   calendar's own leap-every-4 rule (the Julian one), so it diverges from the
   true JDN by one day at each non-Gregorian century boundary. Exact to 2.089e-12
   cycles across 1901–2099; 1.0 day at 2100, 2.0 at 2200. Pinned by
   `TestRealMoonFallback_TheAccuracyBoundIsMeasuredNotAssumed`.

**Where it does NOT reach, on purpose:** the syncapi
(`internal/plugins/syncapi/calendar_api_handler.go`) reads `cal.Moons` off the
60-method calendar service, not the Block spine, so `GET /moons` still answers
`[]` for a real-world calendar and the Foundry module still shows no moon.
Booked in `.ai/todo.md` — the endpoint's partner `PUT /moons` writes rows, so
serving a row-less body through it is a contract question, not a read change.

## Entity Ties (C-CAL-ENTITY-TIES-DATA-MODEL, migration 009)

Optional many-to-many ties between **entities** and calendar **events/eras**,
each carrying a **participation role**. The real persistence behind Phase 1.5's
mock attach-entity picker (operator: "an entity can be but does not have to be
tied to events and eras" — both sides optional). **PR1 shipped the data model + service;
PR2 shipped the dual-side UI hooks** (create-entity ties picker in `calendar_v2.templ`
+ the `entity_calendar` block).

- **`participation_role` enum** (`entity_ties.go` `ParticipationRoles`):
  `involved · present · affected · mentioned` — PINNED to Phase 1.5 R3's
  showcase picker (`__calParticipationRoles`); keep identical so the Phase-2
  port swaps mock→real with no translation. Event ties require a role (empty →
  `involved`); era ties are coarser (role nullable). Validated in the service,
  stored as VARCHAR (not a SQL ENUM — easier to extend).
- **migration 009** (`entity_event_links`, `entity_era_links`): placement =
  **option (a)** hard cross-plugin FKs. Trivially safe: `entities` is a CORE
  table (always migrated before plugins), `calendar_events`/`calendar_eras` are
  this plugin's (migration 001). Precedent: `calendar_events.entity_id` already
  hard-FKs `entities(id)`. All FKs `ON DELETE CASCADE` → **cascade-on-delete is
  DB-enforced** (deleting an entity, event, or era drops its links) — no
  service-layer cascade.
- **entity_ties_repository.go**: link/unlink (idempotent upsert) + both-
  direction queries. `EntitiesForEvent`/`EntitiesForEra` JOIN entities +
  entity_types for display (same source the event list uses);
  `EventsForEntity`/`ErasForEntity` reuse the event/era column projections.
  `EntitiesForEvent`/`EntitiesForEra` take `role, userID` and apply
  `entityVisibilityFilter` (same helper `EntitiesForCalendar` uses, entities
  aliased `e` to match) — see "Entity-tie visibility leak fix" below
  (C-CAL-ENTITY-TIES-LEAK-FIX).
- **entity_ties_service.go**: enum validation + delegation. These methods are
  the **cross-plugin surface** the entities plugin (PR2) consumes via an
  interface — never a direct repo import (CLAUDE.md rule 8).
## World-State Model (C-CAL-WORLDSTATE-SERVER-MODEL, migration 008)

Server-side mirror of the showcase's browser-only `worldState` blob (the
synced atmosphere object driving the sky-band + hourglass). The deliverable is
**data + API, not UI** — it unblocks the Phase-2 production port and the
Phase-5b Foundry push.

- **worldstate.go**: the `WorldStateSeed` wire shape (camelCase JSON tags — a
  1:1 mirror of `static/js/cal-almanac.js` ~L464-481, CATALOG Part 8) + the
  pure `AssembleWorldStateSeed(cal, y, m, d, dayWeather, celestials, moonPhases,

  `Moon.MoonPhase` cycle math; named-phase vocab walk falls back to the
  showcase's short procedural names. New domain types: `DayWeather`,
  `CelestialEvent`, `MoonPhaseVocab`, `SpecialDay`.
- **worldstate_repository.go**: reads for the four migration-008 tables
  (`calendar_day_weather`, `calendar_celestial_events`, `calendar_moon_phases`,
  `calendar_special_days`) + `SetDayWeather`/`SetMoodTint` writes. All
  calendar-scoped (moon-phases join through `calendar_moons`).
- **worldstate_service.go**: `BuildWorldStateSeed` (loads + assembles) and
  `SetWorldState` (persists live mood + date/time via `UpdateCalendar`, emits
  `calendar.worldstate.changed`). `timepieceFill`/`timeControl` are ephemeral —
  never persisted; the seed emits `timeControl` with neutral defaults.
- **worldstate_handler.go** + routes: `GET/PUT /campaigns/:id/calendar/world-state`.
  GET = Player+ (GM-only celestial events filtered via `VisibilityRole`); PUT =
  Owner-only (route-level seam for the Phase-3 co-GM grant). No calId — resolves
  the active calendar (or `?calendarId=`). NB: the dispatch sketched an
  `/api/v1/` path but the GET/PUT are the session-auth production surface
  (roles + dm_only only exist on `CampaignContext`); a token-auth Foundry
  variant can layer on the same service later. **Superseded by
  C-CAL-WORLDSTATE-WIRE (below): the token-auth variant now exists.**
- **migration 008** also ALTERs `calendar_moons` (+base_design/tint/phase_source/
  size/orbit_speed — moon-library render params, read via `GetMoons`) and
  `calendars` (+mood_tint_color/intensity). The parity test
  `TestWorldStateSeed_ParityWithJSContract` is the load-bearing guard against
  server↔JS drift.
- **Footgun**: `SetMoons` (DELETE+INSERT replace) does not write the new moon
  render-prop columns, so a moon edit resets them to defaults. No UI authors
  them yet (read-only for now); revisit when a render-prop write path lands.

## World State on the Wire (C-CAL-WORLDSTATE-WIRE, 2026-07-26)

`calendar.worldstate.changed` and `calendar.weather.zones.changed` were
**publisher-side dead letters**. Both had live emitters — `SetWorldState`
(worldstate_service.go) and `SetWeatherZones` (service.go) — but
`calendarEventPublisherAdapter.PublishCalendarEvent` (`internal/app/routes.go`)
had no `case` for either name, so both hit its `default: return` and were
discarded before ever reaching the bus. Nothing logged. Every meteor, eclipse
and weather-zone edit the operator authored had been swallowed inside the
publisher since the day those emitters shipped. Traced by the Foundry
executor in Chronicle-Foundry-Module PR #82.

Three additive parts, all in this repo:

1. **Public types + adapter cases.** `ws.MsgCalendarWorldstateChanged` /
   `ws.MsgCalendarWeatherZonesChanged` (`internal/websocket/message.go`) plus
   the adapter cases. Pinned by `internal/app/routes_calendar_ws_test.go`,
   which asserts the WHOLE calendar mapping — a `default: return` is a
   silent-drop machine, so adding an emitter without a case must fail a test
   rather than a play session.

2. **Enriched payload, SPLIT BY AUDIENCE.** `WorldStateChangePayload`
   (worldstate.go) is a strict superset of the old `{date, moodTint}` shape —
   those two keep their exact paths because the Foundry module shipped
   `formatWorldstateLine` against them while the event was still a dead letter.
   Added: `events[]` (celestial detail with the STABLE
   `calendar_celestial_events` id, so a consumer dedupes a reconnect replay
   instead of duplicating a note), `moons[]`, `weather`, and an `audience`
   marker. Every nested type is reused verbatim from `WorldStateSeed`, so a
   consumer parses ONE celestial/moon/weather shape whether it arrived by push
   or by a GET refetch — the trap the weather path already fell into (flat
   `WeatherInput` on the wire vs nested `Weather` on the GET).

   **The split is the security property.** The hub gates on
   `Message.RequiresDM`, a PER-MESSAGE flag, so one message cannot be rich for

### The Block theater — depth on demand, from an embed that stays glanceable (C-CALV4-THEATER, R2-3, 2026-08-08)

`theater.go` · `theater.templ` · `static/css/calendar-theater.css` ·
`internal/plugins/calendar/static/js/calendar_theater.js`.

**The founding distinction, because everything else is downstream of it: there
are TWO things called "full tier".** The **CSS tier** — the 60px nameplate, the
named weekday columns, the Ledger docked *beside* the month — is a container
query against `.cal-block-host`'s inline size and nothing else, so widening the
box buys all of it for free. The **zone set** — whether a Ledger and a Shelf
exist in the render at all — is the PRODUCER's, resolved from `LayerState`, and
widening the box buys NONE of it. Moving the embed's existing Block into a wide
overlay therefore produces a **stretched glanceable month**, not a full-tier
Block. That is why the theater renders its own Block rather than borrowing one.

**ONE PROJECTION, TWO RENDERS.** `EntityCalendarBlock` passes neither
`LedgerHidden` nor `ShelfHidden` to the spine, and `block_projection.go` builds
both zone stubs unconditionally; the host then overwrites `d.Layers` post-hoc.
`Layers` is a **post-hoc display gate**, so the projection the page already
holds contains every mark the theater will print, and the theater's Block is a
**struct copy** — one copy, one extra template render, zero extra service work.
A second `spine.Block` call is not a cost to weigh; it is a sign somebody built
the refused fragment-route option by accident.

**THE PLUGIN NOW CARRIES THREE LAYER SEEDS WITH THREE DIFFERENT JOBS**, and the
next reader's instinct will be to unify two of them. Do not.

| seed | keys | job |
|---|---|---|
| `entityBlockLayers` | `moons, eras, weeknums` | the glanceable embed beside somebody's prose ([BR2-8]) |
| `benchBlockLayers` | + `ledger, shelf` | the Bench is a COCKPIT and depth is its job |
| `theaterBlockLayers` | the same five | depth ON REQUEST, over the page the reader is on |

All three go through `resolveBlockLayers`, so the **switchboard still wins**: a
viewer who has turned `shelf` off gets a theater with no Shelf. The theater is
not a second place layers are chosen.

**THE MOUNT CONTRACT — eight lines, and every one of them is a trap it exists to
keep the next host out of.** A surface gets the theater by doing exactly this:

1. Render the scaffold **once per `(calendar, entity)`** — one shared templ
   component, id-namespaced per block, never an unnamespaced copy. ([TH-15];
   the shipped precedent is the worldstate seed's `"cal-v2-worldstate-cal-" +
   entityID` one line above the mount.)
2. Emit it **outside** every `.cal-block-host` (the Block clips) and **inside** a
   `cal-bench` root — top-layer promotion does not change DOM ancestry, so a
   `<dialog>` outside `.cal-bench` gets no register at all. It **may** sit inside
   an HTMX-swappable region; see line 7. ([TH-14], re-signed 2026-08-08.)
3. **Copy the Block you already built; never project twice.** ([TH-2].)
4. **Re-namespace the copy's `Viewer.HostEntity`** before rendering it, or you
   ship duplicate DOM ids and a dead tie toggle. *This is the line that bites.*
   Every id and radio-group name the Block emits is a pure function of
   `(CalendarSlug, HostEntity)`, so two Blocks for one calendar emit identical
   ones, four radios land in one `name` group with two markup-`checked`, and the
   theater's `<label for=…>` resolves by document order to the EMBED's radio.
5. **Suppress the theater copy's switchboard** via the host-owned `LayerState`
   fields (`HasSwitchboard` / `PersistURL`, both cleared together); the EMBED
   keeps the one switchboard. A real absence in the render, never CSS hiding — a
   `display:none` switchboard is still reachable by keyboard and still writes
   the preference. ([TH-13]; **reversible**, and written down as reversible.)
6. **Mount the module through `pluginBodyScripts`, never a page `<script src>`.**
   `tools/page-script-allowlist.txt` pins `entity_calendar_block.templ` at
   exactly 1 and `tools/check-page-scripts.sh` is a shrink-only ratchet that
   fails ABOVE its number as well as below. ([TH-12].)
7. The module **re-inits on `htmx:afterSettle`**, returns immediately when its
   mount is absent, keeps an idempotent wiring guard, and **closes the theater on
   `htmx:beforeSwap` when the swap target contains it** — the required
   counterpart of line 2's permission, because a `<dialog>` removed from the DOM
   mid-modal strands the top layer, keeps the page scroll-locked and drops focus
   on a detached node.
8. Emit **none** of `data-bench-block` / `data-cal-daycard` /
   `data-cal-daycard-payload`. `calendar_daycard.js` rides the same registry and
   is ALREADY LOADED on every entity page; it is dormant only because of those
   three markers, and waking it on a page holding two Blocks with two Ledger
   states re-opens `C-CALV4-CARD-CROSSBLOCK-LEDGER` on a surface never measured
   against it. ([TH-1].)

**THE HAZARD A LATER SLICE WILL BREAK ON.** The entity page now carries TWO
Blocks for the same calendar, so `dayKey` produces the SAME `data-day` on both.
Nothing consumes it here today, but a future host that mounts the day card AND
the theater together must scope its queries to one Block.

**MOTION IS THE ONE REGISTER'S.** The scaffold carries `cal-bench` as a second
scope root and the theater's two reveal rules live BY NAME inside
`calendar-bench.css`'s single `@media (prefers-reduced-motion: no-preference)`
wrapper, exactly as the day card's do. `calendar-theater.css` declares no
`transition`, no `@keyframes` and no `--disc-*`, and a guard enforces it.
**`/schedule` is NOT the precedent** it was drafted as: it inherits the register's
TOKENS and consumes zero of its RULES, and its own guard bans `--disc-open`
there. Copying it faithfully would have shipped a theater with three tokens and
no motion, every guard green.

## Worldstate render architecture (2026-06)

The C-CAL-WORLDSTATE-GM-OVERHAUL work (chronicle#442 + the #443 r2 visual-review
fixes) reshaped how the ambient worldstate is drawn and controlled. Three things
to know before touching the sky band or GM console:

1. **CSS render/chrome split.** `static/css/cal-almanac-render.css` is the
   widget's RENDER layer — the shared styling loaded by EVERY surface (/demo,
   the `calendar_v2` band, both entity embeds, the dashboard shelf). It must stay
   shell-free: a rule scoped to `.cal-almanac-shell` silently skips production,
   which is the historical "works in /demo, broken in prod" bug class.
   `static/css/cal-almanac.css` is now demo CHROME only — it must not (re)style
   the render classes. This contract is the load-bearing guard in
   `test/js/css_render_split.test.mjs` (render layer stays shell-free, chrome
   never restyles render classes, every surface links the render layer, prod
   surfaces never load the demo chrome). NB: this supersedes the older
   "rendering-canvas CSS = cal-almanac.css" note in the Phase-2a section above.

2. **Two sky canvases + layered SKY_FX.** The engine paints a BACK canvas
   (`data-cal-sky-canvas`) and a FRONT canvas (`data-cal-sky-canvas-front`) so
   atmosphere can sit both behind and in front of the sun/moons. Weather and
   celestial events are rows in a single `SKY_FX` registry, each row declaring
   `{ back: [...], front: [...] }` FX builders. They compose by stacking — the
   `WS_LAYER_ORDER` (`timeOfDay · season · celestial · weather · events ·
   moodTint · timeControl`) means an active event (e.g. a meteor shower or
   eclipse) layers ON TOP of the current weather rather than replacing it
   (`celestialFor(...)` "can stack"). Both canvases ship on every surface,
   demo included (parity-asserted in the css-render-split test).

3. **GM console = strip + full-band sheets.** The live GM controls
   (`internal/plugins/calendar/static/css/gm_panel.css` +
   `static/js/gm_panel.js`, markup in `calendar_v2_gmpanel.templ`) are a slim
   always-visible STRIP at the band's top edge (clock + quick time verbs +
   section buttons) that collapses to a "GM" pill. Each section
   (Time/Weather/Events/Mood) opens as a translucent glass SHEET covering the
   sky pane below the strip (`data-gm-sheet` / `data-gm-sheet-open` /
   `data-gm-sheet-panel`); sheets close via ×/re-tap. The whole console is
   server-gated by `data.CanControlWorldState` (Owner or co-DM, #406) — players
   and Scribes never receive the markup, it is not a CSS hide.

## Event recurrence + editor action set (C-CAL-EDITOR-EXPANSION, 2026-06-11)

- **Recurrence has ONE expansion predicate: `Event.OccursOn(cal, y, m, d)`** (`model.go`). Types `weekly|biweekly|monthly|custom|yearly` mirror the sessions plugin's vocabulary (`yearly` added by C-CALV4-GAMEREADY §6); anything else (incl. an empty string) renders once at its stored date, and since [GR-12] the two event handlers **reject** an unsupported value with a 400 rather than storing it. All three day-projection helpers (`eventsForDay`, `eventsForWeekDay`, `allDayEventsForDay`) route through it — never re-implement date matching beside it. The month/range SQL only **widens the candidate set**, and that widening is **DERIVED from the `Recurrence*` constants** (`recurringCandidateClause`, `repository.go`) rather than typed out: it used to be a hand-written `IN ('weekly','biweekly','monthly','custom')` in three places, and when `yearly` shipped the predicate expanded it correctly while the ROW WAS NEVER LOADED. Placement happens in Go. **Multi-day spans are matched separately**, by `blockEventSpansDate` (`block_projection.go`) for placement and `spanningCandidateClause` (`repository.go`) for the month query — beside `OccursOn`, never inside it, because "does the recurrence rule put an instance here" and "is this day inside the stored window" are different questions and every other `OccursOn` consumer would have inherited the answer silently. The visibility filter wraps the widened set, so dm_only recurring events never reach players. `OccursOn` uses the same constant-year `absDayIndex` space as `v2WeekdayIndexFor` ON PURPOSE — weekly events must stay aligned with the grid's weekday columns; do not "fix" it to true leap-aware day counting.
- **`recurrence_day_of_week` (migration 011) is stored but unused** by expansion (base-anchored instead) — schema parity with sessions for a future alignment, not dead code to delete.
- **Cross-plugin entity creation** ("create entity from event") goes through the `EntityCreator` interface (`entity_actions.go`) + `calendarEntityCreatorAdapter` in `internal/app/routes.go` — rule-8 seam, mirrors bestiary. Calendar never imports the entities plugin.
- **World-state PUT additive field `weatherDate`** retargets the weather upsert to an arbitrary day (drawer's "set weather for this day"); absent = current date (wire-pinned). Bounds-validated against the calendar in `SetWorldState` (month/day must exist; year deliberately unbounded for fantasy eras).

## Event RSVPs (C-CAL-RSVP-P1, migration 013, 2026-07-25)

Calendar events now carry FIRST-CLASS RSVPs, distinct from the sessions plugin's
session attendance. See **ADR-046** for the full rationale; this section is the
implementation map.

**Supersedes** the in-code ruling on the drawer's disabled "Collect RSVPs" toggle
(`calendar_v2.templ`) that said RSVPs required an event↔session link. An event is
not a session — most events (festivals, downtime, one-off scenes) never will be.

**Storage (migration 013, plugin chain).**
- `calendar_event_rsvps` — one row per (event, user), `UNIQUE(event_id, user_id)`
  so re-answering UPDATEs in place. No response history to leak; a member cannot
  inflate a count by answering twice.
- `calendar_event_rsvp_tokens` — per-ACTION single-use opaque tokens
  (`crypto/rand` hex, 7-day TTL). Pattern-mirror of `session_rsvp_tokens` in a
  DISTINCT table, the `slot_proposal_tokens` precedent.
- `calendar_events.collect_rsvps` — per-event opt-in, default 0. Read rides
  `eventCols`; the WRITE is deliberately OFF the shared `UpdateEvent` path
  (`RSVPRepository.SetCollectRSVPs`) so the drawer's lossless quick-save, which
  re-sends the whole stored event shape, can never clobber the flag.

**Files.** `rsvp_model.go` (types, ENUM constants, action→status mapping),
`rsvp_repository.go`, `rsvp_service.go` (gating, tokens, week resolution),
`rsvp_handler.go` (campaign API + public token flow + the cross-plugin
interfaces), `rsvp_email.go` (fan-out + standalone token pages). Deliberately a
SEPARATE service/repository pair — `CalendarService`/`CalendarRepository` are
wide interfaces mirrored by a hand-written mock and the syncapi stub, so widening
them collides with every concurrent calendar lane.

**Routes** (`RegisterRSVPRoutes`, same middleware stack as `cg`):
- `POST /campaigns/:id/calendars/:calId/events/:eid/rsvp` — Player+; writes only
  the caller's own row (user id from the session, never the body). Optional
  `action` (`out_week` / `suggest`) reaches the two richer asks without a second
  endpoint per action.
- `GET  …/events/:eid/rsvps` — Player+. Counts for everyone; the per-person
  `responders` array is omitted server-side for anyone below Owner/co-DM
  (`CanControlWorldState()`), mirroring the scheduler overlay's
  density-for-all / identity-for-the-DM split.
- `PUT  …/events/:eid/rsvp-collection` — Scribe+. ON is the INVITE moment.
- `GET|POST /calendar-rsvp/:token` — PUBLIC, root-mounted, distinct from
  sessions' `/rsvp/:token`. GET = pure-read confirm interstitial (mail-scanner
  defence) or the suggestion form; POST = apply. Both ride the global CSRF
  middleware, so GET mints the cookie the POST double-submits.

**Security invariants** (each has a named test):
- One visibility predicate. Every path reuses `canUserView` — a second, subtly
  different path is exactly how the entity-ties leak happened.
- Self-write only. `AvailabilityExceptionWriter` and the RSVP upsert always
  receive the id from the session or the redeemed token.
- Tokens are re-checked at REDEMPTION for membership AND visibility, so a link
  cannot outlive the access that justified it. Unknown / spent / expired all
  return one generic message so the route is not an existence oracle.
- Consumption is atomic (`used_at IS NULL` in the UPDATE); the loser of a
  concurrent double-submit writes nothing.
- "Suggest another time" writes a NOTE + an owner notification. It does NOT mint
  a slot proposal — proposal creation is Scribe+ by ruling.
- RSVP data never rides the campaign or AI export (`rsvp_egress_test.go`).

**UI.** The drawer (Scribe+) owns the collection toggle and the counts/responders
readout. The QUICK-EDIT CARD owns the answer buttons, because the drawer is
Scribe+ and players never receive its DOM — one block there covers month chips,
ledger rows, and mobile agenda cards, which all open it via `[data-event-card]`.
Wiring is `addEventListener` in `event_grid.js` with per-node `dataset.*Wired`
guards, matching the file's existing convention: the quick-edit and drawer
scaffolds are PAGE-level (rendered by `CalendarV2Page`, outside the HTMX-swapped
view slot), so the inline-IIFE-onclick rule for HTMX-loaded fragments does not
apply here.

**"Out this week" week resolution.** Availability exceptions are real-world
dates; a calendar event may be in fantasy reckoning. When the calendar
`UsesRealTime()`, Y/M/D IS the Gregorian date and the event's own Monday-anchored
week is used. Otherwise it falls back to the week containing the redemption
moment — the scheduler's own "out this week" meaning. The resolved week is ALWAYS
named back to the member, so the action can never silently block the wrong one.
Days that already carry any exception are skipped, mirroring
`static/js/availability.js` `fireOutWeek`.

**Cross-plugin seams** (rule 8 / ADR-042; all nil-safe, all wired from
`internal/app/routes.go`): `MailSender` (smtp), `RSVPNotifier` →
`sessions.NotifyUsers` (the first external writer of the generic notifications
store, T-B2), `AvailabilityExceptionWriter` → sessions `ListMyExceptions` /
`ReplaceMyDayExceptions`, `RSVPMemberDirectory` → campaigns. The calendar gains
no import edge into sessions — `internal/wire/plugin_import_guard_test.go`
forbids it. With no SMTP and no scheduler wired, in-app RSVP still works.

**Fixed in passing (pre-existing, blocking).** `scanEvents` supplied 36 Scan
destinations for `eventCols`' 37 columns — `&evt.RecurrenceDayOfWeek` was never
added when migration 011 introduced the column. Every event LIST query
(month/week/day/range/upcoming/search/ledger) therefore failed against MariaDB
with `sql: expected 37 destination arguments in Scan, not 36`; only the
single-row `GetEvent`, which has its own correct inline scan, worked. No test
could catch it (nothing in the repo executes real SQL).
`event_scan_contract_test.go` now parses `repository.go` and pins SELECT arity ==
Scan arity for both read paths.

## Temporary offered availability from RSVP (C-CAL-RSVP-P2, 2026-07-26)

Extends C-CAL-RSVP-P1's "Suggest another time" from a free-text note into
STRUCTURED temporary availability. See ADR-046 §"Amended" for the rationale.

**The gap it closes.** P1 shipped an asymmetry: "Out this week" wrote structured
*un*availability the scheduler could use, but "Suggest another time" wrote prose
the Director had to read and re-key. Players could say when they *couldn't* play
in a schedulable way, and only when they *could* in English.

**What it does.** The suggestion surfaces (quick-edit card + the emailed token
page) now take date + from + to rows alongside the optional note. Those windows
become real `availability_exceptions` rows with `state = 'available'`, so they
land in the DM's week overlay and count toward the computed best window. No new
tables — the storage already supported `available`/`preferred` per date; only a
safe write path was missing.

**THE TRAP, and where the fix lives.** Exception rows fully REPLACE the recurring
pattern for a date (`effectiveBlocks`, `sessions/availability_overlay.go`). A
naive write of just the offered window would therefore ERASE the member's usual
hours for that day — a player answering "I could also do Tuesday evening" would
come out LESS available than before. The composition lives in the SESSIONS
plugin (`sessions.AddMyAvailableWindows` → `composeOfferedDay`), not here,
because the replace-semantics is the scheduler's own invariant: it composes the
day (existing exceptions for the date if any, else the recurring pattern for
that weekday), paints the offer on a minute canvas, and writes the merged set.
Server-side, because this write arrives from an email link with no editor in
front of it. Pinned by `sessions/availability_offer_test.go`.

Painting rules: `preferred` is never downgraded by a generic offer;
`unavailable` IS overwritten (the member is explicitly saying they could make
it); unpainted minutes emit no row (on a date with exception rows, a gap already
means "not available").

**Division of labour changed.** `RSVPService.ApplyToken` no longer takes a note
and no longer writes one. It consumes the token and writes only the status the
action implies; `suggest` carries no status and returns early. Both richer
actions' side-effects are the handler's, because they need the POST body
(windows/note) or the scheduler — neither of which the service has an edge to.
`applySuggestion` is the single shared path for the in-app and emailed surfaces
so the two cannot drift.

**Degradation.** Availability writing is best-effort: the RSVP note and the owner
notification are the promise this flow makes, so a scheduler that is absent
(`h.availability == nil`) or erroring still records the answer and tells the
member their times weren't saved.

**Test-invariant amendment.** `TestEventQuickEditV2_PlayersReadOnly` used to
assert the player card contained no `<input>`/`<textarea>` at all. That was a
proxy for "a player cannot edit the event", and it outlived its meaning the
moment players legitimately type their own RSVP and their own offered times into
that card. It now pins the event-editing fields BY NAME (strictly narrower and
harder to bypass), and `TestEventQuickEditV2_RSVPSurfaceIsForEveryRole` asserts
the RSVP affordances render for non-Scribes — the gate split this feature
depends on.

### Why a SECOND geometry exists

`calendar_v2_helpers.go` reads raw `Months[i].Days` (`monthDays` :277,
`monthEraBands` :961, `monthWeekRowCount` :1053, `daysInRow` :1071). That is
leap-BLIND: a flagged real-time calendar draws February 2028 with **28** cells
while `Event.OccursOn` — which routes through `Calendar.MonthDays` — places a
recurring event on **Feb 29**. The event exists and has nowhere to render, and
nothing on main pinned it. `block_geometry.go` routes every day count through
`Calendar.MonthDays(idx, year)`.

The V2 helpers are FROZEN for the whole calendar-v4 wave — they are the densest
source-text-pin site in the repo and three of those pins PANIC rather than fail.
The duplication is deliberate and temporary; the V2 page is retired by a later
wave. **Do not unify them opportunistically.**

What IS shared, on purpose: the weekday COLUMN comes from the existing
`v2WeekdayIndexFor`, so the Block, the V2 grid and recurrence all place a day in
the same column.

### The three-counter divergence — documented, pinned, NOT fixed

Three day counters disagree in this package:

1. `Calendar.AbsoluteDay` — leap-aware (sums `YearLengthForYear`). Moon phase only.
2. `Calendar.constLenDayIndex` — fixed geometry (`year*YearLength()`). Weekday
   column + recurrence.
3. The legacy V1 path.

1 and 2 diverge by **exactly one day per elapsed leap year**, so a per-day moon
disc drifts against its own cell by that amount. Coordinator ruling COMMON §6.4
freezes `constLenDayIndex` for wave 1: making it leap-aware would shift the
weekday column of every calendar already in the operator's production database.
`TestBlockCounterDivergencePin` measures it (year 40 → 10 days) and pins today's
numbers. Reconciliation is its own dispatch and needs an operator gate.

### The count-oracle rule (the load-bearing one)

`ViewerContext.TiedCount` and `WholeCount` come from **ONE** viewer-filtered
pass. Computing one pre-filter and one post-filter turns the tie toggle into an
oracle whose difference is the number of hidden events. The signed mockup's own
`tiedCount` is that leak and is deliberately not ported.

Compounding trap: `filterEventsByUser` compacts IN PLACE (`events[:0]`,
`service.go` :2394), so it mutates the caller's backing array — a SECOND
filtering pass reads a corrupted slice.
`TestFilterEventsByUserMutatesTheCallerSlice` documents the hazard;
`projectBlock` filters once and nils its input.

### Performance: one absolute day per month

`Calendar.AbsoluteDay` loops `y = 0..year-1`, so one call costs
`year × len(Months)` iterations. Per cell that is `days ×` that. The producer
computes ONE base per month and steps integer offsets — the API takes
`baseAbsDay`, so a caller *cannot* reintroduce the loop.
`TestBlockMoonBaseDayIsSteppedNotRecomputed` asserts both exactness and the cost
ratio (measured 27.6ms → 0.91ms, ~30×).

The same shape at the query layer: `EagerLoadCampaignCalendars` costs **9**
queries for any number of calendars where `eagerLoad` (`service.go` :668) costs
9 **per calendar**. It deliberately does NOT load `Weather` — no `BlockData`
field consumes it — so `Calendar.Weather` is nil on everything it returns.

### The Almanac register — the producer half

1. four declared moons → four lanes, at every `MoonCap` value;
2. the GRID still honours `MoonCap` in the same render, so the two cannot agree

4. the nameplate badge's restored *"— all of them are in the Almanac"* tail is

### The arithmetic is auditable, so none of it is a constant

The signed Moons panel's own footnote is *"no date in the register was typed by

`TestBlockAlmanac_FractionalPhaseAgreesWithTheModel` holds the two together on

different moons on the same night.

(`monthBaseAbsoluteDay`), so the fourth body is computed by identical arithmetic
to the three the grid drew.

**Four things worth knowing before touching a disclosure:**

1. **The `rows` disclosure must stay OUTSIDE `#cal-dash-grid`.** The pre-existing
   owner sort control `hx-get`s that id and swaps it. Render the `<details>`
   inside and every sort destroys and recreates it — the section snaps shut on
   each sort and the store desynchronises from the DOM.
   `TestBenchDisclosure_RowsWrapsTheSwapTargetFromOutside` asserts ancestry, not
   ordering.
2. **The flip rides on the `<details>`, never on the `<summary>`.** `toggle`
   does not bubble, so the listener must be on the target; and a click handler on
   the summary fires *before* the state changes, which would invert every write.
   **And because it rides there, everything it declares is INHERITED**: htmx
   resolves `hx-vals` / `hx-swap` by walking ancestors (`bn()` recurses to
   `parentElement` in `static/vendor/htmx.min.js`), so every control inside a
   section reads them. The section key therefore travels on the **POST URL**

   `hx-vals` it appended `section=` to the player's RSVP trio, the owner's
   `Ask →` form and all five sort links. `hx-swap="none"` *is* still inherited,
   so every HTMX control inside a disclosure declares its own — asserted, not
   trusted. Echo reads the field either way (`FormParams` → `ParseForm`, and on
   a POST `r.Form` merges query and body); **`PostFormValue` would silently stop
   seeing the flips**. No `hx-vals='js:…'` at any price — dead under
   `htmx.config.allowEval = false` (`static/js/boot.js:168`).

### Placement — the Ledger's rect is an exclusion zone, in BOTH axes

`[DC-3] SIGNED`: the card may never occlude the Ledger, because its own
`Open in the Ledger` door points at that column — and, since the door became
conditional, because a **docked** Ledger is repainted by the same click that
opened the card, so covering it would hide the answer the reader just asked for.
Both layouts keep the hard exclusion, for the two reasons. `placeCard` therefore treats the
Ledger's **settled rect** as a hard exclusion zone regardless of the role it is
playing in the layout — a right-hand docked column and a full-width band the
narrow layout has **stacked below the grid** are the same obligation, and the
placer asks "does the box intersect this rect", never "is the Ledger to my
right".

Order, and there is no other geometry:

1. **below** the day (preferred), horizontally clamped left of a docked column
   when there is room;
2. **above** the day, when below cannot clear;
3. the **bottom sheet** — [DC-3] bullet 4's own signed treatment — when neither
   position clears at popover width. The card is never resized to fit.

horizontal only, so between roughly **625px and 884px of `.cal-bench` content

touch this function, the regression cases in `test/js/daycard_payload.test.mjs`

the card no longer covers anything. The **mobile** sheet stays silent: there the
full-width treatment is the layout, not a fallback, and §12 scopes the

### Roles, and the one thing that is easy to get wrong

`[DC-9] SIGNED`. The mockup's owner / co-DM / player are **not** Chronicle's
Owner / Scribe / Player: the co-DM capability is an ORTHOGONAL axis, and
reading them as one ladder ships a Scribe the co-DM's powers.

| affordance | floor |
|---|---|
| open the card, read its rows | **Player** |
| `+ New event`, edit a row, Save | **Scribe** (`cc.MemberRole`, the field `RequireRole` compares) |
| set `dm_only` | **`CanAuthorDmOnly()`** — the capability, not the role |
| Delete | **Owner** |
| change the event's owner | absent — no API field, no signed design |

`[DC-6] SIGNED`, resolved by the first-lander clause: BENCH-R2 landed the
disclosure register and OWNS it, so the card and the editor **consume** it. Two
rules were added by name inside `calendar-bench.css`'s existing register

reusing `--disc-open` / `--disc-close` / `--disc-ease` unchanged. Under reduced

### The one new route, and the whole budget

`GET /campaigns/:id/calendars/:calId/events/:eid` — authed `cg`, `RolePlayer`
floor, literal path. **Zero new write routes**: the editor is a client of the
shipped, IDOR-closed event API (`POST`/`PUT` Scribe, `DELETE` Owner), through
`Chronicle.apiFetch`. The floor is not the security boundary — the grid's own
viewer filter is, applied inside the handler, and `visibility` +
`visibility_rules` ride the SCRIBE floor on top of it because the person who
will overwrite an audience must be able to round-trip it. Hidden, filtered,
`:calId`-mismatched and missing all return **one branch, one body**.
`daycard_route_test.go` is that review in executable form.

**PUT-vs-POST is decided in one pure place, from the DOOR's id.** `writeTarget()`
maps (mode, eventID) to a method, and edit mode with no id returns `null` — the
editor REFUSES the save. It used to take the id from the server's record and
compute `edit = mode === 'edit' && eventID`, so a response without an `id` would
have fallen through to the create branch and POSTed a DUPLICATE event: silent
data duplication whose only symptom is a second row. Delete rides the same id, so
the two cannot disagree about which event the session is holding.

`schedule_stills_test.go` pins twelve of the twenty-two.

### Captions are a model, not a string

`ScheduleCaption` is `[]ScheduleRun{Text, Em}`; `Em` is `""` / `"b"` / `"i"`.
The drawing's bold lead-ins are how a reader FINDS a named honesty claim, and
its italics mark a word the sentence QUOTES rather than uses (`preferred`, `in`,
`maybe`, `out`). **Never store markup in the copy** — the runs stay escaped, so a
caption cannot become an injection site the day one of them takes a campaign's
name. `ScheduleCaption.Text()` joins them back; assertions about WORDING read
that, and only `schedule_stills_test.go` reads the emphasis.

Each panel draws exactly ONE `.caption` block, because the mockup's own
producers return one joined string and three notes in three blocks read as three
unrelated remarks.

### A width-dependent sentence is two sentences

The mockup swaps three strings for shorter ones at 640 (`who`, `free of 5`,
`nothing saved`); its producer re-runs on resize and a server-rendered page
cannot. So the builder fills `IdentCapShort` / `DenominatorShort` / `NoteShort`,
`scheduleWidthTextView` emits both inside `.sc-wide` / `.sc-narrow`, and the
phone block chooses. **Only ever for two forms of the SAME fact** — both are in
the accessibility tree, so this can never be a way to hide something from one
width. It exists because the wide forms did not merely clip: the empty lane's
sentence clipped its own `no pattern` chip out of the row.

### DAY zoom is a real zoom, and `scheduleColumns` is where it is decided

`?zoom=day` shipped for four stages as a control that pressed and changed
nothing: it round-tripped the query and inked `aria-current="true"` while
`scheduleColumns` and `scheduleDayCount` ignored it. **It is built now, out of
the week payload the Matrix already ships** — no route, no query, no seam, no
second read.

`scheduleColumns` is the ONE branch. In week zoom a column is a DAY spanning the
whole visible band; in day zoom it is an HOUR of the selected date. Everything
downstream follows from the column set, which is why nothing else needed a zoom
flag:

| | week zoom | day zoom |
|---|---|---|
| a column is | a day, band-wide | one hour of `?day` |
| `--cols` | the overlay's own day count | `BandTo − BandFrom` |
| `Major` | the weekend's leading edge | `(h − lo) % 6 == 0 && h != lo` |
| the count lane | the day's PEAK, with `@ h` beside it | the hour's own count, no sub |
| the bracket | one day wide | the window's hours, `19:00–22:00` |
| the head's frame | `Mon 20 – Sun 26 Jul · 16:00–24:00` | `Sat 25 Jul · 16:00–24:00` |

Three things are worth knowing before touching it:

- **`data-day` stays on every hour column.** Guard B4's answer key is why the
  surface answers at all, and an hour of Saturday is still Saturday. What could
  NOT stay was the popover id — eight hour columns share one date, so a
  `pc-<user>-<date>` key repeated eight times and every cell in a row would have
  opened the 16:00 detail. `ScheduleCol.Key` (date + hour) is the identity;
  `DayKey` is the answer.
- **A cell's popover belongs to the COLUMN, not the day.** Filtering on the day
  alone was indistinguishable from filtering on the column while a column WAS a
  day. Once it is an hour it lists windows the cell draws nothing for, and mints
  a popover for every empty cell in the row.
- **The bracket refuses a day it is not on.** The drawing finds its start column
  by hour alone, which is the same answer on its own default state and is not
  once a reader steps the day. The bracket is the page's ANSWER in `--accent`,
  which is the tool talking; drawn over a Wednesday the numbers never chose it
  would be the tool lying.

**The sealed sheet declares `.sc-ruler` (11 declarations) and `.sc-head-row b`
(10 more) and RENDERS NEITHER.** `const ruler = DAYZOOM ? '' : '';`
(`mockups/calendar-v4-schedule.html:1683`), and no `<b>` is ever written into a
head row; rendered at `?zoom=day` the drawing reports zero `.sc-ruler` nodes, and
the signed still (`mockups/renders/wg-matrix-day-gm-light-1440.png`) shows one
24px row of hour numbers and no ladder beneath it. Porting those declarations
would ship rules matching nothing — the same defect class as a `:disabled` repair
for a control the page never renders. **Do not add them because a grep says they
are missing.**

### A viewport-dependent refusal is two controls

At 640 and below the drawing REFUSES day zoom: `<button disabled>` in
`--text-muted` with `cursor: not-allowed` and
`title="week zoom is forced at this width"`, because at 390 the panel is 340px
and eight hour columns cannot clear the 24px target floor in what is left after
the identity and answer columns.

It reads `window.innerWidth` to do it. **A page rendered once on a server has no
viewport to read** — the same bound ADR-048 §13 records for CSS-only selection
("a server-rendered `checked` attribute cannot vary by container query") — so
`scheduleZoomOptions` emits THREE rungs for two controls: `Week`, the live `Day`
gated `sc-rung-wide`, and its disabled twin gated `sc-rung-narrow`. Exactly one
is `display:none` at any width, so exactly one is in the accessibility tree and a
screen reader never meets two Day controls. It is the same mechanism as
`.sc-wide` / `.sc-narrow` above, applied to a control instead of a sentence —
**with its own selectors**, because the bare pair is 0,2,0 and
`.cal-schedule .seg a` is 0,2,1, so it would lose the `display` cascade and leave
both Day rungs on screen at 390.

`ScheduleToggle.Disabled` is set on that one rung and nowhere else. Before this
it was set nowhere at all, while its doc comment, the templ branch and a CSS
`:disabled` repair all described the refusal it was supposed to carry.

**Both halves are asserted at the ROUTE as well as in the builder**
(`TestSchedulePage_ZoomReachesTheBuilderAndTheRungs`), on the degraded floor,
because the gap between the two is where the inert zoom lived: every assertion
the package had was either about the query string or about a builder called
directly with a hand-set field, so the halves were proved apart and shipped
disconnected.

An explicit `?zoom=day` is still honoured at every width, deliberately: silently
ignoring a parameter a reader typed, or a link they were sent, would make this
surface's state-addressability a lie in the one place it is easiest to tell. A
narrow reader gets the day grid inside the matrix's own horizontal scroller,
which is what that container is for.

### The door

The Bench's RSVP panel title (`RSVP · Schedule`) is the link to this page, and
the only one: WG-2's signed ruling keeps the nav pointing at `/availability` and
books its retirement as a separate slice. The anchor inherits the signed

## C-CALV4-THEATER (R2-3) — the mount contract, and why the theater has nowhere legal to stand yet

**Read this before building any overlay on an entity-page widget block.** The
Block theater's seventeen rulings are signed; the slice STOPPED at [TH-14], and
the reason generalises well beyond the theater.

### The blocker, as a fact about this plugin's own mount

`calendar_widget_type.go:152` — `RenderBlock` wraps the **entire** output of
`EntityCalendarBlock` in `widgetbindings.BlockHost(WidgetTypeCalendar,
rc.HostID, inner)`, i.e. `<div id="widget-block-calendar-<entityID>">`. And
`widgetbindings/picker.templ` targets exactly that id with
`hx-swap="outerHTML"` on **three live Scribe+ paths** — bind (`:99`), create
(`:54`) and unbind (`:80`).

**So everything `entity_calendar_block.templ` emits is inside an
HTMX-swappable region, and there is no position inside this plugin's files that
is not.** [TH-14] requires a theater scaffold to be outside every
`.cal-block-host`, inside a `cal-bench` root **and** outside any swappable
region; the third cannot be satisfied here without changing either the
four-widget `BlockHost` seam or `internal/app/routes.go` beyond the single
body-script registry line [TH-12] allows. Both are host restructures.

**The trap for the next reader:** [TH-14]'s own citation is
`entity_calendar_block.templ:61` (`BindingAffordance`) — the picker's *inline
slot*, an `innerHTML` target nested inside the block. It is easy to read that
slot as "the swappable region" and conclude there is safe ground beside it in
the same component. **There is not.** The slot is nested inside the real target.

### The mount contract, as signed ([TH-8], eight lines) — for whichever slice unblocks this

A surface gets the theater by doing exactly these eight things. Every one is a
trap the contract exists to keep the next host out of:

1. Render the scaffold **once per `(calendar, entity)`** — one shared templ
   component, id-namespaced per block, never an unnamespaced copy ([TH-15]).
2. Emit it **outside** every `.cal-block-host`, **inside** a `cal-bench` root,
   and **outside** any HTMX-swappable region ([TH-14] — *this is the one that
   currently cannot be satisfied*).
3. **Copy the Block you already built; never project twice** ([TH-2]).
4. **Re-namespace the copy's `Viewer.HostEntity`** before rendering it, or you
   ship duplicate DOM ids and a dead tie toggle ([TH-2]). *This is the line that
   bites.*
5. Suppress the theater copy's switchboard via the host-owned `LayerState`
   fields; the embed keeps the one switchboard ([TH-13]).
6. The module mounts through `pluginBodyScripts` in `internal/app/routes.go`,
   **never** a page `<script src>` — `tools/page-script-allowlist.txt` pins
   `entity_calendar_block.templ` at exactly 1 and the ratchet fails above **or**
   below ([TH-12]).
7. The module re-inits on `htmx:afterSettle` and returns immediately when its
   mount is absent ([TH-12]).
8. Emit **none** of `data-bench-block` / `data-cal-daycard` /
   `data-cal-daycard-payload` — `calendar_daycard.js` already loads on every
   entity page and is dormant only because those three are absent ([TH-1]).

### Three measurements worth keeping, whoever builds it

- **`Layers` is a POST-HOC DISPLAY GATE.** `EntityCalendarBlock` passes neither
  `LedgerHidden` nor `ShelfHidden` to `spine.Block`, `block_projection.go:181-182`
  builds both zone stubs unconditionally, and the host overwrites `d.Layers` at
  `entity_calendar_block.go:253`. **The entity page's existing projection already
  contains the Ledger and the Shelf**, so a theater is a struct COPY plus one

- **Two Blocks for one calendar collide on every id.** `tieGroupName`
  (`helpers.go:503`), `dayPickGroupName` (`:954`), `shelfPickGroupName` (`:1358`),
  `almPickGroupName` (`:1587`), `layerSheetID` (`:1833`) and `layerAnchorName`
  (`:1857`) are all `(CalendarSlug, HostEntity)`, and `nameplate.templ:98` gates
  the tie toggle on `HostEntity != ""` alone. Both Blocks emit it, both radios
  land in one `name` group, and the second Block's `<label for=…>` resolves by

- **`entity_calendar` is registered `Singleton: true`** (`internal/app/routes.go`,
  the `blockRegistry.Register` call at ~`:3264`), so a page cannot carry two of
  these blocks today. That is a *second* line of defence for [TH-15]'s
  once-per-page rule, not a replacement for the id namespacing — and
  `EntityCalendarBlock` builds under `context.Background()` with no shared
  per-request state, so a Go-side "first wins" across invocations is not
  constructible anyway.

`TestEntityCalendarBlock_HostLayerSet` asserts `data-zone="ledger"` and

## C-SWEEP-R4 stage 24 — the wizard's door carries everything the importer keeps

## C-SWEEP-R4 stage 21 — `AbsoluteDay` is closed-form, and that is a security fix

`Calendar.AbsoluteDay` (`model.go`) no longer loops from year 0. Its year term is
`year·YearLength() + leapExtraDays·leapYearsBefore(year)`.

**Why it matters beyond speed.** The `year` it receives comes off an
unauthenticated query string on three routes — `worldstate_handler.go`
`GetWorldState`, `handler_v2.go`'s cursor, and syncapi's `GetWorldState` — through
`BuildWorldStateSeed` → `moonSeeds`. Linear cost there meant `?year=2000000000`
held a core for 53.5 s per request.

**Footgun for anyone editing the date math.** The closed form must stay term-for-term
identical to the loop it replaced, because moon phases and countdowns are computed
from its output and a one-day drift is invisible until an operator notices their full
moon moved. `TestAbsoluteDayClosedFormMatchesLoop` keeps the original loop as an
oracle — if you change `AbsoluteDay`, `YearLengthForYear`, `IsLeapYear`,
`leapExtraDays` or `leapYearsBefore`, that test is the thing that will tell you
whether you changed the ANSWER or only the cost.

**`leapYearsBefore` reduces the offset to a least non-negative residue on purpose.**
`IsLeapYear` is `(y-LeapYearOffset) % LeapYearEvery == 0`, and a negative
`LeapYearOffset` makes Go's `%` return a negative remainder; without the reduction
the progression count is wrong for exactly those calendars. The oracle test carries
an `offset:-9` case for this.

**Amendment R4-S21-A.** `TestBlockMoonBaseDayIsSteppedNotRecomputed` no longer
asserts a ratio between per-cell and stepped forms (the fix makes them equal); it
asserts year-independence. Do not "restore" the ratio — it can only pass on a tree
that has the DoS back.

disagree — `forbidden-lands.json` addresses its first month as 0, `calendar-of-therin`

smallest-index test would read a 1-based file as 0-based, which is precisely the `+1`

index.

the other. `dayStart <= 0` → day 1; a `dayEnd` that is unset or beyond the closing month
runs to that month's last day. The reading is faithful, not tidy: forbidden-lands writes
`dayEnd 45` on seasons that close on 46-day months, so day 46 there belongs to no
season. Do not "fix" that — it is the payload, and the alternative is inventing a nicer
calendar than the one the author exported.

## The sky header's producer — C-CALV4-SKY (R2-5), 2026-08-08

**The sky's whole producer side is four lines** (`blockSkyFacts`,
`block_projection.go`), and the shape of those four lines is the part worth
remembering.

**Two `BlockData` fields and no third, and one of them is a gradient rather than
a fraction.** [SKY-6] binds two things at once: the gradient is
`calendar.SkybandGradient(timeOfDayFraction(cal))` **reused, never re-derived**,
and `BlockData` gains exactly two fields. `internal/widgets/calendar_block`
imports nothing from `internal/plugins/**` **by construction**, so a raw 0..1
fraction landing in the widget could only become a gradient by the widget
growing colour science of its own — the half that is refused — and carrying the
fraction *and* the gradient would be the third field, which is the other half.
So the fraction is consumed here, where the one shipped gradient function lives,
and its **result** crosses the seam. `data_test.go`'s r54 shape pin caught both
fields on the first run, as designed; it is extended by exactly two entries.

**`SkyGradient` is also the SEAT GATE.** The sky seats on the Bench's Primary
Block only ([SKY-1]), so the producer fills both fields there and nowhere else,
and an empty gradient means *"this surface carries no sky"* rather than *"the
sky failed to load"*. `BlockProjectionInput.SkyOn` / `BlockRequest.SkyOn` are
written the **positive** way round for exactly that reason: every host that is
not the Bench's Primary — the builder preview, the entity embed, the real-world

else reads it"*. Measured, that meant a viewer who turned the Shelf layer off —
or a host that docked the Block without one — **silently emptied the sky's
expansion**, invisibly, until somebody reported *"the sky is blank on my page"*.
The gate is now `if (!in.ShelfHidden || !in.SkyHidden) && len(cal.Moons) > 0`
and the comment was corrected in the same commit. **Half of that is not most of

sky's data while tidying.

## An emptied Year field moved the world to year zero (2026-08-09)

A driven parity sweep cleared the **Year** input on the GM's *Set date* control
and submitted. The world moved to **year 0** — HTTP 200, stored, and every
surface then rendered year 0. It reproduced in BOTH writers: the legacy V2
console (`static/js/gm_panel.js`) and the v4 Bench date-verb row shipped by
C-CALV4-GAMEREADY (`static/js/calendar_daycard.js`). Every other coordinate was
range-checked — `SetWorldState` refuses month 0 and month 99 — and year alone
was not.

### Year 0 is a legitimate year, so zero is not what got banned

This plugin had already ruled that twice, and the ruling stands:

- `BuildWorldStateSeed`'s header: *"year 0 is a valid year so it is only
  defaulted when month/day are also unset."*
- the weather-on-date bounds check: *"The year is deliberately unconstrained:
  fantasy calendars may use year 0 or negative era years."*
  `calendar_weather_on_date_test.go` drives a **negative** year end to end.

So the defect was never "zero was accepted". It was that **ABSENT and ZERO had
become the same value** by the time the server saw them. The fix keeps zero (and
negative years) settable and makes absence expressible instead.

### The three places the conflation lived

1. **`PUT /api/v1/…/calendar/date` (`api_handler.go`) — the server-side half, and
   the one no client fix reaches.** `apiDate.Year` was a plain `int`, so a body
   that merely *omitted* `year` decoded to 0 and the handler wrote year 0. Month
   and day already had a `< 1` floor; year had none. `Year` is now `*int` and an
   absent year is a validation error. This is live for the Foundry module: its
   push sites send `year: date.year`, and an `undefined` from a calendar adapter
   is dropped by `JSON.stringify` and arrives as an absent key.
2. **`PUT /campaigns/:id/calendar/world-state` (`worldstate_handler.go`).** The
   pointer fields already separated absent from zero, so its hole was the state
   the browsers demonstrated: a coordinate that arrives **empty**. The five
   date/time fields now decode through `worldStateCoord`, which distinguishes
   absent/null (preserve) from a number (write, zero and negative included) from
   blank-or-unparseable (**refuse, naming the field**). Its `UnmarshalJSON`
   never returns an error on purpose — an error aborts Echo's `Bind` and the GM
   gets a generic *"invalid request"* that does not say which box was empty,
   which is the same dead end as the silent zero. Numeric strings are accepted,
   because an `<input>`'s value *is* a string and refusing them is what pushed
   both writers into `parseInt`-with-a-fallback in the first place.
3. **Both browser writers.** They now read every coordinate through a
   `coordOrNull` helper and refuse to submit, naming the empty field — the v4 row
   through its own `aria-live` line, the V2 console through `Chronicle.notify`.
   A typed `0` still parses and is still sent. The two copies of the helper are
   deliberate: `check-page-scripts.sh` is a shrink-only ratchet and neither file
   may grow a shared page script, so the duplication is pinned by a source
   ratchet instead (`TestDateWriters_NoZeroFallbackForACoordinate`).

`UpdateCalendar` also range-checks the year now, and **the bound is the storage,
not lore**: `calendars.current_year` is an `INT`, so `calMinStorableYear` /
`calMaxStorableYear` keep an out-of-range year from becoming a driver error and
a 500. It is not a `year >= 1` floor and must never become one.

### How it is pinned

`year_absent_test.go`. The two `TestYearProbe_*` tests drive a **real headless
Chromium** over the real rendered Bench / GM console and the real shipped JS,
because a `parseInt` fallback is exactly the class of defect that reads as
correct in source — they were the RED that reproduced the sweep's measurement
(`{"time":{"year":0,"month":1,"day":14}}` leaving the page from an emptied box).
Both directions are pinned: an empty year must move nothing, and an explicit
year 0, a negative year and an ordinary year must all still be settable.

## The real-date anchor (C-CALV4-ANCHOR, migration 018, 2026-08-16)

**One stored pair per calendar: an in-world date, and the real date it equals.**
Every other day follows by counting, because `Calendar.AbsoluteDay` already turns
any `(year, month, day)` into an exact index over the calendar's own month
lengths and leap rule. The whole file is `real_date_anchor.go`.

### Why it had to exist

Chronicle keeps availability on a **real** axis and always has:
`member_availability` is keyed to a Gregorian `day_of_week` and
`availability_exceptions` to a Gregorian `on_date` (`sessions/migrations/002`),
both minute-accurate and DST-correct. The calendar Block renders **fantasy**
days. Nothing joined the two, so on a fantasy calendar the availability strip had
nothing to draw from — which is why `C-CALV4-TILES` §9.5 shipped it complete and
**dormant**.

There was no candidate to reuse: `epoch_name` is a *label*, and
`tracks_real_time`/`real_time_zone` (migration 012) apply only to `reallife` mode
and are about deriving *today* from the wall clock, not about mapping arbitrary
days. The builder's `wz-anchor` is a different concept wearing the same word — it
asks whether the calendar's own declared today resolves *structurally*.

**CORRECTION (2026-08-16).** The first version of this section said "nothing
joined the two", which is overstated. **`sessions` has carried BOTH dates since
its first migration**: `scheduled_date DATE` beside `calendar_year` /
`calendar_month` / `calendar_day`, with a `HasCalendarDate()` helper. Every
reader of those fields was checked — the repository scans them, the export
adapters copy them, the AI renderer prints them — and **nothing relates them to
each other**. So a per-session PAIRING existed and the RULE did not: Chronicle
could state the two dates of a session an owner had already labelled by hand, and
could say nothing about any other day.

That has a practical consequence for the settings form. A session row carrying
both dates is an anchor the owner has **already asserted**, and is therefore a
better source than the *"today + the calendar's current day"* convenience button
— which is only correct if the campaign's clock is standing on today, and a GM
advances the in-world date in bursts. The button now states that assumption and
points at a past session as the safer source. **Seeding the anchor directly from
a session is not built**: it would be the calendar plugin's first read of the
sessions plugin (a consumer-defined service interface wired at the app layer,
per rule 8), and that dependency is worth introducing deliberately rather than
for a form convenience.

### What is stored, and why the NAMED date rather than a day count

| choice | what survives a structure edit |
|---|---|
| `(real_date, absolute_day)` | the **day count** — so the in-world date the anchor names silently slides |
| `(real_date, year/month/day)` ← **shipped** | the **named day** — the count is recomputed from the new structure |

*"The campaign began on Marpenoth 14, which was 3 October"* is a fact about a
named day, and it should survive the owner fixing a month they had mis-declared.
Pinned by `TestAnchor_TheNamedDayHoldsWhenTheStructureChanges`.

### All four columns or none

A partial anchor is not a weaker anchor, it is an **unanswerable** one. Enforced
in three places, deliberately: `RealDateAnchor` (one struct, so three-of-four is
unrepresentable at every write boundary), `HasRealAnchor()` (so a row hand-edited
in the DB degrades to *not anchored* rather than to a wrong answer), and
`parseAnchorRequest` (which names the missing field, because "invalid" in a form
with four inputs is unactionable). **All four empty is the CLEAR**, not an error.

### The one class of bad input that cannot be caught downstream

**The arithmetic never fails on a phantom date.** `AbsoluteDay(1492, 2, 40)`
returns a number quite happily, so an anchor on a day the calendar does not have
maps every *other* day off by however far the phantom overshoots — silently, and
forever. `RealDateAnchor.Validate` is checked against **the calendar it is being
stored on** (month count, that month's length in that year, leap included), at
the service, and it is the only place this is catchable.

### Deliberate non-features

- **No time of day.** Day-granular. Availability windows carry their own minutes
  in their own IANA zone and are resolved by `internal/timeutil`, which is the
  code that already knows about DST.
- **No guessed epoch.** Un-anchored returns `ok=false` everywhere. There is no
  defensible default for someone else's world.
- **No weekday mapping.** A ten-day fantasy week does not correspond to a
  Gregorian one. Callers get a real **date**; `.Weekday()` on that is the real
  world's answer to a real world's question.
- **No `calendar.structure.updated` publish.** That signal means the calendar's
  *shape* changed and makes the Foundry module badge a mismatch. The anchor
  changes no month, weekday or leap rule. Pinned by
  `TestSetRealDateAnchor_DoesNotPublishStructureUpdated`, whose recorder is shown
  non-vacuous by making the same service publish from `SetEras`.
- **No syncapi route.** Owner-set in Chronicle's settings; the module reads the
  consequence, not the pin.

### Where it surfaces

`blockRealDateLabel` (block_geometry.go) fills `DayCell.RealDate` per cell with a
short display label — `Sat 3 Oct 2026` — and the Ledger's **day panel** prints it
under the in-world date as `.ldrd`, sharing the moon line's type exactly. **Not
in the grid cell**: at 34px of column there is room for a numeral, a moon and
three marks, and a fifteen-character date is not among them.

`DayCell.RealDate` is a **display string produced by the producer** — the widget
has no calendar model and must not grow one. Empty means *not known*, and that is
the common case: every calendar is un-anchored until an owner pins one.
`TestBlockRealDate_UnanchoredEmitsNothing` walks a whole month and requires zero.

### The inverse, and its bound

`FromAbsoluteDay` is the inverse of `AbsoluteDay` — exported because moon phases,
season boundaries and era spans all compute *forward* today and every "which day
is index N" question they cannot ask is this function. It **estimates the year by
dividing, then corrects**, and the correction loop is bounded
(`anchorYearSearchCap`) because it runs once per rendered day and a structure
edit can move the estimate. Out of range **reports** rather than approximating.

### Still open

- **The availability lanes are not wired.** The anchor is the prerequisite §8.6
  booked; joining `member_availability` + `availability_exceptions` onto
  `DayCell` is the next slice. The strip's CSS and markup already ship.
- **Nothing re-dates on an anchor change.** Changing it moves every schedulable
  thing at once with nothing on screen to say why, which is exactly why it is
  audited (`calendar.anchor_set`, values included, not just "changed").

## The shipped Holiday default is lime, not amber (C-CALV4-RUNES §10.3, 2026-08-16)

**Operator ruling: gold means GM, so the category moved.**

Below 84px of column the calendar draws no event names, and `C-CALV4-TILES` §9.2
made the rune's *shape* decorative — the glyph comes from the mark's position in
the day, not its type. So **colour is the only channel separating event types**
at that density, and a GM-only day strikes **all** its runes gold, putting a
seventh competitor in the same space.

`#f59e0b` inked **28/255** from that gold. Both are gold *by hue*, and the ink
recipe keeps hue, so no lightness or chroma treatment could separate them — one
of the two had to move, and gold's meaning is load-bearing across the product.

### Lime was measured, not chosen

Every hue on the circle was painted through the shipped rune-ink recipe in both
themes and scored against the GM gold **and** the five other defaults. 115–135°
is the optimum region; `#84cc16` is its Tailwind-500 member, so it sits in the
same family as its neighbours. Strict improvement on both axes:

| | before | after |
|---|---|---|
| Holiday vs GM-gold | 28/255 | **75/255** |
| worst pair of the six | 29/255 (Holiday/Battle) | **43/255** (Battle/Birthday) |

The worst pair is no longer a Holiday pair — it is the pre-existing red/pink
proximity, and it clears the floor.

### Measured on both surfaces, not just the one that failed

The event colour reaches two places. The **rune ink** is where the collision was.
The **chip fill** (`color-mix(in srgb, card 90%, axis)`) is where a desktop GM
looks, and its worst pair is **8/255** — before and after, unchanged by this
change. That is *not* a defect: the chip's identity is its full-strength `.rail`
beside the label, and the fill is a deliberate faint wash. Fixing one surface
while clashing the other would have been a lateral move, so it was checked.

### Existing calendars keep their amber

`DefaultEventCategories` seeds **new** calendars only. A data fix would rewrite a
colour an owner may have chosen deliberately, and the product cannot distinguish
*left at the default* from *picked exactly this*. Changing it on a live campaign
is one colour picker in settings → Categories.

Pinned by `TestDefaultCategories_NoneCollidesWithTheGMGold`, which reads
`DefaultEventCategories()` itself (so it cannot drift from what ships), paints
each through the **real stylesheet**, and produces the GM gold via the shipped
`:has(> .dogear)` rule rather than restating its expression. Proven red against
amber on both arms — the gold collision and the Battle proximity.

## C-RSVP-ROBUST (the RSVP lane) — 2026-08-16

Five defects in the emailed-RSVP flows, each with a guard proved red first. The
sessions half (the overlay OOM, the offered-windows relabel, the exception
endpoint, the session token) is in `internal/plugins/sessions/.ai.md`.

### A member's zone reaches this plugin through ONE seam

`AvailabilityExceptionWriter.MemberZone(ctx, campaignID, userID)` — and it
returns `""` when the member has set no zone anywhere. **Empty is a state, not a
UTC default.** The adapter behind it reads BOTH columns the product lets a member
write, availability page first: `member_availability.tz` (what the control
labelled "Your timezone" writes, and the only zone most players ever set) then
`users.timezone`. `RSVPHandler.memberZone` is the single nil-safe accessor; do
not call the interface directly from a new site.

### "Out this week" resolved the week in UTC

`rsvpWeekDates` anchored on `now.UTC()`, and the emailed link is a one-tap action
with no week picker. A Pacific/Auckland player tapping it over Monday breakfast
(08:30 local = Sunday 20:30 UTC) blocked the week that had already ended and
stayed fully available for the week they meant; mirror image for
Pacific/Pago_Pago late on a Sunday. Seven `availability_exceptions` rows landed
on days they never intended, with no undo on that page.

It now takes `memberTZ` and resolves in it, and every message that names the
resolved week also names the zone (`weekZoneSuffix`) — including the no-zone case,
which says UTC *and* where to fix it. `TestRSVPWeekDates` could not see any of
this: it pinned both branches at 15:04 UTC, a moment that is the same civil day
in every zone on earth. It is now pinned at the edges.

### The emailed "suggest another time" form named no zone

Three bare date + from + to rows, no zone label, no hidden field, no JavaScript —
and the server stamped the minute numbers with the member's stored zone, UTC by
default. A New York player typing "Sat 18:00–22:00" offered 14:00–18:00 their
time, and the confirmation page said their times "were added to your
availability" without ever naming a zone, so neither party could notice.
`rsvpSuggestPage` now takes `memberTZ` and renders `suggestZoneLine`. No picker:
this is a logged-out landing page with no JS, and the durable fix is the member
setting their zone once.

### `emailed: true` while the 24h floor suppressed every send

`SetRSVPCollectionAPI` computed `emailed` from `mailer.IsConfigured` alone and
never consulted the per-recipient floor `fanOutInvites` applies. The floor reads
the SAME `calendar_schedule_asks` log the "Ask availability" control writes, so a
Director who asked the roster in the morning and armed collection that afternoon
mailed NOBODY while being told the party had been invited — verbatim the failure
[GR-10] closed, reopened one file over by [GR-6].

`planInviteFanOut` now computes what a fan-out started right now would actually
do, through the SAME two decisions the fan-out makes (`memberMaySeeEvent`,
`RecentlyAskedRecipients`). `emailed` is `plan.WillEmail > 0`, and a zero plan
carries a notice that names the actual reason — the 24h limit, no addresses, or
nobody who can see the event — because "the mail server is broken" is the guess
an operator reaches for otherwise. `TestInvitePlan_MatchesWhatTheFanOutSends`
measures the plan against the real send: two readings of one rule is the shape
that drifts.

Related, same endpoint: `SetCollectRSVPs` is now
`UPDATE … WHERE id = ? AND collect_rsvps <> ?` returning `changed`, and the
fan-out rides THAT rather than a separately-read event row. Two Scribes arming
at the same moment both used to see `collect_rsvps=0` and both started a fan-out;
the floor absorbs nothing in a tight race because its rows are written only after
each send returns.

### Closing collection turned every live link into the failure page

`rsvpDeadTokenPage` required `evt.CollectRSVPs` before it would admit an answer
exists — the same condition `resolveToken` refuses on. So closing collection
after the head count (a natural thing to do; it is a toggle on the day card) left
every player re-opening their own link reading "RSVP Failed — this RSVP link is
invalid or has expired", including one who answered YES and is still on the
roster. That is the exact sentence [GR-8] exists to stop players seeing.

**`collect_rsvps` is out of that gate; the VISIBILITY gate is untouched.** It is
the operator's go/no-go for taking NEW answers, not a visibility rule, and
reporting a recorded answer to the member who gave it discloses nothing they are
not entitled to. `memberRole` + `CanUserViewEvent` still run, and
`rsvp_collection_off_test.go` pins both leak directions (removed member, event
flipped to dm_only) alongside the reassurance.

### Still open, deliberately

An RSVP note cannot be cleared once written (`normalizeRSVPNote` maps "" to nil,
`UpsertRSVP`'s `COALESCE(VALUES(note), note)` then preserves, and `SuggestTime`
refuses an empty note by design). There is no write path that could clear the
column, so this needs a control that does not exist plus a decision about whether
answering "Going" should clear a note left with an earlier "maybe" — feature
work, not a defect fix. The probe is kept in `zz_scout_probe_test.go` with that
reasoning attached.

## C-RSVP-P10 (2026-08-16) — RSVP collection could be armed and never disarmed

A live defect, found by scouting the RSVP lane rather than by anyone hitting it.

`GET /campaigns/:id/calendars/:calId/events/:eid` returns `eventEditorRecord`,
and that record did **not** carry `collect_rsvps`. The day card renders a
"Collect RSVPs" checkbox for Scribe+ and paints it from that record
(`calendar_daycard.js` → `edRsvpPaint`, `rec.collect_rsvps`), so the box rendered
**unchecked on every open**, including for an event whose collection was already
ON.

**An unchecked box offers no "uncheck" gesture.** There was therefore no path
from the day card back to OFF, ever. The hint underneath compounded it, telling
the GM "Emails the party once, and opens answers in-app" about an event that had
already emailed the party.

### Both halves were pinned, in opposite directions, and both were green

- `daycard_route_test.go` listed `collect_rsvps` among the record's **named
  refusals** and asserted the key must be ABSENT.
- `test/js/daycard_rsvp_collect.test.mjs` built a fixture event that **carried**
  it and asserted the checkbox follows it.

Neither test ever saw the other side. This is the same failure mode as the
reverted week/day views (`.ai/todo.md`): every test fed a hand-built fixture, so
none of them discovered that the producer does not build it.

### The fix, and why the refusal list was not simply wrong

`eventEditorRecord.CollectRSVPs *bool` — Scribe-gated, travelling with
`visibility` / `visibility_rules`, so a Player still gets no key at all.

The refusal list refuses data about **other** things (the campaign, the roster,
the calendar's structure, who wrote the row). `collect_rsvps` was never an
instance of that: it is this event's own state, authored from this very editor
through its own shipped endpoint. Withholding it did not keep the record narrow
— it made the editor unable to round-trip a control it renders. Exactly the
argument DC2-RECUR-DATALOSS made for `is_recurring`, one field over.

`TestGetEvent_CarriesTheRSVPArmingStateToItsOwnEditor` now drives the **real
handler** for both armed and unarmed events, and
`TestGetEvent_RSVPArmingStateIsScribeGated` pins the audience floor.

### Checked and deliberately NOT changed

- **The RSVP bell link points at the Bench, not the event** — `rsvpEventLink`
  drops the calendar and event ids. That is [VS-12], signed: the same link goes
  in **email**, and a door whose blast radius is somebody's inbox must never
  point at a route that can 404. Not a defect.
- **A co-DM whose `campaign_members` role is Player cannot arm RSVP
  collection**, because `RequireRole` compares raw `MemberRole` and never the DM
  grant. This is arguably the WG-4 mistake in a new place, but changing it
  widens a write permission and is the operator's call, not a silent fix.
  **BOOKED, not done.**
