# Calendar Plugin

## Purpose

A per-campaign fantasy (or real-world-synced) calendar: custom months,
weekdays, moons, seasons, eras and events, plus the RSVP/availability layer
sessions reads. V5 is a from-scratch rebuild (#741) landing in parts — this
file describes what has actually shipped, not the full V4-era feature set.

## Tier

**Plugin** — domain layer + repositories + service + handler + Templ page,
following `internal/plugins/maps/`'s shape.

Front end: `static/css/calendar-view.css` (the page's stylesheet, scoped
under `.cal-v5`), `static/js/widgets/calendar_view.js` (mounts as
`data-widget="calendar_view"`: month grid, day/era fold-out cards, event
glance/detail, moons), `static/js/widgets/calendar_editor.js` (loaded only
when the page's mount div carries `data-can-edit="true"`; augments the
already-mounted `calendar_view` instance rather than mounting on its own,
on the calendar's own page or on one mounted later), `static/js/widgets/calendar_event_drawer.js`
(the event editor) and `static/js/widgets/calendar_rule.js` (its pure rule logic). `static/css/calendar_v5.css`
styles the Calendars page (its cards and their peeks) and the wizard, and
`static/js/calendar_open.js` runs the cards' touch peek and the opening.

Moon phase names come from `Moon.MoonPhaseName`, each centred on its turning
point, so the night before a full moon reads "Full Moon". `calendar_view.js`,
`sky_pane.js` and `chronicle_gen.js` each keep a copy of that table, held in
step by `test/js/moon_phase_names.test.mjs`. Every moon phase is read on the
day counter weekdays use (`Calendar.absDayIndex`, `CalDate.dayIndex`,
`SkyWorld.dayIndex`): a real-world calendar's real Moon is anchored to the
Julian Day Number, which `AbsoluteDay` drifts from by a day each leap year.
The silhouette's lit shape is `MoonLitPath`, mirrored by `MoonMath.litPath`.

## The Calendars page: peek and opening (#958)

The signed "card opening" design. Each card is a plain link to its
calendar's own page (`/calendars/:calid/view`), so without script, or when
anything below fails, a card is ordinary navigation, and a direct visit to a
calendar is untouched.

- **Peek:** hovering a card, or focusing it from the keyboard, slides its
  month out from under the card: the month's name and a miniature grid,
  today filled in, a mark on each day with an event. It is server-rendered
  (`calendarPeek`, from `buildMonthGrid` and `countEventsByDay`), so the list
  handler reads each listed calendar's current month of events alongside
  its details; a failed read peeks with no marks. Hover and focus are pure
  CSS (`calendar_v5.css`); the peek is `aria-hidden`, since the card already
  says today's date. On a touch screen the first tap peeks and the second
  opens (`calendar_open.js`, `tapAction`).
- **Opening:** `calendar_open.js` fetches the card's link (prefetched after a
  short hover or on focus), takes the page's `#main-content`, and mounts it
  in place: the list is lifted into a fixed copy that fades back, the
  calendar's page is put where it was and mounted the way boot.js mounts any
  page (`Chronicle.mountWidgets`, `htmx.process`), and the URL is pushed as
  the calendar's own. Motes of light (a pre-drawn glow sprite on one canvas,
  additive on a dark page, normal on paper) fly from the card, or its peek
  if it is showing, to the calendar's pieces in reading order; each piece
  appears as its first mote lands, the calendar's card gains its paper and
  the grid's hairlines are drawn last. It is all done in about a second
  and the calendar is fully usable throughout. The frame loop runs only
  while a mote is flying or fading, then the canvas is removed. A fetch that
  fails or isn't a calendar (a login redirect, say) navigates instead.
- **Back:** "Back to calendars" (a real link on the calendar's page, shown
  only on a calendar opened this way), the browser's Back button, or Escape
  returns to the list kept aside, restored where it was scrolled to, with
  focus on its card. Escape gives way first to anything of the calendar's
  own: an open day, era, moon or event card, the event drawer or weather
  sheet, edit mode, or a field being typed in. Going Forward again opens the
  calendar with a plain crossfade. If another page came in between, the
  list's history entry reloads as a page.
- **Reduced motion:** a 160ms crossfade each way, no motes.
- Leaving through the sidebar (any htmx swap of `#main-content`) drops the
  kept list and stops any motion. The script's listeners are delegated on
  the document and hold no page DOM, so they never need removing.
- The calendar repaints its month when its first fetches return, replacing
  the day cells, so pieces are hidden by one `<style data-cal-veil>` rule
  keyed by selector (a day by its `data-key`) rather than per element.
  Stylesheet links never move with the lifted page, since a link taken out
  and put back reloads its sheet and the page would flash unstyled.
- Pure helpers (reading order, mote paths and timing, the tap rule, when
  Escape goes back) are pinned by `test/js/calendar_open.test.mjs`.

## The page (V5 part A, #741)

`GET /campaigns/:id/calendars/:calid/view` — registered in both the
authenticated member group (`RequireRole(RolePlayer)`) and the public-capable
group (`RequireViewAccess()`), mirroring the existing `GET
/calendars/:calid` JSON route directly above it in `routes.go`. The handler
loads the calendar (`GetCalendarForViewer`, eager sub-resources) and its
current month's events (`ListEventsForMonth`), then renders a thin Templ
shell: breadcrumbs, the stylesheet, and a mount div carrying viewer flags
(`data-can-edit`, `data-can-author-dm-only`, `data-role`, `data-api-base`)
plus a hidden JSON config div (calendar + first month's events) so first
paint needs no extra fetch. Everything else — the grid, the fold-out day and
era cards, event glance/detail overlays, moons, and (for an editor) the
editing surface — is rendered client-side by the two widgets.

Ported from two operator-signed mockups (the calendar page and the owner-
editing surface): the CSS token system (ink/paper, oklch colors, light/dark),
the `.cal`/`.wing`/`.flap`/`.evp`/`.hc`/`.mk` layout vocabulary, and the
motion rules from #760 (grow-from-anchor, final-size-first layout, glance
cards that vanish on leave, reduced-motion crossfade, focus return). The
widgets' JS itself is a fresh implementation against Chronicle's real API —
the mockups' own JS runs against synthetic sample data with a different
field vocabulary, so it was not something to copy statement for statement.
The one exception is the day and era cards' fold (`foldGeo`/`foldAt`/
`foldRun` in `calendar_view.js`), ported from the signed mockup's geometry
as it stands, since its timing is the signed contract.

## What shipped

- Month grid: weeks sized to the calendar's own week length (`--cols`),
  intercalary/festival months rendered as a full-width band, today and past-
  day styling, per-day moon silhouette (phase-accurate, a flat lunar disc
  rather than the mockups' seeded crater/sea texture — see "Honest gaps").
- Event icons on the grid (#761): a small glyph per event (its own icon,
  else its kind's, else a dot), "+N" when a day is busy, a glance card on
  hover (~350ms rest, vanishes on leave), a day card ("wing") on click with
  the clicked event highlighted, and a full-detail overlay ("evp")
  reachable from either the grid or the day card — read-only for players,
  with an Edit/Delete footer for a viewer who may write it.
- The day card and the era card fold out as two leaves of paper (#829, the
  signed calendar mockup): the head (date, weather) and the rest (events,
  then moons), which scrolls on a desktop while the head stays in view. The
  day card goes beside its day where there is room (right, else left), else
  under or over it; the era card drops from the era label. The leaf nearer
  what was pressed turns out first and the other unfolds from behind it;
  what was pressed gives a little, and the day's own marks fly from the
  cell into their rows (and back on close). A second press on the open day
  closes it; another day's press folds this one away first; a press during
  the motion waits for it. Phones get a sheet grown from the tapped day;
  reduced motion cross-fades. A card stays inside the visible part of the
  calendar, except that a form opened in it may grow it to the screen's
  visible edge. `refreshWing()` redraws an open card in place after an
  edit or a fetch, never under a form being filled in.
- The sky over the month (#830, the signed "Sky Pane" mockup): today's sky
  sits flush at the top of the card, and the **Sky** chip that leads the
  header's actions folds it away like a window shade and opens it again,
  remembered per viewer in the browser. It is drawn from the calendar and
  today's events this viewer already has, so a player never sees a hidden
  moon or a `dm_only` sky event in it. The fold and drawing are
  `SkyPane.Dock` in the sky widget (`internal/widgets/sky/.ai.md`, "Docked
  in the calendar"). A day's own sky in its card is #833.
- Era flap: read-only current-era display for everyone; a full list-manage-
  add-edit-delete editor for `canAuthorDmOnly` (Owner or a granted
  co-Director — the era write routes are gated `CanAuthorDmOnly` in
  `routes.go`, same as event kinds and the moon hidden flag).
- Moons (#762): a moon-view dialog with a per-moon strip (phase, % lit) and
  a day-tick strip standing in for the mockups' ambient canvas graph (see
  "Honest gaps"); a moon-night payload (blood/magical/eclipse/harvest, on an
  event whose `payload` carries `MoonNightPayload`) badges its span on the
  tick strip. `HiddenFromPlayers` toggle for `canAuthorDmOnly` (Owner or a
  granted co-Director — the moon write route is gated `CanAuthorDmOnly`,
  same as eras and event kinds). Eclipse and harvest nights are
  intentionally NOT marked on the month grid — only the day card and the
  moon view name them, per the operator's answer on #741.
- Event editor drawer (`calendar_event_drawer.js`): Edit on an event's
  detail, or "Add an event" on a day, opens a side drawer with
  the full set of fields the events API stores: title, all-day or start/end
  times, end date, repeats (with an end after N times or on a date), kind,
  notes, and for `canAuthorDmOnly` who sees it and when players are told.
  Untouched notes are left out of the save so rich text written elsewhere
  keeps its formatting. Delete in the drawer is Owner-only, like the route.
  The compact form in the day card is only the fallback if the drawer's
  script did not load.
- Repeat by a rule (in that drawer; pure logic in `calendar_rule.js`, tested
  by `test/js/calendar_rule.test.mjs`): the Repeats list keeps the plain
  repeats on top, then a "By a rule" group of ready-made rules and "Make
  your own…". A rule shows as a plain sentence, one row per condition (kind
  and its fields, remove; at most 6), "+ Add a condition", a folded "Every
  Nth time, or shift the date", and "Next five" dates from `POST
  .../recurrence/preview` (debounced, with a quiet loading state and an
  error with a retry; the browser never evaluates a rule itself). Editing a
  ready-made rule makes it "your own rule". Rows map to the API kinds
  `moon_phase`, `weekday` (one or several), `nth_weekday`, `day_of_month`,
  `month`, `season_start` (a season, or any season) and `relative_to_event`; a condition the rows have
  no fields for (`months` with several, `season`, `after_event`) is shown as
  a sentence, can be removed, and is sent back unchanged. Moon and season
  kinds and presets are hidden when the calendar has none; a moon hidden
  from players is offered only to a viewer who may author Director-only
  content. The event picker lists events from the months the page has
  loaded, since the events API lists one month at a time. Save sends
  `recurrence_rule` as a value (a rule), `null` (the event had one and now
  repeats plainly) or nothing (kept: a new plain event, or a rule the server
  hid from this viewer, which the drawer leaves alone).
- Repeating dates on the page: `calendar_view.js` reads each repeating
  event's `occurrences` from the month read, so rule events show on every
  date, a moved date shows on its new date, a skipped date is absent for
  players and struck through (grid mark and day card) for editors, and
  `countEventsByDay` counts from the same list. An event flagged
  `occurrences_truncated` shows only what was found. The start date is put back only when a truncated read carried no
  list at all, and never when an occurrence was moved from it. An event that
  arrived without `occurrences` uses the old arithmetic.
  On a repeating event's card, an Owner or co-Director gets "Move this one"
  (a month/day/year picker for that date only), "Skip this one" and, on a
  skipped or moved date, "Undo", through the occurrence endpoints; the
  month is read again afterwards. The override key is the date the series
  put the occurrence on (`moved_from` for a moved one).
- Edit mode + select-many + bulk bar: click or drag across days to select
  them while editing (Ctrl/Cmd-drag removes a range already picked,
  shift/ctrl-click extends); a weekday button picks that column and a
  handle at the end of each week picks the week; on touch a tap toggles a
  day and press-and-hold then drag picks a range. Keyboard: Space toggles
  the focused day, Shift+arrows extend from the anchor, Escape clears the
  selection when no panel is open. The bulk bar offers Hide/Reveal (bulk
  event visibility, gated `CanAuthorDmOnly` — the one bulk action whose
  route already supports a co-Director) and Shift events (moves every event
  touching the selection by N days, client-computed with the same date math
  as the grid, then a PUT per event). Rule events, and repeating events with
  a skipped or moved date, are left as they are and reported as such.
- New-kind-in-place: creating an event kind inline from the event form
  (`canAuthorDmOnly`, since `POST .../event-kinds` is gated
  `CanAuthorDmOnly`).
- Calendar switcher (hub popover): fetches `GET .../calendars/list` and
  links each result to its own `/view` page.
- Keyboard: arrow keys move the roving day focus, Enter/Space opens it, `T`
  jumps to today, Page Up/Down change month (Shift+Page Up/Down by a year);
  Escape closes whichever panel is topmost (event detail, then the day
  wing it grew out of, moon view, era flap, or the calendar switcher);
  every panel returns focus to whatever opened it on close.

## Honest gaps

These are real, not oversights — each is a case of "the mockup shows it, the
server doesn't support it yet" (per this PR's own instructions: build what
the server supports, list the gap rather than inventing data):

- **Day weather: owners' own kinds, player forecasts and Lock are not built (#890, #917, #918).**
  `calendar_weather_days` holds one reading per day, `source` "manual"
  (painted) or "generated"; a generated write never replaces a manual one.
  `GET .../weather/days?year=` (optional `&month=`) gives a Player only days
  up to the calendar's today, whatever `forecasts_enabled` says; an Owner or
  co-Director sees every day. `PUT .../weather/days` and
  `POST .../weather/days/clear` are CanAuthorDmOnly, at most 1000 days per
  call, each date checked against the calendar's months. `calendar_view.js`
  fetches a year at a time (`fetchWeatherYear`) and shows each reading as a
  corner mark on its day (`.wxm`) and a line on the day card, both in the
  reading's own colour, future days faint and tagged; today falls back to
  `Calendar.Weather`. Edit mode tints painted days (`.cal.wxon`,
  `.cpt`/`.cwx`). Writing is in `calendar_editor.js`: the bulk bar's Paint
  weather tray sets a kind on every chosen day as a manual reading, with
  Clear and a one-step Undo; Generate… (bulk bar for chosen days, header for
  the shown month) opens `calendar_weather_sheet.js`, which previews a
  climate's weather as cards and faint grid marks (`view.wxPreview`,
  `.ghost`), lets the owner keep days and reroll the rest or one day, and
  applies as generated readings with Undo on the toast. Painted days go to
  the generator as locks and are never saved over. Both use the generator
  in `chronicle_gen.js`, loaded on first use from `data-engine-src`. Day
  readings are not in campaign export yet (#805).
- **The structure editor edits only what the wizard's editor shows.** A
  moon's phase offset, colour and look, and a season's colour, description
  and weather effect, have no control on the "Edit structure" page; a save
  leaves them as stored. Who besides the Owner may use the editor (#831's
  co-Director question) is not settled, so it stays Owner only.
- **Sessions scheduled by in-world date are not re-dated** when a structure
  save moves months: the sessions plugin owns those rows and has no
  calendar-facing write for them.
- **The moon graph is a simplified day-tick strip, not the mockups' ambient
  canvas.** The signed design (#762) wants a living light/shadow backdrop,
  a blood-moon drip and a magical-moon aura confined to their own date
  span, and calm ambient motion that pauses off-screen. What shipped: a
  horizontally-scrollable strip of per-day phase discs (still phase-
  accurate, still moon-night-badged, still IntersectionObserver-paused and
  reduced-motion-frozen) rather than a canvas/SVG animated graph. Tracked
  in #794.
- **Per-day moon silhouette is a flat lunar-phase disc**, not the mockups'
  seeded crater/sea texture — same phase math, a plain silhouette shape.
- **No backdrop era/season colour field or its sweep transition** on month
  change — the mockups' `.fieldwrap`/`.bleed`/`.crest` layer was ported into
  `calendar-view.css` as dead CSS (kept for a future pass rather than
  deleted, since it costs nothing unreferenced) but `calendar_view.js` never
  attaches it (`_paintDaySkyContext` is a deliberate no-op with a comment
  pointing here).
- **The event drawer has no linked pages or RSVP section.** The signed
  editor shows both; the events API has no field for linked pages, and
  RSVPs are covered below.
- **Game nights show only on a calendar that follows the real clock.**
  `calendar_view.js` reads the sessions plugin's
  `GET /campaigns/:id/sessions/nights` (members only) for the visible month
  and places each night on its real date: a dice mark in the cell, a box in
  the day's card with Going / Maybe / Can't, a note and the count, and a
  page with the whole roster. Answers go to the sessions plugin's own
  `/sessions/:sid/rsvp` and `/rsvp-exclude`; the calendar stores nothing.
  Still missing from the signed game-nights mockup (#837): placing nights
  on a fantasy calendar through its real-date anchor, each viewer's own
  time zone (times show in the zone the organiser set, labelled), the
  answer-by date, the Director's "ask the ones who haven't answered", and
  availability painting. The old event RSVP table (`calendar_event_rsvps`)
  stays dropped: game-night answers live with sessions.

## New-calendar wizard

`GET /campaigns/:id/calendars/wizard` (Owner only) — an HTMX dialog, every
step swapped wholesale into `#calv5-wizard-root`. The Start step groups its
tiles by purpose: **For your table** offers the Real-world calendar (game
nights, RSVPs, everyone's availability, on the real dates — the operator's
own framing); **For your world** offers a shipped preset, Build your own,
importing a file, and Generate one. No tile carries a decorative icon.

Every source — preset, real-world, built, imported, or generated — ends up
as an `ImportResult` (`import.go`) and is created through the SAME
`CreateCalendarFromImport` call, so every one of them gets the same
re-validation (`checkCalendarImportLimits`, `clampCalendarStructure`, name
lengths, color normalization) regardless of how trustworthy its source
looks: a preset is re-parsed from its own shipped file, and a browser-
submitted `import_json` (from the import step, Build your own, or Generate
one) is re-parsed and re-clamped by `parseWizardImportJSON` — never trusted
as already-validated just because it round-tripped through a hidden field.

- **Real-world calendar** (`reallife.go`, `WizardRealWorldReview`): a fixed
  Gregorian definition — twelve real months (true 4/100/400 leap rule via
  `MonthDays`, `daysInGregorianMonth`) and seven real weekdays, Monday
  first, matching how a `TracksRealTime` calendar's `WeekdayIndex` actually
  places a day (`gregorianJDN(...) % 7`, congruent to 0 on a Monday) — plus
  the real Moon, anchored to a documented reference new moon so its phase
  reads correctly against the real sky. That anchor is a mean synodic month,
  not the true perturbed cycle, so it can drift by up to about half a day
  over long stretches — carried forward as an `ImportResult` warning, not
  hidden. It also starts with the four default seasons `defaultRealLifeSeasons`
  already seeds for an existing real-life calendar's first hemisphere
  choice, guessing the northern hemisphere (a starting guess, not a
  geography check — nothing about a campaign says which hemisphere its
  table is in; also carried forward as a warning). Whether a new real-world
  calendar should start with seasons at all is an open decision (`#741`);
  this package's own default is to include them rather than leave the
  calendar season-less. Its own Review step asks for a name (default "Real world"), a time
  zone (`timeutil.CommonZones()`, defaulted from the browser's `Intl`
  detection and, failing that, the owner's stored account time zone when
  `Handler.SetTimezoneLookup` is wired), and "today follows the real date"
  (on by default). While that switch is on, no year/month/day fields show at
  all — `WizardCreate` computes "today" from the wall clock in the chosen
  zone itself, at creation time, rather than trusting anything the browser
  could have sent for it; switching it off asks for an explicit date instead
  (a `reallife`-mode calendar that doesn't track real time, exactly the
  "manual" case `Calendar.UsesRealTime` already documents).
- **Build your own** (`WizardBuildStep`/`WizardBuildPreview`): a client-side
  Alpine editor — months (name, days, optional per-month leap days), an
  optional leap rule (every N years), weekdays, optional moons (name, cycle
  days), and one era (name, starting year) — each addable/removable/
  reorderable with plain labelled buttons, no icons. It starts from sensible
  defaults (twelve months, seven weekdays, one moon, one era) the owner is
  expected to reshape. "Continue" serializes the edited state into the same
  `ImportResult` JSON shape an uploaded file produces and hands it to
  `parseWizardImportJSON`, landing on the ordinary shared Review step from
  there — an oversized or malformed built calendar is refused exactly like a
  tampered upload would be.
- **Generate one** (`calendar_wizard_generate.templ`, `wizard_generate_handler.go`):
  a recipe sheet over the generator engine, `static/js/widgets/
  chronicle_gen.js` — a vendored copy of the design lab's own engine (its
  header documents the full `ChronicleGen.*` API), unchanged apart from the
  `fromSky` extension below.
  Opening the step immediately shows a complete calendar from a fresh seed,
  names included; every recipe chip, stepper, the naming culture and the
  seed are live — change one and the result rebuilds, using the same seed
  unless the owner asks for a new one ("Reroll all" or a part's own Reroll),
  since the engine's own RNG streams are keyed by seed+template+theme and
  already vary with either. Each result part (name, the year's shape, era,
  months, weekdays, seasons, moons, festivals) has its own Keep (freeze
  its current value through the next rebuild) and Reroll (a fresh value for
  that part alone, everything else untouched); Keep needs no separate
  snapshot store — the previous `cal` is still in scope when the next one
  is computed, so a kept part is copied straight across. Generation is
  entirely client-side (Alpine `x-data`, same pattern as Build your own);
  the server never runs the engine.
  - **The engine loads on demand, not through the usual paths.** boot.js
    sets `htmx.config.allowScriptTags=false` (see `tools/check-page-scripts.sh`),
    so ANY `<script>` tag — inline or `src`, in any htmx-swapped fragment —
    is silently stripped, not just on boosted nav; and the plugin
    body-script registry (`routes.go`'s `pluginBodyScripts`) loads on every
    page, wrong for a ~460KB engine only this one step needs. Instead the
    step's `x-init="boot()"` calls `ensureEngine()`, which does
    `document.createElement('script')` and appends it itself — a genuine
    DOM mutation the browser executes on its own, outside htmx's swap
    parsing entirely, paid for only when this step is open.
  - **"Work it out from the sky"** (off by default): three steppers, Suns
    (1–3), Moons (0–4), Wandering planets (0–7), replace the recipe/culture
    controls. `ChronicleGen.calendar.fromSky({suns, moons, planets, seasons,
    theme, seed})` derives the shape instead of drawing it from a template:
    the year's length comes from the sun(s) (a seed-stable flavour knob for
    more than one, same honesty every template already has about not being
    real astronomy); months are sized to the main moon's cycle, with
    whatever the cycle doesn't spend becoming festival days (a small
    remainder) or folded into the last month (too large to be a
    "festival"); the week is one day per visible wanderer — suns, moons and
    planets together, the way our own 7-day week came from 7 wanderers —
    unless that is fewer than three, when a quarter of the main moon's cycle
    takes over instead; and the leap rule falls out of whatever a whole-day
    month count dropped from the true, fractional year length. Returns the
    exact same result shape `calendar.generate()` does (`summary`, `preset`,
    `extras`, `warnings`), so the recipe sheet treats the two
    interchangeably. Covered by `test/js/chronicle_gen.test.mjs` (determinism,
    a full-range validity/round-trip sweep, the moon count always matching
    the stepper, the week-length fallback, extreme and out-of-range inputs).
  - **Review** (`WizardGenerateStep`/`WizardGeneratePreview`): "Review"
    serializes the live calendar with `ChronicleGen.cal.toPreset()` (the
    engine's own chronicle-calendar-v1 shape) into a hidden `generated_json`
    field, POSTed to `/wizard/generate/preview`. The server never trusts
    it: `parseGeneratedCalendarJSON` enforces a local size cap
    (`maxGeneratedCalendarSize`, generous for anything the engine actually
    produces, tight enough to reject a tampered payload) and then calls
    `CalendarService.PreviewImport` — the SAME auto-detecting parser
    (`DetectAndParse` → `parseChronicle`) and clamp/limits
    (`clampCalendarStructure`/`checkCalendarImportLimits`) an uploaded
    Chronicle export already goes through, not a second check invented for
    this path — before rendering the ordinary shared Review step with
    `source="generate"`. This route is deliberately NOT in `app.go`'s
    `calendarImportPathPattern` skip list: a generated calendar never needs
    anything near the other import routes' 10MB allowance, so it stays
    under Echo's global 2MB body limit instead.

## Edit structure

`GET /campaigns/:id/calendars/:calid/structure` (Owner only, like the wizard
and `PUT /calendars/:calid`) is the wizard's "Build your own" editor
(`structureEditorForm`, shared with the wizard through
`structureEditorConfig`) prefilled from the calendar
(`calendarEditorState`), with season rows and each month's Festival and
weekday's Rest day flags added and the wizard's single-era section left
out (eras have their own manager on the calendar). It is reached from the
gear ("Calendar settings") in the calendar header's edit strip, shown to an
Owner only, and from "Edit structure" in a calendar card's menu on the
Calendars page. A calendar that follows the real-world date gets an
explanation instead of the editor: its months are the Gregorian ones.

1. **Preview changes** posts the editor's JSON to `POST .../structure/preview`.
   It is re-validated by `parseWizardImportJSON` (size cap, clamp) like a
   wizard build, then `PreviewStructureEdit` plans the save without writing
   and the plan fills the slot under the editor: month notes (moved,
   renamed, removed, added, resized), the week, leap rule and removed moons
   and seasons, and the events it affects. Changing anything in the editor
   empties the slot (`x-effect`), so a preview on screen always matches it.
2. **Save** posts the same structure and the preview's fingerprint to
   `POST .../structure`. `ApplyStructure` opens a transaction, locks the
   calendar row (`FOR UPDATE`), reads the plan's input through it
   (`loadStructureState`, the same reader the preview uses) and hands it to
   the service, which plans again. If the fingerprint (months, leap rule,
   today, moons, seasons, eras, every event's dates, every day-weather
   reading's date, every repeat rule's stored JSON, every override) differs, nothing is written and the fresh preview
   replaces the old one; a second save on the same calendar waits on the
   lock and so always plans from the first one's result. Otherwise the
   same transaction writes everything and the owner lands on the calendar.

How `planStructureEdit` treats months and events (#741's rules):
- **Months match by name.** A name unique in both lists follows its month
  wherever it moved; a month whose place now holds a name the calendar
  never had is a rename in place. Anything else has no counterpart.
- **Moved:** an event in a month that moved follows it — the one rewrite
  a save makes, listed as a count in the preview. Events, their end and
  recurrence-end months, and eras' start and end months are remapped
  together (`remapMonthPositions`, one `CASE` per column, so swaps are safe).
- **Re-dated:** an event in a month with no counterpart is not touched; if
  its month position still exists it will show in whichever month is there
  now, and the preview names it.
- **End and repeat-until dates** are judged the same way: one left in a
  removed month whose position now holds another month makes the event
  re-dated; one that will not exist makes it stranded.
- **Stranded:** an event whose date (or end date) will not exist — its
  month position is gone, its day is past the new month length, or it is a
  leap day the new leap rule drops — is kept, not touched, and named.
  Events already off the calendar before the save are not reported.
- **Eras** follow their month too; one starting or ending in a removed
  month is named in the preview.
- **Day weather** (`calendar_weather_days`, keyed by year, month position
  and day) follows its month the same way, swap-safe for the primary key
  (`remapWeatherDays` parks moved rows on negative months first). A reading
  in a removed month stays put, except where a moved reading now claims its
  day: then the moved one wins and the other is deleted. The preview counts
  readings moved, re-dated, deleted and stranded, and warns about deletions.
- **Repeat rules and overrides** follow their month too (`structure_repeats.go`).
  A `rule` event's `month` / `months` conditions are rewritten Go-side
  through `ParseRecurrenceRule` and the rule serializer, in the same
  transaction (`StructureWrite.RuleUpdates`); a months list is de-duplicated
  after the rewrite. `calendar_event_overrides` keys (`occurrence_month`)
  and move targets (`new_month`) are remapped by `remapOverrides`, swap-safe
  like day weather because the month is in the primary key. A condition
  naming a month with no counterpart is never rewritten: the rule is left as
  written and named in the preview, as is a rule that repeats by a removed
  moon or season (it matches nothing). An override in a removed month stays
  and is counted, unless a moved override claims its date, where the moved
  one wins and the other is deleted (the preview says so). A stored rule the
  strict parser refuses is left alone.
- **Today** follows its month like an event and is clamped to the nearest
  day that exists only if it would otherwise be gone; the preview says so.
- **Moons and seasons** keep their ids: an existing moon's name and cycle
  change in place (its hidden flag, colour, phase offset, look and phase
  rows survive), an existing season's name and dates likewise.

## Repeat rules and one-off overrides

An event repeats by `recurrence_type` (`weekly`, `biweekly`, `custom`
(every `recurrence_interval` weeks), `monthly`, `yearly`, or `rule`). A `rule` event carries `recurrence_rule`:

```json
{"match": [{"kind": "moon_phase", "moon_id": 3, "phase": "full"},
           {"kind": "weekday", "weekday": 5}],
 "every": 1, "offset_days": 0}
```

A day matches when **every** condition holds; `every: N` keeps every Nth
match counted from the event's start date; `offset_days: K` (−365..365)
moves each kept match K days. `recurrence_max_occurrences` and the
`recurrence_end_*` date still bound the series. Conditions (1–6 per rule):

| `kind` | Fields | Matches |
|---|---|---|
| `moon_phase` | `moon_id`, `phase` (`new`, `first_quarter`, `full`, `last_quarter`) | the day that phase falls on, as the grid's silhouette shows it |
| `weekday` | `weekday` or `weekdays` (0-based) | that weekday; intercalary days have none |
| `nth_weekday` | `n` (1–5, or −1 for last), `weekday` | the nth / last such weekday of its month |
| `day_of_month` | `day` (1-based, or −1 for last) | that day of any month |
| `month` / `months` | `month` / `months` (1-based) | any day of those months |
| `season` / `season_start` | `season_id` (optional for `season_start`) | any day of the season / its first day; `season_start` without a `season_id` is the first day of any season (refused when the calendar has no seasons) |
| `after_event` | `event_id`, `days` (−365..365) | `days` after each occurrence of another event |
| `relative_to_event` | `event_id` | the same days as another event (pair with `offset_days`) |

Every date is read on `Calendar.absDayIndex`, the counter the grid, weekdays
and moons share, so leap days, zero-day leap months and intercalary months
behave as they do on the page. Moon, season and event ids must belong to
this calendar and be visible to the writer; an event used as an anchor
cannot itself repeat relative to another event, so there are no chains or
cycles. Only dependents the writer can see refuse an anchor that starts
following another event; a Director-only dependent never refuses a
Scribe's save (that would reveal it), and read-time expansion follows one
level only, so that dependent's anchor condition simply matches nothing
until the Director re-saves it, which is then refused with the reason. The rule is parsed strictly (unknown fields, size over 4 KB, or a
second document are refused) and is a partial-update field: absent keeps,
`null` clears. It lives only on an event whose type is `rule`: one sent
with another type is ignored, and changing the type away from `rule` drops
the stored rule, so a rule never lies dormant to be judged again later.
Exports carry a rule only for `rule` events.

**Expansion.** `ListEventsForMonth` fills each repeating event's
`occurrences` (`[{year, month, day, skipped?, moved_from?}]`) for the month,
loading anchors and overrides in one query each. A rule that keeps every
match is scanned from the month itself, at most five calendar years
(400–4000 days). A counted rule (`every` > 1 or a max) has to count every
match since its start, so it walks from the start date, only testing days
until the month is near, up to 1000 calendar years (at most 400,000 days);
an override write checks its date the same way. Each anchor is walked once
per request however many rules name it, and one request tests at most
1,500,000 days in all (about 35 ms). An event whose walk hits either bound
is still returned, with what was found (often `"occurrences": []`) and
`"occurrences_truncated": true`: its dates are unknown, not absent. Other
read paths (upcoming, timeline, search, `GET` one event) return the event
with its start date and rule, not expanded dates.

**Overrides.** `calendar_event_overrides` holds "this one only" changes for
any repeating event, keyed by the date the series put it on: `skip`, or
`move` to another date. A skipped occurrence comes back flagged `skipped`
to an Owner, co-Director or Scribe and is left out for a Player; a moved
one appears on its new date, with `moved_from` for editors only. Overrides
are deleted with their event.

**API.** `POST`/`PUT .../calendars/:calid/events[/:eid]` take
`recurrence_rule`. `PUT .../events/:eid/occurrences/:y/:m/:d` with
`{"action":"skip"}` or `{"action":"move","year":..,"month":..,"day":..}`
and `DELETE` on the same path (undo) need the same role as editing the
event; the date must be one the series really falls on, and a move onto
another occurrence is a conflict. `POST .../calendars/:calid/recurrence/preview`
with `{recurrence_rule, year, month, day, count, recurrence_max_occurrences,
recurrence_end_year/month/day}` returns `{"dates":[...], "truncated":bool}`,
at most 10 dates, for anyone who can read the calendar; it writes nothing.

**Visibility.** Rule dates follow the event's own visibility; a rule that
names a hidden moon or an event the viewer cannot see is left out of the
event for that viewer (the `recurrence_rule` key is omitted), so its dates
stay but the hidden thing is not revealed. The page's `calendar_view.js`
and the server-drawn preview grid read `occurrences` (see "Repeating dates
on the page" above); the Foundry module does not read them yet.

Campaign export carries each event's rule and overrides plus moon and
season `ref`s; import creates anchors first, rewrites every id a rule
names to the new calendar's, then replays overrides (skips first, then
moves, retrying a move that conflicts until no more go in). The calendar's
own export format (`BuildExport`, `parseChronicle`) carries rules and refs
the same way, but no overrides; on its import a rule that is unreadable,
names something the file does not carry, or fails the save checks makes
its event a one-off on its start date, with a warning.

## Data model

See `model.go` for the full types; `.ai/data-model.md` is the schema
overview. `Calendar` eager-loads `Months`, `Weekdays`, `Moons`, `Seasons`,
`Eras`, `EventKinds` (campaign-scoped, not calendar-scoped — shared by every
calendar in a campaign), `Cycles`, `Festivals` and `Weather` via
`GetCalendarForViewer`; `Eras`/`EventKinds` are stripped and `Moons` filtered
(`HiddenFromPlayers`) for a viewer that isn't an author (`ADR-049`).

## Security

- Every read is viewer-filtered (`permissions.Viewer`, ADR-049): a hidden
  calendar's events are not found; a linked entity a viewer can't
  separately see has its name/icon/color/id blanked
  (`redactHiddenEntityLinks`), failing closed if the entity gate isn't
  wired.
- Every write is authorized server-side regardless of what the UI shows or
  hides — the client-side role checks described in "Honest gaps" above are
  a UI nicety (don't show a button that will 403), not the security
  boundary; `routes.go`'s middleware is.
- Icons and colors are pattern-checked server-side (`service.go`); the new-
  kind and new-era forms in `calendar_editor.js` only offer a fixed swatch
  list, so a malformed value can't reach the request body from those forms,
  but the server-side check is what actually matters.
