# Homebrew Plugin

## Purpose

The **Homebrew Workshop**'s store and contract. A recipe is the everyday
widgets (tracker, clock, checklist and the rest) and kinds of part other
plugins own (a worked-out field, a creature recipe, an ancestry), wired by
When/Then rules. Recipes are built in the Workshop (Rulebook > House rules,
Director view), placed on pages with the Customizer, and run at the table
from the DM Screen's Homebrew drawer. This plugin holds no kind of part
itself: everything is registered by the plugin that owns it.

## The recipe document

```json
{ "name": "Remnant need", "version": 3,
  "doc": {
    "parts": [ { "key": "need", "kind": "tracker", "label": "Need", "see": "director", "data": { "shape": "count", "max": 5 } } ],
    "rules": [ { "when": { "event": "tracker.reached", "part": "need", "args": { "value": 5 } },
                 "timing": "now",
                 "then": [ { "action": "set", "part": "need", "args": { "to": 0 } } ] } ] } }
```

- `see` is `party`, `name` (players see it exists, not its details) or
  `director`, default `director`. A kind may force it (`ForceSee`).
- `data` and every `args` belong to the owner, whose `Check` validates and
  normalises them; an absent value reaches the owner as `{}`.
- A rule's `part` must be a part of the same recipe, of a kind the event or
  action lists in `PartKinds`, and present exactly when it lists any.
- `timing` is `now`, `encounter_end` or `held` (waits in the drawer).
- `layout` (optional) is where each card sits on the Workshop canvas, keyed
  `p:<part key>`, `r<rule>` (its When) and `r<rule>.<step>` (a Then), both
  counted from 0. The server keeps only keys of cards the doc has, clamped to
  ±`MaxCanvas`; nothing but the Workshop reads it.
- A saved layout ("template") is just a recipe.

## Registering

`*Registry` is filled while the app starts. An owner registers from an
adapter file in `internal/app` whose `init` calls `addWorkshopSource` (see
`homebrew_adapters.go` for trackers and `workshop_parts.go`), so no plugin
imports another and a new owner never edits `routes.go`. A service the
adapter needs comes in through `workshopDeps`, nil while its plugin is
degraded:

| Register | What |
|---|---|
| `RegisterPart(PartKind{Name, Label, ForceSee, Preview, Check})` | a kind of part |
| `RegisterEvent(EventDef{Name, Label, PartKinds, Fields, Preview, Check})` | something that starts a rule |
| `RegisterAction(ActionDef{Name, Label, PartKinds, ClientRun, Fields, Preview, Check})` | something a rule does |

`Fields` lists the args the Workshop's inspector asks for (`Field{Name,
Label, Type}`, type `whole` or `text`); the owner's `Check` still decides.
A new When or Then starts with each whole-number field at 1.

`Sync` (`PartSync{Check, Apply}`), on a part kind, keeps records the owner
holds in step with the recipes: tracker and clock parts are saved as tracker
kinds. The service calls every `Check` with the recipe's parts of that kind
before storing anything (a refusal is shown to the Director and nothing is
written), and every `Apply` after the recipe is stored; a delete applies an
empty list. Each call is the whole picture for one recipe, so a repeat is
harmless and saving again mends a failed apply.

`Preview` lets the Workshop's live preview act a recipe out without knowing
any owner by name. A part kind with `Preview: "shape"` holds a trackers shape,
so the preview shows it as a number. An event's `&Preview{Op: "reach", Arg}`
fires when that number lands on the `Arg` field's value or moves past it,
either way. An action's `Op: "add"` (by `Arg`, or 1 with none) or `"set"` (to
`Arg`) changes it. `Arg` must be one of the def's whole-number fields, and a
client-run action can't have one. With no preview, an event is a button the
Director presses to say it happened, and an action is a line saying what it
would do.

Names are lower-case words joined by `.` or `-`; a second registration of a
name is an error. A `ClientRun` action runs in the Director's browser through
a handler a system package registered there, and only when the Director
presses Run; the server validates and records it but never runs it.

Registered so far: part `tracker` and `clock` (data is a trackers `Shape`; each is saved as a tracker kind the recipe keeps),
event `tracker.reached` `{value}`, actions `step` `{by}`, `set` `{to}` and
`tick` (clocks), all with previews; part `ancestry` `{slug}`, a link to one of the campaign's
own ancestry entries (`system_entry_homebrew_adapters.go`), whose own
visibility decides who sees it. Creature variants
(`variants_homebrew_adapters.go`, over system state): parts `creature-recipe`
`{page}` and `creature-mark` `{recipe, addons, marked, variants}`, both forced
to the Director, which point at the campaign's game-system variant recipes and
never copy them; event `creature.dies` and client-run action `rise-as-variant`
on a mark, both with no args. Parts `field`, `item` and `words` from the field
rules (see `internal/plugins/fieldrules/.ai.md`). From the calendar
(`homebrew_calendar.go`): events `moon.changed` `{moon, state?}` and
`calendar.roll` `{event, result?}` (names, not ids, so a recipe moves between
campaigns; no state or result means any) and action `party.effect` `{name,
text?, who: party|tag, tag?, see: party|director, lasts:
until_change|duration, duration?}` (duration in days); none takes a part. The
agreed names for other owners are in issue #1593.

## Who may do what

Every route is the Director's (`CanAuthorDmOnly`), checked in the service.
Players never read a recipe; they meet its parts through the widgets those
parts place, which keep their own audience rules.

## The Workshop page

`GET /campaigns/:id/homebrew` renders `workshop.templ`, a mount for the
`homebrew-workshop` widget (`static/js/homebrew_workshop.js`, `static/css/workshop.css`).
The rulebook's More menu links to it for Directors. Left: the recipe list
and the palette (the catalog's parts, Whens and Thens). Middle: a pan and
zoom canvas of cards wired part → When → Then → part; cards are dragged to
arrange them and their places save as `layout`. Right: the inspector for the
selected card. Trackers and clocks have their own shape form; another kind's
`data` is shown as set up by its owner. The page's guard is the service's
catalog call, so the page and the API keep out the same people.

Under the inspector, the **live preview** acts the open recipe out in the
page, saving nothing: each numbered part with its bar and band, step buttons,
a button for each When the preview can't start from a number, a Waiting list
for rules timed `held` or `encounter_end` with Run, and a short log. A run
lights the cards it went through; pointing at a preview line lights its card
and clicking selects it. Rules that keep setting each other off stop after 50
steps. **Try it** acts out the first rule. **Where it shows up** lists the
categories whose page layout places the recipe, read from
`GET …/recipes/:rid/placements` when a recipe is opened or saved.

## Placing a recipe

A saved recipe with a tracker or clock is offered in the Customizer's
widget list under **Homebrew**, one entry per recipe: the `homebrew_recipe`
block with `config.recipe_id` (`internal/app/homebrew_recipe_block.go`). On a
category's page layout it shows the recipe's tracker kinds (owner prefix
`homebrew:<recipe>:`) on every page of that category, through the Trackers
widget's owned view; each keeps the "who sees it" its part was given.
`Placements` reads the layouts through `PlacementFinder`, implemented in
`internal/app` over the entities plugin.

## Routes

| Method | Path | |
|--------|------|---|
| GET | `/campaigns/:id/homebrew` | the Workshop page |
| GET | `/campaigns/:id/homebrew/catalog` | registered parts, events and actions, sorted |
| GET, POST | `/campaigns/:id/homebrew/recipes` | list (`{data, total}`), create |
| GET, PUT, DELETE | `/campaigns/:id/homebrew/recipes/:rid` | PUT needs `version`; a mismatch is 409 |
| GET | `/campaigns/:id/homebrew/recipes/:rid/placements` | `[{where, name}]`; `where` is `category` |
