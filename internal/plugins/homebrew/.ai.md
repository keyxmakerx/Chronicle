# Homebrew Plugin

## Purpose

The **Homebrew Workshop**'s store and contract. A recipe is the everyday
widgets (tracker, clock, checklist and the rest) and kinds of part other
plugins own (a worked-out field, a creature recipe, an ancestry), wired by
When/Then rules. Recipes are built in the Workshop (`/campaigns/:id/homebrew`,
opened from the rulebook's ⋯ menu or the wrench in the DM Screen's Homebrew
drawer, which also works with no game system), placed on pages with the
Customizer, and run at the table from that drawer. This plugin holds no kind of part
itself: everything is registered by the plugin that owns it.

## The recipe document

```json
{ "name": "Remnant need", "version": 3,
  "doc": {
    "parts": [ { "key": "need", "kind": "tracker", "label": "Need", "see": "director", "data": { "shape": "count", "max": 5 } } ],
    "rules": [ { "when": { "event": "tracker.reached", "part": "need", "args": { "value": 5 } },
                 "timing": "now",
                 "then": [ { "action": "set", "part": "need", "args": { "to": 0 } } ] } ] } }
```

- `see` is `party`, `name` (players see it exists, not its details) or
  `director`, default `director`. A kind may force it (`ForceSee`).
- `data` and every `args` belong to the owner, whose `Check` validates and
  normalises them; an absent value reaches the owner as `{}`.
- A rule's `part` must be a part of the same recipe, of a kind the event or
  action lists in `PartKinds`, and present exactly when it lists any.
- `timing` is `now`, `encounter_end` or `held` (waits in the drawer).
- `layout` (optional) is where each card sits on the Workshop canvas, keyed
  `p:<part key>`, `r<rule>` (its When) and `r<rule>.<step>` (a Then), both
  counted from 0. The server keeps only keys of cards the doc has, clamped to
  ±`MaxCanvas`; nothing but the Workshop reads it.
- A saved layout ("template") is just a recipe.
- `off` (in `doc`, set only by the Store's add) keeps a recipe from running:
  its rules never fire, its buttons are not in the drawer, and no owner's
  `Sync` runs for it, and `PartsOfKind` skips it. `List` carries `off` so the
  Workshop can mark it. Any save through the Workshop clears it, so a
  Director's own recipe is never off.
- A part's `unlinked` (`[{pick}]`) is a link to a record of another campaign
  that sharing dropped, `pick` saying what to choose ("a deck"). Only a recipe
  from the Store has any; a save is refused while a part has one.

## Registering

`*Registry` is filled while the app starts. An owner registers from an
adapter file in `internal/app` whose `init` calls `addWorkshopSource` (see
`homebrew_adapters.go` for trackers and `workshop_parts.go`), so no plugin
imports another and a new owner never edits `routes.go`. A service the
adapter needs comes in through `workshopDeps`, nil while its plugin is
degraded:

| Register | What |
|---|---|
| `RegisterPart(PartKind{Name, Label, ForceSee, Preview, Widget, Check})` | a kind of part |
| `RegisterEvent(EventDef{Name, Label, PartKinds, Fields, Preview, Check, Match, Press, Pressed, PressArg})` | something that starts a rule |
| `RegisterAction(ActionDef{Name, Label, PartKinds, ClientRun, Waits, Asks, Rolls, Run, Fields, Preview, Says, Check})` | something a rule does |

`Fields` lists the args the Workshop's inspector asks for (`Field{Name,
Label, Type, Optional}`, type `whole` or `text`); the owner's `Check` still decides.
A new When or Then starts with each whole-number field at 1, except an
`Optional` one, which starts empty, and each text field empty.

`Sync` (`PartSync{Check, Apply}`), on a part kind, keeps records the owner
holds in step with the recipes: tracker and clock parts are saved as tracker
kinds. The service calls every `Check` with the recipe's parts of that kind
before storing anything (a refusal is shown to the Director and nothing is
written), and every `Apply` after the recipe is stored; a delete applies an
empty list. Each call is the whole picture for one recipe, so a repeat is
harmless and saving again mends a failed apply.

`Preview` lets the Workshop's live preview act a recipe out without knowing
any owner by name. A part kind with `Preview: "shape"` holds a trackers shape,
so the preview shows it as a number. An event's `&Preview{Op: "reach", Arg}`
fires when that number lands on the `Arg` field's value or moves past it,
either way; with `Every` naming an optional whole-number field, the value
repeats upward (3, again every 3: 3, 6, 9 and on). An action's `Op: "add"` (by `Arg`, or 1 with none) or `"set"` (to
`Arg`) changes it. `Arg` must be one of the def's whole-number fields, and a
client-run action can't have one. With no preview, an event is a button the
Director presses to say it happened, and an action is a line saying what it
would do: its label and part, or, when the action sets `Says`, that sentence
with each `{field}` filled from the step's args and `{part}` with the part's
label ("draws {count} from {part}" reads "draws 2 from Omens"). Every slot
must be one of the action's fields, or `{part}` on an action that takes a
part; the catalog carries it as `says`.

`Match(args, payload)` decides whether a firing meets one rule's When (no
`Match` means every firing of that event and part does). `Press` names a
drawer button that fires the event by hand; a part event can't have one.
`Pressed`, when set, is the owner's own record of a press, run after the
Director check and before any rule; an error stops the press there (the
respite button gives every crafting project its roll this way).
`PressArg` names one of the event's text fields and makes the Director name
the buttons: each distinct value of that field among the saved rules
(single-spaced, compared without case, the first spelling met kept, at most
`MaxNameChars`) is a drawer button labelled with it, and pressing one fires
the event with `{"<PressArg>": "<name>"}`. It needs a `Match` (or every
button would start every rule) and can't be set on a part event or with
`Press` or `Pressed`. A rule a named button sets off writes its owner's log
note as "<name>, from <recipe>" instead of "Rule from <recipe>"; the note is
read from the run's stored payload, so a held run says the same when it runs.
The catalog carries `pressArg`, and the Workshop's preview names the button on
the When's button.
`Run(ctx, campaignID, Act)` does the action on the server and returns the
line the drawer shows; it can't be set with `ClientRun`. An action with
neither is listed for the Director to do. `Waits` marks an action that has a
server `Run` and is still the Director's call: a rule that uses it is held
however it is timed, and `Run` does it as the Director who pressed Run. The
rule for owners is "numbers at once, bigger things wait": a number on a sheet
or a tracker moves at once; a transformation, a card dealt to someone or a note
made public waits. `Waits` can't be set with `ClientRun`, which already waits.
`Asks` marks the "Ask the Director" step (below): it takes no part and can't
have `Run`, `Waits`, `ClientRun` or a preview. The catalog carries `asks`, and
the Workshop's editor says the rule stops there; its preview stops at it too.
`Rolls` (`PlayerRoll{Offer, Roll}`) marks a step a player rolls for ("The
player rolls first", below): it takes no part and can't ask, run, wait or
preview. `Offer` says what that player would roll now (`RollOffer{Label,
Formula, Target}`, worked out from their hero) and `Roll` makes the roll on
the server and returns `Rolled` with its total; both get the player as
`Act.By`, with `Viewer.Name` filled. The catalog carries `rolls`, and the
editor and preview stop there too.

`PartKind.Share(raw, waiting) (raw, []Unlinked, error)` is the owner's say over
what leaves the campaign in a shared recipe: the data without Director-only
text and without links to the campaign's own records (ids), plus what to pick
to restore each dropped link. It has no campaign. `waiting` is the markers the
sender wrote; the owner keeps one only where it would have made it itself, so a
marker is always the owner's word. A kind without `Share` is shared as it is,
which is right for kinds that hold only names, and may carry no markers.
`EventDef.Share` and `ActionDef.Share` (`func(args) (args, error)`) do the same
for a step's args, where there are no ids: they strip Director-only text or
refuse the step.

An owner's `Check` lets a link that is waiting to be chosen be empty, and only
that one: `homebrew.Waiting(ctx, pick)` is true while the part being added
from the Store is waiting for exactly that `pick`.

Names are lower-case words joined by `.` or `-`; a second registration of a
name is an error. A `ClientRun` action runs in the Director's browser through
a handler a system package registered there, and only when the Director
presses Run; the server validates and records it but never runs it.

Registered so far: part `tracker` and `clock` (data is a trackers `Shape`;
each is saved as a tracker kind the recipe keeps, or, with `{link: <name>}`,
uses a hand-made tracker kind the campaign already keeps on pages, so field
rules and card tests read the same count; see "Linked trackers" below),
event `tracker.reached` `{value, every?}` (matched against the move the tracker
made, either way; `every` repeats the value upward), actions `step` `{by}`, `set` `{to}` and `tick` (clocks),
all with previews and all run on the server; event `respite.logged`, pressed
from the drawer as "Log a respite" (`homebrew_rules.go`; also fired when the
Crafting app's Projects tab logs one); event `button.pressed` `{button}`,
"A drawer button is pressed", whose `PressArg` is `button`, so each name
the rules give is its own drawer button ("Dose" setting trackers to 0); the
name is required, single-spaced, at most 40 characters and matched without
regard to case (`homebrew_buttons.go`); part `ancestry` `{slug}`, a link to one of the campaign's
own ancestry entries (`system_entry_homebrew_adapters.go`), whose own
visibility decides who sees it. Creature variants
(`variants_homebrew_adapters.go`, over system state): parts `creature-recipe`
`{page}` and `creature-mark` `{recipe, addons, marked, variants}`, both forced
to the Director, which point at the campaign's game-system variant recipes and
never copy them; event `creature.dies` and client-run action `rise-as-variant`
on a mark, both with no args; `creature.dies` fires with `Scope` set to the
creature's page. Parts `field`, `item` and `words` from the field
rules (see `internal/plugins/fieldrules/.ai.md`). From the calendar
(`homebrew_calendar.go`): events `moon.changed` `{moon, state?}` and
`calendar.roll` `{event, result?}` (names, not ids, so a recipe moves between
campaigns; no state or result means any) and action `party.effect` `{name,
text?, who: party|tag, tag?, see: party|director, lasts:
until_change|duration, duration?}` (duration in days); none takes a part. From the layer store
(`transformations_homebrew_adapters.go`, while it is healthy): part
`transformation`, forced to the Director, holding a whole layer `{name,
source, note, changes}` checked as the store checks one, and client-run action
`put-on-transformation` on it, with no args, which the game system's sheet
answers by opening the scope page with the preset previewed. From card
decks (`decks_homebrew.go`, while the plugin is healthy): events `card.played`
and `card.drawn`, each with optional text fields `deck` and `card` (names,
compared without regard to case; empty means any), fired with `Scope` set to
the hero's page and no part; and actions `deck.add-copies`, `deck.take-out` (for good) and
`deck.shuffle-back`; part `deck` `{deckId, name}`, forced to the Director, which
points at one of the campaign's own decks and never copies it (its `Check`
refuses a deck of another campaign or none, and refreshes `name` from the deck
on every save; the deck's own rules decide who sees the deck); and action
`deck.draw` `{count}` on a `deck` part (1 to 5, 1 when absent), "draws {count}
from {part}", which deals that many cards from the deck to the hero in the
run's `Scope` and refuses with no scope. All deck actions are `Waits`, so a
rule that ends in one is held for a Director.
The catalog carries `waits` for such an action, and the Workshop's editor and
its preview say the rule waits however it is timed.
No rule plays a card for anyone. The ask step `ask-director`
`{ask?}` (`homebrew.AskDirector()`, registered from `internal/app/homebrew_ask.go`).
The roll step `roll-first` `{dice, characteristic?, target}`, "The player
rolls first" (`internal/app/homebrew_roll_first.go`, while the roll log is
healthy): `dice` in the roll log's own grammar (`rolls.CheckFormula`, stored
as the log writes it: "2d10"), `characteristic` one the game system's power
roll declares (matched by key or label, stored as its label; refused when the
system declares none), `target` 1 to 999.
The agreed names for other owners are in issue #1593.

## Sharing a recipe (the Store)

`package.go` is the Workshop's side of the Store kind `homebrew-recipe`; the
adapter is `internal/app/homebrew_store_kind.go`, registered on the designs
kind registry while the Workshop is healthy. A package is
`{name, doc: {parts, rules, layout}, needs: {partKinds, events, actions, system?}}`
in the Workshop's own shape. `needs` is derived from the recipe on every
call, never believed from the sender; `system` is the game system id, recorded
only when a client-run action is used.

- `Package(ctx, campaign, recipeID, viewer)`: a Director's copy of the recipe
  through `StripPackage`, in canonical form. The stored recipe is not touched.
- `StripPackage(raw)`: pure and idempotent, run on share and again on add. Each
  part's owner `Share` drops Director-only text and id links (each id link
  becomes an `unlinked` marker); fields a package doesn't have (`notes`, `off`,
  anything unknown) are dropped. A sender's own markers are input to the owner's
  `Share`, never kept as written, and a kind with no `Share` refuses one. A
  recipe has no notes field and no Director-only
  step text of its own: what is Director-only lives in an owner's part data, so
  only an owner's `Share` can strip it. Today: `field` (a Director-only field
  is refused, not shared), `item` and `words` (Director-only fields and words
  dropped; a words part's place becomes "a place page"), `crafting-recipes`
  (recipe ids dropped), `creature-recipe` and `creature-mark` (page ids
  dropped), `ancestry` (slug cleared, "an ancestry" to pick). A step's args go
  through the event's or action's `Share`: `party.effect` refuses an effect only
  the Director sees. A rule's When test stays as written: it is the condition
  the rule waits on, not hidden text, and dropping it would change what the
  rule does. A registered event or action that comes to hold an id needs an
  id-aware hook before it is shared.
- `ValidatePackage(raw)`: canonical form or an error naming the part. It has no
  campaign, so it holds the package to the Workshop's limits and references,
  refuses unknown fields, a second document, an oversized body and any part an
  owner's `Share` would still change, any marker its owner would not have made
  and any step whose `Share` would change its args. It does not run an owner's `Check`, which
  reads the campaign's own records; that happens on add. A kind, When or Then
  this server doesn't know passes here, for `PackageLacks` to name.
- `PackageLacks(ctx, campaign, raw)`: sentences for each kind, When or Then the
  campaign doesn't have, the game system a browser-run step needs, and, when
  nothing is missing, the first thing an owner refuses against this campaign.
- `AddPackaged(ctx, campaign, viewer, raw)`: Director team only. Strips and
  validates again, runs every owner's `Check` in this campaign (as a save does,
  except that the link a part is waiting on may be empty), and stores a new
  recipe with
  `off` set, markers kept. It answers `{id, leftToPoint}`, one sentence per
  marker ("Words: choose a place page."). A taken name gets " (2)" and on. No
  `Sync` runs; the first Workshop save that passes switches it on and syncs.

The adapter's `Validate`, `Lacks`, `Strip`, `Add` and `Package` pass straight
through to these; `Add` and `Package` take a user id and read the Director team
from the campaign (Owner, or granted the Director's view), so a player or
stranger is refused 403.

## Linked trackers

A tracker or clock part whose data has `link` keeps no kind of its own: its
`Check` (`internal/app/homebrew_adapters.go`) finds the hand-made kind of that
name (ignoring case; a clock part needs a clock, a tracker part anything
else; a kind another recipe keeps is refused) and stores the name as the
campaign spells it with a copy of its shape, refreshed on every save, which
only the Workshop's preview reads. The part's `see` is unused: the tracker's
own audience applies. `step`, `set` and `tick` on it write through the
trackers plugin's `LogKind`: on the event's page when that page has it (or
the kind goes on every page of its category), on every page that has it
when the event came from no page, and never placing it anywhere new. Any
move of that kind's trackers fires `tracker.reached` on every part linked to
it (`PartsOfKind`, which asks the store only for recipes whose document holds
a link, read by `internal/app/homebrew_rules.go`); those firings share one
budget of 50 runs (`ShareBudget`). A renamed or removed kind fails an action
on it with a line asking the Director to choose it again, and a When on it
simply stops firing; the Workshop's picker marks it "(not found)". The
recipe block shows only a recipe's own kinds, so a linked part is seen on
the pages its tracker is already on. The Workshop's inspector offers the link as "Keeps: Its own count / A
tracker on pages", listing the campaign's hand-made kinds from
`GET /campaigns/:id/tracker-kinds`.

## Who may do what

Every route is the Director's (`CanAuthorDmOnly`), checked in the service,
except a person's own asks (`/asks`, `/asks/mine`, `/asks/:run/take-back`),
which are for whoever set the ask off, and `/asks/:run/roll`, which is only
for the player a roll waits on, never a Director. Players never read a recipe; they meet
its parts through the widgets those parts place, which keep their own
audience rules, and an ask shows them only its own words and the answer.

## Asking the Director

`ask-director` is an ordinary Then any rule can drop in, with one optional
arg, `ask`: what the person wants to do, in the author's words ("draw a
card"; a leading "wants to" or "to" is dropped, at most `MaxAskChars`). When
a run reaches it the run stops there, held: the steps before it have run, the
steps after it wait. The run is a `homebrew_runs` row with status `held` and
`ask_at` set to the step (`Run.Asked`, counted from 1). `holds` reads only the
steps before the first ask, so a rule timed `now` whose earlier steps the
server can run does them at once and then asks; a rule held for another
reason asks once the Director presses Run and it reaches the ask (Run on an
asking run is a 409). The asker is the run's `created_by`: the person whose
change set the rule off (for a card event, the player who played or drew).

A Director answers (`Service.Answer`, `ask.go`):

- **Yes** runs the steps after the ask, as the answering Director. The answer
  may carry `steps: [{step, part?, args?}]`, changes to those steps' args and
  parts ("Yes, and…"). Each changed step goes through `checkStep`, the same
  check a saved recipe's Then gets (`validate.go`): the part must be the
  recipe's and of a kind the action lists, and the owner's `Check` judges the
  args. A refusal is a 422 with nothing run and the ask still waiting. So a
  new action's `Fields` and `PartKinds` are its conditions with no new code.
  The run keeps the rule as it ran (`rule_json` is rewritten), and the answer
  says what changed field by field ("Copies: 4 (was 2)").
- **No**, or **Other** with a written reply (required, at most
  `MaxReplyChars`), run nothing more: status `declined` or `replied`. Set
  aside on an ask is a No.

The answer is stored in `answer` (`{kind, reply?, changes?}`). A run moves
on from `held` once (the store's check on the old status), so two Directors
can't both answer and an answer after a take-back is a 409. A Yes whose later
steps reach another ask waits again there. The person who asked may take it
back while it waits (`TakeBack`: status `withdrawn`); nobody else may,
Directors included.

Telling people (`Option`s, each optional): `WithAskPeople` names the asker
and lists the Directors, `WithBell` rings `homebrew_ask` to the Directors
(not the asker), linking to the DM Screen; `homebrew_ask_waiting` to an
asker who isn't a Director when the ask starts ("Waiting for your Director:
draw a card"), since a rule raised it and they may not know it waits; and
`homebrew_ask_answered` to the asker ("Your Director said yes, with changes: draw a card", "said no",
"replied: …"; the changes and a note go in the detail), linking to
`/campaigns/:id/homebrew/asks`. `WithLive` publishes `homebrew.ask` when a run
starts asking and `homebrew.answered` when it is answered or taken back, each
`{id, state}` to the Directors and the asker (`internal/app/homebrew_ask.go`);
the Table's socket turns either into a `chronicle:homebrew-asks` window event,
and the drawer and the asks list read their own route again.

The asker's view (`AskView`) is their ask's words, `state` (`waiting`, `yes`,
`no`, `other`, `taken_back`), the reply and the changes; never the recipe,
the rule or its lines. `homebrew-asks` (`static/js/homebrew_asks.js`,
`static/css/asks.css`) draws it, on the "Your asks" page (`asks.templ`) and
anywhere else a person's own asks belong.

## The player rolls first

`roll-first` is an ordinary Then, so a rule may use it alone or after an ask,
where the Director's "Yes, and…" changes its dice, characteristic or target
through its `Fields` like any later step: a condition is just a later step.
When a run reaches it the run is held exactly as at an ask (`ask_at` is the
step), but it waits on a player, not a Director: `wait_for` (`Run.WaitFor`)
is the player who claimed the run's scope page (`Players.PlayerOf`,
`WithPlayers`, over the entities plugin), or else the person who set the
rule off. It is never in a Director's answer cards: the drawer shows it under
Waiting on you as `kind: "roll"` with `roll: {player, playerId, label,
formula, target, problem}`, not counted as needing them, with only Set aside.
Run and an answer on it are 409.

The player rolls on "Your asks" (`POST …/asks/:run/roll`, `Service.Roll`,
`roll.go`). The body is ignored: the step's owner makes the roll on the
server through the roll log's `Table`, as a public Table roll by that player
(labelled with the characteristic, or "House rule roll", never the recipe's
name, since the roll is public;
as their hero when the characteristic came from one), so it is in the log,
plays on everyone's Table and follows the log's audience rules. The
characteristic's number comes from the rule's scope page when the player
owns it (the hero who played the card), and from their first claimed hero
only when the rule has no hero of theirs in scope, read through the rolls
plugin's power roll source (`rollsPowerAdapter.PowerRollOn`) with GM-only
fields left out; a hero with no such number gets the owner's reason instead of a button. The
service claims the run first (held to running), so a second press is a 409;
a roll the log refuses (its rate limit) puts the run back to held. Then it
compares the total with the target: at or over it, the steps after run under
the Director's standing (as every owner's firing does, with the player named)
and the run ends as they end, or waits again at a later stop; under it, the
run ends `missed` with a line such as "Tam rolled 9 on Might (2d10+2), under
12: the rule stops here." The result is stored as `answer.roll`. Only the
player it waits on may roll; another player or a Director is a 403. The one
exception is a rule a Director set off from no claimed hero page: it waits on
that Director, who then rolls it. A Director may set it aside (`dismiss`: status `dismissed`).

Telling people: when the roll starts waiting, `homebrew.ask` with state
`roll` goes to the Directors and that player, and the bell rings
`homebrew_roll` to the player, linking to Your asks: that one bell, never
"Waiting for your Director" as well, since no Director is waited on. After a Yes that stops
at the asker's own roll, their answer bell says "Your Director said yes, if
you roll first: …" instead, and no second bell rings. After the roll,
`homebrew.answered` with state `rolled` or `missed` goes out and the
Directors (not the roller) get `homebrew_rolled` with the roll's line,
linking to the DM Screen. A roll set aside sends `homebrew.answered` with
`set_aside` and rings the player `homebrew_ask_answered`.

The player's view (`AskView`) of a roll step: `state` `roll` while it waits
(`roll: {label, formula, target}`, `canRoll` for the player it waits on,
`roll.problem` when they can't), then `rolled` or `missed` (`roll.total`,
`roll.made`), or `set_aside`; `answered` is the Director's earlier answer
("yes") and `changes` what they changed. The widget reads "Your Director
said: Yes, if you roll Might 12 or more first." with "Roll Might (2d10 + 2)",
then "Rolled 15. The rule carries on." or "Rolled 9, under 12. The rule stops
here.", and moves focus to that line. It never shows the steps after the
roll, which are the Director's rule.

The Foundry module's asks list (`GET /api/v1/…/homebrew/asks`) carries the
waiting rolls with `kind: "roll"`, so a GM card can show them. There is no
API route that rolls as a player: the module calls Chronicle on the GM's
key, and its player link (`foundry_players`) is the GM client's word for who
someone is, not a player's own sign-in, so a roll made there would be the
Director rolling for them.

## The campaign AI

`ai.go` is the Workshop's part of the AI engine (aiplug). The `workshop`
lookup (tool `homebrew_workshop`, owner's key only) writes each recipe as the
`workshop-recipe` block that sends it back, one JSON line per part and rule,
then the catalog with each event's and action's args (and, for a `PressArg`
event, that each distinct value is a drawer button), then the drawer's
buttons, named ones with their event and name, and waiting rules. A `workshop-recipe` block is matched by `name`
and goes to the owner's review like every request: `Plan` runs
`Service.Check` (every Create/Update check and each owner's `Sync.Check`,
without writing) and records the version it saw; `Apply` refuses if the
recipe changed in the Workshop since. An update's `parts` and `rules`
replace the stored lists whole; the layout is kept. Pressing a drawer button
or running a held rule stays the Director's act at the table, so the AI
reads the drawer but cannot ask for either. Safe privacy and players' keys
are refused, as the service would.

## The Workshop page

`GET /campaigns/:id/homebrew` renders `workshop.templ`, a mount for the
`homebrew-workshop` widget (`static/js/homebrew_workshop.js`, `static/css/workshop.css`).
The rulebook's More menu links to it for Directors. Left: the recipe list
and the palette (the catalog's parts, Whens and Thens). Middle: a pan and
zoom canvas of cards wired part → When → Then → part; cards are dragged to
arrange them and their places save as `layout`. Right: the inspector for the
selected card. Trackers and clocks have their own shape form; another kind's
`data` is shown as set up by its owner. A kind whose `Widget` is set is drawn
by its owner's widget: selecting the part lays it over the canvas
(`data-mode="canvas"`) and mounts it again in the inspector
(`data-mode="inspector"`). Both get `el._hbPart = {campaignId, part,
setData(data), setPrimary(label, run)}`; `setData` hands the part's data back
as an edit, and `setPrimary` lets the widget offer the page's main action
while it is open (Save recipe steps back to an ordinary button). The
Workshop loads the widget's scripts through the plugin widget list, so it
knows nothing of the owner. The page's guard is the service's
catalog call, so the page and the API keep out the same people.

Under the inspector, the **live preview** acts the open recipe out in the
page, saving nothing: each numbered part with its bar and band, step buttons,
a button for each When the preview can't start from a number, a Waiting list
for rules timed `held` or `encounter_end` with Run, and a short log. A run
lights the cards it went through; pointing at a preview line lights its card
and clicking selects it. Rules that keep setting each other off stop after 50
steps. **Try it** acts out the first rule. **Where it shows up** lists the
categories whose page layout places the recipe, read from
`GET …/recipes/:rid/placements` when a recipe is opened or saved.

## Placing a recipe

A saved recipe with a tracker or clock is offered in the Customizer's
widget list under **Homebrew**, one entry per recipe: the `homebrew_recipe`
block with `config.recipe_id` (`internal/app/homebrew_recipe_block.go`). On a
category's page layout it shows the recipe's tracker kinds (owner prefix
`homebrew:<recipe>:`) on every page of that category, through the Trackers
widget's owned view; each keeps the "who sees it" its part was given.
`Placements` reads the layouts through `PlacementFinder`, implemented in
`internal/app` over the entities plugin.

## Running rules

`Fire(ctx, campaign, viewer, Fired{Event, RecipeID, Part, Scope, Payload})`
starts every saved rule whose When the firing meets, only for a Director.
Its caller is the owner of the event: the trackers plugin tells
`internal/app/homebrew_rules.go` whenever a change moves a tracker, and that
fires `tracker.reached` for the recipe and part that own its kind, or for
every part linked to it.
A rule timed `now` whose every action has a server `Run` and none `Waits` runs
at once; one with another timing, a test, a `Waits` action, or a browser or
by-hand action is **held** in the drawer. Pressing Run runs a held rule's server
steps, a `Waits` one included, as the Director who pressed it. A run stops at its first failing action, with the owner's own
message (never a raw internal one). Rules that keep setting each other off
share one budget of 50 runs per change; the 51st records one `stopped` run.

Every run is a row of `homebrew_runs` (`run_repository.go`): what fired,
the rule as it was, the scope page, the status (`done`, `failed`,
`stopped`, `held`, `running`, `dismissed`, and for an ask `declined`,
`replied`, `withdrawn`, and for a roll `missed`), its lines, and for a run
that stopped at an ask or a roll the step, the answer and the roll, and who
a roll waits on. A held run is run
or set aside only once: the store moves it from `held` with a check on the
old status, so two Directors pressing Run can't both run it. The newest 200
finished runs per campaign are kept. Held ones are never pruned, so they are
bounded where they are made: a campaign holds at most 200, and past that a rule
that would be held is dropped with a log line (rules that run at once still
run). A firing marked `Once` (an event a player can set off at will, such as a
card being played) does not hold a rule again while the same rule already waits
for the same scope and payload.

## The drawer

The DM Screen's tankard icon opens the **Homebrew drawer** as a card for the owner
and co-DMs (`internal/app/homebrew_drawer.go` hands the screen
`DrawerMount`, so neither plugin names the other). The `homebrew-drawer`
widget (`static/js/homebrew_drawer.js`, `static/css/drawer.css`) reads
`GET …/drawer` and draws, in order: **Set off** (the press buttons, with how
many rules each starts: the registered presses, then a button for each name
the saved rules give a `PressArg` event, each the same control as "Log a
respite"), **Waiting on you** (held runs with Run and Set
aside; a run waiting at an ask is the answer card instead, first asked first:
"Mira wants to draw a card", Yes, No and Other…; after Yes, "Yes, and…" lists
each later step's part and text fields as rows, whole-number fields behind
"+ Change how many", and Send says what will happen; Other opens the reply;
a refused change stays on the card with the owner's words), **What just changed** (the last 20 runs and their lines) and
**Trackers**, each page that has one with the Trackers widget itself, from
the trackers plugin's `/trackers/pages` (with none, a link opens the shared
"Put on a page" chooser for the Trackers block, `put_on_page.js`). After the server runs a held rule,
its browser steps run through `Chronicle.homebrewActions[action]`, a
function the action's owner adds in the browser that gets `{campaignId,
run, step}` and may return a line or a promise; a waiting `run` carries its
`recipeId` and `scope` (the page the event happened on), so the function can
read its part and act on that page; a step nothing added is
named for the Director to do. The screen's "Player view" button sets
`data-player-view` on the drawer, which hides the Director's sections,
every control and every tracker players can't see.

| Method | Path | |
|--------|------|---|
| GET | `/campaigns/:id/homebrew` | the Workshop page |
| GET | `/campaigns/:id/homebrew/catalog` | registered parts, events and actions, sorted |
| GET, POST | `/campaigns/:id/homebrew/recipes` | list (`{data, total}`), create |

| POST | `/campaigns/:id/homebrew/press/:event` | fires a press event; `?button=<name>` for a named button, 404 for a name no saved rule uses; answers the drawer |
| POST | `/campaigns/:id/homebrew/runs/:run/run` | runs a held rule; answers the run, 409 if already handled |
| POST | `/campaigns/:id/homebrew/runs/:run/dismiss` | sets a held rule aside (an ask: answers no); 409 if already handled |
| POST | `/campaigns/:id/homebrew/runs/:run/answer` | answers an ask: `{answer: yes\|no\|other, reply?, steps?: [{step, part?, args?}]}`; 422 for a refused change, 409 if already answered |
| GET | `/campaigns/:id/homebrew/asks` | "Your asks": the viewer's own asks (any member) |
| GET | `/campaigns/:id/homebrew/asks/mine` | the viewer's own asks, `{data, total}` of `AskView` |

| POST | `/campaigns/:id/homebrew/asks/:run/roll` | the player a roll waits on makes it; the server rolls and judges; answers their `AskView`; 403 for anyone else, 409 if already rolled or set aside |
| GET | `/api/v1/campaigns/:id/homebrew/asks` | the waiting asks, and the rolls waiting on players (`kind: "roll"`), for the Foundry module (owner or co-DM key or session; `syncapi/homebrew_ask_api_handler.go`) |
| POST | `/api/v1/campaigns/:id/homebrew/asks/:runID/answer` | the same answer from the Foundry module |
