# Maps Plugin

## Purpose

Provides interactive map support for campaigns. Each campaign can have multiple
maps (world, region, city, dungeon) with background images displayed via
Leaflet.js. Maps contain positioned pin markers that optionally link to
entities. A drawing subsystem adds vector drawings, tokens, layers, and fog
of war.

## Tier

**Plugin** -- feature app with handler, drawing handler, service, drawing
service, repository, drawing repository, models, and Templ templates.

## Data Model

### Map
- `id` (UUID), `campaign_id`, `name`, `description`, `image_id` (media FK),
  `image_width`, `image_height`, `sort_order`, timestamps.

### Marker
- `id` (UUID), `map_id` (FK), `name`, `description`, `x`/`y` (percentage 0-100),
  `icon` (FontAwesome class), `color` (hex), `pin_category` (nullable: location,
  danger, treasure, quest, note), `entity_id` (optional FK),
  `visibility` (`everyone` or `dm_only`), `visibility_rules` (JSON per-user
  overrides), `created_by`, timestamps.
- Joined fields: `entity_name`, `entity_icon` from LEFT JOIN on entities.
- `pin_category` maps to Foundry VTT pin types for sync (migration 003). The
  service accepts only the five values above or null; on update only a value
  the caller sent is checked, so a legacy stored value never blocks an edit.
- `foundry_id` for stable Foundry VTT ID mapping (migration 004), matching
  the pattern used by drawings and tokens — it is core sync data (per-row
  identity for Foundry mapping). Foundry connection presence itself is
  reported by the campaigns plugin's `GET /campaigns/:id/foundry-presence`,
  not by anything in this plugin.

### Drawing
- Types: `freehand`, `rectangle`, `ellipse`, `polygon`, `text`, `shadow`, `image`,
  `arrow`, `highlight`, `step`, `callout`. `drawing_type` is a VARCHAR checked
  against `validDrawingTypes` in Go, so a new type needs no migration.
- Annotations (see `drawing_annotation.go`), all with hex colours only, rotation 0
  and points on the map (0-100):
  - `arrow`: points `[tail, tip]`, distinct; `stroke_width` up to 60. The viewer
    sizes the head from the width in screen pixels, so it stays readable at any zoom.
  - `highlight`: a freehand stroke of at least two points; `stroke_width` up to 60,
    `fill_alpha` its opacity (0.1-0.7, unset becomes 0.35). Drawn in its own pane
    (z-index 395, `mix-blend-mode: multiply`) so the map shows through.
  - `step`: one point; `text_content` is the number, 1-999, stored as plain
    digits. The viewer numbers a new step from the highest step it can see, plus
    one, so deleting one never renumbers the rest. Numbers are not unique: steps
    placed at the same moment by two people can share a number, and so can a step
    hidden from a scribe and one they place.
  - `callout`: one point, where the tail points; `text_content` trimmed, 1-500
    characters, no control characters other than line breaks and tabs. Drawn with
    `textContent` inside a bubble laid out from the measured, wrapped text.
  - `step` and `callout` take an optional `font_size` of 8-48; `arrow` and
    `highlight` refuse text and `font_size`.
  - `text` labels share the 500-character bound whenever their text is written; a
    longer stored label keeps working until its text is edited.
  - Labels and bubbles are written in an in-map editor and changed by double-click;
    right-click deletes after an in-map confirm. On import (`Imported`), a label's
    text is cleaned to the bound (line endings normalised, cut to 500) instead of
    refused, so older exports still restore. Everything else (visibility,
    visibility rules, layers, the draw gate, edit-own and delete-own for scribes, shadow and
    hex-fog hiding, WebSocket audience, export/import, the sync API) is shared with
    the other drawing types. Like other vector drawings they have no select-and-drag;
    Undo removes the last one drawn in this page session.
  - The Foundry module's map overlay draws only the types it knows and skips any
    other `drawing_type` (it returns nothing for it), so it does not show the four
    annotations; nothing else changes for it.
- `image` (see `drawing_image.go`): a picture from the campaign's media placed on the
  map. Exactly two opposite corners in percentages, `rotation`, `fill_alpha` as
  opacity (clamped 0.2-1.0; unset means 1), `image_id` (a media image of the map's
  own campaign, checked through the injected `MediaVerifier` on create and whenever
  it changes), `crop` (`{t,r,b,l}` percent trimmed per side, each 0-45, null clears)
  and `sort_order` (stacking among pictures). `visibility = dm_only` hides it from
  players through the same list, by-id, sync and WebSocket filtering as any
  drawing, and a picture wholly under a shadow is withheld by the shadow rule.
  A picture whose box overlaps a shadow keeps its drawing but loses its file for
  everyone the shadow hides things from (`shadowWithholdsImageOf`, alongside the
  fog rule below). A turned picture is placed exactly: it turns about its centre
  in map pixels (the map's recorded image size, 1000 by 1000 when none is
  recorded, as the viewer draws it), and only a turned picture that actually
  covers part of a shadow is withheld. If the map's size cannot be read, every
  turned picture on a map with a shadow is withheld.
  Other types reject `image_id` and `crop`. The viewer draws pictures in a Leaflet
  pane at z-index 380, below staff shadows (390) and the vector pane (400). The
  Foundry module ignores unknown drawing types, so it does not show pictures. The drawing endpoints
  add `image_url` to each picture they return: a signed media URL minted for the
  requesting viewer (ADR-058), only on drawings that viewer may receive, so hidden
  pictures never get one. Without it an anonymous visitor of a public campaign, or a
  file also used by a hidden page, would get a 404. Signed URLs expire (about an
  hour), so the viewer re-fetches the one drawing for a fresh `image_url` the first
  time an image fails to load. Rotation is limited to -45..45, and `crop` is stored
  re-serialised as only t, r, b, l. Changing and deleting follow the drawing rule (owners
  and DM access any picture, a scribe the ones they added), and the viewer offers
  selection, editing and Delete (bar and key) on exactly those. The media file itself is served
  by the media plugin; with no entity referencing it, access without a signature falls
  to campaign membership (ADR-058 decision 3).
- `shadow` (see `shadow.go`): two opposite corners in percentages; `fill_alpha` is
  its strength (0.5 "A hint", 0.85 "Almost nothing", anything else becomes 0.5).
  The server withholds pins and drawings lying under a shadow from every viewer
  who is not owner/DM-equivalent (a co-DM grant counts, via the promoted
  visibility role), scribes included: `MapService.ListMarkers`,
  `DrawingService.ListDrawings`, the by-id reads, and the WebSocket publisher
  (restricted to DM-equivalent clients). Creating, updating or deleting a shadow
  is owner/DM-equivalent only (`requireShadowAuthor`, from the `isDM` /
  `CallerIsDM` argument, which handlers fill from `CanAuthorDmOnly`); a scribe
  still draws everything else under the "who can draw" gate, and the "Hide under
  shadow" tool is rendered only for DMs. Shadows themselves are sent. Everyone
  hidden sees one smoke layer per strength masked by the union of the rectangles;
  DMs see a faint per-area version (`static/js/map_shadow.js`). Known gap: the
  Foundry module writes a player copy of pins into world page flags, filtered only
  by dm_only and per-user rules, so pins under a shadow currently reach Foundry
  players. It is tracked privately until fixed.
- **The picture under a shadow is not sent.** `MapService.ForViewer` (and
  `ForViewerList`) is the one place a map reaches a user: for a hidden viewer
  and a map with a shadow it clears `image_id` and sets `image_url` to the
  player-image route (versioned by the cache key, so it changes with the
  shadows). The map page, viewer fragment, entity-page preview, map list,
  `/meta` and the sync API map endpoints all pass through it, and templates build
  picture addresses only with `mapImageSrc`. `PlayerImage` renders the copy in Go
  (`renderPlayerImage`: scaled to at most 4096 px on the long side, so it can be
  lower resolution than the original; strong blur, "A hint" kept at 45% brightness,
  "Almost nothing" at 5%, feathered edges; opaque JPEG), caches it on disk keyed by
  a hash of (picture, map, sorted shadow boxes and strengths) in
  `map-player-images/` next to the media root (not inside it: the media orphan
  sweep deletes unknown files there), and drops a map's older copies when a new one
  is written. An unwritable cache still serves the copy. Any failure is an error,
  never the original. The media plugin refuses the original and its thumbnails
  through `media.MapImageGuard`, implemented by `MapService.IsShadowedMapImage`
  (see the media `.ai.md`). Not covered: the Foundry module syncs with the owner
  key and receives the original.
- Percentage-based coordinates for resolution independence.
- Stroke/fill styling, rotation, layer assignment, DM-only visibility.
- Optional `foundry_id` for Foundry VTT sync integration.

### Token
- Represents characters/NPCs/objects on the map.
- Position (`x`/`y`), size (`width`/`height`), rotation, scale.
- Combat support: `bar1_value/max`, `bar2_value/max` (HP bars).
- Visual effects: `aura_radius/color`, `light_radius/dim_radius/color`.
- Game mechanics: `vision_enabled/range`, `elevation`, `status_effects` (JSON).
- Optional `entity_id` link and `foundry_id` for sync.

### Hex layer
- Turned on by `display_settings` `grid.type = hex`; `grid.size` is measured as if the hex area were 1000 wide. Over the whole map, hex (0, 0) is centred on the map's top-left corner, the same place the plain grid starts. Pointy-top hexes, odd rows shifted right ("odd-r" offset), in `hex.go` and `map_hexes.js` alike; both are checked against the same golden vectors.
- `map_hex_layers`: one row per map, created by the first write. `version` is bumped on every write (the ETag and, later, the live cursor). `anchor_drawing_id`, `fog_enabled`, `party_col/row`, `miles_per_hex` and `miles_per_day` are the layer's anchor, fog switch, party position and travel figures. `map_hex_cells`: sparse rows keyed by (map, col, row) with `terrain`, `piece`, `name`, `notes`, `explored`, `updated_by`. Both tables come from migration 009.
- Pinned to a picture: `map_hex_layers.anchor_drawing_id` names an `image` drawing on the same map (null: the whole map). The field is laid inside the picture's box: hex (0, 0) is the first whole hex at the top-left and the field stops before a hex would cross the right or bottom edge. Because `grid.size` counts as if the picture were 1000 wide, resizing the picture scales the hexes with identical columns, rows and keys. `NewAnchoredHexGeometry` (Go) and `anchoredGeometry`/`layoutFor` (JS) agree on golden vectors. The JS builds the field once in a box 1000 wide and carries it to the picture with one group transform, so moving or resizing a picture only changes that transform; the picture module reports live corners through `onChange('geo')`, which the drawing module republishes as `ctx.pictures` (`ready`, `get`, `list`, `subscribe`, `straighten`). The registry lives in the drawing module so hexes survive "hide drawings".
- Setting the anchor: `PUT /maps/:mid/hexes/layer` with `{"anchor_drawing_id": id | null}`, partial (absent keeps; a body naming nothing is refused). Only an owner or DM grant (`HexActor.IsDM`) may; the route needs membership only. The drawing must exist, be on this map and be an image; a missing id, another map's picture and a non-image get the same 400, so the answer cannot probe other maps. Anchoring turns the picture upright (rotation 0, through the drawing service so other viewers hear of it, and only after the anchor is stored), because hexes do not turn; the write carries the picture's `updated_at` so a concurrent edit is a 409. Every write bumps `version`.
- Reading the anchor (`hexService.anchorState`): the layer reads as hidden (`hidden: true`, `DefaultHexLayer` plus the real version only: no anchor, fog, party, miles or cells; the client draws no hexes and keeps the plain grid away too) for anyone who cannot see dm_only (players, scribes, the public) when the anchor picture is `dm_only`, is wholly under a shadow (`HexPictures.IsShadowed`, the drawing service's own check; a failed check fails the read), or is set but unusable (deleted, on another map, no longer an image: the column has no foreign key, and the picture may have been dm_only before it vanished). Owners and DM grants instead get the whole-map fallback so they can see and fix it. Only an explicit PUT with `anchor_drawing_id: null` shows the cells to players again; a read never rewrites the stored anchor. With no picture lookup wired, a read of an anchored layer fails rather than guessing.
- Controls: owners get a "Make a hex map" rail button while the grid is not hex (flyout menu rows: "Whole map" and one "Picture n" row per picture; pictures have no name, so they are numbered in stacking order). The picture bar offers "Turn into a hex map" to owner or DM access (a DM only on a map whose grid is already hex, because turning the grid on is the owner's), and for the anchored picture shows "This picture is a hex map…", "Open hexes" and, for the owner, "Take the hexes off" (anchor null and grid off; painted hexes stay stored); Turn and Crop are hidden for it. The Hexes panel ends with "Take the hexes off" for the owner, on any hex map; it and the picture bar's button both confirm first. Map settings > Grid shows "Hexes cover" chips under Hexes; the choice previews live and saves with the sheet. Every path that changes the cover or grid size over painted hexes first asks: "Painted hexes stay where they are in the grid, so they may land on different spots. Continue?"
- Terrain is allowlisted in Go (`IsValidTerrain`): plains, forest, hills, mountain, water, swamp, desert, snow, town, road. Names are capped at 120 runes, notes at 2000, both plain text escaped on output. Positions are 0..399 per axis, a batch is at most 500 entries, a map at most 40000 stored cells (a write counts only hexes not already stored, and a hex whose fields are all cleared is deleted, so a full map can always be trimmed). An entry that names no field is refused. The viewer clamps its field to 400 hexes per axis (`MAX_HEX_AXIS`, one more than `MaxHexCoord`).
- Who can read names and notes: everyone who can view the map, minus unexplored hexes when fog is on (see `VisibleCells`). Notes are not private; the writer's card says so.
- `VisibleCells(layer, cells, role)` is the one filter. Fog off: everyone gets every row. Fog on: whoever passes `CanSeeDmOnly` on the visibility role (owner, DM grant) gets every row; everyone else, scribes included, gets explored rows only and nothing that hints at the rest.
- `GET /maps/:mid/hexes` returns `{layer, cells, version, hidden, art}` for anyone who can view the map (public campaigns included); `art` is left out while the layer reads as hidden. `PATCH /maps/:mid/hexes/cells` takes `{cells: [{col, row, terrain?, piece?, name?, notes?}]}` and is partial per entry: an absent field keeps the stored value, an explicit `null` clears it, a value replaces it. The merge is one `INSERT ... ON DUPLICATE KEY UPDATE` per entry, so a paint stroke cannot disturb a name. Who may write is decided in `HexService`, not by route middleware (the route only needs membership, so a DM-granted player reaches the service): an owner or DM grant writes any hex; a scribe only where the map's draw policy lets scribes draw and, with fog on, only on explored hexes; a batch with any refused entry is refused whole; players are refused. A non-DM is also refused (403) while the layer reads as hidden to them (the rules above), so a scribe cannot write to hexes they cannot see. The map must belong to the campaign in the path (404 otherwise).
- Pieces: `piece` is 0..11 (`HexPiecesPerTerrain`, `PieceCount`) for a terrain with pieces, null for Mix (the viewer picks a stable piece from the hex's position). A piece that does not fit the hex's terrain after the write is refused (400); a terrain change that leaves the stored piece out of range clears it. Roads and cleared hexes have no pieces.
- Terrain art: display_settings `hexes.art` is `real` (Realistic), `detailed` (the default, not stored) or `simple`, one per map, and everyone sees that one. The owner sets it in Map settings > Hexes ("Terrain art"); the owner and DM-access members also get Art chips in Paint. Both save through `PUT .../hexes/layer` with `{"art": ...}` (null means Detailed): `HexService` validates it, writes it with the wired `mapService.SetHexArt` and bumps the layer version, so every open map redraws in the new style.
- The viewer draws Simple as one path per terrain kind (flat colour plus a repeating icon pattern). Detailed and Realistic are tiles from `map_hex_art.js` drawn onto one canvas at the bottom of the `mpHexes` pane, so the hatch, party, trip line and hover in the SVG stay on top. Only hexes in view (plus how far their art reaches) are drawn; the canvas is redrawn when a pan or zoom ends, not every frame; tiles are cached per terrain, piece (and, in Realistic, which lower edges show) and zoom step, in a cache capped by count and pixels. Realistic tiles are costly, so they stop growing at 64 px of hex radius, a flat colour or a nearby size stands in until they are ready, and nothing in the art runs long enough to hold the page: tile painting is cut into slices by the clock (about 20 ms, `JobQueue`), a Realistic model is built a few rows at a time (`iso3ModelJob`) and finished tiles are stamped onto the canvas in slices too, in a spare canvas that replaces the visible one only when whole (painted in place the first time, so art appears as it is drawn). Finished tiles are shown at most every few redraw-costs, so redraws stay a small share of the time. In Realistic, Paint shows the brush terrain's pieces in folders (Mix, then one folder per group, as in the design). The art uses only the cells this viewer was sent, so it cannot show fogged land. The viewer gives only the hexes that are changing right now their own elements, to cross-fade the old art into the new (no easing under `prefers-reduced-motion`). A drag paints along the line between pointer samples and sends one PATCH for the whole stroke, debounced. While the hex module runs it draws the hex lines and the viewer skips its plain hex grid (`onHexLines`).
- The Hexes tool (key H) is on the rail only while the grid type is hex; players get a rail holding Move and Hexes so they can open a hex's card. Look opens the name and notes card (editable where the viewer may write, read-only otherwise); Paint is offered exactly where the server lets the viewer write (`MapViewData.CanPaintHexes`, rendered as `data-can-paint-hexes`): an owner or DM grant always, a scribe only when the map's draw policy lets scribes draw, a player never. This is not the drawing gate: a DM-granted player paints hexes without being a scribe.

### Fog of war and the party
- `map_hex_layers.fog_enabled` is the layer's fog switch (`PUT .../hexes/layer`, partial, owner or DM grant; the Map settings sheet's "Fog of war" checkbox stages it and saves with the sheet). With fog off nothing below applies.
- One definition of "unexplored": `FogMask` (`hex_fog.go`), built by `hexService.FogMask` whenever fog is on and the map has a picture size, whatever the grid type, so switching the grid away from hexes does not lift the fog (nil means nothing is fogged). It carries the field geometry at the layer version and the explored set. Everything that hides data from a viewer below `CanSeeDmOnly` (`fogHidingApplies`, the negation of `VisibleCells`' own line) applies it: lists of cells, the party position, pins, drawings, live events and the map picture. Lookups fail closed: no fog lookup wired, or one that errors, hides rather than shows. A point outside the field is not hidden; a pin or drawing is hidden when it lies wholly in unexplored hexes (a drawing that merely touches explored land stays; an unparseable one is hidden). `PointInUnexplored` is the pure check, tested in `hex_fog_test.go`.
- Cells: `GET .../hexes` sends explored rows only to anyone below `CanSeeDmOnly`; the DM gets every row with its `explored` flag. The party position (`party_col/row`) is withheld from them while it sits on an unexplored hex (`VisiblePartyLayer`).
- Pins: `ListMarkers` and `IsMarkerShadowed` drop pins under unexplored hexes, so list, by-id and websocket paths agree. Drawings: `ListDrawings`, `IsDrawingShadowed` and the drawing events do the same; shadows pass (players need them to draw the smoke). Tokens: `ListTokens`, `IsTokenHidden` (by id) and the token and drag events do the same, by the token's point.
- Writes: a caller who cannot author DM-only content who updates or deletes a pin, drawing or token hidden from them (shadow or fog) gets the same NotFound as for a missing id, and nothing is written.
- Reveal and hide: `POST .../hexes/fog`, owner or DM grant only (`requireFogWriter`), at most 500 hexes (`MaxFogBatch`); a reveal counts against the 40000-cell cap; the hex card's "Explored" checkbox sends a one-hex batch. The Fog panel's "Cover everything again" sends `{"reset": true}` after a confirm.
- The party: `PUT .../hexes/party` with `{col,row}`. Who may move it is display_settings `hexes.party_who`: `owners` (an owner or DM grant) or `scribes` (also scribes; the default and not stored). "Everyone" is not offered. The server computes the path (`HexLine`, the same line the viewer walks), reveals radius 1 around every path hex in one transaction (`RevealZone`, clipped to the field) and returns the path. The first placement reveals radius 1 around that hex. A scribe may only move onto an explored hex or a neighbour of one (`OnExploredFrontier`), and, with fog on, only while the party stands on an explored hex (the path starts there); a DM may go anywhere. The move is optimistic (`expectedFrom`) and retried up to three times on a conflict.
- Live updates: every hex write publishes `hex.changed` with `{map_id, version, party_path?}` and never a cell, name or note. It goes to the whole campaign (the version tells a viewer who cannot see the layer nothing); `party_path` is included only when the path is safe for every recipient (not while the anchor picture is hidden). Paint batches publish once. The viewer opens `/ws?campaign=<id>` for every map (also used for `map.items.changed`), ignores an event that is not newer than what it last read or that echoes its own write, and refetches the filtered GET; edits still unsaved wait for their save first. The event never replaces the read, so audience rules live in one place.
- The map picture: for a whole-map layer with fog on, a viewer below `CanSeeDmOnly` is served the player copy (`player_image_service.go`), which smudges unexplored hexes into the pixels (`smudgeFog` in `shadow_render.go`; the soft edge only spills into explored land). The copy's cache key includes the layer version and geometry, so any layer write (paint too) renders a fresh copy; the viewer asks for `/player-image?v=<version>` after each event. `MapImageGuard` (`map_picture_status.go`) treats a fogged whole-map layer as shadowed, so the original file is not served to those viewers.
- Picture files: the fog withholds the file of the picture a layer is pinned to (a pinned layer leaves the map's own picture alone) and of every picture whose box (turned, if rotated) overlaps an unexplored hex (`FogMask.WithholdsImageOf`). Its `image_id` and signed `image_url` are cleared for those viewers on list and by-id reads (`DrawingService.WithholdImages`, also on the sync API), and it draws as a grey placeholder; its events reach staff only. The media server refuses the file itself to them (`MapImageGuard` via `DrawingService.WithholdsPictureFile`), and the sync media API mints no link for it below owner. Pictures overlapping a shadow go through the same three paths. Fog, hex hide/reset and picture writes drop the guard's cached answers.
- The viewer (`map_hexes.js`): players get the unexplored hexes in the same smoke layer as shadows through one union mask (`ChronicleMapShadow.setHexFog`; overlaps never darken; the smoke still rests after 30 s idle, in a hidden tab and under reduced motion); the DM sees them faintly hatched. The shadow module's `attach` is a per-map singleton shared with the drawing tools. The party token walks the returned path with easing (170 ms a hex; no animation under reduced motion), and land leaves the fog as the token reaches it. A player who clicks an unexplored hex sees "Unexplored / The party hasn’t been here yet."
- Trips: "Plan a trip" is a Hexes mode for everyone who can see the layer, players included. A click sets the destination and a click on the party's own hex clears it; the viewer draws the straight hex line from the party (`hexLine`, amber outlines at fill-opacity .12 and a dashed polyline through the centres, easing in unless the viewer prefers reduced motion) and reads out "N hexes · M miles", "About D days on foot" (rounded to halves, at least half a day) and the top three terrain kinds along the path, start hex excluded. The plan is private and client-only: the destination lives in `localStorage` under `chronicle.maptrip.<user>.<map>` and is never sent to the server. It is built from the filtered read only: for a viewer below `CanSeeDmOnly` with fog on, a hex they were not sent reads as "unexplored land" and its cell is never consulted; with no party position they get no hex to click. Travel figures: `map_hex_layers.miles_per_hex` (default 6) and `miles_per_day` (default 24) come back from `GET .../hexes` to everyone (not secret; withheld only with the whole hidden layer). An owner or DM grant sets them through `PUT .../hexes/layer` from the trip panel (saved after a pause, one field per request) and from Map settings > Hexes > Travel (staged, saved with the sheet). `UpdateLayer` refuses a figure outside 1..1000 before writing anything, and null restores the default; a body naming only fog or the anchor leaves the figures alone. The pure helpers (`tripPath`, `travelDays`, `tripTerrain`, `tripSummary`, `parseTrip`) are exported for `test/js/map_hexes.test.mjs`.
- Known gaps: a line, shape or text drawing that touches explored land is sent whole, including the part over unexplored hexes (the same rule as shadows); the hex layer version on `hex.changed` tells players that the DM wrote something, not what.

## Key Functions

- `MapService.CreateMarker`: validates name, coordinates (0-100 range), icon
  pattern (`^fa-[a-z0-9-]+$`), and color pattern (`^#[0-9a-fA-F]{3,6}$`).
  Sets defaults: icon `fa-map-pin`, color `#3b82f6`, visibility `everyone`.
- `MapService.CreateMarker`/`UpdateMarker` also validate `pin_category`
  (`validatePinCategory`).
- `MapService.ListMarkers`: filters by role (role >= 3 sees dm_only markers).
- `MapService.SearchMaps`: name-based search returning results formatted for
  the quick search system (id, name, type_name, type_icon, url).
- `DrawingService.ListDrawings/ListTokens`: role-based visibility filtering.
- `DrawingService.UpdateTokenPosition`: optimized position-only update for
  real-time drag sync.

## Security

- **IDOR protection**: `requireMapInCampaign`, `requireMarkerInCampaign`, and
  `requireMapOwnership` verify ownership before every operation.
- **XSS prevention**: marker `icon` and `color` validated against regex patterns
  since they render into HTML attributes and CSS.
- **Who can draw**: `DrawingService.requireDrawAccess` enforces the map's
  `draw.who` setting (owners / owners and scribes, default scribes) on drawing
  create and update for every entry (web, sync API, import), from an explicit
  role argument. It fails closed on a role below Scribe and on a settings
  lookup error. Tokens and fog are not gated by it yet.
- **Who can delete**: marker and drawing DELETE routes admit Scribe+; the
  service (`canDeleteOwn`) lets an Owner delete any item and a Scribe only an
  item whose `created_by` is them. A missing creator is owner-only (fail
  closed), a role below Scribe never deletes, and a dm_only item the caller
  cannot see answers NotFound. A DM-access grant does not make someone an Owner
  here. The sync API forwards the key owner's user id and resolved role.
- **Addon gating**: all map routes require the `maps` addon via middleware.
- **Visibility**: dm_only markers/drawings/tokens hidden from non-Owner roles.

## Notable Design Decisions

- **Live pins, drawings and shadows.** Every pin, drawing (including shadow and
  picture drawings) write goes through the `mapEventPublisherAdapter`
  in `internal/app/routes.go`, which sends `map.items.changed` with
  `{map_id, kind}` (`markers`, `drawings` or `shadows`; tokens never announce, since the web viewer has no token layer and a notice per hidden drag would leak movement) just before
  the per-item event, from the web handlers and the sync API alike. It carries
  no content. Creating or deleting a DM-only or rule-restricted pin or drawing
  gets that item's audience; updates and shadows go to every client of the
  campaign, like `hex.changed`, so a player's page learns only that something
  changed and then refetches through `GET /maps/:mid/markers` and
  `GET /maps/:mid/drawings`, which already apply the DM-only, shadow and
  hex-fog rules for that viewer. The per-item events stay audience-gated for
  Foundry. The viewer (`map_live.js`) debounces for 300 ms and redraws only the
  affected layer; a failed or malformed refetch leaves the screen as it is. A
  pin being edited or dragged is left alone until the edit ends, and the
  drawing layer is not rebuilt while a tool is active or a picture is selected.
  `shadows` refetches drawings and pins, because a shadow hides and uncovers pins.
- **Map page layout.** `MapEditorBody` renders one wrapper (`#map-wrap`) with
  the Leaflet container beneath and `mapControls` floating over it, each
  control in its own corner (search + Scribe+ tool rail top-left, Pins &
  layers top-right, zoom/fit/full screen bottom-right, tool hint bottom-centre).
  They are siblings of the Leaflet container, not Leaflet controls, so the map
  never sees their clicks; Leaflet's own zoom control is off. Keys: V move, M measure, H hexes (when the grid is hex),
  P pin, D draw, B hide under shadow, Esc closes the nearest popover/card, then stops the tool.
  The rail shows for everyone: players get Move and Measure (and Hexes on a hex map).
  The dedicated page (`mapShowContent`) and the focus view's fragment
  (`MapViewerFragment`) put the wrapper inside the map's resolved frame.
- **Viewer is a static widget, not an inline script.** `MapEditorBody` emits
  markup plus `#map-config` (the server's role-filtered data and the urls of
  the libraries); `static/js/map_viewer.js` starts from it. This keeps the same
  markup usable as a fetched fragment (innerHTML does not run scripts) and
  keeps page `<script src>` tags out of a swapped region. Only one viewer may
  exist per page (fixed ids); `ChronicleMapViewer.destroy` tears a mount down
  (Leaflet, document listeners, `window.chronicleMap`) so the focus view can
  open and close repeatedly.
- **Map on a page: preview, then unfold.** The entity-page block
  (`BlockEntityMapEmbed`) is a picture of the map in its resolved frame (small
  form), not a live map: it carries no marker data and no Leaflet. Clicking
  (or Enter/Space) calls `ChronicleMapFocus.open` from an inline handler, so it
  works after an HTMX swap of the block. The focus view fetches
  `/maps/:mid/viewer`, mounts the real viewer in it and shows a bar with the map
  name, "Open map page" and Close. Esc, the backdrop and Close dismiss it; an
  Esc the viewer used to leave a tool or close a panel (`event.mpConsumed`)
  does not also close the view. The unfold is a one-shot FLIP animation
  (about 620ms, sideways then downward, creases fading); under
  `prefers-reduced-motion` it is a 150ms fade. Nothing loops. A save in the
  viewer that the map page answers with a reload refreshes the unfolded map
  instead (`opts.onReload`).
- **Pin cards.** A click shows a read card; Scribe+ edits from it. A new pin
  (Pin tool or double-click) opens a quick card (name, kind, who can see it)
  with a "More options" link to the full marker modal. The quick card sends
  only the fields the person changed (partial-update contract). "Who can see
  it" is offered only to callers who can author dm_only content.
- **Layers panel is client-side.** Kind, drawings and hidden-pin toggles never
  touch the server; role gating of what a player receives stays server-side.
- `static/js/map_drawing_tools.js` has no UI of its own: it renders saved
  drawings for everyone (so players see them) and, for Scribe+, exposes
  `window.chronicleMap.draw` (start/cancel/setStyle/undo/setVisible) that the
  tool rail drives. Undo only walks drawings created in the current page
  session, so a scribe's undo removes their own drawings; a 403 from the server
  (not their drawing) is reported instead of removing the shape. Pin Remove
  buttons show for a scribe only on pins whose `created_by` is the page's
  user id.

- Marker coordinates are percentages (0-100) not pixels, so maps work at any
  image resolution. Leaflet CRS.Simple converts to pixel space at render time.
- The drawing subsystem uses a separate `DrawingService` and `DrawingHandler`
  from the original map/marker code.
- Token position has a dedicated PATCH endpoint optimized for real-time drag
  sync (smaller payload than full token update).
- Fog of war is Owner-only (GM controls what players see). Reset clears all
  fog regions for a map in one operation.
- `foundry_id` fields on drawings and tokens enable stable ID mapping for
  Foundry VTT sync without relying on Chronicle's internal UUIDs.
- Map deletion cascades to markers via FK constraint in MariaDB.
- `marker_icons.go` is the single source of truth for the marker icon
  vocabulary; `IsValidMarkerIcon`/`NormalizeMarkerIcon` guard rendering.
  Changing the catalog changes the cross-system contract with the Foundry
  module's `scripts/map-sync.mjs` translation table — keep them in sync.
- Widget binding: `map_widget_type.go` registers `"map"` (instance = a map
  record). A `widget_bindings` row (widget_type="map") wins over the legacy
  `entity.map_id` fallback, which still resolves for unbound entities.
  `DeleteMap` calls `BindingCleaner.OnInstanceDeleted` to sweep bindings; the
  legacy `entity.map_id` is independently SET-NULLed by the
  `fk_entities_map_id ON DELETE SET NULL` FK. A bind-to-embed swap shows the
  finished preview at once, because the preview needs no script. The
  `PUT /entities/:eid/map` `AssignMap` endpoint and `entity_map.js` are
  superseded by the binding picker but left in place while `map_id` is still
  read as the fallback.
- The marker PUT is a full replace via `patch.Field`: an absent key preserves
  the stored value, an explicit `null` clears it, a present value replaces
  it. This matters because `entity_id`, `visibility_rules`, and `foundry_id`
  are access-control / sync-pairing data — a client that echoes a full
  marker object back can silently clear another client's edits if it uses
  plain nil-means-preserve pointers instead of `patch.Field`. The web form
  never sends `foundry_id` (pinned by `marker_partial_update_test.go`), so it
  cannot touch the Foundry pairing key.

- **Map display settings.** One nullable JSON column (`maps.display_settings`,
  migration 007) holds frame override/tint, pin style/size/labels, the five
  kinds' labels and colours, grid, opening view, draw gate and the hex party gate (`hexes.party_who`). The service
  validates and normalises it (unknown keys dropped, enums checked, colours
  hex-checked, sizes clamped, default-equal values removed) and merges at group
  granularity, so a PUT with `{"grid": {...}}` leaves every other group alone.
  The `hexes` group merges per field instead (absent keeps, null or the default
  clears), because its fields are saved from different places: `party_who` from
  the settings sheet, `art` through the hex layer.
  Defaults are resolved server-side (`ResolveDisplay` -> `ResolvedDisplay`) and
  handed to the page as `data-display`, so JS never duplicates them. Wire keys
  are snake_case. The legacy unused `grid_*` / `initial_view_*` columns are not
  used.
- **Campaign frame.** Stored in this plugin's `map_campaign_settings`
  (one row per campaign, absent means `atlas`), not on `campaigns`. The
  Customize page is the campaigns plugin's; maps contributes its tab through
  `campaigns.Handler.RegisterCustomizeTab` (same shape as `RegisterSettingsTab`),
  so campaigns never imports maps. A map follows the campaign frame unless its
  own `frame.style` is set.
- **Frames.** Every frame's ornaments are rendered and the stylesheet shows
  the active one, so the settings sheet previews a frame live. Tint is a CSS
  filter on the map image layer only. Runes animation is off under
  `prefers-reduced-motion`.
- **Opening view "where each person left off"** is `localStorage`
  (`chronicle.mapview.<user>.<map>`); nothing is stored server-side.
- **Measuring.** The Measure tool (key M) is for everyone and is private:
  the path, its legs and totals live only in the viewer, are never sent, and
  nothing goes over the websocket. On a hex map it snaps to hex centres,
  highlights the hexes and reads "N hexes · M miles" / "About D days on foot"
  through `map_hexes.js`'s `hexLine` and `tripSummary`, with the layer's
  `miles_per_hex` and `miles_per_day`. Elsewhere it uses the map's scale:
  `display_settings.measure` = two points in percent of the picture (0..100,
  at least 0.1 apart), a length (finite, > 0, at most 100000) and a unit
  (`miles|km|feet|leagues`), all required and refused rather than clamped. The
  sheet's PUT never names `measure`, so it keeps the scale; only
  `PUT /maps/:mid/measure` writes it, and only for `CanAuthorDmOnly` (owner or
  DM grant), checked in the service before the map is read. Without a scale a
  player is told "The owner or a member with DM access can set one."
- **Gear and sheet are owner-only** (the PUT is Owner-only); scribes and
  players see the frame but not the sheet.
