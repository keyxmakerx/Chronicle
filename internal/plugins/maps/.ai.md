# Maps Plugin

Campaign maps (world, region, city, dungeon) shown in Leaflet over a background
picture, with positioned pins that can link to entities or open other maps.
Subsystems: drawings, tokens, layers, fog regions, a hex layer with fog and a
party. Tier: **Plugin** (handler, service, repository, models, Templ components
in the plugin root; drawing and hex code has its own handler/service/repo).

## Data Model

### Map
`id`, `campaign_id`, `name`, `description`, `image_id` (media FK),
`image_width`, `image_height`, `sort_order`, `display_settings` (JSON),
timestamps. The `grid_*` / `initial_view_*` columns from migration 001 are
unused. A map with no picture is a blank 1000-unit square sheet (`.mp-sheet`) in
the viewer and the dashboard widget.

### Marker
- `id`, `map_id`, `name`, `description`, `x`/`y` (percent 0-100, so maps work at
  any resolution), `icon` (`^fa-[a-z0-9-]+$`, default `fa-map-pin`), `color`
  (`^#[0-9a-fA-F]{3,6}$`, default `#3b82f6`), `pin_category` (nullable: location,
  danger, treasure, quest, note; maps to Foundry pin types), `entity_id`,
  `linked_map_id`, `visibility` (`everyone` | `dm_only`), `visibility_rules` (JSON
  per-user overrides), `foundry_id` (stable Foundry mapping), `created_by`.
- Joined: `entity_name`, `entity_icon`; `linked_map_name` (the join also requires
  the linked map to be in the pin's campaign, so another campaign's map reads as
  no link).
- Updates are partial via `patch.Field`: absent preserves, explicit `null` or
  `""` clears, a value replaces. `entity_id`, `visibility_rules` and `foundry_id`
  are access-control/sync data: a client echoing a whole marker must not clear
  another client's edits. The web form never sends `foundry_id`
  (`marker_partial_update_test.go`).
- `pin_category`: the service accepts only the five values or null; on update
  only a sent value is checked, so a legacy stored value never blocks an edit.
- `linked_map_id` (migration 010, FK to `maps`, ON DELETE SET NULL) must name
  another map of the same campaign. The service answers the same 422 for the
  pin's own map, a missing map and another campaign's (no probing); an update
  echoing the stored id is not re-checked. Who can follow a link is the pin's own
  visibility.
- Foundry connection presence comes from the campaigns plugin's
  `GET /campaigns/:id/foundry-presence`, not from this plugin.

### Drawing
- `drawing_type` is a VARCHAR checked against `validDrawingTypes`, so a new
  type needs no migration. Types: `freehand`, `rectangle`, `ellipse`, `polygon`,
  `text`, `shadow`, `image`, `arrow`, `highlight`, `step`, `callout`, `room`,
  `area`, `water`, `wall`, `danger`.
- Common: percent coordinates, stroke/fill, rotation, layer, `visibility`,
  optional `foundry_id`. Visibility `dm_only`, visibility rules, layers, the draw
  gate, edit-own/delete-own for scribes, shadow and hex-fog hiding, WebSocket
  audience, export/import and the sync API are shared by every type. The Foundry
  module draws only the types it knows and skips the rest (annotations, boxes,
  pictures).

**Annotations** (`drawing_annotation.go`): hex colours only, rotation 0, points
on the map (0-100).

| Type | Points | Rules |
|---|---|---|
| `arrow` | `[tail, tip]`, distinct | `stroke_width` up to 60; no text or `font_size`. Head sized in screen pixels |
| `highlight` | freehand, at least 2 points | `stroke_width` up to 60; `fill_alpha` 0.1-0.7 (unset 0.35); own pane (z-index 395, `mix-blend-mode: multiply`); no text or `font_size` |
| `step` | one point | `text_content` is a number 1-999 as plain digits; the viewer numbers a new step from the highest it can see plus one; numbers are not unique; optional `font_size` 8-48 |
| `callout` | one point (tail) | `text_content` trimmed, 1-500 chars, no control characters except line breaks and tabs; rendered with `textContent`; optional `font_size` 8-48 |

`text` labels share the 500-character bound whenever their text is written (a
longer stored label works until edited). On import (`Imported`) label text is
cleaned to the bound rather than refused. Undo removes the last drawing made in
this page session.

**Diagram boxes** (Shapes tool, ADR-067; `validateBoxShape`). Hand-made and
AI-sketch-made maps are the same records.

| Palette | `drawing_type` | `points` | `text_content` |
|---|---|---|---|
| Room, Area, Water | `room`, `area`, `water` | `[top-left, bottom-right]` | optional name |
| Wall | `wall` | same | none (refused) |
| (sketch only) Danger | `danger` | same | optional name |
| Arrow | `arrow` | `[tail, tip]` | none |
| Speech bubble | `callout` | `[tail point]` | required |

A box is two corners in map percent, stored top-left first (the server sorts
them), each side at least 0.5 percent, on the map. A name is trimmed, at most
500 characters; blank or `null` means none. Boxes take hex `stroke_color` /
`fill_color`, `fill_alpha` 0-1, `stroke_width` up to 60, rotation 0, but the
viewer ignores colours for them: the look comes from theme tokens
(`.mp-shp-room` etc.), so a client sends only type, points and name. DM-only
shapes are dropped by the SQL in `ListDrawings` and `DrawingVisibleTo`, not by
the viewer.
- Move, resize, rename and hide are partial `PUT`s of only the changed field;
  the merged row is re-validated, so a resize cannot leave an unselectable box.
- Select is the Move tool (V): a clean click picks a shape up, a press that drags
  still pans. Handles resize; Tab reaches each shape (`role="button"`), arrows
  move one grid cell, Shift+arrows resize, Esc lets go, Delete asks first.
- Placing (rail "Shapes", key S) snaps to `grid.size` even when the grid is not
  drawn (walls to half a cell; Alt skips).
- Selection is offered only where the server allows the change (`mayChange`:
  owner, DM access, or the author); the server refuses the rest.

**`image`** (`drawing_image.go`): a campaign media picture on the map.
- Two opposite corners in percent; `rotation` -45..45; `fill_alpha` is opacity
  (clamped 0.2-1.0, unset 1); `image_id` must be an image of the map's own
  campaign, checked via `MediaVerifier` on create and whenever it changes;
  `crop` `{t,r,b,l}` percent per side 0-45 (null clears), stored re-serialised
  as only t, r, b, l; `sort_order` stacks pictures. Other types reject `image_id`
  and `crop`.
- Drawn in a Leaflet pane at z-index 380, below staff shadows (390) and the
  vector pane (400).
- Drawing endpoints add `image_url`: a signed media URL minted for the
  requesting viewer (ADR-058), only on drawings that viewer may receive.
  Without it, anonymous visitors of a public campaign would get 404s. The URL
  expires (about an hour); the viewer re-fetches the one drawing on the first
  image error. With no entity referencing the file, unsigned access falls to
  campaign membership (ADR-058 decision 3).
- Change and delete follow the drawing rule (owner and DM access: any; scribe:
  own); the viewer offers selection on exactly those.
- A picture whose box overlaps a shadow keeps its drawing but loses its file for
  everyone the shadow hides things from (`shadowWithholdsImageOf`). A turned
  picture is tested exactly (about its centre in map pixels; the recorded image
  size, 1000x1000 if none) and is withheld only when it covers part of a shadow;
  if the size cannot be read, every turned picture on a map with a shadow is
  withheld.

**`shadow`** (`shadow.go`): two opposite corners in percent; `fill_alpha` is
strength (0.5 "A hint", 0.85 "Almost nothing"; anything else becomes 0.5).
- The server withholds pins and drawings under a shadow from every viewer who is
  not owner/DM-equivalent (a co-DM grant counts), scribes included:
  `MapService.ListMarkers`, `DrawingService.ListDrawings`, the by-id reads and
  the WebSocket publisher (DM-equivalent clients only). Shadows themselves are
  sent.
- Creating, updating or deleting a shadow is owner/DM-equivalent only
  (`requireShadowAuthor`, from the `isDM` / `CallerIsDM` argument that handlers
  fill from `CanAuthorDmOnly`). The "Hide under shadow" tool shows only for DMs.
- Hidden viewers see one smoke layer per strength masked by the union of the
  rectangles; DMs see a faint per-area version.

**The picture under a shadow is not sent.** `MapService.ForViewer` /
`ForViewerList` is the one place a map reaches a user. For a hidden viewer of a
map with a shadow it clears `image_id` and sets `image_url` to the player-image
route (versioned by the cache key). The map page, viewer fragment, entity
preview, map list, `/meta` and the sync API map endpoints all go through it;
templates build picture addresses only with `mapImageSrc`.
- `PlayerImage` renders the copy in Go (`renderPlayerImage`: at most 4096 px on
  the long side, strong blur, "A hint" at 45% brightness, "Almost nothing" at
  5%, feathered edges, opaque JPEG). It is cached on disk, keyed by a hash of
  (picture, map, sorted shadow boxes and strengths), in `map-player-images/`
  next to the media root, not inside it (the media orphan sweep deletes unknown
  files there). A map's older copies are dropped when a new one is written; an
  unwritable cache still serves the copy. Any failure is an error, never the
  original.
- The media plugin refuses the original and its thumbnails through
  `media.MapImageGuard`, implemented by `MapService.IsShadowedMapImage` (see the
  media `.ai.md`). Not covered: the Foundry module syncs with the owner key and
  receives the original.

### Token
Characters/NPCs/objects. Position (`x`/`y`), size, rotation, scale; HP bars
(`bar1_value/max`, `bar2_value/max`); `aura_radius/color`,
`light_radius/dim_radius/color`; `vision_enabled/range`, `elevation`,
`status_effects` (JSON); optional `entity_id`, `foundry_id`. Position has its
own PATCH (small payload for drag sync).

### Layer and FogRegion
Layer: types `background`, `drawing`, `token`, `gm`, `fog`; `sort_order`,
`is_visible`, `opacity`, `is_locked`. FogRegion: polygon with `is_explored`.
Region fog is Owner-only; reset clears every region of a map in one operation.
`foundry_id` on drawings and tokens gives stable Foundry ID mapping.

### Hex layer
Not to be confused with FogRegion: this is the hex grid's own layer.
- Turned on by `display_settings` `grid.type = hex`. `grid.size` is measured as
  if the hex area were 1000 wide. Pointy-top, odd rows shifted right ("odd-r"),
  hex (0, 0) centred on the map's top-left corner, in `hex.go` and `map_hexes.js`
  alike, checked against the same golden vectors.
- Tables (migration 009): `map_hex_layers`, one row per map, created by the first
  write: `version` (bumped on every write; the ETag and live cursor),
  `anchor_drawing_id`, `fog_enabled`, `party_col/row`, `miles_per_hex` (default
  6), `miles_per_day` (default 24). `map_hex_cells`: sparse rows keyed by (map,
  col, row): `terrain`, `piece`, `name`, `notes`, `explored`, `updated_by`.
- Limits: terrain is allowlisted (`IsValidTerrain`: plains, forest, hills,
  mountain, water, swamp, desert, snow, town, road); names at most 120 runes,
  notes 2000, plain text escaped on output; positions 0..399 per axis; at most
  500 entries per batch; at most 40000 stored cells (a write counts only hexes
  not already stored; a hex with every field cleared is deleted, so a full map
  can be trimmed). An entry naming no field is refused. The viewer clamps to
  `MAX_HEX_AXIS` (one more than `MaxHexCoord`).
- Pieces: `piece` is 0..11 (`HexPiecesPerTerrain`) for a terrain with pieces,
  null for Mix (the viewer picks a stable piece from position). A piece that
  does not fit the terrain after the write is refused (400); a terrain change
  that leaves the piece out of range clears it. Roads and cleared hexes have none.
- Reads: names and notes are visible to everyone who can view the map, minus
  unexplored hexes when fog is on. Notes are not private; the writer's card says
  so.
- `VisibleCells(layer, cells, role)` is the one filter. Fog off: every row to
  everyone. Fog on: `CanSeeDmOnly` roles (owner, DM grant) get every row;
  everyone else, scribes included, gets explored rows only.
- Terrain art: `display_settings` `hexes.art` is `real`, `detailed` (default, not
  stored) or `simple`, one per map. Set through `PUT .../hexes/layer`
  `{"art": ...}` (null = Detailed); `HexService` validates it, writes it with
  `mapService.SetHexArt` and bumps `version`. Detailed and Realistic tiles are
  drawn by `map_hex_art.js` on one canvas at the bottom of the `mpHexes` pane
  (SVG overlay at z-index 390 stays on top); painting is time-sliced
  (`JobQueue`, `iso3ModelJob`) so art never holds the page, and the art uses
  only cells the viewer was sent, so it cannot show fogged land. While
  `map_hexes.js` runs it draws the hex lines and the viewer skips its plain grid
  (`onHexLines`).

**Pinned to a picture.** `anchor_drawing_id` names an `image` drawing on the same
map (null: whole map). The field is laid inside the picture's box (hex (0, 0) is
the first whole hex at top-left; it stops before a hex would cross the right or
bottom edge). Resizing the picture scales the hexes with identical columns, rows
and keys. `NewAnchoredHexGeometry` (Go) and `anchoredGeometry`/`layoutFor` (JS)
agree on golden vectors. The JS builds the field once in a box 1000 wide and
carries it to the picture with one group transform; the picture module reports
corners through `onChange('geo')`, republished as `ctx.pictures` by the drawing
module (so hexes survive "hide drawings").
- Setting: `PUT /maps/:mid/hexes/layer` `{"anchor_drawing_id": id | null}`,
  partial; owner or DM grant only (`HexActor.IsDM`; the route needs membership
  only). The drawing must exist, be on this map and be an image; a missing id,
  another map's picture and a non-image get the same 400. Anchoring turns the
  picture upright (rotation 0, through the drawing service so other viewers hear
  of it, after the anchor is stored); the write carries the picture's
  `updated_at`, so a concurrent edit is a 409.
- Reading (`hexService.anchorState`): the layer reads as hidden (`hidden: true`,
  `DefaultHexLayer` plus the real version only; the client draws no hexes and no
  plain grid) for anyone who cannot see dm_only when the anchor picture is
  `dm_only`, is wholly under a shadow (`HexPictures.IsShadowed`; a failed check
  fails the read), or is unusable (deleted, on another map, no longer an image;
  the column has no FK). Owners and DM grants get the whole-map fallback so they
  can fix it. Only an explicit PUT with `anchor_drawing_id: null` shows cells to
  players again; a read never rewrites the anchor. With no picture lookup wired,
  a read of an anchored layer fails.
- UI: owners get "Make a hex map" while the grid is not hex. The picture bar
  offers "Turn into a hex map" to owner or DM access (a DM only when the grid is
  already hex); for the anchored picture it shows "Open hexes" and, for the
  owner, "Take the hexes off" (anchor null, grid off, painted hexes stay stored).
  Every path that changes the cover or grid size over painted hexes asks first.

**Endpoints and write rules.**
- `GET /maps/:mid/hexes` returns `{layer, cells, version, hidden, art}` to anyone
  who can view the map (public included); `art` is omitted while hidden.
- `PATCH .../hexes/cells` takes `{cells: [{col, row, terrain?, piece?, name?,
  notes?}]}`, partial per entry: absent keeps, `null` clears, a value replaces
  (one `INSERT ... ON DUPLICATE KEY UPDATE` per entry, so a paint stroke cannot
  disturb a name).
- Who may write is decided in `HexService`, not route middleware (the route needs
  membership, so a DM-granted player reaches the service): owner or DM grant
  writes any hex; a scribe only where the draw policy lets scribes draw and,
  with fog on, only on explored hexes; players are refused. A batch with any
  refused entry is refused whole. A non-DM gets 403 while the layer reads as
  hidden to them. The map must belong to the campaign in the path (404 otherwise).
- The Hexes tool (key H) is on the rail only for hex grids; players get Move and
  Hexes. Paint is offered exactly where the server allows
  (`MapViewData.CanPaintHexes` → `data-can-paint-hexes`): this is not the drawing
  gate, since a DM-granted player paints without being a scribe.
- Live: every hex write publishes `hex.changed` `{map_id, version,
  party_path?}`, never a cell, name or note, to the whole campaign;
  `party_path` only when safe for every recipient. A paint batch publishes once.
  The viewer opens `/ws?campaign=<id>` (also for `map.items.changed`), ignores
  events not newer than what it read or echoing its own write, waits for
  unsaved edits, and refetches the filtered GET. The event never replaces the
  read, so audience rules live in one place.

### Fog of war and the party
- `fog_enabled` is the layer's switch (`PUT .../hexes/layer`, partial, owner or
  DM grant). With fog off nothing below applies.
- `FogMask` (`hex_fog.go`, built by `hexService.FogMask`) is the one definition
  of "unexplored", built whenever fog is on and the map has a picture size,
  whatever the grid type (switching the grid away from hexes does not lift fog;
  nil means nothing is fogged). Everything hiding data from a viewer below
  `CanSeeDmOnly` (`fogHidingApplies`, the negation of `VisibleCells`' own line)
  applies it: cells, party position, pins, drawings, tokens, live events and the
  picture. Lookups fail closed: no lookup wired, or one that errors, hides. A
  point outside the field is not hidden; a pin or drawing is hidden when wholly in
  unexplored hexes (a drawing touching explored land stays; an unparseable one
  is hidden). `PointInUnexplored` is the pure check.
- Cells: players get explored rows only; the DM gets every row with `explored`.
  The party position is withheld while on an unexplored hex (`VisiblePartyLayer`).
- Pins: `ListMarkers` and `IsMarkerShadowed` drop pins under unexplored hexes, so
  list, by-id and websocket paths agree. Drawings: `ListDrawings`,
  `IsDrawingShadowed` and drawing events (shadows pass; players need them for
  smoke). Tokens: `ListTokens`, `IsTokenHidden` and token events, by the token's
  point.
- Writes: a caller who cannot author DM-only content and updates or deletes a pin,
  drawing or token hidden from them (shadow or fog) gets the same NotFound as for
  a missing id; nothing is written.
- Reveal/hide: `POST .../hexes/fog`, owner or DM grant (`requireFogWriter`), at
  most 500 hexes (`MaxFogBatch`), counted against the 40000-cell cap.
- Party: `PUT .../hexes/party` `{col,row}`. Who may move it is `hexes.party_who`:
  `owners` (owner or DM grant) or `scribes` (also scribes; default, not stored).
  The server computes the path (`HexLine`, the line the viewer walks), reveals
  radius 1 around every path hex in one transaction (`RevealZone`, clipped to
  the field) and returns the path; first placement reveals radius 1 around the
  hex. A scribe may only move onto an explored hex or a neighbour of one
  (`OnExploredFrontier`) and, with fog on, only while the party stands on an
  explored hex; a DM may go anywhere. The move is optimistic (`expectedFrom`),
  retried up to three times on conflict.
- Map picture: for a whole-map layer with fog on, viewers below `CanSeeDmOnly`
  get the player copy, which smudges unexplored hexes into the pixels
  (`smudgeFog`). The cache key includes layer version and geometry, so any layer
  write renders a fresh copy; the viewer asks for `/player-image?v=<version>`
  after each event. `MapImageGuard` treats a fogged whole-map layer as shadowed.
- Picture files: fog withholds the file of the picture a layer is pinned to and
  of every picture whose box (turned, if rotated) overlaps an unexplored hex
  (`FogMask.WithholdsImageOf`). `image_id` and `image_url` are cleared for those
  viewers on list and by-id reads (`DrawingService.WithholdImages`, also on the
  sync API), the picture draws as a grey placeholder, and its events reach staff
  only. The media server refuses the file (`MapImageGuard` via
  `DrawingService.WithholdsPictureFile`) and the sync media API mints no link
  below owner. Pictures overlapping a shadow take the same three paths. Fog, hex
  hide/reset and picture writes drop the guard's cached answers.
- Viewer: players get unexplored hexes in the same smoke layer as shadows through
  one union mask (`ChronicleMapShadow.setHexFog`); the DM sees them hatched. The
  party token walks the returned path (170 ms a hex; none under reduced motion).
- Trips: "Plan a trip" is a Hexes mode for everyone who can see the layer. The
  plan is private and client-only (`localStorage`
  `chronicle.maptrip.<user>.<map>`, never sent). It is built from the filtered
  read: with fog on, a hex the viewer was not sent reads as "unexplored land".
  Travel figures come back from `GET .../hexes` to everyone; owner or DM grant set
  them through `PUT .../hexes/layer` (trip panel, one field per request; Map
  settings > Hexes > Travel). `UpdateLayer` refuses a figure outside 1..1000
  before writing; null restores the default; a body naming only fog or the anchor
  leaves them alone.
- Known gaps: a line, shape or text drawing touching explored land is sent whole
  (same as shadows); `hex.changed` tells players the DM wrote something, not what.

## Key Functions

- `MapService.CreateMarker` / `UpdateMarker`: validate name, coordinates, icon,
  color and `pin_category` (`validatePinCategory`); set defaults.
- `MapService.ListMarkers`: filters by role (dm_only needs role >= 3), shadow and fog.
- `MapService.LinkTree` / `ResolveTrail` (`map_links.go`): `buildLinkTree` puts
  maps nothing links to first, then starts each group reachable only through a
  cycle at the map with the most links out (ties: campaign map order).
- `MapService.WhereIs` (`where_is.go`): an entity's place in the maps for one
  viewer, closest first. Step one is a map the entity is pinned on
  (`ListMapsPinningEntity`); each next step is a map holding a pin that opens the
  previous one (`ListMapsLinkingTo`). Every pin is read through `ListMarkers` for
  the viewer, so an invisible pin adds no step and no gap. Among several maps
  opening one, the pick is one players can follow into, then name, then id. A
  visited set ends cycles; `MaxLinkTreeDepth` bounds the walk (`Truncated`). A DM
  is told which steps players cannot reach (`WhereStep.DMOnly`; a pin limited to
  named players counts as hidden), and the walk leads with maps players can see.
  Other pinned maps go in `Also`. Pictures pass through `ForViewer` last. The
  ladder is stored nowhere on the page.
- `MapService.SearchMaps`: name search for quick search.
- `DrawingService.ListDrawings` / `ListTokens`: role-based filtering;
  `UpdateTokenPosition`: position-only update for drag sync.

## Security

- **IDOR**: `requireMapInCampaign`, `requireMarkerInCampaign` and
  `requireMapOwnership` verify ownership before every operation.
- **XSS**: marker `icon` and `color` are regex-validated because they render
  into HTML attributes and CSS. The viewer builds names with `textContent`.
- **Who can draw**: `DrawingService.requireDrawAccess` enforces the map's
  `draw.who` (owners | owners and scribes; default scribes) on drawing create and
  update for every entry (web, sync API, import), from an explicit role argument.
  Fails closed on a role below Scribe and on a settings lookup error. Tokens and
  fog are not gated by it.
- **Who can delete**: routes admit Scribe+; the service (`canDeleteOwn`) lets an
  Owner delete anything and a Scribe only items whose `created_by` is them. A
  missing creator is owner-only, a role below Scribe never deletes, a dm_only
  item the caller cannot see answers NotFound. A DM-access grant does not make
  someone an Owner here. The sync API forwards the key owner's user id and
  resolved role.
- **Visibility**: dm_only markers, drawings and tokens are hidden from non-Owner
  roles (DM-equivalent where noted above).
- **Map links**: a link rides on its pin, so the marker list, `data-markers`, the
  link tree and marker live events carry it only on pins the viewer may see.

## Dependencies

Uses campaigns (access), auth, addons (gating), media (map images), entities
(marker linking). Used by syncapi (external map API including marker CRUD) and
WebSocket updates.

## Design Notes

- **Live updates.** Every pin and drawing write (shadow and picture drawings
  included) goes through `mapEventPublisherAdapter` in `internal/app/routes.go`,
  web handlers and sync API alike. It sends `map.items.changed` `{map_id, kind}`
  (`markers`, `drawings` or `shadows`) just before the per-item event, carrying
  no content. Tokens never announce: the web viewer has no token layer and a
  notice per hidden drag would leak movement. Creating or deleting a DM-only or
  rule-restricted item gets that item's audience; updates and shadows go to the
  whole campaign, and the page refetches through `GET .../markers` and
  `.../drawings`, which apply DM-only, shadow and fog rules for that viewer.
  Per-item events stay audience-gated for Foundry. `map_live.js` debounces 300 ms
  and redraws only the affected layer; a failed or malformed refetch leaves the
  screen alone; a pin being edited or dragged is left alone, and the drawing
  layer is not rebuilt while a tool is active or a picture selected. `shadows`
  refetches drawings and pins.
- **Page layout.** `MapEditorBody` renders `#map-wrap` with the Leaflet container
  and `mapControls` floating over it as siblings (not Leaflet controls, so the map
  never sees their clicks; Leaflet's zoom control is off): search and Scribe+
  tool rail top-left, Pins & layers top-right, zoom/fit/full screen bottom-right,
  hint bottom-centre. Keys: V move/select, M measure, H hexes, P pin, D draw,
  S shapes, B hide under shadow, Esc closes the nearest popover/card, then stops
  the tool. Players get Move and Measure (and Hexes on a hex map).
  `mapShowContent` and `MapViewerFragment` put the wrapper inside the map's
  resolved frame.
- **Viewer is a static widget, not an inline script.** `MapEditorBody` emits
  markup plus `#map-config` (role-filtered data, library URLs) and
  `map_viewer.js` starts from it, so the markup also works as a fetched fragment
  (innerHTML does not run scripts). One viewer per page (fixed ids);
  `ChronicleMapViewer.destroy` tears down Leaflet, listeners and
  `window.chronicleMap` so the focus view can reopen.
- **Map on a page: preview, then unfold.** `BlockEntityMapEmbed` is a picture of
  the map in its frame, not a live map (no marker data, no Leaflet). Click or
  Enter/Space calls `ChronicleMapFocus.open` from an inline handler (works after
  an HTMX swap). It fetches `/maps/:mid/viewer`, mounts the viewer and shows a bar
  with the map name, "Open map page" and Close. Esc, the backdrop and Close
  dismiss it; an Esc the viewer consumed (`event.mpConsumed`) does not also close
  it. One-shot FLIP animation (about 620 ms; 150 ms fade under reduced motion).
  A save the map page answers with a reload refreshes the unfolded map instead
  (`opts.onReload`).
- **Pin cards.** A click shows a read card; Scribe+ edit from it. A new pin (Pin
  tool or double-click) opens a quick card (name, kind, who can see it) with
  "More options" to the full modal. The quick card sends only changed fields.
  "Who can see it" is offered only to callers who can author dm_only content.
  Pin Remove shows to a scribe only on pins they created. Undo only walks
  drawings created this page session; a 403 is reported, not hidden.
- **Layers panel is client-side.** Kind, drawings and hidden-pin toggles never
  touch the server.
- **Marker icons** (`marker_icons.go`): `IsValidMarkerIcon` /
  `NormalizeMarkerIcon` guard rendering. Changing the catalog changes the
  contract with the Foundry module's `scripts/map-sync.mjs` translation table;
  keep them in sync.
- **Widget binding.** `map_widget_type.go` registers `"map"` (instance = a map). A
  `widget_bindings` row wins over the legacy `entity.map_id` fallback, which
  still resolves for unbound entities. `DeleteMap` calls
  `BindingCleaner.OnInstanceDeleted`; `entity.map_id` is SET NULL by
  `fk_entities_map_id`. `PUT /entities/:eid/map` (`AssignMap`) and `entity_map.js`
  stay only while `map_id` is read as the fallback.
- **Map block picker.** With no map resolved, Scribe+ get
  `BlockEntityMapChoose` (search, live count, a grid of maps as `ForViewerList`
  lets this viewer see them, thumbnails from `mapImageSrc`, Pick disabled until a
  card is selected, double-click picks). Create-a-map posts `POST /bindings/create`
  (Scribe+); Pick posts `POST /bindings`, whose answer is the block host
  re-rendered as `BlockEntityMapEmbed` (outerHTML swap). Players get
  `BlockEntityMapEmpty`. Dashboard `map_full` blocks keep their own empty state:
  their map id lives in the owner-only whole-layout PUT.
- **Display settings.** One nullable JSON column `maps.display_settings`
  (migration 007): frame override/tint, pin style/size/labels, the five kinds'
  labels and colours, grid, opening view, draw gate, `hexes.party_who`. The
  service validates and normalises (unknown keys dropped, enums and hex colours
  checked, sizes clamped, default-equal values removed) and merges per group, so
  `{"grid": {...}}` leaves other groups alone. `hexes` merges per field (absent
  keeps, null or default clears) because `party_who` is saved from the sheet and
  `art` through the hex layer. Defaults resolve server-side
  (`ResolveDisplay` → `ResolvedDisplay`, handed to the page as `data-display`);
  JS never duplicates them. Wire keys are snake_case.
- **Campaign frame.** Stored in `map_campaign_settings` (one row per campaign,
  absent = `atlas`), not on `campaigns`. Maps contributes its Customize tab via
  `campaigns.Handler.RegisterCustomizeTab`, so campaigns never imports maps. A
  map follows the campaign frame unless its own `frame.style` is set. Every
  frame's ornaments are rendered and the stylesheet shows the active one (live
  preview in the settings sheet). Tint is a CSS filter on the map image layer
  only. Runes animation is off under `prefers-reduced-motion`.
- **Opening view "where each person left off"** is `localStorage`
  (`chronicle.mapview.<user>.<map>`); nothing server-side.
- **Measuring.** Key M, for everyone, private: path and totals live only in the
  viewer, never sent, nothing over the websocket. On a hex map it snaps to hex
  centres and reads "N hexes · M miles" / "About D days on foot" through
  `map_hexes.js`'s `hexLine` and `tripSummary`. Elsewhere it uses
  `display_settings.measure`: two points in percent (0..100, at least 0.1
  apart), a length (finite, > 0, at most 100000) and a unit
  (`miles|km|feet|leagues`), all required and refused rather than clamped. The
  sheet's PUT never names `measure`; only `PUT /maps/:mid/measure` writes it, for
  `CanAuthorDmOnly` (owner or DM grant), checked in the service before the map is
  read.
- **Gear and sheet are owner-only** (the PUT is Owner-only).
