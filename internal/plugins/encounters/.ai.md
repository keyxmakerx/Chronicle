# Encounters Plugin

## Purpose

Fights a DM plans on a page and loads in Foundry on game night. An encounter
belongs to one page. It names the heroes it was built for and one row per
creature: the creature's page, how many, its initiative group (A to H) and how
it starts: **seen**, **hidden** (token placed hidden) or **later** (left off the
scene until the DM places it). Nothing is revealed automatically; Foundry's
Encounters tab shows or hides a creature only when the DM presses it.

- **Stages:** moments mid-fight when a creature takes another form and/or
  "later" rows arrive. A stage says when it is due (manual, a creature at or
  below a Stamina percent, or the start of a round), but nothing starts on its
  own: the Foundry DM Screen says a stage is due and the DM presses Start.
- **Versions:** the same fight played another way. A version stores only its
  changes to the base rows: rows added, base rows left out, base rows with
  another count. A version can name the **pick**, a result of a test on a page
  (`pagetests`, a montage or any long effort) that chooses it; when that result
  is recorded the encounter reads `picked.version` as that version. Nothing
  loads on its own: Foundry shows which version the results choose and the DM
  sets up the fight.
- **Run:** a Ready encounter can be run on the DM Screen's Fight tab, for a
  table not using Foundry (see "The Fight tab").

Everything here is the DM's. The service refuses any viewer below Owner
visibility on every method, the block draws only for the DM, and the sync API
routes need the owner or a co-DM, so a planned ambush never reaches a player.

## The block and the builder

`page_encounters` is a layout block (template context, sizes 1x2, 2x2, 4x2),
always registered because the Adventures layout places it
(`tile-adv-encounters`). The widget lists the page's encounters; pressing one
slides the builder out from the right: name, hero tick boxes (pages in the
campaign's characters list), creature rows (pages in creature categories or the
NPC list, or a name with no page), Versions, Stages, Ready for game night,
Delete. It saves 600 ms after the last change, one save at a time carrying the
version, and reloads on a conflict. The page list response names the categories
each picker uses (`heroTypeIds`, `creatureTypeIds`, from
`PageDirectory.PickerTypes`), so the widget never guesses from presets;
creature search starts at two characters, the shortest the search API answers.
Opened inside another modal (a page over the DM Screen), the builder mounts
inside that dialog so it draws above it and the dialog's Escape and focus trap
leave it alone.

A creature row with a page folds out its numbers when its name is pressed
(`creature_fold.js`, `Chronicle.CreatureFold`): the game system's stat block
when it has one for the page's type, otherwise the page's filled-in fields from
`GET /campaigns/:id/entities/:eid/fields` (so a field the viewer may not see
never arrives), with "Open the page". A stat block is a panel the system's
manifest aims at creature pages (`entity_panels`, `applies_to: creature`), also
on the NPC types; the page list sends them as `statBlocks: [{widget, systemId,
typeIds}]` from `PickerTypes`. Folds stay open across redraws.

**Game-system hooks** (events on `document`):

- `chronicle:encounter-draft`, after every change, `{campaignId, encounter: {id,
  name, heroes, creatures, stages}, slot}`: the system fills `slot` (Draw Steel
  draws its encounter budget). The builder never computes a budget.
- `chronicle:encounter-forms`, when the builder opens and whenever the creature
  pages change, `{campaignId, entityIds, reply(map)}`: the system calls `reply`
  with `{entityId: [{id, name}]}` (forms other than the first; ids match
  `^[a-z0-9]{1,24}$`). Until a reply the form select offers only "Its first
  form" (id empty); an empty list for a creature adds "This creature has no
  other forms". A saved form the system does not list stays selectable. The
  builder keeps `formName` equal to the chosen option's name.

A stage that does nothing yet (no form change, no arrival, or a Stamina trigger
with no creature) stays in the builder with "Not saved yet" and is left out of
the save, so an unfinished card never blocks other edits.

Versions are tabs, one per version: a name, a "Chosen by" select (every test
result of the campaign, from `GET /campaigns/:id/tests`, or "Only I choose it"),
the base rows with a keep box and a count, and the rows only that version has.
Above the tabs a line says which version the saved results choose. One result
picks one version: choosing a result another version uses moves it.

## The Fight tab

`encounter_run.js` (`data-widget="encounter-run"`, mounted by `RunMount` in
`run.templ`, shown by the DM Screen via `internal/app/dm_fight.go`) runs one
fight per campaign, stored in `encounter_runs`. With no fight it lists Ready
encounters with Start. Start copies the encounter (`newRun` in `run.go`): its
heroes, then the creature rows the recorded results pick (`playedRows`: the
picked version's rows, or the base rows), each with a hit point box per copy;
"later" rows wait under "Arriving later" until Bring in. The copy is the fight
from then on, so editing or deleting the encounter never changes a fight in
progress.

The DM types each line's initiative; until First turn the lines stay as
listed so typing down the column never moves a line, and from then on they
are in turn order (initiative high to low, none last, ties as listed). Next
turn steps through the order and starts a new round past the last line. A
box shows the copy's hit points, or the line's full hit points (set under
the line's "…" with conditions) while untouched; a box at 0 or below is
struck through. Conditions come from the system's list (the DM Screen's Rules
tab) or are typed. A creature's name folds out its numbers as in the
builder. It saves 500ms after a change, the whole fight with the version it
read; a 409 reloads the fight and says it changed elsewhere. A save still in
flight when the tab is torn down is waited on by the next mount. "End the
fight" asks in place, saves any change still waiting (a box set to 0 a
moment ago counts; a save that fails stops the end), then ends the run.

**A fight listener** (`FightListener` in `run.go`) lets another app hear
about fights without encounters importing it; `internal/app` hands one in
with `SetFightListener`, today Crafting's (`crafting_spoils_adapters.go`).
`Current` asks it for a short note per creature page (`leaves`, best
effort), drawn as a chip beside the creature's name; a creature row with no
page reads "No page, so no drops" while any note came back. `End` reads and
deletes the run in one transaction (`EndRun`), so a fight ends once, and
tells the listener which creature rows were down (`endedFight`: each copy at
0 hit points or less, counted as the tab draws a box down; a waiting row
never). The listener's report (a line per creature, a link and a note) shows
above the Ready list until Done or the next fight. A listener that fails
leaves the fight over with a line saying to check by hand.

## Table

`encounters (id PK, campaign_id, entity_id, name, ready, data LONGTEXT,
version, created_by, updated_by, created_at, updated_at)`. FKs to core
`entities` and `campaigns` cascade, so deleting a page removes its
encounters; a trashed page's encounters stay with it and are left out of the
Foundry list until it is restored.

`encounter_runs (campaign_id PK, data LONGTEXT, version, updated_by,
updated_at)`: the fight on the Fight tab, one per campaign. No key to
`encounters`, since the run is a copy; the FK to `campaigns` cascades.

## Rules

- **Who**: Owner visibility (the owner, or a member given DM access) on every
  method; editing also needs the page's own edit rule. A page that is hidden
  or in another campaign is 404 before anything else.
- **Pages named in an encounter** (heroes, creature rows) must be live pages
  of the campaign the DM may see, checked on every save. On read, a hero
  whose page has gone is dropped and a creature row whose page has gone is
  unlinked (its name stays), so Foundry falls back to the name.
- **Stages** (`stages` in the `data` JSON; older documents read as none). Each is `{id, when: {kind, row, percent, round}, forms:
  [{row, form, formName}], arrive: [rowId], how, note}`. `kind` is `manual`,
  `stamina` (needs `row`, an existing creature row of the same save, and
  `percent` 1 to 99, due at or below it) or `round` (`round` 2 to 99, due at
  the start of it); fields the kind does not use are cleared on save. A form
  change needs a row that has a page and a `form` matching `^[a-z0-9]{1,24}$`
  or empty for the creature's first form; `formName` is plain text, 80
  characters. `arrive` holds existing row ids, no repeats. `how` is `reveal`
  (default) or `quiet`: how a form change is shown to players. `note` is plain
  text, 200 characters. A stage needs at least one form change or arrival.
  Stage ids are unique. On read, a form change or arrival whose row is gone
  (or whose row lost its page, for a form change) is dropped, and a Stamina
  stage whose row is gone becomes manual; a stage emptied this way is kept.
  The sync API returns `stages` in the encounter, not in the list.
- **Versions** (`versions` in the `data` JSON; older documents read as none). Each is `{id, name, pick: {test, result} | null,
  add: [creature row], remove: [rowId], counts: [{row, count}]}`. Ids are
  unique; a name is plain text, 80 characters. Added rows follow the creature
  row rules and their ids are unique across the whole encounter. `remove` and
  `counts` name base rows only, each at most once, never the same row in
  both; a count is 1 to 40. A pick needs a test the DM may see and one of that
  test's results, checked on every save; two versions may not share a pick.
  Stages may name a version's added rows. On read, a pick whose test or
  result has gone is cleared, `pick.testName` and `pick.resultLabel` are
  filled in (read only; a save ignores them), and `picked` is `{version, test,
  result, open}`: the first version whose pick is the recorded result, or an
  empty `version` (the base rows play), with `open` naming the picking tests
  that have no result yet. `test`, `result` and `open` are display names and
  labels; the ids are on each version's `pick`. `picked` is absent when there are no versions, or
  when the tests cannot be read; then the picks are kept as stored, unnamed,
  and a save is refused rather than dropping them. The
  AI's whole-encounter update keeps the versions it does not mention and
  drops changes to rows that are gone (`CarryVersions`). The sync API returns
  `versions` and `picked` in the encounter.
- **A run** (the Fight tab) is `{encounterId, name, round, turn, lines:
  [{id, kind, name, entityId, group, init, max, hp, conds, waiting}]}`. A save
  never sets what the fight is or which page a line is: `encounterId`,
  `name` and each line's `entityId` are taken from the stored run by line id
  (a new line gets none). `kind` is hero or creature; a line has 1 to 40 hit
  point boxes (a hero exactly 1), each null (full) or -99999 to 99999; `max`
  0 to 99999; `init` -99 to 999; up to 12 conditions of 40 characters, no
  repeats; at most 60 lines with unique ids; `round` 1 to 9999; `turn` empty
  or a line's id. On read, a line whose page has gone is unlinked.
- **Limits**: name 120 characters, 12 heroes, 30 creature rows, 1 to 40 of
  each, 8 stages, 10 form changes and 30 arrivals per stage, 6 versions with
  10 added rows each, 50 encounters per page.
