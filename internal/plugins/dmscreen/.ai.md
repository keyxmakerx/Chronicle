# DM Screen Plugin

## Purpose

The DM Screen is a control panel for the people running a campaign (owners,
scribes and members the owner has given DM access), opened from a button in the campaign top bar's right-hand icon
row. It shows, on three hinged "leaves" like a paper GM screen:

- **The world**: the downtime switch (armory), the default calendar's date
  and time, today's weather.
- **Time steps**: under the date, three chips ("+1 hour", "+8 hours", "Next
  day") move the default calendar forward. Hours and days are the calendar's
  own (`Calendar.advanceClock` rolls minutes into hours into days with its hours
  per day and month lengths; "Next day" is one calendar day and keeps the time
  of day). Shown only to Owner visibility and only when the calendar is not
  real-time (`WorldView.CanStep`); the calendar service refuses a real-time
  calendar anyway. The chips post `step=1h|8h|1d` to `POST /dm-screen/time`,
  whose `dms-refresh` trigger redraws the panel.
- **Waiting on you** (under the game state): the five oldest requests the
  armory has waiting, stash moves and ask-to-buy purchases together, each one
  plain line with Allow and Refuse. The buttons post to the armory's own
  approve/decline routes, whose `armory-moved` trigger makes the panel
  refetch, so a decided row disappears. More than five shows "N more on the
  Stashes page". Only Owner visibility (owner, DM-granted co-DM) gets buttons;
  the armory builds the list for no one else, so a scribe sees no block.
  `View.Requests` carries the same list as JSON.
- **The party**: each claimed character, folded to one line (the first meter
  with a max as a bar, meters without a max as chips, a count of current
  conditions). Clicking folds open the class, player, remaining meters and
  condition names; an open hero is always shown whole, so the list scrolls
  the others aside and grows if one hero alone wouldn't fit.
- **Rules and reveals**: the system's conditions (searchable) and hidden
  NPCs/creatures with a Reveal button.
- **Notes** (a third tab on the right leaf): a textarea labelled "Kept with
  <next game night>" (or "DM Screen notes" with no night) that autosaves about
  800 ms after typing stops and on blur or close, with a status line and an
  "Open in Notes" link. It is one ordinary note per campaign in the notes
  widget, visibility gm (owner and co-DMs), titled "<night>: DM notes" or
  "DM Screen notes"; a save retitles it to the current next night. Its id is
  derived from the campaign id (`dmNoteID` in the adapter, passed through
  `CreateNoteRequest.ID`), so the screen finds it again with no table or
  column, and two DMs saving at once hit the same primary key. Text is stored
  as plain paragraphs, one per line (`note_text.go`); a note edited in the full
  editor shows as its plain text and loses its formatting on the next save
  from the screen. A panel refetch keeps the open tab and unsaved note text.

A strip above the leaves shows the next game night with its RSVP tally,
"N of M players here", and whether Foundry is connected.

**Who's here.** `View.Presence` counts the campaign's players: members with
the Player role who are not DM-granted (owner, co-DMs and scribes run the game
and are not counted). A player is here when their browser has a live
websocket (`Hub.BrowserUserIDs`), or when the GM's Foundry client reports them
online (`foundry_players`, linked member, report under five minutes old, and
the Foundry socket itself connected). Browser sockets exist only on pages with
live widgets (notes, journal, maps, quest boards), so a player on a plain page
shows as here only through Foundry. The section is omitted with no players. An
open hero's "Played by" line gets a green dot when that player is here
(`HeroView.PlayerHere`).

## Architecture

A view plugin with no tables. `service.go` assembles a `View` from the
`Sources` in `sources.go`; each source is an interface implemented by an
adapter in `internal/app/dm_screen_adapters.go` (armory, calendar, sessions,
entities, campaigns, presence, requests, notes) or by an existing type (`websocket.Hub` for Foundry
presence, `systems.SystemHandler.EnabledSystem` for the game system). A
missing or failing source leaves its section out; it never fails the screen.

The game system decides what the party and rules sections show, through the
optional `dm_screen` block in its manifest (`systems.DMScreenDef`,
`internal/systems/manifest_dm_screen.go`): a list of party meters (sheet
field for the value, optional max field, optional warn-below fraction, fixed
label or a label field), the sheet fields for a hero's subtitle (class) and
current conditions (a list, JSON list or comma string of names or
`{"name"}` objects), and the reference category plus property filter for
the rules tab's conditions. Without it the party lists names only and the rules tab is hidden.

## Routes

| Method | Path | Role | Purpose |
|--------|------|------|---------|
| GET | `/campaigns/:id/dm-screen` | Scribe+ or DM access | Panel fragment (`Panel`) |
| GET | `/campaigns/:id/dm-screen/notes` | Scribe+ or DM access | The note as JSON (`NotesView`) |
| PUT | `/campaigns/:id/dm-screen/notes` | Scribe+ or DM access | Save the note text (`{"text": …}`), 20,000 characters at most |
| POST | `/campaigns/:id/dm-screen/time` | Scribe+ or DM access; the service requires Owner visibility | Move the date forward one step (`step`) |
| POST | `/campaigns/:id/dm-screen/reveal/:eid` | Scribe+ or DM access | Reveal a hidden character; returns `HiddenRow` |

The downtime buttons post to the armory's own `POST /armory/downtime`
(owner-only in the armory service); its `armory-moved` HX-Trigger makes the
panel re-fetch itself. Reveal only ever un-hides: the adapter checks the
entity's campaign and current state before calling the entities toggle.

The Foundry module reads the same `View` as JSON through the sync API
(`/api/v1/campaigns/:id/dm-screen`, plus reveal and downtime; see the syncapi
`.ai.md`), so `View`'s JSON tags are a wire contract. `Service.SetDowntime`
exists for that path; the site panel keeps using the armory's route.

## Front end

`static/js/widgets/dm_screen.js` (`data-widget="dm-screen"`) owns the overlay
on `<body>`, fetches the fragment on every open, and plays the opening: a d20
rolls out of the button and lands on 20, the folded screen pushes up out of
it, and the faces fall, bounce on the window's bottom edge, settle and fade
(a small hand-rolled gravity loop). One click anywhere or Escape skips it;
`prefers-reduced-motion` gets a fade. Nothing loops. Styles are the
`.dms-*` block at the end of `static/css/input.css`.
