# DM Screen Plugin

## Purpose

The DM Screen is a control panel for the people running a campaign (the
owner and Co-DMs: members the owner has given DM access), opened from a button in the campaign top bar's right-hand icon
row. It shows, on three hinged "leaves" like a paper GM screen:

- **The world**: the downtime switch (armory), the default calendar's date
  and time, today's weather.
- **Time steps**: under the date, three chips ("+1 hour", "+8 hours", "Next
  day") move the default calendar forward. Hours and days are the calendar's
  own (`Calendar.advanceClock` rolls minutes into hours into days with its hours
  per day and month lengths; "Next day" is one calendar day and keeps the time
  of day). Shown only to Owner visibility and only when the calendar is not
  real-time (`WorldView.CanStep`); the calendar service refuses a real-time
  calendar anyway. The chips post `step=1h|8h|1d` to `POST /dm-screen/time`,
  whose `dms-refresh` trigger redraws the panel.
- **Waiting on you** (under the game state): the five oldest requests the
  armory has waiting, stash moves and ask-to-buy purchases together, each one
  plain line with Allow and Refuse. The buttons post to the armory's own
  approve/decline routes, whose `armory-moved` trigger makes the panel
  refetch, so a decided row disappears. More than five shows "N more on the
  Stashes page". Everyone who opens the screen gets the block, as on the
  Stashes page. `View.Requests` carries the same list as JSON.
- **The party**: each claimed character, folded to one line (the first meter
  with a max as a bar, meters without a max as chips, a count of current
  conditions). Clicking folds open the class, player, remaining meters and
  condition names; an open hero is always shown whole, so the list scrolls
  the others aside and grows if one hero alone wouldn't fit.
- **Rules and reveals**: the system's conditions (searchable) and hidden
  NPCs/creatures with a Reveal button.
- **Notes** (a third tab on the right leaf): a textarea labelled "Kept with
  <next game night>" (or "DM Screen notes" with no night) that autosaves about
  800 ms after typing stops and on blur or close, with a status line and an
  "Open in Notes" link. There is one ordinary note per game night in the notes
  widget, visibility gm (owner and co-DMs), titled "<night>: DM notes" when it
  is created and never retitled; with no night it is the campaign's standing
  "DM Screen notes". The note's id is derived (`dmNoteID` in the adapter, passed
  through `CreateNoteRequest.ID`) from the campaign and `NightView.Key` (the
  session id, plus the date when the session repeats, so each occurrence has its
  own note), so the screen finds it with no table or column. Two DMs creating
  at once hit the same primary key and the loser updates the winner's note.
  Text is stored as plain paragraphs, one per line (`note_text.go`). The screen
  never overwrites formatting: a note holding anything but plain paragraphs
  (headings, lists, marks, images, mentions, hard breaks, an old block-style
  note) is shown read-only with "This note has formatting, so edit it in
  Notes", and a save is refused (422). Each save sends the body `version` (a
  hash of the stored body) and is refused with 409 if the note changed since;
  the tab then reloads it and says "Changed elsewhere; reloaded." The check
  runs just before the write, with no lock, so a change in that instant can
  still be lost. A panel refetch keeps the open tab and unsaved note text.

- **Adventures** (a fourth tab, DM team only): a board of cards like the quest
  notice board. A card is either a pinned page of the Adventures category
  (kicker, title, a subtitle from the page's `sessions` and `status` fields) or
  a loose note of at most 500 characters. Up to 60 items. Pressing a page card
  opens the page as a sheet over the screen (`GET
  /campaigns/:id/entities/:eid/sheet`, the entities plugin's chrome-less page
  body); the screen underneath is not navigated or redrawn. "Pin a page" opens a
  search over Adventures pages. A pin stores only a page id: the title and
  subtitle are read through `AdventureSource` on every build, which is
  `internal/app`'s `dmAdventuresAdapter` over the entities viewer filter, so a
  page the viewer cannot open, a trashed page, or one moved out of Adventures
  is left off the tab (its pin stays and returns when the page does). Pins are
  accepted only for pages that source returns, so the board cannot be used to
  surface any other category. Loose notes can be added and deleted, not edited.

A strip above the leaves shows the next game night with its RSVP tally,
"N of M players here", and whether Foundry is connected.

**Who's here.** `View.Presence` counts the campaign's players: members below
Owner who are not DM-granted, so Scribes count as players (the owner and
Co-DMs run the game and are not counted). A player is here when they have Chronicle open in
a browser, or the GM's Foundry client reports them online. "Open in a browser"
is a live browser websocket (`Hub.BrowserUserIDs`) or a campaign page load in
the last five minutes: sockets alone miss ordinary pages, so `campaignPageSeen`
(`internal/app`, an Echo middleware) records successful GET page loads and HTMX
fetches by campaign members in `Hub.MarkBrowserSeen` (in memory, swept after 15
minutes). The Foundry rule needs a linked, online row in a report under five
minutes old while the Foundry socket itself is connected. The section is
omitted with no players. An
open hero's "Played by" line gets a green dot when that player is here
(`HeroView.PlayerHere`).

## Architecture

A view plugin whose only table is the Adventures tab's board
(`dm_screen_board_items`, `migrations/`, slug `dmscreen`; a failed migration
leaves the tab out and the rest of the screen working because `Sources.Board`
is wired only when the plugin is healthy). Everything else it shows it reads:
`service.go` assembles a `View` from the
`Sources` in `sources.go`; each source is an interface implemented by an
adapter in `internal/app/dm_screen_adapters.go` (armory, calendar, sessions,
entities, campaigns, presence, requests, notes) or by an existing type (`websocket.Hub` for Foundry
presence, `systems.SystemHandler.EnabledSystem` for the game system). A
missing or failing source leaves its section out; it never fails the screen.

`Sources.Homebrew` (set in `internal/app/homebrew_drawer.go` while the
homebrew plugin is healthy) returns the Homebrew drawer's content as a
component; the service passes it on to the owner and co-DMs only, and with
it the title bar gets the tankard button. The screen draws the drawer's
frame (`brewDrawer` in `panel.templ`: the name, "See it as a player" and
Close) and knows nothing of what fills it; see the homebrew `.ai.md`.

The game system decides what the party and rules sections show, through the
optional `dm_screen` block in its manifest (`systems.DMScreenDef`,
`internal/systems/manifest_dm_screen.go`): a list of party meters (sheet
field for the value, optional max field, optional warn-below fraction, fixed
label or a label field), the sheet fields for a hero's subtitle (class) and
current conditions (a list, JSON list or comma string of names or
`{"name"}` objects), and the reference category plus property filter for
the rules tab's conditions. Without it the party lists names only and the rules tab is hidden.

## Routes

| Method | Path | Role | Purpose |
|--------|------|------|---------|
| GET | `/campaigns/:id/dm-screen` | Owner or Co-DM | Panel fragment (`Panel`) |
| GET | `/campaigns/:id/dm-screen/notes` | Owner or Co-DM | The note as JSON (`NotesView`) |
| PUT | `/campaigns/:id/dm-screen/notes` | Owner or Co-DM | Save the note text (`{"text": …, "version": …}`), 20,000 characters at most; 409 if changed, 422 if formatted |
| POST | `/campaigns/:id/dm-screen/time` | Owner or Co-DM | Move the date forward one step (`step`) |
| POST | `/campaigns/:id/dm-screen/reveal/:eid` | Owner or Co-DM | Reveal a hidden character; returns `HiddenRow` |
| POST | `/campaigns/:id/dm-screen/hide/:eid` | Owner or Co-DM, checked again in the service | Reveal's Undo: hide the character again; returns `HiddenRow` |

| GET | `/campaigns/:id/dm-screen/adventures/pages?q=` | Owner or Co-DM | Pin picker: Adventures pages the viewer can open, `{pages, has_category}` |
| POST | `/campaigns/:id/dm-screen/adventures/pins` | Owner or Co-DM | Pin a page (`{"entity_id"}`); 404 unless it is a viewable Adventures page; pinning twice is a no-op |
| POST | `/campaigns/:id/dm-screen/adventures/notes` | Owner or Co-DM | Add a loose note (`{"text"}`, 500 characters) |
| DELETE | `/campaigns/:id/dm-screen/adventures/items/:itemID` | Owner or Co-DM | Unpin a page or delete a note |

The downtime buttons post to the armory's own `POST /armory/downtime`
(owner-only in the armory service); its `armory-moved` HX-Trigger makes the
panel re-fetch itself. Reveal only ever un-hides: the adapter checks the
entity's campaign and current state before calling the entities toggle. The
revealed row offers the DM team an Undo for ten seconds (`dm_screen.js`
removes it); Undo only ever hides, and only the NPC and creature types Reveal
covers. The list is the NPC list plus every creature type, so a hidden
monster can be shown mid-fight.

The Foundry module reads the same `View` as JSON through the sync API
(`/api/v1/campaigns/:id/dm-screen`, plus reveal and downtime; see the syncapi
`.ai.md`), so `View`'s JSON tags are a wire contract. `Service.SetDowntime`
exists for that path; the site panel keeps using the armory's route.

## Front end

`static/js/widgets/dm_screen.js` (`data-widget="dm-screen"`) owns the overlay
on `<body>`, fetches the fragment on every open, and plays the opening: a rune
d20 from `Chronicle.dice` is thrown from the button with its value fixed at 20
(`crit: 'none'`, nothing read out), and a beat after it lands it gives way to a
flash and shards of light that fall, bounce on the window's bottom edge, settle
and fade (a small hand-rolled gravity loop), while the folded screen pushes up
out of that spot and its leaves swing open. When the die can't be drawn (Calm,
no WebGL, the dice files late) the screen comes out of the middle instead. One
click anywhere or Escape skips it; `prefers-reduced-motion` gets a fade.
Closing is the opening backwards, in place: the side leaves swing shut over
the middle one, the middle folds down, and the folded screen collapses into a
flash where it stands. Nothing loops. Once the opening ends (not
on screens of 700px or less) the screen becomes a movable window: the dim fades
away and stops catching clicks so the page behind is usable, the title bar
(`.dms-titlebar`: the name, Close, and the game-night strip on a solid surface
of the theme tokens, so the page behind never shows through) drags the screen
(pointer events, kept inside the viewport, applied as the CSS
`translate` property so it composes with the opening's `transform`), and the
offset from the default spot is remembered in `localStorage`
(`chronicle.dmscreen.pos`, try/catch). The opening still plays from the button
and then the window eases to the remembered spot. Clicking outside no longer
closes it; Close and Escape do. Styles are the
`.dms-*` block at the end of `static/css/input.css`. The screen is a tool on
the theme tokens (its `--dms-*` names are only local aliases for them); when
the campaign wears a style kit under the Material page look, the same block
maps the kit's palette, faces, accent and corners onto the overlay, which
sits on `<body>` outside `#main-content` and so would not pick them up.
A co-DM the owner let pick their own kit gets `data-dms-kit` on `<html>`
(campaigns "Who can change"): the same palettes and box rules then apply to
`.dms-overlay` alone, and the page-wide rules step aside through
`:not([data-dms-kit])`. `material` is a real pick that drops the page's kit
from the screen.

The tankard (`data-dms-brew`) opens the drawer beside the leaves
(`.dms-brew-open` widens the screen; under 900px the drawer drops below
them). Its open state and player view live on the widget's state, not the
markup, so a refetch or reopening the screen finds it as it was left, and
its widgets mount on first open because the screen's own mount doesn't run
boot.js's pass. "See it as a player" sets `data-player-view` on the drawer.

`static/js/widgets/dm_sheet.js` (loaded before `dm_screen.js`, exposes
`Chronicle.dmsSheet.open/pick`) draws the page sheet as its own layer on
`<body>` above the screen: the panel grows from the pressed card by a
clip-path (plain when reduced motion is on), Tab is trapped, the screen is
made `inert` underneath, Prev/Next walk the pinned cards, and Escape is taken
in the capture phase so it closes only the sheet. Focus returns to the card
(looked up again, since the panel may have been redrawn) or to the tab. The
Pin picker lives in the same file.

## Files

| File | Purpose |
|------|---------|
| `model.go` | `View` and section view models, `Viewer` |
| `sources.go` | Source interfaces the adapters implement |
| `service.go` | Assembles the view; meters, condition filtering, reveal, presence, request trimming, notes |

| `embed.go`, `migrations/` | Plugin slug and the board table's migration |
| `handler.go`, `routes.go` | HTTP layer |
| `panel.templ`, `hidden_row.templ` | Fragment markup |
