# DM Screen Plugin

## Purpose

A control panel for the people running a campaign (owner and Co-DMs, members
the owner gave DM access), docked at the right edge of every campaign page and
shown or tucked from the top bar's icon row. A rail of section icons sits on the
edge; each opens a card in the column beside it. The sections:

- **The world:** the downtime switch (armory), the default calendar's date and
  time, today's weather.
- **Time steps:** chips "+1 hour", "+8 hours", "Next day" post `step=1h|8h|1d`
  to `POST /dm-screen/time` (`dms-refresh` redraws the panel). Hours and days
  are the calendar's own (`Calendar.advanceClock`); "Next day" keeps the time of
  day. Shown only at Owner visibility and only when the calendar is not
  real-time (`WorldView.CanStep`); the calendar service refuses a real-time
  calendar anyway.
- **Waiting on you:** the five oldest armory requests (stash moves and
  ask-to-buy purchases), each with Allow and Refuse posting to the armory's own
  approve/decline routes (their `armory-moved` trigger refetches the panel).
  More than five shows "N more on the Stashes page". Everyone who opens the
  screen gets the block. `View.Requests` carries the list as JSON.
- **The party:** each claimed character folded to one line (first meter with a
  max as a bar, meters without a max as chips, a count of current conditions).
  Opening shows class, player, remaining meters and condition names; an open
  hero is always shown whole.
  A hero's `HeroView.Level` is the sheet's `level` value, read from the same narrowed
  values as the meters; the screen does not draw it, the AI's `players` lookup does.
- **Rules** (only when the system has conditions): the system's conditions,
  searchable.
- **Reveal:** hidden NPCs/creatures with a Reveal button.
- **Fight** (owner and co-DMs): runs a prepped
  encounter when nobody is in Foundry, or a scene whose Show buttons send
  pages and notes to the players' Table; see the encounters `.ai.md`.
- **Notes:** a textarea labelled "Kept with <next game night>" (or
  "Not tied to a game night" with no night), autosaved ~800 ms after typing stops and on
  blur or close, with an "Open in Notes" link. It is one ordinary notes-widget
  note per game night, visibility gm, titled "<night>: DM notes" on creation and
  never retitled; with no night it is the campaign's standing "DM Screen notes".
  The id is derived (`dmNoteID` in the adapter, via `CreateNoteRequest.ID`) from
  the campaign and `NightView.Key` (session id, plus the date for a repeating
  session), so no table or column is needed. Two DMs creating at once hit the
  same primary key and the loser updates the winner's note. Text is stored as
  plain paragraphs, one per line (`note_text.go`). The screen never overwrites
  formatting: a note with anything but plain paragraphs (headings, lists, marks,
  images, mentions, hard breaks, an old block-style note) is read-only ("This
  note has formatting, so edit it in Notes") and a save is refused (422). Each
  save sends the body `version` (hash of the stored body) and is refused with
  409 if the note changed; the card reloads it ("Changed elsewhere; reloaded.").
  The check runs just before the write with no lock, so a change in that instant
  can still be lost. A panel refetch keeps the open cards and unsaved text.
- **Adventures** (DM team): a board of cards. A card is a pinned
  page of the Adventures category (kicker, title, subtitle from the page's
  `sessions` and `status` fields) or a loose note (max 500 characters). Up to
  60 items. A page card opens the page as a sheet over the screen (`GET
  /campaigns/:id/entities/:eid/sheet`, the entities plugin's chrome-less body)
  without navigating. A pin stores only a page id; title and subtitle are read
  through `AdventureSource` on every build (`internal/app`'s
  `dmAdventuresAdapter` over the entities viewer filter), so a page the viewer
  cannot open, a trashed page, or one moved out of Adventures is left off (its
  pin returns with the page). Pins are accepted only for pages that source
  returns, so the board cannot surface another category. Loose notes can be
  added and deleted, not edited.

A strip at the top of the column shows the next game night with its RSVP tally, "N of M
players here", and whether Foundry is connected.

**Who's here.** `View.Presence` counts the campaign's players: members below
Owner who are not DM-granted (Scribes count; the owner and Co-DMs do not). A
player is here when they have Chronicle open in a browser, or the GM's Foundry
client reports them online. "Open in a browser" is a live browser websocket
(`Hub.BrowserUserIDs`) or a campaign page load in the last five minutes
(`pageSeenWindow`): `campaignPageSeen` (`internal/app/campaign_page_seen.go`, an
Echo middleware) records successful GET page loads and HTMX fetches by members
via `Hub.MarkBrowserSeen`, because sockets alone miss ordinary pages. The
Foundry rule needs a linked, online row in a report under five minutes old
(`foundryReportMaxAge`) while the Foundry socket is connected. The section is
omitted with no players. An open hero's "Played by" line gets a green dot when
that player is here (`HeroView.PlayerHere`).

## Architecture

A view plugin with two tables (`migrations/`, slug `dmscreen`): the Adventures
board (`dm_screen_board_items`) and each person's screen layouts and style
(`dm_screen_prefs`, one row per campaign, user and screen). `Sources.Board` and
the prefs store are wired only while the plugin is healthy, so a failed
migration drops the section, or leaves layouts in the browser, and nothing else. Everything
else is read: `service.go` assembles a `View` from the `Sources` in
`sources.go`, each an interface implemented by an adapter in
`internal/app/dm_screen_adapters.go` (armory, calendar, sessions, entities,
campaigns, presence, requests, notes) or an existing type (`websocket.Hub` for
Foundry presence, `systems.SystemHandler.EnabledSystem` for the game system). A
missing or failing source leaves its section out; it never fails the screen.

- `Sources.Homebrew` (`internal/app/homebrew_drawer.go`, while the homebrew
  plugin is healthy) returns the Homebrew drawer as a component, passed to the
  owner and co-DMs only; the rail then gets the tankard icon. The screen draws
  only the frame (`brewBody` in `panel.templ`: a wrench linking to the
  Workshop and "Player view"); see the homebrew `.ai.md`.
- `Sources.Fight` (`internal/app/dm_fight.go`, while the encounters plugin is
  healthy) returns the Fight section (`encounters.RunMount`), given the system's
  condition names; owner and co-DMs only. See the encounters `.ai.md`.
- `Sources.Decks` (`internal/app/dm_decks.go`, while the decks plugin is
  healthy) returns the Card decks section as a component plus its one-line
  summary (for example "3 decks · 2 drawn"); owner and co-DMs only, and only
  while the Card decks add-on is on for the campaign (the adapter asks the
  add-on service, so an off add-on leaves the section out). The section sits
  after the party, uses the layer-group icon, and its component and summary are
  not on the Foundry wire. See the decks `.ai.md`.

The game system shapes the party and rules sections through the optional
`dm_screen` manifest block (`systems.DMScreenDef`,
`internal/systems/manifest_dm_screen.go`): party meters (sheet field for the
value, optional max field, optional warn-below fraction, fixed label or label
field), sheet fields for a hero's subtitle (class) and current conditions (a
list, JSON list or comma string of names or `{"name"}` objects), and the
reference category plus property filter for the rules section. Without it the
party lists names only and the rules section is left out.

## Routes

| Method | Path | Role | Purpose |
|--------|------|------|---------|
| GET | `/campaigns/:id/dm-screen` | Owner or Co-DM | Panel fragment (`Panel`) |
| GET | `/campaigns/:id/dm-screen/notes` | Owner or Co-DM | The note as JSON (`NotesView`) |
| PUT | `/campaigns/:id/dm-screen/notes` | Owner or Co-DM | Save the note text (`{"text": …, "version": …}`), 20,000 characters at most; 409 if changed, 422 if formatted |
| POST | `/campaigns/:id/dm-screen/time` | Owner or Co-DM | Move the date forward one step (`step`) |
| POST | `/campaigns/:id/dm-screen/reveal/:eid` | Owner or Co-DM | Reveal a hidden character; returns `HiddenRow` |
| POST | `/campaigns/:id/dm-screen/hide/:eid` | Owner or Co-DM, checked again in the service | Reveal's Undo: hide the character again; returns `HiddenRow` |
| GET | `/campaigns/:id/dm-screen/adventures/pages?q=` | Owner or Co-DM | Adventure chooser (Plan a fight): every Adventures page the viewer can open, uncapped, `{pages, has_category}` |
| POST | `/campaigns/:id/dm-screen/adventures/pins` | Owner or Co-DM | Pin a page (`{"entity_id"}`); 404 unless it is a viewable Adventures page; pinning twice is a no-op |
| POST | `/campaigns/:id/dm-screen/adventures/notes` | Owner or Co-DM | Add a loose note (`{"text"}`, 500 characters) |
| DELETE | `/campaigns/:id/dm-screen/adventures/items/:itemID` | Owner or Co-DM | Unpin a page or delete a note |
| GET | `/campaigns/:id/player-screen` | Player or Scribe without DM access, or a DM-team member viewing as a player (`CanOpenPlayers`) | The players' screen fragment (`PlayerPanel`) |
| GET | `/campaigns/:id/player-screen/notes` | As above | The viewer's own note as JSON (`NotesView`) |
| PUT | `/campaigns/:id/player-screen/notes` | As above | Save the viewer's own note (`{"text": …, "version": …}`); same limits as the DM note |
| GET | `/campaigns/:id/screen-prefs/:screen` | See below | The caller's own layouts and style for that screen, as JSON (`PrefsView`: `stored`, `prefs`, `kit`) |
| PUT | `/campaigns/:id/screen-prefs/:screen` | See below | Partial update of the caller's row (`UpdateScreenPrefsInput`); returns the merged `PrefsView` |
| GET | `/campaigns/:id/screen-prefs/:screen/kits.css` | See below | Every kit's faces and accent keyed on the dock's `data-dms-kit` (`layouts.DockKitsCSS`), loaded by the Style drawer |

`:screen` is `dm` or `player` (registered once each, so any other name is a 404).
`dm` needs `CanOpen` (owner or co-DM); `player` needs a member who cannot open
the DM Screen. `ScreenAllowed` in `prefs_service.go` is the one gate, used by
the routes and again by the service; a row is only ever the caller's own.

The downtime buttons post to the armory's own `POST /armory/downtime`
(owner-only in the armory service). Reveal only un-hides: the adapter checks the
entity's campaign and current state before calling the entities toggle. The
revealed row offers the DM team an Undo for ten seconds (`dm_screen.js`); Undo
only hides, and only the NPC and creature types Reveal covers (the NPC list plus
every creature type, so a hidden monster can be shown mid-fight).

The Foundry module reads the same `View` as JSON through the sync API
(`/api/v1/campaigns/:id/dm-screen`, plus reveal and downtime; see the syncapi
`.ai.md`), so `View`'s JSON tags are a wire contract. `Service.SetDowntime`
serves that path; the site panel uses the armory's route.

## Front end

`sections.go` lists the rail's sections in order (`View.Sections`: id, title,
icon, the one-line summary a folded card and the icon's tooltip show, and a
badge count); a section whose source is missing is left out. `View.Waiting`
counts the requests waiting, which badges the world icon and the tucked tab.

`static/js/widgets/dm_screen.js` (`data-widget="dm-screen"`, on the top-bar
button `data-dms-toggle`) appends the dock to `<body>` and fetches the fragment
once per page load, tucked or not, so the tab can carry the waiting count. The
fragment renders every card hidden; the widget shows the open ones. A boosted
navigation swaps only `#main-content`, so the dock stays as it is across pages;
the panel refetches itself on `armory-moved` and `dms-refresh`.

- **Open cards.** Several can be open, each whole or folded to one line
  (`.dms-folded`, the summary in place of the body) on its own: a card's header
  folds or opens only that card, opening another never folds it, and a card
  opened from the rail comes whole and first in the column. Folded ids are kept
  per campaign under `chronicle.dms.folded.<id>`. A rail icon opens its section,
  or closes the one already open. Each card's cross closes it; "Close all"
  closes every card.
- **Moving cards.** A card's grip (`data-dms-grip`; any pointer, `touch-action:
  none`) or, with a mouse or pen, its title dragged past 8px lifts it; a bar
  shows where it lands: before or after another card, at the end of a leaf, or
  at the end of the column. The column lists its newest card first, so
  `st.open` is read reversed there. No phone lines: they keep their fixed order.
- **Phone lines.** On a phone or touch screen (`max-width: 700px`, or
  `hover: none` with `pointer: coarse`; the same query in the CSS and
  `phone()`) there is no rail and no "n open / Close all" row. Every section is
  on screen in `Sections()` order as one line: icon, name, and its summary
  (the folded card's one line), with the waiting count as a badge on the
  world line. A tap on a line unfolds it in place and a second tap folds it;
  several can be open, kept per campaign under `chronicle.dms.lines.<id>`
  (the computer's open order is separate). The unroll is a height animation
  at `--dur-standard`, swapped at once under Calm or Off. A heading with the
  screen's name and a close mark (`.dms-phonehead`) puts the whole screen
  away. Summaries come from what the screen already loads: the Fight line from
  `FightSource.ReadyCount`, the party line from the hero count and
  `Presence`, the Adventures line from the board's pins and notes. Where
  nothing is cheap to count (Homebrew) the line is a plain true phrase.
- **Leaves.** On a computer a rail icon dragged toward the page (pointer
  events, mouse or pen; a touch on the rail still scrolls) swings a new leaf
  out on a hinge at the column's left edge, lying over the page, with that
  section on it. Let go before 35% of the way and it swings shut again. Each
  leaf is 264px (`LEAF_W`); there are at most two (`MAX_LEAVES`), fewer when
  the window has no room, and leaves that no longer fit fold back into the
  column (`fitLeaves`). With every leaf out, an icon dropped on a leaf joins it
  as its last card, the others staying as they were. A
  leaf's bar has Merge (its cards go to the front of the column) and Close
  (its cards close); dragging the bar onto the column or another leaf merges
  it there, and the leaves further out slide in. A plain click on an icon
  still opens the card in the column; on a section that is on a leaf it closes
  it there. Sections move into the leaf's body in the DOM, so a panel refetch
  puts them back in the column and the leaves are drawn again from
  `chronicle.dms.leaves.<campaign>` (an array of section id arrays). The hinge
  is a `rotateY` swing over `--dur-slide` on the slide curve, opacity only
  under Calm, none under Off. On a phone there are no leaves and the saved
  ones are left alone for the computer.
- **Out and tucked.** The rail's top icon, the top-bar button and Escape (when
  focus is in the dock) tuck it to a small edge tab carrying the waiting count;
  the tab hangs 12px below the top of the page area (`#beside-row`), so it clears
  any strip above the page (call-to-action, guest, view-as, check-up) rather than
  sitting in its row, and below the header of a page opened beside, whose close
  mark is at that edge;
  the tab or the button brings it back. Out, it narrows the page
  (`html.dms-docked` gives `#beside-row` and the strips above it a right
  margin). At 700px or less it lies over the page instead, a tap outside tucks
  it, it starts tucked on load, and the tab is not drawn (the button is enough).
- **Remembered** per browser and campaign in `localStorage`
  (`chronicle.dms.out.<campaign>`, `chronicle.dms.open.<campaign>` in open
  order, `chronicle.dms.leaves.<campaign>`, try/catch; the default is The world and The party, tucked).
- **Motion.** The dock slides in and out over `--dur-standard`; Calm, Off and
  reduced motion show and hide it at once (`Chronicle.reducedMotion`).
- There is no single-key shortcut: T belongs to the Table.

A card's widgets (the Fight tracker, the Homebrew lists) mount when the card is
first shown in front, because the dock's own mount doesn't run boot.js's pass.
The Homebrew card's "Player view" sets `data-player-view` on its pane; the
choice lives on the widget's state so a refetch keeps it. The screen draws the card's frame, so the
drawer's own padding is dropped there, and every grid in the card has one
`minmax(0, 1fr)` column so a wide tracker row wraps instead of widening the
card past the column.

### Arrange mode and layouts

`static/js/widgets/dm_arrange.js` (`Chronicle.dmsArrange`, loaded before
`dm_screen.js`) adds Arrange mode, the layout menu and the Style drawer to
whichever screen the dock shows: the widget's `data-screen` (default `dm`)
names it, and every key, route and element id is built from that name, so the
players' screen gets the same. The layout rules are pure, in
`static/js/widgets/dm_layout.js` (`Chronicle.dmsLayout`, tested by
`test/js/dm_layout.test.mjs`); the server checks the same rules again in
`prefs.go`. Without the helper the dock works as before.

- **Arrange mode.** The rail's Arrange icon (or Escape, or Done) toggles
  `.dms-arranging` on the dock. A bar under the column head names the layout
  (", changed" when a saved one differs), switches One/Two columns and has
  Reset to default, which puts Default back to the starting cards and shows
  it; for ten seconds the same button reads "Undo reset" and brings back
  Default and the layout that was on. Each card shows its grip, S/M/L (`data-dms-size`: S and M
  cap the body at 9rem and 18rem and scroll it inside, L is the whole card), a
  "two columns wide" switch and an eye. A hidden card stays in view, tinted
  and last, until Done; then it leaves the column, the leaves and the rail.
  While dragging a card a dashed outline of its shape (`.dms-dropghost`) shows
  where it lands, in the column or on a leaf, and a dashed slot beside the
  screen opens a new leaf. A focused grip (a control only while arranging)
  moves its card with the arrows: up and down in the shown order, left out to
  a leaf, right back in; each move is said in the dock's live region. Phones
  have no Arrange mode and ignore hidden cards.
- **Two columns** need a window of 1180px or more: the dock widens to 528px
  (`html.dms-two` sets `--dms-w`, which the page margin follows) and the cards
  sit in a two-column grid where a wide card spans both. A narrower window
  shows one column and keeps the choice.
- **Layouts.** Default is the person's everyday screen (`home`), always there,
  never stored by that name and never renamed or deleted. Up to eight saved
  layouts are snapshots; switching applies at once. A change made while a
  saved layout is on is held as `live` (the menu offers "Save changes to …");
  switching back to that layout shows it as left. Deleting the layout on
  screen goes back to Default. Names are 1 to 40
  characters with no control characters, never "Default", and unique
  ignoring case.
- **Saving.** Every change goes to the account by a partial PUT of only the
  changed keys (`current`, `home`, `live`, `layouts`, `style`), debounced
  600ms; the server merges them in a transaction, so two tabs changing
  different keys do not clobber each other. `chronicle.dms.prefs.<campaign>`
  is this browser's copy and the dock's own open, folded and leaves keys stay
  its fast cache. With no row stored yet, the browser's screen becomes
  Default's starting point. A failed save keeps everything in the browser and
  says so once; the keys not yet saved are kept beside the copy
  (`<copy key>.pending`), so after a reload they still win over the server's
  copy and are sent again. Where the server refuses the prefs (403: the DM
  team viewing the campaign as a player, whose players' screen prefs are not
  kept), the browser keeps them and says nothing.

### Style drawer

The Style tab at the rail's foot slides a drawer out from behind the screen,
with three rows that apply live and only for this person:

- **Kit**: Follow the campaign, or one of the six kits. It is the member look
  pick for the DM Screen (`campaigns.LookPartDmScreen`, `PUT
  /campaigns/:id/my-look/dmscreen`), so the owner's "Who can change" setting
  holds. Picked here it sets `data-dms-kit` on the dock itself (and on the
  drawer's tiles, `.dms-kt`), which wins over the attribute on `<html>`; the
  page keeps the campaign's kit. Where the person cannot pick, the row says
  the screen follows the campaign's choice; the owner is pointed to Customize,
  where their own pick lives. The players' screen has no kit pick yet.
- **Surface**: Solid, Glass over the page (translucent with a backdrop blur;
  the page no longer narrows for the dock; solid where `backdrop-filter` is
  missing or the device asks for less transparency) or Table felt (green
  baize from two tokens and a faint CSS weave, light and dark).
- **Density**: Roomy or Compact, which changes only the spacing tokens
  (`--dms-gap`, `--dms-pad`).

Surface and density are stored in the prefs row (`style`; Solid and Roomy as
empty). The menu grows from its icon over `--dur-everyday` and the drawer
slides over `--dur-slide`; Calm fades both, Off swaps at once.

Styles are the `.dms-*` block in `static/css/input.css`, on theme tokens
(`--dms-*` are local aliases). Under the Material page look with a style kit,
the block maps the kit's palette, faces, accent and corners onto the dock, which
sits outside `#main-content` and would not inherit them. A co-DM the owner let
pick their own kit gets `data-dms-kit` on `<html>` (campaigns "Who can change"):
the kit's rules then apply to `.dms-dock` alone and the page-wide rules step
aside via `:not([data-dms-kit])`. A kit picked in the Style drawer puts the
attribute on the dock, and the rules keyed on `<html>` step aside for it the
same way (one selector list per kit in `style_kits.css`). `material` is a real pick that drops the
page's kit from the screen.

`static/js/widgets/dm_sheet.js` (loaded before `dm_screen.js`; exposes
`Chronicle.dmsSheet.open/pick`) draws the page sheet as its own layer on
`<body>`: the panel grows from the pressed card by clip-path (plain under
reduced motion), Tab is trapped, the screen underneath is `inert`, Prev/Next
walk the pinned cards, and Escape is taken in the capture phase so it closes
only the sheet. Focus returns to the card (looked up again, the panel may have
been redrawn) or the rail. The Pin picker lives in the same file.

## Players' screen

Players and scribes get a screen of their own: the same dock, opened by the
Table's die in the top bar. It is for members who cannot open the DM Screen,
so the owner, co-DMs and anyone with DM access never see it, except while
they view the campaign as a player. A site admin who is not a member and a guest
preview do not get it. It lives here, not in its own plugin, because it is the
DM Screen's dock, cards, party rows, rules list and note logic with a
different set of sections; `PlayerView` is separate from `View` so the
Foundry wire is unchanged.

The route refuses anyone else (`requirePlayers`, `CanOpenPlayers`) and the
service checks again (`Viewer.CanOpenPlayerScreen`: a signed-in member whose
visibility role is player or scribe). The handler passes a DM-team member
viewing as a player as a player (`playerViewerOf`), so they see only what a
player sees. The screen stays on the page across boosted links, so the Table
asks it to fetch itself again (`pls-refresh`) when it comes out after a page
change or a minute away.

Sections, in rail order (`PlayerView.SectionsIn`), each left out when its
source is missing:

- **My hero**: the viewer's own claimed hero (the most recently updated, when
  they have several): name, class and level, the system's meters with their
  numbers, the sheet's current conditions, and, when the system declares a
  power roll, a Power roll button that opens the Table's roller on Rolls
  (`Chronicle.tableRoller`). The meters are read-only.
- **The party**: everyone else's claimed heroes, folded, as the DM Screen's
  party rows.
- **Today**: the calendar's date, time and weather, read as the viewer, so
  players' audience only; players cannot step the date. Left out with no
  calendar.
- **Tonight**, **Rolls**, **Hand** (only with the Card decks add-on, after
  Rolls), **Dice**: empty boxes (`data-widget="table-leaf"`) the Table draws
  its own sections into; see the rolls `.ai.md`. Hand is there because the
  screen replaces the drawer on a computer, and a player's dealt cards, draw
  invites and the bell's `?table=hand` link open it.
- **Rules**: the system's conditions, searchable, as on the DM Screen.
- **My notes**: one private note per member per campaign.

Security: heroes come from `PlayerPartySource` (`dmPartyAdapter.PlayerHeroes`
in `internal/app/player_screen_adapters.go`), which lists claimed pages
through the entities plugin's `ListClaimed` asked as the viewer, so hidden
pages and pages the viewer cannot open never arrive. Each hero carries the
keys its category and its own page mark GM-only or owner-only;
`playerFields` drops GM-only values always and owner-only values on every hero
but the viewer's own. A hero whose category cannot be read shows no values.

My notes (`PlayerNotesSource`, `playerNotesAdapter`) is an ordinary private
note of the viewer's in the notes widget, so it also shows in their Journal.
Its id is derived from the campaign and the viewer's user id
(`playerNoteID`), never taken from a request, and every read checks the viewer
owns it, so nobody, the DM team included, can reach another member's note
through this screen. Saves work as the DM note's do: plain text only, a note
with formatting is read-only here, and a stale version is refused. The note's
title is set on the first save and never changed.

Front end: `app.templ` puts a hidden element (`data-pls-host`) beside the
Table's button for these viewers, configured for `dm_screen.js` by data
attributes (storage prefix `chronicle.pls.`, name, tucked tab label and icon,
first cards: My hero, Tonight, Rolls, The party). It has no `data-widget` of
its own: the Table names it a widget only on a computer, so a phone never
downloads the dock, and it fetches the panel only when first shown
(`data-dms-lazy`). The die, T and R work it through `el._dmsApi`.

The players' screen is for computers for now. On a phone players keep the
Table's bottom sheet.
