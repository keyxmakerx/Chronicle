# Field rules plugin (homebrew rules and local words)

## Purpose

Two homebrew tools a campaign builds for itself, never part of a game system:

- **Worked-out rules**: a field's value follows something through a table.
  A rule names what it `follows` and has rows, each matching an exact value
  (`is`) or a range of numbers (`from`, `to`, both ends included) and saying
  what it `gives`. The first matching row wins. Example: Guild rank follows
  `echelon`: 1 gives Copper, 2 Silver, 3 Gold, 4 or more Starsteel.

## What a rule follows

| `follows` | Value matched |
|---|---|
| a field key | that field on the same page |
| `moon:<name>` | the moon on the main calendar's current date: `is` matches a phase word (`Moon.PhaseWords`: the phase name, new, full, first-quarter, last-quarter, waxing, waning, crescent, gibbous); a range counts days of the cycle, the new moon's day being 1, and may wrap (23 to 1). A hand-set moon has words but no days |
| `tracker:<name>` | the value of a tracker on the same page (a steps tracker's step index) |
| `time of day` | `dawn`, `day`, `dusk` or `night` (`Calendar.DayPart`) |

Field keys hold no colon or space, so these never collide with one. A row may
also need `eventTag` (an event on today's date with that name, or of a kind
with that slug or name) and `time`; a row with only conditions matches
whatever the rule follows, so a first row "on a Bloodnight, 1" overrides the
rest. `adjust` then changes a numeric result, each step in order while its
page tracker passes `op` against `value`: add `add`, keep within `min`/`max`.
Text results are never adjusted.

`Rule.Result` (pure, `rules.go`) does the matching from a `Situation`.
`Evaluate` fills the situation through `World` only for the facts the asked
rules use (`Rule.Needs`), once per page, **as the viewer sees them**: a moon
hidden from players, an event they can't see or a tracker kept from them is a
missing fact, so a result a player is shown never rests on something hidden
from them. A missing fact matches no row and fails every adjustment. A result
is worked out on every read, so it changes with the calendar's date.
- **Local words**: what one place (a page) or one era calls a word. Saltreach
  calls a Mark "Grain"; the Reign era calls it "Bit".

A category field of type `rule` shows its rule's result; a field of type
`link` points at a page of another category. Both field types live in the
entities plugin (`field_kinds.go`, see its `.ai.md`); this plugin only keeps
the rules and words and answers what applies.

## Which local word a page sees

`ChooseWords` (pure, `rules.go`):

1. The nearest place wins: the page itself, then its parents, up the tree.
2. A place beats an era. An era applies only while it is the current era of
   the campaign's main calendar, and a secret era never applies for a player.
3. A word kept DM only counts only for the Director.

`Rename` matches a value ignoring case, or its plural made with a trailing
"s" ("Marks"). Boot's `Chronicle.localName` mirrors it for widgets.

## Who may do what

Only the Director (or a granted co-Director, `Viewer.IsDM`) lists, adds,
changes or removes rules and words, and the route group's `directorOnly()`
refuses everyone else first. Pages read results for any viewer through
`Evaluate` and `WordsFor`, which never fail: a read error is logged and the
page shows stored values.

## Schema notes

- `local_words.scope_key` is `p:<page id>` or `e:<era id>`, so one unique key
  allows one local name per word per place or era. `place_id` cascades on the
  page's removal; `era_id` has no foreign key (eras are the calendar's), and a
  word whose era is gone never applies and is left out of lists.
- A rule's rows are JSON: always read and written whole, at most
  `MaxRuleRows`.

## Routes (JSON)

All under `/campaigns/:id/homebrew`, Director only.

| Method | Path | Does |
|--------|------|------|
| GET | `/rules` | every rule |
| POST, PUT | `/rules`, `/rules/:rid` | add, replace a rule (`name`, `follows`, `rows`, `adjust`) |
| DELETE | `/rules/:rid` | remove a rule; its fields keep values typed by hand |
| GET | `/words` | every local word |
| POST, PUT | `/words`, `/words/:wid` | add, replace (`word`, `local`, `placeId` or `eraId`, `dmOnly`) |
| DELETE | `/words/:wid` | remove a word |

A page's words for viewers are served by the entities plugin at
`GET /campaigns/:id/entities/:eid/local-words`.

## Homebrew Workshop parts

`internal/app/fieldrules_homebrew_adapters.go` registers three kinds of part
with the Workshop (`internal/plugins/homebrew`), so a recipe or a saved
layout can carry these tools. Each part's data is checked to the same limits
as a saved rule or word and normalised.

Saving a recipe saves what its parts describe (`fieldrules_homebrew_sync.go`,
the kinds' `PartSync`): each field joins its category's sheet or updates the
field with the same key, a worked-out field's rule is saved under the field's
label (replacing a rule of that name), and words replace that place's or era's
word. Sync only adds and updates: removing a part or deleting a recipe leaves
its fields, rules and words for the Director to remove by hand. A field the
sheet already has keeps its type; a part that would change it is refused, since
typed values would be read differently. A words part with neither place nor era
is a template and saves nothing.

| Part | Data |
|------|------|
| `field` | `category` (a name) and one field: `label`, optional `key` (else made from the label), `type`, `section`, `options` (select), `linksTo` (link: a category's name), `director`, `rule` (`rule` type only: `follows`, `rows` and `adjust`, named after the field) |
| `item` | `category` and `fields`, a list of the same field shape, keys unique |
| `words` | `words` (`word`, `local`, `director`) and at most one of `placeId` (a page of this campaign) or `era` (a name); neither while it is still a template |

Categories and eras are named, not numbered, so a layout still works in
another campaign; a place is a page, so it is a page id.
