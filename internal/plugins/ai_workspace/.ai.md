# ai_workspace plugin

The owner's AI tools. The AI button in the top bar of every campaign page drops
the AI bubble: Copy and Paste answer, then the connected AI's requests for changes,
each reviewed in the AI panel (a side sheet). "Write a request…" opens the
copy-and-paste tool there (a markdown export of the campaign (`aiexport/`), prompts,
and an importer that writes AI-authored markdown back as pages and records,
create / update / delete per front-matter `action:`). The "Your AI" Manage page
(`/campaigns/:id/ai`, sidebar `manage:ai`) keeps setup and history: connecting an
AI app straight to the campaign (`connector/`), its warnings, and what it did.

A **plugin** under `internal/plugins/ai_workspace/`. It depends on other plugins'
lister interfaces through `aiexport/` and exports nothing to them. The connector
endpoint sits outside the campaign group, under `/api/`.

Tables: `ai_import_parts` (parts of a split answer, waiting or applied),
`ai_import_blocks` (a fingerprint per applied block) and `ai_note_access`
(owner's switches for shared notes), under migrations slug `ai_import_memory`
(`MemorySchemaSlug`), so a failed migration leaves out only those. The connector's
tables are under `ai_connector` (see `connector/.ai.md`).

## The review screen

One list of what the AI asks for, answered Yes or No, then Apply (styles in
`static/css/ai_review.css`, a workshop on the theme tokens). Blocks that can't be used (a parse error, a record whose plan
is an error) sit in a problems box on top with their block number and are
never offered as rows. Rows are grouped: Pages, then records by kind in the
order each kind first appears; on-screen order never changes the form's
`page_N_*` / `rec_N_*` indexes. Each row ends in a radio pair named
`page_N_include` or `rec_N_include` (`on` is Yes, `off` is No).

- Removals start on No, as do page rows the classifier marks
  `StatusActionMismatch` or `StatusParentProblem`. In the review of a
  connected AI's request, changes to existing pages and records start on No
  too (`pageStartsYes` / `recordStartsYes`); everything else starts on Yes.
- A removal's "for good" tick shows only while the row is answered Yes, and
  the review's script (`static/js/widgets/ai_import_review.js`, loaded on
  sight by the `ai-import-review` mount) makes it `required` then. The
  committer re-checks it either way.
- `reason:` (any block) is the AI's one-line why, shown as "AI's reason". It
  is never saved: the parser knows the key and `system-entry` reserves it.
- A page's name, action, category, visibility and conflict mode fold under
  "Change the details"; the defaults for every page fold under a quiet word.
- A connected AI's request is applied once: Apply checks it is still waiting before
  writing anything (a second Apply from a double click or another tab is refused), and
  the form drops a second submit while one is in flight (`hx-sync="this:drop"`).
- J/K move between rows and Y/N answer, never while typing. The save bar
  counts Yes answers (a GM-only row counts once its tick is on) and removals.

## Wiring

`/campaigns/:id` (`auth.RequireAuth` + `campaigns.RequireCampaignAccess`) with

(`SetConnector`) and mounts `connector.RegisterRoutes`; otherwise the page offers
copy and paste only. The backup export/import stays on Settings' Data tab; an old
`?tab=ai-workspace` link redirects here (`campaigns.settingsTabRedirect`).

## Sanitization

Every export HTML field goes through `aiexport.htmlToMarkdown`, which applies
`sanitize.HTMLPtr` first (AST pin `TestRenderers_FunnelThroughHtmlToMarkdown`,
`aiexport/renderer_test.go`). On import every entity mutation goes through
`MarkdownToHTML` before `creator.Create`/`Update`; `commitDelete` is exempt (no
body). Pinned by
`TestCommitter_EntityMutationsFunnelThroughMarkdownToHTML`
(`importer/committer_sanitize_test.go`).

AI Export/Import is a separate, intentionally lossy surface; the lossless backup
pipeline (`internal/app/export_adapters.go`,
`internal/plugins/campaigns/export_handler.go`, `internal/plugins/restore/`) is not
touched by it.

Parser, converter and committer errors are human wording; library prefixes
(`yaml:`, `goldmark:`, `goquery:`) never reach the UI (`importer/parser.go`
`humanizeYAMLError`); detail is kept with `%w` for slog.

## Import: action verbs and conflicts

Front matter `action:` is `create` (default), `update` or `delete`.

| Action | Required FM | Body | Behavior |
|---|---|---|---|
| `create` | `name` (or H1) + `type` (or bulk default) | Required | New entity; conflict-mode dropdown on slug collision |
| `update` | `name` (or H1) | Required | Load by slug, replace metadata + body |
| `delete` | `name` (or H1) | Ignored (warning if present) | Load by slug, `EntityService.Delete` (soft vs hard is the entities plugin's) |

Conflict mode on `create`: `skip`, `rename` (default, `(Imported)` suffix),
`update` (replace). Only a `create` row's line under the name says the page gets a
new name (`renamesOnConflict`).

- Blocks split on their `---` lines (`importer.splitPages`). A textless block
  followed by a single `---` and another block's keys (a `kind:` or `name:` line,
  then a closing `---`) is read as two blocks, so a shared fence never makes the
  second block the first one's text. A first line `# Name` repeating the page's
  name is dropped (`dropTitleHeading`).
- Each `action: delete` row needs the "I understand X will be permanently deleted"
  checkbox; the committer re-checks `DeleteConfirmed`.
- An update (explicit, or a create resolved to `update`) over a page whose text has
  GM-only parts is skipped unless the row's "Replace the text anyway" tick
  (`page_N_replace_gm_confirmed`) is set. GM-only pictures and diagrams never come
  back through markdown, so they always count; table rollers count when the
  incoming text has fewer. A GM-only passage counts only when the incoming body
  does not carry it back: `importer.GMOnlyPartsAfter` compares the page's passages
  with the body's `{gm{…}gm}` passages as a multiset on words. A safe-mode export,
  a dropped, unmarked or edited passage counts as lost, so a page exported without
  its secrets stays protected. The classifier sets `Classification.GMOnly` for the
  review callout; `commitUpdate` re-measures the live page and enforces the tick
  before any write.
- The paste box shows no counter; a warning appears near the 5 MB cap
  (`importBodyCap`).

## GM-only passages in page bodies

Marker `{gm{text}gm}` (`importer.SecretOpen`/`SecretClose`), documented in the
import prompt. The editor's secret is an inline mark, so one pair covers one
paragraph; longer secrets repeat the pair. An unclosed opener hides only the rest
of its block (fails closed).

- **Import:** `MarkdownToHTML` turns markers into `<span data-secret="true">`
  (`convertSecretMarkers`: a tokenizer pass after goldmark, skipping code, and
  closing/reopening inline tags that straddle a marker so no tail leaks); `htmlconv`
  turns the span into the editor's `secret` mark. Only the owner tier (owner or
  co-DM, via `VisibilityRole`) may write it; others get `ErrSecretNotAllowed` and
  the row fails. With no page-link resolver (records), markers stay literal.
- **Export:** `htmlToMarkdownWithSecrets` writes markers in the director's modes
  (permitted, everything); safe mode strips passages first. Every conversion breaks
  literal marker text with a zero-width space, so a marker in an export is always
  one the export wrote. Other `htmlToMarkdown` callers (notes, session text,
  events) flatten passages to plain words.

## Table rollers in page bodies

The editor's rolling-table roller (`/roll`, saved as `<div class="ce-roll
ce-roll--t-<table> ce-roll--n-<1|3|5>">`, stripped for players with other GM-only
parts) is a line of its own: `{roll{Table name|3}}`.

- **Export:** `rollerRule` writes a stand-in that `convertToMarkdown` turns into the
  line in director modes and drops otherwise; literal `{roll{` is broken with a
  zero-width space. The table is named from `Options.RollTableNames`
  (`Service.RollTables`, or the `page` lookup's own read) when import will read the
  name back as that table, else by id.
- **Import:** `linkRollers` runs inside `MarkdownToHTML` for page and era bodies
  only (`WithGMOnlyPassages`) and only for the owner or co-DM. A name resolves
  against `PageLinks.SetRollTables`: campaign tables by name or id plus the paste's
  ticked `kind: table` creates/renames with the ids Apply will give them
  (`Registry.RollTableIDs`). Built-in tables live in the browser, so an id the page
  being replaced already rolls is also accepted (`WithKeptRollers`): a roller on a
  starter table can stay or move, not spread. Anything else stays text with a
  review warning (`RollWarnings`), as does a roller inside other text. `htmlconv`
  turns the div into the editor's `rollTable` node.
- `GMOnlyParts.Rollers` counts rollers the incoming text has fewer of, so a rewrite
  that drops one needs the "Replace the text anyway" tick.

## Import: page-block keys

### Sub-pages (`parent:`)

`parent: <page name>` on a create or update puts the page under an existing page or
one created earlier in the paste (matched by slug, like every name here). Update
follows the partial-update contract: absent keeps the page, `parent: none` lifts it
to the top level (`patch.Null`), a name moves it. The classifier (`checkParents`)
marks a missing, self, later-in-paste, deleted-in-paste or duplicated-in-paste
parent `StatusParentProblem` with a plain-words `Reason`, default-excluded. The
committer resolves the parent (`resolveParent`) against pages saved earlier in the
commit (so renamed rows work), then the campaign, and passes `ParentID` to
`EntityService.Create`/`Update`, which owns the same-campaign and cycle checks (its
400 shows on the row). An unsaved parent fails only that row. The AI sees the tree
through `Lookups.PageIndex`, the `pages` lookup (`Name (in Parent)`) and the export
(`**Parent:**`); a parent outside the reader's visible set is never named.

### Folders (`folder:`)

`folder: <name>` files the page in that sidebar folder of its own category (case
-insensitive; two folders with one name are refused). Absent keeps it, `folder:
none` takes it out. `parent:` and `folder:` with real names together are a parse
error: a page sits under a page or in a folder, never both
(`entities.FolderService.SetEntityFolder` clears the parent; a page gaining a
`parent:` on update leaves its folder).

The committer resolves the folder before writing (`resolveFolder`), so a missing or
ambiguous folder fails only that row and creates nothing; filing runs after the
page is saved (`applyFolder`), like tags. The classifier (`checkFolders`) marks a
missing folder `StatusParentProblem` ("Parent or folder problem") unless a `kind:
folder` create or `rename_to` in the paste makes the name; when another category has
a folder of that name the reason names it (`foldersElsewhere`). A connected AI hears
the same slip when it asks (`Handler.ConnectorCheck`, run by
`connector.Service.Ask`): `Classifier.NewPageFolderSlips` looks up categories and
folders, never pages. For a key that reads as the owner (any privacy but Safe) the
same check also plans every record block as the owner, as the review screen does,
and sends back each one the review would mark unusable, with its reason and any
switched-off feature (`Handler.recordProblems`), so a broken recipe or bench never
reaches the review. A Safe key, which reads as a player, gets the folder check
alone, so a refusal cannot reveal whether a hidden page exists. Each name is looked up once per request
(`Classifier.folderSeen`) and the check stops after a few slips. Folder blocks that
create or change a folder commit BEFORE pages (`commitEarlyFolders`); other records
commit after; a folder removal commits last. The export writes `**Folder:** Name`
under a filed page (`Options.FolderNames`, from `FolderNamer`); the `pages` lookup
and prompt page index read `Name (in folder Gods)`.

### Tags (`tags:`)

`tags:` sets the page's tags (`Committer.applyTags`, `tags.TagService`). A name
matches a campaign tag by slug (`tagSlug`, the tags service's rule); no match
creates one. Absent keeps tags, `tags: []` clears, a list replaces. An update always
keeps GM-only tags (a Safe export never showed them). A page saved whose tags could
not be set is a failed row that still links the page.

### Category (`type:`)

The classifier (`ensureTypes`) matches `type:` against category slugs first, then
the slugified plural name, so `race` and `races` find the same category unless
another category's slug is that word. No match creates a category; the committer
derives singular and plural names from the slug (`categoryNames`) without
re-pluralizing a plural-looking slug.

### Pages by era (`era:`, `known_as:`)

`era: <era name>` writes that era's version of the page `name:` names, never the
usual page. The era matches by name, ignoring case, among the main calendar's eras
as the importing owner sees them. `known_as:` sets the page's name in that era; a
parse error without `era:`. A non-empty body becomes the version's text; an empty
body leaves it. `create`, `update` and no action all mean "write the version"
(created if missing); `action: delete` removes only that version and needs the
delete confirmation. `type`, `subcategory`, `visibility`, `parent` and `tags` are
ignored on an era block, with a warning.

The classifier (`checkEras`) marks a row `StatusActionMismatch` with a `Reason` for
an unknown era (listing the eras that exist), an unwired writer, or a page that
neither exists nor comes earlier in the paste in a block without `era:`. The
committer (`commitEra`) re-resolves the era, finds the page among rows saved earlier
then the campaign, runs the body through `MarkdownToHTML` and `htmlconv`, and hands
it to `EraWriter.WriteVersion`; the calendar plugin's `EraVersionService` sanitizes
again in `SaveEntry`. The outcome is `StatusUpdated` with a reason such as "Wrote
the Age of Ash version". Era rows never count as the page for `parent:`, links or
the relink pass. `EraWriter` is wired by `internal/app/ai_workspace_era_adapters.go`;
unwired, era blocks are refused. The review shows an "<Era> version" pill.

Export: in Owner view and Everything modes each page is followed by one block per
era version (`name:`, `era:`, `known_as:` when the version has its own name, then
text); eras the exporting viewer cannot see are left out. Safe mode exports the page
as players see it now, with the current era's version replacing the usual page and
no other version.

### Page links (`@[Name]`)

Any markdown body (pages, `note` and `event` records) may write `@[Page Name]` or
`@[Page Name|shown text]`. `MarkdownToHTML(body, WithPageLinks(links))` rewrites it
in rendered text nodes (never in `<code>`, `<pre>` or an existing `<a>`), before
`sanitize.HTML`, into the anchor `internal/pagelink` builds (`data-mention-id`,
entity href, `data-entity-preview`: the same as an editor @mention, so hover card,
click-to-preview and backlinks work). Without the option the text stays as written.
`@[Name]` shows "@" plus the page's own name; `@[Name|text]` shows the text.

`importer.PageLinks` resolves by slug: pages this commit already saved, then the
campaign, and only pages `CheckEntityAccess` lets the viewer open. An unresolved
name stays plain words. A page linking a later page in the paste is written once,
then again after the last row (`relinkPending`) through `UpdateEntry`, so editor
JSON, `entry_html` and backlinks stay in step. The review warns per row for a name
found in neither campaign nor paste (`LinkWarnings`; records: `Plan.Warnings`); it
never blocks. Records commit after pages and resolve against the campaign.

Export writes a mention anchor as `@[Name]` (`aiexport.mentionRule`) so the AI sees
links it can send back; the prompt teaches the syntax. A table exports as a Markdown
table (`aiexport.tableRule`: first row as header, one-line cells with escaped pipes,
short rows padded), which reads back on import.

### Sheet fields (`fields:`)

`fields:` sets values on the page's sheet by field key. The entity service saves any
map it is given, so `importer.CheckFields` is the only gate: every key must be in the
category's `Fields`, and each value must fit the type (number, yes/no, a pick-list
option, http(s) address, or text). A list or map goes into a text field as JSON text,
which is how a system's sheet keeps structured data (Draw Steel's `traits`,
`abilities_json`, `villain_actions_json`). A null clears a field.

- The classifier checks against the category the row will have: the page's own on an
  update (an update never changes category), the front matter's on a create. A
  non-fitting row is `StatusFieldProblem` (problems box); a good row shows a "Sheet:
  ..." line. A new category or an era block cannot take fields.
- The committer checks again against the final category before any write. A create
  saves the map as `FieldsData`; an update leaves `FieldsData` absent on `Update` and
  calls `MergeFields` with only the named fields.
- A good row whose category a game system made carries `SheetKind` ("creature" for a
  creature type or sub-type, else the preset category), `SheetFields` (the sheet as
  the row leaves it) and `SheetWritten` (keys the AI wrote), and mounts
  `import-sheet-check` (`static/js/widgets/import_sheet_check.js`). That hands them to
  the system's `Chronicle.sheetChecks[kind]` (`docs/system-package-rendering.md`):
  each number the AI wrote shows beside the published formula's value, and "Use the
  formula" fills the hidden `page_N_sheet_formula` with the system's patch. Commit
  lays it over `fields:` with `importer.UseSheetFormula` (replaces only keys the AI
  wrote), then checks the result like any other. With no such check the mount is
  empty.
- The prompt lists each category's fields in the shape `CheckFields` accepts
  (`prompt.fieldLines`). `prompt.Service.Notes` (`aiFieldNotes`,
  `internal/app/system_sheet_fields.go`) adds the system's word on a field: its
  manifest `format`, and on the hero sheet "Foundry keeps this one" for a field
  Foundry reads off the actor's items or never takes back. A field on a system-sheet
  category that is not the system's (the starting set's `race` or `challenge_rating`
  in a Draw Steel campaign) is marked "Not a <system> field; fill it only when I ask
  for it".
- **Export:** the sheet is one "Sheet fields" line in the category's order
  (`aiexport.sheetLine`). Safe mode leaves out GM-only and owner-only fields
  (`entities.FilterRestrictedFields`); a link field and a value over 200 characters
  are named and left to a `what: page` lookup; an undeclared key is never written.
- Categories a system's sheets live on carry the system's fields: the
  player-character list's types get the character preset's, creature types the
  creature preset's (`addSystemSheetFieldsOnce`, once per site, adds only missing
  keys). Import writes only declared keys, because GM-only hiding reads the
  category's field list.
- A `link` field takes a page's name; the committer turns it into the id
  (`importer.LinkFields`) with the `@[Name]` resolver, so only pages the operator can
  see, and a page this paste makes must come before the page linking to it. The
  entity service checks the category at write. A `rule` field takes hand-typed text.
- A `page` lookup ends with the page's sheet as a `fields:` block, filtered by
  `entities.FilterRestrictedFields`, so the AI can read a stat block, change it and
  send it back. When the layout has a Page map block holding a map, the answer then
  ends with `### Map` (the `page-map` grammar, filtered for the reader); for a
  Director also `### Quest notice` (the `quest` block) and `### Notice boards` (each
  `notice-board` block on the page), as `QuestKind.Export`/`NoticeBoardKind.Export`
  write them.

## Import: answers in parts

An AI splitting a long answer over several pastes starts each with a `kind: part`
block: `name` (same on every part), `part` (from 1), `of`, and `needs` (earlier parts
it relies on); the prompt teaches it ("If your answer comes in parts").
`importer.TakeParts` removes the labels before lookups and review; each other block
belongs to the label above it. An unreadable label is a parse error and its blocks
count as unlabelled.

- Several parts pasted together are ordered first (`importer.OrderParts`: each
  answer's parts by number, answers in first-seen order); the reordered text becomes
  the review's `markdown_source`.
- **Tray.** When a paste holds parts of one answer and it is not complete
  (`importer.AnswerMissing`: every part 1 to the largest `of`, plus every `needs`,
  pasted, waiting or applied), `trayStep` stores each part's text
  (`importer.PartTexts`) in `ai_import_parts` with `markdown` set, and the parse
  returns `TrayNotice` ("2 of 3 in", which parts next) instead of a review. The tray
  (`import_tray.templ`, from `GET …/import/tray`) lists each waiting answer with
  "Review what's here" (posts `tray_review` = the answer key) and "Empty" (`POST
  …/import/tray/clear`).
- When a paste completes the answer, waiting parts and paste are joined, ordered,
  held to the 5 MB cap and reviewed once. A paste with parts of several answers skips
  the tray and is reviewed as pasted.
- Commit marks a label in its `markdown_source` applied (`applied_at` set, `markdown`
  cleared) once at least one of its blocks was applied; a review answered No
  throughout leaves the parts in the tray. A review still lacking a part it needs
  says which in a note box (`checkParts`, `partNote`); nothing is held back.
- Without the tables (`SetImportMemory` unwired) labels are read and shown but
  nothing waits in a tray.

## Import: a paste applied twice

Every block a commit applies (created, renamed, updated, removed) is remembered as
`importer.BlockHash`: the SHA-256 of its text with line endings and trailing spaces
evened out; the text itself is never kept. The review looks the blocks up
(`repeatedBlocks`): a repeated row says "Already applied on <date>", starts on No and
carries `data-air-hold`, so "Yes to all" skips it; a repeated block the review
refuses (the thing it makes exists now) says the same in the problems box. A box on
top says the whole paste, or how many blocks, were applied before. Tray parts were
never applied, so they never count as repeats.

**Planning and commit.** Each record is planned at parse time (`Kind.Plan`: one
summary line, or an error that blocks the row) and re-planned inside `Kind.Apply` at
commit, so nothing the review showed is trusted. Records commit after pages, so a
record may name a page created in the same paste; `Record.Made` (the paste's page
slugs) lets a plan skip the "not a page yet" warning. A record's action is fixed by
the markdown (no per-row override); a delete needs its own `rec_N_delete_confirmed`
tick, re-checked by `commitRecords`. Kind names match ignoring case with `_` and `-`
alike (`roll_night` = `roll-night`).

Records are planned in order (`Registry.PlanAll`) and committed in the same order. A
kind whose row makes something later rows may name is `aiplug.Staged`: after a row
plans cleanly, `PlanAll` plans the rest with the context its `Stage` returns. A
row that makes a folder or map lets later rows name it. A `calendar` create row, or
an update with `main: true` that switches the main calendar, hands that calendar to
later rows, so their dates are checked against it before it is main. A row needing a
calendar and finding none says "Needs a calendar first"; the review counts it as
"can't be imported yet", not a parse error, and names the block that fixes it
(`action: create`, or `main: true` when calendars exist but none is main). A calendar
update's list (months, weekdays, seasons, moons) replaces the whole list, matching
moons and seasons by name so ids and left-out keys survive; a moon hidden from
players is never removed (a player-safe export never lists it); kept seasons follow
their months by name. Eras merge by name.

**Moon/era `page:`** names the page that tells of it (the calendar's link). It
resolves by slug against the campaign (`calendarai.PageResolver`, `aiCalendarPages`
in `internal/app`) and must be a page the
operator can open; a name matching no page, or only an unseen one, is refused at
review with the same words, so a refusal never confirms a hidden page. On update a
name replaces it, `page: none` clears it, a missing key keeps it (partial-update
contract: `MoonInput.LoreSet`, a `patch.Field` on `UpdateEraInput`). On create it
rides on the new calendar's moons and eras; the services check again. The calendar
export and `what: calendar` show the page by name as the privacy mode's viewer may
see it.

**Event `repeat:`** takes the calendar's `RecurrenceTypes`. `repeat: rule` builds a
`calendar.RecurrenceRule` from `repeat_on` conditions naming moons, weekdays,
months, seasons and events (translated to ids here, parsed by
`calendar.ParseRecurrenceRule` at review; the service judges it on save). Naming a
repeat on update replaces the whole repeat; omitting the keys keeps it.

**Visibility words.** A page takes `public`, `private`, `dm_only`, and `everyone`
(read as `public`). Events, pins and map sketches take `everyone` or `dm_only`, and
also `public` and `private` (`Record.Visibility`). A note's `share:` (private, gm,
party) is who it is shared with, a different thing; a Player Note's `share:` takes
private, gm, gm-scribes or everyone.

**Switched-off features.** A feature switched off in Game & features redirects its
pages to the dashboard, so what an import made there would be out of the owner's
sight. `Handler.SetFeatureGate` (`aiFeatureGate` in `internal/app`, over the same
add-ons the routes check) names them by kind (`records.OffFeatures`): Calendar off
rules out `calendar`, `event`, `weather`, `roll_night`, `moon`, `game-night` and every
`generator` run but names; Game nights off rules out `game-night`; Maps off rules out
`map` and `pin`; Crafting off rules out `recipe`, `material`, `drops` and `bench`; the
Armory off rules out `shop-room`, `storefront` and `item-look`. The prompt leaves those kinds out (`Registry.Without`) and says
which are off and where to turn them on; review refuses such a row with
`OffFeatureReason`, and commit refuses again. A failed add-on check counts as on.
"Copy AI instructions" stays unfiltered (saved once for every campaign).

**`house-rule`.** The chapter is in front matter in the book's chapter-file format
(`intro`, `director`, `pages` with the book's blocks), checked by
`systems.ParseHouseChapterDraft` (the editor's rules). With `pages` it is written in
one step by `BookEditService.WriteHouseChapter` and an update replaces every page of
the chapter; without, only the chapter's own lines change (an old-style body is still
the intro). The plan warns about pages a replacement drops and Director-only parts it
loses, and carries `Plan.Preview` (the chapter as a one-chapter book), which the
review row draws with the rulebook reader (`data-book-json`). Export is each chapter
in the same format, in the privacy mode's view.

**Permissions.** Routes are owner-only. Kinds additionally apply the UI's capability
rules from the operator's `Actor` (hidden events and pins, weather, rolling tables and
house rules need `CanAuthorDmOnly`), and services keep their own checks. `note` writes
only notes `IsOwnedBy` the operator, and `player-note` only Player Notes the operator
wrote, each checked on the list and again on the stored note before a write. The one
exception is a Journal note or jot a co-DM or Scribe shared with the operator, when
the owner turned on that switch on the Your AI page; Apply checks on the stored note
that the operator can view it, that the switch is on for its writer (a co-DM is a
member with the DM grant, a Scribe holds the role without it, anyone else or anyone
who left counts as a player), and that nobody else holds its edit lock. The export's
Notes category is the operator's own notes only. The `notes` and `note` lookups read
more: everything the operator can open in the Journal and Jot notes (`JournalAPI`,
`aiJournalAdapter` over the notes widget's `ListVisible`) and the Player Notes whose
audience admits them (`entity_notes.Service.ListInCampaign`, only while that add-on is
on), including others' shared notes (players' game night entries shared with the DM),
marked with their writer and read-only. A note its writer keeps private is never
listed.

**Generators** exist only in the browser (`static/js/widgets/chronicle_gen.js`). A
generator row carries its plan (generator, calendar, scope, seed) in `data-ai-gen`;
on Import `markdown_importer.js` runs each plan and writes the result to
`rec_N_generated`. `GeneratorKind.Apply` treats that output as untrusted: capped,
checked against the plan's scope, written through the same services. Generated
weather is saved as `generated`, so it never replaces a day set by hand or locked. A
weather plan also carries the calendar's climate, continuity and the owner's own
weather kinds (`GeneratorKind.Weather`) as the weather sheet runs it; the row's
`climate` and tuning keys override them for that run. The engine follows the
calendar's seasons from the calendar JSON in the plan.

## Prompts

Every prompt but "Copy AI instructions" starts with today's real date and, when the
calendar is on and has a main calendar, its current date as the reader may see it
(`Lookups.WorldToday`, from the plugged lookup that is `aiplug.Dated`: the
calendar's). Every prompt opens with:

- "What you can do" (`Registry.Capabilities`: one line per wired kind, including the
  own-notes-only rule; `TestAIKindsEachHaveABrief` fails a kind with only a label);
- "If you need more": ask with lookup blocks instead of guessing what exists, and
  `what: format` for a kind's exact format (a `NEED:` list when lookups aren't wired);
- "What already exists" (`Lookups.PageIndex`): page names per type, at most 40 a type
  and 8 KB, in the chosen privacy mode.

The format section lists every kind (`Registry.Docs`) when the front-matter example is
on. The export's "Rolling tables, map pins, house rules" box and the prompt's "All
visible" content add `Registry.ExportAll`. Content choices:

- "House rules" (`prompt.ContentHouseRules`): the house-rule format and today's rules,
  never the world export.
- "Calendar" (`prompt.ContentCalendar`): the formats of `records.CalendarKinds`
  (calendar, event, weather, generator; `Registry.DocsFor`) and the `calendar` and
  `weather-kinds` answers in the chosen privacy (with no main calendar it says how to
  make or choose one), never the world export.

All follow the privacy mode: Safe (default) lists records as a player sees them
(`exportActor`), so hidden pins, rolling tables and Director-only rules stay out.
Events are listed only by the Calendar events category.

**Standing instructions.** "Copy AI instructions" (`GET …/ai-workspace/prompt/instructions`,
`PromptInstructions`) copies the standing half as plain text (`prompt.InstructionsOnly`):
every kind's format, the lookups, the page format and the campaign's page types; no
page index, export or request. Ticking "My AI already has the instructions"
(`instructions_saved`, `prompt.InstructionsSaved`) leaves those out of a generated
prompt, keeping the index, chosen content and request.

## Lookups

A `kind: lookup` block asks a read-only question (`what:` plus a name or date range;
`Lookups.LookupDoc` lists them): pages, page, table, pins, stock, inventory, notes,
note, house-rules, system-entries, tags, encounters, tests, foundry-monsters,
waiting, players, crafting, scenes, then the lookups features plug in
(`Lookups.Plugged`, `aiplug.Lookup`: calendar, weather-kinds, events and weather
from `calendarai.Lookups`, then game-nights), then format. `format` returns one kind's own doc from the registry
(`Lookups.Kinds`), keyed by `block:` since `kind:` is the lookup's own.

`ParseImport` takes lookups out of the paste before review; if any, it answers with
`records.Lookups.Answer` and returns `LookupAnswer` instead of a review (other blocks
counted as left out). Nothing is written. The form sends the privacy choice as
`lookup_privacy`; the answer says which it used. Caps: 20 lookups, 300 lines and 24 KB
each, 120 KB in all. The connector's tools are these lookups, one per tool, with the
same privacy and caps; a plugged lookup's tool comes from its `LookupInfo().Tool`.

Every answer is read as `exportActor` for the privacy mode: Safe answers as a player
sees the campaign (hidden pages, Director-only events, links, entries, rolling tables
and house rules stay out; a hidden page reads "no page called …").

`encounters`, `tests`, `trackers` and `foundry-monsters` are the DM's, so Safe
refuses them. `trackers` lists each page's trackers with value, meaning, whether
players see it and its last three log lines (`aiTrackersAdapter`). `encounters` writes each fight as an encounter block (the export's own
writer), then the version the recorded results pick and any creature with
no page that Foundry did not report. `tests` reads the Tests block's
campaign list (`aiTestsAdapter`). `foundry-monsters` reads the list the GM's
Foundry client last sent (syncapi's `foundry_monster_lists`, through
`aiFoundryMonstersAdapter`), says how long ago, and takes `name` (part of
one), `level` and `role` (a role or organization). It also lists the
creature pages matched to the monsters it shows (syncapi's `FoundryMatcher`,
see its "Creature matches"), and whose numbers each plays with, so the AI
writes lore, not a second stat block, for a matched page. The review notes
on a new creature page whose name Foundry has (`Classifier.WithFoundryMonsters`)
that it will be matched and play with Foundry's numbers.

`crafting` (`Lookups.Crafting`, `aiCraftingAdapter`) with no `part`
is the overview: the system's rules and the campaign's defaults, then a line
each for every recipe, material (with the pages that drop it and the recipes
that use it), drop list, what waits in the spoils tray, projects in progress
and benches, at most 40 lines per list. `part` (`recipes`, `materials`,
`drops`, `looks`) writes that part as the blocks that change it, so a block
sent back unchanged plans as no change; `name` narrows it to one. `looks` is
every item look on a page the reader can see, as `item-look` blocks (at most
30). A reader who is no Director, which includes Safe, gets the rules and
the recipe book as players read it, and is refused a `part`. Without the
crafting plugin (degraded) it says crafting can't be looked up.

`system-entries` reads the character pick lists, package and campaign-made
entries alike (`aiSystemEntriesAdapter` over `systems.CharacterChoiceService`),
as a Director only in Permitted or Everything, so Safe never lists
Director-only entries. A Director's list includes players' entries no
Director has accepted, each marked as a draft or as handed in, so the AI
never takes one for a settled option.

`waiting` lists what waits on a Director's yes or no (`aiWaitingAdapter`):
the connector's requests still waiting and the last five the owner answered,
with the outcome; players' unaccepted pick-list entries, handed in first,
with their writer and any review note; and the armory's stash moves and
ask-to-buy requests as the DM Screen lists them. It only reads: accepting or
turning down stays in Chronicle. Safe refuses it. A queue that fails to read
is named in the answer rather than shown empty.

## The AI button and panel

The owner (outside player view and Site admin) has an AI button in the top bar of
every campaign page (`layouts/ai_chip.templ`, widget `ai-chip`). It counts waiting
requests plus open warnings (`AIChip`, polled every 30 seconds while the tab is in
view; red when there are warnings or AI is stopped). When more requests wait than
this browser last saw (`sessionStorage`), a notice drops under it with Look, which
opens the bubble.

**The bubble.** The button drops a small bubble under it (`#ai-bubble`, loaded fresh
from `AIBubble` each time; pinned to the screen's edges on a phone). Its title bar is
Copy (`CopyForAI`) and Paste answer, then "Side panel", which opens the panel on all
the waiting requests over the same page, and close. Below it a line if AI is stopped
or there are warnings, then "Waiting for you · N" with each request and Review. The
footer has the connection line, what copying shares (the same remembered choice as
the tool, `ai-sees-<campaignID>`, changed in place), "Write a request…" (the tool, in
the panel) and the link to Your AI, the bubble's only way there; on the Your AI page
itself the widget drops that link. When the page has unsaved changes
(`Chronicle.isDirty`), the link asks first: Stay, or "Leave without saving"
(`Chronicle.discardChanges`, then go). Escape, a click outside and its close button
shut it.

**Copy.** On a page (`/entities/<id>`) the button reads "Copy page" and the text
ends with that page as a lookup reads it, asking the AI what to do with it. The page
is read as the remembered choice allows (`exportActor`), so with "What players see" a
page players can't see is left out, never named; the answer then carries
`X-AI-Page: left-out` and the bubble says the page wasn't copied. Elsewhere it copies
the standing instructions alone.

**Paste answer** reads the clipboard (`navigator.clipboard.readText`; when the browser
refuses, a small box in the bubble takes the paste). Text that doesn't start a block
is refused in the bubble; a block closes the bubble, opens the panel and submits it to
the panel's hidden paste form (`pasteReceiver`), so the review grows into the side
sheet. Review on a request opens the panel on that request.

**The panel** is a sheet from the right (full width on a phone), loaded fresh from
`AIPanel` each time it opens: a line linking to Your AI if AI is stopped or there are
warnings, the review of a paste, and "Waiting for you" (the requests, reviewed and
applied in place, or "Nothing waiting"). With `?tool=1` ("Write a request…") it holds
the copy-and-paste tool (`aiCopyPasteSection`) instead. The panel is moved to `<body>`
so the top bar never clips it; Escape, the scrim and its close button shut it. A
review in progress is kept when it closes; otherwise its content is dropped so the
requests stop polling. Anything with `data-ai-open` opens it, and the old
`#copy-and-paste` address opens the tool.

**Ctrl+V anywhere.** Outside a text field, a paste whose text starts a block (a
`---` line, then `key:`) opens the panel and reviews it, the same way as Paste answer; any other paste is left
alone, and an open review keeps its paste. The widget waits for htmx to settle the
panel before submitting, or the form would submit as a plain page load.

## Your AI page and the connector

The page (owner only) keeps setup and history. On top: the warnings, the
connection's line (dot, name, last used, Pause/Resume), and a line pointing to the AI
panel, tinted only while requests wait. Under it two tabs, **What it did** and
**Settings** (`pageTabState`; the open tab lives outside `#ai-connect`, so a Settings
change stays on Settings). It opens on Settings while no key works, or with
`#settings` in the address.

**Settings** starts with "How far may your AI go?" (`aiLevelPicker`, levels in
`ai_page_view.go`): "Look at what players see" (Safe, only look, the default when
connecting), "Look at everything" (Permitted, only look) and "Look and ask for changes"
(Permitted, ask). Each tile's "What it covers" unfolds a sheet listing pages, house
rules and lookups, notes, changes, and what it never does; on a phone the sheet sits
under its own tile. "Custom" picks what it sees and whether it asks separately, and is
the only way to reach "players and ask" (`levelOf` says "custom"). Everything is not
offered since lookups read the same as Permitted. With a working key a pick saves at
once to `/ai/connection/access` (`ChangeAIAccess` answers with "Saved", `LevelSaved`);
moving from what players see to more asks first, and the server refuses without
`widen=yes`. Pause and the level act on the key the page shows (`connection`, never a
newer key made elsewhere) and apply from its next call; the key stays the same.
Without a working key the same picker is part of the connect form ("Connect your AI
app", then "Then connect it": three steps and Make a key). The key and address are
shown once, with steps for Claude, Claude Code and other apps.

Below the levels, Settings is rows (`aic-row`): **Connection** (its line,
"Make a new key" at the same level, Disconnect, which asks first), **Co-DMs' shared
notes** and **Scribes' shared notes** (switches, `ai_notes_panel.templ`, saved on
change), **Players may use an AI here** (switch, "See what they get" unfolds
`playerCanDo`, then each player's key with Pause and Disconnect), and **If something
looks wrong** (Stop all AI here, asks first). The notes switches are campaign-wide
(`ai_note_access`), so they cover copy and paste and the connector alike; while the
key sees what players see, the rows say notes are left out.

**Warnings.** While the connector's watcher is on, the top of the page shows "AI is
stopped in this campaign" with "Turn AI back on" when the owner has stopped it, and
each open warning about the campaign's keys with "That was me" and "Pause the key"
(see `connector/.ai.md` "Watching for misuse").

**What it did** groups kept calls into sittings (`connector.Sittings`, a sitting ends
after `SittingGap`, 30 quiet minutes). Each is one folded line: day and times in the
owner's zone (`SetZone`, UTC when unset), a strip with a tick per call (faint for a
look, accent for a request, red for one not answered), what it did, and pills for
requests still waiting and calls not answered. Unfolded, each call shows its time,
icon, line, why it wasn't answered, and its size or "Waiting for you". A waiting
request is matched to its call by time (within a minute) and its quoted line
(`callWaiting`). Filter chips (Everything, Requests, Waiting for you, Couldn't answer,
with counts) and a search box filter the calls in the browser (`historyState`, held on
the tab outside the polled part, so a filter survives new calls); a sitting with no
match hides, one with a match opens. It lists 8 (`sittingsStep`), "Show older
sittings" adds 8, and it polls every 30 seconds (`?seen=`, 204 when nothing new),
skipping while the search box has focus.

**"Waiting for you"** (in the AI panel) lists the AI's requests, newest first, one card each: app,
change count, the AI's own line in quotes, Chronicle's count ("2 to add, 1 to
change"). It polls every 30 seconds (`?seen=`, 204 when nothing new, so an open "Turn
down?" is never reset; skipped while a review is open in a card). Review posts
`ai_request` to `ParseImport`, which reads the blocks from the campaign's own waiting
request (never the form), skips the tray, and renders the usual review inside that
request's card (`requestHost`, `ai-request-<id>-review`). Each page's text is one fold
away ("Read what it writes", plain text); on wide screens hovering a row shows the
start of it (`.air-peek`, `peekText`). One review is open at a time (opening one
empties the others). The form carries `ai_request`, so Apply marks the request
answered with what was applied; the answer replaces the card list and puts "Made N of
M changes" above it, with the full result one fold away. "Not now" folds the review
back and leaves the request waiting. "Turn down" asks first and applies nothing.
Waiting requests survive Disconnect or a new key (the confirm says so): nothing in them
applies without the owner and dropping them would lose work. "What it did" logs a
request as "sent for your review", which stays true whatever the owner answers.

## Players' AI

Off until the site admin and the campaign's owner both allow it (`connector/.ai.md`
"Players' keys"). A player (not a guest; outside Site admin) gets the same AI button,
pointed at `/ai/me/` (`aiChip("ai/me", true)`), rendered hidden and shown only while
`PlayerChip` says players may use AI; while hidden, Ctrl+V and `data-ai-open` do
nothing.

A player's bubble (`playerBubbleBody`) has the same title bar, Copy for my AI (their
characters and what may change, `PlayerCopy`, `playerInstructions`) and Paste answer,
then their AI's requests with Review, and "Connect your AI app" while no app is
connected. Copy and paste stay when one is. There is no privacy choice (a player's
copy holds only what they can see) and no full page. A paste or Review opens the
player's panel (`playerPanelBody`): what their AI can do (`playerCanDo`), their
requests, each reviewed in place, and the
review of a paste, made by a hidden form with the owner's paste box id so Ctrl+V on
any page fills it. "Connect your AI app" opens the panel's key menu (`?menu=1`: made
once, shown once, Disconnect asks first). When players may not use AI, the bubble and
panel say why.

**What may change.** Only a character the player claimed and can still open, only
`action: update` blocks carrying sheet fields and no page text, and only fields the
player's own sheet editor allows: identity fields and the hero builder's picks, never a
GM-only field (`entities.CheckClaimedOwnerPatch`, judged as a Player whatever the
person's role). `planPlayerChanges` checks each block without writing; anything else is
listed under "Left out, so you never see them as choices" with the reason, and a field
that already holds the value is dropped. Apply re-plans from the server's copy of the
request or the posted paste and applies only kept blocks the player said yes to, so a
forged yes for a left-out block changes nothing. Each write carries
`changesource.KindAI` with the player's id and app name, so the page's history says it
was the player's AI.

**The owner's panel** (`aiPlayersPanel`, on Your AI) has the "Players may use an AI
here" switch (hidden while the site admin blocks players) and each player's live key
with Pause or "Let it back" and Disconnect (asks first). It never shows what a player's
AI read or asked for.
