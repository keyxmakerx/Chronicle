# ai_workspace plugin

## Purpose

Chronicle's AI co-pilot surface: generates a markdown export of a campaign
for pasting into an AI tool, builds prompts, and imports AI-authored markdown
back into pages and the newer features (records, below): create / update /
delete, per front-matter `action:`.

Owner-only; own settings tab via `campaigns.RegisterSettingsTab`, own routes
via `RegisterOwnerRoutes`. Its tables remember what AI Import applied in each
campaign: `ai_import_parts` (the parts of a split answer, waiting in the tray or applied) and `ai_import_blocks`
(a fingerprint per block); see "Import: answers in parts" and "Import: a paste
applied twice".

## Tier

**Plugin** under `internal/plugins/ai_workspace/`. Cross-cutting in
nature — depends on every other plugin's lister interface via the
nested `aiexport/` sub-package, but exports nothing visible to those
plugins. The campaigns plugin is the only consumer (via the
SettingsTab registry and the parent route group).

## The review screen

One list of what the AI asks for, answered Yes or No, then Apply (styles in
`static/css/ai_review.css`, a workshop on the theme tokens). Blocks that can't be used (a parse error, a record whose plan
is an error) sit in a problems box on top with their block number and are
never offered as rows. Rows are grouped: Pages, then records by kind in the
order each kind first appears; on-screen order never changes the form's
`page_N_*` / `rec_N_*` indexes. Each row ends in a radio pair named
`page_N_include` or `rec_N_include` (`on` is Yes, `off` is No).

- Removals start on No, as do page rows the classifier marks
  `StatusActionMismatch` or `StatusParentProblem`; everything else starts on Yes.
- A removal's "for good" tick shows only while the row is answered Yes, and
  the page script (`importReviewScript`) makes it `required` then. The
  committer re-checks it either way.
- `reason:` (any block) is the AI's one-line why, shown as "AI's reason". It
  is never saved: the parser knows the key and `system-entry` reserves it.
- A page's name, action, category, visibility and conflict mode fold under
  "Change the details"; the defaults for every page fold under a quiet word.
- J/K move between rows and Y/N answer, never while typing. The save bar
  counts Yes answers (a GM-only row counts once its tick is on) and removals.

## Wiring

`internal/app/routes.go` constructs the plugin at startup:

```go
aiWorkspaceRenderer := aiexport.NewService(entityService, noteSvc, ...)
aiWorkspaceHandler := ai_workspace.NewHandler(aiWorkspaceRenderer)
aiWorkspaceHandler.SetAuditLogger(&aiWorkspaceAuditAdapter{svc: auditService})

campaignHandler.RegisterSettingsTab(aiWorkspaceHandler.SettingsTabFactory())

aiWorkspaceCampaignAuthed := e.Group("/campaigns/:id",
    auth.RequireAuth(authService),
    campaigns.RequireCampaignAccess(campaignService),
)
ai_workspace.RegisterOwnerRoutes(aiWorkspaceCampaignAuthed, aiWorkspaceHandler,
    campaigns.RequireRole(campaigns.RoleOwner))
```

The settings-tab factory returns a `func(*campaigns.CampaignContext)
campaigns.SettingsTab`, invoked per-request inside `visibleSettingsTabs` so
the tab's `Content` closure can bind `cc.Campaign.ID` into the form's
`hx-get` URL. The tab is Settings' "Data & AI" (slot 50): the campaign's
own export and import (`campaigns.SettingsDataSection`) first, then the AI
tools; campaigns drops its built-in Data tab while this one is registered.
Pinned by `campaigns/settings_tabs_test.go`'s
`TestRegisterSettingsTab_MergesAndSorts`.

## Sanitization

Every HTML field on export funnels through `aiexport.htmlToMarkdown`, which
applies `sanitize.HTMLPtr` before the markdown converter (AST pin:
`TestRenderers_FunnelThroughHtmlToMarkdown` in `aiexport/renderer_test.go`).
On import, every entity mutation funnels through `MarkdownToHTML` before
`creator.Create`/`Update`; `commitDelete` is exempt (`creator.Delete` has no
body to sanitize). Pinned by
`importer/committer_sanitize_test.go::TestCommitter_EntityMutationsFunnelThroughMarkdownToHTML`.

Zero edits to `internal/app/export_adapters.go`,
`internal/plugins/campaigns/export_handler.go`, or `internal/plugins/restore/`:
AI Export/Import is a separate, intentionally lossy egress; the lossless
backup pipeline is untouched.

## Audit

Export fires `campaign.ai_export.generated` with privacy mode + category
count + GM-notes opt-in flag + markdown byte count (no markdown body — audit
log is events, not bulk content). Import fires `campaign.ai_import.committed`
with counts: `created`, `renamed`, `updated`, `deleted`, `skipped`, `failed`,
`new_categories_created`, `new_categories_failed`. Audit hooks are optional
via `SetAuditLogger`; nil disables emission for test fixtures.

## Import: action verbs and conflicts

Front matter carries an `action:` field: `create` (default), `update`, or
`delete`.

| Action | Required FM fields | Body | Behavior |
|---|---|---|---|
| `create` (default) | `name` (or H1) + `type` (or bulk default) | Required | Create new entity; conflict-mode dropdown on slug collision |
| `update` | `name` (or H1) | Required | Load existing entity by slug → replace metadata + body |
| `delete` | `name` (or H1) | Ignored (warning emitted if present) | Load existing entity by slug → `EntityService.Delete`; soft vs hard delegated to the entities plugin |

Conflict-mode dropdown (on `create`): `skip`, `rename` (default, `(Imported)`
suffix), `update` (replace existing). Only a `create` row's line under the name says the page
gets a new name (`renamesOnConflict`); an update or removal works on the
existing page.

Blocks are split on their `---` lines (`importer.splitPages`). A block with no
text that is followed by a single `---` and then another block's keys (a
`kind:` or `name:` line, then a closing `---`) is read as two blocks, so a
fence shared between them never makes the second block the first one's text.
A first line `# Name` that repeats the page's name is dropped from the text,
since the page shows its name as the title (`dropTitleHeading`). Each `action: delete` row requires an
inline "I understand X will be permanently deleted" confirmation checkbox;
the committer re-checks `DeleteConfirmed` against any client-side bypass.

An update (explicit `action: update`, or a create row resolved to the `update`
conflict mode) over a page whose current text has GM-only parts is skipped
unless the row's "Replace the text anyway" tick (`page_N_replace_gm_confirmed`)
is set. GM-only pictures and diagrams never come back through markdown, so they
always count. A GM-only passage counts only when the incoming text does not
carry it back: `importer.GMOnlyPartsAfter` compares the page's passages with
the `{gm{…}gm}` passages of the AI's body as a multiset on their words. A
safe-mode export (which strips passages), a dropped passage, an unmarked one or
edited words all count as lost, so a page exported without its secrets stays
protected. The classifier sets `Classification.GMOnly` for the review callout;
`commitUpdate` re-measures the live page against the converted body and
enforces the tick before any write.

## GM-only passages in page bodies

The marker is `{gm{text}gm}` (`importer.SecretOpen` / `SecretClose`), documented
in the import prompt where page bodies are described. The editor's secret is an
inline mark, so one pair covers one paragraph; a longer secret repeats the pair
per paragraph, and an unclosed opener hides only the rest of its block (failing
closed).

- Import: `MarkdownToHTML` turns markers into `<span data-secret="true">`
  (`convertSecretMarkers`, a tokenizer pass after goldmark, skipping code and
  closing and reopening inline tags that straddle a marker so no tail leaks),
  and `htmlconv` turns the span into the editor's `secret` mark. Only a viewer
  at the owner tier (owner, or a co-DM, via `VisibilityRole`) may write it;
  any other gets `ErrSecretNotAllowed` and the row fails. With no page-link
  resolver (records) markers stay literal text.
- Export: `htmlToMarkdownWithSecrets` writes the markers in the director's
  modes (permitted, everything); safe mode strips passages first, and every
  conversion breaks literal marker text in a page with a zero-width space, so a
  marker in an export is always one the export wrote.
- Other call sites of `htmlToMarkdown` (notes, session text, events) still
  flatten passages to plain words, as before.

### Import: sub-pages (`parent:`)

`parent: <page name>` on a create or update block puts the page under an
existing page or one created earlier in the same paste (matched by slug, like
every other name here). Update semantics follow the partial-update contract:
absent keeps the page where it is, `parent: none` lifts it to the top level
(`patch.Null`), a name moves it. The classifier (`checkParents`) marks a
missing, self, later-in-paste, deleted-in-paste or duplicated-in-paste parent
as `StatusParentProblem` with a plain-words `Reason`, default-excluded. The
committer resolves the parent (`resolveParent`) against pages it saved earlier
in the same commit (so renamed rows still work), then the campaign, and passes
`ParentID` to `EntityService.Create`/`Update`, which owns the same-campaign and
cycle checks; its 400 message is shown on the row. A parent that was not saved
fails only that row. The AI sees the tree through `Lookups.PageIndex`, the
`pages` lookup (`Name (in Parent)`) and the export (`**Parent:**` line); a
parent outside the reader's visible set is never named.

### Import: folders (`folder:`)

`folder: <name>` on a page block files the page in that sidebar folder of the
page's own category (matched ignoring case; two folders with one name are
refused). Absent keeps the page where it is, `folder: none` takes it out of
its folder. `parent:` and `folder:` with real names together are a parse
error, because a page sits under a page or in a folder, never both
(`entities.FolderService.SetEntityFolder` clears the parent page;
a page that gains a `parent:` on update leaves its folder). The committer
resolves the folder before writing (`resolveFolder`), so a missing or
ambiguous folder fails only that row and creates nothing; the filing itself
runs after the page is saved (`applyFolder`), like tags. The classifier
(`checkFolders`) marks a missing folder `StatusParentProblem` ("Parent or
folder problem"), unless a `kind: folder` create or `rename_to` in the same
paste makes the name. Folder blocks that create or change a folder commit
BEFORE the pages (`commitEarlyFolders`), while the other records commit after
them; a folder removal commits last. The export writes `**Folder:** Name` under
a filed page (`Options.FolderNames`, from `FolderNamer`), and the `pages`
lookup and the prompt's page index read `Name (in folder Gods)`.

### Import: tags (`tags:`)

`tags:` on a create or update block sets the page's tags (`Committer.applyTags`,
through `tags.TagService`). A name matches a campaign tag by slug (`tagSlug`,
the tags service's own rule); one that matches none is made. Absent keeps the
page's tags, `tags: []` clears them, a list replaces them. An update always
keeps the page's GM-only tags, since a Safe export never showed them. A page
saved whose tags could not be set is a failed row that still links the page.

### Import: category (`type:`)

`type:` names the page's category. The classifier (`ensureTypes`) matches it
against each category's slug first, then against the slugified plural name, so
`race` and `races` both find the same category unless another category's slug
is that word. A name that matches nothing creates a new category; the
committer derives its singular and plural names from the slug
(`categoryNames`), without pluralizing a slug that already reads as a plural.

### Import: pages by era (`era:`, `known_as:`)

A page block with `era: <era name>` writes that era's version of the page the
block names (`name:`), never the usual page. The era is matched by name,
ignoring case, among the main calendar's eras as the importing owner sees
them. `known_as:` sets the page's name in that era and is a parse error
without `era:`. A non-empty body becomes the version's text; an empty body
leaves the text as it was. `create`, `update` and no action all mean "write
the version" (the version is created when missing); `action: delete` removes
only that version and needs the usual delete confirmation. `type`,
`subcategory`, `visibility`, `parent` and `tags` are ignored on an era block,
with a warning.

The classifier (`checkEras`) marks a row `StatusActionMismatch` with a
plain-words `Reason` for an unknown era (the reason lists the eras that
exist), an unwired writer, or a page that neither exists nor comes earlier in
the paste in a block without `era:`. The committer (`commitEra`) re-resolves
the era, finds the page among those it saved earlier in the commit and then
the campaign, runs the body through `MarkdownToHTML` and `htmlconv` and hands
it to `EraWriter.WriteVersion`; the calendar plugin's `EraVersionService`
sanitizes again in `SaveEntry`. The outcome is `StatusUpdated` with a reason
such as "Wrote the Age of Ash version". Era rows never count as the page for
`parent:`, links or the relink pass. `EraWriter` is wired by
`internal/app/ai_workspace_era_adapters.go`; unwired, era blocks are refused.
The review shows an "<Era> version" pill on these rows.

The export carries versions the other way: in Owner view and Everything
modes each page is followed by one block per era version (`name:`, `era:`,
`known_as:` when the version has its own name, then its text); eras the
exporting viewer cannot see are left out. Safe mode exports the page as
players see it now, with the current era's version in place of the usual page
and no other version.

### Import: page links (`@[Name]`)

Any markdown body (pages, and the `note` and `event` records) may write
`@[Page Name]` or `@[Page Name|shown text]`. `MarkdownToHTML(body,
WithPageLinks(links))` rewrites it in the rendered HTML's text nodes (never in
`<code>`, `<pre>` or an existing `<a>`), before `sanitize.HTML`, into the
anchor `internal/pagelink` builds: `data-mention-id`, the entity href and
`data-entity-preview`, the same as an editor @mention, so the hover card,
click-to-preview and backlinks work. Without the option the text stays as
written. `@[Name]` shows "@" plus the page's own name; `@[Name|text]` shows
the text as written.

`importer.PageLinks` resolves a name by slug (like every other name here):
first pages this commit already saved, then the campaign, and only pages
`CheckEntityAccess` lets the viewer open. A name that resolves nowhere is
left as plain words. A page that links a page later in the same paste is
written once, then again after the last row (`relinkPending`) through
`UpdateEntry`, so the editor JSON, `entry_html` and backlinks stay in step.
The review screen warns per row for a name found in neither the campaign nor
the paste (`LinkWarnings`; records get it in `Plan.Warnings`); it never
blocks. Records commit after pages and resolve against the campaign.

The export writes a mention anchor as `@[Name]` (`aiexport.mentionRule`),
using the anchor's text, so the AI sees links it can send back. The prompt
teaches the syntax in the front-matter section and in the note and event docs.

Every parser/converter/committer error path produces human-readable wording;
raw library prefixes (`yaml:`, `goldmark:`, `goquery:`) never reach the
operator UI — see `importer/parser.go::humanizeYAMLError` for the YAML case.
Technical detail is preserved via `%w` for slog.

A first-load inline callout points at "Copy AI Prompt"; dismissed via
`localStorage` key `ai-workspace-onboarded-<campaignID>`. The import body
char counter surfaces the 5 MB server-side cap (`importBodyCap`) live.

## Import: answers in parts

An AI that splits a long answer over several pastes starts each with a
`kind: part` block: `name` (the same on every part), `part` (from 1), `of`
and `needs` (the earlier parts it relies on). The prompt teaches it in "If your
answer comes in parts". `importer.TakeParts` takes the labels out before
lookups and review; each other block belongs to the label above it. A label
that can't be read is a parse error, and its blocks count as unlabelled.

- Several parts pasted together are put in order first (`importer.OrderParts`:
  each answer's parts by number, answers in first-seen order), and the
  reordered text becomes the review's `markdown_source`.
- **The tray.** When a paste holds the parts of one answer and that answer is
  not complete (`importer.AnswerMissing`: every part from 1 to the largest
  `of`, plus every part named in `needs`, is pasted, waiting or applied),
  `trayStep` stores each part's text (`importer.PartTexts`) in
  `ai_import_parts` with its `markdown` set, and the parse returns
  `TrayNotice` ("2 of 3 in", which parts to paste next) instead of a review.
  The tray (`import_tray.templ`, loaded under the paste box from
  `GET …/import/tray`) lists each waiting answer with "Review what's here"
  (posts `tray_review` = the answer key to the parse, which reviews the
  waiting parts as they are) and "Empty" (`POST …/import/tray/clear`).
- When the paste completes the answer, the waiting parts and the paste are
  joined, put in order, held to the 5 MB paste cap and reviewed once as one
  paste. A paste holding parts of several answers skips the tray and is
  reviewed as pasted.
- Commit marks a label in its `markdown_source` applied (`applied_at` set,
  `markdown` cleared) once at least one of its blocks was applied; a review
  answered No throughout leaves the waiting parts in the tray. A review that still lacks a part it needs says
  which in a note box (`checkParts`, `partNote`); nothing in it is held back.
- Without the tables (`SetImportMemory` unwired) labels are still read and
  shown, but nothing waits in a tray.

## Import: a paste applied twice

Every block a commit applies (created, renamed, updated or removed) is
remembered as `importer.BlockHash`, the SHA-256 of its text with line endings
and trailing spaces evened out; the text itself is never kept. The review
looks the paste's blocks up (`repeatedBlocks`): a repeated row says "Already
applied on <date>", starts on No and carries `data-air-hold`, so "Yes to all"
skips it; a repeated block the review refuses (the thing it makes exists now)
says the same in the problems box. A box on top says the whole paste was
applied before, or how many blocks were. Parts waiting in the tray were never
applied, so they never count as repeats.

## Import: sheet fields

A page block's `fields:` map sets values on the page's sheet, by field key.
The entity service saves any map it is given, so `importer.CheckFields` is the
only gate: every key must be one of the category's `Fields`, and each value
must fit the field's type (number, yes/no, one of a pick list's options, an
http(s) address, or text). A list or map goes into a text field as JSON text,
which is how a system's sheet keeps structured data (Draw Steel's stat block
keeps `traits`, `abilities_json` and `villain_actions_json` that way). A
null clears a field.

- The classifier checks fields against the category the row will have: the
  page's own on an update (an update never changes the category), the front
  matter's on a create. A row whose fields don't fit is
  `StatusFieldProblem` and goes to the problems box; a good row shows a
  "Sheet: ..." line. A new category or an era block can't take fields.
- The committer checks again against the category finally picked, before any
  write. A create saves the checked map as `FieldsData`; an update leaves
  `FieldsData` absent on `Update` and calls `MergeFields` with only the named
  fields, so the rest of the sheet keeps its values.
- The prompt lists each category's fields under it (`prompt.fieldLines`), in
  the shape `CheckFields` accepts.
  `prompt.Service.Notes` (`aiFieldNotes` in `internal/app/system_sheet_fields.go`)
  adds the game system's word on a field: its manifest `format` (how a list is
  written) and, on the hero sheet, "Foundry keeps this one" for a field Foundry
  reads off the actor's items or never takes back.
- The categories a system's sheets live on carry the system's fields: the
  player-character list's types get the character preset's, creature types the
  creature preset's (`addSystemSheetFieldsOnce`, once per site, adds only
  missing keys). The import writes only declared keys, because GM-only hiding
  reads the category's field list.
- A `link` field takes a page's name. The committer turns it into the page's
  id (`importer.LinkFields`) with the `@[Name]` resolver, so only pages the
  operator can see, and a page this paste makes must come before the page
  linking to it. The entity service checks the page is of the right
  category at the write. A `rule` field takes text typed by hand.
- A `page` lookup ends with the page's sheet as a `fields:` block, filtered
  by `entities.FilterRestrictedFields` for the reader, so the AI can read a
  monster's stat block, change it and send it back. When the page's layout
  has a Page map block holding a map, the answer then ends with a `### Map`
  section: the map's lines in the `page-map` grammar, filtered for the reader.
  For a Director it also ends with `### Quest notice` (the page's `quest`
  block) and `### Notice boards` (each `notice-board` block hanging on the
  page), as `QuestKind.Export` and `NoticeBoardKind.Export` write them.

## Import: records

A block whose front matter has `kind:` (anything but `page`) is a record,
not a page. `records.Registry` holds one `Kind` per feature. Each feature
adds its kinds from an `init` in `internal/app` with `addAIKinds(rank, …)`
(`ai_kinds.go`), so a new kind never edits `routes.go`; the rank sets its
place in the prompt, and a degraded plugin's kind is left out:

| kind | Writes | Through |
|---|---|---|
| `calendar` | makes the campaign's calendar (and marks it the main one), makes an existing calendar the main one (`main: true` on update), or changes the main one's months, weekdays, seasons, moons, year label, eras and current date; owner only, never removes | calendar service: `CreateCalendarFromImport` after `calendar.PrepareImport`, `SetDefaultCalendar`, the structure editor's preview/apply, `CreateEra`/`UpdateEra` |
| `event` | calendar events, one-off or repeating, on the main calendar or the one `calendar:` names; `importance` (the campaign's tier levels, `campaigns.GetEventTierDefinitions`), `category` (the calendar's event kinds) and `page` (the event's one linked page, resolved like a moon's; a page the paste makes passes review and is linked at commit); `icon` takes `sun`, `fa-sun` or `fa-solid fa-sun` and stores `fa-sun` | calendar service |
| `weather` | one day's weather, set by hand (`manual`) or cleared | calendar service |
| `table` | rolling tables (whole-document read/edit/write) | rolltables service, via `aiRollTablesAdapter` |
| `shop-stock` | a shop's `sells` relation and its price/quantity metadata | relations service |
| `carried-item` | a character's `Has Item` relation and quantity | relations service |
| `pin` | map pins; a pin may name a map a `map` create earlier in the same paste makes | maps service, via `aiMapsAdapter` |
| `map` | a map drawn from a sketch on a grid of squares (`grid: 40 x 26`, one line per room, area, water, danger zone, wall, road, path, label or pin): `create` makes a new map, `update` (map named by `name` or `map`) adds the sketch onto an existing one and refuses plainly when there is no such map. An update spreads the grid over the whole map (exact percent, no pixel rounding), warns when the squares would stretch on the picture's proportions, replaces everything on the map's `AI sketch` layer (`records.SketchLayerName`; create puts its shapes there too), including a shape a person drew onto that layer, and leaves other layers alone, and leaves out a pin whose name is already on the map so reruns do not stack pins. The layer is cleared before the new shapes are drawn (clearing afterwards would delete them too), so if a shape fails the old sketch is gone and not restored. The map page does not show layers, so the layer only exists to identify sketched shapes. Pictures cannot be attached or changed. A line that cannot be drawn is a review warning and is left out; the map is still made. The line parser is `internal/mapsketch` (shared with the page map block); `records/map_sketch.go` keeps the conversion to map drawings | maps and drawing services, via `aiMapSketchAdapter`: a blank 1000-wide map with a square grid of 1000/width (create), or the existing map found by name and `Inspect`ed for picture size and earlier sketch (update), then each line as the box, ellipse, freehand or text drawing the map page's tools make, and pins as `pin` does |
| `note` | the operator's OWN Journal notes and jots, never notes others wrote | notes service |
| `house-rule` | house-rules chapters of the campaign's rulebook, written whole (see below) | `systems.SystemHandler.CampaignBookPackage` |
| `system-entry` | the campaign's own pick-list entries (ancestry, kit...), Directors only; never the package's | `systems.SystemEntryService` |

Each record is planned at parse time (`Kind.Plan`: one summary line, or an
error that blocks the row) and re-planned inside `Kind.Apply` at commit, so
nothing the review screen showed is trusted. Records commit after pages, so
a record may name a page created in the same paste; `Record.Made` (the
paste's page slugs) lets a plan skip the "not a page yet" warning for one. A record's action is
fixed by the markdown (no per-row override); a delete needs its own
`rec_N_delete_confirmed` tick, re-checked by `commitRecords`.

A kind is found by its name ignoring case, with `_` and `-` alike
(`roll_night` and `roll-night` are the same kind).

A feature switched off in Game & features redirects its pages to the
dashboard, so what an import made there would be out of the owner's sight.
`Handler.SetFeatureGate` (wired from `aiFeatureGate` in `internal/app`, over
the same add-ons the routes check) names those features by kind
(`records.OffFeatures`): Calendar off rules out `calendar`, `event`,
`weather`, `roll_night`, `moon`, `game-night` and every `generator` run but
names; Game nights off rules out `game-night`; Maps off rules out `map` and
`pin`. The prompt leaves those kinds out (`Registry.Without`) and says which
are off and where they are turned on; the review refuses such a row with
`OffFeatureReason`, and the commit refuses it again. A failed add-on check
counts as on. "Copy AI instructions" stays unfiltered, since it is saved once
for every campaign.

Records are planned in order (`Registry.PlanAll`) and committed in the same
order. A row that makes a folder or a map lets the rows after it name that
folder or map. A `calendar` create row, or an update with `main: true` that switches
the main calendar, hands that calendar to the rows after it, so their dates
are checked against it before it is main; a row that needs a
calendar and finds none says "Needs a calendar first", and the review
counts it as "can't be imported yet", never as a parse error, and names the
block that fixes it (`action: create`, or `main: true` when the campaign has
calendars but none is main). A calendar
update's list (months, weekdays, seasons, moons) replaces the whole list,
matching moons and seasons by name so their ids and left-out keys survive;
a moon hidden from players is never removed (a player-safe export never
lists it), and kept seasons follow their months by name. Eras are merged
by name.

A moon or an era may carry `page:`, the name of a page that tells of it
(its lore page, the one the calendar shows as a link). It is resolved by slug
against the campaign (`CalendarKind.Pages`, the entities service) and must be
a page the operator can open; a name that matches no page, or only a page they
cannot see, is refused at review with the same plain words, so a refusal never
confirms a hidden page. Naming a page on update replaces it, `page: none`
clears it, and leaving the key out keeps it (the partial-update contract:
`MoonInput.LoreSet` for moons, a `patch.Field` on `UpdateEraInput` for eras).
On create the page rides on the new calendar's moons and eras; the services
check it against the campaign again. The calendar export and `what: calendar`
show each moon's and era's page by name, as the privacy mode's viewer may see
it (the calendar service blanks one they may not).

A `house-rule` block carries the chapter in its front matter in the book's
own chapter-file format (`intro`, `director`, `pages` with the book's blocks),
checked by `systems.ParseHouseChapterDraft`, the editor's own rules. With
`pages`, it is written in one step by `BookEditService.WriteHouseChapter`, and
an update replaces every page of the chapter; without, only the chapter's own
lines change (an old-style body is still the intro). Its plan warns about
pages a replacement drops and Director-only parts it loses, and carries
`Plan.Preview`: the chapter as a one-chapter book, which the review row draws
with the rulebook reader (`data-book-json`), so it shows in the campaign's
Handbook look with working rolls and flaps. Its export is each chapter in the
same format, in the privacy mode's view.

Permissions: the routes stay owner-only. Kinds additionally apply the UI's
own capability rules from the operator's `Actor` (hidden events and pins,
weather, rolling tables and house rules need `CanAuthorDmOnly`), and the
services keep their own checks. Notes are narrowed to `IsOwnedBy` the
operator, checked on the list and again on the stored note before a write.
The export's Notes category is likewise the operator's own notes only.

Generators exist only in the browser (`static/js/widgets/chronicle_gen.js`).
A generator row carries its plan (generator, calendar, scope, seed) in
`data-ai-gen`; on Import, `markdown_importer.js` runs each plan and writes
the result to `rec_N_generated`. `GeneratorKind.Apply` treats that output as
untrusted: it is capped, checked against the plan's scope, and written
through the same services. Generated weather is saved as `generated`, so it
never replaces a day set by hand or locked.
A weather plan also carries the calendar's climate, continuity and the
owner's own kinds of weather (`GeneratorKind.Weather`), as the calendar's
weather sheet runs it; the row's `climate` and tuning keys override them for
that run. The engine follows the calendar's own seasons from the calendar
JSON in the plan.

An event's `repeat:` takes the calendar's `RecurrenceTypes`. `repeat: rule`
builds a `calendar.RecurrenceRule` from `repeat_on` conditions that name
the calendar's moons, weekdays, months, seasons and events, translated to
ids here and parsed by `calendar.ParseRecurrenceRule` at review; the service
judges it against the calendar on save. Naming a repeat on update replaces
the whole repeat; leaving the keys out keeps it.

Every prompt opens with "What you can do" (`Registry.Capabilities`, one
line per wired kind, including the own-notes-only rule) and "If you need
more", which tells the AI to ask with lookup blocks (below) instead of
guessing what exists, and to ask `what: format` for a kind's exact format
(a `NEED:` list when lookups aren't wired). It also carries
"What already exists" (`Lookups.PageIndex`): page names per type, capped at
40 a type and 8 KB, read in the chosen privacy mode. The format section lists every kind
(`Registry.Docs`) when the front-matter example is on; the export's "Rolling tables, map pins, house rules" box and
the prompt's "All visible" content add `Registry.ExportAll`. The prompt's
"House rules" content (`prompt.ContentHouseRules`) carries only the house-rule
format and today's house rules, never the world export. It follows the
privacy mode: Safe, the default, lists records as a player sees them
(`exportActor`), so hidden pins, rolling tables and Director-only rules stay
out. Events are listed only by the Calendar events category. "Calendar"
content (`prompt.ContentCalendar`) carries the formats of `records.CalendarKinds`
(calendar, event, weather, generator; `Registry.DocsFor`) and the `calendar`
and `weather-kinds` lookup answers in the chosen privacy, so with no main
calendar it says how to make or choose one; never the world export.

The prompt splits in two for an AI that keeps standing instructions. "Copy
AI instructions" (`GET …/ai-workspace/prompt/instructions`, owner only,
`PromptInstructions`) puts the standing half on the clipboard as plain text
(`prompt.InstructionsOnly`): every kind's format, the lookups, the page
format and the campaign's page types, with no page index, export or request.
Ticking "My AI already has the instructions" (`instructions_saved`,
`prompt.InstructionsSaved`) leaves those out of a generated prompt, which
keeps the page index, the chosen content and the request. Audit:
`campaign.ai_prompt.instructions_copied`.

## Lookups

New since the first lookups: `tags` lists tags with their page counts (Directors-only tags only in a Director privacy mode); `pages` shows each page's tags and takes `tag:` beside `type:`, matching by slug and never confirming a tag the reader can't see; `game-nights` lists the nights (Directors only, like the kind); `system-entries` with no `field` lists the character fields that have entries (`SystemEntriesAPI.Fields`, read from the hero creator's plan); `calendar` names the event categories and importance levels that `category:` and `importance:` take on events.

A `kind: lookup` block asks Chronicle a read-only question (`what:` plus a
name or a date range; `records.LookupDoc` lists them: pages, page, calendar,
weather-kinds, events, weather, table, pins, stock, inventory, notes,
house-rules, system-entries, tags, game-nights, players, format). `format` hands back one
kind's own doc from the registry (`Lookups.Kinds`), keyed by `block:` since
`kind:` is the lookup's own. With no main calendar, `calendar`, `events` and
`weather` answer with what calendars exist and the block that sets one up,
not "Not answered". `calendar` and `weather-kinds` print
the calendar and the server's own climate, weather and sky-effect tables
(`calendar.WeatherClimates`, `WeatherPresets`, `WeatherEffects`), so what is
added there shows up with no change here. `ParseImport` takes lookups out of the paste before review; if
there are any, it answers them with `records.Lookups.Answer` and returns
`LookupAnswer` instead of the review, counting any other blocks as left
out. Nothing is written. The panel's Privacy select posts the same paste
again with `lookup_privacy`.

Every answer is read as `exportActor` for that privacy mode, so Safe (the
default) answers as a player sees the campaign: hidden pages, Director-only
events, links and entries, rolling tables and house rules stay out, and a
hidden page reads as "no page called …". Notes are the operator's own
only. `players` reads the DM Screen's party (`aiPartyAdapter`) and the next
game night's answers, and drops characters the mode can't see. Answers are
capped: 20 lookups, 300 lines and 24 KB each, 120 KB in all. Audit:
`campaign.ai_lookup.answered`, counts only.

`system-entries` reads the character pick lists, package and campaign-made
entries alike (`aiSystemEntriesAdapter` over `systems.CharacterChoiceService`),
as a Director only in Permitted or Everything, so Safe never lists
Director-only entries.
