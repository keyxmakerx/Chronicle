# Sync API Plugin

## Purpose

Versioned REST API (v1) for external tool integration: Foundry VTT modules
and custom scripts read/write campaign data programmatically. Also provides a
bidirectional entity sync protocol, API key management, request logging,
security event tracking, and an admin monitoring dashboard.

## Tier

**Plugin** -- handlers, service, repository, middleware, admin templates.

## How It Works

### Authentication

Prefix-lookup + bcrypt-verify: client sends `Authorization: Bearer chron_<hex>`
→ middleware extracts the 8-char prefix, looks up the key row by prefix →
full key verified against the stored bcrypt hash → key must be active and not
expired. Keys are scoped to a single campaign and carry permissions (`read`,
`write`, `sync`).

### Device Fingerprint Binding

Clients may send `X-Device-Fingerprint`. On first use it binds to the key; a
later request from a different fingerprint is rejected with a security event
logged. Prevents key sharing across devices.

### Module Version

The Foundry module sends `X-Chronicle-Module-Version` on every REST request.
When it matches `^[0-9A-Za-z.+\-]{1,32}$` the key's `module_version` is updated
in the same statement that stamps `last_used_at`; an absent or malformed header
leaves the stored value unchanged. The session door's synthetic key (ID 0) is
never written. The campaigns "Apps & game system" page shows the version of the
most recently used active key.

### Rate Limiting

Fixed-window counter per key per minute, configurable per key (default 60,
max 1000). `X-RateLimit-Limit`/`X-RateLimit-Remaining` headers on every
response. Over limit: 429 with `Retry-After: 60`.

### Addon Gating

Calendar and maps API endpoints are gated behind `RequireAddonAPI`: 404 when
the addon is disabled for the campaign, 503 when the check fails (fail-closed).

The `sync-api` addon toggle gates the KEY, not the route: `RequireSyncAPIAddon`
sits on both `/api/v1` groups and on `AuthenticateKeyForWS`, refusing real
Bearer keys with 403 `sync_api_disabled` when the addon is off. A synthetic
session key (Chronicle's own widgets reading the API by cookie) always
short-circuits — the toggle revokes outside access, not the app's own UI.
Enforcement defaults to denied for a campaign with no `campaign_addons` row;
`CreateKey` enables the addon and a boot reconciler backfills existing
campaigns without flipping an already-disabled one back on.

### Middleware Stack

Two parallel groups at `/api/v1`:

- **`v1` (JSON)**: `RequireAuthOrAPIKey` → `RequireKeyOwnerStillOwner` →
  `RateLimit` → `RequireJSONContentType` → `WithChangeSource` → (per-route)
  `RequireCampaignMatch` → `RequirePermission` → optionally
  `RequireAddonAPI`. `RequireJSONContentType` rejects POST/PUT/PATCH without
  `Content-Type: application/json` with 415; safe methods pass through.
  `RequireKeyOwnerStillOwner` refuses a stored Bearer key once its creator
  is no longer an Owner of the key's campaign;
  a session-authed caller always passes through.
- **`v1Multipart`**: `RequireAuthOrAPIKey` → `RequireKeyOwnerStillOwner` →
  `RateLimit` → (per-route) `RequireCampaignMatch` → `RequirePermission`.
  Skips `RequireJSONContentType` for `multipart/form-data`. Only inhabitant
  today: `POST /api/v1/campaigns/:id/media` (`UploadMedia`); any future
  multipart endpoint mounts here, not on `v1`.

`WithChangeSource` puts a `changesource.Source` on the request context: a Bearer
key is `foundry` (with the key holder's user id), a browser session on the same
routes is `web`. Observers of entity field writes (the stash plugin's money
history) read it; it grants nothing.

### Egress HTML sanitization

`GetEntity`, `ListEntities`, `GetNote`, `ListNotes`, `GetEvent`, `ListEvents`
invoke an `egress_sanitize.go` helper before `c.JSON(...)` to re-sanitize HTML
fields on the response copy (`sanitize.HTMLPtr` is the nullable companion to
`sanitize.HTML`); helpers operate on fresh DB-scanned models, so the canonical
row is untouched. This is defense-in-depth: ingress sanitization on the write
path (each source plugin's `service.go`) is the primary defense; egress
covers historical rows or tooling-bug-inserted rows that slipped past
ingress. Scope is `/api/v1/*` Foundry-bound surfaces only — the
backup/restore round-trip (`internal/app/export_adapters.go`,
`campaigns/export_handler.go`, `internal/plugins/restore/`) is a deliberate
lossless carve-out and must not be re-sanitized.

### Stash Endpoints (require the stash feature's addon)

`stash_api_handler.go`; the handler is thin and calls `StashAPIService`, which
`internal/app` implements over the stash plugin (this plugin never imports it,
and the addon slug is passed in by the wiring). JSON is camelCase, money is a
number in whole currency units, and a stash id may be sent as a string or a
number.

**Acting member.** Foundry holds one GM key but speaks for whichever player is
at the table, so every call may carry `actingUserId` (query on GET, body on
POST/PUT). It must be a current member (else 404). The call then runs as THAT
member, with their real campaign role and DM-access grant, never the key's Owner
role unless that member really is an Owner or has DM access. Only a caller who is
themselves an Owner or has DM access may name someone else (else 403); browser sessions
reach these routes as their own user, so a player cannot name the GM. Why this
is safe: such a caller can already do anything, so naming a player only narrows
what the call may do (their stashes and characters, their need for approval),
never widens it. Absent `actingUserId` acts as the key holder. A module
relaying a player therefore cannot approve requests or flip downtime.

## Sync Protocol

`POST /sync` supports bidirectional sync in a single request:

- **Pull**: set `since` (RFC3339) to receive entities modified after that
  time. One request walks at most 10 internal pages of 100. If the campaign
  has more, the response sets `has_more` and `next_cursor`; the client
  re-POSTs the same `since` with that cursor until `has_more` is false, then
  uses the `server_time` from the *first* response of the walk as the next
  `since` (not the last, which would skip anything modified mid-walk).
- **Push**: set `changes` array with `{action, entity_id, ...}` objects.
  Actions: `create`, `update`, `delete`. Max 2000 changes per request. Each
  change's content fields are `patch.Field`: on `update` an absent field
  preserves the stored value, present replaces it; `create` has nothing to
  preserve so reads each field's zero default.
- **Response**: `server_time` for use as the next `since`, `entities` array
  of pulled data, `next_cursor` when `has_more` is true, and a `results`
  array with per-change status.

## Notable Design Decisions

- Keys use bcrypt hashing with prefix-based lookup to avoid full-table scans.
- Rate limiter is in-memory (not Redis), acceptable for single-instance deployments.
- Request logging and security events are fire-and-forget goroutines so they
  don't block API responses.
- IDOR protection on every endpoint: entity/event/media ownership verified
  against the key's campaign before any operation. `PUT`/`DELETE` on a
  relation or note resolve the object and 404 on a campaign or ownership
  mismatch before running the owning plugin's visibility/ownership gate —
  never trust the campaign match alone for an object addressed by its own id.
- WebSocket auth reuses the same key validation path via
  `AuthenticateKeyForWS`, returning owner-level role for API key holders —
  but only after confirming the key's creator is still an Owner of the
  key's campaign (the WS twin of the REST gate
  `RequireKeyOwnerStillOwner`); a demoted or
  removed creator's key is refused instead of silently granted Owner role.
- Media API responses include HMAC-signed URLs when a signer is configured,
  1-hour expiry.
- `GetCurrentDate`'s dm_only visibility gating on celestial/world-state reads
  uses `resolveRole` and the caller's own forwarded identity — a
  `sync`-permission key resolves to Owner, a read/write key to Player.
  Deliberately no second filter: a divergent second visibility path on the
  same data is how a prior entity-ties leak happened.
- `apiUpdateEntityRequest` and `syncChange` use `patch.Field` for every
  content field — `parent_id`, `is_private`, `type_label`, `entry`, `name` —
  so a narrow client body (e.g. a Foundry actor-sync push sending only
  `{name}`) cannot silently detach an entity from its parent, un-private a
  hidden character, or blank its type label.

## Change feed

`RecordingEventBus` (`sync_change_bus.go`) wraps the WebSocket EventBus. For an
allowlisted type (entity, entity_type, note, marker, drawing, token, layer,
fog, map, relation, calendar.event, stash, downtime) it appends a `sync_changes` row, stamps the message
with `seq`, then publishes. The insert has a 500ms timeout; on failure it logs
and still publishes, so live delivery never waits on the feed. The row is
written after the domain write commits, so a crash between the two drops that
change, which clients recover from through `resetRequired`. A daily job
(`StartChangePruner`) deletes rows older than 30 days and raises the
per-campaign `sync_change_watermarks.pruned_through`. Echo suppression is the
module's job; the feed does not carry a sender. A `relation` row's resource is
the relation's source entity, so a client reads it as "this entity's relations
changed" and refetches `GET /entities/:id/relations`.

## Sync history

One record of syncing both ways, read by the campaign's Manage › Sync history
page (`/campaigns/:id/sync-history`, owner and members with DM access) and by
the Foundry module's History tab through `GET /sync/history`. Rows live in
`sync_events` (plugin migration 009); a catch-up run is a parent row with its
steps as children.

- Changes arriving in Chronicle are recorded by `RecordSyncHistory`, mounted on
  the `/api/v1/campaigns/:id` group after `RequireCampaignMatch`: every write a
  real API key makes, with its status, timing and error message, and reads only
  when the server failed them. Session callers (Chronicle's own widgets) and
  token-drag position updates are skipped. The insert runs after the response
  with a 2 s timeout and never fails the call.
- Changes applied in Foundry, connects and catch-up runs are reported by the
  module (`POST /sync/history`), because only it knows the change landed. For a
  `to_foundry` row the server names the Chronicle editor from the page's
  change log (`ChangeEditorLookup`).
- `StartHistoryPruner` deletes rows older than 90 days, daily.

### Call flow

A failed row on the Sync history page opens its call flow: the steps around it
drawn as arrows between three lanes (Chronicle in a browser, the Chronicle
server, Foundry), so the owner sees what led to the failure, why it happened
and what came after. Admin › API & access opens the same flow under a
campaign row, around its latest failure in the last day, with page names
hidden ("Page 1") and Foundry's own error text left out.

- Routes: `GET /campaigns/:id/sync-history/flow/:eventID` (same gate as the
  page; only the steps about the same thing) and
  `GET /admin/api/sync-flow/:campaignID` (site admins; every thing).
- `sync_flow.go` turns rows into steps (`buildCallFlow`): a `to_chronicle` row
  is Foundry's call and Chronicle's dashed answer; a `to_foundry` row is the web
  edit (when the change log names an editor), Chronicle telling Foundry, and
  Foundry applying it; anything else is a loop in Foundry. Steps about the same
  thing (`flowGroupKey`) less than 2 minutes apart chain as cause and result.
  The flow reads 5 minutes either side, at most 40 rows.
- `sync_flow_problems.go` tells a failure's story: what happened, why, what
  Foundry does next, how to fix it, and the same call failing in the last 24
  hours. A date push names the date asked for and the one it would replace:
  `SetDate` notes both (`noteSyncChange`) before its owner check, stored in
  `was_value` (plugin migration 010).
- `sync_flow.templ` lays it out; `static/js/sync_flow.js` fetches it on open,
  shows times in the reader's zone, and does selecting, chaining and the
  "Only problems" and per-thing switches.
