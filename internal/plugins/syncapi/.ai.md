# Sync API Plugin

## Purpose

Versioned REST API (v1) for external tools (the Foundry module, scripts):
entity CRUD, a bidirectional sync protocol, API key management, request
logging, security events and an admin monitoring dashboard. WebSocket
events are documented in the websocket plugin's `.ai.md`.

## How It Works

### Authentication

`Authorization: Bearer chron_<hex>`: the middleware looks the key up by its
8-char prefix, verifies the full key against the stored bcrypt hash, and
requires it active and unexpired. A key is scoped to one campaign and carries
permissions (`read`, `write`, `sync`). A browser session on the same routes
gets a synthetic key (ID 0).

`X-Device-Fingerprint` binds to the key on first use; a different
fingerprint later is rejected and logged as a security event.

`X-Chronicle-Module-Version` (matching `^[0-9A-Za-z.+\-]{1,32}$`) updates the
key's `module_version` in the statement that stamps `last_used_at`; an absent
or malformed header leaves it unchanged, and the synthetic key is never
written. The Foundry page compares the newest active key's version with the
one Chronicle serves.

### Rate limiting

Fixed window per key per minute, set per key (default `DefaultKeyRateLimit`
300, max 1000). `ReconcileLegacyRateLimits` moves keys still on the old default
of 60 to 300 at boot. `X-RateLimit-Limit`/`X-RateLimit-Remaining` on every
response; over the limit is 429 with `Retry-After` (seconds to window
reopen). CORS exposes all three. The limiter is in-memory, not Redis
(single-instance deployments).

### Addon gating

Calendar, maps, shop-room, reward and stash endpoints sit behind
`RequireAddonAPI`: 403 `addon_disabled` (slug in the message) when the addon
is off for the campaign, 503 when the check fails (fail closed). Not a 404, so
a client can tell "switched off" from "Chronicle too old". The gate is applied
per route through `addonRoutes`, never on a `cg.Group("", ...)`: an Echo group
with middleware also claims every unknown path under its prefix and would
answer them with an unrelated addon's 403. Unknown paths answer 404.

The `sync-api` addon gates the key, not the route: `RequireSyncAPIAddon`
(on both `/api/v1` groups and on `AuthenticateKeyForWS`) refuses real Bearer
keys with 403 `sync_api_disabled` when the addon is off; synthetic session
keys always pass (the toggle revokes outside access, not Chronicle's own UI).
A campaign with no `campaign_addons` row is denied; `CreateKey` enables the
addon and a boot reconciler backfills existing campaigns without re-enabling
one that was switched off.

### Middleware stack

Two groups at `/api/v1`:

- `v1` (JSON): `RequireAuthOrAPIKey` -> `RequireKeyOwnerStillOwner` ->
  `RequireSyncAPIAddon` -> `RateLimit` -> `RequireJSONContentType` ->
  `WithChangeSource`; campaign routes add `RequireCampaignMatch` ->
  `RecordSyncHistory`, then per route `RequirePermission` and optionally
  `RequireAddonAPI`. `RequireJSONContentType` answers 415 for
  POST/PUT/PATCH without `application/json`; safe methods pass.
- `v1Multipart`: the same chain without `RequireJSONContentType` and
  `WithChangeSource`. Only `POST /campaigns/:id/media` mounts here; any new
  multipart endpoint goes here, not on `v1`.

`RequireKeyOwnerStillOwner` refuses a stored Bearer key once its creator is no
longer an Owner of the key's campaign (`AuthenticateKeyForWS` applies the same
rule, so a demoted creator's key is refused, not granted Owner). Session
callers pass.

`WithChangeSource` puts a `changesource.Source` on the request context: a
Bearer key is `foundry` (with the key holder's user id), a session is `web`.
Observers of entity field writes (the stash money history) read it; it grants
nothing.

### Security rules

- **IDOR:** every endpoint verifies entity/event/media ownership against the
  key's campaign. `PUT`/`DELETE` on a relation or note resolve the object and
  404 on a campaign or ownership mismatch before the owning plugin's
  visibility gate; the campaign match alone is not trusted for an object
  addressed by its own id.
- **Egress sanitization:** `GetEntity`, `ListEntities`, `GetNote`, `ListNotes`,
  `GetEvent`, `ListEvents` re-sanitize HTML fields on the response copy
  (`egress_sanitize.go`, `sanitize.HTML`/`HTMLPtr`) before `c.JSON`. Ingress
  sanitization in each source plugin is the primary defense; egress covers
  rows that slipped past it. Scope is `/api/v1/*` only: the backup/restore
  round trip is lossless and must not be re-sanitized.
- **Role resolution:** `GetCurrentDate` filters dm_only celestial and
  world-state data with `resolveRole` and the caller's forwarded identity (a
  `sync` key resolves to Owner, read/write to Player), with no second
  filter: two visibility paths over the same data diverge.
- **Partial updates:** `apiUpdateEntityRequest` and `syncChange` use
  `patch.Field` for every content field (`parent_id`, `is_private`,
  `type_label`, `entry`, `name`), so a narrow body such as `{name}` cannot
  detach a parent, un-private a page or blank a label.
- **Media URLs** are HMAC-signed when a signer is configured, with
  `media.SignedURLTTL` expiry.
- Request logging and security events are fire-and-forget goroutines.

### Sheet field check

The entity service saves any `fields_data`, so create, update, fields and
batch-sync check it first (`field_check.go`) and answer 400 naming every bad
key, saving nothing (a batch row gets the error instead). A key must be
declared by the page's category or by a game system's sheet preset; a number
field takes a number, a string holding one, or `""`. A value sent back
unchanged passes, and null clears a key. Other field types are not checked.

### Stash Endpoints (stash addon)

`stash_api_handler.go` is thin and calls `StashAPIService`, which
`internal/app` implements over the stash plugin (the addon slug is passed in by
the wiring). JSON is camelCase, money is a number in whole currency units, and
a stash id may be a string or a number.

**Acting member.** Foundry holds one GM key but speaks for whichever player is
at the table, so every call may carry `actingUserId` (query on GET, body on
POST/PUT). It must be a current member (else 404). The call runs as that
member with their real role and DM-access grant, never the key's Owner role
unless they are an Owner or have DM access. Only a caller who is an Owner or
has DM access may name someone else (else 403); a session caller acts as their
own user. Naming a player can only narrow what the call may do, so a module
relaying a player cannot approve requests or flip downtime. Absent
`actingUserId` acts as the key holder.

| Method | Path | Permission | Description |
|--------|------|------------|-------------|
| GET | `/stashes/view` | read | `?characterId=&actingUserId=` → `{downtimeOpen, character:{id,name,moneyKey,money,items}, stashes:[{id,name,money,items}], destinations:[{kind,id,name}], canApprove}`, computed as the actor with the web panel's rules and redaction |
| POST | `/stashes/moves` | write | `{actingUserId, kind, itemId, quantity, amount, from:{kind,id}, to:{kind,id}}` → `{status:"applied"\|"pending", move}` |
| GET | `/stashes/history` | read | `?characterId=\|stashId=&actingUserId=` → `{history:[…]}`; a sheet money edit is a row whose two ends are the same character; at most the 50 newest rows |
| GET | `/stashes/requests` | read | Pending requests with display names; the actor must be able to approve |
| POST | `/stashes/requests/:moveId/approve`, `/decline` | write | Body `{actingUserId}` optional; the actor must be able to approve |
| GET | `/stashes/downtime` | read | `{open}` |
| PUT | `/stashes/downtime` | write | `{open, actingUserId}`; approver only; opening applies waiting requests |

Live events (`stash.*`, `downtime.changed`) are in `internal/websocket/.ai.md`.

### Calendar Endpoints (calendar addon)

Every route works on the campaign's default calendar through
`calendar.CalendarService`'s `(calendarID, campaignID)` methods, with a Viewer
built as the calendar pages build it (`VisibilityRole`: the key owner's live
role, Owner for a DM-access grant; a stored Bearer key's owner is a live
Owner). The service's filtering applies: hidden calendars, moons, eras and
event kinds (Owner only), dm_only and per-user events, and unannounced future
events never reach a player.

`GET /calendar`, `/calendar/date`, `/calendar/events` and
`/calendar/weather/days` also take `?audience=players`: the read is filtered
for an anonymous Player whatever the key's role (the GM client builds the
players' date bar from it). The date, events and day-weather answers then
carry `"audience":"players"`, so the module can tell a server that ignored the
parameter.

## Sync Protocol

`POST /sync` pulls and pushes in one request.

- **Pull:** `since` (RFC3339) returns entities modified after it. One request
  walks at most 10 internal pages of 100; if more remain the response sets
  `has_more` and `next_cursor`, and the client re-POSTs the same `since` with
  the cursor until `has_more` is false. The next `since` is the `server_time`
  of the first response of the walk, not the last, or anything modified
  mid-walk is skipped.
- **Push:** `changes` is an array of `{action, entity_id, ...}` with action
  `create`, `update` or `delete`, at most 2000. Content fields are
  `patch.Field`: on `update` an absent field keeps the stored value and a
  present one replaces it; `create` reads each absent field as its zero default.
- **Response:** `server_time`, `entities`, `next_cursor` (when `has_more`) and
  `results` with per-change status.

## Dashboard and admin

## Change feed

`RecordingEventBus` (`sync_change_bus.go`) wraps the WebSocket EventBus. For an
allowlisted type (entity, entity_type, note, marker, drawing, token, layer,
fog, map, relation, calendar.event, stash, downtime) it appends a
`sync_changes` row, stamps the message with `seq`, then publishes. The insert
has a 500ms timeout; on failure it logs and still publishes, so live delivery
never waits on the feed. The row is written after the domain write commits, so
a crash between the two drops that change; clients recover through
`resetRequired`. `StartChangePruner` deletes rows older than 30 days daily and
raises the per-campaign `sync_change_watermarks.pruned_through`. The feed
carries no sender; echo suppression is the module's job. A `relation` row's
resource is the relation's source entity: refetch
`GET /entities/:id/relations`.

## Sync history

One record of syncing both ways, shown on the Sync history page
(`/campaigns/:id/sync-history`, owner and members with DM access) and in the
module's History tab through `GET /sync/history`. Rows live in `sync_events`
(plugin migration 009); a catch-up run is a parent row with its steps as
children.

- `RecordSyncHistory` records changes arriving in Chronicle: every write a real
  API key makes (status, timing, error message), and reads only when the
  server failed them. Session callers and token-drag position updates are
  skipped. The insert runs after the response, with a 2 s timeout, and never
  fails the call.
- The module reports changes applied in Foundry, connects and catch-up runs
  (`POST /sync/history`), since only it knows a change landed. For a
  `to_foundry` row the server names the Chronicle editor from the page's change
  log (`ChangeEditorLookup`).
- A row names the key holder (the GM), except a successful shop buy or stash
  call that acted as another member: that member, and only after
  `StashAPI.ActorFor` accepted them (`noteSyncActor`). An unchecked
  `actingUserId` never names anyone.
- `StartHistoryPruner` daily deletes rows older than 90 days, and Foundry
  player reports and monster lists not refreshed for 30 days.

### Call flow

A failed row on the history page opens its call flow: surrounding steps drawn
as arrows between three lanes (Chronicle in a browser, the Chronicle server,
Foundry). Admin > API & access opens the same flow under a campaign row,
around its latest failure in the last day, with page names hidden ("Page 1")
and Foundry's error text left out.

- Routes: `GET /campaigns/:id/sync-history/flow/:eventID` (same gate as the
  page; only steps about the same thing; a fragment, so a non-HTMX request
  redirects to the history page) and `GET /admin/api/sync-flow/:campaignID`
  (site admins; every thing).
- `buildCallFlow` (`sync_flow.go`) turns rows into steps: a `to_chronicle` row
  is Foundry's call and Chronicle's dashed answer; a `to_foundry` row is the web
  edit (when the change log names an editor), Chronicle telling Foundry, and
  Foundry applying it; anything else is a loop in Foundry. Steps about the same
  thing (`flowGroupKey`) under 2 minutes apart chain as cause and result. The
  window is 5 minutes either side, at most 40 rows.
- `sync_flow_problems.go` explains a failure: what happened, why, what Foundry
  does next, how to fix it, and the same call failing in the last 24 hours.
  `SetDate` notes the date asked for and the one it replaces (`noteSyncChange`,
  stored in `was_value`, plugin migration 010) before its owner check.
- `static/js/sync_flow.js` fetches the flow on open and handles times in the
  reader's zone, selecting, chaining and the "Only problems" and per-thing
  switches.

## Monsters in Foundry

The GM's client reports the monsters its world can place
(`POST /sync/monsters`, `foundry_monsters.go`): NPC actors and Actor
compendium entries, each `{name, pack, level, role, organization, ev, linked,
page?}` (`pack` is the compendium label, empty for a world actor; `linked`
marks an actor creature sync made, `page` is that page's id). Owner or
DM-access keys only (403). `cleanMonsters` keeps at most 5000, drops nameless
entries and repeats of a name in the same place, strips control characters,
and caps names and packs at 120 and the rest at 40. The list is one row of
`foundry_monster_lists` (plugin migration 013), replaced by each report, with
the client's `truncated` flag. The AI connection's `foundry-monsters` lookup,
the encounter review and the creature matches read it.

### Creature matches

`foundry_matches.go`: each creature page (a page of a `creature` preset type,
listed by `CreaturePageLister` from `app`) is matched to the monster in the
latest report with the same name, case and spacing aside. A world actor wins
over a compendium entry; actors creature sync made never match (they mark the
page `inPlay`). A name equal only after dropping punctuation, a bracketed note
and a plural `s` is `suggested` until the DM confirms. The match is computed on
every read (`matchCreature`); only the DM's choices are stored, one row per
page in `foundry_monster_matches` (plugin migration 016): a hand-made match,
whose numbers play (`foundry` or `page`; empty means `page` while `inPlay`,
`foundry` otherwise), and names the DM said are a different creature. States:
`matched`, `suggested`, `missing` (hand-matched, no longer reported), `none`,
`not_reported`.

| Method | Path | Notes |
|--------|------|-------|
| GET | `/api/v1/campaigns/:id/foundry-matches` | `{data:[match...],total,truncated,reportedAt}` |
| GET | `/api/v1/campaigns/:id/foundry-monsters?q=` | Unlinked monsters whose name holds `q`, at most 50, for "Match another" |
| GET | `/api/v1/campaigns/:id/entities/:entityID/foundry-match` | `{match,reportedAt}`; 404 for a non-creature page |
| PUT | same | `{"action":"use","use":"foundry"\|"page"}`, `{"action":"match","name","pack"}` (must be reported), `{"action":"not_same","name"}`, `{"action":"reset"}`; answers `{match}` |

All four are owner or DM-access only (`isDMEquivalent`), session or key. A
match is `{entityId,entityName,state,monster?,use?,useChosen,confirmed,inPlay}`.
The Foundry page's "Creatures in Foundry" card (`foundry_creatures.templ`,
`GET /campaigns/:id/foundry/creatures`, owner) lists every page, look-alikes
first, with Match and Not the same buttons
(`POST /campaigns/:id/foundry/creatures/:eid`).

## Players in Foundry

The GM's client reports the world's users every few minutes and on change
(`POST /sync/players`, not recorded in the history). Owner or DM-access keys
only (403). `cleanPlayers` stores at most 100 users, ids of printable ASCII up
to 64, names cut to 100 and failure text to 200 with control characters
removed, and drops a member id not in the campaign. Each report replaces the
campaign's rows in `foundry_players` (plugin migration 011).

- `carryForward`: a report keeps what an earlier one knew; the newer of each
  `LastChangeAt` and `LastFailedAt` wins, since the module counts changes only
  while the world is open.
- `buildPlayerRows`: a linked player is Working when a synced change is within
  7 days (`recentWindow`), Sync failed when the latest sync failed, Linked
  (Idle) otherwise.
- `onlineNow`: online only when the report says so, it is under 11 minutes old
  (`playerOnlineWindow`; the client reports every five and sends nothing when
  the world closes) and the campaign's Foundry world is connected
  (`SetWorldPresence`; unset, the report's age alone decides).

Players never push document changes from their own clients; their shop buys and
stash moves reach Chronicle through the GM's client. So a player's "last
action" and "failures" are those relayed actions, and the GM's row also covers
the GM's own synced changes.

Only the owner reads the rows: the Foundry page's Players in Foundry table and
recent problems, and the "In Foundry" column on People (an out-of-band swap
into each member's cell).

## Foundry scenes

The GM's client reports the world's scenes on connect and soon after one is
made, renamed, moved or removed (`POST /sync/scenes`, not recorded in the
history), so the owner and the owner's AI can tell which maps already exist in
Foundry. Only names, folder paths and two flags travel (the scene players are
on, whether it is in the scene bar), never pictures. Owner or DM-access keys
only (403). `cleanScenes` caps a report at 2000 scenes, ids at 64 printable
ASCII characters, names and folders at 255 with control characters removed, and
keeps the first of a duplicate id. Each report replaces the campaign's
`foundry_scenes` rows and its one `foundry_scene_reports` row (plugin
migrations 014, 015); the report row keeps when it came and the `truncated`
flag, and lets a world with no scenes read differently from one that never
reported. Rows are not pruned. Scenes keep the module's order, Foundry's
sidebar order (`position`), never re-sorted by name.

The page editor marks a mentioned scene "in Foundry" or "map needed"
(`static/js/widgets/editor_scene.js`) from `GET /campaigns/:id/foundry/scenes`
(`ScenesJSON`, session route), which answers `{reported, truncated, reportedAt,
scenes:[{id,name,folder}]}`. Scene names can give away what is coming, so the
route answers 403 unless the viewer may author DM-only content
(`CanAuthorDmOnly`), and the AI's `scenes` lookup refuses players.
