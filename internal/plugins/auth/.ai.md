# Auth Plugin

## Purpose

User authentication, sessions and account security: login, registration,
logout, password reset, account settings, two-factor, provider sign-in, guests,
the CSRF double-submit cookie and session validation. Other plugins import
`auth` for `RequireAuth`, `GetSession` and `GetUserID`. `service.go` never
imports Echo types.

**Tier:** Plugin (core, always enabled).

## Domain Concepts

- **User:** an account with email, password and profile.
- **Session:** a Redis record linking a cookie to a user. The token is 32 random
  bytes as hex in the `chronicle_session` cookie.

## Business Rules

- Passwords are hashed with argon2id.
- Sessions live in Redis; TTL is `SESSION_TTL` (default 30 days)
- Login is limited to 10 attempts per minute per IP (registration 5), plus a per-email throttle in `service.go`: after 10 failures in 15 minutes, further attempts are delayed progressively
- Email is unique, case-insensitive
- My view (`users.view_prefs`, JSON, NULL = defaults) is per account. Values:
  theme `device|light|dark`, motion `owner|calm`, textSize
  `standard|larger|largest`, contrast `standard|high`; the first of each is the
  default. The PUT is partial (absent preserves, null or "" resets that choice,
  anything outside the list is a 400) and writes only the caller's own row;
  nothing reaches a campaign's settings or another member's page. The layout
  injector in `internal/app/routes.go` reads it and `layouts.ViewPrefAttrs`
  writes `data-view-theme` (always, when signed in), `data-view-motion="calm"`,
  `data-view-text` and `data-view-contrast="high"` on `<html>` beside the
  campaign's `data-cz-*`. CSS is in `static/css/input.css` ("My view");
  `static/js/theme.js` saves the top-bar toggle through the same endpoint.
- Notifications (`users.notify_prefs`, JSON, NULL = defaults): one switch per
  kind of message per channel; catalog, defaults and bell-type mapping are in
  `internal/notifyprefs`. `PUT /account/notifications` is partial. A kind not in
  the catalog, or a channel a kind never uses, is always delivered, so the filter
  only narrows. Safety mail (password reset, email change, invites, ownership
  hand-overs) cannot be switched off. If choices can't be read,
  `AllowedRecipients` keeps everyone.
- Deleting your own account (`POST /account/delete`) empties the users row
  rather than deleting it, because entities, relations and media reference users
  by foreign key and a delete would block or cascade away other members'
  content. The row keeps its id and gets a `deleted+<id>@deleted.invalid` email,
  the name "Former member", an unusable password, no profile or preferences,
  `is_disabled` and `deleted_at`. Order: checks, the campaigns side
  (`LeaveAllForDeletedAccount` removes every membership via `RemoveMember`), the
  row, all sessions, then `OnAccountDeleted` hooks (wired in
  `internal/app/routes.go`: character links cleared, private page notes and
  unshared notes deleted, sync API keys deactivated).
- Two-factor: `BeginTwoFactor` generates the authenticator key and holds it in
  Redis for 15 minutes; it is stored encrypted (`ConfigureTwoFactor`) only once a
  code from it checks out. Enabling returns eight twelve-character recovery
  codes, shown once, stored as hashes. Disabling or replacing codes asks for the
  password and a code. `Login` returns `*TwoFactorRequired` with a 10-minute
  challenge instead of a session; `CompleteTwoFactorLogin` takes a 6-digit code
  or a recovery code (the shape decides), and a code is accepted once even
  inside its window. Five wrong codes pause that account's code checks for 15
  minutes, across challenges. "Don't ask again on this device" is a 30-day
  cookie tied to the person; all remembered devices are forgotten when every
  session ends (password change or reset, admin sign-out) and when two-factor is
  turned off. Account deletion asks for a code too. Changing `SECRET_KEY` makes
  every stored key unreadable: those people sign in with a recovery code or an
  admin switches their two-factor off (from People: re-confirmed password,
  emailed to the person, logged; nobody can read the key).
- Guests: a guest code typed at `/join` with only a name creates an account with
  `guest_campaign_id` set, a placeholder email and no usable password; the
  campaigns plugin redeems the code through `GuestCodes` (`ConfigureGuests`).
  `RequireAuth` fences a guest's session to an allow list (`guestMayReach`: their
  campaign's routes, media, notifications, the guest panel, saving their
  timezone, sign-out); anything else redirects to their campaign, and under
  `OptionalAuth` they are anonymous. A banner offers to keep the account (email
  and password; every session is replaced) or merge it into an existing one
  (that account's password and two-factor code are checked like a sign-in;
  `OnGuestMerged` steps move membership, characters and notes, then the guest is
  emptied like a deleted account). A closed site takes no guests. The front
  page, Sign In and Sign Up link to `/join` (`layouts.HaveACodeLink`). For a
  guest, Log out warns first and sidebars omit the ways out of the campaign.
- Provider sign-in (one OpenID Connect provider per site, Admin > Sign-ins &
  sessions > Sign-in provider): round-trip state lives in Redis for 10 minutes,
  is single-use, and must match a cookie set in the browser that started it; the
  code exchange uses PKCE and the ID token is checked for this client and nonce.
  A provider account matches a Chronicle account by its link first; then by
  email only when the provider says the email is verified and sign-up isn't open
  (with open sign-up anyone could have registered that email first, since
  Chronicle never verifies it), which links it; then, if the admin allows
  sign-up this way and sign-up is open, a new account with no usable password
  (`!oidc!...`; Forgot password gives it one). Provider sign-in still asks for
  the two-factor code unless the device is remembered. Linking from the account
  page is a POST and the callback checks the signed-in person started it. Someone
  with no password of their own can't unlink. "Hide password sign-in" refuses
  password sign-in for everyone but admins, so a broken provider never locks the
  site out.
- Forgot password only offers to email a link when the site can send email (`CanEmailResetLinks`); otherwise the page says to ask the site admin.
- Password minimum is 8 characters

## Notes

- The login, register, forgot and reset password pages sit outside the app
  shell: they wrap content in `layouts.SiteAuthStage` and show
  `layouts.SiteAuthMark` (site name, logo and background from Admin > Site look).
- API access is not session auth; it uses per-campaign sync API keys (syncapi).
- A profile picture is visible to any signed-in user and denied to anonymous
  visitors; it has no campaign to scope to (`media.checkMediaAccess`, #730
  decision 2).
- `users.avatar_path` holds a media file id (rendered via `layouts.MediaURL`),
  never a raw path.
