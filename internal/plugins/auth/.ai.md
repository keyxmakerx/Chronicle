# Auth Plugin

<!-- Core plugin -- always enabled, cannot be disabled. -->

## Purpose

Handles user authentication, session management, and password security for
Chronicle: login, registration, logout, password reset, account settings, the
CSRF double-submit cookie, and session validation. Every other plugin that
needs a logged-in user imports `auth` for `RequireAuth`, `GetSession` and
`GetUserID`. Never import Echo types in `service.go`; the handler/middleware
boundary is especially important here.

## Tier

Plugin (Core -- always enabled)

## Domain Concepts

- **User:** A registered account with email, password, and profile info.
- **Session:** A server-side record (stored in Redis) linking a cookie to a user.
- **Session Token:** 32-byte random hex token stored in `chronicle_session` cookie.

## Business Rules

- Passwords hashed with argon2id (memory-hard, GPU-resistant)
- Sessions stored in Redis with configurable TTL (default 30 days)
- Login rate limiting: 10 attempts per minute per IP (registration 5), plus a per-email throttle in `service.go`: after 10 failures in 15 minutes, further attempts are delayed progressively
- Email must be unique (case-insensitive)
- My view (`users.view_prefs`, JSON, NULL = all defaults) is per account and per viewer. Values: theme `device|light|dark`, motion `owner|calm`, textSize `standard|larger|largest`, contrast `standard|high`; the first of each is the default. The PUT is partial (absent preserves, null or "" resets that one choice, anything outside the list is a 400). Only the signed-in person's own row is written; nothing here reaches a campaign's settings or another member's page. `internal/app/routes.go`'s layout injector reads it for full-page renders and `layouts.ViewPrefAttrs` writes `data-view-theme` (always, when signed in), `data-view-motion="calm"`, `data-view-text` and `data-view-contrast="high"` on `<html>` beside the campaign's `data-cz-*`. The CSS is in `static/css/input.css` ("My view"); `static/js/theme.js` saves the top-bar toggle through the same endpoint.
- Notifications (`users.notify_prefs`, JSON, NULL = defaults) are one switch per kind of message per way it arrives; the catalog, defaults and bell-type mapping are in `internal/notifyprefs`. `PUT /account/notifications` is partial. A kind not in the catalog, or a channel a kind never uses, is always delivered, so the filter only ever narrows. Safety mail (password reset, email change, invites, ownership hand-overs) is not in the catalog and can't be switched off. If the choices can't be read, `AllowedRecipients` keeps everyone.
- Deleting your own account (`POST /account/delete`) empties the users row instead of deleting it: entities, relations and media reference users with foreign keys that would block the delete or cascade away other members' content. The row keeps its id, gets a `deleted+<id>@deleted.invalid` email, the name "Former member", an unusable password, no profile or preferences, `is_disabled` and `deleted_at`. Order: checks, then the campaigns side (`LeaveAllForDeletedAccount` removes every membership through `RemoveMember`), then the row, then all sessions, then `OnAccountDeleted` (wired in `internal/app/routes.go`: character links cleared, private page notes and unshared notes deleted, sync API keys deactivated).
- Two-factor: the authenticator key is generated by `BeginTwoFactor`, waits in Redis for 15 minutes, and is stored (encrypted, `ConfigureTwoFactor`) only once a code from it checks out. Turning it on returns eight twelve-character recovery codes, shown once; only their hashes are kept. Turning it off or replacing the codes asks for the password and a code. `Login` returns `*TwoFactorRequired` with a 10-minute challenge instead of a session; `CompleteTwoFactorLogin` takes a 6-digit code or a recovery code (the shape decides), and a code is accepted once even inside its time window. Five wrong codes pause that account's code checks for 15 minutes, across challenges. "Don't ask again on this device" is a 30-day cookie tied to the person; every remembered device is forgotten when all their sessions end (password change or reset, admin sign-out) and when two-factor is turned off. Deleting the account asks for a code too. Changing `SECRET_KEY` makes every stored key unreadable: those people sign in with a recovery code, or an admin switches their two-factor off. An admin can switch two-factor off from People (re-confirmed password, emailed to the person, logged); nobody can read the key.
- Provider sign-in (one OpenID Connect provider per site, set under Admin › Sign-ins & sessions › Sign-in provider): a round trip's state is kept in Redis for 10 minutes, used once, and must match a cookie set in the browser that started it; the code exchange uses PKCE and the ID token is checked for this client and this round trip's nonce. A provider account is matched to a Chronicle account by its link first, then by email only when the provider says the email is verified (which links it), then, if the admin allows sign-up this way and sign-up is open, a new account with no usable password (`!oidc!…`; Forgot password gives it one). A provider sign-in skips two-factor. Linking from the account page is a POST and the callback checks the signed-in person is the one who started it. Someone with no password of their own can't unlink. "Hide password sign-in" refuses password sign-in for everyone but admins, so a broken provider never locks the site out.
- Forgot password only offers to email a link when the site can send email (`CanEmailResetLinks`); otherwise the page says to ask the site admin.
- Password minimum 8 characters

## Notes

- The four pages outside the app shell (login, register, forgot and reset
  password) wrap their content in `layouts.SiteAuthStage` and show
  `layouts.SiteAuthMark`: the site name, logo and sign-in background an admin
  set under Admin > Site look. With nothing saved they render as shipped.

- API access is not session auth: it uses per-campaign sync API keys (see the syncapi plugin).
- A profile picture is visible to any signed-in user (not campaign-scoped —
  it has no campaign to scope against). Anonymous visitors are denied. See
  `media.checkMediaAccess`'s avatar branch and #730 decision 2.
- `users.avatar_path` holds a media file id (rendered via `layouts.MediaURL`),
  never a raw path. `reconcile_avatar_paths.go` runs at every boot to migrate
  or clear any row still holding the dead pre-M0 `/uploads/avatars/...` path.
