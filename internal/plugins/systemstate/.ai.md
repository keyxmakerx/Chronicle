# System State Plugin

## Purpose

Keeps per-page game-system state: small JSON documents a game-system package's
widget reads and writes for one entity, such as a negotiation tracker on an NPC
page. Chronicle stores, scopes and gates the documents; it never interprets
them, so a system adds a new kind of state without a Chronicle release.

Each document is addressed by `(entity, system, key)` and has two halves split
by audience:

- `public`: readable by anyone who can view the page.
- `gm`: returned only to the campaign owner and members given DM access
  (`CampaignContext.CanAuthorDmOnly()`), never to a scribe or player without
  it. When withheld, the `gm` member is absent from the response entirely.

| File | Purpose |

| `routes.go` | Route registration; PUT gated to the DM team |

## Routes

| Method | Path | Who | Notes |
|--------|------|-----|-------|
| GET | `/campaigns/:id/entities/:eid/system-state/:system/:key` | any member who can view the page | `{systemId,key,public,gm?,isGm,updatedAt}`; `gm` only with `CanAuthorDmOnly()`. A page the viewer cannot see, or an entity from another campaign, is 404. |
| PUT | same path | `RequireCapability(CanAuthorDmOnly)` | Body `{"public":{...}?,"gm":{...}?}`; returns the GET shape. |

The sync API serves a read-only twin at
`GET /api/v1/campaigns/:id/entities/:entityID/system-state/:system/:key`
(`syncapi/system_state_api.go`), with the same shape and the same `gm` rule
(Owner after DM-grant promotion).

## Business Rules

- **Partial update.** In `Put`, a half that is absent keeps the stored half; a
  present half replaces it. `{}` clears a half. A JSON `null` is rejected, not
  read as absent (the handler decodes members raw so null survives to the
  service). Unknown body members are rejected.
- `system` and `key` match `^[a-z0-9][a-z0-9_-]{0,63}$`; each half is a JSON
  object of at most 16 KiB (`MaxHalfBytes`).
- The entity must belong to the campaign in the URL (`EntityLookup`); the
  handler also applies the entities show-page visibility gate.
- A write needs the system to be the campaign's enabled system
  (`SystemChecker`). Reads do not, so data survives a system being switched off.
- Last write wins; there is no version check. Two DMs editing the same half at
  once overwrite each other; separate halves do not interfere (single upsert).
- After a write the service publishes `system_state.updated` (`{systemId,key}`,
  `resourceId` = entity id, `RequiresDM`). It is not a change-feed type.

## Dependencies

All through narrow interfaces wired in `internal/app/system_state_adapters.go`
and `routes.go`: `EntityLookup` and `EntityAccess` over the entities service,
`SystemChecker` over the systems handler, `UpdatePublisher` over the WebSocket
bus. No import of another plugin's repository.

## Footguns

- Do not add a field to the response that reveals whether `gm` data exists to
  a caller who cannot read it.
- Keep `campaign_id` in every query; the primary key alone does not scope by
  campaign.
