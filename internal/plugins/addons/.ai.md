# Addons Plugin

## Purpose

The extension framework: installable addons (modules, widgets, integrations)
with a global registry the site admin manages and per-campaign enable/disable
for campaign owners. `player-character-claiming` is a typical example: it gates
the claim UI and the Foundry actor-sync claim stage.

Other plugins gate features with `IsEnabledForCampaign(ctx, campaignID, slug)`
on an injected addon-service interface (or `RequireAddon`); they never import
addons from their own `service.go`.

## Files

| File | Purpose |
|------|---------|
| `model.go` | `Addon`, `CampaignAddon`, `AddonCategory` / `AddonStatus`, DTOs |
| `repository.go` | SQL for `addons` and `campaign_addons` |
| `service.go` | Validation, status checks, campaign enable/disable, `builtinAddons` / `installedAddons` |
| `handler.go`, `routes.go` | Admin pages and campaign toggle API |
| `middleware.go` | `RequireAddon` |
| `setup_provider.go`, `setup_handler.go` | Extension settings / onboarding framework |
| `admin_addons.templ`, `campaign_addons.templ`, `extension_settings_{page,overlay,fragment}.templ` | Pages and fragments |

## Tables

- `addons`: global registry (id, slug, name, category, status, icon, ...).
- `campaign_addons`: per-campaign state (campaign_id, addon_id, enabled, `config_json`).

## Routes

Admin (site admin): `GET /admin/addons`, `POST /admin/addons`,
`PUT /admin/addons/:addonID/status`, `DELETE /admin/addons/:addonID` (behind
re-auth; deleting removes the feature from every campaign).

Campaign (owner only):

| Method | Path | Does |
|--------|------|------|
| GET | `/campaigns/:id/addons/settings` | Settings page |
| GET | `/campaigns/:id/addons` | JSON list with campaign state |
| GET | `/campaigns/:id/addons/fragment` | HTMX list for the Customization Hub Extensions tab |
| PUT | `/campaigns/:id/addons/:addonID/toggle` | Enable/disable |

## Middleware and rules

- `RequireAddon(svc, slug)` (after `RequireCampaignAccess`): disabled gives a
  404 to HTMX and fetch/JSON callers and a redirect to the dashboard otherwise;
  a failed lookup lets the request through. Applied to the calendar, maps,
  timeline, media-gallery, npcs and armory groups, the entity-notes widget
  (`player-notes`) and sessions (gated on `calendar`).
- A new addon starts `planned` and must be `active` to be enabled. Only slugs in
  `installedAddons` (active entries of `builtinAddons`, i.e. with backing code)
  can be activated or enabled.
- Disabling keeps `config_json`; re-enabling restores it.

## Setup provider framework (ADR-043)

An addon may register a slug-keyed `SetupProvider { Slug(); RunChecks();
Questions(); Apply(answers) }` that drives a per-extension settings/onboarding
page with no per-addon template.

- Types (`SetupCheck`, `SetupQuestion`, `SetupResult`, `SetupState`) are
  addons-local, so `addons` never imports `entities`/`systems`. Providers live
  in the app layer (`app/setup_pc.go`) and register through
  `addonService.RegisterSetupProvider` in `app/routes.go`.
- State `{completed, dismissed, answers}` lives in
  `campaign_addons.config_json["setup"]` via `UpdateCampaignConfig` (read-merge-write
  keeps other keys): no table. `GetSetupState`, `SaveSetupState`, `NeedsSetup`
  are on `AddonService`.
- Owner-gated routes: `GET /campaigns/:id/extensions/:slug/settings` (overlay
  fragment or full page), `POST .../settings/apply` (runs `Apply`, persists,
  re-renders, fires `extensions-hub-refresh` and a `chronicle:notify` toast),
  `POST .../settings/dismiss`.
- The Extensions hub card (`campaigns/extensions_hub.templ`) shows a "Setup" pill
  and "Open setup" button when `PluginHubAddon.NeedsSetup` (computed per campaign
  in `app/routes.go`). On enable, `ToggleCampaignAddon` co-emits the toast.
- First provider: player-character setup (`app/setup_pc.go`; see `entities/.ai.md`).
