# System Framework

## Purpose

The system framework enables game system content packs to be added to Chronicle
with minimal or zero custom Go code. Systems are **read-only** — they serve
reference data (spells, monsters, items, classes, etc.) as browsable pages,
searchable lists, and hover tooltips. They never modify campaign data.

## Architecture

### Two Paths to Create a System

**1. Zero-Code (Generic System)** — Drop files, done:
```
internal/systems/my-system/
  manifest.json    # Categories, fields, metadata
  data/
    spells.json    # ReferenceItem[] per category
    monsters.json
    feats.json
```

The loader auto-discovers the manifest, loads JSON data via `JSONProvider`,
and creates a `GenericSystem` with a `GenericTooltipRenderer` that reads
field definitions from the manifest. No Go code needed.

**2. Custom Factory (Override)** — For richer rendering:
```go
// internal/systems/<slug>/<slug>.go
func init() {
    systems.RegisterFactory("<slug>", func(m *systems.SystemManifest, dataDir string) (systems.System, error) {
        // Custom tooltip renderer, special formatting, etc.
        return NewCustomSystem(m, dataDir)
    })
}
```

Register a factory in `init()` and the loader uses it instead of the generic
path. Use this when a system needs category-specific stat-block formatting
beyond what the manifest-driven generic tooltip renderer can express.

### Discovery & Loading Flow

```
systems.Init("internal/systems")
  └── SystemLoader.DiscoverAll()
        ├── Scan subdirectories for manifest.json
        ├── Parse + validate each manifest
        ├── For each "available" system:
        │     ├── Factory registered? → factory(manifest, dataDir)
        │     └── No factory? → NewGenericSystem(manifest, dataDir)
        └── Sort by name, register in global registry
```

### Key Types

| Type | File | Role |
|------|------|------|
| `System` | system.go | Interface: Info + DataProvider + TooltipRenderer |
| `SystemManifest` | manifest.go | JSON manifest with categories, fields, presets |
| `CategoryDef` | manifest.go | Category slug, name, icon, field schema |
| `FieldDef` | manifest.go | Property key, label, type (string/number/list/markdown) |
| `ReferenceItem` | system.go | Universal data shape: name, summary, properties map, tags |
| `DataProvider` | system.go | Interface: List, Get, Search, Categories |
| `TooltipRenderer` | system.go | Interface: RenderTooltip, SupportedCategories |
| `JSONProvider` | json_provider.go | Loads `data/*.json`, auto-discovers categories |
| `GenericSystem` | generic_system.go | System impl using JSONProvider + GenericTooltipRenderer |
| `GenericTooltipRenderer` | generic_tooltip.go | Manifest-driven tooltip: iterates FieldDefs in order |
| `SystemLoader` | loader.go | Scans directories, discovers manifests, instantiates modules |

### Duplicate resolution (never silently downgrade)

Both discovery paths register manifests through `register`/`preferCandidate`
(loader.go), so a duplicate **system ID** can't be resolved by scan order. Policy:
highest `version` wins (numeric `versionLess`); on an exact-version tie a
`package`-source copy overlays a `bundled` one; an older/stale duplicate (e.g. a
leftover `<slug>-1` directory) is **skipped**, not loaded — and the skip is gated
so it can't sneak back in via `systemInstances` instantiation. Skips emit
`EventSkipped` (event_log.go) for the admin diagnostics/event log. The
package-manager scan in registry.go independently picks the newest version
*subdirectory* per slug; this is the ID-collision-level guard beneath it. Tests:
`loader_dedup_test.go`.

### Manifest Schema

```json
{
  "id": "my-system",
  "name": "My RPG System",
  "description": "Reference data for My RPG",
  "version": "1.0.0",
  "author": "You",
  "license": "CC-BY-4.0",
  "icon": "fa-dice-d20",
  "api_version": "1",
  "status": "available",
  "categories": [
    {
      "slug": "spells",
      "name": "Spells",
      "icon": "fa-magic",
      "fields": [
        { "key": "level", "label": "Spell Level", "type": "number" },
        { "key": "school", "label": "School", "type": "string" },
        { "key": "components", "label": "Components", "type": "string" }
      ]
    }
  ],
  "entity_presets": [
    {
      "slug": "my-character",
      "name": "Character",
      "name_plural": "Characters",
      "icon": "fa-user",
      "color": "#4a90d9",
      "fields": [
        { "key": "level", "label": "Level", "type": "number" }
      ]
    }
  ]

```

### Data File Format

Each `data/<category>.json` contains an array of `ReferenceItem`:

```json
[
  {
    "id": "fireball",
    "name": "Fireball",
    "summary": "A bright streak of fire explodes in a 20-foot radius",
    "description": "Full spell text here...",
    "properties": {
      "level": 3,
      "school": "Evocation",
      "components": "V, S, M"
    },
    "tags": ["evocation", "fire", "damage"],
    "source": "Core Rulebook"
  }
]
```

The filename determines the category slug (`spells.json` → "spells").

### Renderers (page-renderer binding)

`SystemManifest.Renderers []RendererDef` (`manifest.go`) lets a pack take over an
entity's show page by mounting one of its own widgets — zero Go (see
`docs/system-package-rendering.md` for the full contract). At boot,
`registerManifestRenderers` (`internal/app/routes.go`) wires each entry into the
`EntityShowRendererRegistry`.

A `RendererDef` binds by **slug XOR `PresetCategory`** (the validator enforces
exactly one):

- **`Slug`** — the renderer takes over the show page of a specific
  `entity_presets[].slug` the pack owns (the original, bespoke binding).
- **`PresetCategory`** (`"preset_category"`) — binds by entity-type
  `preset_category` instead, matching one of the pack's
  `entity_presets[].category`. This is the **system-agnostic seam**: the widget
  then renders **any** type carrying that preset (e.g. the player-character
  addon's category, whose slug Chronicle core owns), not just one bespoke slug.
  At lookup, `lookupEntityShowRenderer` resolves **slug first** (most specific),
  then falls back to the entity type's `PresetCategory` — so a pack's own
  slug-bound type is never shadowed and exactly one renderer fires.

```json
"renderers": [
  { "slug": "drawsteel-character", "widget": "character-sheet" },
  { "preset_category": "character", "widget": "character-sheet" }
]
```

**Page-renderer widgets are excluded from the layout palette.** A widget the
manifest registers as a renderer owns a whole page — it is **not** a placeable
layout block. `GetSystemWidgetBlockMetas` (`handler.go`) filters out any
`widgets[]` entry whose slug also appears in `renderers[].widget`, so it can't be
dropped into a layout (where it would mount without its page context and render an
empty "bare name"). Generic across systems — keyed on the manifest, not any
system name.

### Entity panels (`entity_panels`)

`entity_panels: [{"widget": "<widgets[].slug>", "applies_to": "npc"}]` makes the
host mount that widget under the title of every NPC-family page (the
`npcTypeIDs` rule in `app/routes.go`) in campaigns that have the system
enabled. It adds to a page; a renderer replaces one. Validation
(`validateEntityPanels`) requires the widget to exist in the same manifest and
`applies_to` to be `npc`. `app/system_panels.go` resolves the panels per page
and hands them to the entities plugin, which renders the mount
(`entities/system_panels.templ`). Panel widgets are left out of the layout
palette like renderer widgets (`placeableWidgetMetas`).

### Rulebook front-page mount (widget-slug binding)

The Rulebook reference index page (`SystemIndexContent`, `system_pages.templ`) —
what the sidebar's "Rulebook" link opens — mounts a system's `rulebook-frontpage`
widget in place of the generic category grid whenever the enabled system
declares one (the category routes stay up for the widget's links). The mount
fills the content area edge to edge: it sits in a wrapper whose negative margins
cancel `<main>`'s padding, with no breadcrumb above it. Whether it mounts comes from
`manifest.HasWidget("rulebook-frontpage")` (`manifest.go`), checked directly in
the templ rather than plumbed through the handler, since `Index` already has the
manifest in hand. No manifest field, no Go registration — a pack opts in purely
by naming a `widgets[]` entry `rulebook-frontpage`; any pack can fill this slot,
not just Draw Steel. The mount gets the campaign id through the widget's existing
`campaign_id` config (`data-campaign-id` → boot.js → `config.campaignId`), the
same as any other widget's `data-*` config. This is a fixed-slug binding — the
simpler cousin of the `renderers[]` slug/`preset_category` binding above — because
there is exactly one front page per system, not a per-entity-type dispatch.

### Rulebook book (`book.go`)

A package that ships `book/book.yaml` gets a full-screen, page-turning book on
the Rules page instead of its front-page widget or the category grid
(`SystemIndexContent` picks book, then front page, then grid). The author
format is `docs/system-rulebook-book.md`. The core widget
(`static/js/widgets/rulebook.js`, loaded from `pluginBodyScripts` in
`internal/app/routes.go` like every page script; `static/css/rulebook.css`,
linked from the page) fetches `GET .../systems/:mod/book` (`BookAPI`).

- `LoadBook` reads the YAML strictly (`KnownFields`, so a misspelt key is an
  error), checks every block, and turns a broken chapter into a `problem`
  chapter naming the file, page and block, so the rest of the book still works.
  Only a broken `book.yaml` fails the whole request.
- `FilterBook` is the one place the Player/Director split is decided:
  players never receive Director-only parts, chapters, pages or blocks, creature
  `stats`/`note`, or problem chapters. Directors are `bookViewerIsDirector`
  (owner or dm_only-granted, the same rule as other dm_only surfaces). The
  response is `Cache-Control: private, no-store` because it differs per viewer.
- `book/` is outside `data/` because `SystemDataAPI` serves `data/` raw; the
  book must always pass through `FilterBook`.
- Theme values become CSS custom properties, so they are pattern-checked
  (hex colours, plain font lists); `widget` blocks may only name the manifest's
  own widgets.
- Rules-index chapters (`book_index.go`): a chapter file with `index:` names a
  manifest category; `buildIndexChapter` makes one page per `group` value (or
  A-Z pages of `per-page`), each holding one `index` block that names its
  slice. Entries load lazily from `BookIndexAPI` (`.../book/index/:cat`), which
  serves only a slice a page of the viewer's own filtered book shows and drops
  `gm_only` fields for players. `BookFindAPI` (`.../book/find?q=`) searches
  those chapters for the book's search box; written pages are searched in the
  browser. Parsed data files are cached by path, size and mtime. Generated
  chapters are not editable (`BookChapterEntry.Generated`) and export as
  written.

### Rulebook editor (`book_edit_*.go`, `book_editor.templ`)

A campaign's Directors (owner, or a member with a Director grant:
`cc.CanAuthorDmOnly()`, checked by `bookEditorAllowed` in every editor handler,
the page included) edit their campaign's copy of the book at
`.../systems/:mod/book/edit`. The package's files are never written; a
campaign's edition is the package book plus rows in `campaign_book_pages` and
`campaign_book_chapters`, merged on every read.

- `ApplyBookEdits` (`book_edit_service.go`) is the merge and runs in `BookAPI`
  BEFORE `FilterBook`, so a Director flag on a campaign page or block is
  honoured. A copy replaces the package page at its 0-based index; the
  campaign's own pages follow the package pages; a copy past the package's last
  page is kept after them; house-rules chapters (`house_` ids, which no package
  chapter id can match) form a last "House rules" part. Edits for a chapter the
  package no longer lists, or one that failed to load, are ignored.
- Page states: `package` (no row), `edited` (copy whose `base_hash` still equals
  the package page's hash), `changed` (hash differs or the package page is
  gone), `mine` (own page). The hash is sha256 of the JSON of the authored page
  (`hashBookPage`). Saving a copy again keeps its old hash, so only "Keep mine"
  settles a changed page.
- Pages are stored as authored JSON (`authoredPage`, keys identical to the YAML)
  and re-checked on every read; one that no longer validates becomes a `problem`
  block Directors can read. Request pages go through the same strict decoder as
  package files (`decodeBookBytes`, JSON is YAML, unknown keys are errors) and
  `buildBookPage`, and are capped at the book's 1 MB file limit. An unwritten
  text block (a new chapter's starter page) is stored and shows nothing.
- Limits: 200 own pages per chapter, 50 house chapters, 200 chapters in the merged
  book. A house chapter always keeps at least one page.
- `UpdateBookChapterInput` is a partial update (`patch.Field`): absent keys keep
  their value, explicit null clears only the intro.
- The service takes a `*BookPackage` (package book plus its authored source,
  from `LoadBookPackage`) so it never touches the disk or Echo; the repository
  (`BookEditRepository`) owns the SQL, scoped by campaign and system.
- Export is a zip of package-format YAML (`book/book.yaml`,
  `book/chapters/*.yaml`) with the edition merged in; house chapters are written
  as `house-<slug>` (made unique against package ids) in an appended "House
  rules" part. A package chapter that failed to load has no authored form and is
  left out of the zip. Glossary files live in the package's `data/` and are not
  included.
- The editor widget is `static/js/widgets/rulebook_editor.js`, loaded from
  `pluginBodyScripts`; the page mounts it on `data-widget="rulebook-editor"`.

### Tooltip Rendering

**Generic (default):** `GenericTooltipRenderer` iterates the manifest's
`fields` array for the item's category, rendering each field with its
label and value. Only manifest-declared fields are shown, in manifest order.
Extra properties in the data are ignored in tooltips.

**Custom (override):** A module can implement its own `TooltipRenderer`
interface for richer formatting (stat blocks, icons, conditional layout,
category-specific property rendering).

## System Data Loading

Game systems have no bundled data directories in this repo. They load
exclusively from the **package manager** via `LoadAdditionalDir()` at
startup. The `Init("internal/systems")` call scans this directory for
manifests but normally finds none — it logs "no bundled systems found" and
proceeds normally; a manifest placed directly under `internal/systems/<id>/`
for local development is auto-discovered too (see below). A system with
custom rendering needs registers its factory via `systems.RegisterFactory()`
(`registry.go`) against its external data directory from the package
manager — there is no per-system subdirectory in this repo.

The Foundry VTT integration is the external `chronicle-foundry-module`
GitHub repo; there is no in-repo `foundry-module/` fallback.

## How to Add a New Game System

Systems are now created as **external packages** installed via the package
manager. To create a new system:

1. Create a GitHub repo with `manifest.json` + `data/<category>.json`
2. Tag a release (e.g., `v1.0.0`)
3. Register the package in Chronicle's admin UI
4. Install via the package manager — auto-discovered on install

For bundled development/testing, you can still place a manifest + data
under `internal/systems/<id>/` and it will be auto-discovered at startup.

For custom tooltip formatting, add a Go file with `init()` that calls
`systems.RegisterFactory()`.

### Custom Game System Upload

Campaign owners can upload custom game systems as ZIP files:
- `POST /campaigns/:id/systems/upload` — Upload ZIP (manifest.json + data/*.json)
- `DELETE /campaigns/:id/systems/custom` — Remove custom system
- `GET /campaigns/:id/systems/custom` — Get custom system status
- Stored under `media/modules/<campaignID>/`, auto-prefixed with `custom-`
- Bypasses addon check for the uploading campaign
- Data only: a ZIP with any `.js` file, or a manifest declaring `widgets` or
  `text_renderers`, is refused (`errCustomSystemScripts`), and scripts are
  never served or injected for a custom system, even one uploaded earlier.
  Only installed packages (`Dir(id)` non-empty) serve scripts.
- At most 200 files and 20 MB of data in total, counted from the bytes read

## Auto-Registration as Addons

Game systems are **automatically registered as addons**
at startup. The systems registry exports `AddonInfos()` which returns
addon metadata (slug, name, description, version, icon, author) for all
discovered systems with status "available". The app wiring calls
`addons.RegisterSystemAddon()` for each before `SeedInstalledAddons()`.

This means:
- **No hardcoded addon definitions** for game systems
- Dropping a system folder into `internal/systems/` auto-registers it
- Installing via the package manager auto-registers it
- Campaign owners uploading a ZIP auto-registers it (via CampaignSystemManager)
- The only Go import needed is for a system with **custom Go code** (a bespoke tooltip renderer registered via `systems.RegisterFactory()`)

## Dependencies

- **Uses:** nothing at runtime for the system framework itself (read-only, self-contained); the Rulebook edits (`book_edit_repository.go`) are the one part that reads and writes the database
- **Used by:** Entity pages (tooltips on @mentions), campaign addon settings, addon registry (auto-registration)

## The operator diagnostics live here too

`operator_diag*.go` is the admin-facing, read-only diagnostic catalog the AI
assistant chooses from (`GET /admin/diagnostics?name=…`). Adding a diagnostic =
appending one `Diagnostic{}` to `diagnosticCatalog()`; the renderer, route and
secret redaction are unchanged.

Two rules govern it, and both exist because a diagnostic that answers
confidently and wrongly is worse than one that does not exist:

1. **Cross-layer state arrives through an injected provider, never an import.**
   This package must not import a plugin. The app layer implements the provider
   interface and wires it in `RegisterRoutes` (`SetInstalledPackagesProvider`,
   `SetEntityDiagProvider`, `SetCampaignDiagProvider`, …).
   `internal/app/operator_diag_wiring_test.go` fails CI when a declared setter
   is never called — an unwired provider ships as a diagnostic that reports
   "provider not wired" forever, which reads like an answer.
2. **Degrade loudly.** A read that did not happen must never render like a read
   that returned nothing. "No addon rows" and "nobody could read the addon
   table" are different sentences, and several tests assert exactly that.

Do not add a diagnostic that MIRRORS another plugin's internal logic instead
of calling it; export a trace from the owning plugin.

### Dependencies note

The "Uses: Nothing" line above describes the SYSTEM FRAMEWORK. The diagnostics
half reads injected providers and `internal/hostinfo` / `internal/templates/layouts`.
