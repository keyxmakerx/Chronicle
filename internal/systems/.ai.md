# System Framework

Game system content packs: read-only reference data (spells, monsters, items,
classes) served as browsable pages, search and hover tooltips. Systems never
modify campaign data. No bundled systems live in this repo; they load from the
package manager via `LoadAdditionalDir()`. `Init("internal/systems")` scans this
directory, normally finds nothing (logs "no bundled systems found"), and also
auto-discovers a manifest placed under `internal/systems/<id>/` for local
development. The Foundry module is the external `chronicle-foundry-module` repo.

## Creating a system

External package: a GitHub repo with `manifest.json` + `data/<category>.json`,
tagged as a release, registered in Admin > Packages, installed through the
package manager (auto-discovered on install). Authoring rules and schema:
`docs/build/game-system.md`.

- **Zero code:** the loader finds the manifest, loads JSON via `JSONProvider`
  and builds a `GenericSystem` with a `GenericTooltipRenderer` driven by the
  manifest's field definitions.
- **Custom factory:** for stat-block formatting the manifest cannot express,
  call `systems.RegisterFactory("<slug>", func(m *SystemManifest, dataDir string) (System, error))`
  in `init()` (`registry.go`); the loader uses it instead of the generic path.
- Systems register themselves as addons: `AddonInfos()` (`registry.go`) returns
  metadata for every discovered "available" system, and `internal/app` calls
  `addons.RegisterSystemAddon()` for each before `SeedInstalledAddons()`. No
  hardcoded addon definitions for systems.

Discovery: `SystemLoader.DiscoverAll()` scans subdirectories for `manifest.json`,
parses and validates each, builds each "available" system (factory if
registered, else `NewGenericSystem`), sorts by name and registers it.

| Type | File | Role |

| `SystemLoader` | loader.go | Scans directories, instantiates systems |

## Duplicate resolution

Both discovery paths register manifests through `register`/`preferCandidate`
(loader.go), so a duplicate **system ID** can't be resolved by scan order. Policy:
highest `version` wins (numeric `versionLess`); on an exact-version tie a
`package`-source copy overlays a `bundled` one; an older/stale duplicate (e.g. a
leftover `<slug>-1` directory) is **skipped**, not loaded — and the skip is gated
so it can't sneak back in via `systemInstances` instantiation. Skips emit
`EventSkipped` (event_log.go) for the admin diagnostics/event log. Tests:
`loader_dedup_test.go`.

Package-installed systems load from the package catalog, not from the folders
on disk: the app layer (`loadSystemsFromPackages`) loads the installed folder
of each approved system package, so a leftover version folder or an archived
package never loads. Removing or archiving a package calls
`UnloadPackageDirsUnder` with the package's folder, which stops serving it at
once (`unload_test.go`).

### Manifest Schema

### Renderers (`renderers`)
`SystemManifest.Renderers []RendererDef` lets a pack take over an entity show
page with one of its own widgets (contract: `docs/system-package-rendering.md`).
`registerManifestRenderers` (`internal/app/routes.go`) wires each into the
`EntityShowRendererRegistry`. An entry binds by `slug` XOR `preset_category`
(the validator enforces exactly one):

- `slug`: a specific `entity_presets[].slug` the pack owns.
- `preset_category`: any entity type carrying that preset category (the
  system-agnostic seam). `lookupEntityShowRenderer` tries slug first, then the
  type's `PresetCategory`, so a slug-bound type is never shadowed and exactly
  one renderer fires.

```json
"renderers": [
  { "slug": "drawsteel-character", "widget": "character-sheet" },
  { "preset_category": "character", "widget": "character-sheet" }
]
```

A renderer widget owns a whole page and is never a placeable layout block:
`GetSystemWidgetBlockMetas` (`handler.go`) drops any `widgets[]` entry named in
`renderers[].widget`, since it would mount without page context and render
blank.

### Entity panels (`entity_panels`)
`[{"widget": "<widgets[].slug>", "applies_to": "npc"}]` mounts a widget on every
NPC page (types the owner listed as NPCs) in campaigns with the system enabled;
`"creature"` targets creature types (preset category `creature`, slug
`creature` or `*-monster`, with sub-types) whether or not listed as NPCs. A
panel adds to a page; a renderer replaces it. `validateEntityPanels` requires
the widget to exist in the same manifest and `applies_to` to be `npc` or
`creature`. `app/system_panels.go` resolves panels per page for the entities
plugin (`entities/system_panels.templ`). Panel widgets are left out of the
layout palette like renderer widgets (`placeableWidgetMetas`).

### Terms (`terms`)
`terms: {"gm": "Director"}` names the game master in the system's word. The
layout injector (`app/routes.go`) puts it in `layouts.GMTerm(ctx)` (default
"GM"); templates name the role only through it, widgets through
`Chronicle.gmTerm()` (the page's `data-gm-term`). `validateTerms` allows up to
24 letters, spaces, hyphens or full stops, starting with a letter, so it is safe
in any host-built text; it is used as is, pluralised with a plain "s". A
campaign's custom system has no terms.

### Rulebook front page
`SystemIndexContent` (`system_pages.templ`) mounts a system's
`rulebook-frontpage` widget in place of the category grid when
`manifest.HasWidget("rulebook-frontpage")` (checked in the templ; category
routes stay up for the widget's links). The mount fills the content area edge
to edge (negative margins cancel `<main>` padding, no breadcrumb) and gets the
campaign id through `data-campaign-id`. No manifest field or Go registration:
naming a `widgets[]` entry `rulebook-frontpage` opts in.

## Rulebook book (`book.go`)

A package shipping `book/book.yaml` gets a full-screen page-turning book on the
Rules page; `SystemIndexContent` picks book, then front page, then grid. Author
format: `docs/system-rulebook-book.md`. The widget `static/js/widgets/rulebook.js`
(from `pluginBodyScripts`, styled by `static/css/rulebook.css`) fetches
`GET .../systems/:mod/book` (`BookAPI`).

- `LoadBook` reads the YAML strictly (`KnownFields`: a misspelt key is an error),
  checks every block, and turns a broken chapter into a `problem` chapter naming
  file, page and block. Only a broken `book.yaml` fails the request.
- `FilterBook` is the one place the Player/Director split is decided: players
  never receive Director-only parts, chapters, pages or blocks, creature
  `stats`/`note`, or problem chapters. Director = `bookViewerIsDirector` (owner
  or dm_only-granted). The response is `Cache-Control: private, no-store`.
- `book/` sits outside `data/` because `SystemDataAPI` serves `data/` raw; the
  book must always pass through `FilterBook`.
- A category with `"director": true` is the data side of a Director-only
  chapter: `hiddenFromViewer` answers 404 below Director on `SystemDataAPI`,
  `CategoryList`, `ItemDetail` and `TooltipAPI`, and `Index`, `SearchAPI` and
  quick search omit it. Those answers are `Cache-Control: private`.
- Theme values become CSS custom properties, so they are pattern-checked (hex
  colours, plain font lists; `heading-font`, `body-font`, `ui-font`); `widget`
  blocks may name only the manifest's own widgets. A `contents` block carries
  only a title; the reader lists the chapters it received. A book's `look`,
  theme and fonts always apply; the site's Customize settings do not override.
- Rules-index chapters (`book_index.go`): a chapter file with `index:` names a
  manifest category; `buildIndexChapter` makes one page per `group` value (or
  A-Z pages of `per-page`), each with one `index` block naming its slice.
  `BookIndexAPI` (`.../book/index/:cat`) loads entries lazily, serves only a
  slice a page of the viewer's own filtered book shows, and drops `gm_only`
  fields for players. `BookFindAPI` (`.../book/find?q=`) searches those chapters
  (written pages are searched in the browser). The find index is cached per book,
  data-file version and viewer kind, at most 32 (`maxBookFindIndexes`); a failed
  build is not cached. Parsed data files are cached by path, size and mtime.
  Generated chapters are not editable (`BookChapterEntry.Generated`) and export
  as written.
- The reader also takes the book in `data-book-json` (AI import review): it
  fills its box (`rb-inline`), has no search or Edit, keeps no place and answers
  only keys pressed in it.

### Rulebook editor (`book_edit_*.go`, `book_editor.templ`)
Directors (owner or a member with a Director grant, `cc.CanAuthorDmOnly()`,
checked by `bookEditorAllowed` in every editor handler including the page) edit
their campaign's copy at `.../systems/:mod/book/edit`. Package files are never
written; a campaign's edition is the package book plus rows in
`campaign_book_pages` and `campaign_book_chapters`, merged on every read.

- `ApplyBookEdits` (`book_edit_service.go`) is the merge and runs in `BookAPI`
  before `FilterBook`, so a Director flag on a campaign page or block is
  honoured. A copy replaces the package page at its 0-based index; own pages
  follow the package pages; a copy past the last package page is kept after
  them; house-rules chapters (`house_` ids, which no package id can match) form
  a last "House rules" part. Edits for a chapter the package no longer lists, or
  that failed to load, are ignored.
- Page states: `package` (no row), `edited` (copy whose `base_hash` equals the
  package page's hash), `changed` (hash differs or the package page is gone),
  `mine` (own page). The hash is sha256 of the authored page JSON
  (`hashBookPage`). Re-saving a copy keeps its old hash, so only "Keep mine"
  settles a changed page.
- Pages are stored as authored JSON (`authoredPage`, keys identical to the YAML)
  and re-checked on every read; one that no longer validates becomes a `problem`
  block Directors can read. Request pages go through the package decoder
  (`decodeBookBytes`, unknown keys are errors) and `buildBookPage`, capped at the
  book's 1 MB file limit. An unwritten text block is stored and shows nothing.
- Limits: 200 own pages per chapter, 50 house chapters, 200 chapters in the
  merged book. A house chapter keeps at least one page.
- `WriteHouseChapter` writes a whole house chapter from a `HouseChapterDraft`
  (chapter-file YAML checked by `ParseHouseChapterDraft`, as the AI tool sends
  it) in one repository transaction: a new chapter, or one whose pages the draft
  replaces. `HouseChapterPreview` is the draft as a one-chapter `Book`;
  `HouseChapterYAML` writes a chapter back in that format, in the Director's or
  players' view.
- `UpdateBookChapterInput` is a partial update (`patch.Field`): absent keeps,
  explicit null clears only the intro.
- The service takes a `*BookPackage` (from `LoadBookPackage`) so it never
  touches disk or Echo; `BookEditRepository` owns the SQL, scoped by campaign
  and system.
- Export is a zip of package-format YAML (`book/book.yaml`,
  `book/chapters/*.yaml`) with the edition merged in; house chapters are written
  as `house-<slug>` (unique against package ids) in an appended "House rules"
  part. A package chapter that failed to load has no authored form and is left
  out. Glossary files live in `data/` and are not included.
- The editor widget is `static/js/widgets/rulebook_editor.js` (from
  `pluginBodyScripts`), mounted on `data-widget="rulebook-editor"`.

## Routes (shared handler)

`handler.go`; routes in `routes.go`, behind campaign access and the system's
addon check. Paths are under `/campaigns/:cid/systems/:mid`.

| Method | Path | Handler | Description |
|--------|------|---------|-------------|
| GET | `` | Index | Landing page: category cards (or book / front page) |
| GET | `/:cat` | CategoryList | Items in a category |
| GET | `/:cat/:item` | ItemDetail | Full reference page |
| GET | `/:cat/:item/tooltip` | TooltipAPI | HTML tooltip fragment |
| GET | `/search` | SearchAPI | JSON search results |

### Custom game system upload
Campaign owners upload a ZIP (manifest.json + data/*.json):
- Stored under `media/modules/<campaignID>/`, ID auto-prefixed `custom-`;
  bypasses the addon check for the uploading campaign.
- Data only: a ZIP with any `.js` file, or a manifest declaring `widgets` or
  `text_renderers`, is refused (`errCustomSystemScripts`). Scripts are never
  served or injected for a custom system, even one uploaded earlier; only
  installed packages (`Dir(id)` non-empty) serve scripts.
- At most 200 files and 20 MB of data in total, counted from the bytes read.

## Character field pick lists (`character_choices.go`)

`GET /campaigns/:cid/character-choices/:fieldKey` (Player+) returns
`{fieldKey, systemId, systemName, choices:[{slug,name,summary,source,description?,properties?}]}`
for the campaign's active systems (custom upload first, then enabled built-ins).
The file is the manifest field's `choices` (a data file base name) when a preset
declares one, else the field key's plural (`ancestry` -> `data/ancestries.json`).
Entries may use `slug` or `id`; summaries are markup-stripped. The stored field
value stays the entry's NAME (so Foundry pulls keep working); free text is
always allowed.

`RegisterChoiceSource(func(ctx, campaignID, fieldKey) ([]Choice, error))` appends
entries after the package's own (e.g. campaign-made ones, `Source: "campaign"`);
a failing source is logged and skipped. The handler marks the context with
`WithChoiceViewer(ctx, cc.CanAuthorDmOnly())`; a source reads it with
`ChoiceViewerIsDirector`; an unmarked context is a player's.
`CreatorPlan(ctx, campaignID)` (`character_creator.go`) lists the character
preset's text fields that have entries (preset order, at most 12) for the hero
creator, honouring `WithChoiceViewer`.

## Campaign system entries (`system_entries_*.go`)

A campaign adds its own pick-list entries (ancestry, kit, culture, career,
class, race...) in `campaign_system_entries`, apart from package data so a
package update never touches them. `SystemEntryService` (no Echo types) is
registered as a choice source (`RegisterSystemEntryChoices`), so the picker
shows them with `Source: "campaign"` after the package's.

- Directors (owner or co-Director, `cc.CanAuthorDmOnly()`) write; the handler
  states the caller through `EntryActor` and the service refuses every other
  write except a player's own entry below. The route group is Player+ because
  reading is open; a role middleware cannot express the co-Director grant.
- Player-made entries: a Director gives one player permission to write one entry
  for a list (`EntryGrant`, table `campaign_entry_grants`, with a points
  `budget`). Creating spends it (claimed before the insert, so two saves cannot
  both use it); granting again renews it. The entry is `status` `draft`, or
  `sent` once handed in; its `*_points` properties are held to the budget
  (`holdBudget`); it is kept to a character only when the player plays it, else
  `directors`; the player never sets visibility or the note. Until a Director
  sets `accepted`, `visible` shows it to its writer and Directors only. The
  writer edits while it is a draft and the grant stands; a Director hands it
  back (`draft` + `reviewNote`) or accepts it, choosing who sees it. `CanMake`
  feeds `ChoiceList.canMake` and `CreatorStep.canMake` through
  `RegisterMakeOwnCheck`; a writer's own choices carry `status`, `mine`,
  `entryId`.
- `field_key` must be a `string` field of a `category: "character"` entity
  preset in the campaign's active manifest. Entries are keyed by that manifest's
  id, so they do not show under another system. Name is unique per field
  (case-insensitive); the slug is derived from the name once and never changes.
  `properties` holds strings, numbers and booleans plus up to 6 lists of named
  items shaped like a package entry's (`name`, optional whole-number `cost`
  0-20, optional plain-text `description`; `validateEntryList`), so a homebrew
  ancestry's traits are bought in the hero creator like a packaged one's; all
  size-capped. `description` goes through `sanitize.HTML`.
- Visibility `everyone`, `directors` or `character`. A `character` entry names a
  character page (`for_entity_id`) and is a penciled option for one player:
  Directors and whoever plays that page see it, with `forName` set so the picker
  can mark it a draft. Who plays a page comes from `EntryCharacters`
  (`WithEntryCharacters`, implemented in `app/entry_characters_adapter.go`);
  without it, or when the page is gone or unclaimed, the entry stays with
  Directors. Players never receive `directors` entries or another player's
  `character` ones, and all text they receive has `data-secret` spans stripped
  (`sanitize.StripSecretsHTML`): the pick list, JSON list and lookup by name,
  all through `visible`. Directors see everything. The pick list learns the
  reader from `WithChoiceViewer` and `WithChoiceViewerUser`; an unmarked
  context is a player with no account.
- Deleting an entry never touches characters: they store the name string.
- API (`/campaigns/:id/system-entries`, Player+; writes need Director in the
  service): `GET ?fieldKey=` (Directors see all, others what `visible` allows),
  `POST`, `PUT /:entryId` (`UpdateSystemEntryInput`: absent preserves, null
  clears, value replaces; null name, visibility or status is refused),
  `DELETE /:entryId`; `GET /grants` (all for Directors, own otherwise),
  `POST /grants`, `DELETE /grants/:grantId`.
- The Foundry module reads the player view through syncapi
  `GET /api/v1/campaigns/:id/system-entries`, which answers `everyone` entries
  only. AI Import reaches the service through the `system-entry` record kind
  (`ai_workspace/records/system_entry.go`).

Client: `static/js/widgets/choice_picker.js` defines
`Chronicle.pickChoice({campaignId, fieldKey, anchorEl, current, label, entityId, save, choices})`
and `Chronicle.fetchChoices`. The attributes widget uses it with `save:false`; a
system widget can pass `entityId` to save the pick through
`PUT .../entities/:eid/fields` with `{"fields_patch": {key: value}}` (merge,
Scribe+).

## Operator diagnostics (`operator_diag*.go`)

The admin-facing, read-only diagnostic catalog the AI assistant chooses from
(`GET /admin/diagnostics?name=...`). Add one by appending a `Diagnostic{}` to
`diagnosticCatalog()`; the renderer, route and secret redaction are unchanged.
Rules, because a diagnostic that answers confidently and wrongly is worse than
none:

1. Cross-layer state arrives through an injected provider, never an import. This
   package must not import a plugin; the app layer implements the provider
   interface and wires it in `RegisterRoutes` (`SetInstalledPackagesProvider`,
   `SetEntityDiagProvider`, `SetCampaignDiagProvider`, ...).
   `internal/app/operator_diag_wiring_test.go` fails CI when a declared setter is
   never called: an unwired provider would report "provider not wired" forever,
   which reads like an answer.
2. Degrade loudly. A read that did not happen must never render like a read that
   returned nothing ("no addon rows" vs "nobody could read the addon table");
   tests assert the difference.
3. Never mirror another plugin's internal logic; export a trace from the owner.

## Dependencies

- **Uses:** nothing at runtime for the framework (read-only, self-contained).
  Exceptions: the Rulebook edits (`book_edit_repository.go`) read and write the
  database; diagnostics use injected providers plus `internal/hostinfo` and
  `internal/templates/layouts`.
- **Used by:** entity pages (@mention tooltips), campaign addon settings, the
  addon registry.
