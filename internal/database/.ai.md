# Database Package

## Purpose

Provides database connectivity (MariaDB, Redis), schema migration management,
plugin health tracking, and startup health checks. This is infrastructure code
used by all plugins — it does not own any business logic.

## Files

| File | Purpose |
|------|---------|
| `mariadb.go` | MariaDB connection pool setup (`NewMariaDB`) with DSN config; the `DB_TLS_MODE` env var is mapped to the driver's TLS parameter in `internal/config` |
| `redis.go` | Redis client setup (`NewRedis`) with connection config |
| `migrate.go` | Core migration runner using golang-migrate. Auto-runs `m.Up()` on startup. Fails fast on dirty DB state (no auto-force-retry — recovery is an explicit operator action, per ADR-045) |

## Plugin migration safety (ADR-050)

`plugin_migration_safety.go` guards against one failure mode:
`execPluginMigration` splits a migration on semicolons, runs it statement by
statement on a plain `*sql.DB`, and writes the `plugin_schema_versions` row only
after the **last** statement succeeds. A migration that fails on its second
statement leaves the first statement's effect in the database with **no
record that anything happened** — the next boot would replay from statement
one and die on "duplicate column name", because most plugin ALTERs are not
idempotent, degrading the plugin forever.

**It is not a transaction and does not pretend to be one.** MariaDB has no
transactional DDL: every CREATE / ALTER / DROP / RENAME commits implicitly. Nothing
here undoes a statement that already ran, and the error text says so. What it
actually buys:

1. **Pre-flight applicability check.** Before the first statement executes, every
   statement is validated against the schema catalogue *as it will stand at that
   point in the migration* — the simulation moves forward, so the ordinary
   CREATE-then-ALTER shape is not falsely refused. If any statement cannot succeed,
   the migration aborts having executed **nothing**: half-applied-and-unrecoverable
   becomes nothing-applied-and-actionable. Table granularity, by design — it catches
   the failures that produce unrecoverable states (missing / duplicate / renamed
   tables), not every possible SQL error.
2. **Partial-progress recording** in the runtime table `plugin_migration_progress`
   (created by the runner, not by a migration — it must exist before any plugin
   migration runs). The count of statements that DID apply is written before the
   error returns, so the next boot resumes after them rather than replaying a
   non-idempotent ALTER. Keyed by a **sha256 of the migration text** and honoured
   only on a byte-identical match: migrations are immutable (ADR-044/045) so this
   should never diverge, but a resume that skipped the *wrong* statements would be
   far worse than the crash-loop it replaces, so it is checked, not assumed.

**Every uncertain answer degrades to the pre-existing behaviour.** The pre-flight
**fails open** when `information_schema` cannot be read — refusing every plugin
migration over a metadata hiccup is worse than the bug — and an unmatched or absent
progress row replays from zero. A pre-flight that falsely aborts a real migration is
the one outcome worse than the original defect, which is why
`TestFreshDatabase_EveryPluginSchemaApplies` still passing is load-bearing evidence
and not incidental.

No CI check for non-idempotent plugin DDL exists; ADR-050 records why.

## Fresh-DB migration replay

CI never migrated an empty database until this existed: `tools/restore-drill.sh`
loads a dump of an already-migrated one, and every integration test assumes
`make migrate-up` already ran — so a migration that only breaks on a truly
fresh install could ship unnoticed.

`make test-freshdb` / `cmd/server/freshdb_migration_test.go` replay the real
bootstrap — core migrations, then every plugin's — against genuinely empty MariaDB
schemas: one from zero, one from the pre-consolidation shape. Wired into CI as its own
`Fresh-DB Migration Replay` job, which **greps for PASS on each named test so a SKIP
fails the job**. That rule is the actual guard: a silent skip on a DB-less runner is
exactly the shape that hid the original defect. The three DB-backed
`TestPluginMigration_*` recovery regressions run in the same job and are named in the
same assertion.

Any change to `plugin_schema.go`, `plugin_migration_safety.go`, or any plugin's
migration set must keep both replays green.

## The calendar clean slate empties two tables instead of dropping them

`calendar/019_calv5_clean_slate` (PR #595) drops the old calendar's tables but
only **empties** `calendars` and `calendar_events`. Three foreign keys in other
plugins point at them (`sessions/001` → `calendars`, `timeline/001` →
`calendars` and `calendar_events`). On a fresh install the calendar plugin's
migrations run first, so if 019 dropped the two tables, those later
`CREATE TABLE` statements would fail (errno 150). The first version of 019 did
drop them, and the fresh-DB replay caught it: both plugins died at version 0.
`internal/plugins/calendar/clean_slate_test.go` guards this. It derives the
protected set from the sibling plugins' SQL, so a later migration that drops
one of those foreign keys releases the table without editing the test. 019,
`timeline/002` and `sessions/006` are one-way; see `docs/deployment.md` §6.

## Startup Health Check System

`healthcheck.go` implements a multi-layer validation system that runs after
migrations but before the server accepts traffic. If any check fails, the
server exits with `os.Exit(1)`.

### Check Sequence

1. **Migration Version** (`checkMigrationVersion`) — Queries `schema_migrations`
   table to verify the DB is at the expected version (`ExpectedCoreMigrationVersion`
   in `migrate_state.go`). Detects dirty state and
   logs instructions to run `make migrate-down` then `make migrate-up`.

2. **Critical Columns** (`checkCriticalColumns`) — Queries `information_schema.COLUMNS`
   for a configurable map of required table/column pairs. Catches schema drift
   from failed or partially-applied migrations.

3. **DB Connectivity** (`checkDBHealth`) — Pings the database with a 5-second
   timeout. Reports connection pool stats (open, in-use, idle) and warns when
   pool utilization exceeds 80%.

4. **Security Audit** (`checkSecurity`) — Detects:
   - Weak/default database passwords in production (< 12 chars or common patterns)
   - HTTP BaseURL in production (CSRF cookie vulnerability)
   - Overprivileged DB user grants (SUPER, FILE, PROCESS)
   - World-writable `schema_migrations` table (prevents attacker-side injection)

### Pre-Migration Backup

`MigrateWithBackup` calls `PreMigrationBackup` when a core migration is pending;
`cmd/server/main.go` calls it again before plugin migrations when some are
pending and no snapshot was taken this boot.
- Executes `mysqldump` with gzip compression into the backup directory
  (default `./backups`)
- Also snapshots the media directory and Redis when configured
- Writes a manifest with the sha256 and size of each artifact
- Auto-rotates old backups based on the configured retention (default: 7 days)
- Skips with a warning if `mysqldump` is not available, unless
  `BACKUP_REQUIRED=1`; with that set (default is off), a missing `mysqldump`
  or any failed snapshot aborts the boot

### Configuration

`HealthCheckConfig` struct fields:
- `ExpectedMigrationVersion` — Target migration version to validate against
- `CriticalColumns` — `map[string][]string` of table→column pairs to verify
- `DBHost`, `DBPort`, `DBUser`, `DBPassword`, `DBName` — For backup and security checks
- `BaseURL`, `Environment` — For HTTPS and production security checks
- `BackupDir`, `BackupRetentionDays` — Backup storage configuration

### Integration

Wired in `cmd/server/main.go`: `MigrateWithBackup` (core migrations, with backup),
`RunStartupHealthChecks` (config from `app.StartupHealthCheckConfig`), then the
plugin backup check and `RunPluginMigrations`.

### Cross-references for the production safety system

`cordinator/decisions/2026-05-26-chronicle-production-safety-system.md` is the canonical rubric for this system — it documents the three startup layers, the smoke-test extension pattern (e.g. `campaigns.ScanSmokeTest()` for column-vs-struct drift), the "when does a change need boot verification?" decision tree, and the docker-unavailable substitute pattern (`wiring intact → no symbol leakage → clean binary → reaches DB layer`, established by PR #342).

`.ai/conventions.md` ("When a PR needs boot verification") applies that rubric: a change that touches DB-scan code, plugin smoke-test registrations, migrations, `HealthCheckConfig.CriticalColumns` or `cmd/server/main.go` wiring needs boot verification before merge. Sandboxes without Docker use the substitute pattern and leave the runtime check to the operator.

## DB TLS Support

`NewMariaDB` reads the `DB_TLS_MODE` environment variable to configure TLS on the
MySQL DSN. Supported values: `false` (disabled, default), `true`, `skip-verify`,
`preferred`. The startup health check warns when TLS is disabled in production
environments.

- **Uses:** `database/sql`, `go-sql-driver/mysql`, `golang-migrate/migrate`
