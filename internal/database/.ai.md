# Database Package

## Purpose

Database connectivity (MariaDB, Redis), schema migrations, plugin health
tracking and startup health checks. Infrastructure for all plugins; no business
logic.

## Files

| File | Purpose |
|------|---------|

| `redis.go` | Redis client setup (`NewRedis`) with connection config |
| `migrate.go` | Core migration runner using golang-migrate. Runs `m.Up()` on startup. Fails fast on dirty state; recovery is an explicit operator action (ADR-045) |

## Plugin migration safety (ADR-050)

`execPluginMigration` splits a migration on semicolons, runs it statement by
statement on a plain `*sql.DB`, and writes the `plugin_schema_versions` row only
after the last statement succeeds. A failure on statement two would leave
statement one applied with no record, and the next boot would replay from one and
die on "duplicate column name" (most plugin ALTERs are not idempotent), degrading
the plugin permanently. `plugin_migration_safety.go` guards that case.

**It is not a transaction.** MariaDB has no transactional DDL: every CREATE,
ALTER, DROP and RENAME commits implicitly, and nothing here undoes an applied
statement. It adds:

1. **Pre-flight applicability check.** Before the first statement runs, each
   statement is validated against the schema catalogue as it will stand at that
   point (the simulation moves forward, so CREATE-then-ALTER is not falsely
   refused). If any statement cannot succeed the migration aborts having executed
   nothing. Table granularity by design: it catches missing, duplicate and
   renamed tables, not every SQL error.
2. **Partial-progress recording** in `plugin_migration_progress`, created by the
   runner, not a migration, because it must exist before any plugin migration
   runs. The count of applied statements is written before the error returns, so
   the next boot resumes after them. It is keyed by the sha256 of the migration
   text and honoured only on a byte-identical match; a resume that skipped the
   wrong statements would be worse than the crash-loop it replaces.

**Uncertainty degrades to the plain runner.** The pre-flight fails open when
`information_schema` cannot be read, and an unmatched or absent progress row
replays from zero. A pre-flight that falsely aborts a real migration is the worst
outcome, so `TestFreshDatabase_EveryPluginSchemaApplies` passing is load-bearing.
No CI check for non-idempotent plugin DDL exists; ADR-050 records why.

## Fresh-DB migration replay

`tools/restore-drill.sh` loads a dump of an already-migrated database and every
integration test assumes `make migrate-up` ran, so only a fresh replay catches a
migration that breaks on a new install. `make test-freshdb` /
`cmd/server/freshdb_migration_test.go` replay the real bootstrap (core, then every
plugin's migrations) against empty MariaDB schemas: `TestFreshDatabase_EveryPluginSchemaApplies`
from zero and `TestUpgradeDatabase_FoundryConsolidationStillRuns` from the
pre-consolidation shape. CI runs them as the `Fresh-DB Migration Replay` job,
which greps for PASS on each named test so a SKIP fails the job (a silent skip on
a DB-less runner is the failure to prevent). The DB-backed
`TestPluginMigration_*` recovery tests run in the same job and are named in the
same assertion.

Any change to `plugin_schema.go`, `plugin_migration_safety.go` or a plugin's
migration set must keep both replays green.

## Calendar clean slate empties two tables

`calendar/019_calv5_clean_slate` drops the old calendar's tables but only empties
`calendars` and `calendar_events`: foreign keys in other plugins point at them
(`sessions/001` to `calendars`; `timeline/001` to `calendars` and
`calendar_events`). The calendar plugin's migrations run first on a fresh
install, so dropping those tables would make the later `CREATE TABLE`s fail
(errno 150). `internal/plugins/calendar/clean_slate_test.go` guards this and
derives the protected set from the sibling plugins' SQL, so a later migration
that drops one of those foreign keys releases the table without editing the test.
019, `timeline/002` and `sessions/006` are one-way; see `docs/deployment.md` §6.

## Startup Health Check System

`healthcheck.go` runs after migrations and before the server accepts traffic; a
failed check exits with `os.Exit(1)`.

### Check Sequence

1. **Migration Version** (`checkMigrationVersion`) — Queries `schema_migrations`
   table to verify the DB is at the expected version (`ExpectedCoreMigrationVersion`
   in `migrate_state.go`). Detects dirty state and
   logs recovery instructions.

2. **Critical Columns** (`checkCriticalColumns`) — Queries `information_schema.COLUMNS`
   for a configurable map of required table/column pairs. Catches schema drift
   from failed or partially-applied migrations.

3. **DB Connectivity** (`checkDBHealth`) — Pings the database with a 5-second
   timeout. Reports connection pool stats (open, in-use, idle) and warns when
   pool utilization exceeds 80%.

4. **Security audit** (`checkSecurity`) — Detects:
   - Weak/default database passwords in production (< 12 chars or common patterns)
   - HTTP BaseURL in production (CSRF cookie vulnerability)
   - Overprivileged DB user grants (SUPER, FILE, PROCESS)
   - World-writable `schema_migrations` table (prevents attacker-side injection)

### Pre-Migration Backup

`MigrateWithBackup` calls `PreMigrationBackup` when a core migration is pending;
`cmd/server/main.go` calls it again before plugin migrations when some are
pending and no snapshot was taken this boot.
- Executes `mysqldump` with gzip compression into the backup directory
  (default `./backups`)
- Also snapshots the media directory and Redis when configured
- Writes a manifest with the sha256 and size of each artifact
- Auto-rotates old backups based on the configured retention (default: 7 days)
- Skips with a warning if `mysqldump` is not available, unless
  `BACKUP_REQUIRED=1`; with that set (default is off), a missing `mysqldump`
  or any failed snapshot aborts the boot

### Configuration

`HealthCheckConfig` struct fields:
- `ExpectedMigrationVersion` — Target migration version to validate against
- `CriticalColumns` — `map[string][]string` of table→column pairs to verify
- `DBHost`, `DBPort`, `DBUser`, `DBPassword`, `DBName` — For backup and security checks
- `BaseURL`, `Environment` — For HTTPS and production security checks
- `BackupDir`, `BackupRetentionDays` — Backup storage configuration

### Integration

Wired in `cmd/server/main.go`: `MigrateWithBackup` (core migrations, with backup),
`RunStartupHealthChecks` (config from `app.StartupHealthCheckConfig`), then the
plugin backup check and `RunPluginMigrations`.

### Boot verification

`.ai/conventions.md` ("When a PR needs boot verification") says a change touching
DB-scan code, plugin smoke-test registrations (e.g. `campaigns.ScanSmokeTest()`
for column-vs-struct drift), migrations, `HealthCheckConfig.CriticalColumns` or
`cmd/server/main.go` wiring needs boot verification before merge. Sandboxes
without Docker check that wiring is intact, no symbol leaks, the binary is clean
and it reaches the DB layer, and leave the runtime check to the operator.

## DB TLS Support

`NewMariaDB` reads the `DB_TLS_MODE` environment variable to configure TLS on the
MySQL DSN. Supported values: `false` (disabled, default), `true`, `skip-verify`,
`preferred`. The startup health check warns when TLS is disabled in production
environments.

- **Uses:** `database/sql`, `go-sql-driver/mysql`, `golang-migrate/migrate`
- **Used by:** `cmd/server/main.go`, all plugins (via `sql.DB` and `redis.Client`)
